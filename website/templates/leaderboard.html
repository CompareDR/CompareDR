How to read this ranking

Total = 30% Responsiveness + 30% Evidence + 10% Reasoning + 10% Synthesis + 20% Readability. Queries receive equal weight. Scores combine pointwise audits with ordinal pairwise comparisons, where available. A score is not a percentage of factual accuracy. Bold values identify column leaders, not statistically significant differences.

The comparison pool is part of the protocol: adding a system can change existing systems' pairwise scores. A future expanded leaderboard must be labeled as a new cohort snapshot and consistently aggregated, not appended to this table using an independently computed score. Full scoring explanation ↗

PARTICIPATE / NEW SYSTEMS

Bring your system to CompareDR

01 / GENERATE

Answer the frozen tasks

Run your model and research harness on all 40 original queries. Preserve constraints, report text, and citation links; record generation settings and dates.

02 / PACKAGE

Provide reproducible inputs

Include one complete report per query, query IDs, file hashes, model and harness names, and any failed tasks. Do not include credentials or private session data.

03 / EVALUATE

Use the same comparison protocol

Maintainers validate inputs, bind the new cohort, and run or coordinate judging and aggregation. Accepted results are added with their cohort and evaluation settings.

Submit on GitHub ↗Download submission template ↗Package format & validation ↗
Required submission format

One ZIP per system: submission.json records the model, harness, reasoning setting, tools/budgets, generation dates, and permission scope. Place 40 complete UTF-8 Markdown reports in reports/<query_id>.md, preserving original citations. The template already lists every query ID and includes queries.json with the original tasks, without answer keys.

Run python validate.py . --fill-hashes, then python validate.py .. Attach the ZIP or an accessible package link in the GitHub form and paste the check result. Declare failed tasks explicitly; do not omit them. A format pass is not a quality score or automatic acceptance.

Submission intake uses a GitHub issue form. There is no automatic evaluation or score acceptance. The current evaluator CLI reruns the two bundled cohorts; arbitrary new-system intake still requires maintainer integration.

# Prometheus 的高流失率会造成什么影响，有什么系统的方案可以解决？各家云厂商有没有现有方案

## Prometheus 高流失率的定义与成因

### churn rate 的精确定义与度量方式

#### 定义：churn rate 与 cardinality、active series 的关系

在时序数据库语境下，**churn rate（流失率）** 是指旧时间序列停止接收新样本、新时间序列因标签值变化而替代旧序列的速率。valyala 在 "Prometheus storage: technical terms for humans" 中给出的定义为："Active time series becomes inactive if it stops receiving new samples. New time series can substitute old time series on label value change… The rate at which old time series are substituted by new time series is called churn rate"（[valyala Medium](https://valyala.medium.com/prometheus-storage-technical-terms-for-humans-4ab4de6c3d48)）。

churn rate 与 **cardinality（基数）** 和 **active time series（活跃时间序列）** 之间存在明确的数学关系：

- **Cardinality** 是某一时刻系统中唯一时间序列的总数，是一个**瞬时概念**。
- **Active time series** 是最近一段时间内（Prometheus 默认 head block 2 小时窗口内）接收过新样本的时间序列，由 `prometheus_tsdb_head_series` 指标反映。
- **Churn rate** 描述的是 active series 被新 series 替代的**速率**。高 churn rate 会推高时间窗口内的累计基数——即使瞬时基数不变，随着时间窗口拉长，窗口内出现过的唯一序列数只会单调递增。

Chronosphere 的博客对此有精确阐述："A workload with low point-in-time cardinality but high churn will tend to suffer from poor query performance the farther back in time users try to query, even more so than a workload that has high point-in-time cardinality, but low churn"（[Chronosphere](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。这意味着：**低瞬时基数 + 高流失率** 的场景在长时间窗口查询下性能可能比 **高瞬时基数 + 低流失率** 更差，因为查询需要扫描窗口内所有曾经存在过的序列。

#### Prometheus 原生指标：`prometheus_tsdb_head_series_created_total` 与 `scrape_series_added`

Prometheus 提供了两个不同层级的指标来间接观测 churn：

| 指标 | 层级 | 统计口径 | 适用场景 |
|------|------|----------|----------|
| `prometheus_tsdb_head_series_created_total` | TSDB 级（集群级） | 每次有新时间序列被创建并写入 head block 时递增 | 观测整体 churn rate 趋势 |
| `scrape_series_added` | 抓取级（per-target） | 每次 scrape 中，某 target 的 series 首次出现在 scrape cache 中时计数 | 定位具体哪个 job/target 是 churn 来源 |

**`prometheus_tsdb_head_series_created_total`** 是 TSDB head block 级别的计数器，每当一个全新的时间序列（metric name + label set 组合）被创建时递增。用以下 PromQL 计算集群级 churn rate：

```promql
rate(prometheus_tsdb_head_series_created_total[5m])
```

该查询返回每秒新创建的时间序列数，是衡量整体 churn 趋势的权威指标（[valyala Medium](https://valyala.medium.com/prometheus-storage-technical-terms-for-humans-4ab4de6c3d48)）。

**`scrape_series_added`** 自 Prometheus 2.10 引入，在每次 scrape 时统计该 target 新增到 scrape cache 的 series 数。用以下 PromQL 定位 per-target 级别的 churn 来源：

```promql
sum(sum_over_time(scrape_series_added[5m])) by (job)
```

Robust Perception 的博客指出该指标的局限性："Due to various technicalities it may under or over-report"——某些类型的失败 scrape 也可能创建 series（即使样本未被实际摄入）；Prometheus 重启或 scrape 配置变更会清除 scrape cache 导致计数重置；`up` 和 `scrape_*` 指标本身不计入此指标（[Robust Perception](https://www.robustperception.io/finding-churning-targets-in-prometheus-with-scrape_series_added)）。因此，`scrape_series_added` 更适合**快速定位 churn 来源**，而 `prometheus_tsdb_head_series_created_total` 更适合**精确度量 TSDB 级别的 churn 趋势**。

#### VictoriaMetrics 的 `vm_new_timeseries_created_total` 度量方法

VictoriaMetrics 使用 `vm_new_timeseries_created_total` 指标来度量 churn rate，其统计口径与 Prometheus 原生指标有本质区别。该指标记录的是**被判定为"新"的时间序列数量**——判定逻辑是：当一个时间序列到达时，先查询内存缓存，再查询倒排索引（indexdb），如果两者都未命中，则被视为新序列并递增计数器（[VictoriaMetrics Blog](https://victoriametrics.com/blog/churn-rate-in-victoriametrics/)）。

用以下 MetricsQL 查询 churn rate：

```metricsql
sum(rate(vm_new_timeseries_created_total))
```

或查看 24 小时累计新增序列数：

```metricsql
sum(increase(vm_new_timeseries_created_total[24h]))
```

VictoriaMetrics 官方文档还指出，churn rate 越高，所需的计算资源越多，它直接影响 active time series 数量、缓存效率、查询性能和磁盘压缩效率（[VictoriaMetrics Docs](https://docs.victoriametrics.com/guides/understand-your-setup-size/)）。

#### "假性高 churn"：每日 indexdb 轮换导致的 churn 尖峰

一个关键现象是：**即使没有真正的新时间序列产生，也可能出现高 churn rate**。VictoriaMetrics 官方博客详细分析了这一根因（[VictoriaMetrics Blog](https://victoriametrics.com/blog/churn-rate-in-victoriametrics/)）：

VictoriaMetrics 的倒排索引（indexdb）每日轮换。系统通过 `prefillNextIndexDB` 机制在轮换前 1 小时预填充新索引，以避免午夜 churn 尖峰。然而，内存缓存有 TTL 限制——`cacheExpireDuration` 默认为 **30 分钟**。当数据摄入间隔超过 30 分钟时（如每小时生成一次 downsampling 数据），缓存会在下一次数据到达前过期。此时：

1. 数据不在缓存中（TTL 30 分钟已过期）
2. 数据不在预填充索引中（预填充仅在轮换前 1 小时启动，而每小时摄入的数据在午夜时距预填充窗口已过）
3. 数据在旧索引中，但查询按日期路由到新索引，无法命中

结果：所有时间序列在午夜被判定为"新序列"，产生虚假的 churn 尖峰。解决方案是调整 `cacheExpireDuration` 使其超过数据摄入间隔。

这一案例说明：**churn rate 指标本身可能产生误导**，需要结合摄入模式、缓存 TTL 和索引轮换机制综合判断。

#### 高 churn rate 的阈值

社区对"高 churn rate"的阈值没有统一标准，但有以下参考：

- **Alexandre Vazquez** 在容量规划指南中提出："an instance creating more than 100,000 new series per minute will" 面临性能退化风险，建议将此作为运维限制阈值（[Alexandre Vazquez](https://alexandre-vazquez.com/prometheus-scalability/)）。
- **VictoriaMetrics** 单节点版本官方文档列出可处理的 churn rate 为 "150+ million of new series per day"（约 173,000/秒），这是其架构设计上限而非推荐值（[VictoriaMetrics Docs](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/)）。
- **vmestimator**（VictoriaMetrics 2026 年发布的实时基数估算工具）中，churn rate 为 1 表示 100% 的活跃序列被替代；其示例告警阈值设为 10%——即 30 分钟窗口内超过 10% 的序列被新序列替代时触发告警（[vmestimator Blog](https://victoriametrics.com/blog/vmestimator-announcement/)）。
- **valyala** 指出 Prometheus 的高 cardinality 从几百万序列开始触发性能退化，而高 churn 会加速达到这一阈值（[valyala Medium](https://valyala.medium.com/prometheus-storage-technical-terms-for-humans-4ab4de6c3d48)）。

综合来看，**每分钟超过 10 万新序列创建** 是一个值得关注的运维阈值；**每秒超过 1000 新序列**（即 `rate(prometheus_tsdb_head_series_created_total[5m]) > 1000`）应触发告警并启动诊断。

#### 为什么高 churn 即使不增加瞬时基数也会带来问题

Prometheus 社区讨论揭示了一个关键机制：head block 保留最近 2 小时所有活跃时间序列的内存映射，inactive series 不会立即从内存中清除，而是驻留直到 2 小时窗口结束并被 compaction 刷入磁盘（[Google Groups](https://groups.google.com/g/prometheus-users/c/wRtG7zq6sZ4)）。这意味着高 churn 场景下，2h 窗口内累积的序列数远超瞬时基数，进而推高 head block 内存占用（详见 S2.1）、加剧倒排索引膨胀与 compaction 压力（详见 S2.2）、并放大长范围查询的序列扫描量（详见 S2.3）。

Chronosphere 的总结精准概括了这一问题的本质："as our window of time gets larger, the cardinality of our data will only ever increase"（[Chronosphere](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。churn rate 是连接瞬时基数与时间窗口基数的桥梁——它解释了为什么"看起来不高"的基数在长时间查询下会突然变得不可接受。

### 高流失率的典型成因：动态环境与高基数标签

Prometheus 高流失率（churn rate）的根因可归纳为四大类：Kubernetes 动态环境中的 Pod/Container 生命周期变化、短生命周期工作负载的标签组合爆炸、高基数标签的误用，以及存储引擎内部机制导致的"假性高 churn"。以下按成因逐一分析，并区分**良性 churn**（正常部署与弹性伸缩）与**恶性 churn**（指标反模式），以及各自对应的 churn 模式（持续型 vs 周期尖峰型）。

#### 1. Kubernetes 动态环境：Pod/Container 标签 churn

Kubernetes 是 Prometheus 高 churn 的最主要来源。在 K8s 环境中，`pod`、`container_id`、`pod_name` 等标签值随 Pod 创建和销毁持续变化，每次 Deployment 都会产生新的时间序列。

**`pod` / `pod_name` 标签**是最典型的 churn 贡献者。许多实践者将 Pod 名称作为指标标签，但每次 Deployment 都会创建具有唯一标识的新 Pod——即使本质上是同一服务的新版本。旧 Pod 的时间序列停止接收新样本后失效，新 Pod 的时间序列被创建，导致逻辑上的指标数据序列出现断裂。VictoriaMetrics 创始人 Aliaksandr Valialkin 指出，`pod_name` 标签值在每次 Kubernetes 部署后可能为大量时间序列发生变化，是 churn rate 升高的直接原因（[Valyala Medium](https://valyala.medium.com/prometheus-storage-technical-terms-for-humans-4ab4de6c3d48)）。

**量化影响**：一个三节点 Kubernetes 集群使用 Prometheus Operator 默认安装（含 kube-state-metrics、node-exporter、cAdvisor），仅默认组件就产生约 40,000 条活跃时间序列（[Horovits Medium](https://horovits.medium.com/how-to-fix-kubernetes-monitoring-f30c58722541)）。每次 Deployment 产生的新时间序列数量取决于该服务暴露的指标数与标签组合数——若一个服务暴露 100 个指标且每个指标带 `pod` 标签，则每次部署至少新增 100 条时间序列。

**HPA（Horizontal Pod Autoscaler）扩缩容**是持续型 churn 的典型来源。HPA 根据流量或资源压力自动扩缩 Pod 副本数，每次扩容创建新 Pod 即产生新时间序列，缩容后旧序列停止上报。Chronosphere 指出，HPA 配置的 Pod 每次扩缩都会引入少量 churn，属于"缓慢泄漏"型——持续产生新序列但速率相对稳定（[Chronosphere](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。

**`container_id` 标签**的 churn 贡献甚至大于 `pod_name`，因为容器重启（即使 Pod 未变）会产生新的 container ID。`namespace` 标签本身基数较低，通常不是 churn 的主要贡献者，但在多租户大规模集群中，频繁创建/删除 namespace 也会产生可观的序列增量。

**缓解策略**：使用 ReplicaSet 或 StatefulSet ID 替代 `pod_name` 作为标签，因为这些标识在 Pod 增删时保持不变。Valyala 认为这更像一种"hack"，理想方案是推动 Kubernetes 监控社区建立一致命名规范（[Horovits Medium](https://horovits.medium.com/how-to-fix-kubernetes-monitoring-f30c58722541)）。

#### 2. 短生命周期工作负载：CronJob、Serverless 与批处理

短生命周期工作负载的 churn 模式与长期运行服务有本质差异：长期运行服务以稳定速率产生少量 churn（主要来自部署），而短生命周期任务每次运行都产生全新的标签组合，运行结束后序列即失效。

**Kubernetes CronJob** 每次调度创建新的 Job 对象和 Pod，若指标中包含 `job_name` 或 `pod` 标签，则每次执行都产生新时间序列。对于每分钟调度的高频 CronJob，churn rate 可达每小时数百条新序列。社区通常使用 [PushGateway](https://github.com/prometheus/pushgateway) 处理短生命周期任务的指标暴露，但 PushGateway 本身不解决 churn 问题——它只是将指标推送到 Prometheus，标签组合仍然每次不同。

**Knative / AWS Lambda** 等 Serverless 平台的 churn 更为极端。每个函数实例在冷启动时创建，执行完毕后销毁，生命周期可能仅数秒至数分钟。若将函数实例 ID 或请求 ID 作为标签，则每次函数调用都产生新时间序列，churn rate 与请求速率成正比。

**批处理任务**（如 Spark Job、Argo Workflow）每次运行产生新的 executor Pod 标签组合，运行模式为**周期尖峰型 churn**——任务启动时序列数骤增，任务结束后序列失效但残留在 TSDB 中直到 retention 过期。

#### 3. 高基数标签误用：user_id、request_id、trace_id

高基数标签是同时推高 cardinality 和 churn rate 的最具破坏性的反模式。当 `user_id`、`request_id`、`trace_id`、`session_id` 等无界标识符直接作为 Prometheus 标签时，每个唯一值都会创建一条新时间序列。

**与 churn 的关系**：高基数标签不仅推高瞬时 cardinality，还同时产生极高 churn rate。以 `request_id` 为例，每个 HTTP 请求产生一条新序列，请求结束后该序列不再接收样本——这意味着 churn rate 等于请求速率。若应用每秒处理 10,000 个请求，则 churn rate 为 10,000 序列/秒。Rob Perception 指出，将 per-customer 标签用于拥有数百到数千客户的应用时，通常会导致 cardinality 爆炸（[Robust Perception](https://www.robustperception.io/cardinality-is-key)）。

**高基数 HTTP path 标签**是另一个常见反模式。若将原始 URL 路径作为标签值（如 `http_requests_total{path="/api/users/12345"}`），攻击者或正常用户通过请求大量随机路径即可强制应用创建海量时间序列。Cloudflare 在其大规模 Prometheus 实践中明确指出："永远不要接受来自不可信来源的标签值"（[Cloudflare Blog](https://blog.cloudflare.com/how-cloudflare-runs-prometheus-at-scale/)）。

**高基数标签与 churn 的叠加效应**：高基数标签同时推高 cardinality 和 churn rate，形成恶性循环——高 cardinality 消耗内存和索引资源，高 churn 使这些资源在 2 小时 head block 窗口内持续累积。Grafana 博客指出，`session_id`、`user_id`、`device_id` 等随机生成且无上限的标签值是导致 cardinality 爆炸的最常见原因（[Grafana Blog](https://grafana.com/blog/how-to-manage-high-cardinality-metrics-in-prometheus-and-kubernetes/)）。

**经验法则**：Robust Perception 建议，任何指标的标签基数不应超过 10（考虑增长余量），整个 Prometheus 实例中不超过 5 个指标可超过 100（[Robust Perception](https://www.robustperception.io/cardinality-is-key)）。

#### 4. 存储引擎内部机制导致的"假性高 churn"

VictoriaMetrics 的每日 indexdb 轮换与缓存 TTL 不匹配可能导致"假性高 churn"——即使没有真实的新时间序列产生，每日 0 点仍可能出现 churn 尖峰。该现象的根因分析、`prefillNextIndexDB` 机制与 `cacheExpireDuration` 调优方案详见 S1.1。

#### 5. 动态服务发现中的 instance 标签 churn

AWS EC2 Service Discovery 和 GCE Service Discovery 中，`instance` 标签默认使用实例的私有 IP 地址。当 EC2 实例被终止并替换（如 Auto Scaling 事件、Spot 实例回收）时，新实例获得不同的 IP 地址，导致 `instance` 标签值变化，产生新时间序列。

Prometheus 官方配置文档明确警告：OTLP 端点接收的属性变化可能导致时间序列 churn 并引发高内存使用（[Prometheus Configuration](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)）。在 AWS EC2 SD 场景中，实例替换频率取决于 Auto Scaling 组的配置和底层硬件事件——在大型集群中，每天可能有数十次实例替换，每次替换产生的新序列数等于该实例上运行的 exporter 暴露的指标数。

**GCE SD** 的情况类似，但 GCE 实例的 `instance` 标签默认使用实例名称，在实例重建时名称可能变化。

#### 6. 良性 churn 与恶性 churn 的区分

| 维度 | 良性 churn | 恶性 churn |
|------|-----------|-----------|
| **成因** | 正常 Deployment、HPA 扩缩容 | 高基数标签误用（user_id、request_id） |
| **churn 模式** | 持续型，速率与部署频率成正比 | 持续型或指数型，速率与请求速率成正比 |
| **可预测性** | 可预测，与发布节奏相关 | 不可预测，取决于外部输入 |
| **对系统影响** | 可控，序列数在 retention 内稳定 | 不可控，序列数无上限增长 |
| **典型场景** | 微服务滚动更新、HPA 弹性伸缩 | per-request ID label、per-UUID label |

Chronosphere 指出，最具破坏性的 churn 来自指标反模式——为每个请求创建唯一标签值的工作负载会产生最大量的 churn，导致系统稳定性问题（[Chronosphere](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。

#### 7. 社区应对：限制 per-instance label churn 的提案

GitHub issue #17109 提出了在 Prometheus 中限制 per-instance 标签随时间累积的 feature request，包括基于 `scrape_series_added` 阈值和滚动窗口总和两种方案。该提案的详细讨论、实现挑战与当前状态见 S3.1。

#### 8. 压测验证：Avalanche 工具

[prometheus-community/avalanche](https://github.com/prometheus-community/avalanche) 是 Prometheus 社区的负载测试工具，能够生成指标名称和唯一序列随时间变化的指标，专门用于模拟 series churn 场景。Avalanche 允许配置 churn rate 参数，帮助用户在受控环境中测试 Prometheus 对高 churn 的承受能力，验证 relabeling 策略和 `sample_limit` 等限制机制的有效性。

#### 9. Cloudflare 大规模实践中的 churn 治理

Cloudflare 运行 916 个 Prometheus 实例，总计约 49 亿条时间序列，平均每实例约 500 万条，最大实例达 3000 万条。Cloudflare 将 cardinality 爆炸列为首要挑战——某些指标突然添加大量不同标签值，创建海量时间序列，导致 Prometheus 内存耗尽崩溃（[Cloudflare Blog](https://blog.cloudflare.com/how-cloudflare-runs-prometheus-at-scale/)）。Cloudflare 的治理实践包括：严格审查新增标签、使用 relabeling 丢弃高基数标签、以及通过分片将负载分散到多个实例。

#### 小结

高流失率的成因可归纳为以下模式：

| 成因 | churn 模式 | 典型速率量级 | 可控性 |
|------|-----------|------------|--------|
| K8s Deployment（`pod` 标签） | 持续型，与发布频率成正比 | 每次部署 100–1000+ 序列 | 中（可用 ReplicaSet ID 替代） |
| HPA 扩缩容 | 持续型，缓慢泄漏 | 每次扩缩 10–100 序列 | 中（不可避免，但可治理） |
| CronJob / Serverless | 周期尖峰型 | 每次运行 10–1000 序列 | 中（可用 PushGateway + 聚合） |
| 高基数标签（user_id 等） | 持续型，与请求速率成正比 | 每秒数千至数万序列 | 高（应从源头禁止） |
| indexdb 轮换（假性） | 每日 0 点尖峰 | 取决于缓存 TTL 匹配 | 高（调整 cacheExpireDuration，见 S1.1） |
| EC2/GCE SD 实例替换 | 持续型，与实例生命周期成正比 | 每次替换 100–5000 序列 | 中（不可避免，但可量化） |

良性 churn（正常部署、弹性伸缩）是云原生环境的自然特征，通过标签治理和架构优化可将其控制在可管理范围内；恶性 churn（高基数标签误用）则必须从指标设计源头杜绝，否则任何存储引擎都无法承受无上限的序列增长。

## 高流失率对 Prometheus 系统的影响

### 内存消耗与 OOM 风险

Prometheus 的内存占用与 head block 机制紧密耦合，而高流失率（churn）正是通过放大 head block 中的序列数量来推高内存消耗的核心因素。本节聚焦内存机制本身，级联故障路径与 TCO 分析归 S2.4。

#### Head Block 机制与 churn 的内存放大效应

Prometheus TSDB 的 head block 是内存中的时序数据库，默认保留最近 1–3 小时的数据，每 2 小时将 head block 刷盘为持久 block。head block 中存储了该时间窗口内**所有活跃时间序列**的内存映射，包括序列的标签索引、倒排索引条目和样本数据 chunk。

高 churn 场景下，大量短生命周期时间序列（如 Kubernetes 中频繁创建销毁的 Pod 产生的 `pod`、`container_id` 标签值变化）在 2 小时窗口内持续累积。关键在于，**inactive series 不会立即从内存中清除**——当时间序列停止接收新样本后，它仍然驻留在 head block 的内存结构中，直到下一次 head GC（每 2 小时执行一次）才会被清理。Cloudflare 在其大规模 Prometheus 实践中明确指出："When time series disappear from applications and are no longer scraped, they still stay [in memory]"，直到 head GC 周期触发。GitHub issue #4115 也记录了这一行为：每 2 小时 head GC 执行时，所有 series 先从 head block 中移除，再在约 10 分钟内从 WAL 恢复，期间数据暂时不可用。

这意味着在高 churn 环境中，head block 中的序列数量并非仅由当前活跃序列数决定，而是由 **2 小时窗口内曾经活跃过的所有序列数**决定。即使瞬时基数不高，持续的高 churn 也会使 head block 不断膨胀。

#### 每活跃序列的 head 内存开销

社区对每序列 head 内存开销的估算存在多个参考值，差异主要来自标签数量和 chunk 填充程度：

| 来源 | 每序列估算 | 说明 |
|------|-----------|------|
| Robust Perception（Prometheus 2.20+） | ~3 KB | 综合标签、索引、chunk 开销的经验法则 |
| Reddit 社区讨论 | ~3–4 KiB | 与 Robust Perception 一致 |
| Coveo 实测 | ~8 KB | 含高基数 `id` 标签的极端场景 |
| Alexandre Vazquez | ~3–4 KB | head block 容量规划建议 |

Robust Perception 的详细分析给出了更细的拆解：每序列约 732B 基础开销 + 每对标签 32B + 每个唯一标签值 120B + 时序名称存储两次，再乘以 Go GC 的 2 倍系数。在此基础上，100 万活跃序列约需 2 GiB RAM（纯基数部分），加上 15s 采集间隔的摄入开销约 2.5 GiB，合计约 4.5 GiB。

**高 churn 场景的内存估算公式**：

```
head_memory ≈ (active_series_in_2h_window) × (3–8 KB) + ingestion_overhead
```

其中 `active_series_in_2h_window` 是 2 小时窗口内所有曾活跃的序列数，而非当前瞬时活跃数。在 churn 较高的 Kubernetes 环境中，这个值可能是瞬时基数的 2–5 倍。

#### Prometheus v2.19 memory-mapping 优化的效果与局限

Prometheus v2.19.0 引入了 full chunks memory-mapping 优化：当 head block 中的 chunk 被填满（120 个样本）后，将其刷到磁盘并仅保留文件索引和偏移量的内存引用，操作系统按需将 chunk 加载到内存。

根据 Grafana 官方博客的基准测试数据：

- **低 churn 场景**：内存降低 30–40%，因为大部分 chunk 能被填满 120 个样本后刷盘
- **高 churn 场景**：内存仅降低 10–20%，因为大量短生命周期序列的 chunk 永远无法填满 120 个样本，始终驻留内存

这一优化**不能根治**高 churn 的内存问题，原因有二：(1) 高 churn 下 chunk 填充率低，memory-mapping 的收益大幅缩水；(2) 当查询需要访问大量序列的近期数据时，操作系统仍需将 mmap 的 chunk 加载到物理内存中，实际 RSS 下降幅度小于理想值。

#### 典型 OOM 案例：Coveo 30Gi 内存限制被突破

Coveo 提供了一个高 churn 导致 OOM 的经典案例。其 Prometheus 环境配置了 30Gi 内存限制，但实际运行参数如下：

- 640 个 target，20,000 sample/second
- 1M 活跃序列（`sum(scrape_samples_scraped)`），5.5M 总序列
- 实际 RAM 占用达 40Gi，远超 30Gi 限制

根因分析显示，kubelet/cadvisor 暴露的容器指标中 `id` 标签具有高基数（116,525 个唯一值），且容器频繁轮换导致持续高 churn。Coveo 使用 `tsdb analyze` 工具离线分析 TSDB block，发现 `id` 标签是 churn 的主要贡献者。**丢弃 `id` 标签后，采样率降低 75%，内存占用从 40Gi 降至 8Gi，改善幅度达 375%**。

#### `prometheus_tsdb_head_series` 与 RAM 的关系

`prometheus_tsdb_head_series` 指标直接反映 head block 中的时间序列数量，是监控内存使用趋势的关键指标。Alexandre Vazquez 的容量规划指南建议：**head block 建议不超过 300 万活跃序列，并预留 50% headroom**。当 `prometheus_tsdb_head_series` 持续增长而非趋于平稳时，通常意味着 churn 速率高于序列淘汰速率，head block 正在膨胀。

PromCon 2019 演讲 "Containing your Cardinality" 提供了性能退化的量化参考：单个指标超过约 10 万序列时，查询开始明显变慢（`count(metric_a)` 在 10 万序列时约 1.5 秒，20 万序列时约 5 秒）；单个 Prometheus 可处理超过 1000 万序列，但启动时间可能超过 15 分钟，堆内存可超过 100GB。

#### `storage.tsdb.min-block-duration` / `max-block-duration` 对 churn 下内存行为的影响

`--storage.tsdb.max-block-duration` 控制 head block 刷盘的最大时间间隔（默认 2 小时）。调大此值（如 4h）意味着更多数据在内存中累积，head block 更大，内存压力更高；调小此值（如 1h）则更频繁地刷盘，可减少 head block 中的序列驻留时间，但会增加 compaction 频率和 I/O 压力。

GitHub issue #4110 记录了 compaction 内存需求过高的问题：在长保留期（如 365d）场景下，10% 的 compaction 级别可能导致额外 6Gi 内存需求，引发 OOM。该 issue 建议将 `max-block-duration` 从 10% 降至 2% 或 1%，以减小单次 compaction 的数据量。对于高 churn 场景，适当调小 `max-block-duration` 有助于控制 head block 膨胀，但需权衡 compaction 开销。

#### 小结

高 churn 通过三个机制推高 Prometheus 内存占用：(1) 2 小时 head block 窗口内短生命周期序列持续累积，inactive series 不会立即清除；(2) 高基数标签（如 `id`、`container_id`）使每序列内存开销从 3KB 膨胀至 8KB；(3) v2.19 memory-mapping 在高 churn 下收益降至 10–20%，无法根治。当 head block 中序列数超过约 300 万时，OOM 风险显著上升，尤其在 Kubernetes 环境中 30Gi 内存限制可能被突破。

### TSDB Compaction 压力与磁盘影响

高流失率对 Prometheus TSDB 的影响不仅限于内存层面——compaction 链路、倒排索引膨胀、磁盘 I/O 压力以及长范围查询性能退化共同构成了一条完整的退化路径。本节系统分析这些影响，并调查 `retention.size` 等配置手段的 churn 管理效果。

#### Compaction 工作机制与 churn 的交互

Prometheus TSDB 采用分层压缩（leveled compaction）策略，其核心流程如下：

1. **Head block 持久化**：每 2 小时，内存中的 head block 被压缩为一个持久化的 2h block，写入磁盘。该 block 包含 chunks（压缩样本）、index（倒排索引）和 meta.json（元数据）三部分。
2. **后台 compaction 合并**：compaction 循环每分钟运行一次，按优先级选择待合并的 block 组。默认的压缩时间范围序列为 `[2h, 6h, 18h, 54h, 162h, 486h]`，即从 2h 开始以 3 倍递增。最大 block 跨度取 `min(31天, retention_time / 10)` 中的较小值。
3. **倒排索引重建**：每次 compaction 都会对源 block 中的 series 做 N 路归并排序，重建倒排索引（inverted index），将标签值映射到 series ID。
4. **源 block 删除**：新 block 写入成功后，源 block 被标记为可删除，由 TSDB 在后续周期中清理。

高 churn 对这一链路的影响是多层面的。首先，高 churn 意味着 head block 在 2h 窗口内累积了更多唯一时间序列——包括大量短生命周期序列——导致每次 head compaction 的输入数据量激增。根据 Alexandre Vazquez 的分析，当活跃序列达到数百万级别时，单次 compaction 可能耗时数十秒到数分钟，期间写入性能显著退化，`prometheus_tsdb_compaction_duration_seconds` 超过 30 秒即应视为告警信号。Compaction 失败会留下孤立 block，逐渐消耗磁盘空间并可能破坏 TSDB 完整性。

其次，高 churn 导致 block 数量快速增长。每个 2h block 都包含独立的倒排索引，block 数量增多意味着查询时需要合并更多 block 的结果，延迟放大。Compaction 的合并效率取决于相邻 block 之间 series 的重叠度——低 churn 环境下，相邻 block 的大部分 series 相同，索引去重率高；高 churn 环境下，相邻 block 的 series 集合差异大，索引去重效果差，合并后的 block 索引体积更大。

#### 倒排索引膨胀与查询延迟

倒排索引是 Prometheus TSDB 查询性能的核心。每个持久化 block 的 index 文件将标签值（如 `status="500"`）映射到该 block 内所有匹配的 series ID 列表（postings list）。高 churn 对倒排索引的影响体现在两个维度：

**索引体积膨胀**：高 churn 不断引入新时间序列，每个新序列的所有标签值都需在倒排索引中新增条目。即使旧序列已停止接收样本，只要其所在 block 尚未被 compaction 清理或超出保留期，其索引条目仍占用磁盘空间。VictoriaMetrics 的 churn 分析明确指出，高 churn rate 的直接后果之一是"Increased size of inverted index"，并强调"reducing time series churn rate is important in order to limit the size of indexdb"（[VictoriaMetrics Blog](https://victoriametrics.com/blog/churn-rate-in-victoriametrics/)）。在 VictoriaMetrics 中，indexdb 通常占磁盘总空间的约 20%，高 churn 会显著推高这一比例。

**查询延迟放大**：当查询涉及多个 block 时，Prometheus 需在每个 block 的倒排索引中分别查找匹配的 series ID，然后合并结果。高 churn 导致 block 数量增多、每个 block 的索引体积增大，两者叠加使得查询需要扫描的 series 数量远超预期。如 S1.1 所述，"低瞬时基数 + 高流失率"的场景在长时间窗口查询下性能更差——因为时间窗口基数随 churn 累积增长，7d 或 30d 窗口查询需要扫描的唯一序列数可能比瞬时基数高出一个数量级（[Chronosphere](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。

Grafana Mimir 的工程实践提供了量化案例：在 Mimir 的 store-gateway 中，一个看似简单的查询 `successful_requests_total:rate5m{service="cortex", slo="writes request error", cluster=~".+"}` 最终只选中 38 条序列，但由于 `cluster=~".+"` 这一"宽泛匹配器"（broad matcher）需要加载约 8000 万 series ID 的 postings list（占用 640MB 内存），导致 store-gateway OOM。Mimir 通过优化倒排索引查找策略——利用倒排索引的字节大小预估 postings list 长度，跳过宽泛匹配器的索引查找——将部分集群的 store-gateway 内存使用降低了最多 64%（[Grafana Mimir 博客](https://grafana.com/blog/how-we-scaled-our-new-prometheus-tsdb-grafana-mimir-to-1-billion-active-series/)）。这一案例说明，高 churn 环境下倒排索引的膨胀不仅影响磁盘，还直接传导到查询内存消耗。

#### Compaction 对 CPU 与磁盘 I/O 的影响

高 churn 导致的额外数据量在 compaction 过程中转化为 CPU 和 I/O 压力：

- **CPU 消耗**：compaction 的 N 路归并排序、chunk 重编码、倒排索引重建都是 CPU 密集型操作。高 churn 增加了待处理的 series 数量和 chunk 数量，直接推高 CPU 使用率。Percona 对 Prometheus 2 TSDB 的基准分析指出，TSDB 能处理数百万级 cardinality 和数十万级 samples/s，但"CPU and IO usage spikes"仍然是已知问题，尤其在 compaction 期间（[Percona](https://www.percona.com/blog/prometheus-2-timeseries-storage-performance-analyses/)）。
- **磁盘 I/O**：compaction 需要读取所有源 block 的 chunks 和 index，写入新 block，然后删除源 block。高 churn 增加了 block 数量和每个 block 的数据量，导致 compaction 期间的磁盘读写 I/O 显著上升。如果 compaction 速度跟不上 head block 的生成速度（每 2h 一个），compaction 积压会导致磁盘空间持续增长。
- **WAL 体积膨胀**：高 churn 场景下，WAL 中记录的新序列创建操作增多，WAL 文件体积膨胀。虽然 WAL 压缩（`--storage.tsdb.wal-compression`，Prometheus 2.20+ 默认启用）可将 WAL 大小减半，但高 churn 的绝对数据量仍然可观。WAL 体积膨胀进一步导致重启时 replay 时间延长。

#### `max-block-duration` 调优的代价

`--storage.tsdb.max-block-duration` 控制 compaction 后 block 的最大时间跨度。默认值为 `min(31天, retention_time / 10)`。调大此值（如从默认的 2h 调至 4h 或更长）可以减少 compaction 频率，从而降低 CPU 和 I/O 压力。

然而，这一调优存在明确的代价：

| 调优效果 | 代价 |
|---------|------|
| 减少 compaction 频率，降低 CPU/I/O 峰值 | 单个 block 体积增大，compaction 时内存需求更高 |
| 减少 block 数量，降低查询合并开销 | 查询需扫描更大时间范围的 block，单次查询延迟增加 |
| 减少倒排索引总数 | 每个 block 的索引更大，索引查找粒度变粗 |

在 Thanos 架构中，通常将 `max-block-duration` 设为与 Prometheus 默认值相同或禁用本地 compaction（通过设置相同的 block duration），以避免 Prometheus 本地 compaction 与 Thanos Compactor 的重复工作。对于高 churn 场景，适当调大 `max-block-duration` 可以缓解 compaction 压力，但需确保磁盘和内存资源充足，且查询延迟在可接受范围内。

#### `retention.size` 与 `retention.time` 的 churn 管理效果

Prometheus 提供两种 retention 策略，可单独或组合使用。当两者同时设置时，**先触发者生效**（OR 逻辑）。

**`--storage.tsdb.retention.time`**（默认 15d）：按时间删除 block。一个 block 只有在其最大时间完全超出保留期时才被删除。高 churn 场景下，即使每个序列的生命周期很短，block 的时间跨度仍然覆盖整个保留期，因此 `retention.time` 无法有效控制高 churn 导致的存储增长——磁盘空间仍会随 block 数量和每个 block 的索引体积线性增长。

**`--storage.tsdb.retention.size`**（默认 0，即禁用）：按总磁盘空间删除 block。当 TSDB 总大小（包括 WAL、checkpoint、m-mapped chunks 和持久化 block）超过设定值时，最旧的 block 被删除。高 churn 场景下，`retention.size` 是更有效的存储控制手段，因为它直接限制了磁盘使用上限，而不依赖于序列的生命周期特征。

Prometheus 官方文档建议将 `retention.size` 设为分配磁盘空间的 80-85%，为 WAL 和 head chunk 的峰值预留 15-20% 缓冲（[Prometheus 存储文档](https://prometheus.io/docs/prometheus/latest/storage/)）。社区实践中，有用户反馈"90% 通常可用，但在高 churn 场景下可能过于接近上限"，建议保守设置为 80-85%。

**高 churn 场景下的推荐策略**：组合使用 `retention.size` 和 `retention.time`，以 `retention.size` 作为主要存储控制手段。具体而言：

- 设置 `retention.size` 为磁盘容量的 80-85%，作为硬性存储上限
- 设置 `retention.time` 为业务所需的最小保留期（如 7d 或 15d），避免不必要的长期存储
- 监控 `prometheus_tsdb_head_blocks` 和 `prometheus_tsdb_block_operations_total` 指标，跟踪 block 创建和删除速率
- 监控 compaction 相关指标（`prometheus_tsdb_compaction_duration_seconds`），确保 compaction 不积压

#### VictoriaMetrics 与 Prometheus 原生 TSDB 的差异

VictoriaMetrics 的倒排索引机制与 Prometheus 原生 TSDB 存在结构性差异，对高 churn 场景的应对能力也不同：

- **IndexDB 每日轮换与假性高 churn**：VictoriaMetrics 的 indexdb 按日轮换（每日 0 点 UTC），可能导致假性高 churn 尖峰。该机制的根因分析与 `prefillNextIndexDB`、`cacheExpireDuration` 调优方案详见 S1.1。
- **分区 IndexDB**：从 v1.133.0 起，VictoriaMetrics 采用按日历月分区的 IndexDB 设计，每个分区拥有独立的 IndexDB，保留期到期时分区及其 IndexDB 一并删除。这避免了每日轮换导致的 churn 尖峰问题。
- **压缩效率**：VictoriaMetrics 的压缩比通常为 2x-10x（相对于 Prometheus），部分原因是其倒排索引结构更紧凑，且对高 churn 场景下的索引膨胀有更好的控制（[VictoriaMetrics Blog](https://victoriametrics.com/blog/churn-rate-in-victoriametrics/)）。

相比之下，Prometheus 原生 TSDB 的倒排索引嵌入在每个 block 中，compaction 时合并去重。高 churn 降低了相邻 block 的 series 重叠度，削弱了 compaction 的索引去重效果，导致磁盘上的索引总体积更大。

#### 关键指标与监控建议

| 指标 | 用途 | 高 churn 场景下的关注点 |
|------|------|----------------------|
| `prometheus_tsdb_head_blocks` | 当前 head block 数量 | 持续增多表明 compaction 跟不上写入速率 |
| `prometheus_tsdb_block_operations_total` | block 创建/删除操作计数 | 高 churn 下 block 创建速率显著上升 |
| `prometheus_tsdb_compaction_duration_seconds` | compaction 耗时 | 超过 30s 应告警；持续升高表明 compaction 积压 |
| `prometheus_tsdb_head_series` | head block 中活跃序列数 | 高 churn 下持续增长而非趋于平稳 |
| `vm_new_timeseries_created_total`（VictoriaMetrics） | 新建时间序列速率 | 指标定义与统计口径见 S1.1 |

综上，高 churn 对 TSDB compaction 链路的影响是系统性的：从 head block 持久化、倒排索引膨胀、CPU/I/O 压力到长范围查询性能退化，形成了一个相互关联的退化链路。`retention.size` 是控制高 churn 下磁盘增长的有效手段，但无法解决 compaction 压力和查询性能问题——后者需要从源头治理 churn（S3.1）或采用远程存储架构（S3.2-S3.3）来根本缓解。

### 查询性能退化与告警可靠性

高流失率对 Prometheus 查询链路的影响往往比瞬时基数更隐蔽也更严重。核心问题在于：**查询引擎扫描的不是"当前有多少序列"，而是"时间窗口内出现过多少唯一序列"**。当 churn 持续产生新序列时，即使瞬时活跃基数不高，7d 或 30d 窗口内的唯一序列数也会随时间单调增长，查询需要扫描和合并的 series 数量远超稳态预期。

#### 时间窗口基数：高 churn 场景下查询性能退化的根因

如 S1.1 所述，"低瞬时基数 + 高流失率"的工作负载在长时间窗口查询下的性能可能比"高瞬时基数 + 低流失率"的工作负载更差——查询窗口内某个时间序列曾经出现过，该窗口的基数就不会因序列消失而减少（[Chronosphere 博客](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。

具体来说，假设一个 Kubernetes 服务每次 Deployment 产生新的 `pod` 标签值，旧序列停止接收数据但仍在 7d 窗口内可被查询到。如果每小时部署一次，7d 窗口内将累积约 168 个版本的序列副本。查询 `sum(rate(http_requests_total[7d]))` 时，PromQL 引擎需要：

1. **倒排索引查找**：对每个标签匹配项，倒排索引返回的 posting list 包含窗口内所有历史序列的引用，列表长度随 churn 线性增长。
2. **序列加载与解码**：每个匹配的序列需要从磁盘（或内存 head block）加载 chunk 数据并解码，I/O 和 CPU 开销与序列数量成正比。
3. **结果合并**：`sum` 等聚合操作需要在内存中维护每个标签组合的聚合状态，序列越多，内存占用越高。

ClickHouse 团队在对比 Prometheus 与 ClickHouse 的高基数处理时，详细分析了 Prometheus 的 series-oriented 存储模型如何导致查询开销：每个序列独立存储标签、chunk 元数据和倒排索引引用，查询时"the inverted index effectively stores, for each label name and value, a list of references to all series that contain that label pair. As cardinality increases, these posting lists grow, adding further memory overhead and increasing the work required to evaluate queries"（[ClickHouse 博客](https://clickhouse.com/blog/clickhouse-vs-promethous-high-cardinality-p1-understanding-the-problem)）。高 churn 使 posting list 在长窗口内持续膨胀，直接推高查询延迟和内存消耗。

#### `count_over_time()` 等高基数敏感函数的性能问题

`count_over_time()` 是 Prometheus 中用于统计时间窗口内序列数量的函数，但在高 churn 场景下它本身就会成为性能瓶颈。Chronosphere 指出，对于 Prometheus 用户而言，"the only real option available here is via built-in functions like `count()` or `count_over_time()`. While these work to a degree, they are quite resource-intensive when it comes to higher cardinality series, exactly when we most care about having visibility into the behavior of our workload"（[Chronosphere 博客](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。

这是因为 `count_over_time()` 需要遍历窗口内所有匹配序列的每个样本点，对每个序列执行计数操作。当 churn 导致窗口内序列数达到百万级时，即使查询本身只是"数数"，也可能消耗数秒甚至更长时间，并占用大量内存。

#### 长时间窗口查询（7d / 30d）的性能退化

在长范围查询场景下，高 churn 的影响被进一步放大：

- **Block 合并开销**：Prometheus 将数据按 2h block 存储，7d 查询需要合并约 84 个 block，30d 查询需要合并约 360 个 block。高 churn 使每个 block 包含更多唯一序列，合并时需要处理更多 series 的倒排索引和 chunk 数据。
- **查询超时**：当查询涉及的序列数超过 Prometheus 查询引擎的处理能力时，查询会超时失败。在 Grafana 中表现为面板加载超时或 "query timed out" 错误。
- **内存峰值**：长窗口查询需要在内存中同时持有更多序列的中间结果，高 churn 场景下内存峰值可能触发 OOM，与 S2.1 讨论的 head block 内存问题叠加。

#### 高 churn 导致的 "Missing Time Series" 问题

当时间序列因 churn 消失后（如 Pod 被销毁、Deployment 切换），依赖这些序列的告警规则和 recording rules 会出现一系列异常行为。

**告警规则的静默失败**：PromLabs 的 Julius Volz 在其博客中明确指出，当告警规则的 PromQL 表达式返回空结果时，"Prometheus interprets an empty alerting rule expression output as 'everything is fine'"——即告警静默失败，不会触发任何告警（[PromLabs 博客](https://promlabs.com/blog/2023/09/13/dealing-with-missing-time-series-in-prometheus/)）。这在 churn 场景下尤其危险：

- 如果一个按 `pod` 标签告警的规则（如 `high_cpu_usage{pod="xxx"}`），当该 Pod 被销毁后序列消失，即使系统真的出了问题，告警也不会触发。
- 对于"过低速率"类告警（如 `rate(errors_total[5m]) < 0.1`），当错误序列因 Pod 消失而不存在时，查询返回空结果，告警静默失败。

**告警 flapping**：在动态环境中，序列的消失和重新出现（如 HPA 扩缩容、滚动更新）会导致告警实例反复创建和消除，产生 flapping。Grafana 的告警文档将此分为两种场景（[Grafana 告警文档](https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/)）：

| 场景 | 表现 | 风险 |
|------|------|------|
| **No Data** | 查询返回空结果，所有序列消失 | 告警静默失败，不触发任何通知 |
| **Missing Series** | 部分序列消失，其他序列仍在 | 消失的序列对应的告警实例被 evict，可能发送错误的 resolved 通知 |

Grafana 通过 MissingSeries 机制处理此问题：当告警实例的数据缺失超过两个评估周期后，Grafana 会将该实例标记为 `grafana_state_reason: MissingSeries` 并转为 Normal 状态，发送 resolved 通知（[Grafana 告警文档](https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/)）。但这本身也可能产生误报——在正常扩缩容时，大量告警实例被 evict 并发送 resolved 通知，造成通知噪音。

#### `absent()` 与 `absent_over_time()` 在 churn 场景下的作用与误报风险

`absent()` 和 `absent_over_time()` 是 Prometheus 提供的用于检测序列是否存在的函数。根据官方文档（[Prometheus 函数文档](https://prometheus.io/docs/prometheus/latest/querying/functions/)）：

- `absent(v instant-vector)`：如果输入向量有元素则返回空向量，如果无元素则返回值为 1 的单元素向量。
- `absent_over_time(v range-vector)`：同上，但作用于范围向量。

在 churn 场景下，这两个函数的主要用途是**检测目标是否停止上报数据**。例如：

```promql
absent_over_time(up{job="my-job"}[5m])
```

当所有 `up{job="my-job"}` 序列消失时（如所有 Pod 被销毁），该表达式返回 1，触发告警。

**误报风险**：

1. **无法区分"目标故障"与"正常 churn"**：`absent_over_time()` 不保留标签信息，无法告诉你哪个具体序列消失了。在 Kubernetes 环境中，Pod 的正常销毁和目标故障都会导致序列消失，函数无法区分这两种情况（[Grafana 告警文档](https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/)）。

2. **硬编码标签值不可扩展**：如果按具体标签值检测（如 `absent_over_time(http_request_latency_seconds{region="region1"}[5m])`），在动态环境中需要为每个可能的标签值创建单独的告警规则，"this approach doesn't scale well because it requires hardcoding all possible label values"（[Grafana 告警文档](https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/)）。

3. **窗口选择敏感**：如果 `absent_over_time` 的窗口设置过短（如 5m），在滚动更新期间旧序列消失但新序列尚未完全注册时，会产生误报。如果窗口过长，则无法及时检测到真正的目标故障。

4. **Cortex/Mimir 中的限制**：Cortex 的 changelog 显示，`absent` 和 `absent_over_time` 在 vertical sharding 场景下被禁用（`[BUGFIX] Query Frontend: Disable absent, absent_over_time and scalar for vertical sharding`），表明这些函数在分布式查询引擎中有已知的性能和正确性问题（[Cortex Changelog](https://cortexmetrics.io/docs/changelog/)）。

**更安全的替代方案**：Grafana 文档建议使用 `present_over_time` 结合 `unless` 操作符来动态检测缺失序列：

```promql
group(present_over_time(http_request_latency_seconds{}[24h])) by (region)
unless
group(present_over_time(http_request_latency_seconds{}[10m])) by (region)
```

这种方式可以动态发现"过去 24h 内存在但最近 10m 内消失"的序列，而不需要硬编码标签值（[Grafana 告警文档](https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/)）。

#### 高 churn 对 Recording Rules 的影响

Recording rules 是 Prometheus 中用于预计算表达式并存储为新的时间序列的机制。高 churn 对 recording rules 的影响主要体现在：

1. **输出序列膨胀**：如果 recording rule 的表达式包含高 churn 标签（如 `pod`），则每次评估都会为新的标签组合创建新的输出序列。例如，规则 `sum(rate(http_requests_total[5m])) by (pod)` 在每次 Deployment 后都会产生新的 `pod` 标签值的输出序列，旧序列消失。这实际上将 churn 从原始指标传播到了 recording rule 输出。

2. **评估延迟**：Recording rules 按固定间隔评估，高 churn 场景下每次评估需要处理更多序列，评估时间可能超过评估间隔，导致规则输出延迟或积压。社区建议 recording rules 的执行时间应小于评估间隔的 10%（[OneUptime 博客](https://oneuptime.com/blog/post/2026-02-09-optimize-prometheus-recording-rules-latency/view)）。

3. **下游查询放大**：Recording rule 输出被其他查询或告警引用时，如果输出序列因 churn 频繁消失和重建，下游查询同样面临 missing series 问题。

**最佳实践**：在 recording rules 中应**剔除高 churn 标签**（如 `pod`、`container_id`），仅保留低基数标签（如 `job`、`namespace`、`deployment`），从而将高 churn 指标预聚合为低基数序列。这既能降低 recording rule 输出的 churn，也能提升下游查询性能。

#### 小结

高 churn 对查询链路的影响可以归纳为三个层面：

| 层面 | 影响 | 严重程度 |
|------|------|----------|
| **查询性能** | 时间窗口基数随 churn 增长，长窗口查询扫描更多序列，CPU/内存消耗上升，`count_over_time()` 等函数成为瓶颈 | 高 |
| **告警可靠性** | 序列消失导致告警静默失败或 flapping，`absent()`/`absent_over_time()` 无法区分正常 churn 与真实故障 | 高 |
| **Recording Rules** | 高 churn 标签传播到规则输出，评估延迟，下游查询面临 missing series | 中 |

这些影响与 S2.1（内存消耗）和 S2.2（compaction 压力）相互叠加，共同构成高 churn 场景下 Prometheus 稳定性风险的重要组成部分。解决这些问题需要从源头治理（S3.1 指标治理）和架构调整（S3.2 远程写入、S3.3 长期存储）两个方向同时入手。

### 稳定性风险与成本影响

高流失率对 Prometheus 的影响远不止内存或查询性能的单点退化，而是通过多条路径级联放大，最终威胁整个监控系统的可靠性。本节从级联故障路径、WAL 膨胀、远程写入开销、成本转化和"noisy neighbor"五个维度，系统梳理高 churn 场景下的稳定性风险与 TCO 影响。

#### 级联故障路径：从 OOM 到磁盘耗尽

高 churn 场景下 Prometheus 进程崩溃的典型级联路径如下：

1. **OOM 触发进程崩溃**：head block 需保留最近 2–3 小时所有活跃时间序列的内存映射，高 churn 意味着大量短生命周期序列在 2h 窗口内累积，RSS 远超稳态基数预期。当内存触及 cgroup 限制时，OOM Killer 终止 Prometheus 进程。Cloudflare 在其大规模实践中明确指出，"cardinality explosion"导致 Prometheus 耗尽内存崩溃、丢失全部可观测性是最典型的故障模式（[Cloudflare 博客](https://blog.cloudflare.com/how-cloudflare-runs-prometheus-at-scale/)）。

2. **Compaction 积压**：Prometheus 每 2 小时将 head block 压缩为持久 block。进程崩溃期间，compaction 中断，WAL 中积压的未压缩数据持续累积。重启后，compaction goroutine 需要处理积压的 head block，但此时内存可能再次不足，导致 compaction 反复失败。GitHub issue #6184 记录了 compaction 过程中 OOM 的典型案例——大 block 压缩时内存需求超出预期（[GitHub #6184](https://github.com/prometheus/prometheus/issues/6184)）。

3. **磁盘空间耗尽**：WAL 文件以 128MB 为 segment 持续写入，高 churn 场景下 WAL 体积显著膨胀（详见下文）。同时，compaction 积压导致旧 block 无法被清理，新 block 又持续生成，磁盘空间被双向挤压。Prometheus 官方文档指出，磁盘最小需求为 WAL 和 `chunks_head` 目录的峰值空间之和（每 2 小时一个周期），高 churn 会直接推高这一峰值（[Prometheus 存储文档](https://prometheus.io/docs/prometheus/latest/storage/)）。

4. **查询超时与告警延迟**：进程恢复后，积压的 compaction 任务持续消耗 CPU 和 I/O，导致查询响应变慢、告警规则评估延迟。Last9 的分析指出，长时间窗口查询（如 7d/30d）在高数据量场景下经常导致 Prometheus OOM 崩溃，"延长了 MTTD（平均检测时间），恰恰在最需要这些查询的时候"（[Last9 博客](https://last9.io/blog/challenges-with-running-prometheus-at-scale/)）。

5. **数据丢失**：如果远程写入队列在进程崩溃前未能将 WAL 中的数据发送出去，且 WAL 在 2 小时后被 compacted，未发送的数据将永久丢失。Prometheus 远程写入文档明确警告："如果远程端点持续宕机超过 2 小时，WAL 将被 compacted，未发送的数据将丢失"（[Prometheus 远程写入调优文档](https://prometheus.io/docs/practices/remote_write/)）。

社区报告的一个典型级联案例是 Prometheus 周期性数据丢失：有用户报告每 30 分钟出现一次 rate 计算断点，`prometheus_tsdb_out_of_order_samples_total` 同步上升，最终升级到 2.52.0 后修复——这指向了 head block 在高压下的时序错乱问题（[Prometheus 讨论区](https://discuss.prometheus.io/t/periodic-dropouts/2290)）。

#### WAL 体积膨胀与 Replay 时间延长

Prometheus 的 WAL（Write-Ahead Log）以 128MB segment 文件存储未压缩的原始样本数据，官方文档说明"高流量服务器可能保留超过三个 WAL 文件以保持至少两小时的原始数据"（[Prometheus 存储文档](https://prometheus.io/docs/prometheus/latest/storage/)）。高 churn 场景下 WAL 膨胀的机制包括：

- **新序列元数据开销**：每个新时间序列在 WAL 中需要写入序列 ID 到标签值的映射记录。高 churn 意味着大量新序列在短时间内注册，WAL 中序列元数据占比显著上升。
- **样本数据量**：高 churn 通常伴随高摄入速率（ingestion rate），WAL 中原始样本数据量随摄入速率线性增长。
- **WAL 压缩的局限**：Prometheus 2.11+ 支持 WAL 压缩（`--storage.tsdb.wal-compression`，2.20+ 默认启用），官方称可将 WAL 大小减半，但高 churn 场景下绝对体积仍然可观。

实际案例中，有用户报告 WAL 大小达到 600GB（19 天保留期），磁盘空间被耗尽（[GitHub Discussion #10272](https://github.com/prometheus/prometheus/discussions/10272)）；GitLab Omnibus 用户报告 WAL 大小达 25GB（[GitLab Forum](https://forum.gitlab.com/t/prometheus-wal-size-25-gb-in-gitlab-omnibus-safe-cleanup-approach/132601)）。

**WAL Replay 时间估算**：Prometheus 重启后需 replay WAL 恢复 head block 状态。有用户报告 WAL 大小 2GB 时，Pod 重启后 WAL sync 需要 15–20 分钟（[Reddit r/kubernetes](https://www.reddit.com/r/kubernetes/comments/1ic545c/kube_prometheus_stack_wal_sync_time_is_too_much/)）。高 churn 场景下 WAL 体积可能达到数十 GB 级别，replay 时间相应延长至数十分钟甚至更长。GitHub issue #16942 指出，当前 WAL replay 算法"试图尽快 replay WAL，可能使用比 Prometheus 运行时更多的内存"，这意味着高 churn 场景下重启本身就可能触发 OOM（[GitHub #16942](https://github.com/prometheus/prometheus/issues/16942)）。

**WAL Replay 中的 Race Condition**：Grafana Mimir 在扩展至 10 亿活跃序列的过程中，发现了一个关键问题——TSDB WAL replay 过程中的 race condition 导致后续从 head block compacted 的 block 包含乱序样本（out-of-order samples）。这一发现直接推动了 Mimir 对 TSDB 的改进，包括 out-of-order sample ingestion 功能（[Grafana Mimir 博客](https://grafana.com/blog/how-we-scaled-our-new-prometheus-tsdb-grafana-mimir-to-1-billion-active-series/)）。

**WAL 损坏风险**：`prometheus_tsdb_wal_corruptions_total` 指标记录 WAL 损坏次数。GitHub issue #17833 报告了一个严重问题：当 WAL segment 损坏时，Prometheus 记录损坏并继续运行、正常服务查询，但 WAL compaction 被无限期阻塞，导致 WAL 持续增长直至磁盘耗尽（[GitHub #17833](https://github.com/prometheus/prometheus/issues/17833)）。高 churn 场景下 WAL 写入量大，磁盘 I/O 压力高，WAL 损坏的概率相应增加。

#### 远程写入链路的带宽与请求数影响

高 churn 对远程写入链路的影响体现在两个维度：

**内存开销**：Prometheus 远程写入文档明确指出，"对于 WAL 中的每个序列，remote write 代码缓存序列 ID 到标签值的映射，导致大量序列 churn 显著增加内存使用"。大多数用户报告约 25% 的内存增加，但"这个数字取决于数据形状"——高 churn 场景下增幅更大（[Prometheus 远程写入调优文档](https://prometheus.io/docs/practices/remote_write/)）。

**网络带宽**：远程写入 v1 协议中，每个样本需要 10–2 字节传输（含重复的指标名、标签名、标签值文本），而本地磁盘存储仅需 1–2 字节/样本。高 churn 场景下，大量新序列的元数据（指标名、标签集）需要反复传输，带宽效率极低。Remote Write v2 通过符号表实现字符串去重，在高 churn 场景下收益尤为显著——新序列越多，重复传输的元数据越多，去重节省越大（协议改进详见 S3.2）。

**请求数与背压**：远程写入队列的 shard 内存与 `number of shards * (capacity + max_samples_per_send)` 成正比。高 churn 导致队列积压时，Prometheus 自动增加 shard 数量（上限 `max_shards`），每个 shard 独立发送 HTTP 请求，请求数随之上升。如果远程端点处理不过来，背压会传导至 WAL 读取阻塞，进而影响所有 shard 的吞吐量（[Prometheus 远程写入调优文档](https://prometheus.io/docs/practices/remote_write/)）。

#### Churn 成本转化：自建与云厂商托管

**自建 Prometheus 的成本模型**：

| 成本维度 | 高 churn 影响 | 估算公式 |
|---------|-------------|---------|
| 存储成本 | 随序列数量与保留期线性增长 | `retention_seconds × ingestion_rate × bytes_per_sample`（官方建议 1–2 字节/样本） |
| 内存成本 | head block 2h 窗口内累积大量短生命周期序列，RSS 远超稳态预期 | 每活跃序列约 1–2 KB head 内存 + remote write 序列缓存 |
| 磁盘 I/O | compaction 输入数据量激增，CPU 与 I/O 压力上升 | 与 churn rate × 保留期成正比 |
| 网络成本 | remote write 带宽随摄入速率增长，v1 协议效率低 | 摄入速率 × 10–2 字节/样本（v1）或 × 1–2 字节/样本（v2） |
| 运维成本 | 故障排查、compaction 调优、OOM 恢复的人力投入 | 随 churn 级别非线性增长 |

Prometheus 官方文档给出的磁盘空间估算公式为：`needed_disk_space = retention_time_seconds × ingested_samples_per_second × bytes_per_sample`（[Prometheus 存储文档](https://prometheus.io/docs/prometheus/latest/storage/)）。高 churn 场景下，`ingested_samples_per_second` 因新序列持续注册而显著高于稳态，直接推高存储需求。

AWS AMP 的计费模型与 churn 成本影响详见 S4.1。

**Grafana Cloud 的计费模型**：

Grafana Cloud 同样按摄入样本数、存储和查询计费。Grafana Labs 通过迁移到 Remote Write v2 将内部遥测的网络 egress 成本降低 50%，这间接反映了高 churn 场景下远程写入成本在 TCO 中的显著占比（[Grafana 博客](https://grafana.com/blog/how-prometheus-remote-write-v2-can-help-cut-network-egress-costs-by-as-much-as-50-/)）。

**成本对比的关键差异**：

- **自建**：成本以基础设施（VM/磁盘/网络）和运维人力为主，churn 直接推高资源需求但无按量计费弹性
- **云厂商托管**：成本按使用量弹性计费，churn 直接转化为账单增长，但无需投入运维人力
- **混合架构**（self-managed Prometheus + remote write 到云厂商）：churn 成本体现在远程写入带宽和云厂商摄入费用上，本地存储成本可通过降低 retention 至 2h 最小化

#### "Noisy Neighbor" 问题

在共享 Prometheus 实例中，"noisy neighbor"问题表现为：一个团队或应用的异常 churn（如误用高基数标签、CronJob 频繁创建新序列）导致整个 Prometheus 实例的内存、CPU 或磁盘 I/O 压力上升，影响其他团队的监控数据摄入和查询。

Cloudflare 的大规模 Prometheus 实践（详见 S1.2）中，单个实例的 churn 异常可能影响全局。

AWS AMP 的 label-based active series limits 直接针对这一问题，通过 per-label-set 配额实现多租户级别的 noisy neighbor 防护（详见 S4.1）。

在自建 Prometheus 中，缓解 noisy neighbor 的主要手段是分片（sharding）——通过 `hashmod` relabeling 将不同 job 分散到多个 Prometheus 实例，使单个实例的 churn 被隔离。但分片后跨分片的查询和告警需要联邦（federation）或远程存储层来聚合，增加了架构复杂度（[Last9 博客](https://last9.io/blog/challenges-with-running-prometheus-at-scale/)）。

#### TCO 估算框架

综合以上分析，高 churn 场景下的 TCO 估算框架如下：

```
TCO = 基础设施成本 + 存储成本 + 网络成本 + 运维成本 + 故障成本

其中：
- 基础设施成本 = f(active_series_peak, churn_rate, head_block_window)
  ∝ active_series × (1 + churn_rate × retention_factor) × memory_per_series
  
- 存储成本 = retention_time × ingestion_rate × bytes_per_sample × storage_unit_cost
  高 churn 下 ingestion_rate 因新序列注册而显著高于稳态
  
- 网络成本 = ingestion_rate × bytes_per_sample_remote × network_unit_cost
  v1: 10–2 bytes/sample; v2: 1–2 bytes/sample
  
- 运维成本 = 基线运维 + churn 级别 × 故障排查频率 × 平均排查时长
  
- 故障成本 = P(OOM) × MTTD + P(data_loss) × 数据丢失影响 + P(disk_full) × 恢复时间
```

**关键洞察**：高 churn 场景下，故障成本和运维成本往往超过基础设施成本本身。Last9 的分析指出，"每个全职运维人员维护 Prometheus 的成本，最终可能成为监控基础设施中最大的成本"（[Last9 博客](https://last9.io/blog/challenges-with-running-prometheus-at-scale/)）。这解释了为什么越来越多组织在 churn 级别升高后转向云厂商托管方案——将运维复杂性和故障风险转移给云厂商，同时通过按量计费将 churn 成本透明化。

## 系统性解决方案

### 指标治理与采集侧限制：relabeling、recording rules、标签裁剪与 sample_limit

高流失率的治理第一道防线是在采集侧拦截高基数标签和无效序列，从源头降低进入 TSDB 的新序列产生速率。本节系统梳理 relabeling、recording rules、exemplars、scrape interval 调优及采集侧限制机制的原理、适用场景与局限。

#### 1. relabel_configs 与 metric_relabel_configs：阶段差异与适用场景

Prometheus 的 relabeling 机制在指标生命周期的不同阶段生效，理解这一差异是正确配置的前提：

| 配置项 | 生效阶段 | 操作对象 | 典型用途 |
|--------|---------|---------|---------|
| `relabel_configs` | 抓取**前** | 服务发现产生的 target 标签（`__meta_*`） | 过滤 target、裁剪/重写 target 标签 |
| `metric_relabel_configs` | 抓取**后**、写入前 | 已抓取的指标序列标签 | 丢弃高基数标签、丢弃整条指标 |
| `write_relabel_configs` | remote write 发送前 | 即将发送到远程存储的序列 | 过滤不需要长期存储的序列 |

`relabel_configs` 在抓取前运行，仅能访问服务发现注入的 `__meta_*` 标签和 `__address__` 等内部标签，用于决定"抓哪些 target"以及"如何标记 target"。`metric_relabel_configs` 在抓取完成后、写入 TSDB 前运行，可以访问指标的所有标签（包括 `__name__`），用于决定"保留哪些序列"以及"如何改写序列标签"。这一阶段差异意味着：**如果高基数标签来自指标本身（如应用暴露的 `trace_id` 标签），必须使用 `metric_relabel_configs` 才能裁剪**；而 `relabel_configs` 无法触达这些标签，因为它们尚未被抓取。

两种配置共享相同的 `<relabel_config>` 语法结构，支持 `replace`、`keep`、`drop`、`labelkeep`、`labeldrop`、`hashmod` 等 action。配置按数组顺序依次执行，前一步的输出作为后一步的输入。

#### 2. 高基数标签裁剪策略

**应优先裁剪的标签类型**：

- **`trace_id` / `span_id`**：每次请求唯一，作为标签会直接导致序列数随请求量线性增长。应使用 exemplars 机制替代（见下文）。
- **`user_id` / `session_id`**：用户级标识作为标签会使基数随用户规模增长，通常应通过 recording rules 聚合掉。
- **`request_id` / `uuid`**：每次请求唯一，属于典型的指标反模式，应直接丢弃。
- **高基数 HTTP path**：如 `/api/v1/users/{user_id}` 中的动态路径段，应通过 relabeling 归一化为模板路径。

**裁剪配置示例**：

```yaml
scrape_configs:
  - job_name: kubelet
    metric_relabel_configs:
      - action: labeldrop
        regex: 'path|replicaset|controller_revision_hash|owner_name'
```

上述配置来自一个生产事故修复案例：丢弃高 churn 标签后，Prometheus 实例从约 1000 万序列、60 GB 内存降至 400 万序列、18–25 GB 内存。`labelkeep` 是 `labeldrop` 的逆操作——仅保留匹配正则的标签，丢弃其余所有标签，在可枚举所需标签时更安全。

**关键风险**：如果被丢弃的标签是唯一区分两个序列的标识，丢弃后序列会合并。Prometheus 对同一时间戳的重复样本仅保留第一个，不会合并或求和。自 Prometheus 2.52.0 起，可通过 `prometheus_target_scrapes_sample_duplicate_timestamp_total` 指标检测此类冲突；更早版本会静默丢失数据。因此，任何 `labeldrop` 变更后都应验证结果标签集的唯一性并监控该计数器。

**整条指标丢弃**：对于从未被 dashboard 或告警引用的指标族，可在 `metric_relabel_configs` 中按 `__name__` 匹配直接丢弃：

```yaml
metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'node_sockstat_.*|node_vmstat_.*|node_uname_info'
    action: drop
```

`mimirtool analyze` 可辅助识别未使用的指标：提取 dashboard 和规则中引用的所有指标，与活跃序列对比，输出 `additional_metric_counts` 字段列出未被引用的指标及其序列数。一个实际案例中，38,184 个活跃序列里有 24,137 个未被任何查询使用。

#### 3. K8s 环境中 pod_name churn 的治理局限

在 Kubernetes 环境中，`pod`、`container`、`namespace` 等标签值随 Pod 创建销毁持续变化，是 churn 的主要来源。relabeling 可以裁剪部分 `__meta_*` 标签，但**无法完全消除 pod_name churn**，原因如下：

- Pod 名称本身（如 `myapp-5d4b7c8f9-x2k9p`）包含 ReplicaSet hash 和随机后缀，每次 Deployment 或重启都会产生新值。
- 如果 relabeling 丢弃 `pod` 标签，同一节点上不同 Pod 的指标会因标签冲突而合并，导致数据丢失。
- `kube-state-metrics` 等 exporter 暴露的 pod 身份标签在 rollout 或重启后变化，旧序列在 head block 中持续累积。

**替代方案**：
1. **recording rules 预聚合**：将 pod 级指标聚合为 service 级或 deployment 级序列，保留关键维度（如 `namespace`、`deployment`）的同时消除 pod 级 churn。
2. **调整服务发现粒度**：使用 `role: endpoints` 替代 `role: pod`，以 Service 而非 Pod 为采集单位，减少 target 数量。
3. **remote write + 长期存储**：本地仅保留短 retention（2h），将长期存储和查询卸载到远程系统（见 S3.2）。

#### 4. Recording Rules 预聚合降低 churn

Recording rules 通过预计算 PromQL 表达式并将结果存储为新的低基数序列，是降低 churn 的核心手段。预聚合后的序列通过 `sum without` 或 `sum by` 保留关键维度，同时消除高 churn 标签。

**配置示例**（遵循 `level:metric:operations` 命名规范）：

```yaml
groups:
  - name: aggregate_http_requests
    interval: 5m
    rules:
      - record: service:http_requests:rate5m
        expr: sum without (pod, instance) (rate(http_requests_total{job="myjob"}[5m]))
```

此规则将 pod 级和 instance 级的 HTTP 请求速率聚合为 service 级序列，消除了 `pod` 和 `instance` 标签的 churn。预聚合后，原始高基数序列可通过 `metric_relabel_configs` 或 `write_relabel_configs` 丢弃。

**评估间隔对 churn 缓解效果的影响**：

- 较短的评估间隔（如 1m）能更快地将新序列纳入聚合，但增加 Prometheus 的 CPU 和内存开销。
- 较长的评估间隔（如 5m）降低评估开销，但在间隔内新产生的序列仍以原始高基数形式存在于 head block 中。
- 官方建议根据 dashboard 刷新频率和告警需求设置评估间隔，通常 1m–5m 为宜。

**注意事项**：
- Recording rules 在 Prometheus Agent 模式下不可用（Agent 模式禁用了规则评估），预聚合必须在远程端完成。
- 聚合比时，应分别聚合分子和分母再相除，避免直接平均比率。
- 可通过 `limit` 字段限制每个规则组产生的序列数，超限后所有序列被丢弃。

#### 5. Exemplars 机制替代高基数标签

Exemplars 是附加到指标样本上的 trace ID 引用，允许从指标跳转到对应的 trace，从而避免将 `trace_id` 等高基数标签直接作为指标标签。

**存储格式**：

```
request_duration_seconds_bucket{le="0.1"} 8 # {trace_id="AAA5S4ois0o"} 0.054
```

`#` 后面的部分是 exemplar 注解，包含 `trace_id` 和可选的 `span_id` 及样本值。Exemplar 不增加时间序列数量——它作为样本的元数据存储，不创建新的标签组合。

**工作链路**：
1. 应用需同时暴露 traces 和 metrics，并在 metrics 中包含 trace ID。
2. Prometheus 抓取时解析 exemplar 注解并存储。
3. 查询时通过 Grafana 等前端工具，可从 exemplar 跳转到对应的 trace 详情（如 Grafana Tempo）。
4. 通过 remote write 时，exemplars 可随样本一起转发到远程存储（需配置 `send_exemplars: true`）。

**适用场景**：需要将请求级详情与指标关联，但不想承担 `trace_id` 标签带来的基数爆炸。典型用例包括：排查 p99 延迟尖峰时，直接从延迟分布的 exemplar 跳转到慢请求的 trace。

**局限**：exemplar 仅存储少量代表性样本的 trace ID，无法覆盖所有请求；需要应用端集成 tracing SDK 并正确传播 trace context。

#### 6. Scrape Interval 调优权衡

调整 `scrape_interval` 直接影响 churn 速率和系统负载：

- **缩短间隔**（如 15s→30s）：提高数据新鲜度，但增加抓取频率和 CPU/网络开销，同时高 churn 场景下新序列产生速率不变（churn 由标签变化驱动，而非抓取频率）。
- **延长间隔**（如 15s→60s）：降低系统负载和 remote write 带宽，可将成本降低最多 75%，但牺牲数据时效性。

**权衡建议**：对非关键指标（如基础设施层指标）可延长至 60s；对核心业务指标和告警依赖的指标保持 15s–30s。在 Kubernetes 环境中，Pod 生命周期通常以分钟计，因此 30s–60s 的间隔足以捕捉状态变化，同时显著降低抓取开销。

#### 7. 采集侧限制机制：sample_limit、label_limit 与 label_value_length_limit

Prometheus 提供多个采集侧限制机制，默认均为 0（无限制），可按全局或 per-scrape job 配置：

| 配置项 | 作用 | 超限行为 | 引入版本 |
|--------|------|---------|---------|
| `sample_limit` | 限制单次 scrape 的样本数（metric relabeling 后） | 整个 scrape 失败，`up=0` | v1.5.0 |
| `label_limit` | 限制每条序列的标签数（metric relabeling 后） | 整个 scrape 失败 | v2.27.0 |
| `label_name_length_limit` | 限制标签名长度（字节） | 整个 scrape 失败 | — |
| `label_value_length_limit` | 限制标签值长度（字节） | 整个 scrape 失败 | — |
| `target_limit` | 限制 per-job 的 target 数（target relabeling 后） | 超限 target 不抓取 | v2.21.0 |

**`sample_limit` 的工作机制**：在 `metric_relabel_configs` 执行后检查样本数。若超过限制，整个 scrape 被标记为失败，`up` 设为 0，该次抓取的所有样本被拒绝。`scrape_samples_scraped` 指标仍记录实际抓取数（即使超限），`scrape_samples_post_metric_relabeling` 记录 relabeling 后的样本数，可用于在超限前预警。

**关键局限——无法限制 per-target 的 churn rate**：`sample_limit` 仅限制单次 scrape 的序列数，**不能限制一个 target 在时间维度上持续产生新序列的速率**。一个恶意或配置错误的 workload 可以在每次 scrape 中都产生少量新序列（如每次新增 5 个），远低于 `sample_limit`，但持续累积导致 TSDB 中序列数不断增长。这正是 [GitHub issue #17109](https://github.com/prometheus/prometheus/issues/17109) 提出的问题。

#### 8. GitHub Issue #17109：限制 per-instance label churn over time

[Issue #17109](https://github.com/prometheus/prometheus/issues/17109) 由用户 ringerc 提出，旨在解决"无法限制 workload 随时间产生新序列"的问题。核心提案包括两个方案：

- **Option 1**：对 `scrape_series_added` 设置阈值，当某 instance 的新增序列数超过阈值时丢弃后续新序列。但对首次抓取的 instance 会立即触发限制，需要引入"近期无样本则跳过限制"的例外逻辑。
- **Option 2**：限制 `scrape_series_added` 在时间窗口内的滚动总和，如 `sum_over_time(scrape_series_added{job,instance}[1h]) > 200` 时丢弃新序列。更实用但实现更复杂。

**实现挑战**：
- 需要 appender 查询 TSDB HEAD 以判断是否首次抓取或计算滚动总和，引入额外查询开销和延迟。
- 在 Agent 模式下无法实现（无 TSDB 和查询能力）。
- 无法防御 workload 快速重启导致的 churn（每次重启被视为"新 instance"）。
- 简单的内存计数器方案在 Prometheus 重启后失效，可能允许突发高 churn 序列摄入。

截至本文撰写时，该 issue 仍处于 Open 状态，尚未有合并的实现。社区讨论指向需要更完善的方案，可能结合 Job 级限制和时间窗口计数器。

#### 9. 各手段适用场景与代价总结

| 手段 | 适用场景 | 代价 | 局限 |
|------|---------|------|------|
| `metric_relabel_configs` 丢弃标签 | 已知高基数标签（trace_id、user_id） | 可能丢失维度信息；需验证序列唯一性 | 无法消除 K8s pod_name churn |
| `relabel_configs` 裁剪 target 标签 | 减少 target 标签噪音 | 可能影响 target 识别 | 仅作用于抓取前，无法触达指标标签 |
| Recording rules 预聚合 | 保留聚合信号同时消除高 churn 标签 | 增加 Prometheus 评估开销；Agent 模式不可用 | 需重定向 dashboard/告警到聚合序列 |
| Exemplars 替代 trace_id 标签 | 需要指标到 trace 跳转 | 需应用集成 tracing SDK | 仅存储代表性样本，非全量 |
| 延长 scrape interval | 降低非关键指标的系统负载 | 数据时效性下降 | 不减少 churn 本身，仅降低抓取频率 |
| `sample_limit` | 防止单次 scrape 基数爆炸 | 超限后整个 target 抓取失败 | 无法限制时间维度上的 churn 累积 |
| `label_limit` / `label_value_length_limit` | 防止标签过多或过长 | 超限后整个 scrape 失败 | 仅限制单次 scrape，不限制 churn rate |
| `write_relabel_configs` | 过滤不需要长期存储的序列 | 增加 remote write 链路复杂度 | 本地 TSDB 仍承受 churn 压力 |

**实践建议**：高 churn 治理应采用分层组合策略——首先通过 `metric_relabel_configs` 丢弃明确的高基数标签（trace_id、request_id），其次用 recording rules 预聚合保留关键维度的聚合信号，再通过 `sample_limit` 作为安全阀防止突发基数爆炸，最后通过 `write_relabel_configs` 在远程写入前过滤不需要长期存储的序列。对于 K8s 环境中的 pod_name churn，relabeling 无法根治，需结合 recording rules 聚合或 remote write 架构将长期存储卸载到远程系统。

### 远程写入架构与 Agent 模式

#### 远程写入协议与配置

Prometheus Remote Write 协议允许将采集到的样本实时转发到远程存储后端，使 Prometheus 从本地存储约束中解放出来。协议使用 [Snappy 压缩的 Protocol Buffers 编码](https://prometheus.io/docs/prometheus/latest/storage/) 通过 HTTP POST 发送数据，支持 1.0 和 2.0 两个版本。配置示例如下：

```yaml
remote_write:
  - url: "http://victoriametrics:8428/api/v1/write"
    write_relabel_configs:
      - source_labels: [__name__]
        regex: 'high_cardinality_.*'
        action: drop
    queue_config:
      max_shards: 200
      capacity: 10000
      max_samples_per_send: 2000
```

`write_relabel_configs` 在数据写入远程端点前生效，可丢弃高基数指标或裁剪标签，从而在写入侧直接降低 churn 对远程存储的影响。这与 `metric_relabel_configs`（在 scrape 阶段生效）不同——后者在样本进入本地 TSDB 前过滤，而前者仅影响远程写入链路，[两者可组合使用](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)。

#### 本地 Retention 与 2h 最低保留

在远程写入架构下，Prometheus 本地仅作为采集缓冲区，所有数据实时复制到远程存储。因此本地 retention 可降至最低。[Prometheus 官方文档](https://prometheus.io/docs/prometheus/latest/storage/) 指出，最低支持的 retention 为 2 小时（`--storage.tsdb.retention.time=2h`），这是因为 head block 默认覆盖最近 2 小时数据，且 WAL 至少保留 2 小时的原始数据用于 remote write 读取。若 retention 低于 2h，WAL 可能在 remote write 尚未读取时就被 compaction 清除，导致数据丢失。

使用 Agent 模式时，本地存储被完全替换为定制化的 TSDB WAL，[Agent 模式文档](https://github.com/prometheus/prometheus/blob/main/docs/prometheus_agent.md) 明确指出其使用 `--storage.agent.path`（默认 `data-agent/`）而非 `--storage.tsdb.path`，且 WAL 缓冲上限同样为 2 小时。

#### 网络带宽与远程存储写入速率

Remote write 会增加 Prometheus 的内存和网络开销。[Prometheus 官方调优文档](https://prometheus.io/docs/practices/remote_write/) 指出，大多数用户报告内存增加约 25%，但高 churn 场景下因 series ID 到标签值的缓存映射增大，内存消耗会显著上升。网络方面，典型工作负载下每个 Prometheus 实例产生约 5–10 MB/min 的出站流量。

远程存储的写入速率必须匹配 Prometheus 的摄入速率。关键监控指标包括：

| 指标 | 含义 |
|------|------|
| `prometheus_remote_storage_samples_pending` | 待发送样本积压量，持续增长表示发送跟不上采集 |
| `prometheus_remote_storage_shards` | 当前活跃 shard 数，持续扩容表示后端压力大 |
| `prometheus_remote_storage_samples_dropped_total` | 丢弃样本数，应保持为零 |
| `prometheus_remote_storage_samples_retries_total` | 重试次数，持续重试指向后端或网络问题 |

#### 限流与背压机制

Remote write 通过 `queue_config` 提供多层限流保护。[官方调优文档](https://prometheus.io/docs/practices/remote_write/) 描述了数据流：WAL → shard 队列 → 远程端点。关键参数：

- **`max_shards`**：最大并行 shard 数。当队列积压时，Prometheus 自动增加 shard 数至上限以提高吞吐。在 churn 尖峰下，可降低 `max_shards` 以限制对后端的并发压力。
- **`capacity`**：每个 shard 的内存队列容量（默认 10000）。队列满后阻塞 WAL 读取，所有吞吐停止。建议设为 `max_samples_per_send` 的 3–10 倍。
- **`max_samples_per_send`**：单次 HTTP 请求的最大样本数（默认 2000）。
- **`min_backoff` / `max_backoff`**：失败重试的退避间隔，后端恢复后分散请求压力。

内存估算公式：`shard 内存 ≈ max_shards × (capacity + max_samples_per_send)`。默认配置下每 shard 内存小于 2 MB。高 churn 场景下，series 缓存（每个 WAL 中的 series 需缓存 ID→标签映射）会显著增加内存，需谨慎调优。

#### Downsampling 策略

Downsampling 在写入前降低序列粒度与保留精度，是控制长期存储中序列数量的关键手段。常用策略包括：

- **时间维度聚合**：将 15s/1m 的原始数据聚合为 5m 或 1h 的摘要（sum、avg、max、min），[可减少长期存储的序列数量](https://last9.io/blog/downsampling-aggregating-metrics-in-prometheus-practical-strategies-to-manage-cardinality-and-query-performance/)。
- **标签维度裁剪**：在聚合时去除高基数标签（如 `pod`、`container_id`），仅保留关键维度（如 `namespace`、`deployment`）。
- **写入前 relabeling**：通过 `write_relabel_configs` 在远程写入前丢弃不需要长期保留的高基数原始序列，仅发送聚合后的低基数序列。

Prometheus 本身不内置 downsampling 功能，通常通过 [recording rules](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/) 预聚合实现，或在远程存储侧（如 Thanos Compactor、Mimir）执行降采样。

#### Prometheus Agent 模式（HP1）

[Prometheus Agent 模式](https://prometheus.io/blog/2021/11/16/agent/)（`--agent` flag，Prometheus 2.32+）是专为 remote-write-only 部署设计的运行模式。其设计目标与对 churn 场景的影响如下：

**消除的组件**：
- **本地 TSDB 存储**：不再将数据写入本地磁盘 block，彻底消除 compaction 链路
- **查询引擎**：禁用 PromQL 查询，本地不保留可查询的数据
- **告警与 recording rules**：所有告警和预聚合必须在远程系统完成

**保留的组件**：
- 完整的 scrape 逻辑、服务发现、relabeling 配置
- 定制化的 TSDB WAL（替代完整 TSDB），用于 remote write 缓冲

**对 churn 场景的直接影响**：Agent 模式将 Prometheus 从"采集+存储+查询"简化为纯采集器，churn 对本地存储的影响被完全规避——没有 head block 内存累积、没有 compaction 压力、没有倒排索引膨胀。[Agent 模式文档](https://github.com/prometheus/prometheus/blob/main/docs/prometheus_agent.md) 指出，定制 WAL 在成功写入远程端点后立即移除数据，仅在远程端点不可用时临时持久化到磁盘（上限 2 小时）。

**代价**：无法本地查询、无法使用 recording rules、无法本地告警。所有监控智能必须下沉到远程存储层。

#### Grafana Agent Flow 模式与替代方案（HP2）

[Grafana Agent Flow 模式](https://grafana.com/docs/agent/latest/flow/) 是基于 OpenTelemetry Collector 的可编程采集管线，提供组件化的 relabeling 和 remote write 能力。其与 Prometheus Agent 模式的关键区别：

| 维度 | Prometheus Agent 模式 | Grafana Agent Flow 模式 |
|------|----------------------|------------------------|
| 架构 | Prometheus 二进制内置模式 | 基于 OpenTelemetry Collector 的组件化管线 |
| 配置格式 | 标准 `prometheus.yml` | Terraform-inspired River 语言 |
| WAL | 定制 TSDB WAL（2h 缓冲） | 基于 Prometheus WAL 优化，可配置 `wal_truncate_frequency` |
| 可观测性 | Web UI（仅 targets/配置） | 组件级调试 UI，管线状态可视化 |
| 扩展性 | 仅指标采集 | 指标、日志、 traces、profiles 统一采集 |
| 资源开销 | 较低（[基准测试](https://victoriametrics.com/blog/comparing-agents-for-scraping/)：19GB RSS） | 较高（25.3GB RSS），但功能更全面 |

**重要更新**：Grafana Agent 已于 [2025 年 11 月 1 日达到 EOL](https://grafana.com/docs/agent/latest/flow/)，不再接收安全更新和 bug 修复，用户应迁移至 [Grafana Alloy](https://grafana.com/blog/grafana-agent-to-grafana-alloy-opentelemetry-collector-faq/)。Alloy 是 Agent Flow 的继承者，保持组件化架构和 River 配置语言。

[VictoriaMetrics 的 vmagent](https://victoriametrics.com/blog/comparing-agents-for-scraping/) 是另一个轻量级替代方案，在基准测试中表现最优（2.2GB RSS，网络用量仅为 Prometheus Agent 的 1/3），支持 stream parsing 模式和自研压缩算法，但仅兼容 VictoriaMetrics 远程存储。

#### Remote Write 2.0 协议改进（HP5）

[Remote Write 2.0 规范](https://prometheus.io/docs/specs/prw/remote_write_spec_2_0/)（2024 年 5 月发布 rc.4，仍为 Experimental）相比 1.0 的关键改进：

1. **新 Protobuf 消息**：引入 `io.prometheus.write.v2.Request` 替代 1.0 的 `prometheus.WriteRequest`，支持更高效的编码格式。[Grafana 博客](https://grafana.com/blog/how-prometheus-remote-write-v2-can-help-cut-network-egress-costs-by-as-much-as-50-/) 报告网络出口成本可降低约 50%，代价仅 5%–10% 的 CPU 和内存增加。
2. **强制 Written 响应头**：接收方必须返回 `X-Prometheus-Remote-Write-Samples-Written`、`X-Prometheus-Remote-Write-Histograms-Written`、`X-Prometheus-Remote-Write-Exemplars-Written` 三个头部，使发送方能精确确认哪些数据被成功写入，改善部分写入失败的处理。
3. **向后兼容**：通过 `Content-Type` 和 `X-Prometheus-Remote-Write-Version` 头部实现内容协商，2.0 发送方可自动降级到 1.0 协议与旧接收方通信。
4. **Native Histograms 支持**：改进原生直方图的编码与传输效率。

对高 churn 场景而言，2.0 的改进主要体现在：更高效的数据编码降低网络带宽压力（churn 尖峰时尤为关键），以及更可靠的写入确认机制减少重试带来的额外负载。

#### 远程写入架构与 Agent 模式的区别与联系

两者并非互斥，而是可组合的架构选择：

- **远程写入架构**：完整 Prometheus + `remote_write` 配置，本地保留 2h retention，数据同时写入本地 TSDB 和远程存储。适用于需要本地查询和告警的场景。
- **Agent 模式**：`--agent` flag 启用，完全消除本地 TSDB、compaction 和查询引擎，仅保留 WAL 用于 remote write 缓冲。适用于纯采集转发场景。
- **组合使用**：Agent 模式本质上是远程写入架构的极致形态——将本地 retention 降至最低（仅 WAL 缓冲），所有存储和查询职责完全委托远程后端。[VictoriaMetrics 基准测试](https://victoriametrics.com/blog/comparing-agents-for-scraping/) 显示，在 churn 场景下，Agent 模式的内存占用（19GB）显著低于完整 Prometheus（69GB），且消除了每 2 小时的 compaction/WAL 截断尖峰。

**选型建议**：若团队需要本地 PromQL 查询或本地告警，使用完整 Prometheus + remote write；若仅需将数据转发到远程存储（如 VictoriaMetrics、Mimir、云厂商托管服务），Agent 模式是更轻量、更高效的选择，且直接规避 churn 对本地存储的所有影响。

### 开源长期存储方案对比：VictoriaMetrics、Thanos、Mimir、GreptimeDB

高流失率场景下，Prometheus 本地 TSDB 的 2 小时 head block 窗口、倒排索引膨胀和 compaction 压力会成为系统性瓶颈。将数据 remote write 到专用长期存储引擎是主流解法。本节深入对比四种开源方案对高 churn 场景的治理能力，并给出选型决策矩阵。

#### VictoriaMetrics：压缩效率与 indexdb 治理

VictoriaMetrics 对高 churn 的核心治理机制围绕其倒排索引（indexdb）的每日轮换与缓存 TTL 匹配展开，包括 `prefillNextIndexDB` 预填充机制和 `cacheExpireDuration` 调优，这些机制的详细原理与"假性高 churn"根因分析见 S1.1。

**压缩效率**：VictoriaMetrics 使用 Zstandard 压缩算法，在真实 node_exporter 数据上比 Prometheus 原生 TSDB 压缩率高约 7 倍，比 TimescaleDB 低约 70 倍存储占用。对于高 churn 场景，更高的压缩比直接降低倒排索引和样本数据的磁盘占用，缓解长范围查询时的 I/O 压力。VictoriaMetrics 单节点版可处理约 1 亿活跃序列和 200 万样本/秒，集群版可水平扩展至数十亿活跃序列。

**`vm_new_timeseries_created_total` 指标**：该指标的统计口径与 PromQL 查询方式详见 S1.1。在 VictoriaMetrics 中，通过 MetricsQL 查询 `sum(rate(vm_new_timeseries_created_total))` 可直接观测集群级 churn rate，用于监控 churn 趋势和诊断 indexdb 轮换问题。

#### Thanos：Object Storage 后端与 Receive 横向扩展

Thanos 采用 Sidecar + Store Gateway + Compactor 的经典架构，将 Prometheus 数据持久化到 S3/GCS 等对象存储中，解决了 Prometheus 单实例的存储和查询扩展性问题。

**Thanos Receive 与 churn 分散**：Thanos Receive 实现了 Prometheus Remote Write API，允许 Prometheus 实例将数据 push 到 Thanos 集群。Receive 节点通过 hashring 将时间序列分布到多个节点，支持 Ketama 一致性哈希算法和 shuffle sharding。对于高 churn 场景，Thanos Receive 的横向扩展能力可以将写入压力分散到多个节点，避免单节点成为瓶颈。但需注意：使用旧的 `hashmod` 算法时，新增 Receiver 节点会导致 series churn 和内存使用尖峰，因为序列会重新分布。Ketama 算法通过一致性哈希解决了这一问题，推荐所有新安装使用。

**降采样功能**：Thanos Compactor 自动执行降采样——40 小时后创建 5m 分辨率数据，10 天后创建 1h 分辨率数据。5m 分辨率将样本量减少 20 倍，1h 分辨率减少 240 倍。对于高 churn 场景，降采样不仅降低存储成本，还减少长范围查询（7d/30d）需要扫描的序列数量，因为查询可以自动选择低分辨率数据。

**架构复杂度代价**：Thanos 的组件数量多（Sidecar、Store Gateway、Compactor、Receive、Ruler、Query），每个组件需要独立的 ACL、端口、DNS、路由表和监控。这种微服务架构虽然提供了灵活的扩展能力，但运维复杂度显著高于 VictoriaMetrics 的单节点或三组件方案。

#### Grafana Mimir：Cortex 的继承者与 10 亿序列实践

**与 Cortex 的关系**：Grafana Mimir 是 Cortex 的 fork 和继承者。2022 年 3 月，Grafana Labs 决定停止支持 Cortex，转而开发 Mimir。Mimir 使用 AGPL 许可证（而非 Cortex 的 GPL），由 Grafana Labs 团队独立维护。Cortex 项目已归档，不再接受新功能开发。对于现有 Cortex 用户，Mimir 提供了从 Cortex 配置生成 Mimir 配置的迁移工具，可在 10 分钟内完成 drop-in 替换。

**架构与多租户**：Mimir 采用微服务架构，核心组件包括 Distributor（写入）、Ingester（内存存储近期数据）、Store-gateway（对象存储历史数据查询）、Compactor（压缩与降采样）、Query-frontend（查询分片与缓存）和 Ruler（告警规则）。多租户通过 `X-Scope-OrgID` HTTP 头实现，每个租户的数据在 Ingester 和对象存储中独立管理。这种设计使 Mimir 天然支持多团队隔离，避免高 churn 租户的"noisy neighbor"问题。

**10 亿活跃序列案例**：Grafana Labs 在 2022 年 4 月公开了将 Mimir 扩展至 10 亿活跃序列的实践。关键设计包括：每个 Ingester 目标 500 万活跃序列；使用 split-and-merge compactor 将 2 小时 block 合并为更大的 block 以减少查询时需要合并的 block 数量；倒排索引优化减少内存占用。该案例中，Mimir 在 10 亿序列规模下仍保持稳定的查询延迟，证明了其在高 churn 场景下的扩展能力。

**Query Sharding（HP3）**：Mimir 的 query sharding 功能将单个 PromQL 查询拆分为多个并行子查询，分发到不同 Querier 执行。对于高 churn 场景，长时间窗口查询（如 7d）需要扫描大量唯一时间序列，query sharding 将数据集分片后并行查询，显著降低查询延迟。例如，`sum(rate(metric[1m]))` 在 shard count 为 4 时会被拆分为 4 个并行子查询，每个子查询处理 1/4 的序列。可分片的聚合操作包括 `sum`、`min`、`max`、`count`、`avg`，而 `absent`、`histogram_quantile`、`sort_desc` 等不可分片。Mimir 还支持基于历史基数估计的动态分片（`-query-frontend.query-sharding-target-series-per-shard`），根据查询返回的序列数自动调整分片数量，避免低基数查询被过度拆分。

**`cardinality_analysis_enabled` 诊断端点（HP4）**：Mimir 通过 `-querier.cardinality-analysis-enabled` 标志启用一组 cardinality 分析 API 端点，包括：
- `GET /api/v1/cardinality/label_names`：按标签名统计 cardinality
- `GET /api/v1/cardinality/label_values`：按标签值统计 cardinality
- `GET /api/v1/cardinality/active_series`：按 selector 获取活跃序列

这些端点专为大规模环境设计，比使用 `/series` 端点或 label names/values 端点进行类似分析要高效得多。Mimir 维护者确认这些 API 在大规模集群上运行良好，未出现显著性能问题。对于 churn 诊断，这些端点可以快速定位高 cardinality 的标签和标签值，帮助识别 churn 来源。

#### GreptimeDB：新兴的三组件方案

GreptimeDB 是较新的 Prometheus 兼容 TSDB，采用三组件架构（metasrv、frontend、datanode），相比 Thanos 和 Mimir 的 5-8 组件微服务架构显著简化了部署和运维。

**资源效率**：GreptimeDB 声称在相同活跃序列数下，内存使用比 Mimir 低 80-90%，比 Cortex 低约 90%。其基准数据显示，每百万活跃序列 GreptimeDB 消耗约 1.23 GiB 内存和 0.91 核 CPU，而 Mimir 消耗约 10.24 GiB 和 2.33 核，Cortex 消耗约 15 GiB 和 10 核。对于高 churn 场景，更低的内存开销意味着在相同硬件预算下可以容纳更多短生命周期序列。

**PromQL 兼容性**：GreptimeDB 的 PromQL 兼容性超过 90%，支持 remote write 摄入和 Prometheus HTTP API。用户报告从 Thanos 迁移到 GreptimeDB 仅需约 30 分钟。但作为 2024 年才开始获得关注的方案，GreptimeDB 在生产环境中的成熟度和社区生态仍落后于 VictoriaMetrics 和 Mimir，特别是在大规模高 churn 场景下的实际案例较少。

**统一可观测性**：GreptimeDB 支持指标、日志和事件的统一存储，可与 Prometheus 数据 join 查询。这一特性对于需要将 metrics 和 logs 关联分析的高 churn 场景（如通过 trace_id 关联请求级指标和日志）有独特价值，但 exemplars 机制在 Prometheus 生态中已部分覆盖了这一需求。

#### 基准测试与资源消耗对比

各方案在查询延迟、压缩比和资源消耗方面的公开数据如下：

| 维度 | VictoriaMetrics | Thanos | Grafana Mimir | GreptimeDB |
|------|----------------|--------|---------------|------------|
| 压缩比（vs Prometheus） | ~7x | ~1x（依赖 Prometheus TSDB） | ~1x（依赖 Prometheus TSDB） | 未公开独立基准 |
| 每百万序列内存 | 未公开统一数据 | 未公开统一数据 | ~10.24 GiB | ~1.23 GiB |
| 每百万序列 CPU | 未公开统一数据 | 未公开统一数据 | ~2.33 核 | ~0.91 核 |
| 查询延迟（中位数） | 20-50ms（典型） | 依赖对象存储延迟 | 依赖分片配置 | 未公开独立基准 |
| 最大活跃序列（单节点） | ~1 亿 | 不适用（分布式） | ~500 万/Ingester | 未公开 |
| 架构复杂度 | 低（单节点/三组件） | 高（5+ 组件） | 高（6+ 组件） | 低（三组件） |

#### 选型决策矩阵

| 场景 | 推荐方案 | 理由 | 代价 |
|------|---------|------|------|
| 单集群、<1 亿序列、高 churn | VictoriaMetrics 单节点 | 部署简单、压缩比高、indexdb 预填充直接治理 churn 尖峰 | 单节点扩展上限约 1 亿序列 |
| 多团队、多租户、>1 亿序列 | Grafana Mimir | 多租户隔离、query sharding 优化高基数查询、10 亿序列验证 | 架构复杂、组件多、运维成本高 |
| 已有对象存储、需要长期归档 | Thanos | 对象存储原生、降采样成熟、生态成熟 | 组件最多、运维最复杂、hashmod 有 churn 问题 |
| 资源敏感、需要 metrics+logs 统一 | GreptimeDB | 内存效率最高、三组件架构、统一存储 | 成熟度较低、大规模案例少 |
| 已有 Cortex 部署 | 迁移至 Mimir | drop-in 替换、10 分钟迁移 | 需验证 AGPL 许可证合规 |
| 多云/混合云 | VictoriaMetrics 或 Mimir | 两者均支持跨云部署 | 需自行管理跨云网络 |

**关键决策因素**：
- **churn 治理优先级**：VictoriaMetrics 的 indexdb 预填充与缓存 TTL 调优直接针对 churn 根因（机制详见 S1.1），是 churn 治理最精细的方案
- **查询性能**：Mimir 的 query sharding 对高 churn 场景下的长范围查询改善最显著
- **运维复杂度**：VictoriaMetrics 和 GreptimeDB 的三组件架构远优于 Thanos 和 Mimir 的 5-8 组件架构
- **生态成熟度**：Mimir 和 Thanos 拥有最大的社区和最多的生产案例；GreptimeDB 作为新方案仍需时间验证

### 架构模式：分片、联邦与降采样

当单实例 Prometheus 无法承载高流失率带来的内存、compaction 和查询压力时，需要在架构层面引入分片（sharding）、联邦（federation）和降采样（downsampling）等模式。这些模式可以独立使用，也常与远程存储方案（S3.2–S3.3）组合，形成分层治理体系。

#### 分片：用 `hashmod` relabeling 分散负载

Prometheus 分片的核心思路是将抓取目标分散到多个 Prometheus 实例，使每个实例只处理一部分时间序列，从而降低单实例的 active series 数量和 head block 内存占用。最常用的分片机制是 `relabel_configs` 中的 `hashmod` action。

`hashmod` 的工作原理是：对指定标签值的拼接字符串计算 MD5 哈希，再对 N 取模，将结果写入一个临时标签，随后用 `keep`/`drop` 按模值过滤目标。其配置方式如下：

```yaml
# 分片实例 0（共 3 个分片）
scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__address__]
        modulus: 3
        target_label: __tmp_hashmod
        action: hashmod
      - source_labels: [__tmp_hashmod]
        regex: "0"
        action: keep
```

上述配置中，`__address__` 是目标的 `host:port`，`modulus: 3` 表示总分片数为 3，`regex: "0"` 表示当前实例只保留哈希模值为 0 的目标。每个分片实例使用不同的 `regex` 值（0、1、2）即可实现互斥分片。

**分片策略选择**：

| 策略 | 实现方式 | 适用场景 | 局限 |
|------|---------|---------|------|
| 按 target 哈希分片 | `hashmod` on `__address__` | 通用场景，目标分布均匀 | 同一 job 的序列分散到不同分片，跨分片聚合查询复杂 |
| 按 job 分片 | 不同 job 分配到不同实例 | 团队/业务边界清晰 | 单 job 过大时无法再拆分 |
| 按 namespace 分片 | `hashmod` on `__meta_kubernetes_namespace` | K8s 多团队隔离 | 需配合 `external_labels` 标识来源 |

分片能有效降低单个实例的 active series 数量——N 个分片理论上将单实例负载降至 1/N。但分片后面临两个关键问题：

1. **跨分片查询**：单个分片只持有部分序列，聚合查询（如 `sum by (job) (rate(http_requests_total[5m]))`）需要访问所有分片。Thanos Query 通过全局视图解决此问题——它从所有分片实例的 Store Gateway 或 Sidecar 拉取数据并合并结果。Thanos 的 [vertical query sharding](https://thanos.io/tip/proposals-accepted/202205-vertical-query-sharding.md/) 进一步将大查询按 series 分组标签拆分为多个子查询并行执行，降低单 Querier 的内存压力。

2. **跨分片告警**：告警规则需要全局视图才能正确评估。常见做法是在分片之上部署一个全局 Prometheus 或 Thanos Ruler，通过 `/federate` 端点或 remote write 聚合分片数据后执行告警评估。社区反馈在分片场景下 Thanos Query UI 的告警展示可能不完整，需通过 Thanos Ruler 集中管理告警规则。

#### 联邦：分层聚合多集群数据

[Prometheus 联邦](https://prometheus.io/docs/prometheus/latest/federation/)通过 `/federate` 端点实现层级化数据聚合。与分片不同，联邦不追求负载分散，而是构建一个树形拓扑：叶子节点（leaf Prometheus）保留高基数原始指标，全局节点（global Prometheus）只拉取预聚合的低基数序列。

典型配置如下：

```yaml
# 全局 Prometheus 从区域实例联邦预聚合指标
scrape_configs:
  - job_name: 'federate-eu-west'
    scrape_interval: 30s
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{__name__=~"job:.*"}'
        - '{__name__=~"namespace:.*"}'
        - 'up{job="kubernetes-apiservers"}'
    static_configs:
      - targets:
          - prometheus-eu-west.monitoring.svc:9090
```

联邦的关键设计原则是**只联邦聚合指标**。叶子节点通过 recording rules 将高基数序列（如 per-pod HTTP 请求率）预聚合为低基数序列（如 `job:http_requests_total:rate5m`），全局节点仅拉取这些聚合结果。这样全局节点的 active series 数量远低于所有叶子节点之和，同时仍能提供跨集群的全局视图。

**联邦的局限**：

- `/federate` 端点返回的是瞬时值快照，不支持范围查询（range query），因此全局节点无法对联邦数据执行 `rate()` 等需要时间窗口的操作。
- 全局节点成为单点故障——如果它不可用，跨集群视图中断。
- 网络分区或延迟可能导致联邦数据不完整，产生监控盲区。
- 联邦不提供长期存储，数据保留期受叶子节点 retention 限制。

**AWS AMP 的联邦支持**：AWS AMP 支持跨区域查询，可通过 [resource policy](https://last9.io/blog/aws-prometheus-production-patterns/) 允许一个 workspace 查询另一个 workspace 的数据。但 AMP 本身不提供 `/federate` 端点——跨区域查询是通过 AMP 的查询 API 实现的，而非 Prometheus 原生联邦协议。在 AWS 环境中，更常见的模式是各区域 Prometheus 通过 `remote_write` 将数据推送到 AMP，由 AMP 统一存储和查询。

#### 降采样：用精度换查询性能

降采样（downsampling）将高分辨率原始数据聚合为低分辨率数据，使长时间范围查询（如 7d、30d）只需扫描少量数据点，从而大幅降低查询延迟和内存消耗。在 Prometheus 生态中，降采样主要在远程存储层实现。

**Thanos Compactor 的降采样**：

[Thanos Compactor](https://thanos.io/tip/components/compact.md/) 支持两级降采样：5 分钟和 1 小时分辨率。降采样过程将原始 block 中的序列重写为 `AggrChunk` 格式，包含 min_time、max_time、raw、count、sum、min、max、counter 七种聚合值，确保在低分辨率下仍能准确回答聚合查询。

```bash
# Thanos Compactor 降采样与保留配置
thanos compact \
  --data-dir /tmp/thanos-compact \
  --objstore.config-file=bucket.yml \
  --retention.resolution-raw=30d \
  --retention.resolution-5m=120d \
  --retention.resolution-1h=365d
```

关键注意事项：

- **降采样不节省存储空间**：由于 `AggrChunk` 同时存储多种聚合值，降采样后的数据量约为原始数据的 3 倍。降采样的目标是**查询性能**而非存储成本。
- **保留期须递增**：`retention.resolution-raw` 应短于 `retention.resolution-5m`，后者应短于 `retention.resolution-1h`。如果某级保留期短于下一级降采样的最小等待时间（5m→1h 需 10 天），数据会在降采样完成前被删除。
- **Compactor 必须单实例运行**：同一 bucket 同一 stream 只能有一个 Compactor，否则会导致 overlap 问题。

**Mimir 的降采样现状**：

截至 2024–2025 年，[Grafana Mimir 不支持降采样](https://community.grafana.com/t/intro-to-mimir-webinar-q-a/102614)。Mimir 的 [compactor](https://grafana.com/docs/mimir/latest/references/architecture/components/compactor/) 采用 split-and-merge 压缩策略，通过垂直 compaction（合并同一时间范围的多个 block）和水平 compaction（合并相邻时间范围的 block）减少 block 数量和索引大小，但不生成低分辨率聚合数据。Mimir 社区有[降采样提案](https://github.com/grafana/mimir/discussions/1834)讨论，但尚未进入实现阶段。

这意味着在需要长时间范围查询的场景下，Thanos 的降采样能力是 Mimir 不具备的优势。Mimir 用户通常通过 recording rules 在摄入侧预聚合来弥补这一缺陷。

#### 架构模式组合最佳实践

实际生产环境中，上述模式通常组合使用，形成分层架构：

| 组合模式 | 架构 | 适用场景 | 关键收益 |
|---------|------|---------|---------|
| 分片 + Thanos | 多 Prometheus 分片 → Thanos Sidecar → Object Storage → Thanos Query | 大规模 K8s 集群，需全局查询和告警 | 分片降低单实例负载，Thanos 提供全局视图和降采样 |
| 分片 + Mimir | 多 Prometheus 分片 → remote write → Mimir | 多租户场景，需 per-tenant 配额和隔离 | 分片分散采集压力，Mimir 提供多租户和水平扩展 |
| 联邦 + 远程存储 | 叶子 Prometheus → recording rules → 全局 Prometheus `/federate` → remote write → 长期存储 | 多区域/多团队，需分层治理 | 联邦聚合降低全局节点基数，远程存储提供长期保留 |
| Agent 模式 + 云厂商 | Prometheus Agent → remote write → AWS AMP / GMP / Azure | 纯采集场景，无本地查询需求 | Agent 消除本地 TSDB，云厂商处理存储和查询 |

**组合使用的关键原则**：

1. **分片与远程存储互补**：分片解决单实例采集和 head block 内存问题，远程存储解决长期保留和全局查询问题。分片后的每个 Prometheus 实例仍可通过 `remote_write` 将数据推送到 Thanos/Mimir，实现"分散采集、集中存储"。

2. **联邦与 recording rules 配合**：联邦本身不降低叶子节点的 churn，但通过在叶子节点部署 recording rules 预聚合高 churn 指标，可以显著减少联邦到全局节点的序列数量，降低全局节点的 active series 和查询延迟。

3. **降采样与保留策略协同**：Thanos 的三级保留期（raw → 5m → 1h）应与查询模式匹配。如果业务只需要 7 天内的"缩放"能力和 30 天以上的趋势视图，可以设置 `retention.resolution-raw=7d`、`retention.resolution-5m=30d`、`retention.resolution-1h=365d`，在存储成本和查询能力之间取得平衡。

4. **避免过度分片**：分片数并非越多越好。每个分片实例都有固定开销（head block 内存、compaction CPU），分片过多会导致资源碎片化和运维复杂度上升。一般建议单实例 active series 控制在 100–300 万以内，超过此阈值再考虑分片。

### 检测、诊断与持续监控

高流失率的治理离不开一套可操作的检测与诊断方法论。本节聚焦运维工作流：如何利用 Prometheus 自带指标和工具定位 churn 来源、如何区分"正常 churn"与"异常 churn"、以及如何将 churn 监控纳入日常运营。指标定义与 PromQL 语义见 S1.1，此处不重复。

#### 持续监控与告警体系

建立 churn rate 持续监控的核心是组合使用 `scrape_series_added` 和 `prometheus_tsdb_head_series_created_total` 两个指标，分别覆盖"实时检测"和"趋势分析"两个层面。

**实时 per-target churn 检测。** `scrape_series_added`（Prometheus 2.10+）记录每次 scrape 中新增到 scrape cache 的时间序列数。Robust Perception 博客推荐使用以下 PromQL 定位 churn 最高的 target：

```promql
topk(10, sum without(instance)(sum_over_time(scrape_series_added[1h])))
```

该查询按 job 聚合过去 1 小时的新增序列数（忽略 instance 标签以合并同一 job 的多个实例），返回 churn 贡献最大的 10 个 target。社区实践中，Reddit 用户进一步追问如何从已定位的高 churn instance 下钻到具体 metric——这需要结合 `/api/v1/series` 端点或 `count by (__name__)({instance="ABC"})` 查询，但后者仅统计序列数而非唯一时间序列，无法直接等价于 churn 贡献。

**集群级 churn 趋势监控。** 集群级 churn rate 趋势可通过 `rate(prometheus_tsdb_head_series_created_total[5m])` 观察（指标定义与 PromQL 语义见 S1.1）。将该指标与 `prometheus_tsdb_head_series`（当前活跃序列数）对比，可以判断 churn 是"净增长"（活跃序列数同步上升）还是"替换型"（活跃序列数稳定但 created 速率高）。

**告警阈值设定。** 合理的告警阈值应基于基线而非绝对值。Robust Perception 在告警阈值设置建议中提出：查看过去数周的指标曲线，取正常波动范围的上限作为告警阈值，并在此基础上增加安全余量。对于 churn rate，建议采用分级告警：

| 告警级别 | 条件（示例） | 含义 |
|---------|------------|------|
| Warning | `rate(prometheus_tsdb_head_series_created_total[5m]) > 基线 × 2` | churn 速率翻倍，需关注 |
| Critical | `rate(prometheus_tsdb_head_series_created_total[5m]) > 基线 × 5` | 异常 churn，可能标签设计错误 |
| 紧急 | `prometheus_tsdb_head_series` 接近内存容量上限 | 即将触发 OOM |

基线应考虑部署频率（如每日部署窗口的 churn 尖峰）、K8s 集群规模（Pod 数量与 churn 正相关）和标签设计（高基数标签的 churn 贡献）。建议将告警规则按 job 或 namespace 分组，避免单一 target 的异常触发全局告警。

#### `scrape_series_added` 的局限性与注意事项

`scrape_series_added` 的局限性（可能低估或高估、不包含 `up`/`scrape_*` 指标、scrape cache 重置、仅反映 scrape 阶段）详见 S1.1。在运维实践中，`scrape_series_added` 适合作为 per-target churn 的实时检测工具，但不应作为集群级 churn 的唯一度量。集群级 churn 趋势应结合 `prometheus_tsdb_head_series_created_total` 和 `./tsdb analyze` 离线分析交叉验证。

#### 区分"正常 churn"与"异常 churn"

并非所有 churn 都需要治理。区分正常与异常 churn 的关键在于判断 churn 的来源模式：

**正常 churn（良性）** 通常表现为：
- **周期性尖峰**：与 K8s 部署窗口对齐，如每日固定时间的 Deployment 更新导致 Pod 标签值变化。`pod`、`container` 标签的 churn 在每次部署后出现，随后趋于平稳。
- **可预测的标签变化**：CronJob 或批处理任务每次运行产生新标签组合，但运行间隔和标签模式已知。
- **indexdb 轮换导致的假性尖峰**：每日 0 点 VictoriaMetrics indexdb 轮换时，缓存过期导致 `vm_new_timeseries_created_total` 出现尖峰，但实际活跃序列数未变（机制详见 S1.1）。

**异常 churn（恶性）** 通常表现为：
- **持续高 churn 无回落**：`rate(prometheus_tsdb_head_series_created_total[5m])` 持续高于基线，不随部署窗口回落。
- **高基数标签驱动**：`trace_id`、`user_id`、`request_id` 等高基数标签直接作为 label，导致每次请求产生新时间序列。`./tsdb analyze` 输出中 "Highest cardinality labels" 部分会显示这些标签。
- **标签值长度异常**：`./tsdb analyze` 的 "Label names with highest cumulative label value length" 部分可识别异常长的标签值（如将完整 URL 或 JSON 作为 label 值）。

**诊断流程建议**：当检测到异常 churn 时，按以下步骤定位根因：
1. 用 `topk(10, sum without(instance)(sum_over_time(scrape_series_added[1h])))` 定位高 churn 的 job。
2. 用 `./tsdb analyze` 分析对应时间段的 TSDB block，查看 "Label pairs most involved in churning" 和 "Highest cardinality labels"。
3. 检查高 cardinality 标签是否为已知的高基数标签（trace_id、user_id 等），或是否为标签设计错误（如将动态路径作为 label）。

#### Prometheus `./tsdb` 离线分析工具

Prometheus 自带的 `promtool tsdb analyze` 命令（早期版本为独立 `./tsdb` 工具）可对 TSDB block 进行离线分析，是 churn 诊断的核心工具。该工具仅读取 block 索引，不读取样本数据，因此比 PromQL 查询更高效，且可在 Prometheus 正在使用的 block 上运行（block 是只读的）。

**使用方式**：

```bash
# 列出所有 block
promtool tsdb list /var/lib/prometheus

# 分析指定 block
promtool tsdb analyze /var/lib/prometheus 01KVJAKHJQ6NTDQY1Q01BAF8TE --limit=5

# 按指标名过滤分析
promtool tsdb analyze --match='{__name__="api_request_duration_seconds_count"}' /var/lib/prometheus 01KVJAKHJQ6NTDQY1Q01BAF8TE
```

**输出内容**包含以下关键部分：

| 输出部分 | 内容 | churn 诊断价值 |
|---------|------|--------------|
| 概览 | block 路径、时间范围、序列数、标签名数、postings 统计 | 了解 block 整体规模 |
| Label pairs most involved in churning | 参与 churn 最多的标签对及其稀疏度 | **直接定位 churn 来源标签** |
| Label names most involved in churning | 参与 churn 最多的标签名 | 识别高 churn 标签维度 |
| Most common label pairs | 最常见的标签对 | 了解基数分布 |
| Highest cardinality labels | 基数最高的标签 | 识别高基数标签 |
| Highest cardinality metric names | 基数最高的指标名 | 定位高基数指标 |

"Label pairs most involved in churning" 中的数值表示该标签对在时间序列中的稀疏程度。例如，`job=node` 的值为 17 可能意味着在 2 小时 block 中有 34 个时间序列缺失了 1 小时，或 68 个序列缺失了半小时。该数值本身需与总序列数对比才有意义——数值越高说明该标签对的 churn 越严重。

**注意事项**：`promtool tsdb analyze` 在大型数据目录上可能产生显著的磁盘和内存压力。建议在 Prometheus 主机的低峰期运行，或对数据目录的拷贝快照进行分析。

#### Palark 博客：churn 作为资源优化一等公民

Palark 博客 "Understanding and optimizing resource consumption in Prometheus" 从资源消耗角度系统分析了 Prometheus 的内存分布，将 TSDB 存储列为最大资源消耗者（远超 scraping 的 30% 和 UI 的 10%）。该文指出，TSDB 的内存消耗主要来自两个维度：

1. **数据处理**：每个时间序列对应一个 chunk（默认 120 个数据点），chunk 使用 GORILLA 算法压缩值、Delta-Delta 算法压缩时间戳。高 churn 意味着大量短生命周期序列在 2 小时 head block 窗口内累积，每个序列都需要独立的 chunk 和内存映射。
2. **标签集存储**：所有标签集存储在 Index 结构中，包含 Symbols（字符串去重）和 Postings（标签值到序列 ID 的倒排索引）。高 churn 导致标签值频繁变化，Index 结构持续膨胀。

Palark 的分析将 churn 问题定位为"资源消耗优化的核心矛盾"——不仅是瞬时基数问题，更是时间维度上的累积效应。该文建议通过 pprof 工具分析 Prometheus 进程的内存分布，确认 TSDB 是否为内存消耗的主要来源，再决定是优化标签设计还是引入远程存储。

#### 社区诊断工具与脚本

除 Prometheus 自带工具外，社区还发展了多种 churn 诊断工具：

- **Prometheus `/api/v1/status/tsdb` 端点**：返回 TSDB 的基数统计信息，包括 `numSeries`（head block 中的总序列数）和 `topMetrics`（按序列数排名的前 10 个指标名）。该端点适合快速查看当前 head block 的基数概况，但仅覆盖最近 2-3 小时的数据。Last9 博客推荐将此端点作为 cardinality 诊断的第一步。
- **Grafana 仪表盘**：官方 Prometheus Stats 仪表盘（ID: 1860）和 Prometheus 2.0 Stats（ID: 3662）可视化序列数、churn 相关指标。Grafana Cloud 还提供专门的 cardinality management dashboards，支持按 job、instance、label 维度下钻分析。
- **`promtool check metrics`**：对指标进行 lint 检查，可发现标签一致性问题。`promtool check rules` 可检查 recording rules 和 alerting rules 的有效性。
- **Thanos 的 `/api/v1/status/tsdb` 联邦查询**：Thanos Receive 组件支持通过 `THANOS-TENANT` HTTP 头获取各租户的 TSDB 统计信息，适合多租户场景下的 churn 诊断。

#### 将 churn 监控纳入日常运营

将 churn 监控纳入日常运营的关键是建立标准化的诊断 runbook：

1. **日常巡检**：每日检查 `rate(prometheus_tsdb_head_series_created_total[5m])` 趋势，与基线对比。关注 `prometheus_tsdb_head_series` 是否接近内存容量上限。
2. **部署窗口监控**：在已知部署窗口（如 K8s 每日部署）期间，churn 尖峰属正常现象。但需确认尖峰在部署后回落，而非持续高位。
3. **周级离线分析**：每周运行一次 `promtool tsdb analyze`，分析最近 24 小时的 TSDB block，检查 "Label pairs most involved in churning" 是否有新增的高 churn 标签。
4. **告警响应**：当 churn rate 告警触发时，按以下流程处理：
   - 用 `topk` 查询定位高 churn job
   - 用 `./tsdb analyze` 分析对应 block，识别高 churn 标签
   - 检查是否为标签设计错误（如 trace_id 作为 label）或正常业务变化（如新服务上线）
   - 根据诊断结果决定是 relabeling 裁剪、recording rules 预聚合，还是调整采集策略
5. **容量规划**：结合 churn rate 趋势和 `prometheus_tsdb_head_series` 增长趋势，预估未来 1-3 个月的内存和存储需求，提前规划扩容或迁移到远程存储。

通过上述方法，churn 监控可以从被动响应转变为主动治理，在 churn 问题影响系统稳定性之前及时发现并处理。

## 云厂商现有方案对比

### AWS：Amazon Managed Service for Prometheus（AMP）

AWS Amazon Managed Service for Prometheus（AMP）是一项完全托管的 Prometheus 兼容监控服务，专为容器基础设施和应用程序指标设计，支持高基数指标监控场景。AMP 将 Prometheus 的部署、扩展、安全和高可用性交由 AWS 管理，用户无需运维 Prometheus 服务器本身，同时提供与原生 Prometheus 兼容的 PromQL 查询、告警规则和 recording rules 能力。

#### 架构与 Agentless Collector

AMP 的核心架构由 **Workspace**（逻辑隔离的指标存储与查询空间）、**Scraper/Collector**（指标采集器）和 **Remote Write 端点**三部分组成。数据可通过多种方式写入 AMP Workspace：AWS Managed Collectors（agentless）、自建 Prometheus Server 的 `remote_write`、AWS Distro for OpenTelemetry（ADOT）、Grafana Agent 等，所有写入均通过 [SigV4 签名认证](https://aws.amazon.com/blogs/opensource/best-practices-for-migrating-self-hosted-prometheus-on-amazon-eks-to-amazon-managed-service-for-prometheus/)。

2023 年 11 月，AWS 发布了 **AMP Agentless Collector**（Managed Collectors），这是 AMP 架构的关键组件。该采集器通过为每个指定子网创建 [Elastic Network Interface（ENI）](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP-collector-how-to.html) 直接抓取 EKS 集群中的 Prometheus 兼容指标，并通过 `remote_write` 将数据推送至 AMP Workspace。其核心优势在于：

- **零运维负担**：AWS 完全管理 scraper 的部署、扩展和高可用，无需在 EKS 集群中部署任何 agent 或 sidecar 容器。
- **自动发现与抓取**：scraper 自动发现 EKS 集群中的 Prometheus 端点并抓取指标，支持 Kubernetes 1.28+ 集群的控制平面指标（kube-scheduler、kube-controller-manager）。
- **跨账户支持**：通过 IAM Role Configuration 实现跨账户指标采集，适用于集中式监控架构（如多团队共享一个 AMP Workspace）。
- **安全集成**：通过 EKS Access Entry 或 aws-auth ConfigMap 授权 scraper 访问集群指标，结合 [AWS PrivateLink](https://aws.amazon.com/blogs/opensource/best-practices-for-migrating-self-hosted-prometheus-on-amazon-eks-to-amazon-managed-service-for-prometheus/) 实现 VPC 内安全访问。

Agentless Collector 的计费为 [$0.04/采集器小时 + $0.03/每 10M 采集样本](https://aws.amazon.com/prometheus/pricing/)，在 EKS 场景下相比自建 Prometheus 可显著降低运维成本，但采集的样本仍按 AMP 标准摄入费率计费。

#### Label-Based Active Series Limits（2025 年 4 月）

2025 年 4 月，AMP 推出了 **label-based active series limits** 功能，这是应对高流失率场景的核心治理机制。该功能允许在 Workspace 内按标签集合（label set）设置独立的活跃时间序列配额，实现多租户隔离和 noisy neighbor 防护。

**工作原理**：通过定义 key-value 标签对（如 `{app="payment-service", environment="prod"}`），为每个标签集合设置独立的 `maxSeries` 上限。当某个标签集合的指标出现意外激增（如配置错误导致大量新时间序列产生），仅该标签集合的指标被限流（throttled），其他工作负载不受影响。

**配置方式**：通过 [Workspace Configuration API](https://docs.aws.amazon.com/cli/latest/reference/amp/update-workspace-configuration.html) 配置，支持 AWS Console、AWS CLI 和 SDK。CLI 示例如下：

```json
{
    "workspaceId": "<WORKSPACE_ID>",
    "limitsPerLabelSet": [
        {
            "limits": { "maxSeries": 1000000 },
            "labelSet": {
                "app": "payment-service",
                "environment": "prod"
            }
        }
    ],
    "retentionPeriodInDays": 30
}
```

```bash
aws amp update-workspace-configuration --workspace-id <WORKSPACE_ID> --cli-input-json file://config.json
```

配置标签集合限制后，还需在 Managed Collector 的 scrape 配置中添加匹配的 `external_labels`，使采集的指标携带对应标签以匹配标签集合规则。每个 Workspace 最多可创建 [100 个标签集合限制](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP_quotas.html)。

**对 churn 治理的意义**：在高流失率场景下，label-based limits 将"noisy neighbor"问题从 Workspace 级别隔离到标签集合级别。例如，一个团队的 K8s Pod 频繁伸缩导致 `pod` 标签值持续变化、产生大量新时间序列，只会触发该团队标签集合的限流，而不会影响其他团队的指标摄入。

#### 默认 50M Active Series 上限（2025 年 7 月）

2025 年 7 月，AWS 将 AMP Workspace 的默认活跃时间序列上限从 10M 提升至 [50M](https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-managed-service-prometheus-50M-default-activeserieslimit/)，无需申请即可自动生效。关键配额细节如下：

| 配额项 | 默认值 | 最大值 | 说明 |
|--------|--------|--------|------|
| Active series per workspace | 50M | 1B | 过去 2 小时内有样本上报的序列；2M–50M 区间根据近 30 分钟用量自动调整 |
| Ingestion rate per workspace | 170,000 samples/s | 可调 | 基于 token bucket 算法限流 |
| LabelSet limits per workspace | 100 | 可调 | 每个标签集合限制的数量上限 |
| Labels per metric series | 150 | 可调 | 单条序列的最大标签数 |
| Label size | 7 KB | 不可调 | 所有标签名+值的总大小上限 |

**自动扩缩机制**：AMP Workspace 的活跃序列容量会根据用量自动调整——当 30 分钟平均用量低于 5M 时容量翻倍（如 3.5M → 7M）；当用量超过 5M 时增加 10M 缓冲（如 25M → 35M）。最低容量为 2M，低于 2M 时不触发限流。超出默认配额后，可申请提升至最高 1B，但扩容后若 2 小时内用量翻倍或超过前基线 50M，仍可能触发限流。

**超限行为**：当活跃序列数超过配额时，AMP 会丢弃新样本并在 CloudWatch 中记录 `DiscardedSamples`（reason 为 `rate_limited` 或 `active_series_limit`）。被限流的样本不会重试，直接丢弃。

#### CloudWatch 指标与 Churn 诊断

AMP 通过 CloudWatch 提供丰富的使用指标，其中与流失率监控和诊断直接相关的指标包括：

| CloudWatch 指标 | 命名空间 | 说明 |
|----------------|----------|------|
| `ActiveSeries` | AWS/Usage | 当前 Workspace 活跃时间序列总数 |
| `IngestionRate` | AWS/Usage | 每秒摄入样本数 |
| `DiscardedSamples` | AWS/Prometheus | 被丢弃的样本数（按原因分类） |
| `ActiveSeriesPerLabelSet` | AWS/Prometheus | 每个标签集合的当前活跃序列数 |
| `ActiveSeriesLimitPerLabelSet` | AWS/Prometheus | 每个标签集合的配置上限 |
| `IngestionRatePerLabelSet` | AWS/Prometheus | 每个标签集合的摄入速率 |
| `DiscardedSamplesPerLabelSet` | AWS/Prometheus | 每个标签集合被丢弃的样本数 |

`DiscardedSamples` 指标在 churn 场景下尤为关键。根据 [AWS 文档](https://aws.amazon.com/blogs/mt/optimizing-metrics-ingestion-with-amazon-managed-service-for-prometheus/)，样本被丢弃的原因包括：

- **超过活跃序列上限**：应用程序产生的唯一时间序列超过 Workspace 容量——这是高流失率最直接的体现，大量短生命周期序列在 2 小时窗口内累积导致活跃序列数激增。
- **达到摄入速率上限**：流量尖峰或多系统同时推送大量指标时触发 token bucket 限流。
- **乱序样本**：时间戳超出可接受窗口的样本（通常由时钟同步问题导致）。

通过 `DiscardedSamplesPerLabelSet`，可以精确定位哪个标签集合（即哪个应用或团队）的 churn 导致了样本丢弃，实现 churn 的 per-team 归因。结合 `ActiveSeriesPerLabelSet` 与 `ActiveSeriesLimitPerLabelSet` 的对比，可以提前预警即将触达的配额上限。

#### 计费模型与 Churn 成本影响

AMP 的计费模型由四个维度组成：

| 计费项 | 费率 | 说明 |
|--------|------|------|
| 指标摄入 | $0.90/10M 样本（前 2B） | 阶梯定价，用量越大单价越低 |
| 存储 | $0.03/GB | 按存储的指标样本和元数据总量计费 |
| 查询 | $0.10/B 样本处理 | 按 Query Samples Processed（QSP）计费 |
| Agentless Collector | $0.04/小时 + $0.03/10M 采集样本 | 仅在使用 Managed Collectors 时 |

**高流失率对成本的影响路径**：

1. **摄入成本线性增长**：高 churn 意味着更多新时间序列在 2 小时活跃窗口内累积，每个序列持续产生样本，直接推高摄入量。例如，一个 10 节点 EKS 集群每节点 1000 指标、30 秒采集间隔，月摄入约 892.8M 样本，仅摄入费用即约 [$80.93/月](https://aws.amazon.com/prometheus/pricing/)。

2. **存储成本随序列数与保留期增长**：AMP 默认保留期为 30 天（可通过 Workspace Configuration 调整）。高 churn 导致更多唯一序列的元数据（指标名、标签、标签值）需按日存储，元数据量与序列数和标签基数成正比。

3. **限流导致数据丢失的隐性成本**：当 churn 推高活跃序列数超过配额时，`DiscardedSamples` 增加，意味着监控数据不完整，可能影响告警可靠性。label-based limits 可将此影响隔离到特定标签集合，避免全局性数据丢失。

4. **查询成本放大**：高 churn 场景下，长时间窗口查询（如 7d）需扫描更多唯一时间序列，QSP 增加导致查询费用上升。

#### 混合架构：自建 Prometheus + Remote Write 到 AMP

AMP 支持混合架构，即自建 Prometheus Server 通过 `remote_write` 将数据写入 AMP Workspace，同时保留本地 TSDB 用于短期存储和告警。这种架构的取舍如下：

**适用场景**：已有自建 Prometheus 投资、需要本地 recording rules/alerting rules、或需要保留本地查询能力的团队。

**优势**：
- 本地 Prometheus 保留完整的 TSDB 功能（compaction、本地查询、告警评估），AMP 作为长期存储和集中查询后端。
- 可通过 [Grafana Agent](https://aws.amazon.com/blogs/opensource/best-practices-for-migrating-self-hosted-prometheus-on-amazon-eks-to-amazon-managed-service-for-prometheus/) 替代完整 Prometheus Server，降低约 40% 内存占用，同时支持分片（sharding）。
- 支持 [IRSA](https://aws.amazon.com/blogs/opensource/best-practices-for-migrating-self-hosted-prometheus-on-amazon-eks-to-amazon-managed-service-for-prometheus/) 和 [PrivateLink](https://aws.amazon.com/blogs/opensource/best-practices-for-migrating-self-hosted-prometheus-on-amazon-eks-to-amazon-managed-service-for-prometheus/) 实现安全写入。

**代价**：
- 仍需运维自建 Prometheus Server（部署、扩展、高可用），无法完全消除运维负担。
- 本地 TSDB 仍受高 churn 影响——head block 内存占用、compaction 压力、WAL replay 等问题依然存在。
- 双重计费：本地 Prometheus 的 EC2 资源成本 + AMP 的摄入/存储/查询费用。

**迁移建议**：对于纯 EKS 环境且 churn 较高的场景，优先使用 Agentless Collector 替代自建 Prometheus，可完全规避本地 TSDB 的 churn 影响。对于需要本地告警评估或 recording rules 的场景，可保留 Prometheus Agent 模式（`--agent` flag）+ remote write 到 AMP，消除本地 TSDB 的同时保留采集和规则评估能力。

#### 小结

AWS AMP 通过 agentless collector、label-based active series limits 和 50M 默认上限三层机制，为高流失率场景提供了系统性的治理框架。其核心优势在于将 churn 的影响从 Workspace 级别隔离到标签集合级别，并通过 CloudWatch 指标实现 churn 的精确诊断和归因。对于 AWS 生态内的用户，AMP 是 churn 治理的优先选择；但对于已有自建 Prometheus 且 churn 极高的场景，需评估混合架构中本地 TSDB 的 churn 影响是否仍构成瓶颈。

### GCP：Managed Service for Prometheus

Google Cloud Managed Service for Prometheus (GMP) 是 Google Cloud 提供的完全托管、水平可扩展、Prometheus 兼容的监控服务，构建于 Google 内部使用的同一全球可扩展时序数据库 [Monarch](https://research.google/pubs/pub50652/) 之上。GMP 于 2022 年 3 月正式 GA，将数据采集、查询评估、规则/告警评估和数据存储拆分为独立组件，由 Google SRE 团队维护，用户无需管理 Prometheus 基础设施即可实现全球规模的指标监控与告警。

#### 架构与 Cloud Monitoring 的关系

GMP 与 Cloud Monitoring（原 Stackdriver）共享同一后端和 API 层。在标准 Prometheus 部署中，数据采集、查询评估、规则评估和数据存储全部由单个 Prometheus 服务器处理；GMP 将这些职责拆分到多个组件：

- **数据采集**：由 managed collectors、self-deployed collectors、OpenTelemetry Collector 或 Ops Agent 处理，支持 Kubernetes、Serverless（Cloud Run）和 VM 工作负载，可运行于 GCP 之外（on-prem 或其他云）。
- **查询评估**：由 Monarch 执行查询并跨所有 Google Cloud 区域和最多 3,500 个项目合并结果。
- **规则/告警评估**：通过 Cloud Monitoring 中的 PromQL 告警完全在云端执行，或使用独立规则评估器（standalone rule evaluator）在本地执行规则并将触发的告警转发至 Prometheus AlertManager。
- **数据存储**：由 Monarch 存储所有 Prometheus 数据，保留 24 个月，无额外费用。

GMP 与 Cloud Monitoring 的关系是**同一后端、统一查询**：Cloud Monitoring 指标和 GMP 摄入的指标均可通过 Cloud Monitoring UI 中的 PromQL、Grafana 或任何兼容 Prometheus API 的工具查询。用户可在同一仪表板中将 Prometheus 指标与 GKE 系统指标、负载均衡指标等超过 6,500 个免费 Google Cloud 系统指标并列查看。

GMP 提供四种采集模式：

| 采集模式 | 适用场景 | 管理方式 |
|---------|---------|---------|
| Managed collection | GKE/非 GKE Kubernetes 环境，推荐方式 | 自动部署、扩展、分片、配置和维护，通过 CR 配置 |
| Self-deployed collection | 已有 Prometheus 部署，快速集成 | 替换为 GMP drop-in 二进制，手动扩展和分片 |
| OpenTelemetry Collector | 跨信号（metrics/logs/traces）工作流 | 手动部署，支持 Prometheus receiver |
| Ops Agent | Compute Engine VM 环境 | 通过 gcloud CLI/UI/Terraform 部署 |

此外，Cloud Run 服务可通过 [Prometheus sidecar](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/cloudrun-sidecar) 或 OpenTelemetry sidecar 将指标发送至 GMP，实现跨 Compute Engine、GKE 和 Cloud Run 的统一监控。

#### 默认 2 年保留期与降采样策略

GMP 默认将所有 Prometheus 指标保留 **24 个月（2 年）**，无额外费用。这是 GMP 的核心卖点之一——用户无需自行管理长期存储分片。数据保留策略采用分层降采样：

- **第 1 周**：以原始采样频率存储
- **第 2–6 周**：降采样至 1 分钟间隔
- **第 7 周–24 个月**：降采样至 10 分钟间隔

这意味着高 churn 场景下，短生命周期序列在 2 年保留期内会持续占用存储，但经过降采样后存储压力会随时间递减。用户**无法调整保留期**——24 个月是固定策略，不可缩短或延长。

对于高 churn 场景，2 年保留期的影响需从两个角度看：一方面，降采样机制有效控制了长期存储成本；另一方面，由于 GMP 按摄入样本数计费（而非按存储计费），高 churn 的主要成本压力在摄入端而非存储端。

#### 全局查询（Global Queries）

GMP 的全局查询能力由 Monarch 后端提供支持，可跨所有 Google Cloud 区域和最多 3,500 个项目执行查询并合并结果。Cloud Monitoring 官方支持每个 metrics scope 最多 375 个项目以保证查询性能；超过 375 个项目（最多 3,500 个）时，查询自定义指标或历史数据可能出现性能问题。

在高 churn 场景下，全局查询面临以下挑战：

- **跨区域查询延迟**：Monarch 需跨区域合并结果，网络延迟和数据传输量随参与查询的区域数线性增长。
- **时间窗口基数累积**：高 churn 导致长时间窗口查询（如 7d、30d）需扫描更多唯一时间序列，查询延迟随之增加。
- **响应大小限制**：单次查询响应上限为 200 MB，超过时返回 `RESOURCE_EXHAUSTED`（HTTP 429）错误。高 churn 场景下大量短生命周期序列可能触发此限制。
- **项目数限制**：超过 375 个项目后查询性能无保证，高 churn 多项目场景需特别注意。

GMP 目前**没有**类似 Grafana Mimir 的 query sharding 功能来拆分高基数查询，也没有内置的查询缓存机制来缓解重复查询的压力。

#### High-Usage Tier 与标准 Tier

2022 年 5 月，Google 为 GMP 引入了 [high-usage tier](https://cloud.google.com/blog/products/containers-kubernetes/google-cloud-at-kubecon-eu-2022)，专为每月超过 5000 亿样本的大规模用户设计。2023 年 8 月，Google 宣布 [60% 降价](https://cloud.google.com/blog/products/devops-sre/managed-service-for-prometheus-price-cut)，现行定价结构如下：

| 摄入样本量（每月，按计费账户累计） | 单价（$/百万样本） |
|----------------------------------|------------------|
| 0–500 亿 | $0.060 |
| 500–2500 亿 | $0.048 |
| 2500–5000 亿 | $0.036 |
| >5000 亿 | $0.024 |

此外，Monitoring API 读取请求按 $0.01/1,000 次计费（写入 API 免费），每个计费账户每月前 100 万次读取请求免费。从 2025 年 10 月 2 日起，读取 API 费用将改为按返回的时间序列数计费。

**高 churn 场景应选哪个 tier？** high-usage tier 并非独立服务层级，而是定价阶梯——当用户月摄入量超过 500 亿样本时自动适用更低单价。高 churn 场景下，由于短生命周期序列持续产生新样本，月摄入量往往较大，自然落入更高 tier 享受更低单价。但需注意，tier 定价是按计费账户累计的，不是按 workspace 或项目隔离的。

#### 配额与限制

GMP 与 Cloud Monitoring 共享摄入和读取配额。关键限制如下：

| 限制项 | 值 | 类型 |
|--------|-----|------|
| 活跃时间序列（Prometheus，per monitored resource） | 1,000,000 | 系统限制，不可调整 |
| 活跃时间序列（workload，per monitored resource） | 200,000 | 系统限制 |
| 每个 Prometheus 指标描述符的标签数 | 200 | 系统限制 |
| 单次写入请求的时间序列数 | 200 | 系统限制 |
| 单个时间序列的写入速率 | 每 5 秒 1 个点 | 系统限制 |
| 单次查询响应大小 | 200 MB | 系统限制 |
| 每个 metrics scope 的监控项目数 | 375（保证性能）/ 3,500（可能性能下降） | 配额 |
| 指标描述符创建速率 | 6,000/分钟/项目 | 配额 |

关键区别：GMP **没有**类似 AWS AMP 的 label-based active series limits（2025 年 4 月推出），也没有 per-workspace 的活跃序列上限。GMP 文档明确指出"Managed Service for Prometheus has no limit on the number of active time series or total time series"，但 per monitored resource 的 100 万活跃序列限制仍然存在。这意味着 GMP 对高 churn 场景的配额保护主要依赖 per-resource 限制，而非全局的 label-based 配额。

#### 高流失率场景的缓解机制与潜在风险

**GMP 对高 churn 的缓解能力有限**，主要体现在以下方面：

1. **按样本计费模型**：GMP 按摄入样本数计费，而非按活跃时间序列数计费。这意味着用户"只在容器存活并发送数据时付费"，不会因 HPA 频繁扩缩容而被惩罚。然而，高 churn 场景下大量短生命周期序列持续产生样本，摄入成本随 churn rate 线性增长。

2. **降采样策略**：数据在 1 周后降采样至 1 分钟间隔，6 周后降采样至 10 分钟间隔，有效控制了长期存储的数据量。但降采样发生在摄入之后，不影响摄入端的计费。

3. **成本识别与归因**：Cloud Monitoring 的 [Metrics Management](https://cloud.google.com/monitoring/docs/metrics-management) 页面提供按指标名称和命名空间的摄入量分解，帮助用户识别高成本指标并过滤。但该功能目前仍在 Preview 阶段。

4. **采集侧过滤**：用户可通过 `metric_relabel_configs`（managed collection 的 PodMonitoring/ClusterPodMonitoring CR 中）或 `relabel_configs`（self-deployed 的 scrape config 中）丢弃高基数指标。self-deployed 模式还支持 `sample_limit` 和本地 recording rules 预聚合。

**潜在风险**：

- **无内置 cardinality 控制**：GMP 没有类似 AWS AMP 的 label-based limits，也没有 per-label-set 配额。一个团队的异常 churn（如误用 `user_id` 作为 label）可能影响整个 GMP 实例的稳定性。
- **无多租户隔离**：GMP 不支持多租户，不同团队/项目的指标共享同一 Monarch 后端，存在 "noisy neighbor" 风险。
- **无流式聚合**：GMP 不支持流式聚合（streaming aggregation），仅支持通过 recording rules 进行有限的自定义聚合（且仅限 self-deployed 模式）。
- **无数据分层**：GMP 不支持数据分层存储（data tiering），所有数据统一存储在 Monarch 中。
- **无 SLA**：GMP 不提供读写工作负载的 SLA 保证。
- **2 年固定保留期**：用户无法缩短保留期以降低存储成本，也无法延长。

#### 计费模型与成本影响

GMP 的计费模型由两部分组成：

1. **摄入样本数**：按上述阶梯定价计费，是成本的主要驱动因素。
2. **Monitoring API 读取请求**：$0.01/1,000 次（2025 年 10 月后改为按返回时间序列数计费）。

**churn 对成本的影响**：高 churn 场景下，短生命周期序列（如 K8s Pod 频繁创建销毁）持续产生新样本，直接推高摄入成本。由于 GMP 按样本计费而非按活跃序列计费，churn 的经济影响取决于样本产生速率而非序列数量本身。例如，一个每秒产生 100 个样本的短生命周期序列，在 2 小时 head block 窗口内产生 720,000 个样本，按 $0.060/百万样本计算约 $0.043——但如果每秒有 1000 个这样的序列，成本则达到 $43/小时。

**与 AWS AMP 和 Azure 的成本对比**：根据 [Sysdig 2023 年 4 月的成本分析](https://www.sysdig.com/blog/managed-service-prometheus)（基于 803,059 时间序列、10 秒采集间隔的 K8s 集群场景）：

| 方案 | 月成本（约） | 计费模式 |
|------|------------|---------|
| AWS AMP | ~$8,357 | 按样本 + 存储 + 查询 |
| GCP GMP | ~$27,310 | 按样本 + 读取 API |
| Azure Monitor | ~$4,019 | 按样本 + 告警 |
| Grafana Cloud | ~$6,563 | 按活跃序列 |

该分析显示 GMP 在同等规模下成本显著高于其他方案，主要原因是按样本计费模型在高摄入量场景下的累积效应。不过该数据来自 2023 年 4 月（降价前），当前定价已降低 60%，实际差距已缩小。

[Last9 的对比分析](https://last9.io/blog/levitate-vs-google-managed-prometheus/) 也指出 GMP 缺乏 cardinality 控制、流式聚合和数据分层能力，在成本效率上不如第三方方案。

#### 与 GKE / OpenTelemetry 的集成

GMP 与 GKE 的集成是其核心优势之一：

- **Managed collectors**：通过 GKE UI、gcloud CLI、kubectl 或 Terraform 部署，自动处理 scrape 配置生成、摄入扩展和规则作用域划分。支持从 prometheus-operator 配置直观迁移。
- **GKE 系统指标**：超过 1,500 个免费 Google Cloud 系统指标（包括 GKE 指标）可与 Prometheus 指标在同一 PromQL 查询中混合使用。
- **OpenTelemetry 集成**：支持通过 OTel Collector 采集 Prometheus 指标并发送至 GMP，也支持 Cloud Run 的 OTel sidecar。2024 年 1 月，Google 宣布 GMP 支持 [Cloud Run 的 Prometheus 和 OTel sidecar](https://cloud.google.com/blog/products/management-tools/cloud-run-now-supports-managed-service-for-prometheus)，实现跨 Compute Engine、GKE 和 Cloud Run 的统一监控。
- **Ops Agent**：用于 Compute Engine VM 环境的 Prometheus 指标采集，简化 VM 发现并消除 VM 上部署 Prometheus 的需要。

#### 总结

GMP 是一个成熟的全托管 Prometheus 兼容服务，在 GCP 生态内提供了优秀的集成体验和全球查询能力。然而，对于高 churn 场景，GMP 存在以下关键不足：

1. **无内置 churn 治理机制**：没有 label-based limits、没有 per-tenant 配额隔离、没有流式聚合，churn 治理完全依赖用户在采集侧自行处理。
2. **按样本计费在高 churn 下成本高**：虽然 2023 年降价 60%，但按样本计费模型在高 churn 场景下的总成本仍可能显著高于按活跃序列计费的方案。
3. **2 年固定保留期不可调整**：用户无法根据 churn 特征优化保留策略。
4. **无 SLA 和多租户**：对于需要严格隔离和可用性保证的企业场景，GMP 的保障不足。

对于已在 GCP 生态内、churn 可控的团队，GMP 是低运维负担的合理选择；对于高 churn 或多团队共享场景，需评估采集侧治理的额外运维成本，或考虑第三方方案（如 VictoriaMetrics Cloud、Grafana Cloud）的 cardinality 控制能力。

### Azure：Azure Monitor managed service for Prometheus

Azure Monitor managed service for Prometheus 是微软基于 Azure Monitor Workspace 构建的完全托管 Prometheus 兼容服务。与 AWS AMP 的 agentless collector 和 GCP 的全托管 side-car 不同，Azure 采用了一种独特的 **side-car 容器 + Data Collection Rule (DCR)** 架构，在 AKS 集群内部署 Azure Monitor Agent（`ama-metrics-*` Pod）进行指标采集，同时支持从外部 self-managed Prometheus 通过 remote write 将数据写入 Azure Monitor Workspace。该服务于 2023 年 5 月正式 GA，数据保留期为 18 个月，无额外费用。([GA 公告](https://techcommunity.microsoft.com/blog/azureobservabilityblog/general-availability-azure-monitor-managed-service-for-prometheus/3817973)，[产品概览](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-metrics-overview)）

#### Side-car 容器架构与 150,000 序列上限

Azure 的采集架构由两类 Pod 组成：一个 **ReplicaSet Pod**（`ama-metrics-operator-targets-*`）负责抓取集群级目标（如 kube-state-metrics、自定义应用目标），以及一组 **DaemonSet Pod**（`ama-metrics-node-*`，每节点一个）负责抓取节点级目标（kubelet、cAdvisor、node-exporter）。这些 Pod 以 Prometheus Agent 模式运行，采集的数据通过 remote write 发送到 Azure Monitor Workspace。([AKS 监控启用文档](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/kubernetes-monitoring-enable)，[GitHub Azure-Samples](https://github.com/Azure-Samples/aks-managed-prometheus-and-grafana-bicep)）

**关键限制**：每个 side-car 容器最多处理 **150,000 个唯一时间序列**。当超过此上限时，容器可能因并发连接数过高而抛出错误。微软建议的缓解措施是将 remote batch size 从默认的 500 增加到 1,000，以减少打开的连接数。([扩展最佳实践](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)，[服务限制文档](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/service-limits)）

这一限制对高 churn 场景有直接影响：在 AKS 环境中，Pod 频繁创建销毁会持续产生新的时间序列标签组合。如果单个 side-car 容器负责的 target 集合 churn 速率较高，150K 上限可能很快被触及。由于 side-car 容器是**按 DaemonSet/ReplicaSet 固定部署**的，没有自动扩展机制来应对序列数增长——用户需要手动将采集负载分散到更多 DCR/DCE（Data Collection Endpoint）或拆分 Azure Monitor Workspace。

当 side-car 超过 150K 序列上限时的典型错误表现包括：remote write 请求失败、数据间歇性丢失、Pod 日志中出现连接错误。如果 Pod 因 OOMKilled 重启，说明容器资源（内存 limit 200 MB）不足以处理当前指标量。([故障排查文档](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/prometheus-metrics-troubleshoot)）

#### 配额与限流（Throttling）机制

Azure Monitor Workspace 的 Prometheus 指标摄入有以下核心配额：

| 限制项 | 默认值 | 可否提升 |
|--------|--------|----------|
| 活跃时间序列数（约 12 小时内上报过指标的序列） | 1,000,000 | 可通过 API 提升至 20M，超出需提交支持工单 |
| 每分钟摄入事件数 | 1,000,000 | 可通过 API 提升至 20M，超出需提交支持工单 |
| DCE 每分钟摄入请求数 | 15,000 | **不可提升** |
| DCE 每分钟数据摄入量 | 50 GB | **不可提升** |
| 数据保留期 | 18 个月 | **不可提升** |
| 查询时间范围 | 32 天 | **不可提升** |
| 单指标查询时间序列数 | 500,000 | — |
| 单查询返回样本数 | 50,000,000 | — |

([服务限制文档](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/service-limits)）

当摄入达到限制时，**throttling（限流）** 会发生。Azure Monitor Workspace 暴露了两个关键利用率指标：`Active Time Series % Utilization` 和 `Events Per Minute Received % Utilization`。微软建议在利用率达 75% 时触发预警，95% 时触发高风险告警。([摄入限制监控文档](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-monitor-ingest-limits)）

对于高 churn 场景，throttling 的风险在于：churn 导致大量新序列在短时间内涌入，即使瞬时基数不高，`Active Time Series % Utilization` 也可能因 12 小时窗口内累积的序列数而迅速攀升。DCE 的 15,000 请求/分钟和 50 GB/分钟的硬限制尤其值得注意——这两个限制**不可提升**，意味着在 churn 尖峰下，如果 DCE 成为瓶颈，唯一的缓解路径是创建额外的 DCR/DCE 来分散摄入负载。([扩展最佳实践](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)）

#### Remote Write 支持范围

Azure 支持从多种来源通过 remote write 将数据写入 Azure Monitor Workspace：

- **AKS 集群**中的 self-managed Prometheus
- **Azure Arc-enabled Kubernetes** 集群
- **Azure VM/VMSS**
- **其他云或本地集群**（通过 Microsoft Entra ID 认证）

认证方式包括：system-assigned managed identity（需 Prometheus 3.5.0+）、user-assigned managed identity（需 Prometheus 2.45+）、Microsoft Entra ID（需 Prometheus 2.48+）、Microsoft Entra workload identity（需 Prometheus 3.7.0+）。配置时需在 Prometheus 的 `prometheus.yml` 中添加 `remote_write` 块，指定 Azure Monitor Workspace 的 metrics ingestion endpoint URL 和认证信息。([Remote write 配置文档](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-remote-write)）

值得注意的是，微软建议**从 side-car 容器 remote write 迁移到直接 Prometheus 配置**，即让 self-managed Prometheus 直接通过 DCR 写入 Azure Monitor Workspace，绕过 side-car 组件。这一迁移路径在高 churn 场景下尤为重要——它消除了 150K 序列的 side-car 限制，将序列上限提升到 Workspace 级别的 1M（可提升至 20M）。([Remote write 配置文档](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-remote-write)）

#### 与 AKS / Azure Container Insights 的集成

Azure Monitor managed Prometheus 与 AKS 的集成是三家云厂商中最紧密的：

- 启用 AKS 监控时，Azure Monitor Agent 以容器化形式自动安装到集群中
- 支持从 AKS 集群创建时直接启用 Managed Prometheus
- 与 Azure Container Insights 深度集成，提供预配置的告警规则、recording rules 和仪表盘
- 支持 Private Link 进行数据摄入和查询
- KEDA Prometheus scaler 原生支持 Azure Monitor managed service for Prometheus
- GA 版本支持从 Windows 节点采集指标

([GA 公告](https://techcommunity.microsoft.com/blog/azureobservabilityblog/general-availability-azure-monitor-managed-service-for-prometheus/3817973)，[产品概览](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-metrics-overview)）

#### 高流失率场景的缓解与限制

Azure 方案对高 churn 场景的治理能力可归纳如下：

**缓解手段**：
1. **ConfigMap 配置优化**：通过 `ama-metrics-settings-configmap` 和 `ama-metrics-prometheus-config-configmap` 调整 scrape interval、使用 `metric_relabel_configs` 丢弃不必要标签、降低高基数指标的采集频率
2. **Recording rules 预聚合**：Azure Managed Prometheus Rule Groups 支持创建 recording rules，将高 churn 指标预聚合为低基数序列，减少查询时的序列扫描量
3. **多 Workspace 拆分**：将不同环境（dev/test/prod）或不同区域的指标分散到多个 Azure Monitor Workspace
4. **DCR/DCE 分散**：创建额外的 DCR 和 DCE 来分散摄入负载（但 DCE 的 15K 请求/分钟和 50 GB/分钟限制不可提升）
5. **直接 remote write 迁移**：绕过 side-car 的 150K 限制，直接使用 Workspace 级别的 1M 序列上限

**限制**：
1. **Side-car 150K 硬限制**：在 side-car 架构下，每个容器 150K 唯一序列上限是硬性约束，无自动扩展机制
2. **DCE 不可提升的配额**：15,000 请求/分钟和 50 GB/分钟的 DCE 限制无法通过支持工单提升
3. **无 label-based 配额**：与 AWS AMP 2025 年推出的 label-based active series limits 不同，Azure 目前没有 per-label-set 的配额管理，无法实现多租户级别的 noisy neighbor 防护
4. **查询时间范围限制 32 天**：相比 GCP 的 2 年保留期，Azure 的 18 个月保留期和 32 天查询时间范围对长窗口查询有更大限制
5. **标签长度限制导致整个 scrape job 失败**：标签名超过 511 字符或标签值超过 1023 字符时，**整个 scrape job 的所有指标都会被丢弃**，而非仅丢弃违规序列——这在 churn 场景下可能导致大面积数据丢失

([故障排查文档](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/prometheus-metrics-troubleshoot)，[扩展最佳实践](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)）

#### 计费模型

Azure Monitor managed service for Prometheus 的计费基于**摄入的样本数**和**查询处理的样本数**，数据保留 18 个月无额外费用。没有直接的服务费用或 Workspace 创建费用。([成本与用量文档](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/cost-usage)，[产品概览](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-metrics-overview)）

根据 Sysdig 2023 年的对比分析（基于约 803K 时间序列、25 节点 AKS 集群的模拟场景），Azure 方案月费约 **$4,019**，低于 AWS AMP（~$8,357）和 GCP（~$27,310），但高于 Grafana Cloud（~$6,563 的定价基于 active series 而非样本数）。Azure 的定价优势在于其按样本计费的模式在高摄入量场景下相对经济，但 churn 导致的序列数增长会同时推高摄入样本数和查询处理样本数两项成本。([Sysdig 成本对比](https://www.sysdig.com/blog/managed-service-prometheus)）

#### 与 AWS AMP 和 GMP 的关键差异

| 维度 | Azure Monitor managed Prometheus | AWS AMP | GCP Managed Prometheus |
|------|----------------------------------|---------|------------------------|
| 默认活跃序列上限 | 1M（可提升至 20M） | 50M（2025 年 7 月提升） | 未公开具体数值 |
| Side-car 序列上限 | 150,000（不可提升） | N/A（agentless） | N/A |
| 保留期 | 18 个月 | 默认 15 个月 | 24 个月（2 年） |
| 查询时间范围 | 32 天 | 未明确限制 | 未明确限制 |
| Label-based 配额 | 无 | 有（2025 年 4 月推出） | 无 |
| 多租户隔离 | 无原生支持 | per-label-set 配额 | 无原生支持 |
| DCE 硬限制 | 15K 请求/分钟 + 50 GB/分钟（不可提升） | N/A | N/A |
| 自动扩展 | 无（需手动拆分 Workspace） | 有（agentless 自动扩展） | 有（全托管自动扩展） |

Azure 方案在三家云厂商中的独特定位是：**与 AKS 的集成深度最高**（side-car 直接部署在集群内），但 **side-car 的 150K 序列硬限制和 DCE 不可提升的配额**使其在高 churn 场景下的扩展性弱于 AWS AMP 的 agentless 架构和 GCP 的全托管架构。对于 churn 速率较高的 AKS 环境，建议评估迁移到直接 remote write 架构以绕过 side-car 限制，或采用多 Workspace 拆分策略。

### 第三方托管方案与开源替代对比

除三大云厂商的托管 Prometheus 服务外，市场上还有多种第三方托管方案和开源替代方案，它们在高 churn 场景下各有不同的治理机制、计费模型和适用场景。本节逐一分析 Grafana Cloud、VictoriaMetrics Cloud、New Relic、Chronosphere、Cribl、OpenObserve 和 Datadog 七个方案，为多云/混合云场景提供补充选型参考。

#### Grafana Cloud：Mimir 驱动的托管指标平台

Grafana Cloud 的指标服务底层由 [Grafana Mimir](https://grafana.com/blog/how-to-manage-high-cardinality-metrics-in-prometheus-and-kubernetes/) 支撑，这是一个为高基数场景设计的水平可扩展 TSDB。针对高 churn 治理，Grafana Cloud 提供三层工具链：

1. **Cardinality Management Dashboards**（Pro/Advanced 计划内置）：提供预构建的 Grafana 仪表板，按指标名称、标签键、标签值等维度展示时间序列数量，帮助用户快速定位高基数指标和标签。仪表板将指标按"基数 × 价值"四象限分类，优先识别"高成本低价值"的指标进行裁剪。
2. **Usage Insights**（Advanced 计划）：以时间序列形式追踪特定标签集（如 `team=dev`、`env=prod`）的序列数量变化，使团队能够归因自身对整体基数的贡献，并在时间点上定位导致成本突增的变更。
3. **Mimirtool**（开源 CLI 工具）：可扫描 Mimir/Prometheus 兼容数据库，识别未被任何仪表板、告警规则或 recording rules 使用的指标，生成 JSON 报告供用户安全丢弃。

此外，Grafana Cloud 推出 **Adaptive Metrics** 功能，通过自动聚合和基数优化消除未使用的时间序列数据，官方称可优化高达 80% 的指标成本。The Trade Desk 案例中通过 Adaptive Metrics 节省了 174 万美元。

**计费模型**：Grafana Cloud 按 active series（过去 20 分钟内接收新数据点的时间序列）和 DPM（每分钟数据点）计费。Pro 计划 $6.50/1k series/月，Enterprise 计划低至 $3/1k series/月（基于年度承诺和量价折扣），另加 $19/月平台费。Free 计划提供有限额度。

**适用场景**：已使用 Grafana 生态的团队、需要内置 cardinality 可视化与归因能力的企业、希望利用 Mimir 水平扩展能力处理高 churn 的组织。

#### VictoriaMetrics Cloud：以 Churn Rate 为一等公民的容量模型

VictoriaMetrics Cloud 在容量规划方面与其他方案有本质差异——它将 **Churn Rate**（过去 24 小时内新活跃时间序列数）作为与 Active Time Series、Ingestion Rate 并列的[一等容量指标](https://docs.victoriametrics.com/victoriametrics-cloud/deployments/victoriametrics-tiers/)，直接纳入 Capacity Tier 的选型矩阵。

| Active Time Series | Churn Rate | Ingestion Rate (datapoints/s) | Equivalent Hosts |
|---|---|---|---|
| 500k | 1.25M | 16.7k | 500 |
| 1M | 2.5M | 33.3k | 1,000 |
| 5M | 12.5M | 166k | 5,000 |
| 10M | 25M | 333k | 10,000 |
| 15M | 37.5M | 500k | 15,000 |

每个 Capacity Tier 同时定义了 Active Time Series、Churn Rate、Ingestion Rate、Data Read Rate、Series Read per Query 等参数。用户可在部署的 Monitoring Page 中实时查看这些指标。当某个参数超过当前 Tier 容量时，性能可能退化且 SLA 不再保证，需升级到更高 Tier。

与自建版相比，VictoriaMetrics Cloud 的差异在于：(1) 容量以 Tier 形式预定义，用户无需自行评估硬件配置；(2) 支持在 Deployment Settings 中一键升降级；(3) 提供 [Cardinality Explorer](https://docs.victoriametrics.com/victoriametrics-cloud/deployments/victoriametrics-tiers/) 和 downsampling、retention filters、data deduplication 等成本优化工具；(4) 高级参数如 `-maxLabelsPerTimeseries` 和 `-maxLabelValueLen` 可由用户自行调整。

**计费模型**：按 Capacity Tier 订阅，存储可灵活扩展（只能增不能减），建议从小存储开始按需扩展。高基数数据会增加数据点大小，可能导致实际存储超出推荐值。

**适用场景**：需要显式控制 churn rate 的场景、希望以订阅模式替代自建运维的团队、已使用 VictoriaMetrics 自建版需要托管升级的用户。

#### New Relic：远程写入 + 标签治理

New Relic 通过 Prometheus `remote_write` 集成接收指标数据，其 cardinality 管理主要依赖 Prometheus 原生的 relabeling 机制：

- **`write_relabel_configs`**：在 remote write 阶段按 job 标签 drop 或 keep 特定时间序列，阻止高 churn 数据进入 New Relic。
- **`labelkeep` / `labeldrop`**：在 scrape 阶段裁剪高基数标签（如 `ip_address`），但需确保裁剪后时间序列仍唯一可标识。
- **NRQL 查询**：`FROM Metric SELECT cardinality() FACET job, metricName SINCE today` 可在 New Relic 侧分析 cardinality 分布。

New Relic 本身未提供专门的 churn 检测或自动聚合功能，其治理手段与自建 Prometheus 的 relabeling 策略一致，区别在于存储和查询由 New Relic 托管。

**计费模型**：按数据摄入量计费，Original 计划约 $0.30/GB，Data Plus 计划约 $0.35/GB，另加核心用户费 $49/用户/月。无免费层（有限免费试用）。

**适用场景**：已使用 New Relic APM 生态、希望通过 remote write 将 Prometheus 指标汇入统一可观测性平台的团队。高 churn 治理需在 Prometheus 侧完成，New Relic 侧仅提供存储和查询托管。

#### Chronosphere：聚合规则驱动的 cardinality 治理

Chronosphere 的核心差异化能力是 **Aggregation Rules**（聚合规则），允许用户在指标存储前进行 rollup 和 downsampling，从而[在数据入库前降低 cardinality](https://chronosphere.io/learn/using-aggregation-rules-to-control-data-growth/)。

Chronosphere 提供三种聚合模式：

1. **去除 instance 标签**：对于无状态微服务，移除 `instance` 标签可将 10,000 条序列降至 100 条（99% 减少）。
2. **分解高基数指标**：将一个多维度指标拆分为多个低基数聚合指标。例如，将 `ingress` 和 `namespace` 两个维度分别聚合，从 2,000 条降至 1,200 条（50% 减少）；若同时去除 instance 标签则降至 60 条。
3. **部分保留高基数维度**：对 `customerID` 等高基数标签，仅保留 Top N 值（如前 10 大客户），其余聚合为默认值。3M 条序列可降至 1,100 条（99.96% 减少）。

Chronosphere 还提供 **cardinality over time** 可视化能力，可追踪任意数据子集的 churn 趋势，而非仅提供瞬时基数快照。

**计费模型**：Enterprise 模式，无免费或自助层。采用 persisted-writes 计费模型，激进的中央聚合直接降低账单。

**适用场景**：大型企业、多团队环境、需要在数据入库前进行精细化 cardinality 治理、愿意为托管服务支付溢价的团队。

#### Cribl：可观测性管道中的 cardinality 压缩

Cribl Stream 定位为可观测性管道（observability pipeline），在数据从采集端到分析端的传输过程中执行 cardinality 压缩，[而非替代 Prometheus 或时序数据库](https://cribl.io/blog/cut-costs-not-visibility-the-cribl-way-to-metrics/)。

Cribl 提供三种 cardinality 降低机制：

1. **Rollup Metrics（时间聚合）**：将高频指标（如每秒采集）聚合为低频（如 30 秒间隔），减少时间维度上的数据量。支持 Gauge 和 Counter 两种聚合模式。
2. **Dimensional Aggregation（维度聚合）**：在传输过程中丢弃或扁平化维度标签。例如，将 `host` 维度聚合掉，仅保留 `app` 维度，可将数百台主机的指标压缩为按应用聚合的少量序列。
3. **Logs2Metrics**：将高频日志事件转化为聚合指标，如将 100 条 Windows 登录事件转化为 1 条 `count:90 action:login host:all` 指标。

Cribl 的核心理念是"Cut Costs, Not Visibility"——原始数据完整保留在低成本对象存储中，仅将聚合后的数据送入分析层。客户通常可减少 30%–50% 的数据量。

**计费模型**：按数据量计费，具体价格需联系销售。

**适用场景**：已有 Prometheus 和时序数据库、需要在数据管道中统一处理 logs/metrics/traces 的 cardinality、希望保留原始数据在对象存储中作为 retention tier 的组织。Cribl 是管道优化层，不是 Prometheus 替代品。

#### OpenObserve：开源列式存储的 Prometheus 兼容方案

[OpenObserve](https://openobserve.ai/pricing/) 是一个开源（AGPL-3.0）的可观测性平台，支持 Prometheus 指标存储和 PromQL 查询，底层采用列式存储引擎。

OpenObserve 的 cardinality 治理主要依赖 Prometheus 原生的 relabeling 和 recording rules 机制，平台本身未提供专门的 churn 检测或自动聚合功能。其优势在于：列式存储对高基数数据的压缩效率优于传统倒排索引，且 15 个月的指标默认保留期减少了用户自行管理 retention 的运维负担。

**计费模型**：OpenObserve Cloud 按 $0.50/GB 摄入 + $0.01/GB 查询计费，无 per-host 或 per-seat 费用。15 个月指标保留期包含在定价中。自建版免费（开源）。

**适用场景**：预算敏感、需要长期指标保留、希望避免厂商锁定、有自建运维能力的团队。OpenObserve 适合作为 Datadog/Splunk 等商业方案的开源替代，但在 churn 专项治理工具方面不如 Grafana Cloud 或 Chronosphere 丰富。

#### Datadog：Metrics without Limits 与自定义指标治理

Datadog 通过 Agent 的 [Prometheus/OpenMetrics check](https://docs.datadoghq.com/integrations/prometheus/) 采集指标，所有指标作为 custom metrics 计费。其 cardinality 管理体系包含以下组件：

1. **Metrics without Limits™**：将指标摄入（ingestion）与索引（indexing）解耦。用户可指定哪些标签需要保留用于查询，其余标签仅摄入不索引，从而在不丢失数据的前提下降低 indexed custom metrics 体积。系统会基于查询模式自动推荐标签配置。
2. **Custom Metrics Tags Cardinality Explorer**：在 Metrics Summary 页面展示每个指标的标签基数分布，快速定位导致 cardinality 飙升的标签键。
3. **Metrics Volume Management**：实时展示各团队的 custom metrics 用量，识别体积最大的指标和突增指标。
4. **Usage Attribution**（Enterprise 计划）：按标签键（如 `team`、`service`）分解账单用量，实现团队级归因。
5. **RBAC 与审计**：`metrics_tags_write` 权限控制谁可修改 Metrics without Limits 配置，所有配置变更记录审计日志。

Datadog 的 Prometheus check 默认限制每个 instance 2000 个指标（可通过 `max_returned_metrics` 调整），超出后可能丢弃部分指标。

**计费模型**：按 host + 数据摄入量计费。Custom metrics 按 indexed metrics 数量计费（具体价格随计划不同）。Enterprise 计划提供 Usage Attribution 和更多治理功能。

**适用场景**：已使用 Datadog APM/Infrastructure 的团队、需要统一 logs/metrics/traces 平台、对 custom metrics 治理有成熟流程的大型组织。

**选型建议**：

- **预算敏感、需长期保留**：OpenObserve 的 $0.50/GB 定价和 15 个月保留期具有成本优势，但 churn 治理工具较少。

### 云厂商方案综合对比与选型建议

在明确各家托管方案的架构与能力差异后，本节从 churn 治理视角对 AWS AMP、GCP Managed Prometheus、Azure Monitor managed Prometheus 及主流第三方方案进行横向对比，并给出面向不同场景的选型决策矩阵。

#### 一、架构模式与 churn 治理的根本差异

三家云厂商方案在架构模式上存在根本差异，直接影响其对高 churn 场景的治理能力：

**AWS AMP** 采用 agentless collector + 托管 workspace 架构。2023 年 11 月发布的 [agentless collector](https://aws.amazon.com/blogs/aws/amazon-managed-service-for-prometheus-collector-provides-agentless-metric-collection-for-amazon-eks/) 通过 ENI 直接抓取 EKS 指标并 remote write 到 AMP workspace，消除了自建 scraper 的运维负担。AMP 后端基于 Cortex 项目，数据摄入后由 AWS 完全托管 TSDB 与查询平面。对 churn 治理而言，AMP 的核心优势在于 2025 年 4 月推出的 [label-based active series limits](https://aws.amazon.com/about-aws/whats-new/2025/04/amazon-managed-service-prometheus-label-based-series-limits/)——通过 per-label-set 配额实现多租户隔离，当某个标签组合（如 `{app="payment-service", environment="prod"}`）的序列激增时，仅该标签集被限流，不影响其他工作负载。这是三家云厂商中唯一提供细粒度 noisy neighbor 防护的方案。

**GCP Managed Prometheus** 采用全托管架构，后端基于 Google 自研的 [Monarch 时序数据库](https://research.google/pubs/pub50652/)，由 Google 内部 SRE 团队维护。其 managed collectors 自动部署、扩缩容和分片，通过轻量 CRD 配置抓取与规则。GMP 的 churn 治理策略与 AWS 截然不同：它不设显式的 active series 上限，而是采用 [按样本计费模式](https://cloud.google.com/managed-prometheus)——"charges on a per-sample basis, which does not charge for cardinality up front when a new container is spun up"。这意味着 HPA 扩缩容产生的短生命周期序列不会产生额外的基数费用，仅在容器存活期间按样本付费。GMP 还提供 [Metrics Management 页面](https://cloud.google.com/blog/products/devops-sre/managed-service-for-prometheus-price-cut)（Preview），可识别高成本指标并按 namespace 归属，支持在源头过滤。

**Azure Monitor managed Prometheus** 采用 side-car 容器架构，每个 side-car 容器处理上限为 [150,000 唯一时间序列](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)。当 side-car 超过此上限时，可能因并发连接过多而抛出错误，缓解方法是增大 remote batch size（从默认 500 调至 1,000）。Azure 的 churn 治理主要依赖 Metrics Usage Insights 识别高基数指标、通过 `metric_relabel_configs` 丢弃不必要的标签，以及通过 [recording rules](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice) 预聚合高 churn 指标。Azure 不支持跨租户查询，多区域需创建独立 workspace。

#### 五、迁移建议

**从 self-managed Prometheus 迁移到云厂商托管方案**时，建议遵循以下步骤与风险控制：

1. **评估阶段**：使用 `prometheus_tsdb_head_series` 和 `rate(prometheus_tsdb_head_series_created_total[5m])` 建立当前 churn rate 基线；通过 `/status` 页面和 [TSDB stats API](https://prometheus.io/docs/prometheus/latest/querying/api/#tsdb-stats) 获取 active series 总数；用 `topk(20, count by (__name__)({__name__=~".+"}))` 识别高基数指标。

2. **试点迁移**：选择非关键业务集群，配置 self-managed Prometheus 的 `remote_write` 到目标托管方案，并行运行 2-4 周，对比数据一致性（使用 `absent()` 检测 missing series）与查询延迟。

3. **全量迁移**：确认数据一致性后，逐步将抓取目标从 self-managed Prometheus 切换到云厂商 collector/agentless 模式。迁移期间保留 self-managed Prometheus 的本地 TSDB 作为回滚备份（至少保留一个 retention 周期）。

4. **回滚策略**：保留 self-managed Prometheus 的 PVC 与配置至少一个 retention 周期；在 Grafana 中配置双数据源（self-managed + 托管），切换 dashboard 数据源即可回滚。

5. **监控盲区风险**：迁移期间 self-managed Prometheus 与云厂商 collector 可能同时抓取同一目标，导致重复数据。建议在切换时先停止 self-managed 的抓取，再启动云厂商 collector，确保无缝衔接。使用 `scrape_series_added` 指标监控两端的序列数是否一致。

**多云场景下的关键决策点**：若团队已深度使用某一云厂商的 Kubernetes 服务（如 EKS），优先选择该云厂商的托管方案以获得最深集成；若团队需要跨云全局查询且不愿绑定单一云厂商，GCP Managed Prometheus 的全局查询能力是唯一原生选项；若成本是首要约束且团队具备运维能力，VictoriaMetrics Cloud 或自建 VictoriaMetrics 集群在 [相同 workload 下成本仅为 AWS/GCP 的 1/5 至 1/40](https://victoriametrics.com/blog/managed-prometheus-pricing/)。

## 决策框架与实施建议

### 流失率评估与分级

#### 评估方法论：度量当前环境的 churn rate

评估 Prometheus 环境的流失率需要同时关注**瞬时基数**（point-in-time cardinality）和**时间窗口基数**（windowed cardinality）两个维度。如 S1.1 所述，低瞬时基数 + 高流失率的工作负载在长时间窗口查询下性能可能比高瞬时基数 + 低流失率的工作负载更差——churn rate 是连接瞬时基数与长期查询性能的关键桥梁指标 ([Chronosphere](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/))。

**核心度量指标与采集粒度**

churn rate 的核心度量指标（`prometheus_tsdb_head_series_created_total`、`scrape_series_added`、`vm_new_timeseries_created_total`）的定义、PromQL 查询与统计口径详见 S1.1。以下仅列出各指标的采集粒度：

| 指标 | 采集粒度 |
|------|----------|
| `prometheus_tsdb_head_series_created_total` | 全局 |
| `scrape_series_added`（2.10+） | per-job |
| `prometheus_tsdb_head_series` | 全局 |
| `vm_new_timeseries_created_total`（VictoriaMetrics） | 全局 |

`prometheus_tsdb_head_series_created_total` 是 Prometheus 暴露的 head block 新序列创建计数器，其 5 分钟 rate 直接反映集群级 churn rate ([valyala Medium](https://valyala.medium.com/prometheus-storage-technical-terms-for-humans-4ab4de6c3d48))。`scrape_series_added` 从 v2.10 起提供，按 job 维度拆分，适合定位具体哪个抓取任务在产生 churn ([valyala Medium](https://valyala.medium.com/prometheus-storage-technical-terms-for-humans-4ab4de6c3d48))。在 VictoriaMetrics 环境中，`vm_new_timeseries_created_total` 统计的是被判定为"新"的时间序列——即同时不在缓存和倒排索引中的序列，其统计口径受 `cacheExpireDuration`（默认 30 分钟 TTL）和每日 indexdb 轮换影响 ([VictoriaMetrics Blog](https://victoriametrics.com/blog/churn-rate-in-victoriametrics/))。

**vmestimator 实时估算**

VictoriaMetrics 于 2026 年发布的 `vmestimator` 工具可在采集侧实时估算基数与流失率，无需依赖 TSDB 内部指标。它通过比较不同时间窗口（如 15m vs 30m）的基数估算值来计算 churn rate：当 30m 窗口基数与 15m 窗口基数的差值占 30m 窗口基数的比例超过 10% 时触发告警，表示 100% 的序列在窗口间被替换 ([VictoriaMetrics vmestimator](https://victoriametrics.com/blog/vmestimator-announcement/))。

#### 基线建立方法

建立 churn rate 基线需要考虑以下环境因素：

1. **部署频率**：每次 Kubernetes Deployment 会因 `pod_name` 标签值变化产生新序列。一个 100 Pod 的服务每次部署约产生 `100 × 每 Pod 指标数` 条新序列。Google Groups 社区讨论中举例：每分钟创建销毁 100 个 Pod、每 Pod 1000 条指标，2 小时 head block 窗口内将累积 1200 万条序列 ([Google Groups](https://groups.google.com/g/prometheus-users/c/wRtG7zq6sZ4))。

2. **K8s 集群规模**：HPA 扩缩容、CronJob 每次运行、Pod 重启均产生周期性 churn。基线应区分"部署窗口"和"稳态运行"两个时段的 churn 水平。

3. **标签设计**：高基数标签（`user_id`、`request_id`、`trace_id`）会同时推高 cardinality 和 churn rate。OpenObserve 指出，一个带 `user_id` 标签的 HTTP 请求计数器在 100 万用户规模下可产生 1.5 亿条时间序列 ([OpenObserve](https://openobserve.ai/blog/prometheus-data-cardinality/))。

4. **indexdb 轮换周期**：VictoriaMetrics 的每日 indexdb 轮换可能导致"假性高 churn"（机制详见 S1.1）。基线应排除此类周期性尖峰，或通过调整 `cacheExpireDuration` 消除 ([VictoriaMetrics Blog](https://victoriametrics.com/blog/churn-rate-in-victoriametrics/))。

基线建立步骤：连续采集 7 天的 `rate(prometheus_tsdb_head_series_created_total[5m])` 和 `sum(sum_over_time(scrape_series_added[5m])) by (job)`，按小时聚合取 p50 作为稳态基线、p95 作为峰值基线，并标注部署窗口与 indexdb 轮换时刻。

#### churn 分级标准

综合 Alexandre Vazquez 的容量规划指南（>100,000 新序列/分钟为运维红线）、OpenObserve 的基数阈值（5M 活跃序列 = 问题、10M = 紧急）、以及 vmestimator 的窗口间 churn 比例（>10% 为告警阈值），定义以下四级分级标准：

| 级别 | 集群级 churn rate（新序列/分钟） | 瞬时活跃序列 | 典型症状 | 风险 |
|------|-------------------------------|-------------|----------|------|
| **低** | < 1,000 | < 100K | 无异常；head block 内存稳定 | 无显著风险；正常 K8s 部署 churn 可被 2h 窗口吸收 |
| **中** | 1,000–10,000 | 100K–1M | 长范围查询（7d+）延迟轻微上升；compaction 耗时增长 | 需关注趋势；可能需要 recording rules 预聚合高 churn 指标 |
| **高** | 10,000–100,000 | 1M–5M | head block 内存持续攀升；Grafana 仪表盘偶发超时；`prometheus_tsdb_head_series` 单调增长不回落 | OOM 风险升高；需立即实施 relabeling 裁剪或 remote write 卸载 |
| **极高** | > 100,000 | > 5M | 频繁 OOM 重启；compaction 积压导致磁盘空间耗尽；告警 flapping；WAL replay 时间延长 | 监控系统自身不可用；需紧急架构变更（分片/远程存储/Agent 模式） |

Alexandre Vazquez 明确指出："一个实例每分钟创建超过 100,000 条新序列将导致 head block 在 2 小时内累积超过 1200 万条序列，远超单实例合理容量" ([Alexandre Vazquez](https://alexandre-vazquez.com/prometheus-scalability/))。OpenObserve 的阈值则从活跃序列绝对数角度补充：超过 500 万活跃序列即应调查标签基数问题，超过 1000 万则为紧急状态 ([OpenObserve](https://openobserve.ai/blog/prometheus-data-cardinality/))。

#### 评估指标清单

以下指标清单用于系统化评估 churn 水平，每项标注采集方式与正常范围参考：

| 评估项 | 指标/查询 | 采集方式 | 正常范围参考 | 告警阈值建议 |
|--------|----------|----------|-------------|-------------|
| 集群级 churn rate | `rate(prometheus_tsdb_head_series_created_total[5m])` | Prometheus 自抓取 | < 1,000/s（低） | > 10,000/s 持续 15m |
| per-job churn | `sum(sum_over_time(scrape_series_added[5m])) by (job)` | Prometheus 自抓取 | 视 job 而定 | 单 job 贡献 > 50% 总 churn |
| 瞬时活跃序列 | `prometheus_tsdb_head_series` | Prometheus 自抓取 | < 1M（中等环境） | > 5M 持续 10m |
| head block 内存 | `process_resident_memory_bytes` | node_exporter | < 4GB（1M 序列） | > 8GB 或 RSS 持续增长 |
| compaction 耗时 | `prometheus_tsdb_compaction_duration_seconds` | Prometheus 自抓取 | < 30s | > 60s 持续 3 次 |
| 长范围查询延迟 | `prometheus_engine_query_duration_seconds{slice="inner_eval"}` | Prometheus 自抓取 | p99 < 5s（7d 窗口） | p99 > 30s |
| VM churn rate（如适用） | `sum(rate(vm_new_timeseries_created_total))` | VictoriaMetrics | 与基线比较 | 超基线 3 倍 |
| 窗口间 churn 比例 | vmestimator `cardinality_estimate` 差值比 | vmestimator + vmalert | < 10%（15m vs 30m） | > 20% 持续 30m |
| WAL 体积 | `prometheus_tsdb_wal_storage_size_bytes` | Prometheus 自抓取 | 与 retention 匹配 | 持续增长不回落 |
| 每日 indexdb 轮换尖峰 | `vm_new_timeseries_created_total` 按小时聚合 | VictoriaMetrics | 无 0 点尖峰 | 0 点尖峰 > 日均值 5 倍 |

**告警规则示例**

```yaml
groups:
  - name: churn_assessment
    rules:
      - alert: HighChurnRate
        expr: rate(prometheus_tsdb_head_series_created_total[5m]) > 10000
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "High churn rate detected"
          description: "Cluster churn rate is {{ $value }} new series/sec, exceeding 10k/s threshold"

      - alert: CriticalChurnRate
        expr: rate(prometheus_tsdb_head_series_created_total[5m]) > 100000
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Critical churn rate - OOM risk"
          description: "Cluster churn rate is {{ $value }} new series/sec, exceeding 100k/s operational limit"

      - alert: HeadSeriesMonotonicGrowth
        expr: |
          (
            prometheus_tsdb_head_series
            - prometheus_tsdb_head_series offset 1h
          ) / prometheus_tsdb_head_series offset 1h > 0.3
        for: 30m
        labels:
          severity: warning
        annotations:
          summary: "Active series growing >30% in 1h"
          description: "Head series grew from {{ $value | humanize }} in the past hour, indicating sustained churn without series expiry"
```

#### 区分正常 churn 与异常 churn

评估时必须区分两种模式：

- **正常 churn（良性）**：由 K8s 部署、HPA 扩缩容、Pod 重启等预期行为产生。特征是 churn rate 与部署事件时间相关，head block 序列数在部署后回落（旧序列在 2h 窗口后过期）。基线中应包含此类周期性尖峰。

- **异常 churn（恶性）**：由指标反模式（如 `user_id`/`request_id` 作为 label）、exporter 缺陷、或动态服务发现配置错误导致。特征是 `prometheus_tsdb_head_series` 单调增长不回落，churn rate 持续高于基线 p95，且与部署事件无相关性。OpenObserve 案例中，一个 `user_id` 标签在 90 天内静默产生 500 万条序列，最终导致 TSDB 内存崩溃 ([OpenObserve](https://openobserve.ai/blog/prometheus-data-cardinality/))。

Chronosphere 强调，云原生工作负载的短生命周期特性天然产生较高 churn，但"最具破坏性的情况来自指标反模式——为每个请求引入唯一维度值，此时工作负载具有最大量的 churn，会导致未设计为处理高基数的系统出现稳定性问题" ([Chronosphere](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/))。

### 方案选型决策矩阵

基于 S5.1 的 churn 分级（低/中/高/极高），本节提供一套可操作的方案选型决策框架，覆盖从纯 Prometheus 优化到云厂商托管的完整谱系。每种方案组合标注适用场景、前置条件、代价与风险，并给出成本估算模型。

#### 一、按 churn 级别的方案推荐

| Churn 级别 | 典型特征 | 推荐方案组合 | 核心理由 |
|---|---|---|---|
| **低**（<1k series/min） | 稳态基数 <500K，K8s 部署频率低 | 纯 Prometheus 优化：relabeling + recording rules + 标签治理 | 运维成本最低，无需引入额外组件；源头治理即可控制 churn 在安全水位 |
| **中**（1k–10k series/min） | 稳态基数 500K–2M，HPA 扩缩容频繁 | Prometheus + remote write → 开源存储（VictoriaMetrics 或 Thanos） | 本地 retention 降至 2h，churn 对本地 TSDB 影响被隔离；远程存储承担长期保留与查询 |
| **高**（10k–50k series/min） | 稳态基数 2M–10M，多团队共享，短生命周期负载多 | Prometheus Agent 模式 + remote write → Mimir/VictoriaMetrics 集群；或云厂商托管（AWS AMP / GCP Managed Prometheus） | Agent 模式消除本地 compaction 与查询引擎，churn 压力完全转移到远程后端；托管方案提供自动扩展与配额隔离 |
| **极高**（>50k series/min） | 稳态基数 >10M，churn 尖峰频繁，多区域/多云 | 云厂商托管（AMP label-based limits / GCP high-usage tier）或 Mimir 集群 + 全局查询；混合架构：self-managed Prometheus + remote write 到多家后端 | 需要内置的 noisy neighbor 防护、自动扩展与全局查询能力；自建方案需分片 + 联邦 + 降采样组合 |

#### 二、方案组合详解与适用条件

**方案 A：纯 Prometheus 优化（源头治理）**

- **适用场景**：churn 低–中，团队有 Prometheus 配置能力，无长期存储需求（≤15d）
- **前置条件**：单区域部署，活跃序列 <2M，无跨集群查询需求
- **关键手段**：`metric_relabel_configs` 丢弃高基数标签（`trace_id`、`user_id`）；`relabel_configs` 裁剪 target 标签；recording rules 预聚合高 churn 指标；exemplars 替代 per-request 标签；调整 scrape interval 权衡采集频率
- **代价**：relabeling 规则维护成本；recording rules 增加评估间隔内的 CPU 开销；无法解决跨集群查询与长期存储
- **风险**：churn 随业务增长自然上升，方案天花板有限；高基数标签若来自第三方 exporter，裁剪可能需要修改 exporter 配置
- **参考**：[Chronosphere 聚合规则实践](https://chronosphere.io/learn/using-aggregation-rules-to-control-data-growth/) 展示了通过聚合规则将 10,000 条序列降至 100 条（99% 削减）的案例

**方案 B：Prometheus + remote write → 开源长期存储**

- **适用场景**：churn 中–高，需要长期保留（>15d）与全局查询，团队有运维能力
- **前置条件**：至少 2–3 人 SRE 团队；网络带宽满足 remote write 需求（约 100–200MB/hr per 100K active series，[Last9](https://last9.io/blog/aws-prometheus-production-patterns/)）
- **存储引擎选型**：

| 维度 | VictoriaMetrics | Thanos | Grafana Mimir |
|---|---|---|---|
| 架构 | 单节点/集群，磁盘存储 | Sidecar + Store Gateway + Compactor，对象存储 | 微服务架构，对象存储，多租户 |
| 查询性能 | 高（列式存储，20–50ms median） | 中（依赖对象存储，长范围查询较慢） | 中高（query sharding 改善高基数查询） |
| 压缩比 | 2x–10x（[VictoriaMetrics 文档](https://docs.victoriametrics.com/victoriametrics/faq/)） | 与 Prometheus 原生格式相同 | 与 Prometheus 原生格式相同 |
| 运维复杂度 | 低（单二进制可选） | 中（需管理 Sidecar、Store Gateway、Compactor） | 高（微服务组件多） |
| 高 churn 治理 | `prefillNextIndexDB` 缓解 indexdb 轮换尖峰；`vm_new_timeseries_created_total` 诊断 | Compactor 降采样；对象存储天然扩展 | query sharding 拆分高基数查询；`cardinality_analysis_enabled` 诊断端点 |
| 适用场景 | 单集群/多集群，追求简单运维 | 已有对象存储基础设施，需与 Prometheus 共存 | 多租户、大规模（10 亿+活跃序列），需企业级支持 |

- **代价**：远程存储集群的运维成本；网络带宽成本；remote write 队列积压风险
- **风险**：remote write 后端不可用时本地 WAL 积压（Agent 模式默认 4h 缓冲，[OneUptime](https://oneuptime.com/blog/post/2026-08-03-prometheus-agent-vs-server-remote-write-edge/view)）；长范围查询在对象存储上性能退化

**方案 C：Prometheus Agent 模式 + remote write**

Agent 模式（`--agent` flag，Prometheus 2.32+）的机制与完整 Prometheus 的能力差异详见 S3.2（[Prometheus 官方文档](https://prometheus.io/docs/prometheus/latest/prometheus_agent/)）。本节仅关注选型决策中的场景适配。

- **适用场景**：churn 高，边缘/采集层仅需转发，查询与告警集中在中心
- **前置条件**：中心后端具备完整 PromQL 查询与告警能力；边缘到中心网络稳定（中断窗口 < WAL 保留时间）
- **WAL 保留窗口**：Agent 模式 WAL 默认保留 5min–4h 可配（`--storage.agent.retention.min-time` / `--storage.agent.retention.max-time`），需根据边缘到中心的网络中断容忍度设置。网络不稳定场景应调大至 4h 并挂载持久化 WAL 磁盘（[OneUptime](https://oneuptime.com/blog/post/2026-08-03-prometheus-agent-vs-server-remote-write-edge/view)）
- **HA 考虑**：Agent 不自动提供 HA——两个 Agent 抓取同一 target 会导致重复序列，需通过 target 分区或 receiver 端去重解决
- **代价**：失去本地查询与告警能力；网络中断时数据丢失风险（WAL 窗口有限）；不适合需要本地自治的场景
- **参考**：[OneUptime 对比分析](https://oneuptime.com/blog/post/2026-08-03-prometheus-agent-vs-server-remote-write-edge/view) 明确指出"Agent 模式适用于采集层，完整 Prometheus 适用于独立监控层"

**方案 D：云厂商托管方案**

三家云厂商方案（AWS AMP、GCP Managed Prometheus、Azure Monitor managed Prometheus）在架构模式、配额限制、保留期、计费模型、K8s 集成深度、churn 内置缓解七个维度的详细对比见 S4.5 综合对比表。本节仅关注选型决策中的场景适配。

- **适用场景**：churn 高–极高，团队缺乏 Prometheus 运维能力，或需要自动扩展与内置配额隔离
- **场景化推荐**：
  - **纯 EKS**：AWS AMP + agentless collector，EKS 集成最深，label-based limits 防 noisy neighbor
  - **纯 GKE + 全局查询需求**：GCP Managed Prometheus，2 年保留期无额外费用，Monarch 后端跨区域查询
  - **纯 AKS**：Azure Monitor managed Prometheus，AKS 原生集成，但需注意 side-car 150K 序列上限
  - **多云**：评估 GCP 全局查询聚合，或采用 VictoriaMetrics/Thanos 自建统一查询层
- **代价**：按量计费在高 churn 场景下成本显著（churn 推高 active series 与 ingestion rate）；vendor lock-in；配额限制可能成为瓶颈
- **风险**：AMP 默认 50M 上限在极高 churn 下可能仍需提升；GCP 2 年保留期在极高 churn 下存储成本累积；Azure side-car 150K 上限在 K8s Pod 频繁伸缩时可能触发频繁扩展

**方案 E：混合架构（self-managed Prometheus + remote write 到云厂商）**

- **适用场景**：已有自建 Prometheus 投资，希望逐步迁移到托管；或多云/混合云环境
- **前置条件**：团队同时具备 Prometheus 配置能力与云厂商 IAM/网络配置能力
- **典型模式**：本地 Prometheus 保留 2h retention + 实时告警，remote write 到 AWS AMP / GCP / Azure Monitor 做长期存储与全局查询（[Last9](https://last9.io/blog/aws-prometheus-production-patterns/)）
- **代价**：双重运维（本地 + 云）；remote write 网络成本；数据一致性验证复杂度
- **风险**：迁移期间监控盲区；remote write 链路故障导致长期存储数据缺口

#### 三、关键选型决策条件

**何时选择云厂商托管而非自建远程存储？**

1. **团队规模**：SRE 团队 <3 人，无精力运维 Thanos/Mimir/VictoriaMetrics 集群
2. **churn 不可预测**：业务负载波动大（如事件驱动型流量），需要自动扩展
3. **合规要求**：需要云厂商 IAM 集成、审计日志、SLA 保障（99.9%+）
4. **多云已有绑定**：已深度使用某云厂商的 K8s 服务（EKS/GKE/AKS），托管方案集成成本最低
5. **成本拐点**：当 ingestion rate >500K samples/sec 时，自建 TCO 可能低于托管（见下文成本模型），但需计入运维人力成本

**何时选择 Agent 模式 + remote write 而非完整 Prometheus？**

1. **边缘采集层**：K8s 集群、工厂、分支办公室等仅需转发指标的场景
2. **中心已有完整监控**：查询、告警、仪表盘全部集中在中心后端
3. **资源受限**：边缘节点存储/计算资源有限，需最小化 footprint
4. **churn 极高**：本地 TSDB compaction 成为瓶颈，Agent 模式完全消除 compaction

**何时选择混合架构？**

1. **渐进迁移**：从自建 Prometheus 逐步迁移到托管，避免一次性切换风险
2. **本地自治需求**：需要本地告警在中心不可用时仍能工作（如工厂产线安全监控）
3. **多云策略**：避免单一云厂商锁定，self-managed Prometheus 作为统一采集层，remote write 到多个后端

#### 四、成本估算模型（自建 vs 托管 TCO）

基于 [dev.to 成本分析](https://dev.to/binyam/hosted-prometheus-vs-self-managed-a-neutral-guide-to-costs-control-and-trade-offs-3j6n) 与 [VictoriaMetrics 定价对比](https://victoriametrics.com/blog/managed-prometheus-pricing/) 的数据，构建以下 TCO 估算框架：

**托管方案成本公式**：

```
月成本 = (月摄入样本数 × 每百万样本单价) + (存储 GB × 每 GB 单价) + 查询成本 + 跨区域传输成本
```

以 200K samples/s（约 525.6B samples/月）为例：

| 方案 | 月摄入成本 | 月存储成本 | 月总成本 | 备注 |
|---|---|---|---|---|
| AWS AMP | ~$13,308 | ~$16 | ~$13,324 | 基于 [VictoriaMetrics 定价博客](https://victoriametrics.com/blog/managed-prometheus-pricing/) 计算 |
| GCP Managed Prometheus | ~$75,072 | 未计入 | ~$75,072+ | GCP 定价显著高于 AWS |
| VictoriaMetrics Cloud | ~$183 (compute) | ~$143 (storage) | ~$326 | 按 vCPU + 存储计费，与摄入量无关 |

**自建方案成本公式**：

```
月成本 = 基础设施（VM + 存储）+ 运维人力 + 工具链（Thanos/Mimir/VictoriaMetrics 部署）
```

以 50K samples/s 为例（[dev.to](https://dev.to/binyam/hosted-prometheus-vs-self-managed-a-neutral-guide-to-costs-control-and-trade-offs-3j6n)）：

| 成本项 | 月成本 |
|---|---|
| 3 × r5.large EC2 | ~$750 |
| 10TB 存储 | ~$230 |
| 运维人力（15h/月 × $100/h） | ~$1,500 |
| **合计** | **~$2,480** |

对比同场景托管方案（AWS AMP）：~$3,918/月。自建在 50K samples/s 场景下已有成本优势，且随规模增大优势更明显。

**成本拐点参考**：

- **<100K samples/sec**：托管方案通常更经济（运维人力成本 > 基础设施差价）
- **100K–500K samples/sec**：需根据团队运维能力评估；有经验团队自建更经济
- **>500K samples/sec**：自建 TCO 通常显著低于托管（[VictoriaMetrics 定价博客](https://victoriametrics.com/blog/managed-prometheus-pricing/) 显示 1M samples/s 场景下 AWS AMP 月成本 ~$47K，VictoriaMetrics Cloud ~$6K）
- **churn 对成本的影响**：高 churn 推高 active series 与 ingestion rate，直接增加托管方案的按量计费；自建方案中 churn 主要影响存储与 compaction 资源，边际成本增长较缓

**TCO 决策检查清单**：

1. 计算当前 `sum(rate(scrape_samples_scraped{job!=""}[5m]))` 得到 samples/sec
2. 用上述公式分别估算托管与自建月成本
3. 评估团队运维能力（能否 24/7 响应 Thanos/Mimir 故障？）
4. 评估合规要求（数据主权、加密、审计）
5. 评估 vendor lock-in 风险（迁移成本是否可接受？）
6. 考虑混合方案：prod 用托管（稳定性优先），dev/staging 用自建（成本优先）

#### 五、方案选型决策矩阵（按场景）

| 场景 | 推荐方案 | 理由 | 关键风险 |
|---|---|---|---|
| 纯 EKS，churn 中–高，团队 <5 人 | AWS AMP + agentless collector | 零运维，EKS 深度集成，label-based limits 防 noisy neighbor | 50M 上限可能需提升；vendor lock-in |
| 纯 GKE，churn 高，需长期保留 | GCP Managed Prometheus | 2 年默认保留期，全局查询，GKE 集成 | 高 churn 下 2 年保留期存储成本累积；定价最高 |
| 纯 AKS，churn 中，已有 Azure 生态 | Azure Monitor managed Prometheus | AKS 集成，side-car 架构 | 150K/side-car 上限在 Pod 频繁伸缩时可能频繁触发扩展 |
| 多云（AWS + GCP），churn 高 | self-managed Prometheus + remote write 到两家云；或 VictoriaMetrics 集群 | 避免单一云锁定；VictoriaMetrics 作为统一查询层 | 运维复杂度高；跨云网络成本 |
| 已有自建 Prometheus，churn 上升 | 渐进迁移：先加 remote write 到 VictoriaMetrics/AMP，再切换 Agent 模式 | 保护已有投资；分步降低本地 TSDB 压力 | 迁移期间监控盲区；数据一致性验证 |
| 边缘/工厂，churn 高，网络不稳定 | Prometheus Agent 模式 + remote write 到中心 | 最小化边缘 footprint；中心统一查询告警 | 网络中断时 WAL 窗口有限（默认 4h）；需持久化 WAL 磁盘 |
| 单集群，churn 极高（>50K series/min） | Mimir 集群 或 VictoriaMetrics 集群 | 内置 query sharding、多租户、cardinality 诊断 | Mimir 运维复杂度高；需专业团队 |
| 预算有限，churn 中，团队有运维能力 | VictoriaMetrics 单节点 + Prometheus remote write | 成本最低（$326/月 vs AMP $13K/月）；压缩比 2x–10x | 单节点 HA 需自行保障；无内置多租户 |

> **关键建议**：在做出最终决策前，先用 S5.1 的 churn 评估方法建立当前环境的 churn rate 基线，再结合上述矩阵选择 1–2 个候选方案进行 POC 验证。POC 应覆盖：(1) 模拟真实 churn 负载下的内存/CPU/磁盘表现；(2) 长范围查询（7d/30d）延迟；(3) remote write 链路在 churn 尖峰下的背压行为；(4) 故障场景（网络中断、后端不可用）下的数据完整性。

### 迁移路径规划与风险评估

迁移 Prometheus 到远程存储、云厂商托管方案或 Agent 模式，需要系统性的路径规划、回滚策略和数据一致性验证。不同迁移路径的风险画像差异显著：远程存储迁移主要风险在于历史数据完整性和查询语义差异；云厂商迁移的核心风险在于配额限制和计费模型变化；Agent 模式迁移则需处理本地查询与告警能力的丧失。

#### 一、迁移到远程存储方案（VictoriaMetrics / Thanos / Mimir）

**迁移步骤**

以迁移到 VictoriaMetrics 为例，完整路径如下：

1. **部署目标存储**：通过 Helm 部署 VMSingle 或 VMCluster，配置 retentionPeriod 和资源配额（[OneUptime 迁移指南](https://oneuptime.com/blog/post/2026-02-09-prometheus-to-victoria-metrics/view)）。
2. **历史数据迁移**：使用 `vmctl prometheus` 工具从 Prometheus 快照导入历史数据。对于大数据集，按时间窗口分批迁移以避免过载：
   ```bash
   ./vmctl-prod prometheus \
     --prom-snapshot ./prometheus-snapshot \
     --vm-addr http://vmsingle-vmsingle.monitoring.svc:8428 \
     --prom-filter-time-start 2025-01-01T00:00:00Z \
     --prom-filter-time-end 2025-02-01T00:00:00Z \
     --prom-concurrency 8 --vm-concurrency 8
   ```
3. **配置 remote write**：在 Prometheus 配置中添加 `remote_write` 指向 VictoriaMetrics，设置合理的 `queue_config`（capacity 建议为 `max_samples_per_send` 的 3–10 倍）（[Prometheus 官方 remote write 调优文档](https://prometheus.io/docs/practices/remote_write/)）。
4. **并行运行验证**：同时运行 Prometheus 和 VictoriaMetrics 至少两周，对比查询结果、内存使用和查询延迟。
5. **切换 Grafana 数据源**：将 Grafana 中的 Prometheus 数据源指向 VictoriaMetrics，大多数 PromQL 仪表盘无需修改即可工作。
6. **下线旧 Prometheus**：验证稳定后，停止 Prometheus 抓取并删除资源。

迁移到 Grafana Mimir 的步骤类似，但历史数据上传使用 `mimirtool backfill` 命令，且需注意 Mimir 不支持 Thanos 的 downsampling 块和 external labels 注入（[Grafana Mimir 迁移文档](https://grafana.com/docs/mimir/latest/set-up/migrate/migrate-from-thanos-or-prometheus/)）。

**数据一致性验证**

- **样本计数对比**：在并行运行期间，使用 `count(count_over_time(metric[1h]))` 在两端对比同一时间窗口的序列数量。
- **查询结果对比**：对关键业务指标执行相同的 PromQL 查询，比较返回的样本值。VictoriaMetrics 兼容 PromQL，但部分高级函数（如 MetricsQL 扩展）需确认兼容性。
- **摄入速率监控**：对比 `prometheus_remote_storage_samples_sent_total` 与目标端的摄入指标，确认无丢失。
- **时间窗口完整性**：验证迁移后的数据在时间边界处无缺口，特别是快照创建时刻前后的数据。

**回滚策略**

远程存储迁移的回滚相对简单：保留旧 Prometheus 实例至少一个 retention 周期（如 15 天），在 remote write 配置中保留旧存储的查询端点。如果新存储出现问题，可将 Grafana 数据源切回旧 Prometheus，同时保留 remote write 到双端。VictoriaMetrics 官方 FAQ 确认，启用 remote write 后 Prometheus 继续写入本地存储，因此旧数据在本地仍然可用（[VictoriaMetrics FAQ](https://docs.victoriametrics.com/victoriametrics/faq/)）。

#### 二、迁移到云厂商托管方案（AWS AMP / GCP / Azure）

**AWS AMP 迁移步骤**

1. **创建 AMP Workspace**：通过 AWS CLI 或控制台创建 workspace，配置 IAM 认证（SigV4 签名）（[AWS AMP 迁移最佳实践](https://aws.amazon.com/blogs/opensource/best-practices-for-migrating-self-hosted-prometheus-on-amazon-eks-to-amazon-managed-service-for-prometheus/)）。
2. **配置 remote write**：在现有 Prometheus 中添加 AMP 的 remote write 端点，使用 IRSA（IAM Roles for Service Accounts）进行认证：
   ```yaml
   remote_write:
     - url: https://aps-workspaces.us-west-2.amazonaws.com/workspaces/ws-abc123/api/v1/remote_write
       sigv4:
         region: us-west-2
       queue_config:
         capacity: 10000
         max_samples_per_send: 5000
         batch_send_deadline: 5s
   ```
3. **使用 recording rules 预聚合**：在本地 Prometheus 中配置 recording rules，仅将聚合后的数据发送到 AMP，以控制成本（[AWS 成本优化博客](https://aws.amazon.com/blogs/mt/optimizing-metrics-ingestion-with-amazon-managed-service-for-prometheus/)）。
4. **验证数据摄入**：通过 CloudWatch 指标 `ActiveSeries` 和 `IngestionRate` 确认数据正确摄入 AMP。
5. **切换查询端点**：将 Grafana 数据源从本地 Prometheus 切换到 AMP workspace。

**GCP Managed Prometheus 迁移**

GCP 的迁移路径类似，但需注意其默认 2 年保留期对存储成本的影响。迁移步骤包括：部署 GMP collector（自部署模式或使用 managed collection）、配置 remote write、验证数据摄入。GCP 提供全局查询（global queries）能力，可跨区域查询数据（[Google Cloud 文档](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus)）。

**Azure Monitor 迁移**

Azure 的 side-car 容器架构有 150,000 唯一时间序列上限，迁移前需评估当前序列数是否超限。如果超限，需先通过 relabeling 降低序列数或联系 Azure 支持提升配额（[Azure 扩展最佳实践](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)）。

**云厂商迁移风险**

| 风险维度 | AWS AMP | GCP Managed Prometheus | Azure Monitor |
|---------|---------|----------------------|---------------|
| 配额限制 | 默认 50M active series（2025.7 提升） | 按 tier 划分 | 每 side-car 150K 序列 |
| 计费变化 | 按摄入样本 + 查询 TPS 计费 | 按摄入样本 + 读取请求计费 | 按摄入样本计费 |
| 保留期 | 固定 | 默认 2 年 | 可配置 |
| 历史数据迁移 | 不支持自动迁移，需 remote write 实时写入 | 同左 | 同左 |
| 回滚难度 | 低（保留本地 Prometheus） | 低 | 低 |

**回滚策略**：云厂商迁移的回滚核心是保留本地 Prometheus 实例和 Grafana 数据源配置。由于云厂商不支持历史数据批量导入（仅支持 remote write 实时写入），迁移前的历史数据仍保留在本地 Prometheus 中。回滚时只需将 Grafana 数据源切回本地 Prometheus，并停止 remote write 配置。

#### 三、迁移到 Prometheus Agent 模式

Agent 模式（`--agent` flag，Prometheus 2.32+）的架构设计——禁用本地 TSDB 块存储、compaction、查询引擎与 recording/alerting rules，仅保留 WAL + remote write 管线——详见 S3.2（[Prometheus Agent 模式文档](https://prometheus.io/docs/prometheus/latest/prometheus_agent/)）。以下为迁移步骤：

1. **清单现有能力**：盘点所有本地 PromQL 查询、仪表盘、recording rules 和 alerting rules。这些功能在 Agent 模式下不可用，需全部迁移到中央平台。
2. **迁移规则到中央**：将 recording rules 和 alerting rules 迁移到中央 Prometheus 或远程存储（如 Mimir 的 ruler 组件）。
3. **配置 Agent WAL 与持久化**：按 S3.2 所述配置 Agent WAL 路径与 retention 参数，并确保 WAL 挂载到持久存储以避免容器重启导致数据丢失：
   ```bash
   prometheus \
     --agent \
     --config.file=/etc/prometheus/prometheus.yml \
     --storage.agent.path=/var/lib/prometheus-agent \
     --storage.agent.retention.min-time=5m \
     --storage.agent.retention.max-time=4h \
     --web.listen-address=0.0.0.0:9090
   ```
4. **Canary 验证**：先在一个集群部署 Agent，对比 scrape target 健康和样本速率。
5. **测试中断恢复**：模拟远程存储中断，验证 WAL 缓冲和恢复后的数据完整性。

**回滚策略**：从 Agent 模式回滚到完整 Prometheus 相对简单——移除 `--agent` flag，指定 `--storage.tsdb.path`，重启即可。但新启动的完整 Prometheus 没有历史查询数据，除非通过 `vmctl` 等工具从远程存储回迁。回滚的关键前提是：在迁移到 Agent 模式前，确保远程存储已积累足够的历史数据，或保留旧 Prometheus 的 TSDB 数据作为备份。

**迁移注意事项**：如果边缘站点需要在网络中断期间维持本地告警能力，应继续使用完整 Prometheus 而非 Agent 模式（[OneUptime Agent vs Server 对比](https://oneuptime.com/blog/post/2026-08-03-prometheus-agent-vs-server-remote-write-edge/view)）。

#### 四、迁移期间的监控盲区风险

迁移期间最常见的风险是监控盲区——在切换过程中出现数据缺口或告警失效。

**盲区产生场景**

1. **remote write 队列积压**：当远程存储响应变慢时，Prometheus 的 remote write 队列可能积压。如果远程端不可用超过约 2 小时，WAL 会被压缩，未发送的数据将丢失（[Prometheus remote write 调优文档](https://prometheus.io/docs/practices/remote_write/)）。
2. **快照与实时数据间隙**：使用 `vmctl` 迁移历史数据时，快照创建时刻到 remote write 生效时刻之间存在数据间隙。
3. **Grafana 数据源切换瞬间**：切换数据源时，如果新数据源尚未积累足够历史数据，仪表盘可能出现"无数据"状态。
4. **告警规则迁移遗漏**：从完整 Prometheus 迁移到 Agent 模式时，如果某些告警规则未迁移到中央平台，将导致告警静默失效。

**盲区缓解措施**

- **并行运行期**：新旧系统并行运行至少一个完整 retention 周期，确保新系统已积累足够数据。
- **双写验证**：在迁移期间配置 remote write 到新旧两个后端，对比数据一致性。
- **告警覆盖检查**：迁移前导出所有告警规则清单，逐条确认已迁移到目标平台。
- **监控迁移本身**：创建专门的迁移监控仪表盘，跟踪 `prometheus_remote_storage_samples_pending`、`prometheus_remote_storage_samples_failed_total`、`prometheus_remote_storage_samples_dropped_total` 等指标（[OneUptime Agent 模式指南](https://oneuptime.com/blog/post/2026-08-03-prometheus-agent-vs-server-remote-write-edge/view)）。
- **WAL 磁盘监控**：对 Agent 模式，监控 WAL 磁盘使用率，确保在 retention 窗口内有足够空间。

#### 五、风险评估清单

| 风险项 | 影响 | 概率 | 缓解措施 |
|--------|------|------|---------|
| 历史数据迁移不完整 | 长范围查询缺失数据 | 中 | 使用 vmctl/mimirtool 分批迁移，验证样本计数 |
| remote write 队列积压导致数据丢失 | 监控数据缺口 | 中 | 设置足够 queue capacity，监控 pending 指标 |
| 查询语义差异 | 仪表盘显示异常 | 低 | 并行运行期对比查询结果 |
| 云厂商配额限制 | 数据被丢弃 | 中 | 提前评估序列数，配置 label-based limits |
| Agent 模式丧失本地告警 | 中断期间告警失效 | 高 | 评估边缘站点自治需求，必要时保留完整 Prometheus |
| 回滚后历史数据缺失 | 无法查询迁移前数据 | 中 | 保留旧 Prometheus TSDB 至少一个 retention 周期 |
| 计费模型变化导致成本超预算 | 运维成本激增 | 中 | 使用 recording rules 预聚合，监控摄入量 |
| 迁移期间告警规则遗漏 | 告警静默失效 | 中 | 导出规则清单，逐条确认迁移 |

#### 六、迁移路径决策建议

- **自建远程存储**：适合有运维团队、需要长期保留历史数据、对查询延迟有要求的场景。VictoriaMetrics 适合单节点高性能场景，Mimir 适合多租户大规模场景，Thanos 适合已有 object storage 基础设施的场景。
- **云厂商托管**：适合希望减少运维负担、已有对应云厂商账户的场景。AWS AMP 适合 EKS 深度集成，GMP 适合 GKE 和全局查询需求，Azure Monitor 适合 AKS 环境。
- **Agent 模式**：适合边缘/分支站点仅需转发数据、中央平台负责存储和查询的场景。不适合需要本地告警和本地查询的场景。

无论选择哪种路径，核心原则是：**并行运行 → 验证一致性 → 切换 → 观察 → 下线旧系统**。跳过并行验证阶段是迁移失败的最常见原因（[Chronosphere 迁移失败分析](https://chronosphere.io/learn/why-observability-migrations-fail-2026/)）。

# Prometheus 时间序列高流失率（Series Churn Rate）：影响、系统化 治理与云厂商方案

## TL;DR

- **高 churn（时间序列流失率）比静态高基数更危险**：即使某一时刻的活跃序列数不高，只要 label 值频繁变化（Pod 重建、滚动发布、把 pod name/container id/IP/UUID/trace\_id/user\_id 塞进 label），Prometheus head block 会在默认 2 小时窗口内累 积所有出现过的序列（例如每分钟创建销毁 100 个 Pod、每 Pod 1000 指标，2 小时即 1200 万 序列），导致内存暴涨、OOM、WAL 膨胀、重启时 WAL replay ⻓达数小时、查询变慢、下 游 Thanos/Mimir 压力剧增。
- **治理要分层**：预防（埋点规范禁止高基数 label）→ 检测 （ rate(prometheus\_tsdb\_head\_series\_created\_total\[5m\]) 、 scrape\_series\_added 、 /api/v1/status/tsdb 、 promtool  tsdb analyze 、 cardinality explorer）→ 止血（ sample\_limit / label\_limit / target\_limit 、 metric\_relabel\_configs drop）→ ⻓期（recording rules 预聚合、streaming aggregation、native histograms、functional/hashmod 分片、Agent mode + 集中式后 端）。
- **云厂商三种策略**：**限流**（AWS AMP active series 限额、Azure AMW active time series 限 额、腾讯云 10 万维度组合限制、Mimir per-tenant limits）、**聚合**（Grafana Adaptive Metrics 平均省 35% 成本、Chronosphere aggregation/rollup rules、VictoriaMetrics stream aggregation）、**计费模型**（GMP 按 sample 计费不惩罚基数、Datadog Metrics without Limits 解耦摄取与索引）。选型要看你更痛的是稳定性、成本还是运维。

## Key Findings

1. 1. **churn ≠ cardinality，但会推高 cardinality**。高基数是"某一瞬间活跃序列多"；高 churn 是"序列被快速创建和淘汰"。Chronosphere 指出："低瞬时基数但高 churn 的工作负载，查询 越往历史查越慢，甚至比高瞬时基数低 churn 的更糟"。原因是历史 [Chronosphere][ref-01] block 的 倒排索引（postings）里塞满了早已 stale 的序列。
2. 2. **对 TSDB 的核心冲击集中在 head block、倒排索引和 WAL**。Head block 默认保留 2 小时全 部出现过的序列；据 Robust Perception，"a million series costs around 2GiB of RAM in terms of cardinality, plus with a 15s scrape interval and no churn around 2.5GiB for ingestion"（100 万序列约 2 GiB 基数内存，再加约 0.5 GiB 摄取内存）；WAL 记录每个新序 列，churn 越高 WAL 越大、重启时 WAL replay 越慢（社区 issue 显示近 4000 万序列实例 WAL replay 达 7 小时以上）。
3. 3. **native histograms 是格式层的结构性解药**。经典 histogram 每个 bucket 是一条独立序列 （20 bucket = 22 条序列），native histogram 把整个分布压进单条序列，社区报告可减少 10–20 倍 histogram 相关序列。
4. 4. **各家云厂商的应对策略可归为限流 / 聚合 / 计费三类**，且互相组合。

## Details

### 一、高 churn 的具体影响与原理

**1.1 对 TSDB 内部结构的影响**

- **Head block 内存**：Prometheus 把最近约 2 小时的数据放在内存 head block，压缩后才落 盘。只要 churn 制造新序列的速度快于旧序列过期，head 就不会收缩， prometheus\_tsdb\_head\_series [Alexandre Vazquez][ref-02] 单调上涨直到 OOM。健康实例该指 标应"趋于平台期"。
- **每序列 chunk 内存开销**：每条活跃序列在 head 会持有 chunk，约 1.5–2 KB/序列量级；这是 churn 的隐性成本——即使旧序列不再收到样本，它们在 2 小时窗口内仍占内存。
- **倒排索引（postings）膨胀**：VictoriaMetrics 指出高 churn 直接导致 indexdb（倒排索引） 膨胀，因为索引为"每条至少写入过一个样本的序列的每个 label"都建条目。VictoriaMetrics [VictoriaMetrics][ref-03] 官方数据：索引通常占磁盘约 20%，高基数场景可 >50%；Kubernetes [VictoriaMetrics][ref-04] 典型场景每序列 30–40 个 label、约 1 KB label=value，indexdb 体积可达 数据目录的 2 倍。 [VictoriaMetrics][ref-03]
- **head compaction 变慢 / WAL replay 变慢**：churn 越高，head 里序列越多，每 2 小时的 head 压缩越重；WAL 里记录的序列越多，重启时需要"重放整个摄取过程"重建内存 chunk， 可⻓达数分钟到数小时。 [Promlabs][ref-05]

**1.2 对查询性能的影响**

查询需要在倒排索引里做 postings 的交并集；churn 让历史 block 索引里堆满 stale 序列，range query 的 index lookup 被放大， /api/v1/series 、label values 接口变慢。Grafana Mimir 团队 描述："大量旧序列躺在存储里对写入路径没影响……只有在查询时它们才短暂变得重要"——即 [Grafana][ref-06] churn 的代价主要在查询侧兑现。

**1.3 内存、OOM 与 GC**：churn 推高活跃序列 → 内存线性上涨（"活跃 label 值翻倍，内存约翻倍"） → [OpenObserve][ref-07] Prometheus 不优雅 swap，直接 OOM 死掉。Last9 真实案例：给指标加 pod\_id label、200 个 Pod、每 Pod 50 指标、部署时 2 分钟 Pod churn → 每小时新增 15 万序列， 一周内 Prometheus 内存从 8 GB 涨到 32 GB，最终 OOMKilled 拖垮告警。 [Last9][ref-08]

**1.4 磁盘、block 压缩、remote write 队列**：churn 推高 block 体积和索引占比；remote write 场 景下序列激增会让队列积压（shards、queue capacity 增⻓、WAL 落后）。

**1.5 对 recording/alerting rule 评估**：序列多导致 rule 评估的底层查询变慢，评估延迟增加甚至超 时；GitLab 案例中 Sidekiq histogram bucket 过多导致规则在 Thanos 中"记录失败、序列缺失"， 减少 bucket 后每指标序列从 8000+ 降到约 1500。 [gitlab][ref-09]

**1.6 对下游⻓期存储的影响**：

- **Thanos**：Store Gateway 每个 TSDB block 本地约需 6 MB 索引，"高基数、大 label set 的 block 可达 30 MB 以上"；高基数序列导致 index/postings 拉取更多，Store [GitHub][ref-10] Gateway index cache（in-memory / memcached / redis）、compactor 压力增大。
- **Mimir/Cortex**：以 per-tenant series limit 保护（ max\_global\_series\_per\_user 、 max\_global\_series\_per\_metric ），distributor 层拒绝超限写入。
- **VictoriaMetrics**：churn 直接推高 indexdb，官方以 cardinality explorer 定位、series limiter 限流、stream aggregation 预聚合应对。 [VictoriaMetrics][ref-11]

**1.7 关键指标与排查方法（PromQL）**

- 活跃序列： prometheus\_tsdb\_head\_series
- churn rate（每秒新建序列）： rate(prometheus\_tsdb\_head\_series\_created\_total\[5m\])
- 序列淘汰： prometheus\_tsdb\_head\_series\_removed\_total
- 定位是哪个 target 在制造 churn（Prometheus 2.10+）： topk(20, increase(scrape\_series\_added\[1h\])) ，或 [Kaidalov][ref-12] topk(10, sum without(instance)(rate(scrape\_series\_added\[1h\])))
- 摄取后样本量： topk(20, max\_over\_time(scrape\_samples\_post\_metric\_relabeling\[5m\])) [Kaidalov][ref-12]
- TSDB status ⻚面： http://<prometheus>:9090/api/v1/status/tsdb?limit=50 （列出 top 序列/label 贡献者），UI [Kaidalov][ref-12] 上是 /tsdb-status
- 离线分析： promtool tsdb analyze <datadir> （Brian Brazil 添加的子命令），输出 [Robust Perception][ref-13] "Label pairs most involved in churning"、"Highest cardinality labels/metric names" 等；优势是只读索引、可在运行中的 [robustperception][ref-13] block 上跑、 不受 staleness 影响。真实案例（Coveo [Robust Perception][ref-13] 工程博客，一个撞 30Gi 内存上 限的 Prometheus Pod）分析显示： Series: 5547383 ... Label pairs most involved in churning: 4424281 job=kubelet ... 4417556 endpoint=cadvisor ... 1154707 \_\_name\_\_=container\_network\_tcp\_usage\_total ——一眼看出 kubelet/cAdvisor 是最大 churn 与基数源。

一个常用告警（社区示例）： rate(prometheus\_tsdb\_head\_series\_created\_total\[1h\]) > 10000 for 15m 。

### 二、系统性治理方案（预防 → 检测 → 止血 → ⻓期）

**2.1 埋点规范（预防，最根本）** 禁止把以下放进 label：pod name、container id、instance IP、 UUID/hash、trace\_id/request\_id、user id/email、原始 URL 路径、时间戳/分钟/小时。 VictoriaMetrics 明确点名 postgres\_exporter 的 queryid 、Kubernetes 的 pod 、时间派生 [VictoriaMetrics][ref-11] label、hash/uuid 是高 churn 的主因。做法：label [VictoriaMetrics][ref-03] 值枚举化 （有界集合）、URL 路径归一化（ /user/123 → /user/:id ）、把高基数信息放到日志/trace 而非 metric label。

**2.2 采集侧治理（止血 + ⻓期）**

- metric\_relabel\_configs ：在摄取前 drop 高基数指标、 labeldrop / labelmap 去掉高 流失 label、 keep 白名单。 [Grafana][ref-14]
- relabel\_configs （target 选择阶段）：选择/丢弃 target。
- 注意顺序： metric\_relabel\_configs 在 sample\_limit 之前生效。 [Robust Perception][ref-15]

示例（去掉高流失 label 并丢弃无用指标）：

yaml metric\_relabel\_configs: - source\_labels: \[\_\_name\_\_\] regex: 'go\_gc\_duration\_seconds.\*' action: drop - regex: '(container\_id\|pod\_uid\|image\_id)' action: labeldrop

**2.3 Kubernetes 专⻔治理** 针对 kube-state-metrics、cAdvisor、node-exporter 是最大 churn 源 （⻅上文 Coveo 案例，kubelet/cadvisor 占了绝大部分 churn）。用 Prometheus Operator 的 ServiceMonitor/PodMonitor 中的 relabel 去掉 pod/container 维度的高流失标签，用 workload/deployment 维度聚合替代 pod label。Operator 支持 sampleLimit 、 labelLimit 、 targetLimit （以及 enforced 版本做硬上限），超限时丢弃 target 样本并递增 prometheus\_target\_scrape\_pool\_exceeded\_label\_limits\_total [TFiR][ref-16] / prometheus\_target\_scrape\_pool\_exceeded\_target\_limit 。

**2.4 预聚合 / 降采样 / streaming aggregation（⻓期）**

- **Recording rules**：预聚合成低维度指标，查询更快；但缺点是数据已落盘后再聚合，反而增 加总存储和 Ruler 负载。 [VictoriaMetrics][ref-17]
- **Streaming aggregation**
  
  （摄取前聚合，优于 recording rule）：
  
  - VictoriaMetrics stream aggregation（vmagent 1.86+）：在写入前 by/without 聚合、 可 dropInputLabels / -streamAggr.dropInputLabels 去掉高基数 label，直接降 [VictoriaMetrics][ref-18] churn。
  - Prometheus Agent mode + remote write：本地不建 TSDB，只转发。
  - OpenTelemetry Collector： filter （filterprocessor，OTTL 条件丢弃 metric/datapoint，如 HasAttrKeyOnDatapoint("request\_id") ）、 transform （transformprocessor，OTTL delete\_key(datapoint.attributes, "user.id") 删除高基数 attribute）、 metricstransform （跨 label 值聚合降维，但仅限单 batch 内、不跨源）、 groupbyattrs （按属性分组压实 datapoint）、 deltatocumulative （delta 转 cumulative 以兼容需要累计量的 Prometheus，默认 max\_stale: 5m ）。
  - Grafana Alloy / Adaptive Metrics（⻅云厂商部分）。

**2.5 限流与保护机制（止血）**

- sample\_limit ：单 target 单次 scrape 超过样本数则整个 scrape 失败（up=0），是"应急泄 压阀"不是配额工具；配合告警 [Last9][ref-19] [Robust Perception][ref-15] prometheus\_target\_scrapes\_exceeded\_sample\_limit\_total 。 [Last9][ref-19]
- label\_limit / label\_name\_length\_limit / label\_value\_length\_limit （2.27+）：限 制 label 数量和⻓度。 [Last9][ref-19]
- target\_limit ：限制 job 的 target 数量。 [Last9][ref-19] [Prometheus][ref-20]
- keep\_dropped\_targets （2.47+）：限制内存中保留的被 relabel 丢弃的 target 数量。 [Prometheus][ref-20]

yaml scrape\_configs: - job\_name: 'my\_job' sample\_limit: 5000 label\_limit: 30 label\_value\_length\_limit: 2048 target\_limit: 1000

**2.6 架构方案**

- **功能分片（functional sharding）**：按团队/业务把 target 分到不同 Prometheus。
- **hashmod 水平分片**：用 hashmod 对 target 做取模分片。
- **Agent mode + 集中式后端**（Thanos Receive / Mimir / VictoriaMetrics）。
- **联邦（federation）的局限**：适合聚合少量已降维指标，不适合搬运原始高基数数据。

**2.7 ⻓期存储侧**

- **Thanos**：Store Gateway index cache（memcached/redis）、按时间分片 Store（ --min-time / --max-time ）、compactor 降采样。
- **Grafana Mimir**：per-tenant max\_global\_series\_per\_user （默认 15 万，可 [GitHub][ref-21] runtime 覆盖）、 max\_global\_series\_per\_metric 、 ingestion\_rate ；cardinality analysis API（ /api/v1/cardinality/label\_names 、 label\_values ，需 cardinality\_analysis\_enabled ）；overrides-exporter [GitHub][ref-22] 暴露各租户限额便于告 警。 [Grafana][ref-23]
- **VictoriaMetrics**：cardinality explorer、series limiter、stream aggregation、 downsampling + retention filters（企业/Cloud）。

**2.8 运维层**：定期 cardinality audit、指标成本归因（cost attribution）、CI 中做 metrics lint （ promtool check ）。

**2.9 Prometheus 3.x 与 native histograms**

- Prometheus 3.0（2024 年 11 月发布）：Remote [Greptime][ref-24] Write 2.0（string interning， KubeCon NA 2024 基准显示"60% fewer bytes on the wire, 90% fewer memory allocations, and 70% lower CPU usage during compression/decompression"——网络字节 少 60%、内存分配少 90%、压缩 CPU 低 70%）、OTLP 摄取增强、TSDB CPU/内存优化、 GOGC 默认从 100 调到 75（内存显著下降）、GOMAXPROCS/GOMEMLIMIT [GitHub][ref-25] 自 动匹配容器 limit。 [Greptime][ref-24]
- **native histograms**：单序列承载整个分布，10–20 倍 histogram 序列削减；支持乱序摄取； 已自 [Last9][ref-08] Prometheus v3.8.0 起成为 stable feature（注意 v3.9 起 --enable-feature=native-histograms 变为 no-op，改用 scrape\_native\_histograms 配置项）。 Grafana k8s-monitoring-helm PR #2586 描述 Alloy v1.11 的 convert\_classic\_histograms\_to\_nhcb 可在 scrape 时把经典 histogram 转 NHCB，"reducing active series by 90%+ for histogram-heavy workloads like Temporal, Istio, or any app with high-cardinality classic histograms"（对 Temporal/Istio 等 histogram 密集型工作负载减少 90%+ 活跃序列）。
- **OOO（out-of-order）samples**：Mimir 引入 WBL（Write-Behind-Log），内存中乱序 chunk 限制 30 样本以控内存。 [Grafana][ref-26]

**2.10 调优参数（针对 churn / 重启）**

- --storage.tsdb.retention.time （默认 15d）/ [Debian Manpages][ref-27] --storage.tsdb.retention.size （默认 0 禁用；注意 WAL 与 m-mapped chunk 计入总大 小）。 [Prometheus][ref-28]
- --storage.tsdb.head-chunks-write-queue-size （默认 0 禁用，实验性）：异步写 head chunk 并 m-map，解耦磁盘 I/O，高摄取/高 churn 下有帮助，代价是内存。
- --storage.tsdb.wal-compression （2.20 起默认开启，snappy）：官方称"you [Prometheus][ref-28] can expect the WAL size to be halved with little extra CPU load"，WAL 体 积减半、重启 replay 更快。
- --storage.tsdb.min-block-duration （默认 2h）/ max-block-duration （默认 min(10% retention, 31d)）：官方明确不建议生产调整（内部性能测试用）。 [Prometheus][ref-28]
- --enable-feature=memory-snapshot-on-shutdown （2.30+，实验性）：干净关闭时快照 内存 head，官方与作者博客称重启时间减少 [prometheus][ref-29] 50–80%；但只对干净关闭有效， 崩溃仍走 [Ganeshvernekar][ref-30] WAL replay，也不消除启动内存尖峰。

### 三、各家云厂商与商业产品方案对比

**AWS — Amazon Managed Service for Prometheus (AMP)**

- active series per workspace：2025 年 7 月默认从 1000 万提到 5000 万（"a higher default limit of 50M active time series per workspace, up from 10M"）；2026 年 7 月官方进一步升 级为"supports up to 1.5 billion active metric time series and up to 200,000 total recording and alerting rules per workspace"（单 workspace 最高 15 亿活跃序列、20 万条告警/记录规 则）；序列"过去 2 小时收到样本"即算活跃；2M–50M 区间按最近 30 分钟用量自动调整。 [amazon][ref-31]
- label-based active series limits（2025 年 4 月）：可为不同 label set（如 {app="payment-service", environment="prod"} ）设不同配额，单个应用暴涨只 throttle 它自己。
- 支持 native histogram 摄取/存储/查询。 [AWS][ref-32]
- Active metrics with metadata per workspace 默认 20000。 [amazon][ref-31]
- 策略：**限流**为主。

**Google Cloud — Managed Service for Prometheus (GMP)**

- **按 sample 摄取量计费，不为基数预先收费**：官方强调"新容器启动时不预收整月基数费用，只 在容器存活时按 sample 付费，不惩罚 HPA"。 [Google][ref-33]
- Metrics Management ⻚面：展示各指标摄取量、label/基数、读取次数、在告警/大盘中的使 用情况，可直接排除无用指标。 [Google][ref-34]
- 成本控制： metric\_relabel\_configs drop、拉⻓采样周期（10s→30s 减 66%，10s→60s 减 83%）、高基数低价值数据保留本地不上传。 [google][ref-35]
- 默认摄取配额 500 QPS/项目，单次最多 200 samples ≈ 每秒 10 万 samples。 [Google][ref-36]
- 策略：**计费模型**（按 sample）+ 过滤。

**Microsoft Azure — Azure Monitor managed service for Prometheus / Azure Monitor workspace (AMW)**

- 标准利用率指标 Active Time Series（过去 12 小时摄取的唯一序列数）；每个 [Azure Docs][ref-37] AMW 有摄取限额，超限可在⻔户查看用量。
- ama-metrics pod（Prometheus Agent mode）采集， ama-metrics-prometheus-config configmap 配置自定义 scrape 与 metric\_relabel\_configs ；replica pod 采 kube-state-metrics，daemonset 采 kubelet/cAdvisor/node-exporter。 [Azure Docs][ref-37]
- 不支持重复序列，重复会返回 422 错误（而非静默丢弃）；label/metric [Microsoft Learn][ref-38] 名 大小写不敏感。 [Microsoft Learn][ref-39]
- 单查询结果上限 64 MB。 [Microsoft Learn][ref-39]
- 策略：**限流** + relabel 过滤。

**Grafana Cloud / Grafana Labs**

- **Adaptive Metrics**：分析告警规则、recording rules、大盘和最近 30 天查询日志，识别"未 使用/部分使用"指标，自动生成 [Grafana][ref-40] aggregation rule 聚合掉未用 label。官方初期数 据"150+ 客户环境平均减少 20–50% 序列量"；截至 2026 年 8 月 Grafana 更新称该功能已"帮 客户消除 285 亿条活跃序列，平均降低 35% 指标成本"，客户 Mux "将指标量削减 60%，保留 期从 14 天延⻓到 13 个月"。可通过 UI/API/CLI/Terraform 应用与回滚，不破坏现有查询。按 [Grafana][ref-41] active series 计费（过去 1 小时收到样本），Adaptive Metrics 直接降账单。 [GitHub][ref-42]
- **Cardinality Management dashboards**（免费+付费所有层级）。 [Grafana][ref-43]
- **Grafana Alloy**：采集 agent，支持 relabel/聚合、NHCB 转换。
- **Mimir cardinality API**、per-tenant limits（⻅上）。
- 策略：**聚合**（Adaptive Metrics）为核心差异化。

**阿里云 — 可观测监控 Prometheus 版（ARMS Prometheus）**

- Recording Rule 预聚合能力，官方描述"基于 Recording Rule 提供指标数据的降采样、降维度 等能力，降低数据成本，提高数据查询能力"。
- 全局聚合实例：跨实例、跨账号聚合查询。 [Aliyun][ref-44]
- 集成中心、指标管理、开箱大盘、按量计费。
- 策略：**聚合 + 计费**。

**腾讯云 — Prometheus 监控服务（TMP）**

- 明确的序列限制：**同一指标下 label 维度组合不超过 10 万**（histogram bucket 多时不支持调 整）；label 名⻓ 1024 字符、label 值 2048 字符。
- 查询限制：单查询涉及 time series 不超过 10 万、数据量不超过 100 MB、并发超过 15 可能排 队；对告警规则和预聚合规则同样有效。 [Tencent Cloud][ref-45]
- 采集指标管理：可一键采集预设图表指标，或按监控图表和预聚合规则筛选需要的指标；预聚 合规则做指标筛选（另有"精简监控指标"功能）。 [Tencent Cloud][ref-46]
- 策略：**限流**（硬性维度上限）+ 指标精简。

**华为云 — AOM / CCE 云原生监控**

- AOM 2.x 提供托管 Prometheus 能力、轻量化指标采集插件（官方称"相比社区 Prometheus 资源使用量大大降低"）、全栈监控（基础设施+应用负载关联）。
- 策略：托管 + 轻量采集。

**火山引擎 — 托管 Prometheus (VMP)**

- 基于 VictoriaMetrics 技术栈的托管服务（工作区/workspace 模型、Remote Write 接入、 Federate 端点、vmalert 告警），继承 VM 的高 churn/高基数处理能力。
- 策略：**聚合/限流**（依托 VM 能力）。

**VictoriaMetrics（Cloud / Enterprise）**

- cardinality explorer（v1.94+ 也能查 Prometheus）、 [VictoriaMetrics][ref-17] series limiter（应对 高 churn/高基数）、 [VictoriaMetrics][ref-47] stream aggregation、downsampling + retention filters（企业/Cloud）。
- 策略：全能，**聚合 + 限流** 都强。

**Chronosphere**

- 定位专⻔解决 cardinality 问题的 Control Plane：Metrics Usage Analyzer / Traffic Analyzer（实时看摄取但未持久化的流量、各 label 基数）、aggregation/rollup [Chronosphere][ref-48] rules（存储前聚合降维，"drop instance label 后按服务聚合，Pod 增加也不 加容量"）、drop [Chronosphere][ref-49] rules、quotas（按 service/team 设配额）。官方口径"只按 存储量而非摄取量计费"。 [Chronosphere][ref-50]
- 策略：**聚合 + 配额 + 计费**三管⻬下。

**Datadog**

- **Metrics without Limits™**：解耦摄取与索引成本——全量摄取，但只对 allowlist 的 tag 保持 可查询（可索引）； [Datadog][ref-51] 不需要的 tag 从计费索引里剔除，可即时降本。 [Datadog][ref-52] custom metric = metric 名 + tag 值组合，高基数 tag（如 user\_id 1250 个值）直接乘出海量 custom metrics。 [SigNoz][ref-53]
- 策略：**计费模型**（decouple ingest/index）。

**其他**：New Relic、Last9（Levitate，宣称专治高基数）、SigNoz（ClickHouse 后端，查询时付代 价而非写入时）等。

### 四、可落地的排查与治理流程

**第 1 步：定位（诊断）**

1. 1. 看总量趋势： prometheus\_tsdb\_head\_series 是否单调上涨（不收敛）。
2. 2. 算 churn rate： rate(prometheus\_tsdb\_head\_series\_created\_total\[5m\]) ，对比 \_removed\_total 。
3. 3. 找元凶 target： topk(20, increase(scrape\_series\_added\[1h\])) 。
4. 4. 查 /api/v1/status/tsdb?limit=50 看 top 指标/label。
5. 5. 离线深挖： promtool tsdb analyze 看 "most involved in churning" 和 "highest cardinality labels"（如 Coveo 案例一眼定位到 kubelet/cadvisor）。

**第 2 步：止血（快速）**

1. 1. 对元凶 target 加 metric\_relabel\_configs drop 高基数指标、 labeldrop 高流失 label。
2. 2. 加 sample\_limit / label\_limit / target\_limit 防止再次失控（配合告警）。
3. 3. 若内存危急：临时扩容或缩短 --storage.tsdb.retention 应急；开启 --storage.tsdb.wal-compression （若未开）加速重启。

**第 3 步：⻓期治理**

1. 1. 推行埋点规范（禁高基数 label），CI 里加 metrics lint（ promtool check ）。
2. 2. 用 recording rules / streaming aggregation / native histograms 降维。
3. 3. 把 histogram 迁移到 native histograms（投入产出比最高）。
4. 4. 需要规模化则上 Agent mode + Mimir/Thanos/VictoriaMetrics，用 per-tenant limits + cardinality API 持续治理。
5. 5. 建立成本归因，让团队为自己的序列负责。

**典型阈值经验值**

- 单实例活跃序列：中型生产环境健康区间约 10 万–200 万；超过约 [OpenObserve][ref-07] 200 万–1000 万单机开始吃力，应考虑分片。
- churn rate：社区常用告警阈值 rate(prometheus\_tsdb\_head\_series\_created\_total\[1h\]) > 10000 （持续 15 分钟）； 更本质的判断是看 head\_series 是否"平台化"——持续上涨即有问题。
- 每序列内存：约 1.5–2 KB（head），100 万序列 ≈ 2 GiB 基数内存 + 约 0.5 GiB 摄取内存（15s 间隔无 churn，Robust Perception 数据）。
- Kubernetes 每序列 30–40 label、约 1 KB label=value；indexdb 可达数据目录 2 倍。 [VictoriaMetrics][ref-03]

## Recommendations

1. 1. **先诊断再动手**（本周）：跑上面第 1 步的 5 条 PromQL/工具，确认是 churn 还是静态高基数， 锁定 top 3 元凶 target 和 label。若 head\_series 单调上涨且 scrape\_series\_added 集中 在少数 target，即确诊 churn。
2. 2. **立即止血**（本周）：对元凶用 metric\_relabel\_configs drop + labeldrop ，并全局设 sample\_limit / label\_limit / target\_limit 作为护栏（触发即告警，不要当配额用）。
3. 3. **格式层降基数**（1 个月）：把 histogram 迁到 native histograms（Prometheus 3.x / Alloy NHCB 转换），histogram 密集场景可省 90%+ 序列——这是投入产出比最高的单项。
4. 4. **摄取前聚合**（1 个季度）：用 streaming aggregation（VictoriaMetrics / OTel Collector / Grafana Alloy）或 recording rule 把 pod / instance 等高流失维度聚合到 workload 维度。 优先 streaming aggregation（不增加存储）。
5. 5. **托管选型**：稳定性优先且预算充足 → 直接上托管（AWS AMP / Azure AMW 走限流， Grafana Cloud 走 Adaptive Metrics 自动聚合）；成本敏感且想少惩罚容器弹性 → GMP 的按 sample 计费或 Chronosphere 的按存储计费；已有 K8s 且想自建高性价比 → VictoriaMetrics（stream aggregation + cardinality explorer）；国内合规 → 阿里云 ARMS （Recording Rule 降维）/ 腾讯云 TMP（硬性维度上限）/ 火山引擎 VMP（VM 栈）。
6. 6. **建⻓效机制**：埋点规范写进研发规约、CI 加 lint、每月做 cardinality audit + 成本归因到团 队。

**会改变建议的阈值**：单机活跃序列突破约 200 万–500 万且内存吃紧 → 从"单机调优"转向"分片 + 集 中式后端"；churn rate 持续高但 head\_series 已平台化 → 问题在查询/重启而非内存，重点转向 WAL 压缩、memory-snapshot-on-shutdown 和下游 index cache。

## Caveats

- **各云厂商限额随时间变化**：AWS AMP 默认 active series 限额历史上从 1000 万→5000 万 （2025-07），单 workspace 上限从 10 亿升到 15 亿（2026-07）。本报告数字为撰写时（2026-08）值，采用前请以官方文档为准。
- **native histograms 成熟度**：自 Prometheus v3.8.0 起 stable，但部分工具链、下游存储和查 询兼容性仍需验证；v3.9 起启用方式已从 --enable-feature=native-histograms 改为 scrape\_native\_histograms 配置项，请以 prometheus.io 官方发布为准。
- **"减少 20–50%""平均降 35%""省 90%+" 等数字来自厂商/社区自述**（Grafana Adaptive Metrics、Alloy NHCB、Chronosphere 等），是特定环境结果，实际收益依你的指标结构而 定。
- **min/max-block-duration 调优被官方明确不建议**用于生产；memory-snapshot-on-shutdown 只对干净关闭有效，不消除崩溃后的 WAL replay，也不消除启动内存尖峰。 [Promlabs][ref-05]
- **腾讯云 10 万维度组合上限**等硬限制可能因套餐/版本不同，请以控制台实际为准。
- **WAL replay 达 7 小时**等极端数字来自单个社区 issue（近 4000 万序列实例），"每 WAL segment 约 3 秒"是第三方博客估算，非官方公式，仅作量级参考。

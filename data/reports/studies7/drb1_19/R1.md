# Prometheus 高流失率：影响机理、系统治理与云托管方案研究报告

## 执行摘要

Prometheus 中所谓“高流失率”（high series churn）不是简单的“时间序列很多”。Prometheus 以指标名 + 完整 Label 键值集合唯一标识一条时间序列，因此任何会持续产生新 Label 值或新 Label 组合的行为，都会产生新的 Series。官方明确警告不要把用户 ID、邮箱等无界值作为 Label，并指出每增加一个 Label 组合都会产生额外的 RAM、CPU、磁盘和网络成本。[1]

本报告建议把问题拆成两个正交维度：

因此，一个 Prometheus 可以是“1000 万条稳定 Series、低 churn”，也可以是“只有 100 万条活跃 Series，但每小时替换 30%”。后者看似 Active Series 不大，却可能每天产生数百万甚至上千万个不同 Series identity，对 Head、WAL、索引、Remote Write 缓存和 Compaction 都很不友好。Prometheus 当前提供 prometheus_tsdb_head_series_created_total、Head Series 数量、每 Target 的 scrape_series_added，以及 /api/v1/status/tsdb 的指标/Label 基数统计，可用于建立可量化的 Churn SLO。[2]

最重要的结论是：扩容存储并不是治理高 churn 的第一手段。 优先顺序通常应当是：

数据模型治理 → Relabel/过滤 → Scrape 分级 → 预聚合/Recording Rules → 采集与存储解耦 → Remote Write/分布式长期存储 → Downsampling/Retention 分层。

这是因为高 churn 的根因通常发生在 Series identity 创建之前；如果不先限制无界 Label、短生命周期 ID、Kubernetes UID/hash 等，只把数据从本地 Prometheus 搬到 Thanos、Mimir、Cortex、VictoriaMetrics 或云厂商，往往只是把问题转移到分布式存储的 Ingester、Index、Compactor 和对象存储层。Prometheus Remote Write 本身也不是免费的：官方文档指出其通常会使 Prometheus 内存增加约 25%，并明确指出由于 WAL 中每条 Series 都需要缓存 Series ID 到 Label 的映射，Series churn 会显著增加 Remote Write 内存占用。[3]

从影响面看，高 churn 同时损害四类目标。第一是监控正确性：生命周期短于或接近 scrape interval 的实例可能在消失前没有被成功采集；动态 Label 会切断同一逻辑对象的时间连续性。第二是性能与可靠性：Head metadata、WAL、索引、Compaction、Remote Write queue 和查询匹配集都会增大。第三是成本：多数托管 Prometheus 按样本、写入字节或存储计费，高基数再叠加短 scrape interval 会直接扩大费用。第四是运维噪声：若告警按 pod_uid、实例 hash 等易变维度产生 Alert Instance，同一业务故障可能反复产生新的告警身份。Prometheus 官方存储文档还说明，TSDB 通常先形成约两小时 Block，Compaction 时源 Block 与新 Block 会暂时共存，因此 Compaction 高压期磁盘峰值会高于正常稳态。[4]

在云托管方案中，截至 2026 年 8 月 30 日，差异非常显著。AWS AMP 的默认 Active Series 配额已经达到 5000 万/Workspace，可申请提升到 15 亿，但异常快速增长仍可能触发限流；Google Managed Service for Prometheus 基于 Monarch，保留 24 个月并自动做长期降采样，没有一个简单的项目级 Active-Series 总上限，但存在每 Monitored Resource 100 万条活跃 Prometheus Series 的安全限制；Azure Managed Prometheus 默认约 100 万 Active Series/Workspace，可申请大幅提升；腾讯 TMP 的公开限制更明确，为付费实例最高 450 万 Series，并限制单查询涉及的 Series 数和单指标维度组合；阿里云新一代 Prometheus 则强化了按写入量/样本计费以及指标治理能力。[5]

下面给出本报告建议的目标架构。核心原则是：高 churn 尽可能在采集边缘被消灭，高精度原始数据只保留在有实际诊断价值的时间窗口，跨集群/长期层主要承载稳定维度与聚合数据。

## 高流失率的定义、指标与诊断方法

Prometheus Series identity 可形式化为：

只要其中一个 Label Value 发生变化，就是另一条 Series。例如：

http_requests_total{
 service="checkout",
 pod="checkout-7bd88db5d6-abcde"
}

Pod 重建为：

http_requests_total{
 service="checkout",
 pod="checkout-69cbcb6dd9-fghij"
}

对 Prometheus 而言这是两条不同 Series，即使对业务而言仍然是同一个 checkout 服务。Prometheus 官方数据模型和命名指南明确说明，每一个唯一 Label 键值组合都是独立时间序列。[7]

高基数与高 churn 必须分开度量。 高基数是“当前集合大”；高 churn 是“集合变化快”。Prometheus 并没有官方统一的“超过 X% 就是高 churn”阈值，因此在生产环境更合理的是建立相对于自身基线和容量预算的 Churn Budget。Prometheus 官方对指标设计的经验建议是多数指标的 Label cardinality 应低于 10，并且只应有少数指标超过这一数量级，但这不是整个 TSDB 的 Active-Series 上限。[8]

建议至少建立以下几个指标。

| 维度 | 建议指标 | 含义及使用方法 |
| --- | --- | --- |
| 活跃基数 | prometheus_tsdb_head_series | 当前 Head 中 Series 数；这是容量基线，不等同于 churn。Prometheus TSDB API 也直接暴露 headStats.numSeries。[9] |
| Series 创建速度 | rate(prometheus_tsdb_head_series_created_total[15m]) | 单位时间创建的新 Series，是最直接的 churn 指标之一。Prometheus 项目本身也使用该计数器讨论 Series churn。[10] |
| Series 淘汰速度 | rate(prometheus_tsdb_head_series_removed_total[15m]) | 在支持该自监控指标的版本上，用于观察 Series 从 Head 移出的速度；应与创建速率联合分析。[11] |
| Target 级 churn | scrape_series_added | 每个 Target 每次 Scrape 新增 Series 的近似数量，特别适合定位哪个 Job/Instance 正在制造 churn。[12] |
| Label cardinality | /api/v1/status/tsdb | 返回 seriesCountByMetricName、labelValueCountByLabelName、memoryInBytesByLabelName、seriesCountByLabelValuePair，可直接定位“哪个指标/Label 最发散”。[9] |
| Scrape 前后数量 | scrape_samples_scraped 与 scrape_samples_post_metric_relabeling | 可以验证 Metric Relabel 实际删除了多少样本。[12] |
| Remote Write 压力 | pending、failed/retried、shards、发送延迟等 Remote Storage 自监控指标 | 用来发现 churn 是否已经转化为 Remote Write backlog、重试和队列扩容。Remote Write 队列会为 WAL 中 Series 保存 Label 映射，因此 churn 尤其重要。[3] |
| TSDB/WAL | WAL 大小、Head chunks、Compaction 时间、磁盘 I/O | 用于验证 Head/WAL/Compaction 压力是否随 churn 同步变化；Prometheus 高流量情况下可能保留超过三个 WAL 文件以覆盖至少约两小时原始数据。[13] |
| 查询 | p50/p95/p99、matched series、samples scanned、timeout | 需要和 cardinality/churn 关联观察；高基数查询会触及托管平台的 Series/Sample/Bytes 上限。AWS、GCP、Azure、腾讯均公开了相关查询限制。[14] |

一个很实用的规范化 Churn 指标是：

3600 *
sum(rate(prometheus_tsdb_head_series_created_total[15m]))
/
clamp_min(prometheus_tsdb_head_series, 1)

它表示“一小时内新创建 Series 数，相当于当前 Head Series 的多少比例”。例如 Active Series 长期稳定在 100 万，但该指标为 0.20，意味着每小时大约新建 20 万 Series；如果这种状态持续一天，即使活跃基数始终只有约 100 万，也可能产生约 480 万次新的 Series identity。这个例子说明为什么只看 prometheus_tsdb_head_series 很容易漏掉 churn。

这个指标尤其适合比较不同 Prometheus 实例，因为它进行了规模归一化。实践中建议用“过去 30 天同一时段的 P95/P99 + 容量预算”来设 Warning/Critical，而不是采用某个行业通用百分比；Prometheus 官方没有规定统一 churn 阈值。[15]

诊断时还应区分“样本量问题”和“Series identity 问题”。 假设有 100 万条稳定 Series：

15 秒 Scrape 大约产生 57.6 亿 Samples/日，60 秒约为 14.4 亿 Samples/日，减少 75%。Google Cloud 的官方成本优化文档同样明确指出，将 15 秒间隔改为 60 秒可减少约 75% 的按 Sample 成本。[16]

但这并没有把 100 万 Active Series 变成 25 万条，也不会消除 UID、Request ID 等 Label churn。因此：

> Scrape interval 主要控制样本率；Label/metric design 主要控制 Series cardinality 与 churn。

两者必须分别治理。

## 根因与对监控系统的具体影响

高 churn 最常见的根因可以归纳为“不稳定的身份被编码进时间序列身份”。

典型反模式包括：

| 根因 | 典型例子 | 为什么产生 churn |
| --- | --- | --- |
| 无界高基数 Label | user_id、email、request_id、完整 URL、IP、trace ID | 每一个新值都可能生成新的 Labelset。Prometheus 官方明确列出用户 ID、邮箱等为不适合作为 Label 的例子。[17] |
| Kubernetes 短生命周期身份 | pod_uid、Pod 名、ReplicaSet hash、container ID | Rollout、Autoscaling、Eviction、重调度都会不断制造新的值。 |
| 短命 Target | CronJob、CI runner、Batch Job、Serverless workload | Target 本身生命周期短，Target/instance 标签自然持续变化；如果生命周期与 scrape interval 相近，还可能在一次成功 Scrape 之前消失。Prometheus 默认 scrape interval 是 1 分钟，可按 Job 调整。[18] |
| 过宽 labelmap | 把全部 Kubernetes Labels 映射到 Series | 新的 deployment label、Git SHA、controller revision 等全部变成 Series identity。 |
| Relabel 配置错误 | 在 relabel_configs / metric_relabel_configs 中错误复制 __meta_* | 服务发现元数据从临时发现信息变成持久 Label；Metric Relabel 是采集之后、写入 TSDB 之前执行，应慎重控制。[19] |
| Scrape 间隔不合理 | 所有 Metrics 一律 5s/15s；或短命任务却使用很长 Interval | 过短会放大 Sample、网络和写入成本；过长可能遗漏短命 Target。Prometheus 要求 scrape timeout 不得大于 interval。[18] |
| HA 重复写入 | 两个 Prometheus 抓取同一 Target，但后端未正确 Dedup | 同一逻辑指标重复存储；如果 HA replica Label 处理错误，还会形成额外 Series。 |
| Pushgateway 生命周期错误 | 每个临时 Job 用 instance/随机 ID Push | Pushgateway 不会自动遗忘 Series；目标消失后必须显式删除，因此官方只建议它用于少数服务级 Batch Job 场景。[20] |
| Recording Rule 维度错误 | 聚合结果仍 by(pod,uid,hash) | 看似做了预聚合，实际上仍保留易变身份，甚至额外生成一套新 Series。 |

### 对监控准确性的影响

Prometheus 的 Pull 模型意味着 Target 必须至少存活到一次成功 Scrape。若一个 Job 存活几十秒，而 scrape interval 为一分钟，其部分生命周期很可能完全没有样本。这是 Scrape interval 与短生命周期 Target 的自然结果，因此对极短 Batch Job 应重新设计采集方式，而不是只增加存储容量。Prometheus 官方也明确不建议把 Pushgateway 当作普通 Pull 模型的通用替代，只建议用于有限的服务级 Batch Job。[21]

Label churn 还会打断逻辑连续性。例如同一个 Deployment 的 Pod 更新以后，rate(requests_total[5m]) 是在旧、新两个不同 Series 上计算；如果查询和 Recording Rule 没有先投影到稳定的 service、namespace、cluster 维度，就容易出现短窗口缺口、锯齿或“新实例突然出现”的效果。其根本原因仍是 Prometheus 将完整 Labelset 视为 Series identity。[22]

### 对存储费用和 TSDB 内存的影响

Prometheus 官方给出的 Sample 数据粗略容量估算是平均约 1–2 bytes/sample：

但这个公式主要描述 Sample 压缩后的数据量，并不能完整反映大量不同 Series 所需的 Label、Symbol、Index/Postings 和 Head metadata 成本。Prometheus 官方 instrumentation 指南特别强调，每个 Labelset 都会增加 RAM、CPU、磁盘和网络成本。[23]

因此“每天 10 亿 Samples 来自 10 万稳定 Series”和“每天 10 亿 Samples 来自几千万个短命 Series identity”对 TSDB 并不是相同的工作负载。后者需要处理更多 Series 生命周期、Index entry 和 Label metadata；Prometheus 当前甚至提供实验性的 stale_series_compaction_threshold，在 stale Series 占 Head 比例达到指定阈值时提前压缩并从内存移除这些 Series，直接说明大量 stale Series 会成为 Head 内存治理问题。[24]

### 对 WAL 和 Remote Write 的影响

高 churn 对 WAL/Remote Write 尤其敏感。Prometheus 的 Remote Write 实现会从 WAL 读取数据，并维护 Series ID 到完整 Labels 的缓存；官方 Remote Write tuning 文档明确指出，高 Series churn 会显著增加此缓存的内存需求。同一文档指出，启用 Remote Write 后内存通常会比不启用时增加约 25%，并且每个 Queue Shard 的 capacity 与 max_samples_per_send 都继续占用额外内存。[3]

这意味着“Prometheus OOM → 加一个 Remote Write 后端”可能反而恶化问题。正确顺序应是先消除不必要的新 Series，再考虑通过 Agent Mode 或水平分片把采集与长期存储解耦。Prometheus Agent Mode 为 Remote Write 场景使用定制 WAL，并关闭本地完整 TSDB、查询、Recording Rule 和 Alerting，因此适合纯采集层，但会牺牲本地查询和本地规则能力。[25]

### 对查询延迟的影响

查询成本大致可拆解为：

高 Label cardinality 首先增加 Matcher 可能命中的 Series 数；长时间范围再放大需要读取的 Samples/Blocks。因此多数托管平台都同时限制 Series 和 Samples。例如腾讯 TMP 单查询最多涉及 10 万 Series、100 MB 数据；AWS AMP 对单 Query 有 5000 万 Samples 和 1200 万 fetched Series 等约束；Azure Managed Prometheus 也设置查询样本和 Series 限制。[26]

阿里云官方 PromQL 文档也给出了非常直观的警告：如果 metadata 接口不加合理的 match[]，底层可能命中数百万 Series，查询时间从数百毫秒增加到几十秒，并把内存消耗推到 GB 级。[27]

因此“PromQL 慢”经常并不是 PromQL 语法本身的问题，而是数据模型和选择器允许它触达过多 Series。

### 对 Compaction、磁盘与 CPU 的影响

Prometheus 通常先把 Head 数据形成约两小时 Block，再在后台合并成更大 Block；Compaction 最大 Block 时间跨度可达到 Retention 的 10% 或 31 天。Compaction 期间源 Blocks 和新 Block 会同时存在，所以磁盘使用量可能暂时超过 retention size。WAL 和 chunks_head 也不受 persistent block 删除机制完全控制，因此容量规划必须为两者保留峰值空间。[13]

在分布式 TSDB 中同样存在这一规律。例如 Grafana Mimir 官方建议大致按每 2000 万 Active Series 至少一个 Compactor进行容量规划，并指出 Compactor 的资源利用率直接受 Active Series 数影响；Cortex 也曾把 Compactor 识别为超大规模 Active-Series 场景的重要扩展瓶颈。[28]

### 对告警噪声和资源使用的影响

由于 Labelset 决定 Series identity，若 Alert Query 保留 pod、pod_uid、container_id、revision hash 等易变维度，Pod 一次 Rollout 就可以让旧告警 Instance 消失、新告警 Instance 再出现。从人的角度是同一 Service 的持续故障，从 Alertmanager 的角度却可能是不同的一组 Labels。因此生产告警通常应聚合到稳定的服务/SLO 维度，将 Pod 等信息留作 Annotation 或 Drill-down，而不是 Alert identity 的必要组成部分。这是 Prometheus Label identity 模型的直接推论。[22]

## 系统级治理方案与实施方法

系统治理不应该依赖某一个“魔法配置”。下面按照收益优先级总结主要方案，并给出实现步骤、Trade-off、运行注意事项和验证指标。

| 方案 | 实施方法 | Trade-off / 风险 | 运行注意事项 | 如何验证 |
| --- | --- | --- | --- | --- |
| Metric / Label 设计治理 | 禁止 request_id、user ID、完整 URL、Pod UID、container ID 等无界 Label；将动态 ID 放日志/Trace；对 HTTP route 使用模板路由 /users/:id 而非真实路径。为每个团队设 Series/Label Cardinality Budget。 | 会减少按任意 ID 直接用 PromQL 检索的能力，应通过日志或 Trace 补充。 | Label 政策必须进入 SDK、Exporter 和 Code Review，而不是仅由 Prometheus 运维团队事后处理。Prometheus 官方明确不推荐无界 Label。[1] | head_series、创建率、Top Label values、Top metric Series；治理后应看到新 Series 创建率显著下降。 |
| Target Relabel | 在 relabel_configs 阶段删除不需要的 Targets；只把稳定的 Kubernetes 元数据映射成 Label；避免对所有 __meta_kubernetes_* 做宽泛 labelmap。 | Drop Target 意味着其所有指标消失。 | 这是“抓取前”过滤，收益最大，因为连 HTTP Scrape 开销都不产生。[19] | Targets 数、scrape duration、Samples/s、网络流量。 |
| Metric Relabel | 在 metric_relabel_configs 中 drop 无价值 Metric 或高风险 Series；必要时 labeldrop 动态 Label。 | 删除 Label 后若原本多条 Series 只靠该 Label 区分，可能产生冲突/重复样本；必须先模拟。up 不受 Metric Relabel 自动处理。[19] | 先通过 scrape_samples_scraped - scrape_samples_post_metric_relabeling 估算收益，再灰度。 | scrape_samples_post_metric_relabeling / scrape_samples_scraped、Series creation rate。[12] |
| Write Relabel | 本地保留高精度数据，但在 remote_write 前只发送关键 Metric/稳定 Label；用于把“诊断数据”与“长期数据”分层。 | Remote Backend 不再拥有全部原始数据，因此远端 Alert/Query 必须重新评估。 | 特别适合本地短 retention + 云端长期 retention 的组合。Remote Write 仍需关注 Series cache 和 Queue。[3] | Remote samples/s、网络、远端 Active Series、账单，以及本地/远端关键 Query 一致性。 |
| Scrape 分级 | 按业务价值划分 5/15/30/60/300 秒，而不是全局统一；SLO/故障诊断指标保持较细，容量趋势类指标降低频率。 | Scrape 变长会降低短时事件的时间分辨率，并更容易漏掉极短 Target。 | 调大 Interval 不会降低 Active Series cardinality，只降低 Samples/s。Google 官方举例 15→60 秒可将 Sample 成本降约 75%。[16] | Samples/s、Cost、Dashboard 精度和告警检测延迟。 |
| 短命 Batch 任务治理 | 服务级 Batch 可谨慎使用 Pushgateway；与具体机器绑定的 Batch 更适合 Node Exporter textfile collector；不要为每次执行生成随机 instance Label。 | Pushgateway 不会自动遗忘 Series，需要额外生命周期管理。 | Prometheus 官方明确只建议 Pushgateway 用于有限的服务级 Batch Job。[20] | stale Series 数、Pushgateway Series 增长速度、Batch 成功率。 |
| Recording Rules / 预聚合 | 将 pod/container 级原始指标提前聚合为 cluster/namespace/service/status 等稳定维度；Dashboard 和长期查询优先使用 Recording Series。 | 会牺牲部分事后 drill-down 精度；Rule 本身也会生成 Series，错误 grouping 反而增加 cardinality。 | Rule 的 by(...) 必须经过 Cardinality Review。腾讯 TMP 原生提供预聚合，用于降低复杂查询成本。[29] | Query p95/p99、Samples scanned、Recording Series 数与原始 Series 比例。 |
| Native Histograms / Bucket 治理 | 对经典 Histogram 减少无意义 Buckets，或在生态支持成熟时采用 Prometheus Native Histograms，避免每个 bucket 都扩展为独立经典 Series。 | Client、Remote Write、长期存储和 Grafana 版本必须共同验证兼容性；不应仅为省 Series 盲目切换。 | Prometheus 当前文档已将 Native Histograms 纳入正式能力，但迁移需按客户端和后端逐一验证。[30] | 同一业务 Histogram 的 Series 数、Samples/s、查询结果误差。 |
| Federation | 每个 Cluster/Region 保持自己的 Prometheus；上层 Prometheus 通过 /federate 只抓取预聚合/关键指标。 | Global 层无法查询所有底层 Raw Series；底层 churn 本身仍需治理。 | Prometheus 官方将层级 Federation 作为扩展到大量数据中心/节点的架构之一。[31] | Global Active Series、Federate Samples/s、跨区域查询延迟。 |
| Agent / 边缘采集层 | 将纯采集节点切到 Prometheus Agent Mode，再 Remote Write 到中心 TSDB；或使用具备同类 relabel/buffering 能力的 Collector。 | 没有本地 PromQL、Recording Rules 和 Alerting；中心存储不可用时受 WAL Buffer 窗口约束。 | 适用于“大量 Cluster，各 Cluster 不需要完整本地 Prometheus”的场景。[25] | Agent CPU/RAM、WAL、Remote Write lag、中心端 ingestion success。 |
| Remote Write 横向扩展 | 按 region/tenant/env 分 Workspace/Tenant；为 HA replica 设置稳定 external labels，并在后端启用 Dedup；按 backlog 调整 shards/capacity。 | Queue/shards 越大占用越多内存；Remote Write 不能修复源头 cardinality。 | 高 churn 会扩大 Series cache；容量参数不应只追求“越大越好”。[3] | pending、failed/retried、shards desired、最高已发送时间戳与当前时间差。 |
| Downsampling | 原始 15s/30s 数据仅保留短周期；长期数据转 5m、1h。 | 不适合精确重建瞬时 spike 或短时 SLO 事件。 | Thanos 默认下采样逻辑中，Raw 数据超过约 40h 后生成 5m 数据，5m 数据超过约 10d 后生成 1h 数据；Retention 应保证下一层下采样在数据删除前完成。[32] | 长时间 Query bytes/samples、对象存储增长率、P95 Query。 |
| Retention 分层 | 热：高分辨率；温：聚合/降采样；冷：对象存储或归档。按数据价值而不是“一律保留一年”。 | 历史 Root Cause Analysis 能力下降。 | Prometheus 本地默认 retention 在未配置相关参数时为 15d；长保留更适合对象存储/托管 TSDB。[13] | TB/month、恢复/查询次数、历史 Dashboard 使用率、Cost/Tenant。 |
| Series 限额与治理门禁 | 每 Team/Tenant/Metric 设置 active-series、label count、ingestion rate 和 query budget；在 CI 检查新 Metrics。 | 过严会把真正有价值的数据拒掉。 | 比“系统快 OOM 以后扩机器”更可预测。AWS 已支持按 Label Set 控制 Active Series；Mimir/Cortex 等也提供 Tenant Limits/Cardinality 能力。[33] | rejected samples、limit utilization、top offenders、错误预算。 |

一个安全的 Metric Relabel 例子是先从“明确不需要的指标”开始，而不是立刻删除身份 Label：

scrape_configs:
 - job_name: app
 scrape_interval: 30s

 metric_relabel_configs:
 # 例：确认确实不需要以后，删除某类高成本指标
 - source_labels: [__name__]
 regex: 'debug_.*|experimental_.*'
 action: drop

 # Label drop 必须先验证：
 # 删除后不同原始 series 不能变成同一 labelset
 - regex: 'request_id|trace_id'
 action: labeldrop

Metric Relabel 发生在 Scrape 之后、写入 TSDB 之前，因此能够减少 TSDB、Remote Write 和后端成本，但不会节省 Target HTTP Scrape 本身的流量；若整个 Target 都不需要，应优先使用 Target relabel_configs Drop。[19]

随机丢 Sample 通常不应当成为第一优先级的“Sampling”。 对 Metrics 来说，更可控的策略是确定性地提高 scrape interval、减少 exporter 输出、删除 Metric、预聚合或 Downsample。随机丢点会制造不规则间隔，使短窗口 Rate/Alert 对样本稀疏更加敏感；同时它并不会改变 Series identity，所以对高 churn 的根治价值有限。

## 长期存储方案与主要云厂商对比

长期存储首先应从架构模式选择，而不是直接从品牌选择。

| 方案 | Churn 处理能力 | 长期存储模式 | Dedup / Downsampling | 主要优点 | 主要代价 |
| --- | --- | --- | --- | --- | --- |
| Prometheus Local TSDB | 中低；高 churn 直接压 Head/WAL/Index | 本地磁盘 Block | 无全局 HA Dedup；无内建长期多层 Downsampling | 简单、原生 PromQL、故障面小 | 单节点存储不集群/不复制；长 retention 和大量 churn 对单机压力大。[13] |
| Thanos | 中；不会消除源 Prometheus Head churn | Prometheus Block 上传对象存储，Query 跨 Sidecar/Store | Query 支持 replica Dedup；Compactor 支持 Downsampling 与 Retention。[34] | 对现有 Prometheus 改造小；对象存储经济；Global Query 成熟 | 每个 Prometheus 仍承担本地 Scrape/Head/WAL；Block/Compactor/Store Gateway 需要运维 |
| Cortex | 高，支持分布式多租户 | Ingester + Blocks/Object Storage + Store Gateway | Compactor 合并/去重 Block | Remote Write 原生、多租户、可水平扩展；AWS AMP 基于 Cortex。[35] | 微服务组件多；高 cardinality 大 Tenant 仍会把压力转到 Ingester/Compactor/Query |
| Grafana Mimir | 高 | Ingester 保存近期数据，对象存储长期 Blocks；现代架构还支持独立 ingest-storage 设计。[36] | Compactor 合并 Block、去重 Chunks，降低 Index/Storage 并改善查询。[37] | 多租户、限额、Query Frontend、对象存储，适合大规模集中平台 | 运维复杂；Compactor 等组件必须按 Series 数容量规划，官方建议约每 2000 万 Active Series 一个 Compactor。[38] |
| VictoriaMetrics | 很强，产品明确针对 high-cardinality/high-churn 提供 Series Limiter/Cardinality Explorer | 自有时序存储，支持单机和 Cluster | 支持 Dedup；集群/存储层支持 Retention/Downsampling 相关处理 | 高 churn 场景专门提供治理工具；Active-Series cache/slow inserts 可直接监控。[39] | 与纯 Prometheus TSDB 架构不同，需要对 PromQL/MetricsQL、运维工具和迁移流程做验证 |
| Cloud Managed Prometheus | 通常最高，容量由厂商分布式后端吸收，但各有 quotas | 厂商管理 | 按服务不同 | 不维护 TSDB/Compactor/Object Store；弹性与 SLA 较清晰 | 锁定厂商计费模型、Quota 和跨云网络；源端 churn 仍会影响采集/Remote Write 和账单 |

其中 Thanos 更像“把 Prometheus 的长期存储与全局查询外置”；Cortex/Mimir 更像“以 Remote Write 为入口的分布式 Prometheus 数据库”。因此如果现有大量独立 Prometheus 已经运行稳定、主要缺的是长期保留和统一查询，Thanos 通常改造较小；如果目标是构建多租户中心化 Metrics Platform，则 Cortex/Mimir 或托管 Prometheus 通常更自然。这个判断是基于各项目官方架构进行的系统设计推论。[40]

云服务选型不能仅看“最大 Series”。一个极端但重要的例子是：AWS Workspace 可以扩展到很高的 Active-Series 数，但官方同时明确设置“Active Series 突然增长”的保护机制；如果 Series 在短时间内比过去基线翻倍或突然增加数千万，仍可能被限流。因此高上限不是允许无限 churn。[42]

同样，Google 的“没有全局 Active-Series 硬上限”并不等于无 Cardinality 风险：每 Monitored Resource 仍有 100 万 Active Prometheus Series 的保护限制，查询返回大小和 API 配额也存在边界。[47]

从成本角度也必须区分厂商模型：

AWS 明确拆分 Ingestion、Storage 和 Query；GCP 的 Prometheus Metrics 长期 retention 包含在模型中但按 Samples 和 Read API 计费；Azure 按 Metrics Ingestion/Query 计费并含 18 个月 retention；腾讯把 retention 长度直接纳入每百万数据点单价；阿里则允许按未压缩写入 GB 或按数据点计费，并提供不同热/归档层。[68]

所以同一 workload 应当至少用以下三个输入做实际账单模型：

第一项决定大多数 ingestion 费用；第二项决定 metadata/churn 压力；第三项决定 Query 与长期读取成本。只用“每天 Samples”估算容量，会系统性低估高 churn 工作负载的 RAM、Index、Compactor 和 Remote Write 成本。

## 推荐目标架构与技术取舍

在没有明确 Cluster Size、预算和 Retention 前，最稳健的默认架构不是“单个超大 Prometheus”，也不是立即把所有数据送到一个远端 TSDB，而是采用分层、局部故障域、稳定维度长期化：

|  |
| --- |

边缘层的目标不是存很多数据，而是控制数据进入中央系统之前的形态。 当某个 Exporter 因软件升级突然把 request_id 当 Label 输出时，边缘 Cardinality Guard 可以只影响一个 Cluster，而不是立刻让全局 Mimir/AMP/TMP Workspace 接收数百万新 Series。

对于“是否保留本地 Prometheus”，建议按需求分三种：

| 需求 | 推荐 |
| --- | --- |
| Cluster 内必须在中央平台断网时继续本地告警/查询 | 保留完整 Prometheus，较短本地 retention，同时 Remote Write |
| 所有查询/告警已经中心化，只需要可靠采集 | Prometheus Agent / Collector → Remote Write；减少本地 TSDB 资源。[25] |
| 多 Cluster 只需中央汇总 SLO/容量指标 | Cluster 内 Recording Rules + Federation 或 Remote Write 预聚合结果。Prometheus 官方支持层级 Federation。[31] |

Thanos 与 Remote-Write 型架构也有一个关键区别。 Thanos Sidecar/Object Storage 模型一般允许原 Prometheus 继续负责抓取和本地 TSDB，然后把 Blocks 上传，因此能很好地解决长期存储，却不会自动解决原 Prometheus Head churn；Agent → Mimir/Cortex/Managed Prometheus 则能把长期 TSDB 移出 Cluster，但 Agent 的 WAL/Remote Write Series cache 仍然会受到 churn 影响。[69]

因此，不存在一个后端能够让错误的数据模型“免费”。

Retention 建议采用按信息价值分层，而不是简单规定所有数据 180 天 Raw。一个可作为起始设计的策略是：

| 层 | 示例用途 | 示例精度 | 原则 |
| --- | --- | --- | --- |
| Hot | Incident、短窗口 SLO、Pod Debug | 15s/30s Raw | 时间短、查询快 |
| Warm | 周/月容量与性能分析 | 1m–5m | 以 Recording / Downsample 为主 |
| Cold | 年度容量趋势、审计性趋势 | 1h | 对象/归档存储 |
| Ephemeral diagnostic | 高基数 Pod/Endpoint debug | Raw | 最短 retention，必要时不进入中央长期层 |

这些时间长度本身应由业务 SLO 决定，不是 Prometheus 的固定要求。Thanos 给出的默认 Downsampling 时机则是很好的参考：Raw 超过约 40 小时生成 5 分钟分辨率，5 分钟数据超过约 10 天生成 1 小时分辨率，并提醒 Retention 不应早于下一阶段 Downsampling。[32]

对 HA，应将“复制”和“去重”一起设计。Thanos Query 明确支持 replica sample deduplication；Mimir Compactor 会合并 Blocks 并删除重复 chunks，从而降低对象存储和索引成本。[70]

但 Dedup 只能消除“同一 Series 的重复副本”，不能消除：

pod_uid=A
pod_uid=B
pod_uid=C

这样的真实 Series churn。因此不要把 Dedup 与 Cardinality Reduction 混为一谈。

## 迁移路线图与优先级检查清单

对一个当前已经出现高 churn 的生产系统，最危险的做法是同时更换采集器、Remote Write、后端 TSDB 和告警体系。更稳健的方法是先稳定数据模型，再逐层迁移。

最高优先级：先止血。 在任何扩容或迁移之前，先建立 head_series、Series creation rate、scrape_series_added、Top Metric/Label cardinality、Prometheus RSS/CPU、WAL、Remote Write pending/retry、Query p95/p99 和每日 Samples/s Dashboard。Prometheus 自身的 /api/v1/status/tsdb 已可返回 Head、Metric、Label、Label-pair 的 Cardinality 统计，因此无需额外平台就能建立第一版诊断。[71]

随后应立即冻结新增的无界 Labels。对当前 Top offenders，优先处理 request_id、trace ID、user ID、Pod UID、container ID、动态 URL、Git SHA/Revision 等；对已经发现的高风险 Metric，用 Metric Relabel 做灰度 Drop。Prometheus 官方关于 Label cardinality 的建议支持这一优先顺序。[1]

可以将实际迁移检查表按以下优先级执行：

| 优先级 | 检查项 | 完成标准 |
| --- | --- | --- |
| P0：立即 | 建立 Active Series 与 Churn Dashboard | 能回答“每小时新增多少 Series、哪个 Job/Metric/Label 制造最多” |
| P0：立即 | 审计 Top 20 Metric 与 Top 20 Label Values | 明确哪些是有界业务维度，哪些是 ID 类无界维度 |
| P0：立即 | 检查 Kubernetes Relabel | 不再把 UID/container ID/revision 等无意持久化 |

其中最值得关注的是 Normalized Churn，而不是单独的 Active Series。如果优化以后 Active Series 从 100 万降到 80 万，但每天仍创建 500 万个新 Series identity，那么问题只得到有限缓解。

最终，从系统设计角度，高 churn 的治理原则可以归纳为：

> 把稳定业务维度放进 Metrics，把高熵身份放进 Logs/Traces；在离数据源最近的位置限制 Cardinality；高精度数据短存，稳定聚合数据长存；利用 Remote Write、Federation、分布式 TSDB 和对象存储解决规模问题，但不要期待存储层替代数据模型治理。

Prometheus 官方本身已经在多个层面体现了这一原则：限制高 Cardinality Labels、在入库前提供 Metric Relabel、通过 Agent Mode 解耦采集与存储、通过 Federation 聚合多 Prometheus，并在 Remote Write 文档中特别警告 Series churn 的内存影响。[74]

对于没有既定 Cluster Size、Retention 或预算的环境，最稳健的默认决策不是预先选择某一家“大容量后端”，而是先把以下四个指标变成组织级 SLO：Active Series、New Series/hour、Samples/sec、Query scanned series/samples。一旦这四项能够稳定预算化，Prometheus 本地、Thanos、Mimir/Cortex、VictoriaMetrics 以及 AWS/GCP/Azure/阿里云/腾讯云之间的容量和成本选择就会从“猜配置”变成可计算的工程问题。[75]

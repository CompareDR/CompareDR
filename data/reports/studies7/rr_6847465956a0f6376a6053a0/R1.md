# Technical Proposal for a Globally Distributed Live Audio Streaming and Chat Platform

## Executive Summary

This proposal recommends a **dual-plane architecture** for a browser- and mobile-accessible live audio platform supporting **100,000 concurrent listeners globally** and an **interactive-stream latency objective below two seconds**:

- A **real-time media plane** based primarily on **WebRTC + Opus**, using a globally distributed managed SFU for one-to-many audio fan-out. WebRTC is standardized for browser real-time communication, and Opus is explicitly designed for interactive speech and audio; its standardized operating range includes both speech and high-quality stereo music. [[1]](https://www.w3.org/TR/webrtc/)

- An independent **real-time application plane** for chat, presence, moderation, metadata, and synchronization, using authenticated **WebSockets** at the client edge and **gRPC/Protocol Buffers** between services. WebSocket provides persistent bidirectional messaging over a single connection, while gRPC's normal service model uses Protocol Buffers as the IDL and message format. [[2]](https://www.rfc-editor.org/info/rfc6455/)

- A **durable event and data plane** using PostgreSQL for relational control data, DynamoDB-style partitioned NoSQL storage for large chat histories, Redis/Valkey-class ephemeral storage for presence and rate limits, object storage for recordings and analytics, and NATS JetStream for low-latency durable messaging. JetStream adds persistence, replay, and at-least-once delivery to NATS's pub/sub model. [[3]](https://docs.nats.io/concepts/jetstream)

- A **secondary HTTP media path** using CMAF-packaged LL-HLS/HLS with AAC for graceful degradation, DVR, recording playback, and offline-capable VOD. Apple describes LL-HLS as retaining HTTP-streaming scalability while reducing latency, and Apple has described the low-latency extension as capable of roughly two seconds or less under suitable conditions. [[4]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls)

For the managed WebRTC edge, **Cloudflare Realtime SFU is the reference recommendation**, subject to contractual capacity and SLA validation before production commitment. Cloudflare documents an anycast architecture in which clients connect to their nearest location, tracks can be retrieved globally, and its SFU uses more than 250 network locations rather than customer-selected media regions. [[5]](https://developers.cloudflare.com/realtime/sfu/calls-vs-sfus/) Its current published SFU pricing is **$0.05/GB egress**, with ingress free and the first 1,000 GB included each month. [[6]](https://developers.cloudflare.com/realtime/sfu/pricing/) At the proposed 64-kbit/s Opus baseline and an engineering allowance of 15% for media/network overhead, that translates to approximately **$0.00166 per listener-hour**, or roughly **$119,000/month for 100,000 average—not merely peak—concurrent listeners running 24×7**. This is an order-of-magnitude model, not a vendor quote.

The important architectural decision is **not** to merge media and chat merely because WebRTC DataChannels can carry chat. Cloudflare's current SFU supports low-latency application data over DataChannels and explicitly lists chat as a use case, including reliable/ordered and partially reliable modes. [[7]](https://developers.cloudflare.com/realtime/sfu/datachannels/) Nevertheless, durable live chat needs server-authoritative ordering, history, moderation, replay after reconnect, rate limiting, and auditability. The proposed design therefore keeps **WebRTC for audio** and **WebSocket + durable messaging for chat**.

The recommended consistency model deliberately differs by subsystem. **Media is real-time and lossy; chat is strongly ordered per room/stream epoch; presence is eventually consistent; catalog/configuration is transactionally consistent; analytics is eventually consistent and at-least-once.** Trying to impose one global consistency model would increase latency, cost, and failure coupling without improving the user experience.

The system should be deployed across at least **three geographically separated application regions**, while leaving the WebRTC media fan-out on the global edge. Kubernetes Deployments and Horizontal Pod Autoscaling are appropriate for stateless APIs, WebSocket gateways, chat processors, and moderation workers; Kubernetes' HPA can dynamically adjust replicas for Deployments or StatefulSets using observed metrics. [[8]](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) Stateful databases should normally use managed services rather than be colocated with general application workloads.

**Recommended production targets** are:

| Dimension | Proposed target |
| --- | --- |
| Peak concurrent listeners | 100,000 |
| Media glass-to-glass latency | p95 < 800 ms, p99 < 1.8 s |
| Playback-session establishment | p95 < 1.5 s, p99 < 3 s |
| Chat client-to-client delivery | p95 < 500 ms, p99 < 1.5 s |
| Media join success SLO | ≥ 99.95% monthly |
| Established-session media availability | ≥ 99.99% monthly |
| Chat send/receive availability | ≥ 99.99% monthly |
| Catalog/API availability | ≥ 99.95% monthly |
| Presence freshness | normally < 10 s |
| Room-local chat ordering | Strict by room_seq within one stream epoch |
| Control-plane RPO | ≤ 1 minute for regional disaster |
| Chat-history RPO | ≤ 5 seconds for regional disaster |
| Regional control-plane RTO | ≤ 15 minutes |
| Security | TLS externally; mTLS/service identity internally; OIDC/OAuth 2.0; short-lived scoped media/chat credentials |
| Cost constraint | **None specified**; optimize unit economics and prevent unbounded fan-out charges |

The proposal prioritizes **operational simplicity over theoretical purity**: managed global media, conventional regional microservices, one durable messaging technology, explicit room ownership rather than multi-master chat sequencing, and server-authoritative timestamps.

## Goals and Nonfunctional Requirements

**Functional scope.** The platform must allow a host or production encoder to begin a live audio stream, globally distribute that stream to browsers and iOS/Android clients, let listeners enter and leave dynamically, expose live metadata, support synchronized chat and moderation, optionally record streams, and make past content available through normal HTTP adaptive streaming. The media architecture should also permit a future “listener goes on stage” capability without redesigning transport.

The primary interactive transport is WebRTC. W3C's current WebRTC Recommendation defines browser APIs for sending and receiving media and arbitrary application data, while the IETF's WebRTC architecture standardizes the accompanying real-time protocol suite. [[9]](https://www.w3.org/TR/webrtc/) For standards-oriented contribution ingest, expose **WHIP** at the platform boundary: RFC 9725 defines WHIP as a simple HTTP-based protocol for ingesting WebRTC content into streaming services or CDNs. [[10]](https://www.rfc-editor.org/info/rfc9725/)

**Latency objective.** “Sub-2s” should be interpreted as the **p99 steady-state glass-to-glass objective for interactive streams**, not merely a median measured from a nearby wired connection. The proposed operating goal is considerably tighter—p95 below 800 ms—so that temporary jitter-buffer growth, mobile-network variation, or a longer geographic path does not immediately break the contractual two-second boundary.

A useful engineering latency budget is:

| Stage | Normal engineering budget |
| --- | --- |
| Capture + audio preprocessing | 20–60 ms |
| Opus frame formation / encoding | 20–60 ms |
| Publisher → nearest media edge | 20–100 ms |
| Edge/backbone forwarding | 30–150 ms |
| Listener jitter buffer | 60–300 ms |
| Decode/audio-device scheduling | 10–50 ms |
| **Typical designed total** | **160–720 ms** |
| **p99 product objective** | **< 1.8 s** |

These numbers are **design budgets rather than vendor guarantees**. They leave a 200-ms error margin beneath the user's two-second requirement.

A pure HTTP-segmented solution is not recommended as the sole interactive transport. Apple describes LL-HLS as reducing live delay while retaining HLS scalability and has characterized its low-latency extensions as supporting delays around two seconds or less; this makes LL-HLS valuable as a fallback but leaves too little safety margin for a strict global sub-two-second SLO. [[4]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls) WebRTC therefore owns the interactive path, while HLS owns compatibility, DVR, replay, and downloadable media.

**Scalability.** The design target is 100,000 simultaneous listeners, but capacity planning should distinguish **global CCU**, **CCU in one stream**, and **connections at one regional WebSocket edge**. One 100,000-listener event is materially harder than 1,000 rooms containing 100 listeners because the former creates a concentrated chat and media fan-out hotspot. Cloudflare documents that its SFU architecture can support millions of connected WebRTC clients globally and that tracks are globally retrievable, but that statement should not be treated as a contractual promise that one published audio track may have 100,000 simultaneous subscribers. [[11]](https://developers.cloudflare.com/realtime/sfu/introduction/) **A vendor-certified 100k-subscriber single-track test is therefore a launch gate.**

For chat, design for at least:

- 100,000 active WebSocket connections associated with a single global event.

- 5,000 inbound chat submissions/second platform-wide during bursts.

- 100,000 outbound message deliveries for each message in an exceptionally large room.

- Backpressure rather than unlimited queue growth when clients cannot receive quickly.

Those are deliberately more aggressive than the baseline product requirement.

**Availability and graceful degradation.** Media, chat, presence, analytics, and catalog must not share a single failure domain. A failure of recommendations, presence, typing indicators, analytics, or ML moderation must not stop an already-authorized audio session. A chat outage must not terminate audio. A media-edge failure should cause media-session reconstruction without forcing the user to reauthenticate.

Availability classes should therefore be:

| Capability | Failure behavior |
| --- | --- |
| Audio playback | Highest priority; automatically reconnect/re-establish |
| Stream authorization | Required on join; cached short-lived grants may bridge brief control-plane failure |
| Chat | Retry/reconnect with sequence-gap recovery |
| Moderation bans/mutes | Fail closed for explicitly banned identities; configurable policy for unavailable ML classifier |
| Presence counts | May become stale or approximate |
| Metadata/catalog | Cache stale-safe immutable/read-mostly fields |
| Analytics | Buffer/retry asynchronously |
| Recordings | May lag live output; must not affect live media |

Cloudflare's current SFU documentation explicitly recommends reconnecting after connectivity loss and notes that sessions/tracks remain available for a short period before inactivity cleanup, reinforcing the need for client-side reconnection logic rather than treating PeerConnections as permanent. [[12]](https://developers.cloudflare.com/realtime/sfu/limits/)

**Consistency.** The platform does not need global serializability:

| Domain | Required consistency |
| --- | --- |
| Stream lifecycle/configuration | Strong transaction semantics in authoritative region |
| Entitlement / bans | Strong at authorization point |
| Chat inside a room | Total order within (stream_id, epoch) |
| Cross-room chat order | None |
| Presence | Eventual |
| Listener count | Approximate/eventual for public UI; accurate asynchronously for billing |
| Analytics | At-least-once, eventual |
| Recordings | Eventual |
| Global chat replica | Eventual; ordering retained from authoritative room sequence |

DynamoDB Global Tables illustrate why consistency should be chosen per workload rather than globally: current Global Tables can be configured for multi-Region eventual consistency or multi-Region strong consistency; the MREC mode replicates asynchronously, normally within about a second, and resolves concurrent same-item modifications with last-writer-wins behavior. [[13]](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html) That model is suitable for replicated immutable chat records after a room sequencer has assigned the authoritative sequence, but **not** for letting several regions independently generate the authoritative order for one room.

**Security objectives.** No provider secret may be exposed to a browser or application bundle. Cloudflare specifically warns that its Realtime application secret must be protected because arbitrary session/track management can otherwise be abused. [[14]](https://developers.cloudflare.com/realtime/sfu/https-api/) Public clients authenticate through an OpenID Connect identity provider using OAuth Authorization Code + PKCE; OIDC is the identity layer over OAuth 2.0, and the current OAuth security BCP requires PKCE for public clients. [[15]](https://openid.net/specs/openid-connect-core-1_0.html)

Security targets additionally include short credential lifetimes, audience-restricted authorization, server-side moderation enforcement, encryption at rest and in transit, per-user/IP/device/room rate limiting, immutable moderation audit trails, and systematic prevention of chat amplification attacks.

**Cost constraint.** There is **no strict budget**, as specified by the user. The optimization target is therefore not “minimum cost at all costs,” but predictable cost per listener-hour while avoiding architecture choices whose expense grows as messages × room_population.

## Proposed Architecture and Component Design

The architecture separates globally distributed media forwarding from application state.

| ![rId26](assets/6847465956a0f6376a6053a0/rId26.png) |
| --- |

Cloudflare Realtime is a particularly suitable reference implementation for the SFU box because it presents WebRTC sessions/tracks rather than imposing rooms, delegates presence and participant state to the application, and connects the user's PeerConnection to the nearest Cloudflare datacenter using anycast. [[16]](https://developers.cloudflare.com/realtime/sfu/calls-vs-sfus/) That precisely matches this proposal's separation of media forwarding from room state.

**Ingest.** There are three ingest modes:

| Ingest type | Transport | Primary use |
| --- | --- | --- |
| Browser/mobile host | WebRTC/Opus | Consumer-created live stream |
| Standards-based professional client | WHIP/WebRTC | Studio/encoder integration |
| Legacy production gateway | RTMPS/SRT → normalized ingest | Migration only |

WHIP is the standards-first public interface because RFC 9725 standardizes HTTP-based WebRTC contribution into streaming platforms. [[10]](https://www.rfc-editor.org/info/rfc9725/) The internal adapter can translate WHIP's signaling model to the selected SFU API if the provider does not expose WHIP natively.

The host does not receive a reusable media-provider secret. It requests an **ingest session** from the platform, receives a short-lived capability scoped to a single stream and epoch, and then publishes a track. The backend stores the returned provider session/track identifiers against the internal stream_epoch_id.

**Encoding and transcoding.** Opus should be preserved end-to-end whenever possible. RFC 6716 specifies Opus across 6–510 kbit/s and identifies useful operating regions including approximately 48–64 kbit/s for full-band mono music and 64–128 kbit/s for full-band stereo music. [[17]](https://www.rfc-editor.org/info/rfc6716/) Recommended service profiles are therefore:

| Profile | Proposed Opus payload | Use |
| --- | --- | --- |
| Speech-low | 24–32 kbit/s mono | Weak/mobile connection |
| Speech-standard | 48 kbit/s mono | Talk radio, podcasts, spaces |
| Music-standard | 64–96 kbit/s stereo or high-quality mono | General music |
| Music-high | 128 kbit/s stereo | Premium/high-fidelity live |

The defaults above are product choices, not codec limits.

For the majority of rooms, publish one normal Opus rendition and let WebRTC's normal transport adaptation handle short-term network variation. For very large events, the central audio processor may produce **two Opus tracks**, e.g. 24/32 and 64 kbit/s, allowing the listener to resubscribe to a lower rendition when sustained packet loss or throughput warrants it. This avoids per-listener server-side transcoding.

The same normalized audio is asynchronously encoded as AAC-LC and packaged into CMAF/fMP4 for LL-HLS/HLS. HLS is formally documented by RFC 8216 as a protocol for unbounded multimedia streams, while current Apple LL-HLS adds mechanisms intended to reduce latency without abandoning HTTP/CDN delivery. [[18]](https://www.rfc-editor.org/info/rfc8216/)

**Media SFU and edge delivery.** Each listener establishes a PeerConnection to the global SFU and subscribes to the current track for stream_epoch_id. Cloudflare's model maps one Session to one WebRTC PeerConnection, supports globally available track identifiers, and routes clients to nearby network locations. [[19]](https://developers.cloudflare.com/realtime/sfu/sessions-tracks/)

The application—not the SFU—is authoritative for this mapping:

stream_id
  -> stream_epoch
  -> publisher_session_id
  -> primary_audio_track_id
  -> low_bandwidth_audio_track_id?
  -> fallback_hls_manifest

This abstraction is important for portability: clients request a logical playback session from **our** API, not a permanent provider-specific track.

**HTTP CDN path.** The fallback media path packages content once and distributes immutable segments through an ordinary HTTP CDN. CloudFront, for example, officially supports live/VOD HLS, DASH and CMAF packaging formats and caches media fragments at the edge. [[20]](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/on-demand-streaming-video.html) Akamai Adaptive Media Delivery likewise targets prepared adaptive-bitrate live/VOD media and offers explicit low-latency support for DASH and LL-HLS workflows. [[21]](https://techdocs.akamai.com/adaptive-media-delivery/docs/welcome-adaptive-media-deliv)

The HTTP path serves four purposes:

- Graceful playback fallback when UDP/WebRTC connectivity is persistently bad.

- DVR and pause/seek support.

- Recorded-stream playback.

- Offline downloads for authorized VOD content.

It is **not** part of the primary interactive latency SLO.

**Storage.** Object storage contains immutable recordings, CMAF chunks/manifests, moderation exports, and analytics batches. PostgreSQL contains small-to-medium relational control state. NoSQL contains high-volume chronological chat history. Redis/Valkey-class storage contains disposable presence and rate-limit state.

**Metadata and catalog.** A stateless Catalog Service owns channel descriptions, stream titles, artwork references, scheduling, visibility, language, tags, entitlement rules, and stream lifecycle. PostgreSQL is authoritative. Public catalog results may be CDN/Redis cached; stream lifecycle transitions use optimistic concurrency/version numbers.

Suggested stream state machine:

| ![rId34](assets/6847465956a0f6376a6053a0/rId34.png) |
| --- |

Every transition increments stream_version, and every new live-media incarnation increments stream_epoch. An old publisher cannot accidentally overwrite the new one because media and chat commands contain the epoch.

**Authentication and authorization.** An external or managed OIDC provider handles login. OIDC explicitly layers identity over OAuth 2.0. [[22]](https://openid.net/specs/openid-connect-core-1_0.html) Public browser/native clients use Authorization Code + PKCE in accordance with the current OAuth security BCP. [[23]](https://www.rfc-editor.org/info/rfc9700/)

Three token classes should exist:

| Credential | Lifetime | Scope |
| --- | --- | --- |
| User access token | 5–10 min | API audience and user capabilities |
| Playback/ingest capability | 1–2 min to initiate | One stream + one operation |
| WebSocket ticket | ~30 s, single-use | One user/session/stream |

The browser should preferably use a BFF/secure HTTP-only session cookie for the main authenticated web application; native clients can maintain OAuth tokens in platform-secure storage. The WebSocket handshake first obtains a single-use opaque ticket through authenticated REST, avoiding long-lived bearer tokens embedded in a WebSocket URL.

**Presence.** Presence must not imply that every room maintains an exact globally transactional set of users. Each connected client sends a heartbeat every approximately 10 seconds. A regional presence record expires after roughly 30 seconds. Public listener counts are aggregated and smoothed. An exact member list is generated only for smaller rooms or privileged moderation tools.

At very large scale, exposing an exact 100,000-member presence roster is both unnecessary and expensive. The normal public representation is {listener_count, speakers[], friends_present?}.

**Chat.** The chat path is server authoritative:

| ![rId38](assets/6847465956a0f6376a6053a0/rId38.png) |
| --- |

One **room-home region** owns sequencing for one (stream_id, epoch). A lease with a monotonically increasing room_owner_epoch prevents two regions from being authoritative simultaneously. All ingress gateways may be local to users, but messages are routed to that room's sequencer before acceptance.

This architecture trades perhaps tens to a few hundred milliseconds of additional inter-region chat latency for deterministic ordering and much simpler failure semantics. The media path remains direct to the nearest SFU edge.

NATS JetStream is a good event substrate here because Core NATS provides ephemeral publish/subscribe while JetStream adds persistence, consumer state, acknowledgements, at-least-once delivery, and replay. [[24]](https://docs.nats.io/concepts/jetstream) Consumers must still be idempotent because at-least-once systems can redeliver.

**Moderation.** Moderation is a pipeline, not a single model:

authentication → account sanctions → rate/slow mode → syntax/size → deterministic policy → optional ML classifier → room policy → publish.

High-confidence bans and mutes are synchronous. Computationally expensive models can be asynchronous for low-risk traffic or synchronous only for newly created/high-risk accounts. Every decision emits an append-only audit event including policy/version identifiers.

Deletion is itself an ordered room event:

{
  "type": "chat.deleted",
  "stream_id": "str_8de1",
  "epoch": 42,
  "room_seq": 981233,
  "target_message_id": "msg_01K...",
  "reason_code": "HARASSMENT",
  "moderator_actor": "system",
  "server_ts": "2026-08-19T20:15:24.201Z"
}

Clients never infer deletion solely from a missing message.

**Analytics.** Events such as stream_started, playback_joined, first_audio, rebuffer, track_switched, playback_left, chat_sent, and moderation_action flow asynchronously to object storage and a warehouse. WebRTC's statistics API exposes PeerConnection-level statistics through getStats, making client-measured transport telemetry available for QoE analysis. [[25]](https://www.w3.org/TR/webrtc-stats/)

Sample only what is necessary: a 100,000-listener event can create enormous telemetry cardinality if metrics include raw user, connection, or stream identifiers as Prometheus labels.

**Monitoring.** Services emit traces, metrics and structured logs through OpenTelemetry; current OpenTelemetry specifications provide correlated telemetry models for traces, metrics and logs. [[26]](https://opentelemetry.io/docs/concepts/signals/) Prometheus-compatible SLO metrics drive alerts; Prometheus officially supports alert rules, with Alertmanager handling grouping, silencing, inhibition and notification routing. [[27]](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)

## Protocols, APIs, Data Models, and Synchronization

### Technology comparisons embedded in the protocol decision

| Transport | Typical role | Strengths for this system | Weaknesses | Decision |
| --- | --- | --- | --- | --- |
| **WebRTC** | Interactive live media | Browser real-time APIs; low-latency RTP media; NAT traversal ecosystem; Opus-native | Stateful PeerConnection; SFU/signaling complexity; harder CDN caching | **Primary live audio**. W3C standardizes the browser API. [[28]](https://www.w3.org/TR/webrtc/) |
| **LL-HLS** | Low-latency HTTP media | Standard HTTP/CDN path; DVR; Apple ecosystem | Segment/part latency leaves less margin for strict global <2 s; not conversational transport | **Fallback + DVR**. Apple documents low-latency extensions. [[4]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls) |
| **HLS** | Conventional live/VOD | Ubiquitous HTTP/CDN delivery model; straightforward recording/offline | Higher live latency | **VOD/offline/fallback**. RFC 8216 defines HLS. [[29]](https://www.rfc-editor.org/info/rfc8216/) |
| **DASH / LL-DASH** | Adaptive HTTP streaming | Open ISO ecosystem; common on non-Apple platforms | Additional manifest/player surface; unnecessary for initial browser/mobile scope | **Optional**. IETF operational guidance recognizes low-latency HLS and DASH approaches. [[30]](https://www.rfc-editor.org/info/rfc9317/) |
| **WebSocket** | Chat/presence/control | Persistent bidirectional application messaging, native browser support | TCP head-of-line effects; application must define semantics | **Primary client realtime application transport**. [[31]](https://www.rfc-editor.org/info/rfc6455/) |
| **WebRTC DataChannel** | Ephemeral low-latency data | Shared real-time path; selectable reliability | Poor fit for authoritative durable chat/history/moderation | **Control/special features only**; current Cloudflare implementation supports reliable or partial-reliability modes. [[7]](https://developers.cloudflare.com/realtime/sfu/datachannels/) |
| **gRPC** | Service-to-service RPC | Typed contracts; code generation; unary/streaming APIs | Not ideal as primary browser-facing protocol | **Internal service RPC**. [[32]](https://grpc.io/docs/what-is-grpc/introduction/) |

WebSocket remains RFC 6455-compatible as the baseline. HTTP/2 can bootstrap WebSocket via RFC 8441 where infrastructure supports it, but the product contract should not depend on that optimization. [[33]](https://www.rfc-editor.org/info/rfc8441/)

**Codec comparison.**

| Codec | Interactive audio | HLS fallback | Speech efficiency | Music | Recommendation |
| --- | --- | --- | --- | --- | --- |
| **Opus** | Excellent | Support varies by packaging/client | Excellent | Excellent | **WebRTC primary**. RFC 6716 spans speech through high-quality stereo. [[17]](https://www.rfc-editor.org/info/rfc6716/) |
| **AAC-LC** | Possible but not preferred for WebRTC architecture | Excellent practical native-HLS choice | Good | Excellent | **HLS/CMAF fallback and VOD** |
| **G.711** | Very interoperable real-time voice | Poor streaming efficiency | Acceptable narrowband voice | Poor | Emergency interoperability only |
| **MP3** | Widely decodable | Legacy-friendly | Inefficient relative to modern codecs | Acceptable | VOD/legacy only |

For an audio-only product, codec simplicity is more valuable than a large video-style bitrate ladder. **Opus 48–64 kbit/s should be the normal speech/general-audio target**, consistent with standardized Opus operating ranges, with an optional low rendition and higher music profile. [[17]](https://www.rfc-editor.org/info/rfc6716/)

**Messaging-system comparison.**

| System | Delivery/persistence model | Ordering | Operational character | Fit |
| --- | --- | --- | --- | --- |
| **NATS Core + JetStream** | Core ephemeral; JetStream persistent/replayable, at-least-once | Ordered stream/subject processing under controlled topology | Compact system serving both regional fanout and durable events | **Recommended** for chat/event plane. [[24]](https://docs.nats.io/concepts/jetstream) |
| **Apache Kafka** | Durable distributed log | Kafka guarantees order within a topic-partition | Excellent high-throughput event backbone; heavier for request/fanout-oriented realtime | Preferred if the company already operates Kafka. [[34]](https://kafka.apache.org/documentation/) |
| Managed cloud queue/pub-sub | Provider-specific | Depends on service/key topology | Minimal infrastructure operations | Viable, but multiple services are often required to reproduce durable log + realtime fanout |
| Direct WebSocket gateway memory | No durable substrate | Per-process only | Very simple | Insufficient alone; loses recovery/audit |

Kafka deserves particular consideration in an existing Kafka organization: its documented semantic partitioning can preserve order within a partition while balancing work across partitions. [[35]](https://kafka.apache.org/43/design/protocol/) A room_id partition key is therefore natural. For a medium-sized company starting greenfield, NATS reduces the number of distinct messaging abstractions because its Core and JetStream modes cover both ephemeral fanout and durable replay.

**Database comparison.**

| Store | Best use | Global consistency characteristic | Decision |
| --- | --- | --- | --- |
| **Managed PostgreSQL** | Streams, channels, policies, entitlements, configuration, transactions | Single logical authority with replicas/failover | **System of record for control plane** |
| **DynamoDB Global Tables / equivalent wide KV** | Chat history, idempotency keys, large chronological records | Can use multi-region eventual or strong modes; MREC normally replicates asynchronously | **Chat/history store**. [[36]](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html) |
| **Redis/Valkey-class cache** | Presence TTLs, ephemeral counters, token buckets | Deliberately non-authoritative | **Presence and rate limits** |
| **Object storage** | Recordings, segments, analytics parquet, exports | Immutable/eventually catalogued | **Bulk durable storage** |

DynamoDB MREC is preferred over MRSC for chat history because the room sequencer has already established canonical ordering. Cross-region synchronous consensus on every chat-history write would add latency without improving the user-visible order. Current DynamoDB documentation notes that MREC writes replicate asynchronously and that MRSC synchronously replicates before acknowledging writes. [[37]](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html)

### Audio/chat synchronization

Synchronization is based on a **server-owned stream timeline**, not the sender's local wall clock.

When an epoch starts, the media coordinator creates:

stream_epoch
stream_epoch_start_server_time
media_timeline_origin

Periodic sync.anchor messages bind authoritative stream_time_ms to server UTC. Every accepted chat message receives its stream_time_ms from the room sequencer using the same epoch timeline.

The client maintains:

estimated_audio_playout_stream_time
estimated_server_clock_offset
last_anchor

It displays a synchronized chat message when:

message.stream_time_ms
    <= estimated_audio_playout_stream_time + presentation_tolerance_ms

A reasonable initial presentation_tolerance_ms is 50–150 ms.

This solves an otherwise subtle problem: the listener may be 250 ms behind live because of WebRTC jitter buffering while the chat WebSocket is only 80 ms behind. Without synchronization, listeners see reactions before hearing the event that caused them.

After reconnect, the client asks for chat history from its last room_seq, deduplicates by message_id, then schedules backfilled events against stream time.

For the HLS fallback path, segment timestamps and HLS timeline metadata can provide a more explicit media presentation timeline. The HLS specification defines ordered playlist/media semantics for unbounded multimedia streams. [[29]](https://www.rfc-editor.org/info/rfc8216/)

A user-selectable “live chat” mode may intentionally show chat immediately rather than synchronized to delayed playback, but the UI must label that state because spoilers are otherwise inevitable during DVR playback.

## Clients, Scalability, Reliability, Security, and Operations

**Web client.** The browser implementation should use native RTCPeerConnection for WebRTC and a thin internal AudioStreamingSDK wrapping:

authorize()
join(streamId)
leave()
onMetadata()
onAudioQuality()
switchRendition()
getPlaybackClock()
reconnect()

WebRTC is a browser-standard API surface specifically for real-time media and generic data. [[28]](https://www.w3.org/TR/webrtc/) The SDK should isolate provider signaling so that replacing the SFU does not rewrite product UI.

Fallback playback uses native HLS where available or an MSE-based player where required. The current W3C Media Source Extensions specification allows JavaScript to append media segments to an HTMLMediaElement and dynamically adjust appended media based on system conditions, which is the core browser mechanism behind adaptive HTTP players. [[40]](https://www.w3.org/TR/media-source-2/)

**iOS.** Use a native WebRTC library for interactive live audio and AVFoundation/AVPlayer for HLS/VOD fallback. Apple explicitly documents using AVFoundation to play and persist HLS streams for offline playback. [[41]](https://developer.apple.com/documentation/avfoundation/using-avfoundation-to-play-and-persist-http-live-streams) The app should integrate normal iOS background-audio controls, interruption handling, route changes, Bluetooth devices, and lock-screen transport controls.

**Android.** Use native WebRTC for interactive playback and Jetpack Media3/ExoPlayer for HLS/VOD. Google's Media3 documentation supports downloading adaptive streams, including HLS and DASH, for offline use. [[42]](https://developer.android.com/media/media3/exoplayer/downloading-media)

**Offline behavior.** There is no meaningful “offline live stream.” On network loss:

- Continue playing any already buffered audio.

- Transition UI to reconnecting.

- Do **not** queue ordinary chat sends for later publication; a chat message sent minutes late is usually semantically wrong.

- Persist only harmless local UI state.

- Reauthorize and reconstruct media/WS sessions after connectivity returns.

- Fill chat gaps by room_seq.

- Allow explicit VOD downloads independently.

Apple and Android both provide platform-level facilities for persistent/offline HLS-style media, making downloaded VOD a native-client feature rather than a custom chunk-cache protocol. [[43]](https://developer.apple.com/documentation/avfoundation/using-avfoundation-to-play-and-persist-http-live-streams)

**Adaptive audio and buffering.** WebRTC clients initially subscribe to the standard track. The SDK periodically inspects transport statistics and switches to a lower rendition only after sustained impairment; the W3C WebRTC statistics model exposes RTCPeerConnection statistics for such monitoring. [[25]](https://www.w3.org/TR/webrtc-stats/)

Suggested policy:

Initial jitter target:             ~150 ms
Healthy range:                     100–250 ms
Temporary impaired range:          up to ~750 ms
Downshift trigger:                 sustained loss/jitter/throughput problem
Upshift hysteresis:                15–30 s stable health
Hard WebRTC fallback evaluation:   repeated reconnect/failure over ~10 s

These values are tuning starting points and should be calibrated with production QoE data rather than treated as protocol constants.

Application services run in three Kubernetes regions. Stateless components use Deployments; Kubernetes HPA can automatically adjust replica counts for workloads according to observed resource/custom metrics. Autoscaling signals should include:

| Workload | Scale on |
| --- | --- |
| REST gateways | request rate, p95 latency, CPU |
| WebSocket gateways | active sockets, outbound bytes/s, event-loop/run-queue lag |
| Chat sequencers | active rooms, submissions/s |
| Fanout workers | deliveries/s, NATS consumer lag |
| Moderation workers | queue age + inference latency |
| Encoding workers | active encoders + real-time factor |
| Analytics workers | backlog age |

CPU alone is an inadequate WebSocket scaling metric: a pod can hit file descriptor, memory, kernel-buffer, or outbound-bandwidth limits before CPU reaches a conventional HPA threshold.

**Stateful versus stateless.** APIs, session brokers, WS gateways and fanout processors are stateless from a failover perspective. Connection state resides transiently in a gateway but is reconstructible. PostgreSQL, chat history, object storage and durable messaging are stateful. Prefer managed databases. If NATS JetStream is self-operated, isolate its StatefulSets and disks from normal application node pools; Kubernetes specifically provides StatefulSets for workloads requiring stable state/identity. [[45]](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)

**Serverless use.** Serverless functions are suitable for webhook processing, recording-completion jobs, moderation enrichment, thumbnail/waveform jobs, and asynchronous analytics transforms. They are deliberately **not** on the core WebRTC or long-lived WebSocket path, where persistent connections and predictable latency make ordinary services preferable.

### Fault tolerance

**Media.** A failed PeerConnection creates a new media session. The logical playback session persists while the provider-specific connection changes. During a major stream, a warm standby ingest processor may retain the source so it can republish a new track quickly.

**Chat.** Delivery is at least once internally; message_id and client_message_id provide deduplication. JetStream documents acknowledgement-based redelivery and at-least-once semantics, so consumers must be explicitly idempotent. [[3]](https://docs.nats.io/concepts/jetstream)

Room ownership uses a fencing token:

room_id
owner_region
owner_instance
owner_epoch
lease_expires_at

A failover instance must obtain owner_epoch=N+1. Events carrying N are rejected after failover. This prevents split-brain sequencing.

**Regional loss.** New sockets route elsewhere. Existing users reconnect. Room leases are reacquired in another region. Replicated chat data may lag by a few seconds but carries permanent room sequences, so delayed records do not reorder the history.

DynamoDB's multi-region eventual mode explicitly makes this trade-off—local regional operation plus asynchronous replication—while MRSC offers a different synchronous consistency model. [[13]](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html) This proposal uses application-level single-writer room authority with asynchronous history replication rather than global synchronous chat writes.

**Backpressure.** Slow listener sockets must never block room progression. Each connection gets a bounded outbound queue. Under pressure, discard in this order:

typing/presence deltas → nonessential reactions → redundant metadata → disconnect slow consumer.

Do not silently drop accepted ordinary chat. If a client is too slow, disconnect it and make it recover by sequence from history.

### Security and abuse prevention

**Authentication.** OIDC supplies identity, with Authorization Code + PKCE for public applications in line with the latest OAuth security guidance. [[46]](https://www.rfc-editor.org/info/rfc9700/)

**Authorization.** Services distinguish:

stream:read
stream:publish
stream:moderate
chat:read
chat:write
recording:read
admin:...

A playback capability carries only stream:read for one stream/epoch. The browser never receives an account-wide SFU secret. This is particularly important with provider APIs that can create, modify, or close media tracks. [[14]](https://developers.cloudflare.com/realtime/sfu/https-api/)

**Transport encryption.** REST/WebSocket endpoints use TLS. Internal gRPC uses mTLS or equivalent workload identity. WebRTC uses its standardized encrypted real-time transport stack; the SFU/TURN path should never downgrade media to plaintext. Cloudflare's TURN documentation, for example, notes that WebRTC-level encryption remains in effect across TURN relaying. [[47]](https://developers.cloudflare.com/realtime/turn/faq/)

**HTTP media authorization.** Paid/private recordings use short-lived signed manifests/cookies rather than exposing permanent object-storage locations. CloudFront's documentation specifically recommends signed cookies for HLS/DASH situations where a client must authenticate many manifest and segment requests. [[48]](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/signed-cookies-PHP.html)

**Rate limiting.** Apply independent token buckets:

account login attempts
playback session creation / IP
publisher session creation / account
WebSocket connection attempts / IP + account
chat submissions / user
chat submissions / device
chat submissions / IP
chat submissions / room
moderation API / moderator

Room-level rate limiting is critical: 100 compromised users acting separately can otherwise remain below their individual quotas while collectively flooding a 100,000-listener room.

**Amplification defense.** Fanout cost is proportional to accepted message count × recipients. Therefore rate limiting happens **before** the message enters the durable/fanout pipeline.

**Moderation and account abuse.** Maintain:

- permanent and timed account bans;

- per-room mute/ban;

- slow mode;

- link/domain restrictions;

- spam similarity detection;

- new-account velocity rules;

- moderator deletion;

- optional shadow mode for bot containment;

- immutable audit events.

High-risk text classifiers should be versioned so later appeals can identify exactly which policy/model produced a decision.

**Data protection.** Do not put email addresses, phone numbers, access tokens, raw IP addresses, or message text into metric labels. Separate security audit storage from general application logs. Apply retention schedules to chat, presence, analytics, and recordings independently.

OpenTelemetry provides a vendor-neutral way to collect correlated traces, metrics, and logs, while Prometheus alert rules and Alertmanager provide standard rule evaluation and alert routing/grouping. [[49]](https://opentelemetry.io/docs/)

Can users send/receive chat?
Is room sequencing healthy?
Are event consumers falling behind?
Are moderation and authorization functioning?
Is a vendor dependency failing?

**Media incident runbook**

- Compare join failures against already-established sessions.

- Segment by region, ASN, transport candidate type, client release and media provider edge.

- Verify SFU session creation and track discovery separately.

- Reissue playback sessions/new tracks if signaling is impaired.

- Increase reconnect backoff to avoid a thundering herd.

- Enable HLS fallback if WebRTC remains impaired.

- Freeze unrelated deploys.

**Chat incident runbook**

- Determine whether failure is ingress, sequencer, durable publish, fanout, or socket delivery.

- If presence fails, disable presence—not chat.

- If asynchronous moderation is failing, apply predefined degraded moderation policy.

- If room owner fails, fence old owner and advance owner_epoch.

- If history persistence is lagging but JetStream is healthy, continue serving live messages.

- If fanout cannot keep up, shed nonessential realtime events before accepted chat.

**Regional-loss runbook**

- Global router removes unhealthy region.

- Clients reconnect to alternate gateway.

- Room lease recovery advances ownership epochs.

- Control-plane writes shift to designated failover.

- Chat history catches up from durable stream/global table.

- After stability, restore region as a follower before moving room ownership back.

## Testing, Cost Model, and Rollout

### Testing strategy

**Unit and property testing.** Test state machines, room sequencing, idempotency, token scopes, rate limiters, moderation transformations, synchronization arithmetic, and codec-profile selection. Property tests should verify invariants such as:

room_seq strictly increases within an epoch
message_id is never reused
old owner_epoch cannot write after fencing
old stream_epoch cannot publish after restart
duplicate JetStream delivery produces one visible chat item
deletion never precedes its target in reconstructed history

**Contract testing.** Validate OpenAPI and Protobuf backward compatibility in CI. An old client must safely ignore unknown fields/message types. A server must not repurpose existing enum values.

**Media integration testing.** Automated publisher/listener agents should join through actual WebRTC, play deterministic audio, measure first-audio latency, verify packet continuity, and compare captured timestamps. Run probes continuously from North America, Europe, South America, Asia-Pacific, and at least one mobile-network environment.

WebRTC statistics are programmatically accessible through the standardized getStats model, making packet loss, RTT and related measurements suitable for automated QoE probes. [[25]](https://www.w3.org/TR/webrtc-stats/)

**Network impairment testing.** Inject:

50–500 ms RTT
1–15% packet loss
packet reordering
short outages
bandwidth step-down/up
Wi-Fi ↔ cellular transition
NAT rebinding
UDP blocked / relay-required networks

The acceptance test is user-observable behavior, not simply “PeerConnection stayed connected.”

**Scale testing.** The release gate includes:

- 100,000 concurrent WebRTC listener sessions;

- 100,000 WebSocket connections;

- one 100,000-listener room;

- thousands of simultaneous stream starts;

- reconnect storm of 20–30% of peak population;

- chat burst load with 100k-recipient fanout;

- delayed consumers and slow sockets;

- regional failure during the load test.

Cloudflare's architecture documentation describes globally available tracks and very large aggregate WebRTC capacity, but the single-track 100k test is still required because aggregate vendor architecture is not a per-customer/per-track capacity guarantee. [[11]](https://developers.cloudflare.com/realtime/sfu/introduction/)

**Chaos testing.** Kill WebSocket pods, room sequencers, event consumers and a full Kubernetes availability zone. Simulate database read-only conditions, NATS leader transitions, DNS failure, IdP latency, SFU signaling errors, and object-storage throttling. Expected degraded modes are documented before the exercise.

**Security testing.** CI includes dependency and image scanning, secret detection, SAST, API schema fuzzing, WebSocket payload fuzzing, authorization matrix tests, replay tests, token-expiration tests and rate-limit bypass tests. Regular external penetration testing should explicitly target stream theft, unauthorized track manipulation, moderator privilege escalation, token leakage and fanout-amplification abuse.

### Cost model

The dominant variable cost is media egress.

Cloudflare currently prices Realtime SFU/TURN at **$0.05 per GB of egress**, charges no SFU ingress, and includes the first 1,000 GB monthly. [[6]](https://developers.cloudflare.com/realtime/sfu/pricing/)

For an approximate 64-kbit/s Opus stream with an **engineering assumption of 15% protocol/transport overhead**:

payload bitrate      = 64.0 kbit/s
modeled wire bitrate = 64 × 1.15
                     = 73.6 kbit/s

GB / listener-hour
  = 73,600 bit/s × 3,600 / 8 / 1e9
  = 0.03312 GB

media cost / listener-hour
  = 0.03312 × $0.05
  = $0.001656

At 720 hours/month:

| Average CCU | Listener-hours/month | Approx. SFU egress cost at 64 kbit/s + 15% overhead |
| --- | --- | --- |
| 10,000 | 7.2 M | ~$11,900 |
| 25,000 | 18 M | ~$29,800 |
| 50,000 | 36 M | ~$59,600 |
| 100,000 | 72 M | **~$119,200** |

The 1,000-GB included allowance changes these high-scale figures by only about $50/month.

For a 96-kbit/s stream with the same 15% overhead assumption:

wire bitrate = 110.4 kbit/s
GB/hour      = 0.04968
cost/hour    = $0.002484/listener

At 100,000 **average** CCU, that is approximately **$178,800/month**.

These values highlight why “peak CCU” and “average CCU” must not be conflated. A service peaking at 100k but averaging 25k costs roughly one quarter as much for a bandwidth-priced SFU.

As a managed-service comparison, AWS's current IVS page advertises Real-Time Streaming latency that can be below 300 ms; its published US audio-only example prices 1,008 participant-hours at $0.0072 per participant-hour. [[50]](https://aws.amazon.com/ivs/features/) At that example rate, 72 million participant-hours would be about **$518,000/month before applicable volume tiers or enterprise negotiation**, illustrating that provider charging models can differ substantially.

AWS IVS also publishes a 25,000-viewer figure for its Real-Time Streaming mode in its feature comparison, so a 100,000-listener single event would require explicit architecture/quota validation or audience sharding. [[51]](https://aws.amazon.com/ivs/features/)

Managed chat whose pricing is directly proportional to **every delivered message** deserves special scrutiny. ### Migration and rollout

Assuming an existing conventional HTTP audio platform, rollout should not be a flag-day replacement.

| ![rId81](assets/6847465956a0f6376a6053a0/rId81.png) |
| --- |

Dates are illustrative planning dates, not estimates of team velocity.

**Foundation phase:** introduce the new stream IDs, epochs, catalog schema and authorization APIs while the old media path continues serving production.

**Shadow phase:** connect the new ingest processor and generate WebRTC media in parallel, but keep users on the old player. Synthetic listeners continuously validate the shadow media.

**Internal/canary phase:** employees and opt-in users use WebRTC while normal traffic remains on HLS. Compare join success, startup time, dropouts, client battery/network usage and support incidents.

**Percentage rollout:** enable by stable user hash, starting around 1%, then 5%, 25%, 50%, and 100%, with automatic HLS fallback.

**Mobile rollout:** keep remote kill switches because App Store releases cannot be rolled back as quickly as web deployments.

**Chat migration:** during transition, either designate one service as authoritative or bridge old chat into the new ordered event stream. Never run two independent writable chat authorities and attempt to merge their sequence histories afterward.

**Completion gate:** only retire the old media path after at least one full high-concurrency event, regional-failure exercise, WebRTC-provider capacity certification, and sustained SLO compliance. Retain HLS permanently as fallback/VOD rather than removing it.

## Alternatives, Trade-offs, and Recommended Stack

### CDN and media-edge alternatives

| Option | Interactive latency | Scale model | HTTP VOD/live | Operational burden | Assessment |
| --- | --- | --- | --- | --- | --- |
| **Cloudflare Realtime SFU** | WebRTC real-time | Globally distributed anycast SFU; tracks globally retrievable | Separate HTTP CDN/Stream path required | Low media-server ops; application owns room state | **Recommended primary media edge**, pending contractual single-track 100k validation. Cloudflare documents 250+ locations and nearest-edge PeerConnections. [[5]](https://developers.cloudflare.com/realtime/sfu/calls-vs-sfus/) |
| **AWS IVS Real-Time** | Published as potentially <300 ms | Managed stages; published feature table shows up to 25k viewers | IVS low-latency/HLS ecosystem | Very low | Excellent managed alternative, but 100k single-room scale and cost require sharding/contract validation. [[50]](https://aws.amazon.com/ivs/features/) |
| **AWS CloudFront** | HTTP segmented, not WebRTC SFU | CDN cache fanout | HLS/DASH/CMAF live and VOD | Low | **Good fallback/VOD CDN**, not interactive media plane. [[53]](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/on-demand-streaming-video.html) |
| **Akamai Adaptive Media Delivery** | Low-latency HTTP options | Large CDN distribution | HLS/DASH/CMAF workflows | Low–medium | Strong HTTP-media alternative, particularly for existing Akamai customers. [[54]](https://techdocs.akamai.com/adaptive-media-delivery/docs/add-low-latency-support) |
| **Self-hosted SFU** | Potentially excellent | Company designs regional mesh/fanout | Company builds separately | **High** | Best control/portability, but disproportionate global media-operations burden for a medium-sized company |

The major trade-off in selecting a managed global SFU is **provider dependence versus operating complexity**. Self-hosting eliminates a vendor-specific signaling/control API but transfers worldwide UDP routing, capacity planning, TURN/SFU upgrades, DDoS handling, regional capacity and incident response to the engineering team. At this company size, managed media is the better default.

To contain lock-in:

Client
  -> Company MediaSession API
       -> MediaEdgeProvider interface
            -> Cloudflare adapter
            -> future AWS/self-host adapter

Persist logical stream IDs and epochs, never provider IDs as externally visible primary identifiers.

### Why not LL-HLS alone?

LL-HLS has the crucial advantage that it retains ordinary HTTP/CDN scaling, and Apple's published material describes around-two-second operation. [[4]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls) That would be compelling for a noninteractive broadcast product.

It is nevertheless the wrong sole transport here. A **sub-two-second global requirement means a technology capable of two seconds under favorable conditions leaves essentially no error budget** for mobile RTT, client buffering, origin problems or CDN path variation. WebRTC provides more latency margin and naturally accommodates a future bidirectional “listener on stage” feature.

Therefore:

WebRTC = interaction; LL-HLS/HLS = scale-compatible fallback, DVR and persistence.

### Why not carry authoritative chat over WebRTC DataChannels?

Current Cloudflare Realtime DataChannels explicitly support low-latency application payloads including chat and configurable ordering/reliability. [[7]](https://developers.cloudflare.com/realtime/sfu/datachannels/) This would reduce transport count.

It would also couple chat lifetime to media-session lifetime and force the application to rebuild durable history, moderation sequencing and reconnect replay around a media-oriented delivery channel. A persistent WebSocket chat connection is easier to inspect, moderate, rate-limit, route independently, and recover from by sequence number.

DataChannels remain useful for **ephemeral synchronized control**, such as:

speaker hand-raise hints
real-time reactions where loss is acceptable
transient UI state
producer controls
latency-sensitive collaborative features

They are not the system of record.

### Why NATS over Kafka?

Kafka has an exceptionally strong model for durable partitioned logs and explicitly guarantees topic-partition ordering. [[34]](https://kafka.apache.org/documentation/) Choose Kafka instead when the company already has Kafka expertise, a mature managed Kafka environment, or a large stream-processing ecosystem.

For a greenfield medium-sized company, NATS provides a more compact combination: Core NATS handles realtime pub/sub, while JetStream adds durable streams, acknowledgements, replay and at-least-once behavior. [[24]](https://docs.nats.io/concepts/jetstream) That allows the same operational platform to serve regional chat fanout and durable chat/system events.

The trade-off is that Kafka has the deeper ecosystem for large analytical event pipelines. This proposal avoids forcing transactional chat through an analytics-first architecture; analytics is downstream from the realtime event plane.

### Why hybrid PostgreSQL + NoSQL?

A PostgreSQL-only implementation is attractive initially and would simplify transactions. At 100k listeners, however, chat history has a very different access pattern from channels, entitlements, policy and stream configuration: it is append-heavy, TTL-heavy, partitionable by room/time, and globally replicated for local reads.

The hybrid design puts relational invariants in PostgreSQL and chronological chat in a horizontally partitioned store. DynamoDB Global Tables provide explicit multi-region eventual and multi-region strong consistency modes, making those replication trade-offs operationally visible. [[36]](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html)

The cost is an additional database abstraction. The benefit is that neither workload forces the other into an unnatural schema or scaling model.

### Recommended final stack

| Layer | Recommendation | Rationale |
| --- | --- | --- |
| **Interactive media transport** | **WebRTC** | Required latency margin and future bidirectional interaction; standardized browser API. [[28]](https://www.w3.org/TR/webrtc/) |
| **Audio codec** | **Opus** | Purpose-built for interactive speech/audio with broad operating range. [[17]](https://www.rfc-editor.org/info/rfc6716/) |
| **Professional ingest interface** | **WHIP / RFC 9725** | Standards-track HTTP/WebRTC ingest boundary. [[10]](https://www.rfc-editor.org/info/rfc9725/) |
| **Managed media edge** | **Cloudflare Realtime SFU**, contractual validation required | Global edge/anycast model, raw WebRTC tracks, application-controlled state, usage-based bandwidth pricing. [[55]](https://developers.cloudflare.com/realtime/sfu/calls-vs-sfus/) |
| **Fallback / DVR / VOD** | **CMAF + LL-HLS/HLS + AAC-LC** | CDN-friendly, mobile-native fallback and persistence; LL-HLS designed to reduce HTTP-streaming latency. [[56]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls) |
| **HTTP CDN** | Existing strategic CDN; **CloudFront** is a strong AWS-aligned default | Native distribution model for HLS, DASH and CMAF. [[57]](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/on-demand-streaming-video.html) |
| **Public API** | **REST/JSON + OpenAPI** | Simple client/control interactions, cacheability, broad tooling |
| **Realtime application protocol** | **WebSocket/JSON** | Native browser bidirectional transport; straightforward moderation and reconnect semantics. [[31]](https://www.rfc-editor.org/info/rfc6455/) |
| **Internal RPC** | **gRPC + Protocol Buffers** | Strong schemas/code generation and streaming RPCs. [[32]](https://grpc.io/docs/what-is-grpc/introduction/) |
| **Durable realtime messaging** | **NATS + JetStream** | Pub/sub plus persistence/replay/at-least-once in one system. [[3]](https://docs.nats.io/concepts/jetstream) |
| **Control DB** | **Managed PostgreSQL** | Transactional relational state and configuration |
| **Chat history** | **DynamoDB Global Tables or equivalent partitioned KV** | Room/time partitioning and regional replication; selectable multi-region consistency. [[13]](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html) |
| **Presence/rate limiting** | **Redis/Valkey-compatible managed cache** | Ephemeral TTL state and counters |
| **Media/bulk storage** | **Object storage** | Recordings, CMAF segments, exports, analytics |
| **Analytics** | **JetStream → object storage/Parquet → warehouse** | Keeps analytical processing off interactive request paths |
| **Authentication** | **OIDC + OAuth Authorization Code/PKCE** | Interoperable identity and current security best practice for public clients. [[15]](https://openid.net/specs/openid-connect-core-1_0.html) |
| **Container orchestration** | **Kubernetes, three application regions** | Standardized stateless deployments and metric-driven autoscaling. [[8]](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) |
| **Serverless** | Async jobs only | Good for bursty webhook/moderation/analytics work; avoid on persistent media/socket path |
| **Observability** | **OpenTelemetry + Prometheus-compatible metrics + Alertmanager/Grafana** | Correlated telemetry plus established rule/notification model. [[58]](https://opentelemetry.io/docs/concepts/signals/) |
| **Web client** | TypeScript + native WebRTC + MSE/native HLS fallback | Browser-standard real-time media plus adaptive HTTP fallback; MSE supports JS-managed segmented media. [[40]](https://www.w3.org/TR/media-source-2/) |
| **iOS client** | Swift + native WebRTC + AVFoundation | Interactive WebRTC plus native HLS/offline capability. [[41]](https://developer.apple.com/documentation/avfoundation/using-avfoundation-to-play-and-persist-http-live-streams) |
| **Android client** | Kotlin + native WebRTC + Media3 | Interactive WebRTC plus native adaptive/offline media support. [[42]](https://developer.android.com/media/media3/exoplayer/downloading-media) |

The central architectural principle is that the platform should treat **audio distribution, conversation state, durable history, and product metadata as separate consistency and scaling domains**. WebRTC/SFU infrastructure solves the difficult real-time packet fanout problem; WebSockets and a room sequencer solve authoritative interaction; durable messaging and partitioned storage solve recovery/history; HTTP media solves persistence and degraded compatibility.

For the stated requirements—**100k concurrent listeners, global reach, browser/mobile clients, live chat, and a strict sub-two-second interactive target**—this hybrid architecture is preferable to either extreme: it avoids trying to force HTTP streaming into conversational latency, while also avoiding the substantial operational burden of building and operating a worldwide SFU fleet internally. The most important pre-production validation is consequently not another design exercise but a **full 100,000-listener single-stream capacity test, reconnect-storm test, vendor quota/SLA review, and regional-failure exercise** against the actual selected media provider.

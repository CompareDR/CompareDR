# Write a technical proposal for a distributed audio streaming system

## System Architecture & Design Principles

### High-Level Architecture & Component Topology

The proposed system is organized as a seven-layer distributed architecture in which audio media and control-plane traffic follow separate, independently scaleable paths. The layers are: (1) **Client layer** — browser (React/TypeScript) and mobile (iOS/Android) applications; (2) **Edge/CDN layer** — globally distributed caching nodes that serve HLS segments and static assets; (3) **API Gateway / BFF layer** — a single entry point that authenticates, rate-limits, and routes control-plane requests; (4) **Microservices layer** — user, room/session, stream, chat, and analytics services; (5) **Media pipeline** — ingest → transcode → package → deliver, occupying the media plane; (6) **Storage & data layer** — object storage, relational databases, and caches; (7) **Real-time chat layer** — WebSocket gateway cluster backed by a message broker. The interfaces between layers are: HTTP/HTTPS between clients and the CDN/gateway; gRPC or REST between the gateway and microservices; RTMP/SRT/WHIP between broadcaster encoders and the ingest service; HLS/LL-HLS between the packaging stage and the CDN edge; and WebSocket between chat clients and the WebSocket gateway cluster, with Redis Pub/Sub or Kafka as the fanout broker behind it. This decomposition mirrors the canonical layered anatomy used by production audio platforms such as [Spotify's streaming backend](https://fastpix.com/blog/system-design-and-site-architecture-for-an-audio-streaming-app-like-spotify) and [Twitch's video and chat infrastructure](https://blog.twitch.tv/en/2015/12/18/twitch-engineering-an-introduction-and-overview-a23917b71a25/).

#### Architecture Diagram (Textual Description)

The final report should render a top-to-bottom flow diagram with the following structure:

- **Top row**: Client devices (browser, iOS, Android) on the left; broadcaster encoder (OBS, mobile) on the right.
- **Second row**: CDN edge nodes (CloudFront/Cloudflare) on the left serving HLS segments; API Gateway (Kong/Envoy) in the center; Ingest server cluster (SRS/Ant Media Server) on the right.
- **Third row**: Microservices cluster (user, room/session, stream, chat, analytics) behind the API gateway; WebSocket gateway cluster + message broker (Redis Pub/Sub or Kafka) for chat.
- **Fourth row**: Transcoding worker pool (Kubernetes + FFmpeg) fed by the ingest service; SFU cluster (LiveKit) for WebRTC low-latency path; TURN/STUN servers (coturn or LiveKit built-in) adjacent to the SFU cluster for NAT traversal.
- **Fifth row**: Object storage (S3/GCS) for VOD and recordings; PostgreSQL (primary + read replicas) for relational data; Redis for caching and pub/sub; analytics pipeline (Kafka → Flink → ClickHouse).
- **Arrows**: Broadcaster → Ingest (RTMP/WHIP) → Transcode → Package → CDN → Listener. Listener join: DNS → CDN edge → API gateway (auth) → microservices (room lookup) → CDN playlist fetch → audio playback. Chat: Client → WebSocket gateway → message broker → all gateways in room → clients.

#### Data Flow: Broadcaster Encoder to Listener Playback

A broadcaster captures audio, encodes it (Opus or AAC at 64–128 kbps), and publishes via [RTMP to the ingest server cluster](https://getstream.io/blog/protocol-comparison/). The ingest service authenticates the stream key, assigns a channel ID, and forwards the transcoded output to the media pipeline. A Kubernetes-based FFmpeg worker pool transcodes the single-bitrate source into an adaptive bitrate ladder (e.g., 64/96/128/192 kbps AAC for HLS; 32/64/128 kbps Opus for WebRTC), packages the output into HLS segments (`.m3u8` playlist + `.ts` or `.fMP4` segments), and pushes them to object storage and the origin shield. The CDN replicates segments to edge nodes globally. A listener opens the stream URL, the CDN edge serves the live playlist and segments, and the player (hls.js on Chrome/Firefox, native AVPlayer on Safari/iOS, ExoPlayer on Android) begins playback within 2–4 seconds via [LL-HLS](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026) or 0.5–1.3 seconds via WebRTC when the ultra-low-latency path is available.

#### Data Flow: Chat Message Delivery

Chat messages traverse an entirely separate path from audio. A client sends a message over a persistent WebSocket connection to a gateway node. The gateway publishes the message to a per-room channel on the message broker (e.g., `room:{roomId}:chat` on Redis Pub/Sub or a Kafka topic). All gateway nodes subscribed to that channel push the message to their connected clients. This path operates at sub-100ms latency on the control plane, independent of the media plane's 2–4 second buffering pipeline, and can scale horizontally by adding gateway nodes without any awareness of the media pipeline's state. Twitch's chat system uses the same hierarchical pattern: an Edge layer receives and distributes messages via WebSocket, a PubSub layer handles internal fanout across Edge nodes, and a Room layer aggregates viewer lists — a design that delivers [hundreds of billions of messages per day](https://blog.twitch.tv/en/2015/12/18/twitch-engineering-an-introduction-and-overview-a23917b71a25/).

#### Listener Join Request Lifecycle (DNS to First Audio Frame)

1. **DNS resolution**: The client resolves the stream hostname via DNS-based geo-routing (e.g., AWS Route 53 latency-based routing or Anycast), directing the listener to the nearest CDN point of presence.
2. **TLS handshake**: The client establishes a TLS connection to the CDN edge node.
3. **Playlist request**: The client requests the `.m3u8` playlist from the CDN edge. If the playlist is cached (short TTL of 1–2 seconds), it is served immediately; otherwise, the edge fetches from the origin shield.
4. **Authentication**: The API gateway validates the playback token (signed URL or JWT) and checks room/session access permissions via the room/session service.
5. **Segment fetch**: The client requests the latest 2-second partial segment from the CDN edge. For LL-HLS, the player uses blocking playlist reloads and preload hints to minimize the number of round trips.
6. **First audio frame**: Once the first segment is decoded, playback begins. Total glass-to-glass latency from encoder to first listener frame is 2–4 seconds for LL-HLS or 0.5–1.3 seconds for [WebRTC-delivered streams](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026).

#### Media Plane vs. Control Plane Separation

The media plane and control plane have fundamentally different scaling characteristics, and decoupling them is essential for cost efficiency and operational resilience:

| Dimension | Media Plane (Audio) | Control Plane (Chat, Metadata, Auth) |
|---|---|---|
| **Traffic pattern** | High-bandwidth, steady-state, unidirectional (one-to-many) | Low-bandwidth, bursty, bidirectional |
| **Scale unit** | Concurrent listeners (10k–100k), segments/second | Concurrent WebSocket connections, messages/second |
| **Scaling trigger** | Bandwidth and segment storage | Connection count and message throughput |
| **Hardware profile** | Network I/O-bound, CDN offload | CPU-bound (protocol handling, pub/sub fanout) |
| **Failure impact** | Playback interruption (user-visible) | Chat delay or loss (degraded but not fatal) |
| **CDN caching** | Highly cacheable (immutable segments, shared playlists) | Not cacheable (per-user, ephemeral) |

Separating these planes means a media pipeline overload (e.g., a viral stream saturating the transcoding pool) does not affect chat delivery, and a chat spike (e.g., thousands of emoji reactions per second) does not compete with media server resources. The [control plane / data plane separation principle](https://streamkap.com/resources-and-guides/control-plane-data-plane-separation) is well established in distributed systems: the control plane handles configuration, orchestration, and access control at low throughput, while the data plane handles high-throughput processing. In this architecture, the API gateway, room/session service, and chat service constitute the control plane; the ingest → transcode → package → CDN pipeline constitutes the media (data) plane. The two planes communicate through well-defined interfaces — the room/session service issues stream keys and playback tokens to the media pipeline, while the stream service reports stream status events back to the control plane via an async message bus.

#### Shared Room/Session Identity Without Tight Coupling

The audio streaming and chat subsystems are coupled through a shared **room/session identifier** — a logical channel ID that both the media pipeline and the chat system reference — but they remain independently scalable. The room/session service is the single coordination point: when a broadcaster starts a stream, the service creates a room record, generates an ingest token (for the broadcaster) and a playback token (for listeners), and provisions a chat channel named `room:{roomId}:chat` on the message broker. The media pipeline uses the room ID to route audio from ingest through transcode to packaging and CDN. The chat system uses the same room ID to scope its pub/sub channels. Neither subsystem holds direct references to the other's internal state; they communicate only through the room/session service's API and the shared room ID. This design follows the [microservices coordination pattern](https://netflixtechblog.com/rebuilding-netflix-video-processing-pipeline-with-microservices-4e5e6310e359) where a lightweight metadata service acts as the source of truth for stream and room lifecycle events, and all other services react to those events asynchronously. The coupling is limited to: (1) a shared naming convention, (2) a shared event stream (stream started/ended events published to the message broker), and (3) a shared authentication boundary (both ingest and chat joins require valid tokens issued by the room/session service).

#### TURN/STUN Servers in the WebRTC Delivery Path

For the WebRTC ultra-low-latency delivery path, TURN/STUN infrastructure is required for NAT traversal — most client devices operate behind NAT and firewalls that prevent direct peer-to-peer media connections. A **Selective Forwarding Unit (SFU)** replaces peer-to-peer connections in the one-to-many streaming architecture, forwarding the broadcaster's audio stream to each listener without decoding. TURN servers sit alongside the SFU to relay media for listeners who cannot connect directly. The full ICE framework, STUN/TURN deployment, and listener connectivity analysis are covered in S3.1.

#### SCTE-35 Ad-Insertion Signaling (Architectural Reservation)

[SCTE-35](https://trackit.io/scte-35-standard-core-signaling-for-digital-ad-insertion) (Digital Program Insertion Cueing Message) is the standard signaling protocol for marking ad insertion points in live MPEG Transport Streams and, by extension, in HLS and MPEG-DASH workflows. In HLS, SCTE-35 cues are carried as `EXT-X-DATERANGE` or `EXT-X-SCTE35` tags within the `.m3u8` playlist, signaling timestamps where a player or server-side ad insertion (SSAI) system should splice in alternative content. In DASH, SCTE-35 is carried per [SCTE-214-1](https://account.scte.org/standards/library/catalog/scte-214-1-mpeg-dash-for-ip-based-cable-services-part1-mpd-constraints-and-extensions/) constraints. AWS Elemental MediaTailor is a managed SSAI service that consumes SCTE-35 markers to perform server-side ad insertion by rewriting manifests at the CDN edge.

Full monetization is out of scope for this proposal, but the architecture should reserve the SCTE-35 signaling hook: the packaging stage (HLS segment generator) should be capable of injecting SCTE-35 cue messages into the manifest or stream, and the manifest manipulation pipeline should be designed so that an SSAI layer (e.g., MediaTailor or a custom component) can be inserted between the origin and the CDN without re-architecting the delivery path. The Fora Soft team, which [built the Wowza SCTE-35 module](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026) for server-side ad insertion, confirms that this is a module-level integration, not a platform-level design decision — provided the manifest pipeline is designed with ad-insertion markers in mind from day one.

#### Multi-Region Deployment

For a global audience, the system should be deployed across multiple geographic regions with the following considerations:

**Regional WebSocket chat server placement**: Chat latency is dominated by the round-trip time (TT) between the client and the nearest WebSocket gateway. Deploying chat gateway clusters in at least three regions (e.g., US-East, EU-West, AP-Southeast) and routing clients to the nearest gateway via DNS-based geo-routing (AWS Route 53 latency-based policies or Cloudflare Load Balancing). Each regional gateway cluster connects to the local read replica of the room/session service for authorization checks. Cross-region chat message replication is handled by the message broker: Redis Cluster with cross-region replication, or Kafka with MirrorMaker 2 replicating topic partitions across regions, so that a message sent by a user in Europe is delivered to a listener in Asia within the replication lag (typically <100ms for Kafka with low-latency links).

**Database replication**: The primary PostgreSQL instance (user, room, stream metadata) should deploy with read replicas in each region to minimize read latency. Alternatively, [CockroachDB](https://www.cockroachlabs.com/docs/v24.3/multiregion-overview) provides globally distributed SQL with multi-region tables, allowing reads from the nearest replica with tunable consistency (stale reads for low latency, strong consistency for writes). For a medium-sized team, PostgreSQL with read replicas is simpler to operate; CockroachDB is justified if the team can absorb its operational complexity and needs strong consistency across regions for features like viewer counts or moderation state.

**DNS-based or Anycast geo-routing**: Broadcast and listener traffic is routed to the nearest CDN point of presence via DNS resolution. Anycast (used by Cloudflare and increasingly by AWS Global Accelerator) routes to the nearest PoP at the BGP level, while DNS-based routing (Route 53, NS1) resolves to the nearest edge based on the client's resolver IP. For media traffic, CDN edge selection handles this automatically. For chat gateway selection, the API gateway should redirect WebSocket connections to the regional gateway with the lowest measured latency.

**Multi-region media pipeline**: Each region should have a media pipeline (ingest + transcode + package) for local broadcasters to minimize ingest latency. For listeners, the CDN's global edge network handles delivery regardless of which region originated the stream. A stream started in Europe is available to listeners in Asia via the CDN without requiring the media pipeline to run in Asia.

#### Reference Architectures

The architecture draws on patterns proven at scale by several platforms:

- **Twitch**: [RTMP ingest → transcode to multiple HLS streams → CDN distribution](https://blog.twitch.tv/en/2015/12/18/twitch-engineering-an-introduction-and-overview-a23917b71a25/), with a separate chat system using hierarchical pub/sub (Edge → PubSub → Room layers). Twitch's chat delivers over 10 billion messages per day. The separation of video and chat into independently scaling systems is the core architectural pattern this proposal adopts.

- **Spotify Live** (formerly Spotify Greenroom): Audio-first live rooms with speaker/listener roles. The architecture follows standard podcasting infrastructure patterns — CDN-based HLS delivery with a control plane for room management — but adds real-time audio interaction via WebRTC-constrained paths.

- **Twitter/X Spaces**: Live audio chatrooms built on Twitter's existing social graph. Spaces uses a mix of WebRTC for low-latency speaker audio and CDN-based delivery for listeners, with a control plane that leverages Twitter's existing user graph for authentication and presence. The platform demonstrates the shared room-identity pattern: the Spaces room ID serves as both the audio stream identifier and the chat channel identifier.

- **Clubhouse**: Pioneered the social audio pattern using a custom SFU for real-time audio delivery. Clubhouse's architecture was notable for using Twilio's video infrastructure (repurposed for audio) in early iterations, later moving to a custom WebRTC stack. The key lesson is that a room/session service as the shared coordination point, with separate audio and chat subsystems, is a proven pattern for live audio + chat platforms.

### Non-Functional Requirements & Design Principles

Every technology decision in this proposal is driven by a set of non-functional requirements (NFRs) and explicit design principles. This section defines those constraints, explains the trade-offs they encode, and states the assumptions that bound the design space.

---

#### Latency Tiers and Protocol Implications

Latency is the single most consequential NFR for a live audio platform with integrated chat. The gap between a broadcaster speaking and a listener hearing it — glass-to-glass latency — directly determines whether chat feels synchronized with the stream or frustratingly disconnected. We define three latency tiers, each mapped to a delivery protocol:

| Tier | Latency | Protocol | Mechanism |
|------|---------|----------|-----------|
| Ultra-low | 0.5–1.3s real-world CDN-delivered; 100–500ms ideal | WebRTC (SFU-relayed) | Continuous UDP/SRTP packet flow; no segment buffering; ICE negotiation adds 1–3s startup |
| Low | 2–4s glass-to-glass | LL-HLS (CMAF, HTTP/2) | Partial segments (200–300ms each), blocking playlist reloads, preload hints |
| Standard | 8–12s (segment-based); up to 20–45s with player buffer | Standard HLS (MPEG-TS, 6–10s segments) | Full-segment production + 2–3 segment player buffer |

The 100–500ms figure for WebRTC is an *ideal* under controlled conditions. Independent production measurements put CDN-delivered WebRTC at **0.58–1.30s** glass-to-glass, and Fora Soft explicitly warns that "sub-500ms is not a number you should plan around" — it is a figure copied between marketing pages until it acquired the texture of fact ([Fora Soft, 2026](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)). We therefore budget **0.6–1.3s** for the WebRTC path and treat anything faster as a gift.

LL-HLS achieves 2–4s by breaking the media timeline into ~200–300ms partial segments (`EXT-X-PART`), using blocking playlist reloads so the server holds the HTTP request open until new content is available, and emitting preload hints (`EXT-X-PRELOAD-HINT`) so the player can have the next request in flight before the current segment completes ([Mux, 2024](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf); [Fora Soft LL-HLS glossary](https://www.forasoft.com/learn/video-streaming/glossary/terms-streaming/ll-hls)). The catch is operational: the entire chain — packager, origin, every CDN POP, and the player — must support partial-segment fetching and chunked transfer encoding. A misconfigured CDN that serves each partial as a separate cache entry kills the gains.

Standard HLS, by contrast, uses 6–10 second segments and the player buffers 2–3 of them before playback, yielding 15–30s of glass-to-glass latency even before transcoding and CDN propagation ([Mux, 2024](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf)). This is acceptable for VOD or slow-paced broadcasts but breaks chat synchronization for live events.

**The latency-scale trade-off is the central architectural tension.** WebRTC delivers sub-second latency but requires a Selective Forwarding Unit (SFU) to fan out media to each listener, with a single SFU node scaling to a few hundred concurrent viewers before cascading is required (see S3.1 for protocol-specific scaling limits and cost analysis). LL-HLS, by contrast, scales to **100K+ concurrent viewers** on any commodity CDN with no SFU fleet, because segments are immutable HTTP objects that CDN edge nodes cache and serve. The cost is 2–4s of latency.

The recommended architecture is therefore **hybrid**: WebRTC for interactive scenarios (live Q&A, co-listening, speaker panels) where sub-second latency is a hard requirement and concurrent viewers are under a few hundred; LL-HLS as the primary delivery protocol for the mass audience at 1K–100K concurrent listeners. This is the pattern most modern live platforms ship as of 2026 ([Fora Soft, 2026](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)).

#### Availability Target: 99.95%

We target **99.95% availability** (≈4.38 hours of downtime per year, or 21.36 minutes per month) for the streaming and chat platform. This is an appropriate SLO for a medium-sized company: it is stringent enough to require real redundancy and failure-domain isolation, but not so aggressive (e.g., 99.99% = 52.6 min/year) that it demands multi-region active-active deployment with its associated cost and complexity ([Hyperping SLA calculator](https://hyperping.com/99.95); [incident.io SLO guide](https://incident.io/blog/slo-sla-sli)).

Redundancy patterns that support 99.95%:

- **Stateless services** (API gateway, chat WebSocket gateways, user/room services): run ≥2 replicas across availability zones; any single instance failure is absorbed with no session loss.
- **Media servers (SFU)**: stateful by nature; deploy in an SFU cluster with cascading capability so that a node failure triggers client reconnection to a healthy node. WebRTC's ICE restart mechanism handles this at the protocol level.
- **CDN**: inherently redundant; origin shield pattern with a secondary origin for failover.
- **Database**: PostgreSQL with synchronous replication to a standby in a different AZ; automated failover via Patroni or cloud-managed equivalents.
- **Redis**: Redis Sentinel or Redis Cluster for cache and pub/sub availability.

We do **not** target 99.99% (four nines) at this scale. The incremental cost of multi-region active-active — duplicate SFU fleets, cross-region database replication, global load balancing — is difficult to justify for a medium-sized company when 99.95% already provides a robust user experience. If a specific product tier later demands higher availability, that tier can be carved out into a dedicated multi-region deployment.

#### Concurrency Scale Points

We define three scale points that drive architecture choices:

| Scale Point | Concurrent Listeners | Architecture Implications |
|-------------|---------------------|---------------------------|
| **1K** | ~1,000 | Single SFU node sufficient for WebRTC; single HLS origin + CDN; single PostgreSQL instance; Redis standalone. Viable with a single Kubernetes cluster in one region. |
| **10K** | ~10,000 | WebRTC requires SFU cluster (cascading or multi-node); HLS origin behind CDN origin shield; PostgreSQL with read replicas; Redis Cluster. Multi-AZ deployment within one region. |
| **100K** | ~100,000 | WebRTC path limited to interactive sub-rooms (hundreds of viewers); LL-HLS is the primary delivery for the mass audience; multi-region CDN; PostgreSQL read replicas or CockroachDB; Kafka for chat fanout at scale. Multi-region deployment. |

At 100K concurrent listeners, WebRTC alone is not viable as the primary transport — a single SFU node handles only a few hundred subscribers, and cascading to 100K is cost-prohibitive (see S3.1 for scaling limits and cost analysis). The economically sound approach is to serve the mass audience via LL-HLS on a CDN and reserve WebRTC for the interactive sub-rooms where its low latency justifies the per-listener SFU cost.

**Launch vs. 2–3 years out**: At launch, we plan for 1K–10K concurrent listeners per stream with a single-region deployment. The architecture is designed so that scaling to 100K requires adding CDN capacity and read replicas, not re-architecting. The media plane (SFU + transcoding) and control plane (chat, API, metadata) are decoupled so that each scales independently — a viral stream that draws 100K listeners does not proportionally increase chat server load, because chat fanout is per-room, not per-listener.

#### Handling 10x Traffic Spikes

A viral stream or a scheduled event (e.g., a popular podcast episode going live) can produce a 10x traffic spike within minutes. The system must handle this without pre-provisioning for the peak, which would be economically wasteful.

**Auto-scaling strategy**:

- **Stateless services** (API gateway, chat WebSocket gateways): Kubernetes Horizontal Pod Autoscaler (HPA) with aggressive scale-up behavior — `stabilizationWindowSeconds: 0`, `scaleUp` policy of 100% per 15-second window — and conservative scale-down (`stabilizationWindowSeconds: 300`, remove at most 2 pods per 60 seconds) to avoid flapping ([OneUptime, 2026](https://oneuptime.com/blog/post/2026-01-27-capacity-planning-traffic-spikes/)).
- **Chat WebSocket servers**: HPA on CPU/memory is insufficient because a server can be at 30% CPU while handling thousands of idle connections. We use **KEDA** (Kubernetes Event-Driven Autoscaling) with custom Prometheus metrics — `websocket_active_connections` and `websocket_messages_received_total` — to scale on actual connection count and message throughput. A target of ~1,000 connections per pod and ~100 messages/sec per pod drives the scaling decisions ([OneUptime, 2026](https://oneuptime.com/blog/post/2026-02-09-auto-scaling-websocket-keda/view); [KEDA documentation](https://keda.sh/)).
- **Transcoding workers**: KEDA scaling on queue depth (number of pending ingest/transcode jobs), with spot/preemptible instances for batch transcoding to cut compute cost 40–60% ([Fora Soft, 2026](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)).
- **CDN**: The CDN absorbs traffic spikes for HLS segment delivery. When a stream goes viral, CDN edge nodes cache the immutable segments (long TTL) and serve them without hitting the origin. The origin shield pattern — a single caching layer between media servers and the CDN — prevents the origin from being overwhelmed by cache-miss storms.
- **Pre-warming for scheduled events**: For known events (a popular show's scheduled broadcast), a pre-warm script scales up infrastructure 30–60 minutes before the event and warms caches by hitting key endpoints ([OneUptime, 2026](https://oneuptime.com/blog/post/2026-01-27-capacity-planning-traffic-spikes/)).

The CDN's edge caching and origin shield absorb the simultaneous listener surge when a stream starts, preventing origin overload (see S3.3 for the full thundering herd and request collapsing discussion). For chat, the pub/sub pattern (Redis Pub/Sub or Kafka) means that a single message published to a room channel is fanned out by each WebSocket gateway to its local connections, avoiding a database query per listener.

#### Managed Services vs. Self-Hosted: The Cost Trade-Off

A critical build-vs-buy decision is whether to self-host media servers (SRS, LiveKit, mediasoup) or use managed services (AWS Elemental MediaLive/MediaPackage, Mux, Cloudflare Stream). The trade-off is between operational control and operational simplicity. For a medium-sized company (~20–50 engineers), we recommend a **hybrid approach**: self-host the SFU for the WebRTC ultra-low-latency path (a core differentiator requiring tuning, with a bounded audience of hundreds of concurrent viewers per interactive room), use a managed CDN for HLS/LL-HLS delivery (undifferentiated heavy lifting where managed services excel), and consider managed transcoding for initial launch before evaluating self-hosting FFmpeg on Kubernetes once volume justifies it. The full media server comparison — including managed-service alternatives, pricing, and break-even analysis — is in S3.2. CDN egress is the dominant cost variable in the overall infrastructure bill; the full CDN cost model and pricing analysis are in S3.3.

#### Design Principles

We state four explicit design principles that govern every architectural decision:

1. **Prefer managed services for undifferentiated heavy lifting.** CDN delivery, DNS, load balancing, and managed Kubernetes are commodities. Building and operating them in-house consumes engineering capacity that should be spent on product differentiation (the streaming experience, chat features, moderation). Managed Kubernetes (EKS/GKE) costs ~$72–73/month per cluster for the control plane — a trivial cost that eliminates the operational burden of self-managing etcd, API server upgrades, and control plane redundancy ([Sedai, 2026](https://sedai.io/blog/kubernetes-cost-eks-vs-aks-vs-gke); [Intercept, 2025](https://intercept.cloud/en-gb/blogs/kubernetes-cost-eks-vs-gke)).

2. **Stateless services for horizontal scaling.** Every control-plane service (API gateway, chat WebSocket gateway, user service, room/session service) must be stateless — any instance can serve any client. This enables HPA-based autoscaling, rolling deployments with zero downtime, and simple failover. State (WebSocket connections, SFU media flows) is confined to specific components (chat gateways, media servers) that are explicitly designed as stateful with connection draining and graceful shutdown.

3. **Event-driven for chat fanout.** Chat messages are published to a per-room channel (Redis Pub/Sub or Kafka topic) and fanned out by each WebSocket gateway to its local connections. This decouples message producers from consumers, allows any gateway to serve any client, and scales horizontally by adding more gateway pods. The pub/sub pattern is inherently event-driven — no gateway polls a database for new messages.

4. **CDN-first for delivery.** All HLS/LL-HLS media segments are served through a CDN with an origin shield. The origin servers (media servers, transcoding pipeline) are never exposed directly to listeners. This ensures that 100K concurrent listeners are served by CDN edge nodes, not by the origin infrastructure. WebRTC media, which cannot be cached by a CDN, is the exception — it flows through SFUs — and this is one reason WebRTC is reserved for smaller interactive rooms.

#### Explicit Assumptions

The entire proposal is bounded by the following assumptions:

- **Audio-only (no video).** This dramatically reduces transcoding cost, storage, and bandwidth compared to video streaming. A 128 kbps AAC stream moves ~0.57 GB per viewer-hour; a 720p H.264 video stream moves ~1.35 GB per hour — a 2.4× difference. Audio-only also simplifies the SFU design (no simulcast layer selection, no video codec negotiation) and reduces the per-listener CPU cost of media relay.
- **Cloud-first deployment.** The system runs on public cloud infrastructure (AWS, GCP, or a multi-cloud combination). We do not design for on-premises or hybrid cloud at launch. Managed Kubernetes (EKS or GKE) is the orchestration layer, with Terraform for infrastructure-as-code and Helm/Kustomize for application deployment.
- **Medium-sized team (~20–50 engineers).** This constrains the operational complexity we can absorb. We cannot run a multi-region active-active deployment with a dedicated SRE team on call 24/7. We choose managed services over self-hosted wherever the operational burden exceeds the differentiation value. We design for a single-region deployment at launch with a clear path to multi-region as the team and user base grow.

## Audio Ingestion & Media Processing Pipeline

### Ingest Protocols & Broadcaster-Side Architecture

#### Protocol Comparison: RTMP, SRT, WHIP, and WebRTC

Audio enters the system through an ingest protocol — the "first mile" between the broadcaster's encoder and the media server. Four protocols are viable in 2025–2026, each with distinct trade-offs in latency, reliability, encoder support, and firewall traversal.

| Protocol | Transport | Latency (ingest) | Encoder Support | Firewall Traversal | Encryption | Best For |
|----------|-----------|-------------------|-----------------|---------------------|------------|----------|
| **RTMP** | TCP (port 1935) | 3–5 s | Universal (OBS, Wirecast, vMix, hardware encoders) | Excellent (TCP 1935 or 443 for RTMPS) | None by default; RTMPS adds TLS | Default ingest for all broadcasters |
| **RTMPS** | TCP over TLS (port 443) | 3–5 s | Same as RTMP | Excellent (port 443, indistinguishable from HTTPS) | TLS 1.2+ | Production ingest requiring encryption in transit |
| **SRT** | UDP | ~1 s (tunable 500 ms–2 s) | Good (OBS 25+, FFmpeg, Haivision, AJA, Blackmagic) | Requires UDP port open; harder on restrictive firewalls | AES-128/256 built in | Remote production over lossy public internet |
| **WHIP** | UDP (WebRTC) | 0.5–1.3 s real-world CDN-delivered | Growing (OBS 30+, FFmpeg, browser-native) | Excellent (HTTPS port 443 for signaling; UDP for media) | DTLS-SRTP (mandatory) | Ultra-low-latency interactive scenarios |
| **WebRTC (direct)** | UDP | 0.5–1.3 s | Browser-native; mobile via react-native-webrtc / flutter_webrtc | Requires STUN/TURN for NAT traversal | DTLS-SRTP (mandatory) | Browser-based broadcasting, interactive co-hosting |

**RTMP** remains the de facto standard for encoder-to-server ingestion despite its age. The protocol runs over TCP on port 1935, providing reliable, ordered delivery that works on virtually every network without special firewall configuration. Its latency of 3–5 seconds is acceptable for the vast majority of live audio streaming use cases — the ingest leg is not the dominant latency contributor when downstream delivery uses HLS (8–12 s) or LL-HLS (2–4 s). Critically, RTMP is not deprecated. The widely repeated claim that Adobe deprecated RTMP is false: Adobe has never deprecated the protocol. The string "RTMP" appears zero times on Adobe's Flash Player end-of-life page. What reached end-of-life on 31 December 2020 was Flash Player — the browser container — not the RTMP protocol itself. The protocol outlived its container by design, not by accident ([Fora Soft, July 2026](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)).

**Enhanced RTMP v2** extends the protocol to address modern gaps. In 2023, Adobe became a founding member of the nonprofit [Veovera Software Organization](https://veovera.org/docs/enhanced/enhanced-rtmp-v2.html), which maintains Enhanced RTMP v2 (currently at version v2-2026-01-31-r2, with repository commits as recent as June 2026). The contributor list includes Adobe, Google, Twitch, Intel, Meta, and the OBS maintainers. Enhanced RTMP v2 adds support for HEVC, AV1, and VVC codecs with HDR, multitrack audio and video capabilities for concurrent management of multiple media streams, and improved metadata signaling — addressing the codec and metadata gaps that had accumulated since the original RTMP specification was published in December 2012 ([Veovera Enhanced RTMP v2](https://veovera.org/docs/enhanced/enhanced-rtmp-v2.html); [SRS RTMP documentation](https://ossrs.net/lts/en-us/docs/v6/doc/rtmp)). For audio-only streaming, the most relevant enhancement is multitrack audio support, which allows a broadcaster to send multiple audio tracks (e.g., separate tracks for host, guest, and ambient audio) over a single RTMP connection.

**SRT** (Secure Reliable Transport), developed by Haivision and open-sourced in 2017, is the purpose-built challenger for contribution over unpredictable public internet connections. SRT runs over UDP and implements ARQ (Automatic Repeat reQuest) at the application layer, selectively retransmitting only lost packets without stalling the entire stream — a fundamentally different failure mode from RTMP's TCP-based head-of-line blocking. SRT achieves approximately 1 second of glass-to-glass latency with a configurable latency buffer (typically 120 ms–2000 ms), and includes native AES-128/256 encryption. It is the standard ingest format for broadcast contribution and professional remote production workflows, used by CNN, BBC, Al Jazeera, ESPN, and NBC Sports ([Mux: RTMP vs. SRT vs. WebRTC](https://www.mux.com/articles/rtmp-vs-srt-vs-webrtc-live-streaming-ingest-protocols); [Wowza: RTMP vs SRT](https://www.wowza.com/blog/rtmp-vs-srt-choosing-the-right-protocol)). SRT's weakness is firewall traversal: it requires UDP ports to be open, which adds IT configuration overhead compared to RTMP on TCP 443. Encoder support is good and growing (OBS 25+, FFmpeg, most modern hardware encoders) but not yet universal.

**WHIP** (WebRTC-HTTP Ingest Protocol) became [RFC 9725](https://www.rfc-editor.org/info/rfc9725) in March 2025, published as an IETF Standards Track document (Proposed Standard maturity level) after 16 working-group draft revisions. Authors Sergio Garcia Murillo (Millicast) and Alexandre Gouaillard (CoSMo Software) submitted the first draft in late 2020; the IETF chartered the WISH working group in 2021. WHIP standardizes the signaling layer for WebRTC ingest: an encoder POSTs an SDP offer with a bearer token to a WHIP endpoint, the server responds with `201 Created` containing an SDP answer and a session URL, and media flows over standard WebRTC transport (DTLS-SRTP). The entire protocol surface is four HTTP verbs (POST, DELETE, PATCH, OPTIONS) against two resource URLs ([RFC 9725](https://www.rfc-editor.org/info/rfc9725); [Fora Soft: WHIP RFC 9725](https://www.forasoft.com/learn/video-streaming/articles-streaming/whip-webrtc-ingest-rfc-9725)). WHIP's key value is portability: an encoder that speaks WHIP can push to any WHIP-compatible server — Cloudflare Stream, AWS IVS, Dolby Millicast, or a self-hosted Ant Media Server — without vendor-specific SDKs. OBS Studio (from version 30+), FFmpeg, and GStreamer all support WHIP ingest. However, WHIP does not reduce media latency — it reduces connection setup time and integration cost. The sub-second latency comes from WebRTC itself, not from WHIP ([Fora Soft: WHIP and WHEP](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)). WHIP's limitations include no mid-stream renegotiation (cannot add tracks or change codecs after initial setup) and the requirement for STUN/TURN servers for NAT traversal, which adds infrastructure complexity.

**WebRTC ingest** (with or without WHIP signaling) delivers the lowest latency — 0.5–1.3 seconds real-world CDN-delivered, with 100–500 ms as the ideal but not a reliable planning target. It is the only option for genuinely interactive scenarios: live Q&A where delay would break conversation, synchronized co-listening, or real-time audience participation. Browser-based broadcasting is a meaningful advantage: a WebRTC broadcast tool requires no software install for the presenter. However, WebRTC's P2P model does not scale to one-to-many broadcasting without an SFU, and the protocol's inherent complexity (ICE, SDP, DTLS-SRTP, STUN/TURN) makes server-side implementation significantly more involved than RTMP or SRT ([Mux: RTMP vs. SRT vs. WebRTC](https://www.mux.com/articles/rtmp-vs-srt-vs-webrtc-live-streaming-ingest-protocols); [Ant Media: WebRTC vs RTMP](https://antmedia.io/webrtc-vs-rtmp/)).

#### Recommendation: Multi-Protocol Ingest

For a medium-sized company building a production-grade platform, the recommendation is to support **RTMP/RTMPS as the default ingest protocol** with **SRT and WHIP as optional alternatives**:

- **RTMP/RTMPS** for the broadest encoder compatibility. Every hardware and software encoder supports RTMP. RTMPS (RTMP over TLS on port 443) should be the default for production deployments, providing encryption in transit without firewall changes. Standard RTMP transmits unencrypted; RTMPS adds TLS 1.2+ and uses port 443, making it indistinguishable from HTTPS traffic to firewalls ([Wowza: RTMP](https://www.wowza.com/blog/rtmp); [CDNetworks: RTMP Ingest](https://www.cdnetworks.com/blog/media-delivery/what-is-rtmp-ingest/)).
- **SRT** for broadcasters contributing from remote locations over lossy public internet connections — field reporters, remote guests, mobile hotspots. SRT's ARQ error recovery and tunable latency buffer make it the right tool when network conditions are unpredictable.
- **WHIP** for browser-based broadcasters and interactive scenarios requiring sub-second latency. WHIP's HTTP-based signaling integrates cleanly with existing reverse proxies, load balancers, WAFs, OAuth bearer tokens, and signed URLs — no dedicated publish appliance needed ([Fora Soft: WHIP and WHEP](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)).

This multi-protocol approach avoids vendor lock-in and accommodates the full range of broadcaster scenarios without forcing architectural purity on users who just want to go live.

#### Ingest Server Architecture

The ingest layer is a **stateless cluster behind a load balancer** that accepts incoming streams, authenticates the publisher, assigns a stream key, and forwards the media to the transcoding/packaging pipeline. The architecture is:

```
Broadcaster (OBS / FFmpeg / Browser)
    │
    ▼
Load Balancer (L4: NLB / Envoy / HAProxy)
    │
    ├── Ingest Node 1 (SRS / Ant Media Server / Nimble Streamer)
    ├── Ingest Node 2
    └── Ingest Node N
         │
         ▼
    Transcoding Pipeline (FFmpeg worker pool on Kubernetes)
         │
         ▼
    Packaging & CDN Distribution
```

Each ingest node runs a media server — [SRS](https://github.com/ossrs/srs) (C++, supports RTMP, RTMPS, SRT, WebRTC, HLS, DASH), [Ant Media Server](https://antmedia.io/) (Java, supports RTMP, WebRTC, HLS, SRT), or Nimble Streamer — configured identically. The load balancer distributes new ingest connections across the cluster using consistent hashing on the stream key (or round-robin for new connections). Because each stream is long-lived (potentially hours), the load balancer must maintain session affinity: once a TCP connection is established to a node, all packets for that flow must continue to the same node. Mux's production experience with Google Cloud's Network Load Balancer (Maglev) demonstrated that L4 load balancers using consistent hashing can misroute packets during backend drains, causing TCP RST packets to be sent to the wrong backend and dropping streams. Their solution was to deploy a pool of Envoy proxies, each with a distinct public IP, that terminate the TCP connection and reverse-proxy to the RTMP workers — providing reliable connection draining without customer impact ([Mux: Cloud Load Balancing and Long-Lived TCP Streams](https://www.mux.com/blog/network-virtualization-cloud-load-balancing-and-long-lived-tcp-streams)).

For the transcoding pipeline, ingest nodes forward the accepted stream to a Kubernetes-based FFmpeg worker pool (discussed in S2.2). The ingest nodes themselves are stateless with respect to media processing — they accept the stream and hand it off. If an ingest node fails, the stream can be re-established on another node (see failover below).

#### Stream Key Authentication and Unauthorized Publisher Rejection

Stream key authentication prevents unauthorized users from publishing to the platform. The stream key is a unique, opaque token generated by the stream service when a broadcaster creates a new stream session. The key is appended to the ingest URL:

```
rtmp://ingest.example.com/live/{streamKey}
```

or as a query parameter for servers that support token-based authentication:

```
rtmp://ingest.example.com/live/{streamId}?publishToken={token}
```

The ingest server validates the stream key against the room/session service before accepting media. If the key is invalid, expired, or does not correspond to an active stream session, the connection is rejected with an RTMP error response. Ant Media Server supports publish tokens appended to the stream key for production deployments requiring stream authentication ([Ant Media: RTMP Live Streaming Encoder](https://antmedia.io/rtmp-live-streaming-encoder/)). For RTMPS, the TLS handshake occurs before the RTMP handshake, providing transport-layer encryption; the stream key authentication happens at the application layer after the TLS tunnel is established.

Best practices for stream key security:

1. **Generate cryptographically random stream keys** (128+ bits of entropy) — not sequential or predictable.
2. **Bind stream keys to user identity and room/session** — the key is issued by the stream service after authenticating the broadcaster (JWT or OAuth2 token) and authorizing them to publish to the specified room.
3. **Set expiration** — stream keys should expire when the stream session ends or after a configurable TTL (e.g., 24 hours for recurring streams).
4. **Support key rotation** — allow broadcasters to regenerate a compromised key without disrupting the stream by using a secondary validation path (e.g., the room ID + a server-side secret).
5. **Log all publish attempts** — successful and failed — for audit and abuse detection.
6. **Use RTMPS in production** — standard RTMP transmits the stream key in cleartext; RTMPS encrypts the entire connection including the key.

#### Ingest Server Failover

When an ingest server fails mid-stream, the goal is to restore the stream without dropping it from the listeners' perspective. There are two failure scenarios:

**Scenario 1: Ingest node failure (hard crash, network partition).** The TCP connection between the encoder and the ingest node is broken. The encoder (OBS, FFmpeg) detects the disconnect and automatically attempts to reconnect — this is built into most encoder software. The reconnection logic should use exponential backoff (e.g., 1 s, 2 s, 4 s, 8 s, max 30 s) to avoid overwhelming the cluster. When the encoder reconnects, the load balancer routes it to a healthy ingest node. The new node accepts the stream key, validates it, and the stream resumes. There is a gap of a few seconds during reconnection, but the downstream HLS/LL-HLS delivery pipeline continues serving segments from the origin buffer, so listeners experience a brief rebuffer rather than a complete outage. The transcoding pipeline must handle the stream restart gracefully — the FFmpeg worker detects the new ingest connection and resumes transcoding from the current timestamp.

**Scenario 2: Planned maintenance (rolling upgrade, scale-down).** The ingest node is gracefully drained: it stops accepting new connections, signals the load balancer to mark it unhealthy, and waits for active streams to complete or be migrated. The Mux team used a health-check workflow where workers declare themselves unhealthy via the load balancer's HTTP health check when at capacity, allowing graceful draining ([Mux: Cloud Load Balancing](https://www.mux.com/blog/network-virtualization-cloud-load-balancing-and-long-lived-tcp-streams)). For Kubernetes deployments, a `preStop` hook on the ingest pod sends a SIGTERM, the pod stops accepting new connections, and the load balancer's readiness probe fails, removing the pod from the service. Active streams are given a grace period (e.g., 30 s) to complete or for the encoder to reconnect to another pod.

For **hot standby** (zero-downtime failover), the broadcaster can configure two ingest URLs — primary and backup — in their encoder. If the primary fails, the encoder automatically switches to the backup URL. This is the approach used by Ant Media Server's stream failover playback and is supported by OBS's "automatic reconnect" feature ([Ant Media: Stream Failover Playback](https://docs.antmedia.io/guides/playing-live-stream/stream-failover-playback/)). The backup ingest node runs in a different availability zone or region, and the stream key is valid on both nodes because authentication is checked against the shared room/session service.

For the transcoding pipeline, the job queue (e.g., NATS or Kafka) holds the transcoding job. If the FFmpeg worker processing a stream dies, the job is requeued and picked up by another worker. The new worker connects to the new ingest node's output and resumes transcoding. This requires the transcoding job to be idempotent — restarting from the current timestamp rather than from the beginning of the stream.

#### Audio Encoding Pipeline Overview

The audio pipeline for this platform follows a linear flow: **source capture → encoder → transcoding (if needed) → packaging → segment generation → CDN distribution**. For live streams, the broadcaster's encoder (OBS, FFmpeg, or a mobile SDK) captures audio and pushes it via RTMP, SRT, or WHIP to the ingest layer (covered in S2.1). The ingest server forwards the stream to the transcoding pipeline, which produces one or more bitrate renditions, packages them into HLS segments or WebRTC RTP streams, and pushes them to the CDN edge for listener consumption. For audio-only content, this pipeline is substantially cheaper to operate than video transcoding — a single FFmpeg worker can process dozens of concurrent audio streams on one vCPU, whereas video transcoding typically requires dedicated GPU or high-core-count CPU per stream.

#### Codec Comparison: Opus vs. AAC vs. MP3

The three codecs relevant to this system are Opus (IETF [RFC 6716](https://www.rfc-editor.org/info/rfc6716)), AAC (MPEG-4 Part 3, with AAC-LC and HE-AAC profiles), and MP3 (MPEG-1 Audio Layer 3, legacy reference). The table below summarizes the decisive trade-offs:

| Dimension | Opus | AAC-LC | HE-AACv1/v2 | MP3 |
|---|---|---|---|---|
| **Standard** | IETF RFC 6716 (2012) | ISO/IEC 13818-7 | ISO/IEC 13818-7 + SBR/PS | ISO/IEC 11172-3 (1993) |
| **Bitrate range** | 6–510 kbps | 8–320 kbps | 32–64 kbps (v1), 16–48 kbps (v2) | 32–320 kbps |
| **Encode+decode latency** | <40 ms (20 ms frame typical; 2.5 ms minimum) | ~100–200 ms (1024-sample frame ≈ 21.3 ms) | ~100–200 ms | ~100–200 ms |
| **Quality at 64 kbps (speech)** | Excellent (SILK mode) | Good | Good (SBR extends bandwidth) | Poor |
| **Quality at 64 kbps (music)** | Good (CELT mode) | Fair | Fair | Poor |
| **Quality at 128 kbps (music)** | Excellent (transparent for most listeners) | Transparent | Good | Fair |
| **Hardware decode (mobile)** | Decode-only on most modern devices; encode is CPU-based | Hardware encode + decode on iOS/Android | Hardware decode on most devices | Universal hardware decode |
| **Browser support** | All major browsers (WebRTC mandatory per [RFC 7874](https://www.rfc-editor.org/info/rfc7874)) | Native in Safari; via hls.js in others | Limited | Universal |
| **Licensing** | Royalty-free, open-source | Patent-protected (Via Licensing) | Patent-protected (Via Licensing) | Patents expired, royalty-free |
| **Best for** | WebRTC, interactive audio | HLS/DASH delivery | Low-bitrate radio streaming | Legacy compatibility only |

**Opus** is the default codec for the WebRTC path. It combines two engines — SILK (speech, from Skype) and CELT (music, from Xiph.Org) — with an automatic mode selector that switches between them or blends them in hybrid mode, all within a single bitstream ([Fora Soft, 2026](https://www.forasoft.com/learn/audio-for-video/articles-audio/opus-codec-explained)). This dual-engine design is why Opus handles both whispered conversation and full-band stereo music without requiring a mid-stream codec switch. Its algorithmic delay is 22.5–60 ms depending on frame size, with the standard 20 ms frame producing ~26.5 ms total delay — roughly one-fifth of AAC-LC's ~21.3 ms per frame alone, before accounting for encoder and decoder buffering ([Ant Media, 2026](https://antmedia.io/best-audio-codec/); [GetStream, 2026](https://getstream.io/resources/projects/webrtc/advanced/codecs/)). Opus also provides in-band Forward Error Correction (FEC) and Discontinuous Transmission (DTX), which cut silent-period bandwidth by 85–90% and maintain intelligibility through packet loss — features that are essential for interactive audio but absent from AAC.

**AAC** is the default codec for the HLS delivery path. AAC-LC at 128–192 kbps is perceptually transparent for stereo music, and the codec benefits from universal hardware encode and decode acceleration on iOS and Android, which directly translates to lower battery consumption during playback ([Ant Media, 2026](https://antmedia.io/best-audio-codec/)). HE-AACv1/v2 extends AAC with Spectral Band Replication (SBR) and Parametric Stereo (PS), achieving acceptable quality at bitrates as low as 32–48 kbps — useful for the lowest rung of the ladder on constrained networks. However, AAC's ~100–200 ms encode+decode latency makes it unsuitable for interactive, chat-synchronized scenarios where round-trip delay must stay under 500 ms.

**MP3** is included only as a legacy reference. At equivalent bitrates, AAC delivers better quality than MP3 (128 kbps AAC ≈ 160 kbps MP3 in perceptual quality), and MP3's patents have expired, making it royalty-free but technically obsolete for new streaming deployments ([Ant Media, 2026](https://antmedia.io/best-audio-codec/)).

#### Quality-per-Bitrate at Low Bitrates (≤96 kbps)

For an audio-only streaming platform, the low-bitrate rungs matter because listeners on weak cellular connections will spend significant time at 64–96 kbps. The official Opus listening tests provide the most direct comparison:

- **At 64 kbps (stereo music, 48 kHz):** HydrogenAudio ABC/HR tests show Opus outperforming both Vorbis and HE-AAC at this bitrate, with Opus maintaining musical detail that HE-AAC renders as noticeably compressed ([Opus Codec comparison](https://opus-codec.org/comparison/)).
- **At 96 kbps (stereo music, 48 kHz):** A second HydrogenAudio test shows Opus matching or exceeding LC-AAC at 96 kbps, while MP3 requires 136 kbps to reach comparable quality — a 40% bandwidth penalty ([Opus Codec comparison](https://opus-codec.org/comparison/)).
- **For speech:** Nokia's published characterization of Opus speech quality confirms that Opus's SILK mode delivers excellent narrowband and wideband speech at 8–40 kbps, with the hybrid mode providing natural full-band speech at 28–40 kbps ([Opus Codec comparison](https://opus-codec.org/comparison/); [Fora Soft, 2026](https://www.forasoft.com/learn/audio-for-video/articles-audio/opus-codec-explained)).

The practical implication: at 64 kbps, Opus is the clear choice for both speech and music. At 128 kbps, both Opus and AAC are perceptually transparent for most listeners, but AAC's hardware decode advantage on mobile makes it the better choice for the HLS path where battery life matters.

#### Mobile Hardware Decode and Battery Impact

On iOS and Android, **Opus is typically hardware-accelerated for decode only**; encoding remains CPU-based on both platforms ([GetStream, 2026](https://getstream.io/resources/projects/webrtc/advanced/codecs/)). This asymmetry is acceptable for this platform because: (1) the WebRTC path is primarily one-to-few (broadcaster encodes once, SFU forwards to many), so the CPU cost of Opus encoding is borne by a small number of publishers, not thousands of listeners; (2) listeners decoding Opus via WebRTC benefit from hardware decode on modern devices, reducing battery drain during playback. AAC, by contrast, has full hardware encode **and** decode on both iOS and Android, making it the more efficient choice for the HLS delivery path where millions of listeners may be decoding simultaneously. The battery impact of software Opus encoding on mobile is real but bounded — it affects only broadcasters, who are a small fraction of the user base, and modern mobile SoCs (Apple A-series, Qualcomm Snapdragon 8-series) handle Opus encoding at 32–64 kbps without thermal throttling in typical usage.

#### Patent and Licensing Considerations

AAC is protected by patents administered through the **Via Licensing Alliance** AAC patent pool. Reported royalty rates have varied from approximately **$0.10 to $0.98 per unit**, with structures including per-unit fees and annual royalty caps ([Via Licensing](https://www.via-la.com/licensing-programs/aac/); [Lumenci, 2026](https://lumenci.com/blogs/aac-licensing-explained-patent-pools-royalty-obligations-and-sep-exposure/)). For a medium-sized company shipping a streaming app, this licensing cost is manageable but non-trivial — it scales with the number of devices or distributions, and requires legal review of the patent pool agreement. HE-AAC carries a separate, higher royalty schedule (reported at $1.08/unit for 1–500,000 units, decreasing at volume tiers) ([Radio World, 2021](https://www.radioworld.com/industry/via-licensing-sets-up-extended-high-efficiency-aac-patent-pool)).

Opus, by contrast, is **completely royalty-free and open-source** — its IETF standardization (RFC 6716) was specifically designed to be patent-free, with contributors from Mozilla, Skype, and Xiph.Org committing to royalty-free licensing ([Fora Soft, 2026](https://www.forasoft.com/learn/audio-for-video/articles-audio/opus-codec-explained)). This eliminates licensing cost and legal risk for the WebRTC path. MP3's patents have also expired, making it royalty-free, but its technical obsolescence makes it irrelevant for new deployments.

**Recommendation:** Use Opus for the WebRTC path (no licensing cost, superior low-bitrate quality, mandatory in WebRTC) and AAC for the HLS path (hardware efficiency, universal compatibility, acceptable licensing cost for a medium-sized company). Avoid HE-AAC unless the lowest rung of the ladder must go below 48 kbps, where its SBR technology provides a quality advantage that may justify the higher royalty.

#### Audio Bitrate Ladder for Adaptive Streaming

For an **audio-only** platform, the audio is the entire stream — there is no large video "passenger" to hide behind, so every bit of audio adaptation is a real bandwidth saved. This is the "Case 2" pattern identified in the Fora Soft analysis: audio-only services need a two-to-four-rung ladder as a core product feature, not an optional extra ([Fora Soft, 2026](https://www.forasoft.com/learn/audio-for-video/articles-audio/audio-adaptive-bitrate-ladders)).

**Recommended AAC ladder for HLS delivery:**

| Rung | Bitrate | Use case | Perceptual quality |
|---|---|---|---|
| Low | 64 kbps | Weak cellular, 2G/3G fallback | Acceptable speech; music noticeably compressed |
| Medium | 96 kbps | Typical cellular | Good speech; fair music |
| High | 128 kbps | WiFi / strong cellular | Transparent for most listeners |
| Premium | 192 kbps | WiFi, audiophile content | Fully transparent for stereo music |

**Recommended Opus ladder for WebRTC delivery:**

| Rung | Bitrate | Use case | Perceptual quality |
|---|---|---|---|
| Low | 32 kbps | Constrained network, speech-only | Excellent speech (SILK mode) |
| Medium | 64 kbps | Typical interactive | Good speech; fair music |
| High | 128 kbps | Full-band stereo music | Transparent for most listeners |

These ladders align with real-world platform practice: YouTube Music offers 48/128/256 kbps (AAC on mobile, Opus on web), and Apple's HLS Authoring Specification recommends stereo AAC between 32–160 kbps ([Fora Soft, 2026](https://www.forasoft.com/learn/audio-for-video/articles-audio/audio-adaptive-bitrate-ladders)). The four-rung structure provides enough granularity for the player to adapt to network changes without the cost of encoding and storing six or more renditions (a mistake common when teams copy video ladder patterns onto audio).

**ABR switching logic** is handled client-side: hls.js (browser), ExoPlayer (Android), and AVPlayer (iOS) all implement throughput-based and buffer-based bitrate selection. The player measures download speed per segment and climbs or descends the ladder accordingly, starting at the lowest rung and ramping up as bandwidth allows ([Cloudflare, 2024](https://www.cloudflare.com/learning/video/what-is-adaptive-bitrate-streaming/)).

#### Transcoding Architecture: Kubernetes FFmpeg Worker Pool

The transcoding pipeline is built on a **Kubernetes-based FFmpeg worker pool** with event-driven autoscaling. The architecture follows the queue-driven pattern validated in production at scale ([MpegFlow, 2026](https://www.mpegflow.com/blog/ffmpeg-in-kubernetes-pod-queue-operator-pattern)):

1. **Ingest event queue:** When a broadcaster starts a stream, the ingest service publishes a transcoding job to a message queue (Redis, NATS, or RabbitMQ). The job contains the stream key, source codec, target renditions, and output destination.

2. **Worker Deployment:** A Kubernetes `Deployment` of long-lived FFmpeg worker pods pulls jobs from the queue and runs them serially. Each worker is a containerized FFmpeg binary with the necessary codec libraries (libopus, libfdk-aac or native AAC encoder).

3. **KEDA autoscaling:** A [KEDA](https://keda.sh/) `ScaledObject` scales the worker Deployment based on queue depth — the number of pending transcoding jobs. When the queue is empty, workers scale to zero (or a minimum of 1 for fast cold-start). When a viral stream triggers a burst of ingest events, KEDA scales workers up to a configured cap (e.g., 200 pods) in seconds. This is the correct signal to scale on — "are there jobs to run?" — rather than CPU/memory, which is a lagging symptom ([MpegFlow, 2026](https://www.mpegflow.com/blog/ffmpeg-in-kubernetes-pod-queue-operator-pattern)).

4. **Output:** Each transcoded rendition is packaged into HLS segments (.ts or .fMP4) and pushed to the origin storage (S3-compatible object storage), which the CDN edge nodes pull from.

**For audio-only streaming, transcoding cost is significantly lower than video.** A single FFmpeg worker can process dozens of concurrent audio streams on one vCPU, because audio transcoding is orders of magnitude less CPU-intensive than video (no motion estimation, no frame reconstruction). This means the worker pool can be small at launch (4–8 pods) and scale to handle 100+ concurrent streams with modest resources. The dominant cost is not transcoding compute but **CDN egress** — the cost of delivering audio bytes to listeners, which accounts for 70–95% of the total infrastructure bill for streaming platforms (covered in S3.3).

**Passthrough consideration:** For audio-only streaming, if the broadcaster already encodes at a high bitrate (e.g., 192 kbps AAC) and the client player can adapt, the origin can **pass through** the single high-bitrate stream without transcoding to lower rungs. This eliminates transcoding cost entirely for that stream. However, this approach fails for listeners on weak connections who need the 64 kbps rung. A pragmatic hybrid: transcode only when the listener base justifies it (e.g., a stream with >1000 concurrent listeners gets the full ladder; a stream with <100 listeners gets passthrough at 128 kbps). This decision can be made dynamically by the stream service based on concurrent listener count.

#### Live vs. VOD Transcoding Trade-off

Live transcoding prioritizes **latency** over quality. The FFmpeg encoding preset for live audio should use the `ultrafast` or `superfast` preset (for x264 video) or the equivalent low-latency tuning for audio codecs — for Opus, this means using the `voip` or `lowdelay` encoding mode, which disables look-ahead and reduces algorithmic delay to 2.5–20 ms. The trade-off is a 5–15% quality penalty at equivalent bitrates compared to a `medium` or `slow` preset, but for live audio this penalty is imperceptible to most listeners and the latency savings are essential.

VOD transcoding (for recorded streams made available on-demand) prioritizes **quality** over latency. The same audio can be re-encoded with a slower preset, producing 10–20% better quality at the same bitrate, or the same quality at 10–20% lower bitrate. Since VOD content is not time-sensitive, the encoding can take minutes per stream rather than milliseconds. The system should use a separate transcoding queue and worker pool for VOD jobs, with lower priority and higher quality presets.

#### Segment Duration Trade-offs

Segment duration is the primary knob controlling the latency-vs-cache-efficiency trade-off in HLS:

| Segment duration | Latency impact | Cache efficiency | Playlist reloads | Best for |
|---|---|---|---|---|
| 2s | Lowest latency (~6s glass-to-glass with 3-segment window) | Lower (smaller objects, more requests) | Frequent | LL-HLS live |
| 4s | Moderate latency (~10–12s) | Moderate | Moderate | Standard live |
| 6s | Standard latency (~18–25s) | Higher (larger objects, fewer requests) | Less frequent | Standard live / VOD |
| 10s | Higher latency | Highest | Least frequent | VOD only |

The HLS specification historically recommended 6-second segments, and this remains the default for standard HLS. However, for **LL-HLS** (Low-Latency HLS), Apple's specification introduces **partial segments** of 200–300 ms each, which are sub-segments within a 2s container segment. The playlist is updated with delta updates (only sending the changed portion of the .m3u8), and preload hints (`EXT-X-PRELOAD-HINT`) tell the browser to start fetching the next partial segment before the current one completes. This achieves 2–4s glass-to-glass latency while maintaining reasonable CDN cache efficiency ([Mux, 2024](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf); [Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/glossary/

## Media Delivery & Streaming Protocols

### Delivery Protocol Selection: LL-HLS vs. WebRTC vs. DASH

#### The Latency–Scale Triangle

Every delivery protocol for live audio sits at a different point on the tension between three axes: end-to-end latency, concurrent-listener scale, and infrastructure cost. Standard HLS (8–12s glass-to-glass) scales to millions via commodity CDN but is too slow for interactive experiences. WebRTC (0.5–1.3s real-world CDN-delivered, 100–500ms ideal) delivers sub-second latency but requires a Selective Forwarding Unit (SFU) per listener-leg, making fan-out expensive beyond a few hundred concurrent viewers ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf)). Low-Latency HLS (LL-HLS, 2–4s) occupies the middle ground — fast enough for most live use cases, cheap enough to scale to 100K+ via standard CDN egress. The recommendation for this platform is a **hybrid**: LL-HLS as the primary delivery path for the mass audience, with WebRTC as an optional ultra-low-latency path for interactive scenarios (live Q&A, co-listening, speaker panels) where sub-second latency is a hard requirement.

#### How LL-HLS Achieves 2–4 Seconds

LL-HLS, published in the HLS Authoring Specification revision 2020 and refined annually (current revision 2025-09), preserves HLS's HTTP-based segment model but introduces four mechanisms that collectively collapse latency from 20–45s to 2–4s ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf); [Fora Soft](https://www.forasoft.com/learn/video-streaming/glossary/terms-streaming/ll-hls)):

1. **Partial segments (`EXT-X-PART`)**: A full segment (typically 1–2s) is subdivided into ~200–300ms "parts." The player can begin downloading and decoding the first partial as soon as it is available, without waiting for the complete segment to finish. This eliminates the segment-boundary wait that dominates standard HLS latency.

2. **Blocking playlist reloads**: Instead of the player polling the manifest and receiving `304 Not Modified` responses (adding hundreds of milliseconds per cycle), the player issues a request for the *next* playlist update using the `_HLS_msn=` query parameter. The server holds the HTTP connection open until new content is available, then responds immediately. This removes the polling overhead that compounds across every segment delivery cycle.

3. **Preload hints (`EXT-X-PRELOAD-HINT`)**: The server tells the player the URL of the next partial segment before it exists, so the HTTP request can be in flight the moment the segment lands. This eliminates the gap between segments that would otherwise require a new request cycle.

4. **Rendition reports**: The player receives metadata about available ABR renditions preemptively, allowing it to anticipate quality switches without parsing every variant playlist — reducing ABR decision latency.

**Operational requirement**: LL-HLS requires the entire chain — packager, origin, every CDN POP, and the player — to support partial-segment fetching, chunked transfer encoding (or HTTP/2 server push), and request coalescing. A misconfigured CDN that serves each partial as a separate cache entry kills the gains ([Fora Soft](https://www.forasoft.com/learn/video-streaming/glossary/terms-streaming/ll-hls)). Apple's reference implementation is the canonical test target; popular players (hls.js since 1.1, Shaka Player since 4.0, AVPlayer natively on iOS 14+) all support LL-HLS as of 2026 ([Fora Soft](https://www.forasoft.com/learn/video-streaming/glossary/terms-streaming/ll-hls)).

**Fallback strategy**: LL-HLS is backward-compatible with standard HLS. A player that does not understand `EXT-X-PART` or `EXT-X-PRELOAD-HINT` simply ignores the new tags and pulls at standard HLS latency (8–12s). This means the same stream URL serves both LL-HLS-capable and legacy clients — no separate pipeline required. On iOS/macOS, Safari's native AVPlayer handles LL-HLS with no JavaScript player and lower battery usage; on Android and other browsers, hls.js or Shaka Player provide LL-HLS via Media Source Extensions (MSE).

#### WebRTC: Sub-Second Latency at a Real Cost

WebRTC achieves sub-second latency by abandoning the HTTP segmentation model entirely. Instead of packaging media into files served over HTTP, WebRTC negotiates direct media sessions using SRTP (Secure Real-time Transport Protocol), a UDP-based protocol designed for real-time communication with minimal buffering. Frames arrive, decode, and render immediately — there is no segment boundary to wait for ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf)).

**Real-world latency**: The only independent glass-to-glass test of CDN-delivered WebRTC puts it at 0.58–1.30s. The frequently cited "100–500ms" figure is an ideal that assumes optimal network conditions; sub-500ms is not a number to plan around ([Fora Soft](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)).

**The scale problem**: WebRTC's peer-to-peer model does not scale horizontally the way CDN-backed HLS does. To reach large audiences, an SFU receives one stream and retransmits it to each viewer — effectively rebuilding a CDN layer on top of WebRTC. A single well-tuned SFU node forwards roughly 500–800 concurrent subscribers (up to ~5,000 for low-bitrate audio forwarding on a high-end box), but higher bitrates push the practical limit closer to a few hundred ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)). Beyond that, SFUs must be cascaded (a master SFU feeds edge SFUs that re-fan-out), which adds latency (packet hops) and operational complexity.

**Cost at scale**: Above 100K concurrent viewers, WebRTC SFU cost per viewer-hour exceeds CDN-delivered LL-HLS by a factor of 5–15 ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)). For 10,000 viewers watching one hour of a 128 kbps audio stream (~57.6 GB total), a budget CDN at $0.005/GB costs ~$0.29/hour, while AWS CloudFront at ~$0.075/GB costs ~$4.32/hour. WebRTC SFU compute for the same audience would cost $50–500/hour in instance costs alone, before egress. Mux, a major streaming infrastructure provider, does not offer WebRTC streaming — a deliberate product decision reflecting the operational burden ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf)).

**When WebRTC is worth it**: Under a few hundred simultaneous viewers, the infrastructure cost is reasonable, and sub-second latency is a hard requirement — live auctions, real-time gaming, audience interaction where 2s of delay makes the product feel broken, or bidirectional communication (speaker panels, live Q&A) where viewers must send media back ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf)). For this platform, WebRTC serves the interactive path: a small group of speakers or co-listeners who need sub-second RTT, while the mass audience watches via LL-HLS.

**SFU → HLS bridge for CDN offload**: When a WebRTC stream must reach more than a few thousand listeners, the SFU output can be bridged to HLS/LL-HLS via LiveKit Egress, FFmpeg, or a custom pipeline. The SFU handles the interactive speaker group, and the bridge encodes a single feed to LL-HLS for CDN distribution to the mass audience. This is the hybrid pattern that most modern live platforms ship as the 2026 default ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)).

#### MPEG-DASH and LL-DASH

MPEG-DASH (ISO standard, codec-agnostic) and its low-latency variant (LL-DASH, using CMAF chunked transfer) deliver 3–6s glass-to-glass latency — slightly higher than LL-HLS because CMAF's chunked transfer has more overhead than LL-HLS's partial-segment model ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf)). DASH's primary value is cross-platform delivery: the same CMAF segments can be served over both HLS and DASH playlists, supporting Android/browser DASH players alongside Apple ecosystem HLS players. If the platform has a genuine requirement to support DASH-based players (common in Smart TV ecosystems, Android TV apps, or enterprise video deployments), CMAF means encoding once and packaging twice rather than running two separate pipelines. For this platform — targeting browser and iOS/Android mobile — LL-HLS is simpler and faster; DASH is noted as a future extension point via CMAF but not recommended as a primary delivery protocol.

#### WHEP: Standardizing WebRTC Delivery-Side Signaling

WHEP (WebRTC-HTTP Egress Protocol) is the delivery-side counterpart to WHIP. It standardizes how a viewer pulls a WebRTC stream from a media server: the viewer POSTs an SDP offer to a WHEP endpoint, the server responds with an SDP answer (or a counter-offer), and media flows over ordinary WebRTC transport. The entire negotiation is one HTTP POST — no proprietary WebSocket signaling, no vendor SDK ([WebRTC Developers](https://www.webrtc-developers.com/webrtc-streaming-with-whip-and-whep/)).

**Standards status (July 2026)**: WHEP remains an IETF draft — [draft-ietf-wish-whep-04](https://datatracker.ietf.org/doc/draft-ietf-wish-whep/), dated 22 June 2026, expiring 24 December 2026. Working-group state is "In WG Last Call, Revised I-D Needed"; IESG state is "I-D Exists" (the earliest stage). The working group's own milestone said WHEP would go to the IESG in December 2024 — roughly 19 months overdue. Four revisions in four years is not a dead draft, but it is not a sprint either ([Fora Soft](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)).

**Vendor asymmetry matrix**: Vendors implement different WHEP revisions and do not always disclose which:

| Vendor | WHIP | WHEP | Notes |
|--------|------|------|-------|
| AWS IVS | ✅ | ❌ | WHIP ingest only; no WHEP egress |
| LiveKit | ✅ | ❌ | WHEP closed as "not planned" |
| Wowza | ✅ | ✅ | Shipped both (2026) |
| Cloudflare | ✅ | ⚠️ | References draft-murillo-whep-01 (pre-WG revision) |
| OvenMediaEngine | ✅ | ❌ | WHIP ingest; proprietary playback |

This asymmetry means WHEP interoperability cannot be assumed. A vendor claiming "WHEP compliance" should be asked, in writing, which revision they implement — draft-03, draft-04, or the pre-WG draft-01 are not the same protocol in the corners that matter ([Fora Soft](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)).

**Practical implication**: For the WebRTC delivery path, WHEP is architecturally reserved as the signaling protocol, but the implementation should abstract the signaling layer so that a custom WebSocket fallback can be used if a target media server lacks WHEP support. The WebRTC media path itself (ICE, DTLS, SRTP) is unaffected by the signaling protocol choice.

#### TURN/STUN: Essential Infrastructure for Global WebRTC

STUN (Session Traversal Utilities for NAT) helps devices discover their public-facing network information, enabling direct peer-to-peer connections. In open-internet consumer traffic, direct connections (host + server-reflexive) succeed in roughly 75–80% of sessions; the remaining 20–25% require a TURN relay ([GetStream.io](https://getstream.io/resources/projects/webrtc/advanced/stun-turn/)). Carrier-grade NATs (CGNs) used by mobile providers are almost always symmetric NATs, which have STUN success rates of only 20–40% — explaining why mobile networks frequently require TURN.

TURN (Traversal Using Relays around NAT) servers relay media traffic when direct connections cannot be established. They are essential for a global audience because:

- **20–25% of users cannot connect directly** without a relay, and this percentage is higher on mobile/cellular networks.
- **Symmetric NATs** (common in corporate firewalls, mobile CGNs, and some ISPs) are incompatible with STUN alone.
- **Without TURN, those users simply cannot join the stream** — a silent failure that is difficult to diagnose.

TURN servers should support UDP (lowest latency, best media quality), TCP (fallback when UDP is blocked), and TLS over TCP port 443 (highest success rate, firewall-friendly, last resort). The ICE framework orchestrates this: it gathers host, server-reflexive (STUN), and relay (TURN) candidates, performs connectivity checks, and selects the best working path — prioritizing direct connections over relays to minimize latency and bandwidth cost ([GetStream.io](https://getstream.io/resources/projects/webrtc/advanced/stun-turn/)).

**Deployment options**: [coturn](https://github.com/coturn/coturn) is the standard open-source TURN/STUN server; LiveKit ships built-in TURN support. TURN servers should be deployed in multiple regions close to the SFU nodes to minimize relay latency. TURN relay bandwidth is a direct cost — every relayed media byte passes through the TURN server — so capacity planning must account for the 20–25% of sessions that will use it.

#### Protocol Comparison Table

| Protocol | Latency (glass-to-glass) | Browser Support | Mobile Support | ABR | Ingest or Delivery | Best For |
|----------|--------------------------|-----------------|----------------|-----|--------------------|----------|
| **Standard HLS** | 8–12s (up to 20–30s) | All (native Safari; hls.js elsewhere) | AVPlayer (iOS), ExoPlayer (Android) | ✅ Full | Delivery | VOD, non-live, massive scale |
| **LL-HLS** | 2–4s | hls.js 1.1+, Shaka 4.0+, Safari native (iOS 14+) | AVPlayer (iOS), ExoPlayer (Android) | ✅ Full | Delivery | **Primary live delivery** — 1K–100K+ listeners |
| **MPEG-DASH / LL-DASH** | 3–6s (LL-DASH: 1–3s) | Shaka Player, dash.js | ExoPlayer (Android) | ✅ Full | Delivery | Cross-platform (Smart TV, Android TV) |
| **WebRTC** | 0.5–1.3s real-world (0.1–0.5s ideal) | Native (Chrome, Firefox, Safari, Edge) | Native (iOS, Android) | ⚠️ Simulcast only | Delivery (SFU-relayed) | **Interactive** — <500 viewers, sub-second latency |
| **RTMP** | 3–5s | ❌ (Flash EOL) | ❌ | ❌ | Ingest only | Broadcaster encoder → server |

#### Recommendation

**Primary delivery: LL-HLS** for all one-to-many live audio streams. It delivers 2–4s latency at 100K+ concurrent listeners on any commodity CDN, requires no SFU fleet, supports ABR, and falls back to standard HLS automatically for legacy clients. The operational simplicity — no media servers to manage for the delivery path, just a packager and a CDN — is decisive for a medium-sized team.

**Secondary delivery: WebRTC** for interactive scenarios where sub-second latency is a hard requirement and concurrent viewers are under a few hundred. The SFU handles the speaker group, and if the audience grows beyond the SFU's capacity, an SFU→HLS bridge offloads to LL-HLS for the mass audience. WHEP is the architecturally reserved signaling protocol for this path, with a custom WebSocket fallback for media servers that lack WHEP support.

**DASH/CMAF**: Not recommended as a primary delivery protocol for this platform's target clients (browser + iOS/Android). Noted as a future extension point via CMAF if Smart TV or Android TV support becomes a requirement.

**Reference architectures**: Google Meet and Discord use WebRTC for interactive sub-second communication. Twitch and YouTube Live use RTMP ingest → HLS/LL-HLS delivery at massive scale. The hybrid pattern (WebRTC for speakers + LL-HLS for viewers) is the 2026 default for platforms that need both interactivity and scale ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)).

### Media Server & SFU Selection

The media server is the architectural hinge of a live streaming platform — it determines latency ceilings, scaling limits, operational burden, and the SDK ecosystem available to client teams. For a system supporting both LL-HLS delivery at scale (10k–100k listeners) and WebRTC ultra-low-latency interactivity (sub-second for live Q&A or co-listening), no single open-source server optimally serves both paths. The proposal below justifies running **SRS** for the RTMP-ingest → HLS delivery path and **LiveKit** for the WebRTC SFU path, with a full comparison of the candidate landscape.

#### Architectural Models: SFU vs. MCU vs. P2P

Before comparing individual servers, the foundational topology choice must be settled. Three media-routing models exist in WebRTC systems:

- **P2P (peer-to-peer):** Each participant sends media directly to every other participant. Zero media-server cost, but each peer must upload *N−1* streams, which collapses around four participants on typical client uplink bandwidth. Practical ceiling: 2–4 participants, 50–150ms latency ([Fora Soft, 2026](https://www.forasoft.com/blog/article/p2p-vs-mcu-vs-sfu-for-video-conference-app-805)).

- **MCU (Multipoint Conferencing Unit):** The server decodes every incoming stream, mixes audio into a single composite (or layers video into a grid), and re-encodes one output per subscriber. Downstream bandwidth is minimized, but the decode-mix-re-encode loop is CPU/GPU-intensive and adds 200–400ms of latency. An MCU costs several times more server capacity than an SFU for equivalent room sizes, and the composite output is inflexible — per-stream volume control or custom layouts are impossible. MCU is justified only for recording a single broadcast feed, serving thin/legacy clients that decode one stream, or producing a fixed-layout video canvas ([LiveKit SFU docs](https://docs.livekit.io/reference/internals/livekit-sfu/); [Fora Soft, 2026](https://www.forasoft.com/blog/article/p2p-vs-mcu-vs-sfu-for-video-conference-app-805)).

- **SFU (Selective Forwarding Unit):** The server never decodes media. Each participant uploads one encoded stream; the server inspects packet headers, selects which subscribers should receive each stream, and forwards it untouched. Server CPU stays low because encoding/decoding happens on clients. The trade-off is higher downstream bandwidth — a subscriber to *N−1* streams downloads *N−1* independent streams rather than one composite. For one-to-many audio streaming (one broadcaster, many listeners), this is ideal: a single audio track is forwarded to all subscribers with negligible CPU cost, and each client independently adapts bitrate ([LiveKit SFU docs](https://docs.livekit.io/reference/internals/livekit-sfu/)).

**For this platform, SFU is the correct model.** The dominant workload is one broadcaster → many listeners, where SFU fan-out is O(listeners) in forwarding cost but O(1) in encode cost. MCU would be necessary only if the platform requires server-side composite recording (LiveKit Egress already handles this separately via FFmpeg) or a single HLS bridge feed for CDN offload.

#### Candidate Media Server Comparison

The following seven open-source projects were evaluated. Each is production-tested; the question is which fits the specific latency/scale/ops profile of this platform.

**SRS (Simple Realtime Server)** — C++, MIT license, v8.0 (2025). Supports RTMP, WebRTC, HLS, HTTP-FLV, SRT, MPEG-DASH, and GB28181 on x86_64/ARM/MIPS. SRS is the most mature and resource-efficient option for the RTMP-ingest → HLS-delivery pipeline. Its RTMP implementation is the de-facto industry standard, supported by every hardware and software encoder (OBS, FFmpeg, vMix). SRS generates HLS playlists (.m3u8) and segments (.ts or .fMP4) directly from RTMP ingest with configurable segment durations. Critically for low-latency delivery, SRS supports LL-HLS extensions: partial segments (200–300ms), blocking playlist reloads, and preload hints — the same mechanisms that the LL-HLS specification defines for 2–4s glass-to-glass latency ([SRS GitHub](https://github.com/ossrs/srs); [Bitmovin LL-HLS deep-dive](https://bitmovin.com/blog/live-low-latency-hls/)). SRS also supports MPEG-DASH and SRT ingest for broadcasters on lossy networks. Its single-node architecture is deliberately simple — no clustering dependencies — which keeps operational overhead low for the HLS origin tier. Resource footprint is minimal; a single SRS instance on a 4 vCPU node can serve thousands of concurrent HLS listeners since HLS delivery is CDN-offloaded after the origin.

**LiveKit** — Go (SFU core built on [Pion](https://github.com/pion/webrtc)), Apache 2.0, released 2021. LiveKit is a complete real-time platform: SFU + Ingress service (RTMP, WHIP, HLS, MP4 file ingest) + Egress service (composite/individual track recording, RTMP out, HLS out) + client SDKs for web, iOS, Android, React Native, Flutter, and server SDKs for Go, Node.js, Python, Rust. The SFU is horizontally scalable by design — nodes run identical configuration and coordinate via Redis for distributed multi-node routing. LiveKit also ships [LiveKit Agents](https://docs.livekit.io/agents/), an open-source AI framework (1.0 in April 2025) that wires speech-to-text + LLM + text-to-speech to a participant's audio track with adaptive interruption handling and MCP tool support — relevant for AI moderation and voice-agent scenarios (covered in §4.2). Built-in TURN server support simplifies NAT traversal ([LiveKit SFU docs](https://docs.livekit.io/reference/internals/livekit-sfu/); [LiveKit distributed mesh blog](https://livekit.com/blog/scaling-webrtc-with-distributed-mesh)).

**mediasoup** — C++ media path with Node.js control API, ISC license, launched 2017. mediasoup is a low-level SFU *library*, not a turnkey server. Each Node.js process spawns C++ worker subprocesses pinned to individual CPU cores; each worker hosts routers (rooms) with producers and consumers. A single worker comfortably handles ~500 consumers (mediasoup's official scalability documentation). `pipeToRouter` interconnects workers on the same host (shared memory) or across hosts. mediasoup does not provide signaling, room management, authentication, or recording — the team builds all of it. This makes mediasoup the highest-control, highest-build-effort option: ideal for telemedicine or custom conferencing products with bespoke media pipelines, but time-to-first-call is weeks, not hours ([mediasoup scalability docs](https://mediasoup.org/documentation/v3/scalability/); [Fora Soft SFU comparison](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)).

**OpenVidu** — Built on mediasoup, higher-level API. OpenVidu replaces LiveKit's Pion-based SFU engine with mediasoup's C++ implementation while maintaining LiveKit's signaling protocol, API, and SDK compatibility. OpenVidu claims up to **2x the load per server** compared to base LiveKit Open Source — their load tests on 8-participant rooms with 1 video + 1 audio track per participant showed mediasoup nearly doubling the total participants per node at 480p on an `m6in.xlarge` (4 vCPU) instance. The performance advantage comes from C++ manual memory management and hardware-direct access vs. Go's garbage collector and runtime overhead. The mediasoup engine does not support the Opus `red` (REDundant Encoding) codec that Pion provides — a minor limitation for audio resilience. OpenVidu's value proposition is LiveKit's developer experience with mediasoup's raw performance ([OpenVidu performance docs](https://openvidu.io/latest/docs/self-hosting/production-ready/performance/)).

**Janus** — C, plugin-based, GPL v3, maintained by Meetecho. Janus is a general-purpose WebRTC gateway: a core handling ICE/DTLS-SRTP/JSEP, with plugins for VideoRoom (SFU), audiobridge (audio mixing), streaming (RTSP/RTP ingest), SIP gateway, recording, and more. Janus is actively maintained (v1.4.0 shipped February 2026). Its plugin model makes it the strongest choice when the same server must bridge multiple protocol worlds — SIP/PBX interop, RTSP camera ingest, WebRTC conferencing, and recording from one binary. However, Janus does not provide a built-in horizontal-scaling story; the team routes rooms to instances at the application layer. The C codebase is a barrier for Go/JS-first teams, and configuration surface area is large ([Trembit comparison](https://trembit.com/blog/choosing-the-right-sfu-janus-vs-mediasoup-vs-livekit-for-telemedicine-platforms/); [Fora Soft SFU comparison](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)).

**Jitsi Videobridge** — C-based, mature WebRTC SFU used in production by 8x8, Wire, and meet.jit.si. Jitsi Videobridge pioneered the **Octo protocol** in 2018 for cascading SFU inter-server routing — wrapping RTP packets in a fixed-length header to relay media between bridges in a full-mesh topology. The separating of signaling (Jicofo) from media (Videobridge) allowed cascading to be added without major refactoring. Octo enables each participant to connect to a geographically local bridge, with bridge-to-bridge relay over a reliable backbone, reducing last-mile latency. However, hop-by-hop reassembly means end-to-end RTT is higher with an extra server, though per-hop stream repair (NACK-based) can reduce jitter buffer requirements. LiveKit's distributed mesh (described below) packages the same cascading-SFU concept as default behavior ([WebRTC Hacks, Boris Grozev, 2018](https://webrtchacks.com/sfu-cascading/); [Fora Soft SFU comparison](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)).

**Ant Media Server** — Java, Apache 2.0 (Community) / commercial (Enterprise). Supports WebRTC (~0.5s latency), RTMP, RTMPS, SRT, RTSP, HLS, CMAF, LL-HLS, and LL-DASH. Community Edition is limited to WebRTC ingest only (no playback) and 8–12s HLS latency; Enterprise Edition unlocks one-to-many WebRTC streaming at ~0.5s, full HLS, LL-HLS, and Kubernetes clustering. Ant Media Server is a solid all-in-one option but carries higher resource overhead (JVM) compared to SRS (C++) or LiveKit (Go), and its Kubernetes support is Enterprise-gated ([Ant Media Server docs](https://docs.antmedia.io/); [Ant Media streaming protocols](https://antmedia.io/streaming-protocols/)).

#### The Octo Protocol and LiveKit's Distributed Mesh

The **Octo protocol**, pioneered by Jitsi Videobridge in 2018, enables cascading SFU topologies where multiple media servers relay media to each other rather than forcing all participants onto a single server. Octo wraps RTP packets in a fixed-length header with conference-ID and stream-identifier fields, allowing bridges to relay media in a full-mesh topology without explicit inter-bridge signaling — all signaling remains between Jicofo (signaling) and Videobridge (media). The key insight: each participant connects to a geographically local bridge, and bridge-to-bridge relay over a high-quality backbone reduces last-mile latency even though hop count increases. Per-hop NACK-based retransmission limits packet loss impact locally ([WebRTC Hacks, 2018](https://webrtchacks.com/sfu-cascading/)).

LiveKit implements the same cascading-SFU concept as **default behavior** rather than opt-in. A LiveKit cluster consists of identical nodes coordinated by Redis. Any participant connects to any node; the cluster routes media to whichever node hosts the other participants in the same room. A single room can span multiple physical servers. State synchronization (participant metadata, track lists) uses Redis pub/sub with eventual consistency — each server publishes state changes to a session-specific topic, and a server joining an existing session requests a full state re-sync over the bus. For media relay between SFUs, LiveKit uses a custom [FlatBuffers](https://google.github.io/flatbuffers/)-based protocol (not WebRTC/SDP, which would add unnecessary ICE and signaling overhead) while still using RTP for the actual media packets. This design is architecturally identical to Octo but packaged as zero-configuration default behavior — no separate signaling server, no manual bridge configuration ([LiveKit distributed mesh blog](https://livekit.com/blog/scaling-webrtc-with-distributed-mesh)).

#### Resource Benchmarks and Scaling Ceilings

Resource consumption per concurrent stream varies significantly across SFUs. The canonical benchmark from Fora Soft (2026) is **1 vCPU handles ~150–250 participant-legs at 480p**, depending on bitrate — applicable to LiveKit, mediasoup, Jitsi, and Janus SFU nodes ([Fora Soft cost guide, 2026](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)). For **audio-only streaming** (this platform's primary workload), the CPU cost per leg is substantially lower than the 480p video benchmark since audio forwarding requires no transcoding and minimal packet processing — a single LiveKit node can handle thousands of audio-only listeners in a one-to-many topology. Specific benchmarks:

- **mediasoup:** ~500 consumers per worker (pinned to 1 CPU core). Scales by spawning workers up to core count; `pipeToRouter` chains rooms across workers ([mediasoup scalability docs](https://mediasoup.org/documentation/v3/scalability/)).
- **LiveKit:** Hundreds to thousands of audio-only participants per node depending on bitrate. Distributed mesh via Redis allows linear horizontal scaling. OpenVidu's mediasoup-based engine claims ~2x participants vs. base Pion at 480p ([OpenVidu performance docs](https://openvidu.io/latest/docs/self-hosting/production-ready/performance/)).
- **Jitsi Videobridge:** ~100–300 participants per instance for video; audio-only scales higher. Cascading via Octo extends this horizontally but adds per-hop latency trade-offs.
- **Janus:** Plugin-dependent; audiobridge handles hundreds of mix participants, videoroom handles 50–200 publishers per instance. No built-in clustering.
- **Ant Media Server:** Community Edition is single-node; Enterprise Edition supports Kubernetes clustering but JVM overhead per node is higher than Go/C++ alternatives.
- **SRS:** Not an SFU — SRS's role is RTMP/HLS origin and WebRTC ingest/egress for smaller-scale interactive use. For one-to-many HLS delivery, SRS hands off to CDN after origin generation, so its own concurrent-listener ceiling is effectively unbounded (CDN absorbs the fan-out).

#### Recommendation: Dual-Server Architecture

**Run SRS for the HLS delivery path and LiveKit for the WebRTC ultra-low-latency path.** This dual-server approach is justified because the two paths serve fundamentally different latency/scale trade-offs that no single server optimally covers:

- **SRS (HLS path):** Broadcasters ingest via RTMP (ubiquitous encoder support, TCP reliability). SRS transcodes/packages into HLS segments and serves a small number of LL-HLS renditions. The CDN (CloudFront, Cloudflare) absorbs listener fan-out from the origin. Latency: 2–4s glass-to-glass with LL-HLS, 8–12s with standard HLS. Scale: effectively unlimited via CDN. SRS's maturity, low resource footprint, and excellent RTMP→HLS pipeline make it the ideal origin server. It also supports SRT ingest for broadcasters on lossy networks and WebRTC for small-scale interactive egress.

- **LiveKit (WebRTC path):** For interactive scenarios requiring sub-second latency — live Q&A, co-listening sessions, voice chat rooms — LiveKit's SFU forwards Opus audio with 0.5–1.3s real-world CDN-delivered latency. The distributed mesh via Redis enables horizontal scaling across regions. LiveKit's Ingress service accepts RTMP/WHIP for broadcasters who prefer those protocols, and Egress handles server-side recording and HLS bridge output for CDN offload when a WebRTC room grows beyond a few hundred concurrent listeners. The SDK ecosystem accelerates mobile and browser client development.

The two servers are **not redundant** — they are complementary. A stream can flow through both simultaneously: the broadcaster sends one RTMP feed to SRS (which packages HLS for the masses) and one WebRTC feed to LiveKit (which serves the interactive tier). The room/session service (§1.1) coordinates room identity across both paths, but each path scales independently.

**OpenVidu** should be evaluated as a drop-in LiveKit alternative if mediasoup's 2x performance advantage is needed for large multi-party WebRTC rooms (e.g., 20+ simultaneous speakers). Its LiveKit API/SDK compatibility means the migration cost is low. However, for the audio-only one-to-many pattern that dominates this platform's workload, base LiveKit's Pion engine is sufficient, and the operational simplicity of LiveKit's default mesh outweighs OpenVidu's marginal throughput gain.

**mediasoup** is the right choice only if the team has deep WebRTC engineering capacity and needs fine-grained control over the media plane (custom simulcast layer selection, bespoke recording pipelines, HIPAA-shaped compliance where every byte must be audited). For a 20–50 engineer team, the build investment is hard to justify when LiveKit provides equivalent SFU functionality with a complete platform layer.

#### SFU → HLS Bridge for CDN Offload

When a WebRTC room exceeds a few hundred concurrent listeners, the SFU's fan-out cost becomes prohibitive. **LiveKit Egress** addresses this: it subscribes to room media from the SFU and outputs an HLS stream (or RTMP feed to SRS) that enters the CDN delivery path. This bridges the WebRTC interactive tier (a few hundred participants) with the HLS mass-audience tier (10k–100k listeners) without architectural discontinuity. The Egress service auto-transcodes and can composite individual tracks into a single recording for VOD ([LiveKit Egress blog](https://livekit.com/blog/livekit-universal-egress-launch)).

#### Audio-Specific Considerations

All discussed SFUs handle audio-only streaming, but with nuances:

- **Codec support:** LiveKit, mediasoup, and Jitsi all support Opus natively (the default for WebRTC). OpenVidu's mediasoup engine does not support Opus `red` (redundant encoding), which marginally reduces audio resilience on lossy networks — not a blocker for typical streaming but worth noting for mobile listeners on cellular ([OpenVidu limitations](https://openvidu.io/latest/docs/self-hosting/production-ready/performance/)).
- **Audio processing:** WebRTC's built-in AEC3, noise suppression (RNNoise), and AGC are available in browser and mobile clients connecting via LiveKit or mediasoup. SRS's WebRTC path also inherits these. No server-side audio processing is needed for the forwarding path.
- **Audio ducking:** When chat notifications play, the client-side audio pipeline must duck stream volume. This is a client-side concern (Web Audio API on browser, AudioManager on Android, AVAudioSession on iOS) and is independent of the SFU choice.
- **Recording:** LiveKit Egress handles server-side recording of WebRTC rooms. SRS can record HLS segments directly. For VOD, both paths store segmented audio in object storage (S3/MinIO) and serve via the same HLS delivery path.

### CDN & Edge Delivery Strategy

The CDN is the single most cost- and performance-critical layer in the audio streaming path. For a platform targeting 10k–100k concurrent listeners per stream with global distribution, the CDN edge network is what makes sub-10-second latency at scale economically viable — and it is also where 70–95% of the total infrastructure bill originates ([Fora Soft, 2026](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)). This subsection specifies the caching architecture, CDN selection, cost model, thundering-herd mitigation, and access-control mechanism.

#### Origin Shield and Tiered Caching Architecture

The canonical streaming cache hierarchy has five layers, read from viewer to origin: (1) the player's local buffer (2–4 segments ahead), (2) the edge POP (nearest CDN server), (3) a regional/mid-tier cache, (4) an origin shield, and (5) the origin server itself ([Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/articles-streaming/origin-shield-tiered-caching)). The **origin shield** is a single designated cache layer — usually one POP in the same region as the origin — through which every upstream request from every edge and regional cache must funnel before the origin is consulted. Only the shield talks to the origin, and only on its own cache miss.

This pattern is essential for live audio because the request pattern is fundamentally different from static content delivery. Every viewer of the same live event requests the same segment at nearly the same instant, every 2–6 seconds. At 100k concurrent listeners, that is a 100,000-fold spike on a single segment file, followed by an identical spike on the next segment two seconds later. Without a shield, 500 edge POPs each send an independent upstream fetch for the same uncached segment — 500 origin requests for one file at the same millisecond. The shield collapses these into a single origin fetch, reducing origin egress by 90–99% for popular live workloads ([Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/articles-streaming/origin-shield-tiered-caching)).

All major CDNs implement origin shielding: [CloudFront Origin Shield](https://aws.amazon.com/cloudfront/media/), Cloudflare's tiered cache, Fastly's shielding POP, and Akamai's Cloud Wrapper. The shield should be deployed in the same cloud region as the origin to minimize the shield-to-origin hop to a few milliseconds — the shield serves a global audience indirectly through the regional caches, so proximity to the audience is irrelevant ([Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/articles-streaming/origin-shield-tiered-caching)).

#### Cache TTL Strategy for Live HLS and LL-HLS

The key insight for live audio caching is that **playlists and segments have diametrically opposite freshness requirements**:

| Object Type | Cache-Control | TTL | Rationale |
|---|---|---|---|
| Live playlist (`.m3u8`) | `max-age=0, must-revalidate` or `no-store` | 0–2s | Must reflect newly appended segments immediately; stale playlists cause players to miss segments and stall |
| LL-HLS partial segment (`.m4s`) | `max-age=1–2` | 1–2s | Short enough to stay fresh, long enough to get cache hits from edge |
| Standard HLS segment (`.ts`/`.m4s`) | `max-age=30–60` (immutable) | 30–60s | Segments are immutable once written; long TTL maximizes cache hit ratio and minimizes origin load |
| VOD segment | `max-age=86400+` (immutable) | 24–48h | Fully cacheable; versioned filenames prevent staleness |

For LL-HLS specifically, the CDN must support HTTP/2 or HTTP/3 multiplexing to avoid head-of-line blocking across the many small requests that partial segments and preload hints generate. The CDN must also respect origin `Cache-Control` headers rather than overriding them, and must handle long-polling "held" responses for preload hints where the origin holds the HTTP connection open until the partial segment is ready ([CDNsun, 2026](https://blog.cdnsun.com/low-latency-hls-with-cdn-the-ultimate-production-guide/)). `stale-while-revalidate` can be applied to playlists as a secondary defense: if a player's playlist request arrives just before a TTL expiry, the CDN serves the stale copy immediately while revalidating in the background, preventing a stall at the cost of potentially serving a playlist one segment behind ([Blazing CDN, 2026](https://blog.blazingcdn.com/en-us/cache-control-stale-while-revalidate-cdn-caching)).

#### Thundering Herd and Request Collapsing

When a popular stream goes live or goes viral, the simultaneous arrival of thousands of listener requests for the same uncached segment creates a **cache stampede** (also called the thundering herd problem). Without mitigation, every edge POP that has not yet cached the segment sends an independent upstream fetch — 500 edges means 500 origin requests for one file at the same millisecond, which can saturate the origin's request-per-second budget and egress capacity ([OTTVerse, 2021](https://ottverse.com/request-collapsing-thundering-herds-in-cdn/)).

The standard defense is **request collapsing** (also called coalescing or collapse forwarding): when multiple simultaneous cache misses for the same object arrive at a cache layer, the CDN sends only one upstream request and queues the remaining requests, releasing them all when the single response arrives. This is complementary to origin shielding — the shield is a cache *hit* (content already present), while collapsing handles cache *misses* (content being fetched once on behalf of many). Cloudflare reports origin request reduction of over 90% during stampedes from coalescing alone; adding the shield's tiered cache on top reduces the residual 10% further ([Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/articles-streaming/origin-shield-tiered-caching)). All major CDNs — CloudFront, Cloudflare, Fastly, Akamai — implement request collapsing by default for streaming-marked properties ([OTTVerse, 2021](https://ottverse.com/request-collapsing-thundering-herds-in-cdn/)).

For a 100k-concurrent-listener stream, the combination of origin shield + request collapsing means the origin sees at most one request per segment per shield cache expiry cycle, rather than 100,000. This is what makes single-origin architectures viable at this scale.

#### Cost Model: Egress at 100k Concurrent Listeners

Egress is the dominant variable cost for audio streaming — 70–95% of the total bill ([Fora Soft, 2026](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)). The cost scales linearly with concurrent listeners and bitrate:

**Assumptions**: 128 kbps AAC (mid-tier quality), 100k concurrent listeners, 1 hour of streaming.

- Total throughput: 100,000 × 128 kbps = 12.8 Gbps = ~5.76 TB/hour
- At CloudFront ($0.085/GB): ~$490/hour
- At Bunny Volume ($0.005/GB): ~$29/hour
- At Cloudflare (unmetered, $250/mo Business): ~$0.35/hour (amortized)

For a more realistic ABR scenario where the average listener consumes 96 kbps (blending 64/96/128 kbps tiers), the hourly egress at 100k concurrent is ~4.32 TB, costing ~$367/hour on CloudFront vs. ~$22/hour on Bunny. At 10k concurrent, these figures drop by 10×. The CDN choice alone swings the bill by more than 10× ([Fora Soft, 2026](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)).

The four-line cost model for the entire platform is: (1) egress (70–95%), (2) storage (2–10%), (3) compute — origin + SFU + transcoder + signaling, and (4) third-party services — DRM, TURN, analytics. Architecture choices (ABR ladder, aggressive CDN TTLs, SFU over MCU) routinely cut total bills by 40–70% more than provider choice alone ([Fora Soft, 2026](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)).

#### Chat Delivery: CDN Edge vs. Dedicated WebSocket

Chat messages should **not** traverse the CDN media path. The audio CDN is optimized for cacheable, immutable, high-throughput segment delivery — the opposite of chat's requirements: ephemeral, ordered, bidirectional, low-latency messages with per-connection state. Instead, chat uses a dedicated WebSocket gateway cluster backed by a pub/sub message broker (Redis Pub/Sub or Kafka), as specified in S4.1.

However, CDN edge computing can play a role in chat **presence and fanout optimization**. [Cloudflare Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) can act as WebSocket servers that connect thousands of clients per instance, with each Durable Object instance managing a single room's state and broadcasting messages to all connected clients. This is architecturally appealing for small-to-medium rooms (up to a few thousand concurrent) because it eliminates the need for a separate WebSocket gateway cluster — the edge *is* the gateway. For the 10k–100k concurrent listener scale targeted here, a dedicated WebSocket gateway cluster with Redis Pub/Sub fanout remains the primary architecture, with Cloudflare Workers/Durable Objects as a potential optimization for regional chat server placement to minimize chat latency for geographically distributed audiences.

The separation is clean: the CDN handles the **media plane** (audio segments, immutable, cacheable, high-throughput), and the WebSocket layer handles the **control plane** (chat messages, presence, signaling, ephemeral, low-latency, stateful). This decoupling allows each to scale independently — the CDN scales to millions of concurrent listeners via edge caching, while the WebSocket layer scales to hundreds of thousands of concurrent connections via horizontal gateway scaling.

#### Token-Signed URLs for Access Control

For paid or private streams, access control is enforced via **token-signed URLs**. The application server generates a signed URL after verifying the user's entitlement (subscription, payment, or authorization), and the CDN validates the signature before serving content.

[CloudFront signed URLs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html) support two policy types:

- **Canned policy**: Simple expiration-based restriction. The URL includes a base64-encoded policy with a start and end time. Cannot restrict by IP or specify a start time.
- **Custom policy**: Supports expiration, start time, IP address range restrictions, and wildcard resource matching. More flexible but produces longer URLs.

The signing process uses RSA 2048 or ECDSA 256 key pairs. The application holds the private key; CloudFront holds the public key (via a trusted key group). When a user requests a stream, the application verifies entitlement, generates a signed URL with an appropriate expiration (typically 5–15 minutes for live streams, longer for VOD), and returns it to the client. CloudFront validates the signature and policy at request time — if the URL has expired or been tampered with, the request is rejected with HTTP 403.

For HLS, the signed URL is typically applied to the **playlist URL** (`.m3u8`), not individual segments. This means the player must re-request the playlist on each refresh, and each request must carry a valid signature. Some CDNs support **signed cookies** as an alternative, which are better for HLS because the cookie is sent automatically with every segment request without requiring per-segment URL signing. The trade-off is that signed cookies are less granular — they grant access to all content matching the cookie's resource pattern, whereas signed URLs can restrict to a specific stream.

For a multi-CDN strategy, token-signed URLs must be generated per-CDN (CloudFront signed URLs are not interchangeable with Cloudflare's access tokens). A BFF layer can abstract this by generating the appropriate signed URL based on which CDN the client is routed to, using the user's session token as the entitlement check.

#### WebRTC and CDN Caching

WebRTC media cannot be cached by a traditional CDN. WebRTC is inherently peer-to-peer or SFU-relayed — media flows over UDP (or TCP fallback) through DTLS/SRTP-encrypted connections that are established via SDP offer/answer signaling, not through HTTP segment requests. There are no immutable, cacheable objects to store at the edge. This is a fundamental architectural difference from HLS delivery.

For the WebRTC ultra-low-latency path (S3.1), the SFU *is* the edge — it relays media directly to each connected client. The only CDN-relevant component for WebRTC is the **TURN/STUN relay server**, which handles NAT traversal for clients behind restrictive firewalls. TURN servers relay media traffic and can be co-located with CDN PoPs for lower latency, but they do not cache content. The SFU-to-HLS bridge (LiveKit Egress, FFmpeg) is the mechanism by which WebRTC media enters the CDN cacheable path — the bridge transcodes the WebRTC stream to HLS segments, which are then distributed through the standard CDN caching hierarchy described above.

#### Summary of Recommendations

1. **Deploy an origin shield** in the same region as the media origin. This is the single highest-ROI infrastructure change — it reduces origin egress by 90–99% and is available on all major CDNs at no additional cost.
2. **Set cache TTLs differentially**: playlists at 0–2s (`max-age=0, must-revalidate`), segments at 30–60s (immutable, long TTL). For LL-HLS, partial segments at 1–2s.
3. **Enable request collapsing** on all cache tiers. This is default on CloudFront, Cloudflare, Fastly, and Akamai, but verify it is active for streaming-marked properties.
4. **Use a dual-CDN strategy**: CloudFront for primary delivery (AWS integration, broad PoP coverage) and Cloudflare for cost-sensitive high-volume traffic (unmetered egress). This provides both cost optimization and redundancy.
5. **Keep chat on a dedicated WebSocket path**, not the CDN media path. Consider Cloudflare Durable Objects for regional chat server placement to minimize latency.
6. **Implement token-signed URLs** (CloudFront signed URLs or signed cookies) for access control on paid/private streams, with a BFF layer abstracting per-CDN signing.
7. **Model cost per user-hour**, not monthly totals. At 100k concurrent listeners and 96 kbps average bitrate, egress alone costs $22–$490/hour depending on CDN choice — the CDN decision is the single largest cost lever in the architecture.

## Live Chat Subsystem

### Real-Time Messaging Architecture: WebSocket Gateway & Message Fanout

#### Transport Layer Selection

The transport decision shapes every downstream architectural choice. Four candidates exist for real-time chat delivery:

| Transport | Direction | Protocol | Key Limitation |
|---|---|---|---|
| **WebSocket** ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)) | Full-duplex | TCP (ws/wss) | Stateful; firewall traversal issues |
| **Server-Sent Events (SSE)** | Server→Client only | HTTP | 6 concurrent connections per browser; UTF-8 only; no client→server push |
| **HTTP long-polling** | Simulated duplex | HTTP | High overhead per "connection"; latency from poll intervals; server resource waste |
| **WebRTC DataChannel** | Full-duplex | SCTP (UDP) | Designed for P2P media data; requires signaling server; no native server-push fanout |

**WebSocket is the standard for bidirectional chat**, and the justification is direct: chat requires the server to push messages to clients the instant they arrive (server→client) while simultaneously accepting user input on the same connection (client→server). After the initial HTTP upgrade handshake, the persistent connection eliminates per-message HTTP header overhead and enables sub-100ms delivery latency. [WebSocket provides full-duplex, low-overhead communication with near-universal browser support](https://ably.com/blog/websockets-vs-sse).

SSE is eliminated for interactive chat because it is strictly unidirectional—[server-to-client only](https://ably.com/topic/websocket-architecture-best-practices). A user could not send a message over an SSE connection; a separate HTTP POST round-trip would be required per sent message, adding latency and complexity. Additionally, [browsers limit SSE to ~6 concurrent connections per domain](https://ably.com/blog/websockets-vs-sse), which is untenable for a multi-room chat interface. SSE remains viable for one-way notification feeds (e.g., system announcements, viewer count ticks), but not for the primary chat path.

HTTP long-polling is a legacy workaround that introduces polling latency (typically 1–5s) and wastes server resources on connection setup/teardown. It is unacceptable for a synchronized chat experience where messages must appear within 200–500ms.

WebRTC DataChannel operates over SCTP and is[P primarily designed for peer-to-peer data exchange alongside media streams](https://getstream.io/blog/webrtc-websockets/). While technically capable of carrying chat messages, it requires a dedicated signaling server (SDP offer/answer, ICE negotiation) and[P lacks a native server-side fanout mechanism](https://getstream.io/blog/webrtc-websockets/)—every recipient would need a separate DataChannel connection, reintroducing the N-squared problem that SFU-based delivery solves for media. [WebRTC vs WebSocket analysis confirms WebSocket is the better choice for server-relayed chat messaging](https://getstream.io/blog/webrtc-websockets/).

**Design decision: WebSocket (wss://) is the primary transport, with HTTP long-polling as a fallback** for corporate firewall environments that block WebSocket upgrades (notably Sophos XG, WatchGuard, and McAfee Web Gateway, [per Ably's WebSocket disadvantages analysis](https://ably.com/blog/websockets-vs-sse)). Libraries like [Socket.IO provide automatic fallback](https://socket.io/) from WebSocket to long-polling, but the additional abstraction layer and client-side lock-in risk must be weighed against raw `ws` library usage.

#### Fanout Architecture: Pub/Sub with Stateless Gateways

The core architectural pattern is **publish/subscribe with stateless WebSocket gateways**. When a user sends a message in a room, the chat service publishes the message to a channel (e.g., `room:{roomId}:chat`) on a message broker. All WebSocket gateway nodes subscribed to that channel receive the message and push it to their locally connected clients.

This design makes WebSocket servers **stateless**: any gateway can serve any client because message routing is delegated to the broker, not tracked locally. This is the fundamental enabler of horizontal scaling—[adding or removing gateway nodes requires no session migration](https://ably.com/topic/websocket-architecture-best-practices).

The message flow is:

1. **Client A** sends a chat message over its WebSocket to **Gateway 1**.
2. **Gateway 1** (or a fronting chat service) validates the message (auth, rate limit, moderation check), then publishes it to Redis Pub/Sub channel `room:abc123:chat`.
3. **Gateways 1, 2, 3, … N**—all subscribed to `room:abc123:chat`—receive the message from Redis.
4. Each gateway pushes the message to its locally connected clients subscribed to that room.
5. **Client B** (on Gateway 3) receives the message with sub-200ms end-to-end latency.

[The WebSocket + Redis pub/sub pattern is well-documented with code examples](https://ably.com/blog/scaling-pub-sub-with-websockets-and-redis): a Node.js server using the `ws` library subscribes to Redis channels and forwards messages to connected WebSocket clients, with NGINX or AWS ALB distributing connections across instances.

#### Message Broker Selection

The broker choice determines delivery semantics, durability, and scaling ceiling:

| Broker | Delivery Semantics | Durability | Best For | Scaling Limit |
|---|---|---|---|---|
| **Redis Pub/Sub** | At-most-once (ephemeral) | None (messages dropped if no subscriber) | Low-latency ephemeral chat where occasional loss is acceptable | Single node ~100K msg/s; Cluster for horizontal scale |
| **NATS (core)** | At-most-once | None | Lightweight ephemeral fanout | Very high throughput, minimal overhead |
| **NATS JetStream** | At-least-once (configurable) | Yes (persistent streams) | Chat requiring replay on reconnect | Horizontal scale with consumer groups |
| **Apache Kafka** | At-least-once (consumer groups) | Yes (durable log) | Audited chat, analytics integration, consumer replay | Millions msg/s; higher operational complexity |

[Redis Pub/Sub provides at-most-once delivery semantics](https://redis.io/docs/latest/develop/pubsub/)—if a subscriber is disconnected when a message is published, that message is permanently lost. For interactive live chat where users are expected to maintain persistent connections, this is acceptable for the hot path: the real-time experience is the product, and a dropped message during a brief reconnection is tolerable (especially since [chat history can be replayed from a durable store on reconnect](https://systemdesignschool.io/problems/chatapp/solution)).

**Recommendation: Redis Pub/Sub as the primary broker for real-time fanout, with a synchronized write to a durable store (Redis Streams or PostgreSQL) for history and replay.** This dual-path approach—ephemeral pub/sub for live delivery, persistent store for recovery—is the [canonical pattern for real-time chat at scale](https://systemdesignschool.io/problems/chatapp/solution). Redis Pub/Sub's [sharded Pub/Sub (Redis 7.0+)](https://redis.io/docs/latest/develop/pubsub/) helps scale in cluster mode by restricting message propagation within a shard rather than broadcasting to every node, reducing cluster bus traffic.

If the system requires guaranteed at-least-once delivery (e.g., for moderation audit trails or paid-stream access logs), [NATS JetStream provides persistence and replay](https://dev.to/young_gao/pubsub-messaging-patterns-redis-nats-and-when-to-use-what-2el2) with lower operational overhead than Kafka. Kafka becomes warranted when chat events must feed an analytics pipeline (Flix, Flink) for real-time QoE monitoring, or when replay-based offline delivery is a hard requirement. [NATS and Kafka comparison confirms Kafka's durability advantage but higher complexity](https://www.synadia.com/blog/nats-and-kafka-compared).

#### Channel Structure and Lifecycle

Channels are structured as **per-room topics**: `room:{roomId}:chat`. This naming convention provides natural isolation—only gateways and clients interested in a specific room subscribe to that channel. Channel lifecycle is tied to room lifecycle:

- **Channel creation**: Implicit—the first publish to a channel creates it in Redis. No explicit provisioning needed.
- **Channel subscription**: When a client joins a room, the gateway subscribes to that room's channel. When the last local subscriber leaves, the gateway unsubscribes and the Redis connection is cleaned up. [The implementation pattern tracks channel subscribers in a Map and cleans up Redis clients when subscriber count reaches zero](https://ably.com/blog/scaling-pub-sub-with-websockets-and-redis).
- **Channel teardown**: When a room is deleted, gateways stop receiving messages (publishers stop), and subscriptions naturally expire.

For very large streams (100K+ concurrent listeners), a single Redis channel can become a bottleneck because every gateway node must process every message. The mitigation is **channel partitioning**: split `room:{roomId}:chat` into `room:{roomId}:chat:shard:N` where N is determined by consistent hashing of the client's user ID. Each gateway subscribes only to the shards its connected clients require. [Scaling Redis Pub/Sub to millions of channels requires sharding across multiple Redis instances](https://centrifugal.dev/blog/2026/06/29/scaling-redis-pub-sub).

#### Fanout on Write vs. Fanout on Read

Two delivery models exist for group messaging:

- **Fanout on write**: When a message is sent, the system pushes it to all connected members immediately (N deliveries for N online recipients). Reads are trivial—messages arrive in the client's WebSocket buffer. This is the standard for chat.
- **Fanout on read**: Messages are stored in a shared log per conversation; clients pull/replay on demand. Writes are cheap (one write), but reads require a fetch round-trip.

[Small groups should fan out on write](https://systemdesignschool.io/problems/chatapp/solution): one message becomes N deliveries, which is cheap for rooms with hundreds of participants. For very large audiences (10K+ concurrent chatters in a single room), the write-amplification becomes problematic—one message from a popular broadcaster might trigger 10,000 pushes. In this regime, a hybrid is warranted: push to online members via WebSocket, store to the durable log, and let late joiners or reconnecting clients pull from the log.

[The system design pattern confirms: "Small groups fan out on write cheaply; very large groups favor a shared log the members read."](https://systemdesignschool.io/problems/chatapp/solution) For the target scale of 10k–100k concurrent listeners per stream, fanout on write via Redis Pub/Sub is appropriate because chat density per user is typically low (a few messages per minute per user), keeping total message throughput manageable.

#### Connection Scaling: Handling 100K+ Concurrent Connections

A single WebSocket gateway server can handle substantial connection counts, but the limits are about message throughput, not connection count:

- **Idle connections**: A properly tuned Linux server handles [500K+ idle WebSocket connections](https://websocket.org/guides/connection-limits/), with memory of roughly [2–10 KB per idle connection](https://websocket.org/guides/connection-limits/) depending on framework and buffer sizes. At 500K connections × 5 KB, that is ~2.5 GB of connection state alone.
- **Active connections**: Connections with pending messages jump to [10–100 KB each](https://websocket.org/guides/connection-limits/) due to serialization buffers, application state, and kernel socket buffers.
- **Real bottleneck—connection churn**: [The actual limit is not connection count but connection rate](https://websocket.org/guides/connection-limits/). Each new WebSocket connection requires a TCP handshake (1 RTT), TLS negotiation (1–2 RTTs, with CPU-intensive RSA/ECDHE key exchange), and HTTP upgrade. [RSA-2048 handshakes cost ~1–5 ms of CPU each; a server handles roughly 1,000–3,000 TLS handshakes per second per core](https://websocket.org/guides/connection-limits/). At 10,000 new connections per second, that is 10–50 seconds of CPU time per second—the server stalls.

**Scaling targets for the system**: At 100K concurrent listeners with, say, 20% active chatters (20K active connections), a single gateway handling 50K connections can manage it. But when all 100K are active chatters (e.g., during a viral moment with emoji bursts), the gateways must be horizontally scaled.

**Horizontal scaling strategy**: Deploy a fleet of stateless WebSocket gateway pods behind a load balancer. The load balancer distributes connections using least-connections or consistent hashing. Because gateways are stateless (message routing via Redis Pub/Sub), [a client can reconnect to any gateway without session migration](https://ably.com/topic/websocket-architecture-best-practices). [Past ~100K active connections or 50K messages/sec on a single server, horizontal scaling with a pub/sub backplane becomes the only viable path](https://websocket.org/guides/connection-limits/).

**Thundering herd mitigation**: When a gateway restarts or a network blip disconnects 100K clients, the simultaneous reconnection storm is worse than the original failure. Mitigations include: [exponential backoff with random jitter on the client side](https://websocket.org/guides/connection-limits/) (spreading reconnections over 10–30 seconds), [server-side connection rate limiting](https://websocket.org/guides/connection-limits/) (rejecting excess connections with WebSocket close code 1013 "try again later"), and [rolling deploys with connection draining](https://websocket.org/guides/connection-limits/) (stop accepting new connections on old instances, grant 30-second grace period, then shut down).

#### Load Balancing and Sticky Sessions

WebSocket connections are stateful, which complicates load balancing. Two approaches exist:

1. **Sticky sessions (connection affinity)**: The load balancer ensures a client always connects to the same backend server. This simplifies server-side state management but [introduces hot spots, single points of failure, and uneven load distribution](https://ably.com/topic/websocket-architecture-best-practices). If the sticky server goes down, clients lose their session and must resynchronize.

2. **Stateless with pub/sub backplane**: [Any gateway can serve any client](https://ably.com/blog/scaling-pub-sub-with-websockets-and-redis). Message routing is externalized to Redis Pub/Sub. This is the recommended approach for this system.

**Load balancers that support WebSocket-aware routing**: [NGINX](https://nginx.org/) (with `proxy_http_version 1.1` and `Upgrade`/`Connection` headers), [HAProxy](https://www.haproxy.com/) (with `http-check` and WebSocket upgrade support), [AWS ALB/NLB](https://aws.amazon.com/elasticloadbalancing/) (ALB supports WebSocket natively; NLB at Layer 4), and [Envoy](https://www.envoyproxy.io/) (native WebSocket support with `upgrade_configs`). [NGINX WebSocket configuration requires specific proxy headers for upgrade handling](https://abcdocker.github.io/2021/11/07/how-to-reverse-proxy-websockets-with-nginx/).

For the stateless approach, **round-robin or least-connections distribution** is sufficient. [Consistent hashing based on user ID can reduce rebalancing churn](https://ably.com/topic/when-and-how-to-load-balance-websockets-at-scale) but is not required. Health-aware load balancing should track actual load (CPU, message rate), not just process liveness, to avoid routing to servers near capacity.

#### Message Format and Protocol

Chat messages follow a JSON schema typed by `message_type`:

```json
{
  "messageId": "uuid-v4",
  "roomId": "abc123",
  "type": "chat_message",
  "authorId": "user:456",
  "authorName": "display_name",
  "body": "Hello world!",
  "timestamp": "2026-01-15T10:30:00.000Z",
  "clientMsgId": "client-generated-uuid",
  "replyTo": null,
  "mentions": []
}
```

**Message types**:

| Type | Description | Source |
|---|---|---|
| `chat_message` | User text message | Client send |
| `system_message` | Room lifecycle events (stream started/ended, user joined/left) | Server-generated |
| `moderation_action` | Message deleted, user timed out, user banned | Moderator action |
| `presence_update` | Online/offline status change, viewer count | Server-generated |

[The message schema includes `clientMsgId` for deduplication and `serverSeq` for ordering](https://systemdesignschool.io/problems/chatapp/solution). Every message carries a unique message ID for idempotency; the server assigns a monotonic `serverSeq` per room at persist time, and [clients sort and deduplicate by it](https://systemdesignschool.io/problems/chatapp/solution). This gives [per-conversation ordering without a global clock](https://systemdesignschool.io/problems/chatapp/solution), which is sufficient because global cross-room ordering is neither needed nor affordable.

#### Ordering and Delivery Guarantees

Message delivery semantics:

- **Redis Pub/Sub default: at-most-once**. Messages are delivered once if at all; if a subscriber is disconnected, the message is [permanently lost](https://redis.io/docs/latest/develop/pubsub/).
- **Practical standard: at-least-once with client deduplication**. The `clientMsgId` field enables [deduplication at the client](https://systemdesignschool.io/problems/chatapp/solution): the client tracks recently-seen IDs and discards duplicates. The guarantee is at-least-once because network retries can deliver duplicates, but [true exactly-once delivery is expensive and rarely worth it](https://bravenewgeek.com/you-cannot-have-exactly-once-delivery/).

The system adopts **at-least-once with per-room ordering via `serverSeq`**. When the server persists a message, it assigns a monotonic `server_seq` for the room. [Clients sort messages by `server_seq` and deduplicate by `clientMsgId`](https://systemdesignschool.io/problems/chatapp/solution). WebSocket's TCP transport guarantees in-order delivery on a single connection. If a client disconnects and reconnects, the server replays missed messages from the durable store using a `sync` API: `sync(roomId, sinceSeq)` returns all messages after the specified sequence.

[The canonical API design for chat uses four operations](https://systemdesignschool.io/problems/chatapp/solution): `connect()`, `send(conversationId, clientMsgId, body)`, `sync(conversationId, sinceSeq)`, and `ack(conversationId, upToSeq)`. This provides the full lifecycle: connect establishes the WebSocket, send transmits with dedup ID, sync replays missed messages on reconnect, and ack confirms receipt.

#### WebRTC Signaling vs. Chat WebSocket

The WebRTC signaling channel (SDP offer/answer, ICE candidate exchange for media session establishment) is **separate** from the chat WebSocket. The reasons are architectural:

1. **Different lifecycles**: WebRTC signaling is transient—it occurs only during session setup and renegotiation. Chat is persistent, lasting the entire time a user is in a room.
2. **Different reliability requirements**: Signaling requires reliable, ordered delivery (ICE candidates must arrive in order). Chat is more tolerant—a dropped chat message is less disruptive than a dropped ICE candidate, which could fail the entire media connection.
3. **Different scaling characteristics**: Signaling is bursty and short-lived; chat is continuous. Sharing a connection would cause chat message bursts to interfere with signaling latency.
4. **Different authentication**: WebRTC signaling authenticates the broadcaster/listener role for media; chat authenticates the user identity for messaging.

[WebRTC's lack of a standard signaling protocol means developers implement custom solutions](https://getstream.io/blog/webrtc-websockets/), and coupling that custom signaling to the chat transport would compound complexity. Separate WebSocket connections—one for signaling (short-lived, transacted during session setup), one for chat (long-lived, persistent for the room duration)—is the clean separation. A typical client opens the signaling WebSocket only when initiating or accepting a media connection, then closes it after ICE completion; the chat WebSocket remains open throughout the room session.

#### Mobile Push Notification Fallback

When a mobile app enters the background, the OS terminates the WebSocket connection (iOS suspends network activity for backgrounded apps; Android's Doze mode and App Standby kill background connections). A push notification fallback is therefore required: the server detects the disconnect via heartbeat timeout and routes subsequent messages through APNs (iOS) or FCM (Android) until the client reconnects. The full APNs/FCM integration details—including payload constraints, rate limits, connection keep-alive, and reconnection backoff—are specified in S5.2.

#### Authentication and Integration with Room/Session Service

The chat system integrates with the room/session service for three concerns:

1. **Connection authentication**: When a WebSocket connection is established, the client presents a JWT or session token. The gateway validates the token (signature check, expiry) and extracts the user ID and room ID. The room service confirms the user is authorized to join the room (e.g., room exists, user is not banned, room is not private-whitelisted).

2. **Message authorization**: Before publishing a message, the chat service checks the user's role in the room (broadcaster, moderator, viewer) against the requested action (send message, delete message, ban user). Slow mode and follower-only mode are enforced server-side by checking timestamps against room configuration fetched from the room service.

3. **Stream event synchronization**: System messages (stream started, stream ended, viewer count updates) are generated by the stream/room service and published to the chat channel as `system_message` and `presence_update` types, ensuring chat and audio stay synchronized—e.g., a "stream ended" message in chat corresponds to the actual stream termination event from the media pipeline.

[The WebSocket servers remain stateless by delegating auth to the token and authorization to the room service](https://ably.com/blog/scaling-pub-sub-with-websockets-and-redis), meaning any gateway can serve any client without maintaining per-user session state. The room service is the single source of truth for room membership and permissions.

### Chat Features, Moderation & Persistence

#### Feature Set and Technical Implications

The chat subsystem must support a feature set comparable to Twitch and Discord livestream chat: plain text messages, emoji reactions, message threading/replies, @mentions, slow mode, follower-only mode, and moderator actions (delete, timeout, ban). Each feature carries distinct technical implications for the fanout pipeline, persistence layer, and client rendering.

**Text messages** are the baseline: a JSON envelope containing `message_id` (Snowflake or UUIDv7 for time-sortability), `room_id`, `author_id`, `body`, `timestamp`, and optional `reply_to` field. The message schema must be version-tolerant—new fields (e.g., `mentions`, `emote_references`) should be ignorable by older clients to support schema evolution without breaking compatibility. Protocol Buffers offer the strongest backward/forward compatibility guarantees, but JSON with a `version` field is pragmatically sufficient for a medium-sized team and easier to debug in production. MessagePack is a middle ground: binary-encoded, ~30% smaller than JSON, with native libraries across browser and mobile.

**Emoji and reactions** deserve special architectural treatment. Unlike text messages, which are displayed individually, reactions are *aggregated*—a single emoji type (e.g., ❤️) sent by 5,000 users in a 2-second burst should render as a floating animation with a counter, not 5,000 individual chat lines. The system must distinguish between two message types: `chat_message` (persisted, displayed in scrollback) and `reaction_event` (ephemeral, aggregated client-side or server-side). Reaction events can be batched server-side: the fanout pipeline aggregates reactions by `(room_id, emoji_type)` over a 100–250ms window and emits a single `reaction_burst` event containing the emoji type and delta count. This reduces fanout load by orders of magnitude during viral moments. The [system design for real-time emoji broadcast](https://yschooloftech.substack.com/p/system-design-of-real-time-emoji) at 10M concurrent users confirms that not every individual reaction needs to be shown to every user—a representative subset broadcast globally is sufficient, and aggregation is the standard approach.

**Message threading/replies** require a `reply_to` field referencing the parent `message_id`. The server must validate that the parent message exists and is not deleted. Threaded replies are persisted as normal messages with the `reply_to` pointer; the client renders them as indented sub-conversations. This adds a read-path cost (fetching the parent message for context) but no special fanout handling.

**@mentions** are parsed server-side from the message body using a regex pattern (e.g., `@(\w+)`). When a mention is detected, the server emits a separate `mention_notification` event to the mentioned user's WebSocket connection (or push notification if offline). This requires a user-id-to-connection mapping, maintained in Redis as a hash of `user_id → [connection_ids]`.

**Slow mode** is a per-room rate limit that restricts how often individual users can send messages. The server maintains a per-user, per-room timestamp of the last sent message. When a new message arrives, the server checks `now - last_sent < cooldown_interval`; if the interval has not elapsed, the message is rejected with a `rate_limited` error and the client displays a countdown timer. [GetStream's slow mode documentation](https://getstream.io/chat/docs/react/slow-mode/) confirms the pattern: a configurable cooldown interval (e.g., 5s, 30s, 60s) enforced server-side, with the client receiving the cooldown duration in the error response. The implementation is a simple Redis key `slowmode:{room_id}:{user_id}` with a TTL equal to the cooldown interval—if the key exists, the user is throttled.

**Follower-only mode** is a per-room access control that restricts messaging to users who have followed the broadcaster for a minimum duration (e.g., 10 minutes). The server checks the user's follow timestamp against the room's `follower_only_minutes` setting before accepting the message. This is a read-path check against the user service or a cached follow record in Redis.

**Moderator actions** (delete, timeout, ban) must propagate to all connected clients in real time. When a moderator deletes a message, the server publishes a `moderation_action` event to the room's chat channel with the action type and target `message_id`. All clients receiving this event remove the message from their local state. For timeouts, the server sets a Redis key `timeout:{room_id}:{user_id}` with a TTL equal to the timeout duration; any message from that user during the TTL is rejected. Bans are persisted in the database and checked at message ingestion time. The key design principle is that moderation actions are *chat messages of a different type*—they flow through the same fanout pipeline as regular messages, ensuring all clients receive them with the same latency guarantees.

#### Moderation Pipeline

The moderation pipeline operates in three tiers, each with distinct latency, cost, and accuracy trade-offs:

**Tier 1 — Client-side filtering** is the first line of defense. The client strips or masks obvious profanity before transmission. This is purely a UX optimization (reducing server load for the most common cases) and provides no security guarantee—any client can bypass it. It is not a substitute for server-side moderation.

**Tier 2 — Server-side keyword filtering** is the mandatory baseline. The server maintains a banned-word list (stored in Redis for O(1) lookup) and applies regex patterns to each incoming message before fanout. Messages matching a banned pattern are either rejected (with a `moderation_rejected` error to the sender) or masked (replaced with `***` and flagged for review). The banned-word list is room-specific (broadcasters can customize) and globally updated by the platform. Regex patterns handle leetspeak variants (e.g., `h3ll0` for `hello`). This tier adds <1ms latency per message and is sufficient for the majority of moderation needs.

**Tier 3 — AI-based toxicity detection** is optional and applied selectively. Three services are relevant in 2025–2026:

| Service | Type | Latency | Cost | Notes |
|---|---|---|---|---|
| [Perspective API](https://aisecurityandsafety.org/en/compare/perspective-api-vs-openai-moderation-api/) | Toxicity scoring | ~100–300ms | Free | Google's Jigsaw team; **sunsetting December 2026** per [Lasso Moderation](https://www.lassomoderation.com/blog/perspective-api/) |
| [OpenAI Moderation API](https://aisecurityandsafety.org/en/compare/perspective-api-vs-openai-moderation-api/) | Content classification | ~50–200ms | Free | Returns category flags (hate, harassment, self-harm, etc.); no custom model training |
| [Azure Content Moderator](https://azure.microsoft.com/en-us/pricing/details/cognitive-services/content-moderator/) | Content classification | ~100–500ms | Per-transaction pricing | Supports custom blacklists; part of Azure Cognitive Services |

The trade-off is clear: AI moderation adds 50–500ms latency per message and incurs per-request cost, but catches contextual toxicity that keyword filters miss (e.g., veiled threats, dog whistles). The recommended approach is a **two-pass architecture**: pass all messages through Tier 2 (keyword filter) synchronously; for messages that pass, optionally send to Tier 3 (AI moderation) asynchronously. If Tier 3 flags a message that was already fanned out, a `moderation_action` delete event is published to the room. This "moderate-after-publish" pattern keeps chat latency low while still catching toxic content within a 1–3 second window. For high-risk rooms (e.g., unmoderated new streams), Tier 3 can be applied synchronously before fanout, accepting the latency cost.

**LiveKit Agents as a platform-native AI path.** If the system adopts LiveKit for the WebRTC delivery path (as recommended in S3.2), [LiveKit Agents](https://docs.livekit.io/agents/) provides a natural integration point for AI-powered moderation and voice-agent scenarios. LiveKit Agents is an open-source framework (Apache 2.0) that reached [1.0 in April 2025](https://docs.livekit.io/reference/migration-guides/v0-migration/python/), with the Python SDK at [1.5.x as of April 2026](https://www.forasoft.com/learn/livekit-for-ai-agents-guide) featuring adaptive interruption handling and native [Model Context Protocol (MCP)](https://docs.livekit.io/agents/logic/tools/mcp/) tool support. An agent joins a LiveKit room as a participant, subscribes to audio tracks, and runs a streaming STT → LLM → TTS pipeline. For moderation, an agent could transcribe broadcaster audio in real time, run toxicity detection on the transcript, and emit moderation events back to the room via the data channel. For voice-agent scenarios (e.g., an AI co-host that responds to listener questions), the same pipeline applies TTS output back into the room. The [Fora Soft production guide](https://www.forasoft.com/learn/livekit-for-ai-agents-guide) reports that end-to-end latency for a cascaded STT → LLM → TTS pipeline sits at a production median of 1.4–1.7 seconds (P99 at 3–5s), with sub-500ms achievable with disciplined streaming. This is acceptable for post-publish moderation but too slow for synchronous pre-fanout filtering. LiveKit Agents is therefore positioned as a *complementary* moderation layer, not a replacement for the keyword filter.

#### Rate Limiting

Rate limiting operates at two levels: per-user and per-room.

**Per-user rate limiting** uses a token bucket algorithm. Each user has a bucket with a configurable capacity (e.g., 5 messages) and refill rate (e.g., 1 message per 2 seconds). The bucket is stored in Redis as `ratelimit:user:{user_id}` with tokens as the value and a TTL. When a message arrives, the server atomically decrements the token count; if the count is zero, the message is rejected. The token bucket allows short bursts (e.g., 5 messages in 2 seconds) while enforcing a steady-state rate, which is more user-friendly than a fixed-window counter that resets abruptly. [ByteByteGo's rate limiter design](https://bytebytego.com/courses/system-design-interview/design-a-rate-limiter) and the [Arcjet rate limiting guide](https://arcjet.com/learn/rate-limiting-guide) confirm the token bucket as the standard for chat applications.

**Per-room rate limiting** uses a sliding window log to prevent any single room from overwhelming the fanout pipeline. The server tracks message timestamps per room in a Redis sorted set (`ratelimit:room:{room_id}`), pruning entries older than the window (e.g., 10 seconds). If the count exceeds a threshold (e.g., 100 messages per 10 seconds), the room enters a throttled state where messages are queued and released at a controlled rate. This protects the WebSocket gateway cluster from being overwhelmed by a viral stream's chat activity.

#### Chat-Streaming Platform Integration

Chat is not a standalone feature—it is tightly coupled to the streaming experience. The integration points are:

1. **Chat overlay on the audio player**: The chat UI renders as a translucent overlay on the audio player component. Messages appear with a timestamp aligned to the stream's playback position. Since the audio stream has a known latency (2–4s for LL-HLS, 0.5–1.3s for WebRTC), chat messages are timestamped with the *stream time* (the audio playback position at which the message was sent), not wall-clock time. This ensures that a message sent at "0:30 into the stream" appears at the 0:30 mark for all listeners, regardless of their individual buffering latency. The client maintains a mapping between wall-clock time and stream time, adjusted by the player's current latency.

2. **Chat-triggered stream events**: Certain chat actions can trigger events on the audio stream. For example, a "hype train" (sustained high-rate emoji reactions) could trigger a visual effect on the broadcaster's overlay or a sound effect played through the audio pipeline. These events flow through the same pub/sub channel as chat messages but are typed as `stream_event` and consumed by the broadcaster's client.

3. **Shared room/session identity**: The chat room ID and the stream session ID are the same identifier. When a user joins a stream, they simultaneously open a WebSocket connection to the chat channel `room:{roomId}:chat` and an audio connection (HLS or WebRTC). The room/session service (S1.1) is the coordination point that validates the user's access to both the audio stream and the chat channel using the same authorization token.

#### Message Persistence

Chat message persistence must balance write throughput, read latency for late joiners, and storage cost. Three storage options are evaluated:

**Redis Streams** is the recommended primary store for hot chat history. Each room's messages are appended to a Redis Stream keyed `chat:{room_id}`. Redis Streams provides an append-only log with unique time-ordered IDs, consumer groups for distributed processing, and the ability to trim old entries with `XTRIM` or `MAXLEN`. [Redis Streams documentation](https://redis.io/docs/latest/develop/data-types/streams/) confirms O(1) append and O(M) range queries where M is the number of returned messages. A late joiner retrieves the last N messages via `XRANGE` with a count limit. Redis Streams supports TTL-based expiration via `EXPIRE` on the stream key, automatically deleting chat history after a configurable retention period (e.g., 24 hours). The [Reddit discussion on Redis Streams for chat](https://www.reddit.com/r/cpp/comments/1u13p31/why_we_put_chat_messages_in_redis_streams_and/) highlights the key advantage: "Redis assigns each entry a unique, time-ordered ID, so you get message ordering and cursor-based pagination for free. No schema migrations." The limitation is that Redis Streams is in-memory; for 100k concurrent rooms with high message rates, memory cost can be significant. Trimming to the last 1,000 messages per room bounds memory usage.

**Cassandra/ScyllaDB** is the recommended store for long-term chat history and analytics. [Discord's engineering blog](https://discord.com/blog/how-discord-stores-trillions-of-messages) details their migration from Cassandra to ScyllaDB for message storage, using a schema partitioned by `(channel_id, bucket)` where bucket is a static time window. This partitioning strategy avoids hot-partition issues that plague naive single-channel partitioning. ScyllaDB (a C++ rewrite of Cassandra with better performance) is the preferred choice for new deployments. Messages are written with a TTL (e.g., 30 days) for automatic expiration. The [ScyllaDB blog on streaming chat messages](https://www.scylladb.com/2022/04/25/streaming-real-time-chat-messages-into-scylladb-with-apache-pulsar/) demonstrates the pattern of streaming messages from a message bus (Pulsar/Kafka) into ScyllaDB for persistent storage. The trade-off: Cassandra/ScyllaDB has higher write latency (~5–10ms vs. <1ms for Redis) but much lower cost at petabyte scale and built-in TTL.

**PostgreSQL with pg_partman** is a viable alternative for smaller-scale deployments. Messages are stored in a partitioned table with time-based partitions (e.g., daily). The `pg_partman` extension automates partition creation and dropping old partitions. This approach is simpler to operate than Cassandra/ScyllaDB but does not scale to the same write throughput. It is appropriate for the 1k–10k concurrent listener range but becomes a bottleneck at 100k+.

**Recommended hybrid approach**: Redis Streams for hot history (last 1,000 messages per room, 24-hour TTL) + ScyllaDB for long-term storage (30-day TTL). Messages are written to Redis Streams synchronously on send (write-through), then asynchronously batch-written to ScyllaDB every 5–10 seconds. Late joiners read from Redis Streams first (sub-millisecond latency); if they need older history, they query ScyllaDB. The consistency implication is that there is a 5–10 second window where a message is in Redis but not yet in ScyllaDB—acceptable for chat, where eventual consistency is the norm.

#### Presence Tracking

Presence (online/offline status and viewer count) is tracked using Redis data structures:

- **Viewer count**: Redis HyperLogLog (`PFADD room:{roomId}:viewers {user_id}`) provides an approximate count of unique viewers with a standard error of 0.81% and a fixed memory footprint of 12KB per key, regardless of cardinality. [Redis HyperLogLog documentation](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/) confirms this. For 100k concurrent viewers, the approximate count is sufficient—exact counts are not needed for display purposes. For exact counts (e.g., for analytics), a Redis Set (`SADD room:{roomId}:viewers {user_id}`) can be maintained in parallel, but this requires O(N) memory and is only recommended for smaller rooms.

- **Online/offline status**: When a user connects, their `user_id` is added to a Redis Set for the room. When they disconnect, it is removed. The set cardinality gives the exact online count. For global presence (across all rooms), a Redis key `presence:{user_id}` with a TTL (e.g., 30 seconds) is set on heartbeat; if the key exists, the user is online. The TTL is refreshed by the client every 10–15 seconds. If the key expires, the user is considered offline.

- **Connection draining**: When a WebSocket server shuts down (e.g., during a rolling update), it must not abruptly close connections. The server sends a `server_shutdown` event to all connected clients, which triggers the client to reconnect to another server. The server then waits for clients to disconnect naturally (with a grace period of 30–60 seconds) before terminating. This is implemented via Kubernetes `preStop` hooks and `terminationGracePeriodSeconds`.

#### Message Bus Selection

Redis Pub/Sub is the recommended primary broker for real-time chat fanout, providing at-most-once delivery with sub-millisecond latency. As the system scales beyond a single Redis node, the message bus must evolve to Redis Cluster (10k–100k concurrent listeners) or Apache Kafka (100k+ or when durability is required). The full message broker selection analysis—including delivery semantics, durability trade-offs, NATS as a lightweight alternative, and the decision matrix for each scale tier—is covered in S4.1.

#### Data Retention and GDPR

Chat messages and stream recordings are personal data under GDPR when they contain user-generated content linked to an identifiable user. The full data retention policy—including retention periods for chat messages (30 days in ScyllaDB, 24 hours in Redis Streams), stream recordings (90 days), moderation records (1 year), the GDPR right to erasure (Article 17) workflow, and the anonymization and deletion propagation mechanism—is specified in S6.2.

## Client-Side Architecture (Browser & Mobile)

### Browser Client Architecture

#### Framework Selection

**React with TypeScript** is the recommended default for the browser client. React's component model maps cleanly onto the dual-pane streaming UI (player + chat), and TypeScript's type safety is critical when maintaining a shared chat message schema and stream URL builder that must stay compatible with the mobile clients (see S5.3). The ecosystem maturity is decisive: hls.js, react-virtuoso, TanStack Virtual, and React Query all have first-class React bindings. [Vue 3](https://vuejs.org/) with `<script setup>` and TypeScript is a viable alternative for teams with existing Vue expertise; its Composition API achieves similar ergonomics. [Svelte](https://svelte.dev/) offers superior runtime performance and minimal boilerplate, but its smaller ecosystem means fewer maintained streaming-specific components and less community knowledge for edge cases like LL-HLS error recovery. For a medium-sized team (~20–50 engineers), React's talent pool and library ecosystem reduce hiring and maintenance risk.

#### Audio Playback Stack

The browser audio playback stack has three layers, each serving a distinct purpose:

**1. HTML5 `<audio>` element — baseline playback.** The native `<audio>` element handles progressive audio (MP3, AAC, Opus via `<source>` tags) with built-in play/pause/seek controls and hardware-accelerated decoding. However, it cannot play HLS streams natively on non-Apple browsers, and it offers no programmatic access to the audio buffer for visualizers or custom processing. For a streaming platform, the `<audio>` element alone is insufficient — it is the fallback for VOD playback of single-file audio, not the primary live streaming path.

**2. hls.js — cross-browser HLS/LL-HLS delivery.** [hls.js](https://github.com/video-dev/hls.js) is a JavaScript library that reads an HLS playlist (`.m3u8`), fetches segments, transmuxes MPEG-2 TS to fragmented MP4 (fMP4), and appends the bytes into a `SourceBuffer` via the [Media Source Extensions (MSE) API](https://developer.mozilla.org/en-US/docs/Web/API/Media_Source_Extensions_API). It is the de facto cross-browser HLS player, used by Twitch's web client, JW Player, Mux, and Wowza, with several million weekly npm downloads as of early 2026 ([Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/articles-streaming/hls-js-deep-dive)). hls.js is necessary because only Safari ships a native HLS demuxer (via AVFoundation); Chrome, Edge, Firefox, and Opera all require a JavaScript-based player.

For **Low-Latency HLS (LL-HLS)**, hls.js supports partial segments (200–300ms each), blocking playlist reloads, and preload hints, achieving 2–4s glass-to-glass latency. Key configuration knobs include `liveSyncDuration` (target latency from the live edge) and `liveMaxLatencyDuration` (maximum allowed drift before the player skips segments to catch up). The ABR controller uses a throughput-based heuristic with configurable safety factors (`abrBandWidthFactor` default 0.95, `abrBandWidthUpFactor` default 0.7) to select the next variant, and can mid-flight abort a segment download if the buffer is depleting ([Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/articles-streaming/hls-js-deep-dive)).

**Safari native HLS vs. hls.js trade-off.** On iOS Safari and macOS Safari, the correct pattern is to skip hls.js entirely and set `video.src` to the HLS playlist URL, letting AVFoundation handle playback natively. This provides hardware-accelerated decoding and significantly lower battery usage than the JavaScript transmux path. The `Hls.isSupported()` check returns `false` in Safari, and hls.js automatically falls back to the native `<video>` element. This dual-path approach — hls.js for Chrome/Firefox/Edge, native for Safari — is the production standard ([Fora Soft, 2026](https://www.forasoft.com/learn/video-streaming/articles-streaming/hls-js-deep-dive)).

**3. Web Audio API — custom audio processing.** The [Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API) provides a `AudioContext` graph for real-time audio analysis and processing. For the streaming client, it serves two purposes: (a) **audio visualizers** — an `AnalyserNode` connected to the audio source provides frequency/time-domain data for waveform or spectrum visualizations rendered via `requestAnimationFrame` on a `<canvas>`; (b) **custom audio effects** — `BiquadFilterNode` for equalization, `GainNode` for volume normalization or audio ducking when chat notifications play. The `createMediaElementSource()` method bridges the HTML5 `<audio>` element into the Web Audio graph, allowing visualization and processing without replacing the playback pipeline ([Chrome Developers](https://developer.chrome.com/blog/html5-audio-and-the-web-audio-api-are-bffs)). The Web Audio API runs on a separate audio thread, so processing does not block the main JavaScript thread.

#### Media Source Extensions (MSE) and Adaptive Bitrate Switching

[MSE](https://developer.mozilla.org/en-US/docs/Web/API/Media_Source_Extensions_API) is the W3C standard that enables plugin-free streaming in browsers. It works by replacing the `src` URI on a `<video>` or `<audio>` element with a `MediaSource` object, which contains one or more `SourceBuffer` instances. JavaScript appends encoded media segments into these buffers, and the browser decodes and plays them. This is the foundation upon which hls.js (for HLS) and Shaka Player/dash.js (for DASH) build adaptive bitrate (ABR) streaming.

MSE enables ABR switching by allowing the player to fetch different-quality segments for the same time range and append them to the `SourceBuffer`. The ABR controller in hls.js monitors download throughput and buffer occupancy, then selects the highest-quality variant whose bitrate fits within the safety-adjusted bandwidth estimate. When network conditions degrade, the controller can abort an in-flight segment and downshift to a lower bitrate to prevent rebuffering. The `SourceBuffer` API also exposes `buffered` (a `TimeRanges` object showing what is currently buffered) and `mode` (which controls timestamp behavior for seamless switching) ([MDN, 2026](https://developer.mozilla.org/en-US/docs/Web/API/Media_Source_Extensions_API)).

For audio-only streaming, MSE is still required for HLS/LL-HLS playback on non-Safari browsers, but the transmuxing cost is lower than video since audio segments are smaller and the fMP4 repackaging is less CPU-intensive.

#### WebRTC Path for Ultra-Low-Latency Audio

For interactive scenarios (live Q&A, co-listening, audience participation), the browser client uses [`RTCPeerConnection`](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection) to establish a WebRTC connection to the SFU (LiveKit or mediasoup, per S3.2). The WebRTC path delivers 0.5–1.3s real-world CDN-delivered latency, compared to 2–4s for LL-HLS ([Fora Soft, 2026](https://www.forasoft.com/blog/article/whip-whep-replace-rtmp-live-streaming-2026)). The client obtains an SDP offer via WHEP (WebRTC-HTTP Egress Protocol, an HTTP POST carrying an SDP offer) and exchanges it with the media server through the signaling channel. The audio stream is then received via SRTP (Secure Real-time Transport Protocol) and decoded by the browser's built-in Opus decoder.

The WebRTC path is optional and scenario-gated: it is enabled for interactive rooms where sub-second latency matters, and disabled for passive listening where LL-HLS suffices. The client maintains both playback paths simultaneously — the HLS path for the broadcast audio and the WebRTC path for interactive participants — and the UI switches between them based on room mode.

#### Chat UI Component Architecture

The chat UI is the most performance-critical component in the browser client. A live stream with 10k concurrent listeners can generate hundreds of messages per second, and the DOM must not become the bottleneck.

**Virtualized message list.** A virtualized list renders only the visible subset of messages, recycling DOM nodes as the user scrolls. Two libraries dominate this space:

- **[react-virtuoso](https://virtuoso.dev/)** — purpose-built for chat interfaces, with bidirectional infinite scrolling (load older messages on scroll-up, newer on scroll-down), dynamic item heights, and a "follow output" mode that auto-scrolls to the latest message only when the user is already at the bottom. This matches the chat UX pattern where users read history by scrolling up but expect new messages to appear automatically when at the bottom.
- **[TanStack Virtual](https://tanstack.com/virtual/latest)** — a lower-level virtualizer that gives more control over the scroll container and item measurement. It requires more boilerplate for chat-specific behaviors (reversed scroll, dynamic heights) but offers better performance for extremely high message rates ([PkgPulse, 2026](https://www.pkgpulse.com/guides/tanstack-virtual-vs-react-window-vs-react-virtuoso-2026)).

For a chat-synchronized streaming UI, react-virtuoso is the recommended default due to its chat-specific features; TanStack Virtual is preferred if the team needs custom scroll behavior or is already using TanStack Query for server state.

**Message rendering.** Each chat message is a React component that renders: author name (with role badges for moderators/subscribers), timestamp, text content (with emoji rendering, @mention highlighting, and link previews), and optional reply threading. Message types are discriminated by a `type` field in the chat schema: `chat_message`, `system_message`, `moderation_action`, `presence_update`. The component uses a `React.memo` wrapper to prevent re-rendering unchanged messages during high-frequency updates.

#### State Management

The streaming client has two distinct state domains that benefit from different management strategies:

**Player state (client-side, high-frequency).** Playback state — current time, buffered range, playing/paused, volume, selected quality level, latency from live edge — changes frequently and must not trigger re-renders of unrelated components. **Zustand** is the recommended choice for this domain: it is a minimal, hook-centric store with no boilerplate, excellent performance (components subscribe to specific state slices), and a small bundle size (~3KB). **Jotai** is an alternative for teams that prefer atomic, composable state — useful if the player state is highly granular (e.g., separate atoms for volume, quality, latency). **Redux Toolkit** is appropriate only if the team already has Redux infrastructure or needs time-travel debugging for complex player state transitions ([State of React 2025](https://2025.stateofreact.com/en-US/libraries/state-management/)).

**Server state (remote, cached).** Room metadata, user profiles, chat history (for late joiners), stream configuration, and presence counts are server-managed and benefit from caching, deduplication, and background revalidation. **React Query (TanStack Query)** or **SWR** handle this domain: they provide stale-while-revalidate caching, automatic refetch on window focus, pagination for chat history loading, and optimistic updates for sent messages. React Query is recommended for its superior devtools and mutation handling; SWR is lighter and simpler for read-heavy workloads ([Vercel SWR](https://vercel.com/oss/swr)).

The key architectural principle is **separation**: Zustand/Jotai for ephemeral player state that lives and dies with the component lifecycle, React Query/SWR for server state that persists across navigation and benefits from caching. Mixing these domains in a single store leads to unnecessary re-renders and cache invalidation complexity.

#### Audio-Visual Synchronization: Chat and Playback Alignment

Synchronizing chat messages with audio playback is a non-trivial problem because the two paths have different latencies. The audio stream arrives via HLS (2–4s latency) or WebRTC (0.5–1.3s latency), while chat messages arrive via WebSocket (typically <100ms). A chat message sent at wall-clock time T will appear on screen nearly instantly, but the corresponding audio content is still 2–4 seconds in the future.

The solution is **timestamp-based alignment with latency compensation**:

1. **Server-side timestamping.** Each chat message is stamped with the server's wall-clock time when it was received, not when the user sent it. This provides a common reference frame.

2. **Playback position tracking.** The player exposes `currentTime` (the playback position in the media timeline) and a `liveEdge` estimate (the current live edge position in the media timeline). The difference `liveEdge - currentTime` is the playback latency.

3. **Chat message alignment.** When rendering a chat message, the client computes the message's "playback time" as `message.timestamp + playbackLatency`. Messages are displayed in a timeline that is offset from the wall clock by the playback latency, so a message appears in the chat at the moment the corresponding audio is being heard. This is implemented as a virtualized list where the scroll position is driven by the playback clock, not wall-clock time.

4. **Latency drift correction.** The playback latency can drift over time due to buffer adjustments, ABR switches, or network conditions. The client periodically recalculates `liveEdge - currentTime` and adjusts the chat timeline offset. For WebRTC, the jitter buffer depth can be monitored via `peerConnection.getStats()` to track `jitterBufferDelay` and adjust the offset ([GetStream, 2026](https://getstream.io/blog/av-sync-webrtc-streams/)).

For the WebRTC path, synchronization is simpler because the audio and chat can share the same WebRTC data channel or be timestamped against the same NTP-derived clock that WebRTC uses for RTP synchronization. The browser's built-in jitter buffer handles arrival-time variation, and the playout scheduler aligns audio samples to the NTP wall-clock reference from RTCP Sender Reports ([GetStream, 2026](https://getstream.io/blog/av-sync-webrtc-streams/)).

#### Component Architecture for the Streaming UI

The browser client is organized as a component tree with clear separation of concerns:

```
<App>
  <AuthProvider>                    // JWT/session management
    <Router>
      <StreamPage roomId={...}>
        <PlayerPane>
          <AudioPlayer>               // hls.js or native HLS
            <VideoElement>            // <audio> or <video> element
            <ABRControls>             // quality selector
            <LiveIndicator>           // latency badge
          </AudioPlayer>
          <AudioVisualizer>           // Web Audio API + canvas
          <StreamMetadata>            // title, broadcaster, viewer count
        </PlayerPane>
        <ChatPane>
          <ChatMessageList>           // react-virtuoso virtualized
            <ChatMessage />           // individual message component
            <SystemMessage />
            <ModerationAction />
          </ChatMessageList>
          <ChatInput>                 // message composer
            <EmojiPicker />
            <MentionAutocomplete />
          </ChatInput>
          <ChatControls>              // slow mode indicator, follower-only badge
        </ChatPane>
        <ParticipantList>             // WebRTC participants (if interactive mode)
      </StreamPage>
    </Router>
  </AuthProvider>
</App>
```

The `StreamPage` component is the orchestrator: it initializes the audio player, establishes the WebSocket chat connection, and (optionally) the WebRTC peer connection. It manages the shared room/session identity that couples the audio and chat subsystems (per S1.1). State is split: the `AudioPlayer` component owns playback state via a Zustand store, the `ChatPane` owns chat state via React Query (server state) and a local Zustand store (UI state like input draft, scroll position).

**Responsive design.** The layout uses CSS Grid with a two-column layout on desktop (player left, chat right) and a stacked layout on mobile (player top, chat bottom, with a collapsible chat drawer). The player pane maintains a 16:9 aspect ratio container for the visualizer, collapsing to a compact bar when the user scrolls to chat on mobile.

#### PWA Considerations

Progressive Web App capabilities enhance the browser client but have significant limitations for audio streaming:

**Service workers** enable offline caching of static assets (JS/CSS bundles, emotes, UI shell) and can serve cached VOD audio when offline. They also enable **background sync** for chat messages sent during network interruptions — messages are queued in IndexedDB and synced when connectivity returns. The [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API) enables server-initiated notifications for stream events (e.g., "a broadcaster you follow went live").

**Critical limitation: background audio on iOS.** PWAs on iOS cannot play audio in the background. When the user switches apps or locks the screen, audio playback stops. This is a platform restriction — iOS does not grant PWAs the `UIBackgroundModes` audio entitlement that native apps receive. On Android, background audio works in PWAs via the Media Session API, but the experience is less reliable than native. A real-world case study documented that an iOS PWA audio player worked only in the foreground, stopped completely when minimized or screen-locked, and had spotty lock-screen controls — ultimately forcing the team to build a native iOS app ([Prototyp Digital, 2026](https://prototyp.digital/blog/what-we-learned-about-pwas-and-audio-playback)).

**Recommendation.** Ship the PWA for Android and desktop browsers, where it provides a near-native experience with offline caching and push notifications. For iOS, the PWA is a discovery and onboarding channel — users can browse and preview streams, but full playback (especially background audio) requires the native iOS app (see S5.2). The PWA should detect iOS and show a banner prompting the user to install the native app from the App Store. This is the same pattern used by Spotify, Twitch, and YouTube.

The PWA should also implement the [Media Session API](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API) to provide lock-screen media controls (play/pause, skip) on Android and desktop, and to expose metadata (stream title, broadcaster, artwork) to the OS media controls. This API is well-supported on Chrome and Safari but does not enable background audio playback on iOS.

### Mobile Client Architecture & Background Audio

#### Framework Selection: React Native vs. Flutter vs. Native

The mobile client must serve two platforms (iOS and Android) from a single codebase where possible, but audio streaming imposes platform-specific constraints that no cross-platform framework fully abstracts. The three viable options are:

| Dimension | React Native | Flutter | Native (Swift/Kotlin) |
|---|---|---|---|
| **Audio player** | Native module bridge to ExoPlayer/AVPlayer | Platform channels to native players | Direct ExoPlayer/AVPlayer API |
| **WebRTC** | [react-native-webrtc](https://www.npmjs.com/package/react-native-webrtc) (wraps libwebrtc) | flutter_webrtc (wraps libwebrtc) | libwebrtc native SDK |
| **Background audio** | Native module + platform config | Platform channel + platform config | Full control |
| **Performance** | JSI bridge overhead; improving with New Architecture | Native machine code compilation; Impeller renderer | Best possible |
| **Team velocity** | Single JS/TS codebase; large talent pool | Single Dart codebase; growing ecosystem | Two codebases; 2× maintenance |

**Recommendation: React Native with TypeScript** for a medium-sized team (~20–50 engineers) that likely already has web developers familiar with React. The key justification is talent reuse: the same engineers who build the browser client (React + TypeScript per S5.1) can share stream URL construction, chat schema, authentication logic, and reconnection logic with the mobile app via a shared TypeScript package (see S5.3). Flutter is a strong alternative if the team prefers Dart and wants slightly better rendering performance, but it requires a separate skill set and its audio plugin ecosystem ([just_audio](https://pub.dev/packages/just_audio)) has documented issues with HLS live-stream reconnection on iOS ([GitHub issue #1277](https://github.com/ryanheise/just_audio/issues/1277)). Native development (Swift + Kotlin) is justified only if the team has dedicated mobile engineers and needs maximum control over audio session management, but it doubles the maintenance burden for a medium-sized company.

A critical caveat: **both React Native and Flutter require native modules for HLS playback and WebRTC**. Neither framework runs these in a JavaScript/Dart engine — both bridge to the platform-native library. This means the team must still write and maintain native glue code for background audio, audio session configuration, and WebRTC peer connections, and they own the bugs in that glue layer ([Fora Soft, 2026](https://www.forasoft.com/blog/article/video-streaming-app-development-challenges-solutions-whm3v)).

#### Audio Player Libraries

**Android — ExoPlayer (AndroidX Media3):** [ExoPlayer](https://developer.android.com/media/media3/session/background-playback) is Google's open-source player supporting HLS, DASH, and SmoothStreaming. It offers built-in Widevine L1/L3 DRM support, CPU-efficient ABR switching, and ~1.5s startup on 4G. LL-HLS support exists but has historically had synchronization issues — a [long-standing GitHub issue (#5011)](https://github.com/google/ExoPlayer/issues/5011) documents that ExoPlayer does not fully implement LL-HLS blocking playlist reloads, causing latency to drift above the 2–4s target. For audio-only streaming at 64–192 kbps AAC, this is acceptable because segment duration variance matters less than for video, but teams should validate LL-HLS behavior against their specific SRS or LiveKit origin before committing. ExoPlayer is now part of the AndroidX Media3 library, which provides the `MediaSessionService` infrastructure for background playback.

**iOS — AVPlayer:** [AVPlayer](https://www.mux.com/blog/background-audio-handling-with-ios-avplayer) is Apple's native HLS engine, available since iOS 8. It provides excellent hardware-accelerated AAC decoding, native LL-HLS support on iOS 14+, and 2–3s startup latency on good networks. Its limitations are significant: it freezes on corrupt segments with no recovery mechanism, does not expose ABR state to application code (developers must infer the active rendition from bitrate logs), and does not support DASH without custom parsing. For an audio-only streaming app, these limitations are manageable — corrupt segments are rare in a controlled origin-to-CDN pipeline, and ABR state exposure is less critical when the bitrate ladder is simple (3–4 rungs).

**Cross-platform options:** [react-native-track-player](https://www.npmjs.com/package/react-native-track-player) provides a fully-fledged audio module with background mode, lock-screen controls, and external media controls for React Native apps. However, users have reported [HLS buffer management issues](https://github.com/doublesymmetry/react-native-track-player/issues/2348) where playback starts at an advanced position rather than the live edge, and the library's HLS handling is less mature than the native players. For Flutter, [just_audio](https://pub.dev/packages/just_audio) supports HLS but has [documented reconnection failures](https://github.com/ryanheise/just_audio/issues/1277) with live streams on iOS. **Recommendation: use the native players (ExoPlayer on Android, AVPlayer on iOS) directly** rather than cross-platform wrappers, because background audio reliability is a hard requirement and the native players have fewer abstraction layers to debug.

#### Background Audio: iOS

Background audio on iOS requires three coordinated steps, all of which are mandatory:

1. **Enable the background mode:** In Xcode, enable "Audio, AirPlay and Picture in Picture" in the target's Capabilities. This adds the `audio` value to `UIBackgroundModes` in `Info.plist`, signaling to iOS that audio playback is central to the app's function.

2. **Configure AVAudioSession:** Set the audio session category to `.playback` at app launch. This tells iOS that audio is "central to the successful use of your app" and is required for audio to persist when the device locks or the app is backgrounded ([Mux, 2021](https://www.mux.com/blog/background-audio-handling-with-ios-avplayer)):
   ```swift
   let audioSession = AVAudioSession.sharedInstance()
   try audioSession.setCategory(AVAudioSession.Category.playback)
   ```

3. **Detach the player from the UI:** In `SceneDelegate`, listen for `sceneDidEnterBackground` and detach the `AVPlayer` instance from the `AVPlayerViewController` or `AVPlayerLayer`, saving a reference. On `sceneWillEnterForeground`, re-attach the player. Without this step, iOS may suspend the app's audio when the view hierarchy is torn down.

A subtle but important issue: AVPlayer does **not** automatically switch to an audio-only rendition when the video surface is detached. For an audio-only streaming app this is irrelevant, but if the app ever carries video, developers must manually set `preferredPeakBitRate` to force a lower rendition — and even then, AVPlayer's `preferred*` properties are treated as "suggestions" that iOS may ignore ([Mux, 2021](https://www.mux.com/blog/background-audio-handling-with-ios-avplayer)).

#### Background Audio: Android

Android's background audio model is more structured but requires more boilerplate. The [Media3 library](https://developer.android.com/media/media3/session/background-playback) provides a `MediaSessionService` that hosts the `Player` and `MediaSession` in a separate Android `Service`, allowing playback to continue when the app is not in the foreground:

```kotlin
class PlaybackService : MediaSessionService() {
  private var mediaSession: MediaSession? = null
  override fun onCreate() {
    super.onCreate()
    val player = ExoPlayer.Builder(this).build()
    mediaSession = MediaSession.Builder(this, player).build()
  }
  override fun onGetSession(controllerInfo: MediaSession.ControllerInfo): MediaSession? = mediaSession
}
```

The service must be declared in the manifest with `foregroundServiceType="mediaPlayback"` and the `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK` permissions. The `MediaSessionService` automatically creates a `MediaNotification` with playback controls, and external clients (Google Assistant, Wear OS, Bluetooth devices) can discover and control playback without accessing the app's UI.

**Doze and App Standby:** Android's [Doze mode](https://developer.android.com/training/monitoring-device-state/doze-standby) suspends network access and defers jobs when the device is unused for long periods. App Standby defers background network activity for apps with no recent user interaction. **A running foreground service is exempt from both Doze and App Standby**, which is why the `MediaSessionService` approach works: as long as the foreground service is active with a visible notification, the audio stream continues uninterrupted. If the service is killed (e.g., by the system under extreme memory pressure or by a user swiping away the app), playback stops.

**User-facing mitigation:** On some OEM devices (particularly Xiaomi, Huawei, and other Chinese manufacturers), aggressive battery optimization can kill foreground services even when they are properly declared. The mitigation is to guide the user to whitelist the app in `Settings > Battery > Battery Optimization` via the `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` intent. This is a known pain point in the Android ecosystem and should be documented in the app's onboarding flow.

#### Audio Session Management and Interruptions

**iOS AVAudioSession:** The audio session manages interruptions from phone calls, Siri, alarms, and other apps. When an interruption begins, AVAudioSession posts a notification; the app should pause or duck audio. When the interruption ends, the app should reactivate the session and resume playback if appropriate. The [Apple documentation](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions) provides the `AVAudioSession.interruptionNotification` API for this. Route changes (e.g., user plugs in headphones, switches to speaker) also post notifications via `AVAudioSession.routeChangeNotification`, and the app should update its audio route accordingly. For an audio streaming app, the default interruption behavior is usually sufficient — pause on phone call, resume after — but the app must handle the case where the user manually stops playback during a call and the call ends (the app should not auto-resume in that case).

**Android AudioManager:** Android handles audio focus through `AudioManager`. The app requests `AUDIOFOCUS_GAIN` for persistent playback or `AUDIOFOCUS_GAIN_TRANSIENT` for short sounds. When another app takes audio focus (e.g., a phone call), the system sends `AUDIOFOCUS_LOSS` and the app should pause. The Media3 `MediaSession` handles audio focus automatically when configured with the correct `androidx.media3.common.AudioAttributes`. For speaker vs. earpiece routing, the app can use `AudioManager.setSpeakerphoneOn()` or, on modern Android, `AudioDeviceCallback` to detect route changes and update the UI.

#### Network Switching (WiFi → Cellular)

HLS players handle network switching through their internal buffer. When the network transitions from WiFi to cellular, the player's HTTP connection may briefly stall, but playback continues from the buffer. The key design decision is **buffer size**: a larger forward buffer (e.g., 30–60s of audio) survives network transitions seamlessly but increases latency; a smaller buffer (e.g., 10s) keeps latency low but risks rebuffering during the switch. For a live audio streaming app targeting 2–4s latency with LL-HLS, a forward buffer of 15–20s is a reasonable compromise — enough to survive a 2–5s network handoff without audible interruption.

Some apps handle this better than others: [community reports](https://emby.media/community/topic/121043-transition-issues-between-wi-fi-and-mobile-data/) indicate that Jellyfin's HLS player handles WiFi→cellular handoff seamlessly, while Emby pauses and fails to resume. The difference is in the player's error recovery logic — ExoPlayer and AVPlayer both have robust retry mechanisms for network transitions, but the app must not treat a transient network error as a fatal playback failure. The recommended approach is to listen for `onPlayerError` events, check if the error is a network type change (via `ConnectivityManager` on Android or `NWPathMonitor` on iOS), and if so, increase the buffer target and retry rather than surfacing an error to the user.

#### Mobile WebRTC Considerations

For the ultra-low-latency path (0.5–1.3s), the mobile client uses WebRTC rather than HLS. The [react-native-webrtc](https://www.npmjs.com/package/react-native-webrtc) library wraps the native libwebrtc library for both iOS and Android, exposing `RTCPeerConnection`, `getUserMedia`, and `RTCDataChannel` to JavaScript. It supports iOS CallKit integration and Android ConnectionService for native call UI. A [known issue](https://www.reddit.com/r/reactnative/comments/1t60hly/react_native_webrtc_not_audible_on_real_ios/) is that audio may not be audible on real iOS devices if the AVAudioSession category is not set to `PlayAndRecord` — the library sets this internally, but developers must verify it works on their target iOS version.

For Flutter, `flutter_webrtc` provides equivalent functionality. Both libraries bridge to the same underlying libwebrtc native library, so performance is comparable. The choice between them follows the framework decision above.

Mobile networks fail direct connectivity more often than fixed broadband: [roughly 15–20% of WebRTC sessions fall back to a TURN relay](https://antmedia.io/how-to-build-a-webrtc-mobile-app/), adding 10–80ms depending on geography. This makes TURN/STUN infrastructure (coturn or LiveKit's built-in TURN) a mandatory component for mobile WebRTC delivery, not optional. The mobile client must be configured with TURN server credentials and ICE candidate gathering that includes host, server-reflexive, and relayed candidates.

**Codec support on mobile:** Codec hardware acceleration differs by platform and direction — Opus is hardware-accelerated for decode only on modern iOS and Android, while AAC has full hardware encode+decode support on both platforms. The WebRTC path (Opus) is therefore efficient for listeners but may consume more battery for broadcasters encoding in real time, while the HLS path (AAC) is fully hardware-accelerated in both directions. See S2.2 for the full mobile hardware decode and battery impact analysis.

#### Push Notifications for Background Chat

When the app is in the background, the WebSocket chat connection may be suspended by the OS. To deliver chat notifications, the app must integrate with platform push services:

- **iOS:** Apple Push Notification service (APNs) via the `UserNotifications` framework. The app registers for remote notifications at launch, receives a device token, and sends it to the backend chat service. When a chat message arrives and the app is in the background, the backend sends a push notification via APNs. The notification can carry a payload with the message content for display, but the full chat history is fetched when the user opens the app.

- **Android:** Firebase Cloud Messaging (FCM) provides the same capability. [Google recommends FCM](https://developer.android.com/training/monitoring-device-state/doze-standby) over maintaining a persistent WebSocket connection for background messaging, because FCM uses a single shared connection that is far more battery-efficient. High-priority FCM messages can wake the app temporarily to fetch new chat messages during Doze mode.

The architecture is: WebSocket for real-time chat while the app is foregrounded, FCM/APNs for background notification delivery, and a chat history API (REST or GraphQL) for fetching missed messages when the app returns to the foreground. This three-tier approach balances real-time responsiveness with battery efficiency.

#### Summary of Mobile Architecture Decisions

| Concern | iOS | Android |
|---|---|---|
| **Framework** | React Native + TypeScript | React Native + TypeScript |
| **Audio player (HLS)** | AVPlayer (native) | ExoPlayer / Media3 (native) |
| **Audio player (WebRTC)** | react-native-webrtc → libwebrtc | react-native-webrtc → libwebrtc |
| **Background audio** | UIBackgroundModes + AVAudioSession `.playback` + SceneDelegate detach/attach | MediaSessionService + foreground service + `mediaPlayback` type |
| **Battery optimization** | N/A (iOS manages background audio natively) | Foreground service exempts from Doze/App Standby; OEM whitelist guidance |
| **Audio interruptions** | AVAudioSession interruption notifications | AudioManager audio focus + Media3 AudioAttributes |
| **Push notifications** | APNs via UserNotifications | FCM with high-priority messages for Doze |
| **Network switching** | NWPathMonitor + buffer increase on network change | ConnectivityManager + ExoPlayer retry logic |
| **Codec (HLS)** | AAC (hardware encode+decode) | AAC (hardware encode+decode) |
| **Codec (WebRTC)** | Opus (hardware decode only) | Opus (hardware decode only) |

### Shared Cross-Platform Logic

A distributed audio streaming platform targeting both browser and mobile (iOS/Android) clients faces a fundamental engineering question: which logic is genuinely shareable, and which must remain platform-specific? Getting this boundary right determines whether the team maintains one source of truth or drifts into divergent implementations that produce inconsistent behavior across platforms.

#### Identifying the Shareable Logic Boundary

The logic that can be shared falls into five categories:

1. **Stream URL construction** — building HLS playback URLs with signed-token query parameters, WebRTC WebSocket signaling URLs, and room/session identifiers. The URL template, query-parameter ordering, and token-signing logic are identical regardless of whether the client is a browser or a native app.

2. **Chat message protocol/schema** — the message envelope (message ID, room ID, sender ID, timestamp, message type, payload), the set of message types (`chat_message`, `system_message`, `moderation_action`, `presence_update`), and the serialization/deserialization logic. A message sent from a browser must be renderable by a mobile client without special-casing.

3. **Authentication token handling** — JWT acquisition, storage, refresh-on-expiry, and attachment to WebSocket upgrade requests and HTTP API calls. The OAuth2/OIDC flow, token refresh logic, and expiry-margin calculations are platform-independent.

4. **Reconnection logic** — exponential backoff with jitter, session resumption via sequence numbers, pending-message retry queues, and token-refresh-before-reconnect checks. The [WebSocket reconnection guide](https://websocket.org/guides/reconnection/) documents that connections drop constantly in production (mobile network switches, laptop sleep/wake, server deploys, proxy timeouts), and the recovery algorithm is identical across platforms.

5. **Audio quality selection** — the adaptive bitrate decision logic: given available network bandwidth, device capabilities, and battery state, select the appropriate bitrate ladder rung (e.g., 64/96/128/192 kbps AAC for HLS, 32/64/128 kbps Opus for WebRTC). The decision algorithm is platform-agnostic, though the inputs (battery API, network type) are platform-specific.

What **must** remain platform-specific: audio playback engines (HTML5 `<audio>`/hls.js vs. ExoPlayer/AVPlayer), background audio session management (iOS `AVAudioSession` vs. Android `ForegroundService` + `MediaSession`), push notification integration (APNs vs. FCM), and native UI rendering. These are non-shareable because they depend on platform APIs that have no cross-platform abstraction.

#### Approaches to Code Sharing

Three approaches are viable for a medium-sized team, each with distinct trade-offs:

**TypeScript monorepo with a shared package.** If the team adopts React Native for mobile and React for web (see S5.1 and S5.2), a monorepo structure (Yarn workspaces, Turborepo, or Nx) with a `@shared` TypeScript package is the lowest-friction path. The shared package contains the five logic categories above as pure TypeScript modules with no platform-specific imports. The [React Native web](https://dev.to/brunolemos/tutorial-100-code-sharing-between-ios-android--web-using-react-native-web-andmonorepo-4pej) approach extends this further by allowing some React components to render on all three platforms. The advantage is a single language (TypeScript), single toolchain, and single team skill set. The limitation is that this approach only works if the team commits to React Native — it does not help if the team chooses Flutter or native Swift/Kotlin.

**Kotlin Multiplatform (KMP).** [Kotlin Multiplatform](https://kotlinlang.org/docs/multiplatform/multiplatform-reasons-to-try.html) has reached stable status (November 2023) and seen adoption more than double from 7% of Kotlin developers in 2024 to 18% in 2025, with [Google announcing official support at Google I/O 2024](https://android-developers.googleblog.com/2024/05/android-support-for-kotlin-multiplatform-to-share-business-logic-across-mobile-web-server-desktop.html). KMP allows sharing business logic (data models, API clients, validation, chat schema, reconnection state machines) across Android, iOS, web (JavaScript/WASM), and server while keeping native UI. Companies like Baidu, Quizlet, 9GAG, and Cash App use KMP in production. For an audio streaming platform, KMP is a strong choice if the team is already Kotlin-proficient on Android and wants to share logic with a native iOS (Swift) client — the shared Kotlin code compiles to a native framework consumable by Swift. However, KMP does not help the browser client unless the team also targets Kotlin/JS or Kotlin/WASM for web, which is less mature than the React ecosystem for browser UIs.

**Backend-for-Frontend (BFF) layer.** A BFF is a dedicated backend service that sits between the API gateway and the client applications, aggregating data from multiple microservices and tailoring responses to each client's needs ([Teleport's BFF guide](https://goteleport.com/learn/backend-for-frontend-bff-pattern/)). Unlike an API gateway (which handles routing, rate limiting, and auth), a BFF handles data transformation and aggregation. For this platform, a BFF can abstract the media and chat APIs: the web BFF returns HLS playlist URLs and WebSocket endpoints in a format optimized for hls.js, while the mobile BFF returns the same data optimized for ExoPlayer/AVPlayer. The BFF is justified when web and mobile clients have genuinely different data requirements — for example, mobile may need compact payloads to save cellular bandwidth, while web can afford richer metadata. However, a BFF adds operational complexity (another service to deploy, monitor, and scale) and can become a bottleneck if it grows too large. For a medium-sized team, a single BFF that serves both web and mobile is preferable to separate BFFs per platform, and it should be kept thin — aggregation and transformation only, no business logic.

**Recommendation:** Use a TypeScript monorepo with a shared package as the primary sharing mechanism (assuming React Native + React web), supplemented by a thin BFF layer for platform-specific API adaptation. This gives the team one language, one set of shared schemas, and one reconnection implementation, while the BFF handles the few cases where mobile and web need different data shapes. Kotlin Multiplatform is the recommended alternative if the team chooses native mobile development (Swift/Kotlin) over React Native.

#### Chat Message Serialization Format

The choice of serialization format for chat messages affects bandwidth, parsing CPU cost, and schema evolution capabilities. Three formats are relevant:

| Format | Encode Speed | Decode Speed | Payload Size | Schema Evolution | Human-Readable |
|--------|-------------|-------------|-------------|-----------------|----------------|
| **JSON** | 1× (baseline) | 1× (baseline) | ~500 bytes (sample) | Ad hoc (manual) | Yes |
| **MessagePack** | 3.5× faster | 3.5× faster | ~295 bytes (1.7× smaller) | Schema-optional | No |
| **Protobuf** | 6.5× faster | 7.5× faster | ~190 bytes (2.6× smaller) | Built-in (field numbers) | No |

*Benchmarks from [production Go payloads](https://dev.to/devflex-pro/json-vs-messagepack-vs-protobuf-in-go-my-real-benchmarks-and-what-they-mean-in-production-48fh), November 2025.*

**JSON** is the right choice for the WebSocket chat transport at the system boundary — it is human-readable for debugging, universally supported without code generation, and the performance cost is negligible for chat messages (small payloads, low frequency). A typical chat message is 100–300 bytes; even at 10,000 messages per second, the JSON parsing overhead is dwarfed by network I/O. JSON should also be used for the REST API responses from the BFF.

**Protobuf** is the right choice for internal service-to-service communication (e.g., chat service → message broker → persistence) where throughput is high and schema evolution is critical. Protobuf's [built-in schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/serdes-develop/serdes-protobuf.html) — using field numbers rather than field names, with unknown fields preserved by default — makes it the safest format for a system that will add chat features over time. The [Confluent Schema Registry](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) enforces compatibility rules (BACKWARD, FORWARD, FULL) when registering new schema versions, preventing breaking changes from reaching production.

**MessagePack** is the best drop-in replacement if the team wants binary efficiency without the build-pipeline overhead of Protobuf. It requires no `.proto` files and no code generation — it serializes Go/TypeScript structs directly. However, it lacks Protobuf's schema evolution guarantees, making it riskier for long-lived message contracts.

**Recommendation:** Use JSON for the WebSocket chat transport (client-facing) and Protobuf for internal service-to-service chat message flow (server-side). This matches the [production recommendation](https://dev.to/devflex-pro/json-vs-messagepack-vs-protobuf-in-go-my-real-benchmarks-and-what-they-mean-in-production-48fh) to "use JSON only at system boundaries" and Protobuf for high-throughput internal paths.

#### Schema Evolution Without Breaking Older Clients

Chat features will evolve — reactions, threading, @mentions, and moderator actions will be added over time. The schema must evolve without breaking older clients that don't understand new message types or fields.

**Protobuf field-number discipline.** Protobuf's core evolution rule is: never reuse or change a field number. New fields are added with new numbers; old fields are reserved (not deleted) to prevent number reuse. Unknown fields in a message are preserved by default, so an old client receiving a new message type will skip the fields it doesn't understand and still render the message envelope. The [Confluent Schema Registry](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) recommends `BACKWARD_TRANSITIVE` compatibility for Protobuf, which ensures that consumers using the latest schema can read data produced by any previous schema version. The key rules:

- **Adding a new optional field** — backward and forward compatible. Old clients ignore the new field; new clients see a default value for messages from old producers.
- **Removing an optional field** — backward compatible if the field was optional. Reserve the field number to prevent reuse.
- **Adding a new message type** — not forward compatible under `BACKWARD` mode; use `BACKWARD_TRANSITIVE` or `FULL` compatibility.
- **Changing a field type** — only compatible if the types are wire-compatible (e.g., `int32` → `int64`). Otherwise, add a new field and deprecate the old one.

**Feature flags for behavioral changes.** Schema changes that alter behavior (e.g., a new moderation action that hides messages) should be gated by feature flags rather than schema changes alone. The server includes a `features` bitfield or version string in the session handshake, and the client enables or disables UI elements accordingly. This allows the server to roll out new capabilities gradually and lets older clients continue functioning with a degraded but non-broken experience ([schema evolution best practices](https://www.conduktor.io/glossary/schema-evolution-best-practices)).

**Version compatibility testing.** The CI pipeline should include a compatibility test that runs an older production build of the client against a new staging backend, verifying that the old client can still connect, receive chat messages, and render the stream without crashing. This catches schema regressions before they reach users ([mobile API versioning guide](https://blog.stackademic.com/android-api-versioning-best-practices-designing-backward-compatible-mobile-systems-94b0a37dbc09)).

**JSON schema evolution for the WebSocket transport.** Since the client-facing chat transport uses JSON, the team should adopt a JSON Schema (draft 2020-12) for the message envelope and validate incoming messages server-side. The schema should use `additionalProperties: true` to allow new fields without rejecting messages, and the server should strip unknown fields before forwarding to older clients. This provides a lighter-weight evolution mechanism than Protobuf for the client-facing path while still catching malformed messages.

**Practical evolution workflow:**

1. Add new fields as optional with defaults in the `.proto` file.
2. Register the new schema version with the Schema Registry (which validates compatibility).
3. Deploy the server changes (which now produce messages with the new fields).
4. Deploy client updates that understand the new fields.
5. Old clients continue to work — they ignore unknown fields and use default values for missing ones.
6. After all clients have updated (or after a deprecation period), remove the old field by reserving its number.

This workflow ensures that a user who hasn't updated their app in six months can still join a stream, send and receive chat messages, and see the audio — they simply won't see the new reaction emojis or threaded replies until they update.

## Backend Services & Data Infrastructure

### Microservices, API Gateway & Service Communication

#### API Gateway: The Control-Plane Entry Point

The API gateway is the single ingress point for all client-to-backend traffic, but it handles **only control-plane APIs** — never media bytes. Audio segments flow through the CDN edge layer (S3 → CloudFront → client), and WebRTC media traverses the SFU mesh directly; neither path touches the API gateway. This separation is deliberate: media traffic is high-bandwidth, long-lived, and cache-friendly, while control-plane requests are low-latency, short-lived, and require authentication and rate limiting. Routing them through the same component would force the gateway to handle two radically different traffic profiles, complicating scaling and failure isolation.

The gateway's responsibilities are:

- **Routing**: Path-based dispatch to internal services (`/api/v1/users` → user service, `/api/v1/rooms` → room service, `/api/v1/streams` → stream service).
- **Authentication**: Validating JWT bearer tokens or session cookies on every request, offloading auth logic from individual services.
- **Rate limiting**: Token-bucket or sliding-window limits per user, per IP, and per endpoint to protect downstream services from abuse.
- **TLS termination**: Centralizing certificate management and HTTP/2 termination at the edge.
- **Request transformation**: Protocol translation (REST → gRPC) and payload normalization for internal services.

For a medium-sized team, **Kong** is the recommended default. It runs on NGINX with a Lua plugin layer, offers 100+ plugins for auth (JWT, OIDC, OAuth2), rate limiting, and request transformation, and supports DB-less declarative configuration — eliminating a PostgreSQL dependency for the gateway itself ([Kong vs Envoy vs Traefik 2026](https://lucaberton.com/blog/kong-vs-envoy-vs-traefik-api-gateway-2026/)). Kong's multi-protocol support (HTTP, gRPC, WebSocket, GraphQL) is valuable for a streaming platform where the chat service uses WebSocket and internal services use gRPC. **Envoy** (via Envoy Gateway) is the alternative if the team already runs a service mesh or needs maximum C++ data-plane performance, but its xDS configuration complexity is a steeper operational burden ([Kong vs Envoy vs Traefik 2026](https://lucaberton.com/blog/kong-vs-envoy-vs-traefik-api-gateway-2026/)). **Traefik** is the simplest option for small clusters but lacks the plugin depth for production-grade API management. **AWS API Gateway** is a managed alternative that reduces operational overhead but introduces vendor lock-in and per-request pricing that becomes significant at scale.

#### Core Service Decomposition

The control plane is decomposed into five services, each with a single, well-defined boundary. This follows the pattern Netflix established when rebuilding its video processing pipeline: identifying functional boundaries along the media lifecycle and creating independent microservices for each, enabling separate scaling and deployment ([Netflix Tech Blog, Jan 2024](https://netflixtechblog.com/rebuilding-netflix-video-processing-pipeline-with-microservices-4e5e6310e359)).

| Service | Responsibility | Scaling Characteristic |
|---|---|---|
| **User Service** | Registration, profiles, preferences, playback history, social graph | Read-heavy, cache-friendly |
| **Room/Session Service** | Room lifecycle (create, join, leave), participant state, room metadata, stream-to-room binding | Moderate read/write, stateful during active streams |
| **Stream Service** | Ingest token generation, stream key assignment, stream state (live/offline), transcoding job orchestration | Low request count, high criticality |
| **Chat Service** | WebSocket gateway management, message fanout, chat history persistence, presence tracking | High-concurrency, connection-heavy |
| **Analytics Service** | Playback event ingestion, QoE metric aggregation, real-time dashboards | Write-heavy, batch-processed |

The **room/session service** is the shared coordination point between the audio streaming and chat subsystems. A room has a unique ID; both the media pipeline (SFU room) and the chat system (WebSocket channel `room:{roomId}:chat`) reference this ID. The room service does not handle media or chat bytes — it manages the metadata and lifecycle that both subsystems depend on, allowing them to scale independently. This is the same decoupling principle that separates the media plane from the control plane at the architecture level.

The **stream service** is the most critical control-plane component for broadcasters. It generates ingest tokens (for RTMP/SRT/WHIP publish authentication) and playback tokens (for HLS/WebRTC consume authorization). When a broadcaster starts a stream, the stream service:

1. Validates the broadcaster's credentials and room ownership.
2. Generates a unique stream key (for RTMP ingest) or a WHIP token (for WebRTC ingest), signed with a short-lived JWT containing the room ID, stream ID, and expiration.
3. Registers the stream as "live" in the room service.
4. Triggers the transcoding pipeline to provision resources for the new stream.

#### Language Choices: Go, Node.js/TypeScript, Python

Language selection is driven by the concurrency model, ecosystem maturity, and team velocity requirements of each service:

- **Go** is the default for the **room/session service** and **stream service**. Go's goroutine + channel concurrency model is purpose-built for high-concurrency, I/O-bound workloads — exactly the pattern of managing thousands of concurrent room states and stream lifecycles. Go's static typing and single-binary deployment simplify Kubernetes operations. The language's standard library includes production-grade HTTP/2, gRPC, and WebSocket support, reducing dependency surface. LiveKit, the recommended SFU, is written in Go, so using Go for media-adjacent services enables code sharing and operational consistency ([Level Up, Aug 2025](https://levelup.gitconnected.com/beyond-syntax-a-research-driven-showdown-of-python-node-js-2d03abcfca33)).

- **Node.js/TypeScript** is the default for the **API gateway** (if self-hosted) and **chat service**. Node.js's event-loop model is well-suited to the chat service's workload: thousands of long-lived WebSocket connections with intermittent message traffic. The non-blocking I/O model handles connection fanout efficiently without the memory overhead of thread-per-connection. TypeScript provides type safety for the complex message schemas in chat protocols. The API gateway benefits from Node.js's rapid development velocity and the rich middleware ecosystem (Express, Fastify) for request transformation and auth. Kong's Lua plugin layer is an alternative, but a custom Node.js BFF (Backend for Frontend) layer can abstract platform-specific differences for browser and mobile clients ([Talent500, Dec 2025](https://talent500.com/blog/backend-2025-nodejs-vs-python-vs-go-java-comparison/)).

- **Python** is reserved for the **analytics service** and any ML/moderation pipelines. Python's ecosystem (NumPy, Pandas, scikit-learn, PyTorch) is unmatched for data processing and model inference. The analytics service ingests playback events via Kafka, processes them with Apache Flink or Kafka Streams, and stores aggregates in ClickHouse. Moderation models (Perspective API, OpenAI Moderation API) are called from Python services. Python's slower runtime is acceptable here because analytics and moderation are not latency-critical paths — they operate on batch or near-real-time data, not on the request/response path of live streaming.

This polyglot approach is not gratuitous: each language is chosen for the service's dominant workload, and the team size (~20–50 engineers) is sufficient to maintain three language runtimes without excessive cognitive load, especially when each language is confined to a small number of services.

#### Authentication: JWT, OAuth2/OIDC, and Stream-Specific Tokens

The system uses a layered authentication strategy:

**User authentication** uses **OAuth2/OIDC** for social login (Google, Apple, GitHub) and **JWT access tokens** for API access. The OAuth2 authorization code flow with PKCE is used for mobile and browser clients; the identity provider (IdP) returns an ID token (JWT) and an access token. The API gateway validates the JWT signature (using the IdP's JWKS endpoint), checks expiration and audience claims, and forwards the user identity to downstream services via a header (`X-User-Id`). Short-lived access tokens (5–15 minutes) paired with longer-lived refresh tokens (7–30 days) balance security and user experience. The refresh token is rotated on each use, and the old token is invalidated — preventing token reuse attacks ([LoginRadius, Apr 2026](https://www.loginradius.com/blog/identity/jwt-vs-session-based-authentication)).

The choice of JWT over server-side sessions is driven by the microservices architecture: JWTs are stateless, so any service can validate a token without calling a central session store. This eliminates the session-store bottleneck that becomes a critical-path dependency at scale. However, JWT revocation requires either a short token lifetime (limiting the window of misuse) or a distributed revocation list (Redis-backed denylist checked by the gateway). For a streaming platform, the short-lifetime + refresh-rotation pattern is sufficient because the primary risk is token theft, not session fixation.

**Stream-specific authentication** operates at two levels:

- **Ingest tokens** (broadcaster → server): When a broadcaster starts streaming, the stream service generates a signed token containing the room ID, stream ID, and expiration (typically 1–4 hours). For RTMP ingest, this token is embedded in the stream key (e.g., `stream-key?token=<JWT>`). The ingest server (SRS, LiveKit) validates the token before accepting the connection. For RTMPS (RTMP over TLS), the TLS layer provides transport encryption, and the token provides application-level authorization. For WHIP ingest, the token is sent as a bearer token in the HTTP POST request. Unauthorized publishers are rejected at the ingest server before any media enters the transcoding pipeline.

- **Playback tokens** (server → listener): For private or paid streams, the CDN requires a signed URL for segment access. CloudFront signed URLs (or signed cookies) embed an expiration time, IP restriction, and a cryptographic signature. The stream service generates these tokens on behalf of authorized listeners, and the CDN edge validates them before serving segments. For HLS playback, the `.m3u8` playlist URL and segment URLs are signed; for WebRTC, the WHEP session URL is similarly protected. This approach offloads authorization to the CDN edge, avoiding a round-trip to the origin for every segment request ([Mux, 2024](https://www.mux.com/articles/securing-video-playback-with-signed-urls)).

#### Service Communication: REST, gRPC, and Async Messaging

The system uses three communication patterns, selected by latency and reliability requirements:

**Synchronous REST (HTTP/1.1 + JSON)** is used for client-facing API calls through the gateway and for simple service-to-service calls where the request-response pattern is natural (e.g., user service → room service to validate room membership). REST's ubiquity, debuggability, and JSON human-readability make it the default for external-facing and low-complexity internal calls. However, JSON serialization overhead and HTTP/1.1's lack of multiplexing make it suboptimal for high-throughput internal paths.

**Synchronous gRPC (HTTP/2 + Protocol Buffers)** is used for internal service-to-service calls where latency and throughput matter. gRPC's HTTP/2 transport enables multiplexing multiple requests over a single TCP connection, and Protocol Buffers provide 10x smaller payloads and 77% lower latency than JSON for small messages ([Tech Insider, Apr 2026](https://tech-insider.org/grpc-vs-rest-2026/)). The stream service calls the room service via gRPC to register a new stream; the chat service calls the user service via gRPC to resolve @mentions. gRPC's strong typing (protobuf schema) and code generation reduce integration bugs between services. The trade-off is that gRPC requires HTTP/2 and is not directly callable from browsers (a gRPC-Web proxy or the API gateway handles browser-to-gRPC translation) ([AWS, 2024](https://aws.amazon.com/compare/the-difference-between-grpc-and-rest/)).

**Asynchronous message bus** is used for event-driven communication where the sender does not need an immediate response. The primary bus is **NATS** for lightweight, ephemeral events (stream state changes, chat fanout triggers) and **Apache Kafka** for durable, replayable event streams (playback analytics, chat history persistence). NATS is preferred for control-plane events because of its sub-millisecond latency, at-most-once delivery (acceptable for ephemeral signals), and minimal operational overhead — it is a single binary with no external dependencies. Kafka is preferred for analytics and chat history because of its durability, consumer group semantics, and ability to replay events for late-joining consumers or batch processing ([Index.dev, 2025](https://www.index.dev/skill-vs-skill/backend-kafka-vs-rabbitmq-vs-nats)). RabbitMQ is an alternative for task queues (e.g., transcoding job dispatch) where message acknowledgment and dead-letter queues are needed.

The decision framework:

| Pattern | Use When | Example |
|---|---|---|
| REST | Client-facing, simple queries, debuggability | User profile fetch, room metadata query |
| gRPC | Internal, low-latency, high-throughput | Stream service → room service registration |
| NATS | Ephemeral events, fire-and-forget | Stream started/stopped notifications |
| Kafka | Durable events, replay, analytics | Playback events, chat history |

#### Service Discovery and Configuration in Kubernetes

Service discovery is handled by **Kubernetes DNS** (CoreDNS). Each microservice is exposed as a Kubernetes Service with a stable DNS name (`user-service.default.svc.cluster.local`), and the API gateway and other services resolve dependencies via DNS. This eliminates the need for a separate service registry (Consul, Eureka) at this scale. Kubernetes Services provide internal load balancing (round-robin across pods) and health-check-based endpoint removal.

For **configuration management**, the system uses Kubernetes ConfigMaps and Secrets for environment-specific configuration (database connection strings, JWT signing keys, API keys for external services). Sensitive values (database passwords, OAuth client secrets, CDN signing keys) are stored in Kubernetes Secrets, with external secret management (AWS Secrets Manager, HashiCorp Vault) for production environments. The Spotify case study demonstrates that a platform running 1,600+ production services on Kubernetes can manage configuration at scale using native Kubernetes primitives, though they migrated from a homegrown orchestration system (Helios) to standardize on Kubernetes ([Kubernetes Case Study: Spotify](https://kubernetes.io/case-studies/spotify/); [Altoros, Sep 2021](https://www.altoros.com/blog/spotify-runs-1600-production-services-on-kubernetes/)).

For **dynamic configuration** (feature flags, rate limit thresholds, A/B test parameters), the system uses a lightweight configuration service backed by etcd or a Redis key-value store, with watch-based propagation to service instances. This avoids the need for a full configuration management platform (Apollo, Nacos) at this scale.

#### Service Mesh: Over-Engineered at This Scale

A service mesh (Istio, Linkerd) provides mTLS between services, traffic management (canary, circuit breaking), observability (distributed tracing, metrics), and policy enforcement. At 10k–100k concurrent users with ~5–10 control-plane services, a service mesh is **over-engineering**.

The operational cost of a service mesh is significant: each service gets a sidecar proxy (Envoy for Istio, Linkerd2-proxy for Linkerd) that adds 5–10ms latency per request and consumes CPU/memory on every node. Istio's control plane (istiod) requires dedicated resources and expertise to operate. Linkerd is lighter — benchmarks show it adds 40–400% less latency than Istio — but still introduces a sidecar per pod and a control plane to manage ([Buoyant, 2024](https://www.buoyant.io/linkerd-vs-istio); [Linkerd, May 2021](https://linkerd.io/2021/05/27/linkerd-vs-istio-benchmarks/)).

For a medium-sized team, the benefits of a service mesh are better achieved through simpler mechanisms:

- **mTLS**: Kubernetes NetworkPolicies and pod-to-pod TLS (via cert-manager) provide network-level encryption without a sidecar.
- **Circuit breaking**: Implemented in the API gateway (Kong's circuit breaker plugin) and in client libraries (gRPC retry policies).
- **Observability**: OpenTelemetry instrumentation in each service, with Jaeger/Tempo for distributed tracing — no sidecar required.
- **Traffic management**: Kubernetes Ingress/Gateway API with canary routing (Flagger, Argo Rollouts) handles progressive delivery.

A service mesh becomes justified when the service count exceeds ~20–30, when multi-cluster traffic management is required, or when the team needs fine-grained L7 traffic policies (per-user rate limiting, header-based routing) that cannot be expressed at the gateway. At the proposed scale, the team should defer a service mesh and revisit when the operational complexity of managing service-to-service communication exceeds the cost of operating the mesh.

#### Summary: Build vs. Buy

| Component | Recommendation | Rationale |
|---|---|---|
| API Gateway | Kong (self-hosted) or AWS API Gateway (managed) | Kong's plugin ecosystem and DB-less mode reduce operational overhead; AWS API Gateway eliminates ops but locks in |
| Service mesh | Defer; use Kong + OpenTelemetry | Over-engineering at 5–10 services; revisit at 20+ |
| Service discovery | Kubernetes DNS (CoreDNS) | Native, zero additional infrastructure |
| Message bus | NATS (ephemeral) + Kafka (durable) | NATS for control-plane events; Kafka for analytics/chat history |
| Auth | OAuth2/OIDC + JWT (self-hosted) or Auth0/Clerk (managed) | Self-hosted reduces cost; managed reduces ops for social login |
| Language strategy | Go (room/stream), Node.js/TypeScript (gateway/chat), Python (analytics/ML) | Each language matched to service workload; team size supports 3 runtimes |

### Storage, Caching & Data Layer

The storage and data layer for a distributed audio streaming platform with live chat must serve three fundamentally different workloads: (1) **structured metadata** — users, rooms, streams, memberships — which is low-volume, heavily joined, and transactional; (2) **high-velocity chat messages** — append-heavy, time-ordered, write-dominated, with reads concentrated on recent data; and (3) **playback telemetry** — millions of small events per hour that must be aggregated in real time for QoE monitoring. No single database handles all three well. The design below uses a polyglot persistence strategy, with each store matched to the workload it is shaped for, following the same architectural pattern that Discord, Slack, and Meta have converged on for chat at scale ([GetStream](https://getstream.io/blog/chat-app-database/)).

---

#### Data Model and Access Patterns

The relational core stores entities that change slowly and require transactional integrity:

| Entity | Key Fields | Access Pattern |
|--------|-----------|----------------|
| `users` | `user_id`, `username`, `email`, `created_at`, `preferences` (JSONB) | Read-heavy by `user_id`; occasional writes on profile update |
| `rooms` | `room_id`, `title`, `broadcaster_id`, `status` (live/offline), `created_at`, `metadata` (JSONB) | Read-heavy by `room_id`; status transitions on stream start/end |
| `streams` | `stream_id`, `room_id`, `started_at`, `ended_at`, `ingest_key`, `playback_token`, `recording_path` | Write on stream start; read by `room_id` for active stream lookup |
| `chat_messages` | `message_id`, `room_id`, `user_id`, `body`, `type`, `created_at`, `edited_at`, `deleted_at` | Append-heavy writes; range reads by `(room_id, created_at)` |
| `moderations` | `moderation_id`, `room_id`, `target_user_id`, `action`, `reason`, `created_at` | Write on moderator action; read for ban enforcement |
| `recordings` | `recording_id`, `stream_id`, `storage_key`, `duration`, `format`, `created_at` | Write on stream end; read for VOD playback |

The `chat_messages` table is the highest-volume entity in the system. At 10k concurrent listeners with even modest chat activity (e.g., 1 message per user per minute), the system sustains ~10,000 writes/minute with reads concentrated on the most recent 50–100 messages per room. This access pattern — append-heavy writes, partition-keyed reads ordered by time, with the active set always being the most recent window — is the defining characteristic that drives the storage choice for chat history ([GetStream](https://getstream.io/blog/chat-app-database/)).

---

#### Relational Database: PostgreSQL as the Primary Store

**PostgreSQL** is the recommended primary relational database. Its JSONB type accommodates flexible metadata (room preferences, user settings, stream configuration) without schema migrations, while its mature ecosystem — including `pg_partman` for time-based table partitioning, logical replication for read replicas, and strong operational tooling — makes it the lowest-risk choice for a medium-sized team.

**CockroachDB** is the recommended alternative if multi-region write latency is a hard requirement. CockroachDB provides PostgreSQL wire compatibility with horizontal scaling and automatic multi-region replication, eliminating the need for manual read-replica management. However, it carries higher operational cost and complexity, and for a platform with 10k–100k concurrent users (not millions of writes per second), a single-region PostgreSQL instance with read replicas in secondary regions is sufficient and simpler to operate. CockroachDB becomes justified only when the team needs active-active multi-region writes with strong consistency — a requirement that typically emerges at larger scale ([Cockroach Labs](https://www.cockroachlabs.com/compare/cockroachdb-vs-postgresql/); [Bytebase](https://www.bytebase.com/blog/cockroachdb-vs-postgres/)).

**MySQL** remains a viable alternative but offers no advantage over PostgreSQL for this workload. PostgreSQL's superior JSONB support, richer indexing (GIN, GiST), and more mature partitioning make it the better fit for a platform where metadata schemas evolve as features are added.

For chat messages specifically, PostgreSQL with a composite index on `(room_id, created_at)` and time-based table partitioning works well **under ~10 million messages in a single region**. Beyond that, the B-tree index maintenance and vacuum overhead become operational burdens, and a purpose-built wide-column store is preferred ([GetStream](https://getstream.io/blog/chat-app-database/)).

---

#### Chat Message Storage

Chat messages are stored in a wide-column store (ScyllaDB) with TTL-based expiration, using a hybrid Redis Streams + ScyllaDB architecture for hot and cold history. See S4.2 for the full chat persistence architecture.

---

#### Object Storage: S3 / MinIO for Recordings and VOD

Recorded streams, VOD segments, and emote/media assets are stored in **object storage**. The choice is between:

- **AWS S3** (or GCS): Managed, durable, CDN-integrated, with lifecycle policies for automatic tiering to Infrequent Access or Glacier. S3 is the default for cloud-first deployment.
- **MinIO**: Open-source, S3-API-compatible, self-hosted. MinIO is the recommended choice for teams that want to avoid cloud vendor lock-in or need on-premises deployment for data sovereignty. It integrates with the same S3 client libraries and supports erasure coding for durability ([MinIO](https://docs.antmedia.io/guides/recording-live-streams/s3-recording-and-integration/minio-storage/)).

The recording pipeline works as follows: live streams are recorded at the SFU/egress level (via LiveKit Egress or FFmpeg), producing segmented audio files (`.fMP4` or `.ts`) that are written to object storage. The `recordings` table in PostgreSQL stores the metadata (storage key, duration, format), while the actual bytes live in S3/MinIO. Clients fetch recordings through the same CDN path used for live HLS delivery, with token-signed URLs for access control. This separation — metadata in the relational store, bytes in object storage — avoids bloating the database with large binary columns and keeps the hot path for metadata queries fast ([GetStream](https://getstream.io/blog/chat-app-database/); [FastPix](https://fastpix.com/blog/system-design-and-site-architecture-for-an-audio-streaming-app-like-spotify)).

---

#### Caching Layer: Redis for Hot Data

**Redis** serves as the caching and ephemeral-state layer, handling four distinct workloads:

1. **Active room metadata**: Room configuration, stream status, and broadcaster details are cached with a TTL of 30–60 seconds. On cache miss, the service falls back to PostgreSQL and repopulates the cache. This reduces database load proportionally to the cache hit rate — for a popular stream, the metadata is read thousands of times per second but changes only when the stream starts or ends ([Redis](https://redis.io/docs/latest/develop/use-cases/cache-aside/)).

2. **User sessions**: JWT validation results and session state are cached to avoid hitting the user service on every API request. Session keys use a TTL matching the JWT expiry.

3. **Rate limit counters**: Token-bucket and sliding-window rate limiters for chat messages and API calls are implemented in Redis using atomic `INCR` + `EXPIRE` operations. This provides sub-millisecond rate limit checks without database writes.

4. **Presence and viewer counts**: Online/offline status and viewer counts are tracked in Redis using HyperLogLog for approximate cardinality and Sets for exact online status. See S4.2 for the full presence tracking implementation.

The **cache-aside** pattern is the recommended strategy: the application reads from Redis on every request, falls back to the primary database on a miss, and writes the result back to Redis with a TTL. On writes, the application updates the database and invalidates the cache key. This pattern keeps P95 read latency under 5 ms for cached entities at peak traffic and reduces primary database load proportionally to hit rate ([Redis](https://redis.io/docs/latest/develop/use-cases/cache-aside/)).

A critical concern is the **cache stampede** — when a popular key expires under high concurrency, dozens of processes simultaneously query the database for the same record. Redis mitigates this through Lua scripting for atomic probabilistic early refresh or mutex locks, ensuring only one process repopulates the cache while others serve stale data briefly ([Redis](https://redis.io/docs/latest/develop/use-cases/cache-aside/)).

---

#### Analytics Pipeline: Kafka → Flink → ClickHouse

The analytics pipeline captures playback events emitted by client-side players (browser and mobile) and processes them in real time for QoE monitoring. The pipeline architecture is:

```
Client Players → Kafka (event ingestion) → Flink/Kafka Streams (real-time processing) → ClickHouse (time-series storage) → Grafana (dashboards)
```

**Event ingestion via Apache Kafka**: Playback events are emitted from clients as JSON or Protocol Buffer messages and published to Kafka topics partitioned by `room_id` or `stream_id`. Kafka's pull-based consumption model, partition replication, and configurable retention (hours to days) make it the right choice for durable event ingestion. Redis Pub/Sub is explicitly **not** used for this path — Redis does not retain messages after delivery and cannot support replay or multiple independent consumers ([AWS](https://aws.amazon.com/compare/the-difference-between-kafka-and-redis/)).

**Real-time processing with Apache Flink**: Flink consumes the Kafka stream and computes QoE metrics in real time using windowed aggregations (tumbling or sliding windows of 10–60 seconds). The key metrics computed are:

| Metric | Definition | Target |
|--------|-----------|--------|
| **Startup Time (TTFF)** | Duration from play intent to first frame render | < 1s excellent, < 2s acceptable, > 4s abandonment risk |
| **Rebuffer Ratio** | Total rebuffer duration / total watch time | < 0.5% (at 2%, viewers hemorrhage) |
| **Exit Before Video Starts (EBVS)** | % of play attempts where viewer leaves before first frame | < 5% |
| **Error Rate** | Errors per view (fatal and non-fatal) | Non-fatal < 1%, fatal < 0.1% |
| **Bitrate Switch Frequency** | Number of ABR switches per minute | Context-dependent; frequent switching indicates instability |

These metrics follow the CTA-2066 standard for streaming QoE events and CTA-5004 (CMCD) for player-attached request data, ensuring consistent definitions across dashboards ([Fora Soft](https://www.forasoft.com/learn/video-quality/articles-vqm/streaming-qoe-metrics); [Mux](https://www.mux.com/articles/video-analytics-for-developers-guide)).

Research from Conviva (SIGCOMM 2011) and Akamai (IMC 2012) establishes that **rebuffer ratio has the largest impact on engagement** across all content types, and that viewers begin abandoning once startup exceeds ~2 seconds, with each additional second raising abandonment by ~5.8 percentage points. A 6-second startup on 1M play attempts yields ~232,000 lost sessions compared to a 2-second start ([Fora Soft](https://www.forasoft.com/learn/video-quality/articles-vqm/streaming-qoe-metrics)).

**Flink vs. Kafka Streams**: Flink is recommended for this pipeline because it supports both bounded and unbounded streams, provides exactly-once processing semantics, and handles complex event-time windowing with late-arriving data. Kafka Streams is a simpler embedded library that is adequate for basic aggregations but lacks Flink's stateful processing capabilities, backpressure handling, and support for complex event processing patterns. For a medium-sized team, Flink's operational complexity is justified by the need for accurate windowed aggregations over late-arriving client events ([Conduktor](https://www.conduktor.io/glossary/kafka-streams-vs-apache-flink); [Onehouse](https://www.onehouse.ai/blog/apache-spark-structured-streaming-vs-apache-flink-vs-apache-kafka-streams-comparing-stream-processing-engines)).

**Time-series storage with ClickHouse**: Processed metrics are written to ClickHouse, a columnar OLAP database optimized for time-series aggregations. ClickHouse's columnar storage with LZ4/ZSTD compression achieves high compression ratios (often 10:1 for telemetry data), and its SQL interface supports ad-hoc queries for debugging. **TimescaleDB** (a PostgreSQL extension) is the alternative for teams that want to keep everything in PostgreSQL, but ClickHouse outperforms it on large-scale aggregations and compression efficiency ([Tinybird](https://www.tinybird.co/blog/clickhouse-vs-timescaledb); [DoubleCloud](https://medium.com/doublecloud-insights/clickhouse-vs-timescaledb-what-is-the-difference-a-detailed-comparison-62127a989d8d)).

**Acceptable latency**: The end-to-end pipeline from client event to dashboard visibility should be under 30 seconds for real-time QoE monitoring. This is sufficient for detecting degradation during a live stream and triggering alerts. Batch processing with Apache Spark runs on the same data (exported from Kafka to S3) for offline analysis, model training, and historical trend reporting.

#### Data Retention and GDPR Deletion

Data retention policies must balance product requirements (chat history for late joiners, recordings for VOD) against GDPR's storage limitation principle — personal data should only be kept as long as necessary for the purpose ([Proton](https://proton.me/business/blog/data-retention-policy)).

| Data Type | Retention Policy | Rationale |
|-----------|-----------------|-----------|
| Chat messages | 30–90 days (configurable per room) | Late joiners need recent history; indefinite retention is rarely justified |
| Stream recordings | 90 days default; user-configurable | VOD value decays over time; storage cost accumulates |
| Playback events | 180 days hot (ClickHouse), 1 year cold (S3) | Sufficient for trend analysis; aggregate after 1 year |
| User profiles | Until account deletion | GDPR right to erasure |
| Moderation records | 1 year minimum | Legal and safety compliance |

GDPR's right to erasure (Article 17) requires that when a user deletes their account, their personal data — including chat messages, profile information, and playback history — must be deleted or anonymized. In practice, this means:

- **Chat messages**: The `user_id` foreign key is set to NULL (anonymized) rather than deleting the message row, preserving conversation context while removing personal data. ScyllaDB's TTL-based expiration handles the eventual cleanup of old messages.
- **Recordings**: If a recording contains the deleted user's audio, the recording is either deleted or the user's segments are excised. For audio-only streaming, this is simpler than video — the user's audio track can be removed from the mixed recording.
- **Playback events**: Aggregated metrics are retained (they are not personal data once anonymized), but raw events with `user_id` are purged.

Automated retention schedules should be implemented as cron jobs or Kubernetes CronJobs that run TTL expiration and anonymization queries, aligning with GDPR's data minimization principles ([Smarsh](https://www.smarsh.com/blog/gdpr-call-recording-rules-what-should-you-do-to-comply/)).

---

#### Data Consistency: Eventual Consistency and the Saga Pattern

In a microservices architecture, operations that span multiple services — such as starting a stream (which involves the room service, stream service, and media pipeline) — cannot use distributed transactions (2PC) without introducing unacceptable latency and availability risks. The **Saga pattern** is the recommended approach: each step in the cross-service operation is a local transaction with a compensating action that undoes it if a subsequent step fails ([Microservices.io](https://microservices.io/patterns/data/saga.html); [Temporal](https://temporal.io/blog/mastering-saga-patterns-for-distributed-transactions-in-microservices)).

For example, the "start stream" saga proceeds as:

1. **Room service**: Set room status to `live` (local transaction).
2. **Stream service**: Create stream record, generate ingest token (local transaction).
3. **Media pipeline**: Allocate SFU node, configure transcode job (local transaction).

If step 3 fails, the compensating actions are: release the SFU node allocation, mark the stream record as `failed`, and set room status back to `offline`. Each compensating action is idempotent, ensuring that retries do not cause partial state.

**Eventual consistency** is the accepted model for cross-service data. The room status in PostgreSQL may briefly show `live` while the SFU is still initializing — this is acceptable because the client polls the room status API and will see the stream as available once the media pipeline is ready. The system does not require strong consistency between the room metadata store and the media server state; it requires that the system converges to a consistent state within a bounded time (typically < 5 seconds).

For the chat subsystem, consistency requirements are even more relaxed. Chat messages are written to ScyllaDB first (the source of truth), and a CDC pipeline (Debezium → Kafka → Elasticsearch) asynchronously updates the search index. The search index may lag by 1–2 seconds but is never wrong — it can only lag, never diverge ([GetStream](https://getstream.io/blog/chat-app-database/)). Presence, typing indicators, and unread counts in Redis are explicitly best-effort: if Redis restarts, clients reconnect and the state rebuilds from durable stores within seconds.

#### Summary: Storage Technology Selection

| Layer | Technology | Justification |
|-------|-----------|---------------|
| Relational metadata | PostgreSQL (primary), CockroachDB (multi-region alt) | JSONB for flexible metadata, mature ecosystem, partitioning support |
| Chat messages | Wide-column store with TTL expiration (see S4.2) | Append-heavy writes, partition-keyed reads, TTL expiration, horizontal write scaling |
| Object storage | AWS S3 / GCS (managed), MinIO (self-hosted) | Durable, CDN-integrated, lifecycle policies, S3 API compatibility |
| Cache & ephemeral state | Redis | Sub-millisecond reads, cache-aside pattern, rate limiting, presence, pub/sub |
| Event ingestion | Apache Kafka | Durable, replayable, partition-replicated, multiple independent consumers |
| Real-time processing | Apache Flink (primary), Kafka Streams (simpler alt) | Stateful windowing, exactly-once, event-time processing |
| Time-series analytics | ClickHouse (primary), TimescaleDB (PostgreSQL alt) | Columnar compression, fast aggregations, SQL interface |
| Batch processing | Apache Spark | Offline analysis, model training, historical trends on S3-exported data |

## Infrastructure, Security & Observability

### Kubernetes Orchestration, Autoscaling & CI/CD

#### Why Kubernetes as the Orchestration Layer

Kubernetes is the default orchestration choice for this platform because it provides a unified control plane for the four fundamentally different workload types in the system: stateless API services, stateful media servers (SFUs), ephemeral transcoding workers, and long-lived WebSocket chat gateways. A medium-sized team of 20–50 engineers cannot afford to operate separate deployment pipelines for each workload class. Kubernetes abstracts the underlying compute—whether EKS, GKE, or self-hosted—behind a common API, allowing the same `kubectl` and GitOps workflows to manage an SFU pod, a chat server deployment, and a transcoding Job. The key justification is not containerization itself (Docker alone would suffice for packaging) but the **scheduling, self-healing, and autoscaling primitives** that Kubernetes provides out of the box: liveness/readiness probes, horizontal pod autoscaling, rolling updates, and resource quotas. These are essential when a single viral stream can cause a 10x traffic spike within minutes.

The alternative—deploying directly on VMs with systemd or a process supervisor—would require building custom health-check, restart, and scaling logic for each service class. For a team this size, that operational overhead is not justified when managed Kubernetes is available at ~$73/month for the control plane ([Sedai, 2026](https://sedai.io/blog/kubernetes-cost-eks-vs-aks-vs-gke)).

#### Managed Kubernetes (EKS/GKE) vs. Self-Hosted

For a medium-sized company, **managed Kubernetes (EKS or GKE) is the recommended default**. The control plane cost is modest: EKS charges $0.10/hour per cluster (~$73/month), and GKE offers a free tier with $74.40 in monthly credits per billing account, equivalent to one free Autopilot or zonal Standard cluster per month ([AWS EKS Pricing](https://aws.amazon.com/eks/pricing/); [GKE Pricing](https://cloud.google.com/kubernetes-engine/pricing)). The real cost of self-hosting is not the control plane software (Kubernetes is open source) but the **operational labor**: managing etcd, API server upgrades, node provisioning, and multi-AZ redundancy. Analysis shows managed Kubernetes reduces operational overhead by 60–80% compared to self-managed clusters ([HostingX, 2026](https://hostingx.co.il/articles/managed-kubernetes-services-guide)), and is almost always cheaper when accounting for the hidden costs of self-hosting (redundancy, on-call rotation, upgrade windows) ([Hidora, 2025](https://hidora.io/en/blog/kubernetes-self-hosted-vs-managed)).

**Recommendation**: Use EKS if the team is already on AWS (CloudFront, S3, ALB integration is tighter); use GKE if multi-cloud or Google-native services (BigQuery for analytics, Cloud Memorystore for Redis) are preferred. Self-hosted Kubernetes (e.g., k3s on bare metal) is only justified if the team has existing bare-metal infrastructure and a dedicated platform engineering group of 3+ engineers—neither of which is assumed here.

#### Workload Deployment Patterns

Each workload class maps to a different Kubernetes primitive:

| Workload | Kubernetes Primitive | Scaling Strategy | Rationale |
|---|---|---|---|
| API services (user, room, stream, chat) | Deployment (stateless) | HPA on CPU/memory | Stateless; any pod can serve any request |
| WebSocket chat gateways | Deployment (stateless, but connection-affine) | HPA on custom metric (active WebSocket connections) | Stateless message routing, but connections are long-lived; need graceful draining |
| SFU media servers (LiveKit, SRS) | StatefulSet | HPA on custom metric (concurrent tracks/participants) + KEDA for bursts | Stateful: each room is pinned to a node; connections are long-lived and cannot be abruptly terminated |
| Transcoding workers (FFmpeg) | Kubernetes Job | KEDA on queue depth (Kafka lag, Redis list length) | Ephemeral; scale-to-zero when no transcoding is needed |

**Stateless API services** (user service, room/session service, stream service, chat service) are deployed as standard Deployments with HPA configured on CPU and memory utilization. These services hold no in-memory state—room metadata lives in PostgreSQL, session state in Redis—so any pod can serve any request. HPA with `minReplicas: 3` and `maxReplicas: 20` at 70% CPU target is a reasonable starting point.

**WebSocket chat gateways** are stateless in the message-routing sense (any gateway can push to any client via Redis Pub/Sub fanout), but each client maintains a persistent TCP connection to a specific pod. This means the pod must not be terminated while connections are active. The autoscaling metric should be **active WebSocket connections per pod**, exposed via a Prometheus custom metric (e.g., `websocket_connections_active`) and fed to HPA through the Prometheus Adapter ([Datadog, 2026](https://www.datadoghq.com/blog/autoscaling-custom-metrics/); [AWS re:Post, 2023](https://repost.aws/questions/QU0ruLF1T5TAStkSKcIJDN5Q/hpa-in-eks-based-on-number-of-active-connections)). A single Node.js or Go WebSocket server can handle 50k–100k concurrent connections on a 4 vCPU / 8 GB pod, so the HPA threshold might be set at 40k connections per pod to leave headroom.

**SFU media servers** are the most challenging workload. LiveKit's SFU is horizontally scalable—nodes use peer-to-peer routing via Redis to ensure clients joining a particular room connect to the same node ([LiveKit SFU docs](https://docs.livekit.io/reference/internals/livekit-sfu/)). This means each room is **pinned to a specific pod**, and the pod cannot be terminated without disconnecting all participants in that room. Deploying SFUs as a StatefulSet provides stable network identities (pod-0, pod-1, etc.) and ordered scaling, which is useful for capacity planning but does not solve the fundamental problem of long-lived connections.

**Transcoding workers** are ephemeral by nature. When a broadcaster starts a stream, an ingest event is published to a message queue (Kafka or Redis Streams), and a Kubernetes Job is created to run FFmpeg for the duration of the stream. KEDA (Kubernetes Event-Driven Autoscaling) monitors the queue depth and scales the worker pool from zero to N based on pending jobs ([KEDA](https://keda.sh/)). KEDA supports 70+ built-in scalers including Kafka lag, Redis Streams length, and Prometheus metrics, making it the natural fit for event-driven transcoding autoscaling. For audio-only transcoding, the CPU cost is low (a single FFmpeg process for Opus→AAC transcoding uses ~0.5–1 vCPU), so the worker pool can be small at baseline and scale up quickly for multi-bitrate ladder generation.

#### Autoscaling Stateful SFU Media Servers

The core challenge with SFU autoscaling is that **WebRTC connections are long-lived (minutes to hours) and stateful**. Unlike HTTP requests that can be retried on a different pod, a WebRTC peer connection is bound to a specific SFU node. Abruptly terminating a pod mid-session disconnects all participants.

The recommended approach combines three strategies:

1. **Custom metric-based HPA**: Expose the number of concurrent participants (or tracks) per SFU pod as a Prometheus metric. HPA scales up when the average participant count per pod exceeds a threshold (see S3.2 for the canonical SFU resource benchmark). For audio-only streaming, the per-participant CPU cost is significantly lower than the video benchmark, so a single pod can handle more participants.

2. **KEDA for burst handling**: HPA alone has a scale-up latency of 30–60 seconds (metrics collection interval + HPA evaluation period). For sudden spikes (a viral stream gaining 10k listeners in minutes), KEDA provides faster reaction by monitoring the rate of new join events from a Kafka topic or Redis counter. A KEDA `ScaledObject` can trigger aggressive step scaling when the join rate exceeds a threshold ([HackerNoon, 2025](https://hackernoon.com/scaling-real-time-video-on-aws-how-we-keep-webrtc-latency-below-150ms-with-kubernetes-autoscaling)).

3. **Graceful scale-down with connection draining**: When HPA decides to scale down, the SFU pod must not be terminated immediately. Instead:
   - The pod is marked as "draining" (a `preStop` hook sets a flag in Redis).
   - New join requests are routed to other pods (the room/session service checks the draining flag).
   - Existing connections are allowed to continue until participants naturally disconnect or are migrated.
   - `terminationGracePeriodSeconds` is set to 300+ seconds to give ample time for natural session end.
   - LiveKit supports **live migrations** via ICE restart, which allows a participant's connection to be seamlessly transferred to a different SFU node without dropping the session ([LiveKit blog, 2022](https://livekit.com/blog/scaling-webrtc-with-distributed-mesh)).

For multi-region deployment, each region runs its own EKS/GKE cluster with identical SFU deployments. Route 53 latency-based DNS routing directs clients to the nearest cluster, and a "geo-sticky" JWT embeds the selected region to prevent DNS fallback from moving a client to a different cluster mid-session ([HackerNoon, 2025](https://hackernoon.com/scaling-real-time-video-on-aws-how-we-keep-webrtc-latency-below-150ms-with-kubernetes-autoscaling)).

#### Connection Draining for Chat Servers

Rolling updates of WebSocket chat gateways require careful coordination to avoid dropping active connections. The pattern is:

1. **`preStop` hook**: When Kubernetes decides to terminate a pod, the `preStop` hook executes first. For chat servers, this hook should (a) call a `/shutdown` endpoint on the application, (b) wait 15–20 seconds for the load balancer to deregister the pod, and (c) allow the application to send WebSocket close frames to all connected clients.

2. **Application-level graceful shutdown**: On receiving SIGTERM, the chat server stops accepting new connections, sends a `CloseGoingAway` WebSocket close message to each client, and waits for clients to reconnect to a different pod. The load balancer (AWS ALB or Nginx) must be configured with a deregistration delay of 30+ seconds to match.

3. **`terminationGracePeriodSeconds`**: Set to 60–120 seconds for chat servers (long enough for clients to reconnect, short enough to not block the update indefinitely).

4. **`maxUnavailable: 0`**: Ensures no existing pod is terminated until a replacement is ready, preventing capacity loss during the update.

The key insight is that WebSocket connections are **not** like HTTP requests—they cannot be transparently retried on a different pod without the client noticing. The client must receive a close frame and initiate a reconnection, which the chat client's reconnection logic handles by reconnecting to a different pod in the pool ([OneUptime, 2026](https://oneuptime.com/blog/post/2026-02-09-connection-draining-rolling-updates/view); [Google Cloud Blog, 2018](https://cloud.google.com/blog/products/containers-kubernetes/kubernetes-best-practices-terminating-with-grace)).

#### Infrastructure-as-Code: Terraform + Helm + Kustomize

Infrastructure-as-code for Kubernetes spans three distinct layers, and the right approach combines one tool from each layer rather than trying to use a single tool for everything ([Pulumi, 2026](https://www.pulumi.com/blog/best-kubernetes-iac-tools-2026/)):

| Layer | Tool | Responsibility |
|---|---|---|
| Cluster & cloud infrastructure | **Terraform** (or OpenTofu) | Provision EKS/GKE clusters, VPCs, node pools, IAM roles, load balancers, S3 buckets, CloudFront distributions |
| Workload packaging | **Helm** (or Kustomize) | Package application Deployments, Services, ConfigMaps, HPA, KEDA ScaledObjects into versioned charts with templated values |
| Continuous reconciliation | **ArgoCD** (GitOps) | Continuously sync the desired state (declared in Git) with the actual cluster state; detect and correct drift |

**Terraform** is the default for the cluster layer because the AWS, Google, and Azure providers are mature, and the Kubernetes and Helm providers allow the same HCL codebase to reach into the cluster after provisioning. The main friction is that Terraform plans at plan time before talking to a live cluster, which can cause "plan differs from apply" surprises with CRDs (e.g., KEDA ScaledObject, ArgoCD Application). The workaround is a two-stage apply: provision the cluster in one Terraform run, then apply workload manifests in a second run ([Pulumi, 2026](https://www.pulumi.com/blog/best-kubernetes-iac-tools-2026/)).

**Helm** is the de facto package manager for Kubernetes workloads. Charts bundle manifests with a templating layer and values files, and the Artifact Hub ecosystem provides charts for common software (Redis, PostgreSQL, Prometheus, Nginx ingress). Helm 4 made Server-Side Apply the default, reducing drift bugs. For this platform, each microservice (user, room, stream, chat, analytics) gets its own Helm chart with environment-specific values files for staging and production.

**Kustomize** is an alternative to Helm for teams that prefer patch-based overlays over templating. It ships inside `kubectl` and avoids Helm's Go templating limitations, but is less expressive for conditional resource generation. For a medium-sized team, Helm is recommended for its ecosystem and packaging maturity; Kustomize is a reasonable choice for environment-specific overlays on top of a base chart.

**ArgoCD** implements GitOps: the desired state of every Kubernetes resource is declared in a Git repository, and ArgoCD continuously reconciles the cluster to match. This provides auditability (every change is a Git commit), rollback (revert to a previous commit), and drift detection (alert when the cluster deviates from Git). ArgoCD consumes the output of Helm/Kustomize rather than replacing them—it can render Helm charts or Kustomize overlays as part of the sync.

#### CI/CD Pipeline and Deployment Strategies

The CI/CD pipeline should be structured in two stages:

**Stage 1: Build and publish** (GitHub Actions or GitLab CI):
- Run unit and integration tests.
- Build container images and push to a registry (ECR, GCR, or Docker Hub).
- Run security scanning (Trivy, Snyk) on images.
- Update the GitOps repository with the new image tag (via a bot account or CI job).

**Stage 2: Deploy** (ArgoCD):
- ArgoCD detects the Git change and syncs the new image to the cluster.
- Deployment strategy depends on the service type:

| Service Type | Strategy | Tool | Rationale |
|---|---|---|---|
| API services (user, room, stream, chat) | **Canary** | Argo Rollouts or Flagger | Route 5% → 25% → 100% of traffic to the new version; automated analysis (error rate, latency) gates promotion |
| Chat gateways | **Rolling update** | Kubernetes native | Stateless; `maxUnavailable: 0` with `preStop` hook for connection draining |
| SFU media servers | **Blue-green** | Argo Rollouts | Spin up a parallel set of SFU pods with the new version; switch the service selector to the new pods; keep old pods running for draining |
| Transcoding workers | **Rolling update** | Kubernetes native | Ephemeral Jobs; old workers finish their current job before terminating |

**Canary deployments** for API services use [Argo Rollouts](https://argoproj.github.io/rollouts/) or [Flagger](https://flagger.app/), which integrate with ArgoCD and service meshes (Istio, Linkerd) or ingress controllers (Nginx, ALB) to shift traffic gradually. The canary analysis checks error rate (must stay below 1%), P99 latency (must not regress by more than 20%), and custom business metrics (e.g., stream join success rate) before promoting the canary to full rollout. If any check fails, the canary is automatically rolled back.

**Blue-green for SFU media servers** is necessary because SFU pods are stateful and cannot be gracefully drained in the same way as stateless services. The blue-green approach creates a parallel set of SFU pods (the "green" deployment) with the new version, then switches the Kubernetes Service selector to point to the green pods. The old "blue" pods remain running with their existing connections until those sessions naturally end. This is more resource-intensive (doubles SFU capacity during the update) but ensures zero-downtime for active streams. For a medium-sized company, this cost is acceptable if updates are batched (e.g., weekly) rather than continuous.

**GitHub Actions** is the recommended CI engine for a medium-sized company already using GitHub for source control. It provides matrix builds (build for multiple architectures), reusable workflows, and a large ecosystem of actions. **GitLab CI** is the alternative for teams using GitLab. The key principle is that CI builds and publishes images, while CD (ArgoCD) handles deployment—this separation ensures that the deployment mechanism is independent of the build tool.

#### WebRTC's Built-In Security Model: DTLS/SRTP

WebRTC provides **mandatory, non-negotiable encryption** at the protocol level—there is no unencrypted mode, and no API surface through which application code can bypass it. This is defined in [IETF RFC 8827](https://antmedia.io/webrtc-security/) (WebRTC Security Architecture), which mandates DTLS-SRTP as the sole permitted encryption mechanism for all WebRTC media streams. Browser vendors (Chrome, Firefox, Safari, Edge) enforce this independently—any WebRTC implementation that attempts to bypass DTLS-SRTP will be rejected.

The security model has three layers:

1. **DTLS (Datagram Transport Layer Security, RFC 6347)**: Handles key exchange and peer authentication. DTLS is a datagram-adapted variant of TLS designed for UDP transport. During the DTLS-SRTP handshake, both endpoints exchange certificates, verify each other's identity via SHA-256 fingerprints embedded in the SDP, and negotiate the SRTP keying material—all before the first media frame is transmitted. The mandatory cipher suite is `SRTP_AES128_CM_HMAC_SHA1_80` (128-bit AES counter-mode encryption with 80-bit HMAC-SHA1 authentication tag). As of 2025, the ecosystem is migrating from DTLS 1.2 to DTLS 1.3 (RFC 9147) ([Ant Media, 2026](https://antmedia.io/webrtc-security/)).

2. **SRTP (Secure Real-time Transport Protocol, RFC 3711)**: Encrypts the actual audio/video payloads. SRTP provides three guarantees: confidentiality (payload encryption), integrity (tamper detection via HMAC-SHA1), and replay protection (sequence number tracking). SRTP does not perform its own key exchange—the symmetric keys are derived entirely from the DTLS handshake via the DTLS-SRTP profile (RFC 5764). Once the DTLS handshake completes, SRTP handles all ongoing encryption independently; DTLS is not involved in per-packet processing ([Ant Media, 2026](https://antmedia.io/webrtc-security/)).

3. **Browser permission gates**: The `getUserMedia()` API requires explicit user consent for camera/microphone access, and WebRTC APIs are restricted to HTTPS origins only. This prevents unauthorized media capture at the OS level.

**How this differs from HLS/TLS security**: The HLS delivery path uses standard TLS (HTTPS) to encrypt the transport between the CDN edge and the client. This is transport-layer encryption—the media segments are encrypted in transit but are decrypted at the CDN edge (the CDN must decrypt to cache and re-serve segments). In contrast, WebRTC's DTLS-SRTP provides **end-to-end encryption at the media layer**: the DTLS encryption wraps the payload at the sender's device and can only be decrypted by the intended recipient. A TURN relay server forwards SRTP packets without being able to access plaintext media. This means the SFU (which acts as a TURN relay in the WebRTC path) cannot eavesdrop on media, even if compromised.

**Implication for the platform**: The WebRTC delivery path (LiveKit SFU) has baseline media encryption built in—no additional encryption layer is needed for media in transit. However, the **signaling channel** (WebSocket for WebRTC signaling, HTTPS for WHEP) must use WSS (Secure WebSocket) to prevent SDP fingerprint substitution attacks. If an attacker modifies the SDP in transit, they can substitute their own DTLS fingerprint and perform a man-in-the-middle attack on the DTLS layer. RFC 8827 explicitly states that signaling channel security is a prerequisite for DTLS-SRTP's MITM protections to hold ([Ant Media, 2026](https://antmedia.io/webrtc-security/)). For the HLS path, standard HTTPS/TLS is sufficient since the CDN terminates TLS at the edge.

### Observability, Monitoring & Alerting

A distributed audio streaming platform with live chat spans ingest, transcoding, packaging, delivery, and real-time messaging — each layer introducing distinct failure modes. Without a unified observability stack, latency regressions, media degradation, and chat outages become unreproducible incidents. This subsection defines a three-pillar observability architecture (metrics, logging, tracing) with SLO-driven alerting, justified for a medium-sized engineering team (~20–50 engineers) operating at 10k–100k concurrent listeners.

#### Metrics: Prometheus, Grafana, and Client-Side QoE Telemetry

**Infrastructure metrics** are collected via [Prometheus](https://prometheus.io/), the de facto monitoring toolkit for Kubernetes-native systems. Each microservice exposes a `/metrics` endpoint using the official `prometheus_client` library (language-specific: Go, Node.js, Python). Prometheus scrapes targets on a 15-second interval — short enough to capture media degradation (which manifests in seconds) but light enough to avoid TSDB overload. Key infrastructure metrics include CPU, memory, network I/O per service, and pod restart counters. For services running in Kubernetes, the [kube-state-metrics](https://github.com/kubernetes/kube-state-metrics) and [node-exporter](https://github.com/prometheus/node_exporter) agents expose cluster-level and host-level metrics respectively. A critical operational rule: **never use `user_id` or `room_id` as Prometheus label values** — high-cardinality labels explode the TSDB index and can crash Prometheus. Use `region`, `service`, and `msg_type` labels instead.

**Player QoE metrics** are collected from the client side, because the player — not the server — is the ultimate arbiter of quality. A CDN can count bytes leaving its edge, but only the player knows that the buffer emptied at second 47 and the picture froze for two seconds. On the browser, `navigator.sendBeacon()` flushes the QoE summary on the `visibilitychange` → `hidden` event, ensuring the end-of-session beacon survives page unload and mobile backgrounding. Batching events in memory and sending periodic bundles (rather than one request per event) prevents instrumentation from becoming a cost problem. For native mobile, platform-specific background-upload queues serve the same purpose. The [W3C WebRTC Statistics API](https://www.w3.org/TR/webrtc-stats/) (`RTCPeerConnection.getStats()`) provides low-level transport metrics — `inbound-rtp` (packets lost, jitter, bytes received), `remote-inbound-rtp` (round-trip time), and `outbound-rtp` (bytes sent, bitrate) — which are essential for the WebRTC delivery path. The open-source [ObserveRTC client-monitor-js](https://github.com/ObserveRTC/client-monitor-js) library wraps `getStats()` into anomaly detectors for network congestion, CPU limitation, and stuck RTP flows, providing a ready-made instrumentation layer for browser clients. The specific QoE metric definitions (startup time, rebuffering ratio, error rate, etc.) and the analytics pipeline that computes them are detailed in S6.2.

Server-side SFU metrics serve as **leading indicators** of client-perceived degradation. Client metrics are lagging indicators — by the time a viewer reports a freeze, the degradation has already occurred. Server metrics predict failure before user perception is impacted. LiveKit exposes Prometheus-compatible metrics out of the box (room count, participant count, packet loss, bandwidth). For SFUs that lack native Prometheus endpoints (Janus, mediasoup), a lightweight **exporter sidecar** polls the SFU's Admin/Stats API and translates JSON to Prometheus gauges. The key SFU health indicators are:

- **NACK count** (retransmission requests) — a spike indicates network congestion
- **PLI/FIR count** (keyframe requests) — expensive; if spiking, the encoder is overloading CPU
- **Participant legs per SFU node** — approaching the resource ceiling triggers horizontal scaling
- **Ingress/egress bitrate per stream** — identifies abnormal bandwidth patterns
- **ICE negotiation duration** — tracks signaling plane health

A 15-second Prometheus scrape interval with a federated architecture — regional Prometheus instances scraping local targets, with a central Thanos or Cortex aggregating cross-region metrics — prevents the latency penalty of a single global Prometheus scraping servers across continents.

**Dashboards and visualization** are built in [Grafana](https://grafana.com/), which natively queries Prometheus, Loki, and Tempo (traces). This unified interface allows engineers to pivot from a metric spike to the underlying logs to the trace of a specific request, all within a single UI. Dashboards are organized by subsystem: (1) media pipeline health (transcode queue depth, segment generation latency), (2) SFU cluster metrics (participant legs, NACK rates, packet loss by region), (3) delivery metrics (CDN cache hit ratio, origin egress volume), (4) chat subsystem (WebSocket connection count, message fanout latency, fanout-on-write lag), and (5) player QoE percentiles (p50/p95 startup time, rebuffering ratio, error rate by platform/region).

#### Logging: Structured JSON, Centralized Aggregation, and Correlation IDs

All services emit **structured JSON logging** — not plaintext — from day one. Structured logs are machine-parseable, indexable, and queryable. Every log entry includes a **correlation ID** (also called trace ID), generated at the API gateway entry point and propagated through all downstream services via HTTP headers (`X-Correlation-ID`) or gRPC metadata. This allows an engineer to reconstruct the full lifecycle of a listener joining a stream: from authentication → room join → playlist fetch → segment request → first frame rendered, crossing 5+ service boundaries.

For the **logging backend**, the choice between [Grafana Loki](https://grafana.com/oss/loki/) and the [ELK stack](https://www.elastic.co/elastic-stack/) (Elasticsearch, Logstash, Kibana) involves a trade-off between cost efficiency and search capability:

| Dimension | Grafana Loki | ELK (Elasticsearch) |
|-----------|-------------|---------------------|
| **Indexing** | Label-based metadata only (like Prometheus) | Full-text inverted index over all log content |
| **Storage cost** | Low — compressed chunks in object storage (S3/GCS) | High — index structures often exceed log data size |
| **Query model** | Label filter → grep-style sequential scan | Full-text search, complex boolean queries, ad-hoc analytics |
| **Operational burden** | Low — few components, Prometheus-native | High — shard tuning, index lifecycle management, JVM heap |
| **Best fit** | High-volume Kubernetes logs, operational troubleshooting | Security forensics, deep ad-hoc analysis across all log content |

For a medium-sized company running Kubernetes with ephemeral pods, **Loki is the recommended default**. It integrates natively with Prometheus and Grafana (the PLG stack: Promtail, Loki, Grafana), uses object storage for log bodies, and indexes only label metadata — dramatically reducing CPU, memory, and storage costs. The trade-off is weaker full-text search; Loki excels at label-scoped queries (`{app="sfu", region="us-east-1", stream_id="..."}`) but is not built for arbitrary keyword search across all logs. If the team requires deep forensic search (e.g., "find all log lines mentioning this error pattern across all services"), a secondary Elasticsearch instance can be maintained for security/audit purposes, with Loki handling the bulk of operational logging.

**Log volume discipline for the media plane**: logging every dropped packet or retransmission request in the WebRTC media path would saturate disk I/O faster than the network interface. Logs are reserved for control-plane events — signaling errors, authentication failures, ICE state transitions, and room join/leave events. Metrics handle the real-time health monitoring; logs are reactive tools for post-mortem analysis of specific session failures.

#### Distributed Tracing: Jaeger, Tempo, and OpenTelemetry

**Distributed tracing** is critical for debugging latency in a multi-service media pipeline. When a listener experiences a 3-second startup time, the trace reveals whether the delay originated in DNS resolution, API gateway authentication, room service lookup, CDN cache miss, origin segment generation, or client-side buffer priming. [OpenTelemetry](https://opentelemetry.io/) provides the instrumentation SDK — services are instrumented with auto-instrumentation libraries (or manual spans for custom operations) and traces are exported to a backend.

Two open-source trace backends are recommended:

- **[Jaeger](https://www.jaegertracing.io/)** (CNCF graduated): Mature, full-featured, supports Cassandra/Elasticsearch for storage. Jaeger v2 (late 2024) re-architects core components on top of the OpenTelemetry Collector, tightening OTEL compatibility.
- **[Grafana Tempo](https://grafana.com/oss/tempo/)** (CNCF incubating): Designed for high-scale, cost-efficient trace storage in object storage (S3/GCS). Stores traces cheaply and relies on metrics and logs for trace discovery — a "trace ID in logs" correlation model rather than standalone trace search.

For this platform, **Tempo is recommended** for a medium-sized team because it stores traces in cheap object storage, integrates with the existing Prometheus/Grafana/Loki stack, and avoids the operational burden of managing a Cassandra or Elasticsearch cluster for trace data. The trade-off: Tempo is less mature than Jaeger and its trace discovery relies on having metrics or logs with trace IDs already present — which the structured logging strategy provides.

**Tracing the WebRTC media path** requires special consideration. RTP packets lack the header space for trace IDs found in HTTP, and sampling distributed traces across a mesh of media servers often outweighs the benefit. The recommended approach is to trace the **control plane** (signaling, room join, ingest → transcode → package → CDN delivery) with OpenTelemetry, while using **WebRTC `getStats()`** as the primary observability signal for the UDP-based media plane itself. The `getStats()` API exposes `inbound-rtp`, `outbound-rtp`, `remote-inbound-rtp`, `candidate-pair`, and `transport` reports, which provide packet loss, jitter, RTT, and bandwidth at the transport level — the media-plane equivalents of server-side metrics.

#### SLO-Based Alerting: Error Budgets and Multi-Window Burn Rate

**Service Level Objectives (SLOs)** define target reliability for each service, and **error budgets** (100% − SLO) quantify how much unreliability the team can afford. For a medium-sized company's streaming platform:

| Service | SLO | Error Budget (30-day) | Equivalent Downtime |
|---------|-----|-----------------------|-------------------|
| API Gateway (control plane) | 99.95% | 0.05% | 4.38 hours/month |
| Ingest service (broadcaster entry) | 99.9% | 0.1% | 43.8 minutes/month |
| Media delivery (HLS CDN path) | 99.95% | 0.05% | 4.38 hours/month |
| WebRTC SFU (interactive path) | 99.9% | 0.1% | 43.8 minutes/month |
| Chat WebSocket gateway | 99.9% | 0.1% | 43.8 minutes/month |
| Chat message delivery | 99.5% (at-most-once) | 0.5% | 3.65 hours/month |

The **alerting strategy** follows Google SRE's multi-window, multi-burn-rate approach — the recommended best practice from the [SRE Workbook](https://sre.google/workbook/alerting-on-slos/). Instead of alerting when an error rate exceeds a threshold for a fixed duration (which produces alert fatigue), the system alerts when the **error budget burn rate** exceeds a threshold over multiple windows. Burn rate measures how fast, relative to the SLO, the service consumes its error budget:

> A burn rate of 1 means the service consumes exactly 100% of its error budget by the end of the SLO window. A burn rate of 10 means 1% error rate (for a 99.9% SLO) — exhausting the budget in 3 days. A burn rate of 1000 means 100% outage — exhausting the budget in 43 minutes.

The recommended configuration uses **two alert tiers per SLO**:

1. **Page (fast burn)**: Burn rate ≥ 14.4 over 1 hour OR burn rate ≥ 6 over 6 hours — meaning 5% of the 30-day error budget is consumed. This page alerts an on-call engineer immediately.
2. **Ticket (slow burn)**: Burn rate ≥ 3 over 1 day OR burn rate ≥ 1 over 3 days — meaning 2% of the error budget is consumed. This creates a ticket for the next business day, catching chronic low-grade degradation that doesn't warrant a page.

This multi-window approach provides good **precision** (alerts correspond to significant events), good **recall** (both fast outages and slow degradation are caught), and reasonable **detection time** (minutes for fast burn, hours for slow burn).

**Preventing alert fatigue** requires two additional practices: (1) **snooze windows** — suppress duplicate alerts for the same incident for a configurable cooldown period; (2) **error budget gates on deployments** — when a service's error budget is consumed (burn rate ≥ 1 for the full SLO window), halt automatic deployments of that service and require manual approval, creating a direct link between reliability and release velocity.

#### Infrastructure Monitoring vs. Product Monitoring

The distinction between infrastructure monitoring and product monitoring determines whether the on-call engineer is awakened for a problem that affects users:

**Infrastructure monitoring** answers: *Is the service up?* It tracks system-level health — CPU, memory, network I/O, pod restarts, disk usage, queue depths. A Prometheus alert on `up{job="sfu"} == 0` or `kube_deployment_status_replicas_unavailable{deployment="chat-gateway"} > 0` is an infrastructure alert. These alerts are necessary but insufficient — they detect component failure but not user experience degradation. A service can be fully operational (all pods healthy, CPU nominal) while users experience 8-second startup times due to a CDN cache misconfiguration.

**Product monitoring** answers: *Is the user experience good?* It tracks outcome-level metrics — player QoE percentiles (p95 startup time > 3s), rebuffering ratio > 2%, error rate > 1%, chat message delivery latency p95 > 500ms, buffer ratio by platform/region. These alerts fire when user-perceived quality degrades, even if infrastructure metrics look healthy. Product monitoring requires client-side telemetry beacons (the QoE instrumentation described above) ingested into a time-series database (Prometheus via a remote-write gateway, or a real-time analytics store like [ClickHouse](https://clickhouse.com/) for high-volume event data) with Grafana dashboards aggregating by platform, region, and stream tier.

The two layers complement each other: infrastructure monitoring provides **cause** (the SFU is CPU-saturated), product monitoring provides **effect** (startup times spiked in the EU region). When both alert simultaneously, the correlation is immediate. When only product monitoring fires, the engineer investigates infrastructure metrics for the root cause. When only infrastructure fires, the engineer assesses whether users are impacted or if the issue is contained to non-user-facing components.

#### Media Server Metric Exposure

Media servers expose metrics differently depending on their architecture:

| Media Server | Metric Exposure | Integration Approach |
|-------------|----------------|---------------------|
| **LiveKit** | Native Prometheus `/metrics` endpoint | Direct Prometheus scrape; room count, participant count, packet loss, bandwidth, track metrics |
| **SRS** | HTTP API for server info | Exporter sidecar polls `/api/v1/streams` and `/api/v1/clusters` every 15s, translates to Prometheus gauges |
| **Janus** | Admin API (`/admin` with `janusoverlord` secret) on port 7088 | Exporter polls for session/handle counts, NACK/PLI stats; custom plugin for detailed stream metrics |
| **mediasoup** | `worker.on('newrouter')` and `transport.on('trace')` events | Node.js event hooks push to central aggregator; no native Prometheus endpoint |
| **Ant Media Server** | REST API for stream metrics | Exporter polls `/WebRTCAppEE/rest/v2/streams` every 15s |

For LiveKit's native Prometheus metrics, the scrape target is the LiveKit server pod itself (port 7080 by default), exposing room-level and participant-level gauges. This eliminates the need for a custom exporter in the recommended architecture (LiveKit for the WebRTC path, SRS for the HLS path). For SRS, the exporter sidecar is a lightweight Go or Python binary running in the same pod, leveraging the [Prometheus client library](https://github.com/prometheus/client_golang) to expose SRS-specific metrics like `srs_streams_active`, `srs_clients_connected`, and `srs_bitrate_kbps` as Prometheus gauges.

**Client-side WebRTC stats** flow through a separate path: the browser or mobile app calls `getStats()` at 5-second intervals, aggregates the reports into QoE beacons, and POSTs them to a `/qoe/collect` endpoint (using `sendBeacon` for reliability). These events are ingested into Kafka for real-time processing (via Flink or Kafka Streams for computing percentile aggregations) and/or stored in ClickHouse for ad-hoc analytics. The real-time pipeline powers Grafana dashboards showing p50/p95/p99 QoE metrics by platform, region, and stream tier — the product monitoring layer that alerts engineers to user-perceived degradation before support tickets accumulate.

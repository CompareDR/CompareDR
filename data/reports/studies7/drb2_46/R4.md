## Auto-Scaling Technology Classification

### Reactive Methods

Reactive auto-scaling operates on a **post-event response** paradigm: resource adjustments are triggered only after load changes have already occurred and monitoring metrics have crossed predefined thresholds or rules. The core control loop follows a MAPE (Monitoring, Analysis, Planning, Execution) architecture, where the autoscaler continuously observes metrics, evaluates whether scaling is needed, determines the magnitude of adjustment, and executes the action via cloud provider APIs ([Qu et al. 2018](https://clouds.cis.unimelb.edu.au/papers/AutoScaleWebAppClouds-ACMCS.pdf)). While simple to implement and widely deployed, all reactive methods share an inherent **lag effect** — by the time a scaling action is triggered and new instances become operational, the workload surge may have already caused SLA violations. The following subsections detail six specific reactive methods.

---

#### 1. Threshold-Based (Rule-Based) Scaling

**Core Principle.** Threshold-based scaling uses static rules defined on continuous monitoring metrics such as CPU utilization, memory usage, network I/O, or request latency. A typical rule reads: "if CPU > 70% for 5 consecutive minutes, add one instance; if CPU < 30% for 5 minutes, remove one instance." Scaling actions are triggered when the evaluated metric breaches a predefined boundary. Two variants exist:

- **Horizontal scaling** adds or removes instances (VMs, pods) to match load changes.
- **Vertical scaling** adjusts the CPU or memory allocated to existing instances.

**Kubernetes HPA Implementation.** The Kubernetes HorizontalPodAutoscaler (HPA) operates as a control loop that runs at a configurable interval (`--horizontal-pod-autoscaler-sync-period`, default 15 seconds). During each cycle, the controller manager queries resource utilization from the metrics API (e.g., Metrics Server), computes the ratio between current and desired metric values across all targeted pods, and adjusts the replica count accordingly. If the ratio is sufficiently close to 1.0 (within a configurable tolerance of 0.1 by default), no scaling action is taken ([Kubernetes HPA Documentation](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)).

To prevent flapping — rapid oscillation between scale-up and scale-down actions caused by transient metric fluctuations — Kubernetes provides three stabilization parameters:

| Parameter | Default | Function |
|---|---|---|
| `--horizontal-pod-autoscaler-downscale-stabilization` | 5 minutes | Downscale stabilization window; the controller considers all scale recommendations within this window and selects the highest, smoothing out rapidly fluctuating metric values |
| `--horizontal-pod-autoscaler-cpu-initialization-period` | 5 minutes | Time window after pod start during which CPU usage is ignored (unless the pod is Ready and the metric sample was taken during the Ready period), excluding misleading high CPU from initializing pods (e.g., Java apps warming up) |
| `--horizontal-pod-autoscaler-initial-readiness-delay` | 30 seconds | Short delay after pod start during which pods that are currently Unready are treated as still initializing, even if they briefly transitioned to Ready, avoiding inclusion of pods that rapidly fluctuate between Ready and Unready during startup |

([Kubernetes HPA Documentation](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/))

**AWS EC2 Auto Scaling.** AWS provides three scaling policy types. **Simple scaling** policies trigger a single scaling action when a CloudWatch alarm breaches a threshold; **step scaling** policies define multiple step adjustments with different scaling increments based on the magnitude of the breach (e.g., add 1 instance if CPU > 70%, add 3 instances if CPU > 85%); **target tracking** policies maintain a target metric value by automatically calculating the required capacity ([AWS Step Scaling Documentation](https://docs.aws.amazon.com/autoscaling/application/userguide/step-scaling-policy-overview.html)).

**Cooldown periods** prevent oscillation. After a simple scaling action launches or terminates instances, the Auto Scaling group waits for a cooldown period (default 300 seconds / 5 minutes) before further simple scaling actions can begin. This allows the system to stabilize and the effects of the previous scaling activity to become visible in monitoring metrics. Critically, target tracking and step scaling policies can initiate scale-out activities immediately without waiting for the cooldown period to end — instead, individual instances have a warmup period during which their metrics are not fully trusted. While a scale-out is in progress, all scale-in activities from target tracking and step scaling are blocked until instances finish warming up ([AWS Cooldown Documentation](https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-scaling-cooldowns.html)).

**Google Cloud Compute Engine Autoscaler.** Google Cloud's autoscaler supports scaling based on CPU utilization or custom metrics. It operates in a reactive mode by default, scaling the managed instance group (MIG) based on real-time observed load. The autoscaler also supports a predictive mode (covered in S1.2), but its reactive threshold-based mode is the default behavior ([Google Cloud Autoscaler Documentation](https://docs.cloud.google.com/compute/docs/autoscaler/predictive-autoscaling)).

**VPA Pod-Restart Limitation.** The Kubernetes VerticalPodAutoscaler (VPA) adjusts pod resource requests and limits based on historical and real-time utilization analysis. However, VPA's default `Recreate` update mode requires **pod eviction and recreation** to apply resource changes — the updater evicts pods whose current resource requests differ significantly from recommendations, and the workload controller creates replacement pods with updated resources via the VPA admission controller. This means VPA cannot adjust resources in-place in its default mode, causing a brief service disruption during pod replacement. Newer update modes (`InPlaceOrRecreate` and `InPlace`) attempt to use the in-place pod resize feature (available as alpha in VPA 1.7.0 with Kubernetes 1.33+), but these require specific cluster feature gates and may have limitations on which resources can be modified without restart ([Kubernetes VPA Documentation](https://kubernetes.io/docs/concepts/workloads/autoscaling/vertical-pod-autoscale/)).

**Advantages.** Simple to implement and reason about; low computational overhead; widely supported across all major cloud providers; effective for workloads with gradual, sustained load changes.

**Limitations.** The lag effect — by the time new instances are operational (typically 60–120 seconds for VM boot, plus application startup time), the load spike may have already caused SLA violations. Threshold tuning is difficult: thresholds that are too sensitive cause oscillation (thrashing), while thresholds that are too conservative result in over-provisioning. Cooldown periods trade responsiveness for stability. VPA's pod-restart requirement causes service disruption during vertical scaling. Sudden, sharp traffic spikes that exceed the threshold-to-action latency cannot be handled effectively.

#### 2. Schedule-Based Scaling

**Core Principle.** Schedule-based scaling creates pre-scheduled resource adjustments at specific times to match predictable, periodic load patterns — for example, increasing capacity before daily business hours begin and decreasing it after hours end, or scaling up before a known weekly batch processing window.

**AWS Scheduled Scaling.** AWS EC2 Auto Scaling supports scheduled actions that increase or decrease the desired capacity of an Auto Scaling group at specified times. Scheduled actions can be one-time or recurring (using cron expressions). After a scheduled action executes, the group's scaling policies continue to make dynamic decisions within the new capacity bounds, allowing scheduled and reactive approaches to complement each other. A maximum of 125 scheduled actions can be created per Auto Scaling group ([AWS Scheduled Scaling Documentation](https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-scheduled-scaling.html)).

**Google Cloud Scheduled Scaling.** Google Cloud also supports schedule-based autoscaling through scaling schedules, which are recommended for one-time or non-recurring load patterns that do not follow daily or weekly cycles (predictive autoscaling handles recurring patterns) ([Google Cloud Autoscaler Documentation](https://docs.cloud.google.com/compute/docs/autoscaler/predictive-autoscaling)).

**Advantages.** Eliminates lag for known patterns; no monitoring overhead during off-peak periods; cost-efficient for workloads with strong diurnal or weekly cycles.

**Limitations.** Ineffective for unpredictable traffic spikes, flash crowds, or any deviation from the scheduled pattern. If the actual load differs from the scheduled capacity, the system may still require reactive threshold-based scaling as a backstop. Schedule maintenance requires manual updates when patterns change.

#### 3. Event-Driven Scaling

**Core Principle.** Event-driven scaling responds to discrete business events or alarms rather than continuous metric values. When a specific event occurs — such as a marketing campaign launch, a queue backlog exceeding a threshold, or a CloudWatch alarm state change — a scaling action is triggered immediately. This differs from threshold-based scaling in that the trigger is a discrete event signal rather than a continuously evaluated metric crossing a boundary.

**Implementation.** AWS supports event-driven scaling through CloudWatch Alarms that trigger scaling policies. For example, an SQS queue backlog alarm can trigger a target tracking scaling policy to add EC2 instances when the number of messages in the queue exceeds a threshold — this is particularly useful for batch processing workloads where CPU is a lagging proxy and the queue depth is the true bottleneck ([AWS SQS Scaling Documentation](https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-using-sqs-queue.html)). Custom CloudWatch metrics can also be published and used as scaling triggers, enabling application-specific event-driven scaling.

**Advantages.** Can respond to business-level events that are not captured by infrastructure metrics; useful for batch processing and message-driven architectures; can be combined with other scaling methods.

**Limitedations.** Still reactive — the event must occur before scaling triggers. Event storms can cause cascading scaling actions. Requires careful event design to avoid false positives. The lag between event detection and instance readiness remains.

#### 4. Queuing Theory-Based Scaling

**Core Principle.** Queuing theory-based scaling models the cloud service system as a mathematical queue, where requests arrive at rate λ (arrival rate) and are served at rate μ (service rate) by c servers. The autoscaler dynamically adjusts the server count c to maintain response time or queue length below target thresholds.

**Key Models and Formulas.**

- **M/M/1 queue**: Single-server model with Poisson arrivals and exponential service times. The average number of requests in the system is L = ρ/(1−ρ), where ρ = λ/μ (utilization). This model provides baseline capacity estimation but is limited to single-server scenarios.

- **M/M/c queue**: Multi-server model with c identical servers, Poisson arrivals, and exponential service times. The Erlang-C formula calculates the probability that an arriving request must wait in queue:

  P(wait) = [(cρ)^c / (c!(1−ρ))] / [Σ_{k=0}^{c−1} (cρ)^k/k! + (cρ)^c/(c!(1−ρ))]

  where ρ = λ/(cμ) is the per-server utilization. Given a target waiting probability and response time, the minimum server count c can be solved iteratively.

- **M/G/1 queue**: Single-server model with Poisson arrivals and general (non-exponential) service time distribution, using the Pollaczek-Khinchine formula for mean queue length. This is more realistic for cloud workloads where service times often follow heavy-tailed distributions.

- **Little's Law (L = λW)**: A fundamental theorem relating the average number of requests in the system (L), the arrival rate (λ), and the average time a request spends in the system (W). This holds for any stable queueing system regardless of arrival or service distributions, providing a quick capacity estimation tool.

**Application to Auto-Scaling.** Given a target response time W_target and observed arrival rate λ, the autoscaler computes the required service rate μ and server count c using the Erlang-C formula or Little's Law. For example, if λ = 1000 req/s and the target response time is 50ms, Little's Law gives L = 1000 × 0.05 = 50 concurrent requests in the system; if each server handles 20 req/s, then c = 50/20 = 2.5 → 3 servers needed (with safety margin).

**Advantages.** Provides a principled, mathematically grounded approach to capacity planning; can incorporate multiple performance targets (response time, queue length, waiting probability); more systematic than ad-hoc threshold rules.

**Limitations.** The Poisson arrival assumption is often violated in real cloud environments — web traffic exhibits burstiness, self-similarity, and long-range dependence that deviate significantly from Poisson processes. Service times in cloud applications are rarely exponentially distributed (the M/M/c model's assumption), and the M/G/1 model, while more general, still assumes independence and stationarity. Queueing models assume steady-state behavior and do not handle transient spikes well. Parameter estimation (λ, μ) requires continuous monitoring and may itself be noisy. Effectiveness degrades when workloads exhibit non-stationary patterns, sudden regime changes, or correlated arrivals.

#### 5. Control Theory-Based Scaling

**Core Principle.** Control theory-based scaling models resource allocation as a feedback control problem, where the autoscaler is a controller that adjusts system inputs (number of servers, CPU allocation) to maintain desired outputs (response time, utilization) despite disturbances (load changes).

**PID Controller.** A PID (Proportional-Integral-Derivative) controller computes the control signal as:

u(t) = K_p · e(t) + K_i · ∫e(τ)dτ + K_d · de(t)/dt

where e(t) = r(t) − y(t) is the error between the reference setpoint r(t) (e.g., target CPU utilization) and the measured output y(t) (actual CPU utilization). The three terms serve distinct functions:

- **Proportional (P)**: Produces a control action proportional to the current error. Provides fast response to load changes but can cause oscillation if K_p is too large, and leaves steady-state error if K_p is too small.
- **Integral (I)**: Accumulates past errors over time, eliminating steady-state error by continuing to adjust until the error is zero. Can cause overshoot and slow response if K_i is too large.
- **Derivative (D)**: Predicts future error based on the current rate of change, providing damping that reduces oscillation and improves stability. Sensitive to noise in the measured signal.

**Model Predictive Control (MPC).** MPC extends PID by using a dynamic model of the system to predict future behavior over a finite horizon and computing an optimal control sequence that minimizes a cost function (e.g., weighted sum of SLA violations and resource cost) subject to constraints (e.g., maximum/minimum instances, rate limits). MPC handles multi-variable control (e.g., simultaneously scaling CPU and memory) and explicit constraints, but requires a reasonably accurate system model and significant computational resources for online optimization ([Wikipedia: Model Predictive Control](https://en.wikipedia.org/wiki/Model_predictive_control)).

**Advantages.** Provides systematic stability analysis and formal guarantees (e.g., bounded overshoot, settling time) that threshold-based methods lack. PID naturally handles feedback delays through the derivative term. MPC handles constraints and multi-variable optimization explicitly. Both approaches can be analyzed using well-established control-theoretic tools (Bode plots, Nyquist criteria, Lyapunov stability).

**Limitations.** Requires a precise system model (transfer function or state-space model) that is often difficult to obtain for complex cloud applications. Parameter tuning (K_p, K_i, K_d for PID; prediction horizon, cost weights for MPC) is complex and workload-dependent. Model inaccuracies can lead to poor performance or instability. The control loop's sampling interval introduces quantization effects. Control-theoretic approaches are less effective when the system dynamics change rapidly (non-stationarity), as the controller designed for one operating point may perform poorly at another.

#### 6. Serverless / FaaS Auto-Scaling

**Core Principle.** Serverless (Function-as-a-Service) auto-scaling represents a fundamentally different paradigm from VM-based reactive scaling. Platforms such as AWS Lambda, Google Cloud Functions, and Azure Functions abstract scaling entirely from the user — the platform creates and destroys execution environments per invocation. The key characteristics are:

- **Scale-to-zero**: When no requests arrive, the platform releases all resources, incurring zero cost. This is the default behavior and a core economic advantage of serverless.
- **Event-driven invocation**: Each function invocation triggers the platform to allocate an execution environment, execute the function, and (if no further invocations occur) eventually release the environment.
- **Cold-start latency**: When a function has been idle (scaled to zero), the first invocation must wait for a new execution environment to be provisioned, initialized, and the function code loaded. This cold start adds latency ranging from tens of milliseconds (for lightweight runtimes) to several seconds (for large functions or complex initialization) ([Cold Start Systematic Review, arXiv 2024](https://arxiv.org/html/2310.08437v2)).

**Reactive Scaling Patterns.** Serverless platforms scale reactively based on invocation concurrency. When concurrent requests arrive, the platform automatically creates additional execution environments up to the configured concurrency limit. AWS Lambda uses a concurrency-based scaling model: when the number of open requests increases, Application Auto Scaling increases provisioned concurrency in steps until the configured maximum is reached ([AWS Lambda Provisioned Concurrency Documentation](https://docs.aws.amazon.com/lambda/latest/dg/provisioned-concurrency.html)).

**Provisioned Concurrency.** To mitigate cold starts, AWS Lambda offers provisioned concurrency — a user-specified number of pre-initialized execution environments that are kept warm and ready to serve requests. Provisioned concurrency eliminates cold starts for the configured capacity but incurs cost even when idle, creating a direct trade-off between cold-start latency and cost efficiency. Application Auto Scaling can dynamically adjust provisioned concurrency based on utilization metrics ([AWS Lambda Provisioned Concurrency Documentation](https://docs.aws.amazon.com/lambda/latest/dg/provisioned-concurrency.html)).

**Comparison with VM-Based Reactive Scaling.** Unlike VM-based scaling, where the autoscaler explicitly manages instance lifecycles and cooldown periods, serverless scaling is entirely platform-managed with no user-visible cooldown mechanism. The scaling latency is determined by the platform's internal provisioning speed rather than a configurable cooldown. The scale-to-zero capability provides superior cost efficiency for spiky, low-frequency workloads but introduces cold-start latency as a first-class constraint that has no direct equivalent in VM-based scaling.

**Advantages.** Zero operational overhead for scaling management; scale-to-zero eliminates idle costs; pay-per-invocation pricing model; automatic and rapid scaling without cooldown delays.

**Limitations.** Cold-start latency is the fundamental trade-off — applications with strict latency requirements (e.g., real-time APIs) may require provisioned concurrency, partially negating the cost advantage. Limited control over scaling behavior (no custom thresholds or cooldown tuning). Vendor lock-in due to platform-specific invocation models and cold-start characteristics. Resource limits (memory, execution time, concurrency caps) may constrain scaling. Debugging and monitoring are more challenging due to the ephemeral nature of execution environments.

### Proactive Methods

Proactive auto-scaling fundamentally inverts the reactive paradigm: instead of waiting for load changes to occur and then responding, proactive methods leverage historical data, predictive models, or learning algorithms to adjust resources **before** demand shifts happen. This eliminates the inherent lag of reactive approaches — the interval between a load change and the completion of a scaling action — which is critical for applications with long initialization times or rapidly varying workloads. The architectural pipeline common to most proactive methods consists of three stages: (1) **data collection and feature engineering** — gathering historical metrics (CPU utilization, request rate, memory usage, temporal features) and constructing input features; (2) **model inference** — feeding features into a trained model to produce a forecast or scaling decision; and (3) **decision mapping** — translating the model's output (a predicted load value or a Q-value) into a concrete scaling action (add/remove N instances, change instance type). The following subsections detail five specific proactive method families.

---

#### 1. Time Series Forecasting-Based Scaling

**Core Principle.** Statistical time series models analyze historical load sequences to extrapolate future demand. The most widely used models include:

- **ARIMA (Autoregressive Integrated Moving Average)** — combines autoregression (AR), differencing (I), and moving average (MA) components, parameterized by *(p, d, q)* where *p* is the autoregressive order, *d* is the degree of differencing, and *q* is the moving average order. Seasonal ARIMA (SARIMA) extends this with seasonal terms *(P, D, Q, s)* to capture periodic patterns such as daily or weekly cycles. When the forecasted load exceeds a predefined threshold, the autoscaler provisions additional instances in advance.
- **Exponential Smoothing (Holt-Winters)** — maintains exponentially decaying weighted averages of past observations, with separate smoothing equations for level, trend, and seasonal components. It is particularly effective for workloads with clear seasonal decomposition.
- **Moving Average** — computes the arithmetic mean of the most recent *k* observations as the forecast for the next time step; simple but effective for smoothing short-term fluctuations.

The relationship between **forecast horizon** and scaling effectiveness is direct: a longer horizon allows more time for instance initialization (especially important for applications with startup times of several minutes), but prediction accuracy degrades as the horizon extends, increasing the risk of over- or under-provisioning. A study on cloud resource provisioning using Holt-Winters exponential smoothing demonstrated that the method effectively captures seasonal patterns for advance resource allocation, but its accuracy drops when workloads deviate from established seasonal norms ([Shahin 2017](https://arxiv.org/pdf/1701.03296)).

**Advantages.** Mature mathematical foundation with well-understood statistical properties; handles seasonality naturally (especially SARIMA and Holt-Winters); low computational cost suitable for real-time inference; interpretable parameters that can be tuned by domain experts.

**Limitations.** Assumes **stationarity** — that the statistical properties of the workload (mean, variance) remain constant over time — which is frequently violated in real cloud environments where traffic patterns shift due to business growth, marketing events, or application updates. Cannot handle **sudden bursts** or one-off events (e.g., a flash sale or viral content) that have no historical precedent. Prediction accuracy degrades with longer forecast horizons, creating a fundamental trade-off between lead time and decision quality.

#### 2. Machine Learning-Based (Supervised) Scaling

**Core Principle.** Supervised learning models learn a mapping from historical load features to future demand by training on labeled datasets (past workload measurements as inputs, actual future load as targets). The training pipeline proceeds as follows: **feature engineering** — constructing input vectors from historical CPU utilization, request rates, memory usage, and temporal features (hour of day, day of week); **model training** — optimizing model parameters via backpropagation (for neural networks) or least-squares fitting (for regression); **prediction** — feeding new feature vectors into the trained model to produce a load forecast; **decision mapping** — comparing the forecast against scaling thresholds to determine the number of instances to add or remove.

Key model architectures include:

- **LSTM (Long Short-Term Memory)** — a recurrent neural network variant with gating mechanisms (input, forget, output gates) that control information flow, enabling the network to learn long-range temporal dependencies in workload sequences. LSTM overcomes the vanishing gradient problem of standard RNNs, making it suitable for capturing multi-scale patterns in cloud workloads.
- **GRU (Gated Recurrent Unit)** — a simplified gating architecture with fewer parameters than LSTM, offering comparable prediction accuracy with lower computational cost.
- **Feed-forward neural networks and multiple linear regression** — simpler models that serve as baselines or components in ensemble systems.

The **MLScale system** (Wajahat et al.) exemplifies this approach: it is an application-agnostic autoscaler composed of a neural network-based online (black-box) performance model and multiple linear regression predictors. MLScale uses supervised learning to forecast resource demand and then maps the forecast to scaling decisions. The TUM survey by Lemke & Majumdar (2022) compared MLScale with RLPAS and concluded that MLScale's supervised learning approach provides substantial improvement over manual threshold-based autoscalers, but identified **reactiveness as a prohibitive weakness** — because the model is trained on historical data and makes predictions based on past patterns, it cannot proactively anticipate novel workload shifts that differ from training distributions ([Lemke & Majumdar 2022](https://www.net.in.tum.de/fileadmin/TUM/NET/NET-2022-07-1/NET-2022-07-1_11.pdf)).

The **Bi-LSTM multi-variable autoscaling framework** (Dang-Quang & Yoo, MDPI Applied Sciences 2022) extends the standard LSTM architecture by processing the workload sequence in both forward and backward directions, capturing dependencies that precede and follow each time step. This multivariate framework ingests multiple input features — CPU, memory, network I/O, and request rate — simultaneously, allowing the model to learn cross-metric correlations (e.g., that rising request rates precede CPU spikes by a characteristic lag). The bidirectional architecture improves prediction accuracy over univariate models, particularly for workloads with complex multi-metric patterns ([Dang-Quang & Yoo 2022](https://www.mdpi.com/2076-3417/12/7/3523)). For a full treatment of prediction failure modes including cold-start and concept drift, see S2.5.

**Advantages.** Learns complex, non-linear temporal patterns that statistical models cannot capture; can incorporate multiple input features (CPU, memory, request rate, temporal markers); adaptable to different application types through retraining; generally outperforms ARIMA on workloads with non-stationary or multi-seasonal patterns.

**Limitations.** Requires **large labeled datasets** for training — a significant barrier for newly deployed services lacking historical data (the cold-start problem, treated fully in S2.5). **Model aging** degrades prediction accuracy over time as workload patterns evolve (concept drift), necessitating periodic retraining. Training and maintaining ML models adds operational complexity. The black-box nature of deep learning models makes it difficult to explain scaling decisions to operators.

#### 3. Reinforcement Learning-Based Scaling

**Core Principle.** Reinforcement learning (RL) formulates auto-scaling as a **Markov Decision Process (MDP)**, defined by the tuple *(S, A, P, R, γ)* where:

- **State space (S)** — describes the current system configuration, typically including current resource utilization (CPU, memory), request rate, number of active instances, and queue length.
- **Action space (A)** — the set of scaling actions: scale up (add *n* instances), scale down (remove *n* instances), or no-op. Actions may also include vertical scaling (adjust instance CPU/memory) or changing instance types.
- **Transition probabilities (P)** — the (unknown) probability distribution over next states given the current state and action. Model-free RL methods learn this implicitly through interaction.
- **Reward function (R)** — encodes the optimization objective, typically a weighted combination of negative SLA violations (penalizing response time exceeding thresholds) and resource cost (penalizing provisioned capacity): *R = −(w₁ · SLA_violations + w₂ · resource_cost)*.
- **Discount factor (γ)** — balances immediate versus future rewards.

The agent learns an optimal policy *π\*: S → A* that maps each state to the action maximizing expected cumulative discounted reward. Unlike supervised learning, RL does not require labeled datasets — it learns through trial-and-error interaction with the environment, receiving rewards that guide policy improvement.

**RLPAS (Reinforcement Learning based Proactive Auto-Scaler)** uses the **SARSA (State-Action-Reward-State-Action)** algorithm, an on-policy temporal difference learning method. SARSA updates its action-value estimate *Q(s, a)* after each transition using the actual next action taken (rather than the maximum over all actions, as in Q-Learning), making it inherently conservative — it accounts for the exploration policy's behavior when updating value estimates. The update rule is:

*Q(Sₜ, Aₜ) ← Q(Sₜ, Aₜ) + α[Rₜ₊₁ + γ · Q(Sₜ₊₁, Aₜ₊₁) − Q(Sₜ, Aₜ)]*

where *α* is the learning rate and *γ* is the discount factor. RLPAS's MDP formulation defines states as discretized system configurations (e.g., current CPU utilization bucket, request rate level), actions as scaling operations (add/remove instances), and rewards as a function of SLA compliance and resource cost. The TUM survey found that RLPAS's ability to predict required resource spikes and provision resources proactively gives it a "decisive advantage" over the reactive MLScale, though its greater algorithmic complexity poses challenges for real-world deployment ([Lemke & Majumdar 2022](https://www.net.in.tum.de/fileadmin/TUM/NET/NET-2022-07-1/NET-2022-07-1_11.pdf)).

**DRL-Cloud** (IEEE ASP-DAC 2018) extends this approach to deep reinforcement learning. It addresses the joint problem of **resource provisioning (RP)** and **task scheduling (TS)** for large-scale cloud service providers with thousands of servers and hundreds of thousands of tasks per day. DRL-Cloud uses a **deep Q-learning-based two-stage RP-TS processor**: the first stage determines how many VMs to provision (resource provisioning), and the second stage assigns tasks to those VMs (task scheduling). The system employs three key training techniques: **experience replay** (storing and sampling past transitions to break correlation in training data), **target network** (a separate network providing stable Q-value targets during training), and **exploration-exploitation** (ε-greedy policy balancing random exploration with greedy exploitation). The MDP formulation encompasses states describing the current server/task configuration, actions for VM provisioning and task assignment, and a reward function that minimizes energy cost while maintaining low task rejection rates. For DRL-Cloud's energy-specific results, see S2.1.

**Q-Learning vs. SARSA for Scientific Workflows (2024).** A study published in *Future Generation Computer Systems* (2024) provided a systematic comparison of Q-Learning and SARSA for online RL-based cloud autoscaling targeting scientific workflows. Results showed that **SARSA outperforms Q-Learning in almost all tested cases**, achieving significant gains of up to 40.8% in certain workflow scenarios. This finding is architecturally significant: SARSA's on-policy nature (updating based on the actual next action taken, including exploration) makes it more conservative and better suited to the safety-critical nature of autoscaling, where aggressive over-exploration can cause costly over-provisioning. Q-Learning's off-policy updates (using the max over all next actions) can lead to overoptimistic value estimates that result in aggressive scaling decisions ([Garí & Pacini 2024, Future Generation Computer Systems](https://www.sciencedirect.com/science/article/abs/pii/S0167739X24001432)).

**Advantages.** Learns optimal scaling policies through environment interaction without requiring labeled datasets; naturally handles the stochastic, dynamic nature of cloud workloads; can optimize arbitrary reward functions combining SLA compliance, cost, and energy; online learning enables continuous policy adaptation; deep RL (DQN, DDPG) can handle high-dimensional state spaces that tabular methods cannot.

**Limitations.** Requires extensive interaction with the environment to converge, which can be costly in production systems (sample inefficiency); reward function design is critical and non-trivial — poorly designed rewards lead to suboptimal or unstable policies; policies trained in one workload environment may not generalize to others (addressed by meta-RL, below); cold-start problem where the agent starts with no knowledge and must explore extensively before producing useful policies (cross-reference S2.5 for full treatment).

#### 4. Meta Reinforcement Learning-Based Scaling

**Core Principle.** A fundamental limitation of standard RL-based autoscaling is that a policy trained on one workload pattern or application environment fails when deployed in a new setting — the agent must relearn from scratch, incurring the same sample inefficiency that made initial training costly. **Meta reinforcement learning (meta-RL)** addresses this by training a **meta-learner** across a distribution of related tasks (different workload patterns, different application types) such that the resulting policy can rapidly adapt to new, unseen tasks with minimal additional interaction.

Xue et al. proposed an end-to-end predictive meta model-based RL algorithm that incorporates a **deep periodic workload prediction model** as input and embeds a **Neural Process** — a class of neural models that learn distributions over functions — to guide the learning of optimal scaling actions across numerous application services in the cloud. The meta-learner captures shared structure across workload patterns (e.g., daily cycles, burst behaviors) and uses this shared knowledge to accelerate adaptation. The algorithm was deployed online at **Alipay**, supporting autoscaling for the world-leading payment platform, demonstrating that the approach achieves significant performance improvement over existing algorithms while maintaining high sample efficiency ([Xue et al., arXiv 2022; ACM 2025](https://arxiv.org/abs/2205.15795)).

**Advantages.** Dramatically improves generalization across workloads and environments, reducing or eliminating retraining when deploying to new services; maintains the flexibility and adaptability of RL while mitigating its sample inefficiency; the meta-learned prior captures universal scaling patterns that transfer across applications.

**Limitations.** Increased architectural and training complexity; requires diverse training tasks to learn a useful meta-prior — if training tasks are too similar, the meta-learner overfits to a narrow pattern class; the Neural Process and meta-learning components add computational overhead; deployment at scale (as at Alipay) requires substantial engineering investment.

#### 5. Hybrid/Ensemble Scaling

**Core Principle.** Hybrid autoscaling systems combine multiple prediction models or combine reactive and proactive strategies to exploit complementary strengths. The architectural pattern common to most hybrid systems is a **two-layer design**: a proactive model (e.g., ARIMA + LSTM, or a Pelican optimization-based predictor) provides a baseline scaling decision based on predicted load, while a reactive controller monitors real-time metrics and handles residual errors — sudden spikes, prediction inaccuracies, and unanticipated events that the proactive model failed to forecast.

The **hybrid Pelican optimization algorithm** (Pothu & Kailaswamy, IIETA 2025) exemplifies model-level hybridization. It combines **ARIMA-OLSTM** — a two-step forecasting model where ARIMA captures linear trends in historical workload sequences and an LSTM (optimized by RMSProp) learns non-linear sequential patterns from ARIMA's residuals — with a **Hybrid Pelican Optimization Algorithm (POA)** inspired by pelican hunting techniques and enhanced with Lyrebird Optimization. The POA determines optimal VM parameters during the planning stage, balancing cost-effectiveness, system responsiveness, and SLA fulfillment. Extensive tests on realistic cloud workloads demonstrated that the model achieves an RMSE of 0.1513 and MAPE of 0.1557, outperforming existing models (RHAS, GRASP, ADA-RP), while maintaining 50% less resource usage and achieving a 70% reduction in reaction time compared to traditional methods ([Pothu & Kailaswamy 2025, IIETA](https://www.iieta.org/download/file/fid/168740)).

**Google Cloud Predictive Autoscaling** represents a commercial hybrid implementation. When enabled, Compute Engine forecasts future load based on the managed instance group's (MIG) CPU utilization history and scales out in advance of predicted load, so that new instances are initialized and ready to serve when demand arrives. The system works with both real-time data and historical data: the predictive algorithm handles anticipated daily or weekly cycles, while the standard reactive autoscaler handles real-time deviations from predictions. Compute Engine requires **3 days of CPU-based autoscaling history** before generating predictions and uses up to **3 weeks of load history** to feed its ML model. The system is designed for workloads with initialization periods exceeding 2 minutes and predictable daily/weekly patterns — it explicitly does not predict monthly, annual, or one-time events, which are instead handled by schedule-based autoscaling ([Google Cloud Predictive Autoscaling documentation](https://docs.cloud.google.com/compute/docs/autoscaler/predictive-autoscaling)).

Research on "transforming reactive auto-scaling into proactive" has explored architectures where a proactive predictor continuously generates scaling recommendations that override or augment the reactive controller's decisions. The TUM survey noted that hybrid approaches combining proactive foresight with reactive flexibility represent the most promising direction for industry adoption, as they provide the safety net of reactive control while gaining the latency benefits of proactive scaling ([Lemke & Majumdar 2022](https://www.net.in.tum.de/fileadmin/TUM/NET/NET-2022-07-1/NET-2022-07-1_11.pdf)).

**Advantages.** Combines the low-latency safety net of reactive methods with the advance-provisioning benefits of proactive methods; robust to prediction failures since the reactive component handles unanticipated spikes; flexible — different model combinations can be tailored to specific workload characteristics; commercially validated (Google Cloud) and research-validated (Pelican/ARIMA-OLSTM).

**Limitations.** Increased system complexity from maintaining multiple models and a coordination layer; potential conflicts between proactive and reactive decisions (e.g., proactive scaling down while reactive detects a spike) require careful arbitration logic; the proactive component's effectiveness depends on workload predictability — for inherently unpredictable workloads, the reactive component dominates and the hybrid system degrades toward pure reactive behavior; Google Cloud's predictive mode is limited to CPU utilization as the scaling metric and requires minimum history thresholds.

#### Summary Comparison of Proactive Methods

| Method | Core Model | Key Advantage | Key Limitation |
|--------|-----------|---------------|----------------|
| Time Series Forecasting | ARIMA/SARIMA, Holt-Winters | Mature, interpretable, handles seasonality | Assumes stationarity; cannot handle bursts |
| Supervised ML (LSTM/GRU) | Neural networks, regression | Learns complex multi-feature patterns | Requires large labeled data; model aging |
| Reinforcement Learning | SARSA, DQN, DDPG | Learns optimal policies via interaction | Sample inefficient; reward design critical |
| Meta Reinforcement Learning | Meta-RL with Neural Process | Generalizes across workloads without retraining | High complexity; needs diverse training tasks |
| Hybrid/Ensemble | ARIMA + LSTM + reactive | Robust to prediction failures; low latency | System complexity; potential decision conflicts |

All proactive methods share a fundamental dependency on the quality and availability of historical data and the assumption that future workloads will resemble past patterns to some degree. When these assumptions break — due to cold starts, concept drift, non-stationarity, or burstiness — prediction errors propagate directly to scaling decisions, causing over-provisioning (wasted cost) or under-provisioning (SLA violations). The specific failure modes and their mitigations are treated in S2.5.

## Main Challenges and Solutions

### Energy Efficiency

Cloud data centers are among the largest electricity consumers in the modern economy. U.S. data centers alone consumed approximately 176 TWh in 2023, representing about 4.4% of total U.S. electricity consumption ([Shehabi et al. 2024, LBNL](https://eta-publications.lbl.gov/sites/default/files/2024-12/lbnl-2024-united-states-data-center-energy-usage-report.pdf)). Auto-scaling decisions directly and quantitatively affect this consumption: over-provisioning leaves servers idle yet drawing significant power, while under-provisioning causes SLA violations that trigger costly remediation. The central challenge is the **energy-performance tradeoff** — minimizing energy consumption while maintaining acceptable response times and availability.

#### The Energy-Performance Tradeoff and Idle Server Energy

A critical but often underestimated factor is that servers consume substantial power even when idle. Research has established that a typical idle server draws 30–40% of its maximum power ([ABB 2020](https://new.abb.com/news/detail/66580/how-data-centers-can-minimize-their-energy-use)), and some studies report idle power reaching 60–70% of full-load power for certain server configurations ([PMC 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13438616/)). Dougherty et al. (2012) cite data indicating that data centers operate at only 20–30% utilization, meaning 70–80% of power consumption is lost due to over-provisioned idle resources — resulting in roughly 29 million tons of unnecessary CO₂ emissions annually ([Dougherty et al. 2012](https://www.cs.wm.edu/~dcschmidt/PDF/Model-driven-Auto-scaling-of-Green-Cloud-Computing-Infrastructure.pdf)). The Uptime Institute has similarly found that roughly 30% of data center energy is wasted on idle capacity.

This creates a fundamental tension for auto-scaling: maintaining a buffer of pre-provisioned resources (e.g., a queue of prebooted VMs) ensures fast response to traffic spikes but incurs continuous idle energy drain. Conversely, scaling aggressively to zero eliminates idle energy but introduces cold-start latency that may violate SLA response time requirements. The Power Usage Effectiveness (PUE) metric — defined as total data center energy divided by IT equipment energy — captures this overhead, with typical values around 1.5, meaning 0.5 kWh is lost to cooling and power distribution for every 1 kWh delivered to IT equipment ([Google Data Centers](https://datacenters.google/efficiency/)).

#### Does Scale-to-Zero Always Save Energy?

Scale-to-zero, a hallmark of serverless/FaaS platforms, eliminates idle resource energy by destroying instances when not in use. However, it does not universally save energy. Frequent cold starts incur initialization overhead — including VM setup, container creation, and runtime initialization — that itself consumes energy and adds latency. Kaur et al. (2024) identify six function instance states in serverless computing (initializing, cold-start, warm-start, running, idle, expired), noting that the cold-start phase introduces both performance degradation and additional energy expenditure ([Kaur et al. 2024, STET Review](https://www.stet-review.org/articles/stet/full_html/2024/01/stet20240095/stet20240095.html)). For workloads with frequent, bursty invocations, the cumulative cold-start energy cost can offset the savings from eliminating idle periods, making provisioned concurrency or partial pre-warming a more energy-efficient strategy.

#### Dougherty et al. (2012): Model-Driven Engineering for Green Auto-Scaling

The primary research case for this challenge is **Dougherty et al. 2012** ("Model-driven auto-scaling of green cloud computing infrastructure," *Future Generation Computer Systems*), which proposes the SCORCH (Smart Cloud Optimization for Resource Configuration Handling) framework. SCORCH uses a Model-Driven Engineering (MDE) approach to simultaneously optimize VM configuration, energy consumption, and operating cost for cloud auto-scaling infrastructure ([Dougherty et al. 2012](https://www.cs.wm.edu/~dcschmidt/PDF/Model-driven-Auto-scaling-of-Green-Cloud-Computing-Infrastructure.pdf)).

The approach works in three stages:

1. **Feature modeling**: VM configuration options (processor type, OS, memory, middleware) are captured as feature models — hierarchical representations of configuration options and their constraints. For example, Amazon EC2 at the time supported 5 processor types, 6 memory configurations, and over 9 OS types, with power consumption ranging from 150 to 610 watts per hour depending on configuration.

2. **CSP transformation**: Feature models are automatically transformed into Constraint Satisfaction Problems (CSPs), where variables represent VM configuration choices and constraints encode configuration rules, response time requirements, and resource limits.

3. **Optimization solving**: A constraint solver derives the optimal set of VM configurations for the auto-scaling queue — minimizing energy consumption and cost while guaranteeing that VM allocation requests can be serviced within a required response time limit.

The key innovation is treating energy as a first-class optimization objective alongside cost and configuration, rather than as an afterthought. The case study on Amazon EC2 demonstrated measurable energy consumption and cost reduction while maintaining auto-scaling response time requirements. The approach is particularly effective because it reasons about the tradeoff between queue size (more prebooted VMs = faster response but more idle energy) and response time guarantees.

#### Kaur et al. (2024): Q-Learning for Energy-Efficient Serverless Autoscaling

The supplementary case is **Kaur et al. 2024** ("An autoscalable approach to optimize energy consumption using smart meters data in serverless computing," *Science and Technology for Energy Transition*), which applies Q-learning to dynamically adjust serverless resources for energy efficiency ([Kaur et al. 2024](https://www.stet-review.org/articles/stet/full_html/2024/01/stet20240095/stet20240095.html)).

The Q-learning design is structured as follows:

- **State space**: The state captures the current system condition, including the number of active function instances, request arrival rate, and instance states (initializing, cold-start, warm-start, running, idle, expired).
- **Action space**: Actions include scaling up (adding function instances), scaling down (removing idle instances), or maintaining the current allocation.
- **Reward function**: The reward balances multiple objectives — maximizing resource utilization, minimizing energy consumption, reducing cold-start probability, and maintaining acceptable average response time. The approach is validated on AWS Lambda with smart meter data as a real-world workload, demonstrating improvements across all key performance metrics: probability of cold start, average response time, idle instance count, and energy consumption compared to baseline approaches.

This work is notable for addressing the serverless-specific energy challenge, where scale-to-zero and cold-start tradeoffs make energy optimization fundamentally different from VM-based autoscaling.

#### DRL-Cloud (IEEE 2018): Deep Reinforcement Learning for Energy Cost Minimization

The DRL-Cloud system (Cheng et al. 2018, IEEE ASPDAC) achieves up to **320% energy cost efficiency improvement** compared to state-of-the-art energy-efficient algorithms, while maintaining a lower task reject rate ([Cheng et al. 2018, IEEE](https://ieeexplore.ieee.org/document/8297294/); [ACM DL](https://dl.acm.org/doi/pdf/10.5555/3201607.3201635)). The system formulates cloud resource allocation and energy cost minimization as a semi-Markov Decision Process (SMDP), where the reward function encodes the energy-cost tradeoff by penalizing both power consumption (electric bill) and task rejections (SLA violations). DRL-Cloud operates in two stages: resource provisioning (determining how many VMs to allocate) and task scheduling (assigning tasks to provisioned VMs), enabling it to minimize energy cost for large-scale cloud service providers with very large data centers. For the RL method architecture (MDP formulation, SARSA/DQN algorithms), see S1.2.

#### Summary of the Energy Efficiency Challenge

The energy efficiency challenge in auto-scaling manifests across three dimensions: (1) **idle resource waste** — over-provisioned servers consume 30–70% of peak power while doing no useful work; (2) **scaling overhead** — frequent VM start/stop and cold starts themselves incur energy costs that can offset savings; and (3) **SLA-energy tension** — aggressive energy minimization risks response time violations. The three research cases illustrate complementary approaches: Dougherty et al. use model-driven optimization to derive energy-optimal VM configurations analytically; Kaur et al. use Q-learning to learn energy-efficient scaling policies for serverless workloads with cold-start dynamics; and DRL-Cloud uses deep reinforcement learning to minimize electric bills at cloud-scale through learned resource provisioning and task scheduling policies.

### Dynamic Nature of Telecom Services

**Problem Description.** The fifth-generation (5G) mobile network architecture fundamentally departs from legacy telecom designs by adopting Network Function Virtualization (NFV) and cloud-native principles. In this paradigm, network functions that once ran on proprietary hardware are decoupled and implemented as software — Virtual Network Functions (VNFs) or Cloud-Native Network Functions (CNFs) — executing on general-purpose cloud infrastructure. This shift introduces auto-scaling challenges that are qualitatively different from those of conventional cloud applications. Telecom services exhibit **highly dynamic and bursty traffic patterns**, impose **strict QoS requirements** (e.g., Ultra-Reliable Low-Latency Communication, or URLLC, demands one-way latency below 1 ms and availability of 99.999% ([ITU-R specifications](https://www.sciencedirect.com/topics/engineering/ultra-reliable-low-latency-communication))), and require **stateful scaling** of network functions that maintain session and mobility context. Furthermore, 5G network slicing partitions a shared physical infrastructure into multiple logical networks — eMBB (enhanced Mobile Broadband), URLLC, and mMTC (massive Machine-Type Communications) — each with vastly different traffic characteristics and SLA constraints, making a single scaling policy insufficient.

**Differences from Traditional Cloud Auto-Scaling.** Traditional cloud auto-scaling (e.g., for web applications) typically relies on stateless horizontal scaling triggered by CPU or request-rate metrics. Telecom service auto-scaling differs in several fundamental ways. First, 5G core network functions such as the **Access and Mobility Management Function (AMF)**, **Session Management Function (SMF)**, and **User Plane Function (UPF)** are inherently stateful: AMF tracks UE registration and mobility context, SMF manages PDU sessions and QoS flows, and UPF handles packet routing and forwarding state ([Passas et al. 2022](https://dl.acm.org/doi/abs/10.1016/j.compeleceng.2022.108327)). Scaling these functions requires careful state migration or replication, not simply adding or removing stateless replicas. Second, the QoS constraints are far more stringent than typical web-application SLAs: URLLC services require sub-millisecond latency and 99.999% reliability ([Ericsson, 2021](https://www.ericsson.com/en/blog/2021/10/realizing-time-critical-communication-with-5g)), meaning that any scaling delay — whether from monitoring lag, decision computation, or instance startup — can directly cause SLA violations. Third, 5G network slices have heterogeneous traffic patterns: eMBB generates high-bandwidth, bursty data traffic; URLLC produces small, frequent, latency-critical packets; and mMTC involves massive numbers of low-rate, intermittent connections ([Samsung 5G Core white paper](https://images.samsung.com/is/content/samsung/p5/global/business/networks/insights/white-paper/cloud-native-5g-core/Samsung-5G-Core-Vol-2-Cloud-Native-5G-Core.pdf)). A single auto-scaling policy cannot simultaneously satisfy these divergent profiles.

**The Ceilometer Monitoring Bottleneck.** A critical bottleneck in telecom auto-scaling lies in the monitoring layer that feeds scaling decisions. The traditional OpenStack telemetry service, **Ceilometer**, was designed for coarse-grained metering of cloud resources (e.g., polling VM CPU utilization at minute-level intervals). When applied to VNF auto-scaling, Ceilometer encounters two severe problems:

1. **Storage bloat**: Ceilometer stores all raw metric samples in its backend database without automatic downsampling. As the number of VNF instances and the frequency of metric collection grow, the database grows unmanageably, leading to slow query performance and excessive disk consumption ([Zafar et al. 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC9571204/)).

2. **Retrieval latency from on-demand aggregation**: Ceilometer performs **aggregation on demand** — when a scaling alarm needs to be evaluated, the system queries the raw samples and computes aggregate statistics (e.g., average CPU over a window) in real time. For high-frequency VNF metrics (e.g., per-second or sub-second polling), this requires scanning millions of raw samples, causing retrieval delays on the order of seconds to minutes. These delays prevent timely scaling triggers, directly undermining the responsiveness required for URLLC-grade services ([Zafar et al. 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC9571204/); [Gnocchi benchmark, OpenStack SuperUser](https://superuser.openinfra.org/articles/benchmarking-gnocchi-for-fun-and-profit/)).

**Primary Research Case: Zafar et al. 2022 — Gnocchi-Based VNF Auto-Scaling Framework.** To address Ceilometer's limitations, Zafar et al. (2022) proposed replacing Ceilometer's metering storage component with **Gnocchi**, a purpose-built time-series database, within a comprehensive NFV auto-scaling framework. The framework was deployed on a fully functional OpenStack cloud with integrated NFV-MANO orchestration, using Heat orchestration templates to define VNF descriptors (VNFD) and scaling policies ([Zafar et al. 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC9571204/)).

The key technical innovation is Gnocchi's **eager aggregation** mechanism, which fundamentally differs from Ceilometer's on-demand approach. When Gnocchi receives raw metric measures, it immediately aggregates them (computing mean, max, min, count, etc.) according to a user-defined **archive policy** that specifies the granularity and retention period. The pre-aggregated values are stored directly, so that alarm evaluation queries return results by fetching pre-computed aggregates rather than scanning raw samples. This reduces retrieval time from seconds to milliseconds. Additionally, Gnocchi performs automatic **rollup and rolloff**: older data is downsampled to coarser granularities (e.g., from 1-second to 5-minute intervals) and eventually purged, preventing unbounded database growth ([Zafar et al. 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC9571204/)).

The experimental comparison demonstrated significant improvements over the legacy Ceilometer configuration across four dimensions: (a) **reduced metering storage size** — Gnocchi's archive policies keep the database bounded by automatically rolling off old data, whereas Ceilometer's raw-sample storage grows without limit; (b) **faster data retrieval speed** — eager aggregation enables near-instant alarm evaluation compared to Ceilometer's on-demand scanning of millions of samples; (c) **lower memory consumption** — Gnocchi's background processing daemon (gnocchi-metricd) handles aggregation asynchronously with bounded memory, while Ceilometer's on-demand queries consume increasing memory as the dataset grows; and (d) **timely alarm triggering** — the framework successfully demonstrated end-to-end auto-scaling of VNF instances based on CPU utilization thresholds, with alarms evaluated and triggered within the required time window ([Zafar et al. 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC9571204/)).

**Supplementary Case: Passas et al. 2022 — AI-Based Dynamic Scaling for Cloud-Native 5G Core.** While Zafar et al. addressed the monitoring-layer bottleneck, Passas et al. (2022) tackled the higher-level challenge of *intelligent scaling decision-making* for network functions in a cloud-native 5G core network. Their work, published in *Computers and Electrical Engineering*, identified three core problem statements: (1) how to adopt network measurement metrics on-the-fly for optimal scaling decisions, (2) what is the best time instance to trigger scaling in/out, and (3) how to dynamically combine different metrics to ensure optimal scaling under varying network contexts ([Passas et al. 2022](https://dl.acm.org/doi/abs/10.1016/j.compeleceng.2022.108327)).

Passas et al. demonstrated that default CPU-metric-based scaling in Kubernetes and OpenStack cannot satisfy the low-latency and real-time requirements of 5G networks, leading to three characteristic failure modes: (1) **long response time** for scaling out containers or pods, (2) **ping-pong effects** where services are repeatedly scaled out and then scaled in due to delayed metric feedback, and (3) **waste of network resources** from unnecessary over-provisioning. To overcome these, they proposed a **Deep Learning AI approach** applied to the Access and Mobility Function (AMF) in a real test-bed setup. The AI model proactively predicts network load based on real mobility-traffic datasets and makes scaling decisions before congestion occurs. Experimental results showed two major benefits: a **significantly higher number of users** could be admitted to the 5G network, and traffic was **balanced evenly** among different AMF replicas, avoiding the hotspots that reactive CPU-threshold scaling produces ([Passas et al. 2022](https://dl.acm.org/doi/abs/10.1016/j.compeleceng.2022.108327)).

**QoS Constraints on Auto-Scaling Decisions.** The QoS requirements of telecom services impose hard constraints on auto-scaling that do not arise in general cloud computing. The entire scaling pipeline — from metric collection through alarm evaluation, scaling decision, to instance startup and state synchronization — must complete within an extremely tight budget. In practice, VM startup alone can take 30–60 seconds, and even container startup (faster at 1–5 seconds) may exceed URLLC tolerances if state synchronization is required. This creates a fundamental tension: reactive scaling is too slow for URLLC, while proactive scaling (as in Passas et al.'s AI approach) must predict demand far enough in advance to absorb the startup latency, yet not so far that it wastes resources on false predictions. The 5G network slicing architecture compounds this problem: each slice (eMBB, URLLC, mMTC) has its own SLA, traffic pattern, and scaling policy, and the auto-scaling framework must manage multiple slices simultaneously on shared infrastructure without violating isolation guarantees ([Samsung 5G Core white paper](https://images.samsung.com/is/content/samsung/p5/global/business/networks/insights/white-paper/cloud-native-5g-core/Samsung-5G-Core-Vol-2-Cloud-Native-5G-Core.pdf)).

**Summary of the Challenge Space.** The dynamic nature of telecom services creates a multi-layered auto-scaling challenge: the monitoring layer must handle high-frequency metrics without storage bloat or retrieval delay (solved by Zafar et al.'s Gnocchi-based framework); the decision layer must predict network load and trigger scaling before QoS violations occur (addressed by Passas et al.'s AI-driven proactive scaling); and the orchestration layer must manage stateful VNF/CNF instances across heterogeneous network slices with divergent SLA requirements, using NFV-MANO orchestration and Heat templates to coordinate scaling actions. Together, these challenges demand auto-scaling solutions that are simultaneously faster, more predictive, and more context-aware than traditional reactive cloud autoscaling.

### Big Data Processing

#### Problem Description

Auto-scaling for big data processing frameworks such as Apache Hadoop and Apache Spark in cloud environments presents challenges fundamentally distinct from those of web application scaling. These differences arise from the architectural characteristics of distributed data processing systems.

**Data locality constraints.** Hadoop's HDFS co-locates data with compute nodes so that MapReduce tasks can process data locally, avoiding expensive network transfers. When autoscaling adds or removes nodes, data blocks must be rebalanced across the cluster, and HDFS decommissioning requires copying blocks to other DataNodes before a worker can be removed — a process that Google Cloud explicitly notes "can take hours" depending on data size and replication factor ([Google Cloud Dataproc autoscaling documentation](https://docs.cloud.google.com/managed-spark/docs/concepts/configuring-clusters/autoscaling)). This coupling of storage and compute means that scaling decisions cannot treat compute resources as independently elastic.

**Phase-dependent resource requirements.** Long-running batch jobs in MapReduce and Spark exhibit distinct resource profiles across execution phases. The Map phase typically requires more CPU for data parsing and transformation, while the Reduce phase demands higher network I/O and memory for shuffling and aggregation. In Spark, the shuffle phase causes significant resource fluctuation as intermediate data is redistributed across partitions, creating transient spikes that do not correlate with average cluster utilization ([Li et al. 2025, *Computers, Materials & Continua*](https://www.sciopen.com/article/10.32604/cmc.2025.063047)). A single cluster size for an entire pipeline is often suboptimal, yet changing resource allocation mid-iteration incurs data redistribution overhead.

**Data skew.** When certain partitions contain significantly more data than others — a condition known as data skew — a small number of nodes become bottlenecks while the majority remain underutilized. Threshold-based autoscaling rules that rely on average CPU or memory utilization across the cluster fail to detect these localized hotspots, because the average may remain well below the scaling threshold even as a subset of nodes is overloaded ([USENIX HotCloud 2012](https://www.usenix.org/system/files/conference/hotcloud12/hotcloud12-final50.pdf)). This makes reactive threshold methods particularly ineffective for big data workloads.

**Coupled storage and compute scaling.** In traditional Hadoop deployments, HDFS and MapReduce are tightly coupled: DataNodes and TaskTrackers run on the same machines. Scaling compute independently of storage is therefore non-trivial. Google Cloud's autoscaling documentation explicitly states that autoscaling is "not intended for scaling on-cluster HDFS" because HDFS utilization is not a reliable signal for autoscaling, and decommissioning DataNodes can delay worker removal ([Google Cloud Dataproc documentation](https://docs.cloud.google.com/managed-spark/docs/concepts/configuring-clusters/autoscaling)). Modern architectures increasingly decouple storage from compute using services like Cloud Storage or BigQuery, but legacy HDFS-based deployments remain common.

**High VM startup and migration overhead.** Provisioning new virtual machines in cloud environments typically takes several minutes — far longer than the sub-second scaling latency achievable for containerized or serverless workloads. For long-running big data jobs, this overhead is amortized over the job duration, but for interactive or near-real-time analytics, VM startup latency constrains scaling responsiveness and limits the effectiveness of reactive approaches that must wait for new instances to become available.

#### Primary Research Case: CEAS Framework

The **CEAS (Cost-Effective Auto-Scaling) framework** (Jannapureddy et al. 2019, *Applied Sciences*, vol. 9, no. 7, 1417) addresses the challenge of dynamically adjusting Hadoop cluster size in AWS cloud environments. The framework is designed around two core workload case studies: a MapReduce application and a sentiment analysis application processing Twitter data ([MDPI Applied Sciences](https://www.mdpi.com/2076-3417/9/7/1417)).

The CEAS framework operates by monitoring workload characteristics and automatically scaling computing resources of the Hadoop cluster — adding nodes when workload intensity increases and removing them when it decreases — to reduce computing resource use during low-demand periods while maintaining processing performance during peaks. The framework leverages AWS infrastructure to perform auto-scaling and demonstrates cost optimization through its ability to right-size the cluster dynamically rather than maintaining a fixed-size cluster provisioned for peak load. The sentiment analysis case study on Twitter data illustrates the framework's applicability to real-time big data processing scenarios where workload arrival patterns are bursty and unpredictable ([ResearchGate](https://www.researchgate.net/publication/332219555_An_Auto-Scaling_Framework_for_Analyzing_Big_Data_in_the_Cloud_Environment)).

#### Supplementary Research Cases

**Li et al. 2016 — Automatic Hadoop Scaling for Geospatial Big Data.** Researchers at the University of South Carolina proposed a performance-driven and cost-awareness framework to automatically scale Hadoop clusters for geospatial data processing in cloud environments (*ISPRS International Journal of Geo-Information*, vol. 5, no. 10, 173). The framework introduces two key innovations: (1) a new storage structure that enables timely removal of computing resources without incurring extra data transfer overhead, and (2) a predictive auto-scaling algorithm that more accurately calculates the number of resources to add. Using Digital Elevation Model (DEM) interpolation as a test case, the experimental results demonstrated that the framework could reduce computing resource utilization by approximately 80% while delivering similar performance as a full-powered cluster, and could effectively handle spike processing workloads by automatically increasing resources ([MDPI ISPRS](https://www.mdpi.com/2220-9964/5/10/173)). This work directly addresses the data locality challenge by designing a storage structure that avoids the data transfer penalty when scaling down.

**Khosravi et al. 2024 — Energy-Efficient Auto-Scaling for Spark on Kubernetes.** This study explores energy-efficient auto-scaling mechanisms for big data workloads, with a focus on Apache Spark running on Kubernetes clusters (*Energy-Efficient Auto-Scaling Mechanisms for Big Data Workloads in Cloud Environments*, 2024). The approach formulates a modeling framework that captures dynamic workload behavior, resource usage patterns, and node energy consumption characteristics. By continuously monitoring workload intensity, the mechanism predicts future fluctuations in computational demand, adjusts the number of allocated worker nodes, and orchestrates container-based resources to minimize energy overhead while meeting performance constraints. The study highlights the trade-offs between runtime efficiency, throughput, and power utilization across varying workload profiles, and demonstrates that a well-structured auto-scaling strategy can substantially reduce energy consumption without sacrificing latency or completion time ([ScienceQuill](https://sciencequill.com/index.php/TESRTCA/article/view/2024-08-04)).

#### Synthesis

The research collectively demonstrates that effective big data auto-scaling requires moving beyond simple threshold-based approaches that assume uniform resource utilization. The CEAS framework and the University of South Carolina work show that workload-aware and predictive scaling can achieve substantial cost reductions (up to 80% resource savings) while maintaining performance, but they must explicitly account for data locality, phase-dependent resource profiles, and the overhead of data migration during scale-down. Khosravi et al.'s work extends these principles to modern containerized Spark environments, adding energy efficiency as an explicit optimization objective alongside cost and performance. The Google Cloud Dataproc documentation confirms that production autoscaling systems still grapple with the fundamental tension between HDFS coupling and compute elasticity, recommending external storage and ephemeral cluster models as practical architectural responses ([Google Cloud](https://docs.cloud.google.com/managed-spark/docs/concepts/configuring-clusters/autoscaling)).

### Cost-Effective Graph Processing

**Problem Description.** Large-scale graph processing — encompassing algorithms such as PageRank, breadth-first search (BFS), single-source shortest path (SSSP), and connected component analysis — poses distinctive auto-scaling challenges that set it apart from conventional cloud workloads like web services or batch data analytics. Graph algorithms exhibit **irregular memory access patterns** because vertex neighborhoods are defined by sparse, unstructured edge connections rather than dense arrays, leading to unpredictable data access latencies that vary across partitions and supersteps. The computation is inherently **iterative**: the Pregel programming model, introduced by [Google in 2010](https://15799.courses.cs.cmu.edu/fall2013/static/papers/p135-malewicz.pdf), structures graph algorithms as a sequence of synchronized supersteps in which each vertex processes incoming messages, optionally updates its state, and sends messages to neighbors; a global barrier synchronizes all workers between supersteps. This iterative, barrier-synchronized nature means that **changing resource allocation mid-iteration incurs data redistribution overhead** — migrating graph partitions across workers requires serializing vertex state, transferring it over the network, and re-establishing partition metadata, which can dominate the actual computation time if performed too frequently.

Traditional graph processing frameworks such as [Apache Giraph](https://github.com/apache/giraph) and GraphLab were designed for static HPC clusters with fixed resource pools, assuming unlimited or pre-allocated resources. When deployed in cloud environments, these frameworks cannot exploit elasticity or pay-as-you-go pricing, leading to either **waste** (over-provisioning during low-activity supersteps) or **performance degradation** (under-provisioning during communication-intensive phases). Furthermore, **graph partition quality** directly affects scaling efficiency: poorly partitioned graphs generate excessive cross-partition message traffic, increasing network communication between workers and making resource demand harder to predict. Heterogeneous cloud resources — different VM types with varying CPU, memory, and network performance at different price points — further complicate scaling decisions, as the optimal VM mix depends on the graph structure, algorithm, and current superstep's communication-to-computation ratio.

**The Pregel Model and Its Interaction with Auto-Scaling.** In the Pregel vertex-centric model, a graph *G = (V, E)* is partitioned into *k* partitions distributed across *c* worker machines. During each superstep *S*, every active vertex executes a user-defined `Compute()` function in parallel; after all vertices finish, a global barrier ensures all messages sent during *S* are delivered before *S+1* begins. This Bulk Synchronous Parallel (BSP) model creates a fundamental tension with auto-scaling: scaling decisions can only be safely made **between supersteps**, not during them, because the barrier assumes a fixed set of workers. Adding or removing a worker mid-superstep would break synchronization and lose in-flight messages. Consequently, the effective scaling granularity is bounded by superstep duration — if a superstep takes 30 seconds, the system can only re-evaluate resource allocation at 30-second intervals, which may be too coarse for rapidly changing workloads. Additionally, the **communication-to-computation ratio varies dramatically across supersteps**: early supersteps in BFS or PageRank may be compute-heavy with little messaging, while later supersteps may become communication-dense as frontier vertices exchange messages across partition boundaries. A static resource allocation cannot adapt to this phase-dependent demand fluctuation.

**Primary Research Case: iGiraph and Heterogeneous Auto-Scaling (Heidari & Buyya 2021).** The iGiraph framework, originally introduced at [IEEE Cloud 2016](https://clouds.cis.unimelb.edu.au/~rbuyya/papers/iGiraph-Cloud2016.pdf), is a cost-efficient Pregel-like graph processing system designed for public clouds. Its core innovation is a **dynamic re-partitioning approach based on messaging patterns**: by monitoring the network traffic generated by message exchange between partitions, iGiraph identifies when the communication overhead justifies migrating partitions to fewer workers, thereby reducing the number of active VMs and lowering cost. The framework leverages the concept of **high-degree vertices** (hubs that generate disproportionate message traffic) and the **convergence level** of the running algorithm — as algorithms converge, fewer vertices remain active, allowing the system to scale down workers progressively.

The follow-up work by [Heidari & Buyya (2021)](https://www.computer.org/csdl/journal/ts/2021/08/08798698/1cun0oXpLR6), published in *IEEE Transactions on Services Computing* (vol. 14, no. 8, pp. 1729–1741), extends iGiraph into a full **auto-scaling algorithm for heterogeneous cloud resources**. The key advancement over the 2016 version is the explicit modeling of heterogeneous VM types — different instance families with varying CPU-to-memory ratios, network bandwidth, and pricing (on-demand, spot, reserved). The scaling policy evaluates the current workload's resource requirements (CPU, memory, network I/O) and selects the optimal combination of VM types that minimizes monetary cost while meeting SLA deadlines. The algorithm operates between supersteps, assessing whether the current resource allocation matches the projected demand for the next superstep based on historical message volume and active vertex counts. If demand is decreasing (algorithm converging), the system scales down by migrating partitions to fewer workers and releasing excess VMs; if demand is increasing (new frontier expansion), it scales up by provisioning additional workers of the most cost-effective VM type.

Experimental results reported in the paper demonstrate that this approach **decreases more than 50% of the dollar cost compared to standard Giraph** running on homogeneous on-demand instances, while maintaining comparable execution times. The earlier [GPaaS work (Heidari & Buyya 2019)](https://clouds.cis.unimelb.edu.au/papers/QoS-ResouceProvisioningAlgorithms-Graphs-FGCS.pdf), published in *Future Generation Computer Systems*, had already shown that the service-based architecture with SLA-driven resource provisioning reduces monetary cost by more than 40% compared to Giraph and PowerGraph, while reducing execution time by 10–15%. The 2021 IEEE TSC paper's contribution of heterogeneous resource selection compounds these savings by exploiting price-performance differences across VM types — for example, using memory-optimized instances for graph algorithms with large vertex state and compute-optimized instances for compute-intensive supersteps.

The relationship between **graph partitioning quality and auto-scaling efficiency** is critical: better partitioning reduces cross-partition edges, which reduces inter-worker communication, which in turn reduces the number of workers needed at any given superstep. iGiraph's dynamic re-partitioning actively improves partition quality during execution by observing actual message patterns and co-locating highly communicating vertex groups, creating a positive feedback loop — better partitioning enables more aggressive scaling down, which further reduces communication overhead.

**Supplementary Case: FaaSGraph — Serverless-Native Graph Computing (ACM 2024).** [FaaSGraph](https://dl.acm.org/doi/10.1145/3620665.3640361), published at ACM ICPE 2024, takes a fundamentally different approach by co-designing graph processing with serverless infrastructure rather than adapting VM-based frameworks. The paper identifies that directly migrating IaaS-based graph systems (e.g., Gemini) to serverless degrades performance: IaaS-based systems suffer from **tail latency surges during query spikes** and **resource waste under low load** because their processing capability is constant regardless of workload fluctuations. FaaSGraph introduces three key architectural innovations:

1. **ContainerSet as resource abstraction**: Instead of allocating VMs, FaaSGraph uses unified, fine-grained containers to execute graph processing tasks, maintaining scheduling flexibility while improving cluster resource utilization.
2. **Locality-aware resource fusion**: By reintroducing the "illusion of locality" through resource sharing and data consolidation, the system improves both computation and communication performance, mitigating the network overhead inherent in serverless environments.
3. **Bounded scaling**: Rather than immediately allocating new containers for incoming requests (unbounded scaling, which wastes memory), FaaSGraph waits for currently occupied resources to become available, reducing memory footprint and latency.

FaaSGraph also introduces graph-specific optimizations including **single-mode, main-initiated message passing** (reducing memory usage compared to mirror-initiated approaches) and **fast graph loading** (reducing preprocessing overhead, which the authors found dominates total execution time in serverless deployments). The system was evaluated on standard graph benchmarks (BFS, connected components, PageRank, SSSP) using SNAP datasets and a real-world road network graph. Results show that FaaSGraph **reduces monetary cost by up to 85.7%** compared to state-of-the-art graph processing systems while delivering steady 99th-percentile performance under highly fluctuated workloads, with tail latency improvements of up to 6× during query spikes. The [presentation at LDBC TUC 2023](https://datasets.ldbcouncil.org/event/eighteenth-tuc-meeting/day1/12.%20FaaSGraph-ShixuanSun-LDBC.pdf) confirms these results on billion-edge graphs including the Twitter (41.7M vertices, 1.47B edges) and Friendster (65.6M vertices, 1.8B edges) datasets.

**Comparative Insights.** The two approaches represent complementary strategies for cost-effective graph processing auto-scaling. iGiraph's VM-based approach retains the familiar Pregel/BSP programming model and achieves cost reduction through intelligent VM lifecycle management and heterogeneous resource selection, making it suitable for organizations with existing graph processing pipelines on IaaS. FaaSGraph's serverless-native approach eliminates the operational burden of VM management entirely, achieving higher cost savings (85.7% vs. >50%) and better tail-latency stability, but requires re-architecting graph algorithms to fit the serverless execution model. Both approaches confirm that **static resource allocation is fundamentally inadequate for graph workloads** and that auto-scaling policies must account for the superstep structure, partition quality, and phase-dependent resource demands unique to iterative graph computation.

### Workload Prediction

Proactive auto-scaling fundamentally depends on accurate workload prediction, but prediction quality is degraded by four interrelated challenges: (1) **Cold-start problem** — newly deployed services lack historical data, making ML models initially inaccurate or inoperable; (2) **Concept drift** — workload patterns shift over time due to changing user behavior, application updates, or seasonal effects, degrading model accuracy post-deployment; (3) **Burstiness and unpredictability** — sudden traffic spikes are inherently difficult to forecast, yet they are precisely the events where scaling decisions matter most; (4) **Non-stationarity** — cloud workloads combine periodic patterns (daily/weekly cycles) with noise, trend components, and irregular bursts, making it difficult for any single prediction model to maintain high accuracy across all scenarios. Prediction errors propagate directly to scaling decisions: overestimation causes over-provisioning (wasted cost), while underestimation causes under-provisioning (SLA violations). As E3Former's authors note, "an inadequate forecast could lead to under-provisioning [that] causes the system to overload, while over-provisioning incurs unnecessary resource costs" ([arXiv 2508.12773](https://arxiv.org/html/2508.12773v1)).

#### Cold-Start Problem

The cold-start problem in ML-based auto-scaling arises when a new application or microservice is deployed and has no workload history for training a prediction model. Without sufficient historical data, supervised models (LSTM, GRU, etc.) cannot learn temporal patterns, and the autoscaler must fall back to reactive thresholds — negating the proactive advantage. E3Former explicitly addresses this through **transfer forecasting**: experiments on twelve real-world datasets simulate cold-start scenarios by training on one workload and transferring to another. In these transfer tasks, E3Former reduces forecast MSE/MAE/WMAPE by an average of 15.3%/14.1%/26.3% compared to baselines, demonstrating generalization ability even without target-domain training data ([arXiv 2508.12773](https://arxiv.org/html/2508.12773v1)). The model's Representer component, which extracts multi-resolution periodic features through patching operations, and its Ensembler, which combines multiple sub-networks via adaptive weighting, together provide robustness against distribution shifts that characterize cold-start conditions.

#### Concept Drift

Concept drift occurs when the statistical properties of cloud workloads change over time — for example, a viral event alters request patterns, an application update changes resource consumption profiles, or seasonal shifts modify traffic cycles. Traditional batch-trained ML models degrade silently as drift accumulates. The **Proceed** framework (arXiv 2412.08435, 2025, published at KDD 2025) addresses this by proactively estimating concept drift between recently used training samples and the current test sample, then using an adaptation generator to translate the estimated drift into model parameter adjustments. Unlike conventional online learning, which updates parameters using delayed ground-truth values (creating a temporal gap that itself introduces drift), Proceed proactively adapts the model before the forecast is needed. Experiments on five real-world datasets show Proceed brings significant performance improvements over state-of-the-art online learning methods ([arXiv 2412.08435](https://arxiv.org/html/2412.08435v3)). E3Former similarly combats concept drift through its **Adapter** component, which implements online adaptation via cumulative gradient-based parameter updates, enabling rapid refining to workload dynamics as they shift ([arXiv 2508.12773](https://arxiv.org/html/2508.12773v1)).

#### Non-Stationarity and Burstiness

Cloud workloads are non-stationary: they exhibit multi-scale periodic patterns (hourly, daily, weekly, seasonal cycles) intertwined with irregular bursts, long-term trends, and noise. This non-stationarity makes univariate models (e.g., ARIMA on CPU alone) insufficient, as they cannot capture cross-metric correlations that signal impending load changes. The **Bi-LSTM multi-variable auto-scaling framework** (Dang-Quang & Yoo, MDPI Applied Sciences 2022) addresses non-stationarity by incorporating multiple workload variables — CPU utilization, memory usage, network I/O, and request rate — into a single bidirectional LSTM model that captures both forward and backward temporal dependencies. Experimental results show the multivariate Bi-LSTM autoscaler was 47.2% and 14.7% more efficient than the multivariate LSTM and CNN-LSTM autoscalers, respectively, demonstrating that multivariate modeling substantially improves prediction under non-stationary conditions ([MDPI Applied Sciences 2022](https://www.mdpi.com/2076-3417/12/7/3523)). However, Bi-LSTM's supervised training still requires substantial labeled historical data and does not inherently handle concept drift without retraining.

Burstiness — sudden, short-duration traffic spikes — is particularly challenging because it violates the smoothness assumptions underlying most time series models. The **Monash University LSTM-based multi-step prediction** approach (Suleiman et al., ICSOC 2023 Workshops, Springer 2024) addresses this by predicting workload over multiple future time steps rather than a single step, enabling the autoscaler to anticipate burst onset earlier than single-step methods. Using real-world datasets (1998 World Cup and NASA web request traces), the multi-step LSTM model reduces P95 latency fluctuations and timeout rates under complex workload scenarios, demonstrating that multi-step horizons improve scaling decision quality when bursty traffic is present ([Monash University research](https://research.monash.edu/en/publications/predictive-auto-scaling-lstm-based-multi-step-cloud-workload-pred/)).

#### Primary Research Case: E3Former

The **Online Ensemble Transformer (E3Former)** (arXiv 2508.12773, 2025) is the primary research case for mitigating prediction failure modes at scale. E3Former synergizes four components: (1) a **Representer** that extracts multi-resolution periodic features through patching operations, explicitly modeling nested cycles; (2) a **Transformer** that leverages self-attention to capture long-range dependencies; (3) an **Adapter** that implements online adaptation via cumulative gradient-based parameter updates for rapid refining to changing dynamics; (4) an **Ensembler** that combines results from different sub-networks through adaptive weighting, enhancing robustness against distribution shifts. The ensemble strategy directly addresses the limitation of single-model approaches: when one sub-network fails to capture a particular pattern (e.g., a burst or a regime shift), other sub-networks compensate, and the adaptive weighting dynamically adjusts each sub-network's contribution based on recent performance.

Verified quantitative results from the paper include: in online forecasting tasks on twelve real-world datasets, E3Former reduces forecast MSE/MAE/WMAPE by an average of 13.9%/11.7%/19.1% compared to previous state-of-the-art methods. In transfer forecasting tasks simulating cold-start scenarios, it reduces MSE/MAE/WMAPE by an average of 15.3%/14.1%/26.3%. E3Former has been deployed within **ByteDance's Intelligent Horizontal Pod Auto-scaling (IHPA) platform**, supporting the stable operation of over 30 applications (including Douyin E-Commerce, TouTiao, and Volcano Engine), with predictive auto-scaling capacity reaching over 600,000 CPU cores. Compared with Kubernetes' built-in Naïve HPA module, E3Former-based scaling reduces average/maximum Pod occupation by 7.3%/29.4% and decreases average/maximum system latency by 5.6%/91.7%, while reducing resource utilization by over 40% ([arXiv 2508.12773](https://arxiv.org/html/2508.12773v1)).

#### Supplementary Research Cases

**FELT** (Ding et al., Tsinghua Science and Technology, 2025) addresses prediction failure through a complementary angle: workload heterogeneity. Rather than training a single model per container (which becomes impractical at scale) or a single model for all containers (which struggles with heterogeneity), FELT introduces a **feature-enhanced workload similarity-aware algorithm** that adaptively groups containers with similar workload patterns in real time by analyzing both historical and recent similarity. It characterizes workload dynamics from both waveform and value perspectives, reducing model complexity while capturing macroscopic and detailed variations. FELT leverages a Transformer with customized position encoding and attention masks based on real-time workload similarity, employing multi-head self-attention for parallelized training. On three real cloud workload datasets (Alibaba cluster-trace-microservices-v2021, v2022, and Fisher), FELT improves prediction accuracy by up to 28.06%, reduces training time by up to 95.75%, and reduces model parameters by up to 84.55% compared to SOTA methods ([Tsinghua Science and Technology](https://www.sciopen.com/article/10.26599/TST.2025.9010102); [FELT PDF](https://www.sciopen.com/local/article_pdf/10.26599/TST.2025.9010102.pdf)). FELT's approach to grouping containers by similarity mitigates non-stationarity: when one container's workload pattern shifts, the grouping algorithm can reassign it to a more appropriate model, avoiding the accuracy degradation that would occur if a mismatched model persisted.

The **Bi-LSTM multi-variable framework** (Dang-Quang & Yoo, 2022) contributes to handling non-stationarity through multivariate input, as described above. A key limitation is that Bi-LSTM, like all supervised models, remains vulnerable to concept drift and cold-start conditions unless paired with online adaptation mechanisms.

#### Prediction Horizon and Error Propagation

The relationship between prediction horizon length and scaling decision quality is critical: longer horizons (minutes to hours ahead) are necessary because physical resource allocation in data centers incurs latency — VM startup, container scheduling, and load balancer reconfiguration take time. However, prediction error grows with horizon length, as uncertainty compounds over time. This creates a fundamental trade-off: short horizons yield accurate predictions but may not provide enough lead time for resource provisioning, while long horizons provide adequate lead time but with degraded accuracy. E3Former addresses this by combining offline training (for stable periodic patterns) with online adaptation (for recent dynamics), achieving a 10% average error reduction in online forecasting that translates directly to more timely and accurate scaling decisions ([arXiv 2508.12773](https://arxiv.org/html/2508.12773v1)). The Monash multi-step LSTM approach similarly demonstrates that multi-step prediction (forecasting several steps ahead) outperforms single-step prediction by enabling earlier scaling triggers, though at the cost of higher per-step error ([Monash University research](https://research.monash.edu/en/publications/predictive-auto-scaling-lstm-based-multi-step-cloud-workload-pred/)).

Prediction error propagates to scaling decisions in a direct and quantifiable manner. Over-prediction leads to over-provisioning: E3Former's authors report that over-provisioning "not only wastes physical resources but also incurs unnecessary costs," while under-provisioning "can lead to system overload and a decrease in service quality" ([arXiv 2508.12773](https://arxiv.org/html/2508.12773v1)). The practical impact is measured in SLA violations (latency spikes, timeouts) and resource waste (idle instances). E3Former's deployment at ByteDance demonstrates that reducing prediction error by ~10% translates to a 40%+ reduction in resource utilization while maintaining service quality — illustrating that even modest prediction improvements yield significant operational and economic benefits at scale.

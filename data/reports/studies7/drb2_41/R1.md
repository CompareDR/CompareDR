# 截至2021年底的低代码开发：市场与技术全景调研

本文把时间截点严格放在 2021年12月31日：重点回答当时的低代码开发（Low-Code Development，LCD）究竟建立在什么技术之上、主要解决什么问题、市场上有哪些代表性平台，以及企业为什么愿意采用它。这里的“低代码”主要指：通过声明式、高层抽象、可视化建模和预制组件减少手写代码，同时通常仍允许专业开发者在必要时加入传统代码；与之相邻的“无代码（No-Code）”更强调让业务人员在几乎不编程的情况下完成应用构建。2021年的研究同时提醒，市场对“low-code”这个标签的使用非常宽泛，因此本文会区分严格意义上的企业级 LCAP 与更广义的低代码/无代码工具生态。[1]

从市场成熟度看，到2021年，低代码已经不是一个只有少数创业公司的边缘类别。Bock 与 Frank 当年估计，市场上已有“大约二十家到数十家”厂商以 low-code 名义销售产品；Forrester 在2021年第二季度针对专业开发者的低代码平台评估中，则筛出了 14家最重要的供应商。与此同时，微软、Mendix、OutSystems 和 ServiceNow 等企业厂商都在2021年企业级 LCAP 市场中获得了主要分析机构的高度评价。[2]

## 核心技术基础

低代码最容易被误解的一点，是把它当作一种全新的编程技术。2021年的系统性平台研究得到的结论恰恰相反：低代码真正的新意主要在“集成和产品化”，而不是发明了一套全新的计算模型。 它把模型驱动开发、可视化编程、数据建模、GUI 编辑器、组件复用、API 集成、工作流、部署工具和托管运行时等已有多年的技术，整合进一个高度统一的开发环境，并提高抽象层级。[3]

| 技术基础或设计范式 | 在低代码平台中的体现 | 为什么重要 |
| --- | --- | --- |
| 声明式编程与高层抽象 | 与其逐行告诉计算机“怎样做”，开发者更多描述“应用需要什么”：数据实体、页面、规则、流程、权限等。2021年的典型 LCAP 定义明确把 model-driven、metadata-based 等声明式高层抽象视为基本特征。[3] | 把开发单位从语句、函数提升到“表单、实体、流程、服务”等更大粒度对象，从而减少样板代码。 |
| 模型驱动开发（MDD/MDE）与概念建模 | 数据模型、关系、流程、状态以及页面行为通过模型表达，再由平台映射或转换成可执行实现。对10个平台的研究发现，所有受考察平台都提供数据结构定义，而且几乎都使用 ER 类模型或简化的专有建模语言。[3] | 这是低代码减少手写程序最核心的技术机制之一；Bock 与 Frank甚至认为概念建模实际上处于低代码平台的技术核心。[3] |
| 可视化编程、拖放与 WYSIWYG | 页面通过 GUI Designer、控件面板、拖放和可视化属性编辑完成；逻辑也可以表现为流程图、规则或可视化动作。2021年实践者研究中，“drag-and-drop”“visual programming”“WYSIWYG”都是最常见的低代码特征描述。[4] | 让开发者直接操作接近业务概念的可视对象，同时降低前端布局与交互代码的负担。 |
| 预制组件、模板与可复用构件 | 平台提供 widgets、页面模板、组件、服务、SDK、流程动作和通用功能模块。实践者研究发现，低代码平台的主要实现单元包括 API、模板、组件、服务、框架和 widgets。[5] | “搭积木”替代重复实现，形成速度优势；真正复用的通常是通用架构能力，而不一定是某一行业的完整业务模型。[3] |
| 数据建模、CRUD 自动化与 ORM 思想 | 平台把数据库表、对象、表单和 UI 自动连接起来，可自动产生常见增删改查行为，开发者不必手工实现完整 MVC、数据库访问层和对象—关系映射。[6] | 这解释了为什么数据录入、台账、管理后台等“数据中心型应用”特别适合低代码。 |
| API、连接器与服务组合 | 外部数据库、REST/Web Services、JDBC、SaaS API 等被封装成连接器或可视化服务。对10个平台的研究发现，全部支持某种外部数据/API访问；实践者数据中，API也是最常见的高层实现单元。[7] | 低代码因此不只是“页面生成器”，而逐渐成为企业应用之间的组合与集成层。 |
| 工作流/BPM、规则与事件驱动 | 审批流、任务状态、条件分支、业务规则、事件处理通过 BPMN、专有流程模型、表达式语言或事件脚本表达。大型平台中相当一部分以工作流引擎作为核心能力，不过并非所有低代码平台都有完整 BPM 引擎。[3] | 企业业务往往本质上是“数据 + 人员 + 状态 + 流程”，因此 BPM 与低代码天然容易融合。 |
| 统一的应用生命周期与自动部署 | 开发环境往往同时处理 UI、数据、逻辑、权限、测试/发布和运行；多数受研究平台提供较强的部署支持，有的平台运行在厂商托管运行时，有的可以形成独立部署物。[3] | 速度提升并不只来自“少写代码”，也来自少配置数据库、框架、部署环境和多个开发工具之间的集成。 |
| 内建身份、角色和权限体系 | 被研究的平台几乎全部提供角色与用户权限组件，并与应用一起部署。[3] | 将企业应用反复需要的安全与治理基础设施平台化，减少每个项目重复实现。 |
| 传统代码的“逃生舱” | 真正的低代码通常不是彻底禁止编码。2021年的平台比较发现，一些平台明确提供 Java、JavaScript 等扩展点，而且几乎所有复杂平台在某一层都允许回到传统代码；实践者也确实报告在低代码项目中使用 Java、JavaScript、C#、Python 等。[7] | 这是低代码和严格无代码的重要区别：可视化负责常规80%式工作，特殊需求仍由代码扩展。 |

内在联系与趋势。 这些技术可以串成一条相当清晰的“抽象链”：业务概念 → 模型/元数据 → 可复用组件与服务 → 平台运行时/生成实现 → 自动部署。因此，低代码的本质并不是简单的“拖拽界面”，而是把软件工程中许多反复出现的决策预先固化在平台里。GUI、ORM、MVC、身份管理、API 连接和部署等工作原本由程序员在每个项目中重新组合，现在由平台提供一套预先集成的参考架构。Bock 与 Frank 据此认为，2021年的低代码没有表现出根本性的新技术突破，其生产率来源主要是减少低到中等复杂度项目中的例行工作。[3]

这也解释了另一个看似矛盾的现象：低代码一方面号称“少写代码”，另一方面却与专业编程语言、API、微服务和云平台关系越来越密切。它并不是取代这些技术，而是在它们之上增加更高一级的抽象层。2021年的实践者研究甚至发现，同一个平台往往同时横跨前端、工作流、后端和集成；这表明低代码正从单一“页面/表单生成器”向综合应用平台演进。[8]

## 主要应用领域

截至2021年底，低代码的最佳适配场景具有一个共同结构：业务数据比较明确、界面和流程有一定规律、需要较快迭代，并且大量工作属于常见企业应用模式。 这比简单按“金融、制造、零售”等行业分类更能解释它为什么有效。Bock 与 Frank 对当时产品的观察甚至可以粗略归纳为四类来源：简单数据管理平台、传统工作流系统、GUI/数据中心型 IDE，以及能够同时完成配置、集成和应用开发的综合平台。[3]

| 主要应用领域 | 典型应用/业务问题 | 低代码为什么适配 |
| --- | --- | --- |
| 内部数据管理与部门级业务应用 | 数据采集、登记台账、资产/库存记录、工单、项目管理、小型业务数据库、员工工具、管理后台 | 这类应用主要由数据模型、CRUD、表单、权限和少量规则组成，恰好对应低代码最成熟的基础能力。所有被研究的典型平台都提供数据结构定义和 GUI 设计器。[3] |
| 工作流、审批与业务流程自动化 | 请假/采购/报销审批、员工入职、服务请求、案件/工单流转、多角色业务流程 | 流程节点、条件、角色、状态和通知特别容易以可视模型表达。2021年的实践者研究中，BPM 是明显出现的应用领域；一些大型 LCAP 本身就继承自工作流/BPM 产品。[9] |
| Web 应用与门户 | 客户门户、合作伙伴门户、营销/服务网站、业务自助门户、后台 Web 系统 | 可视化 UI、响应式页面、数据绑定和现成组件可显著压缩前端开发量。实践者样本中的70个明确应用案例里，有28个属于 Web 应用。该数字反映的是社区样本，而非全市场份额。[10] |
| 移动应用 | 现场作业、巡检、销售工具、移动数据采集、员工应用和客户应用 | 平台可从同一模型支持手机、平板和浏览器，并封装跨设备布局及部署问题；同一实践者样本中有31个明确的移动应用，是出现最多的类型。[11] |
| CRM、CMS 与电商周边应用 | 客户关系流程、内容管理、B2B/B2C 商务应用、销售流程或现有 SaaS 的扩展 | 这些领域具有高度重复的数据、页面、权限和流程模式。2021年实践者样本中，电商、CRM 和 CMS 均有明确使用实例，其中电商是该小样本中提及最多的业务领域。[10] |
| 系统集成与“组合式”应用 | 把 ERP、CRM、数据库、SaaS 和内部服务组合成一个新业务界面；同步或转换数据；API 编排 | 大量现成连接器、REST/Web Service 和 API 抽象减少接口胶水代码，因此低代码逐步从“应用制作工具”扩展为集成平台。[7] |
| 遗留系统现代化 | 在旧系统外增加现代 Web/移动界面、快速重建部门应用、逐步替代老旧手工系统 | 低代码可以保留现有数据库/API，同时快速增加新的应用层。微软在2021年介绍 Power Apps 企业用途时明确列举了流程自动化、遗留应用现代化和规模化解决业务问题。[12] |
| RPA、ETL 与自动化生态 | 重复任务自动化、数据转换、机器人流程、跨系统触发与自动化 | 2021年的低代码研究已经把 RPA、ETL 列入实际讨论领域，一些大型平台也开始把 RPA、BI、AI 功能作为可配置构件放入同一环境。[9] |
| 制造业与工业数字化 | 生产现场应用、流程数字化、工业工程工具、操作数据采集与快速业务应用 | 2020年前后的研究已专门讨论 low-code 作为制造业数字化转型的使能方式，说明应用边界已超出传统办公自动化。[13] |
| IoT 与边缘/设备应用 | 设备数据接入、传感器应用、IoT 管理和面向领域工程师的应用构建 | 2020年的 ACM/IEEE 研究分析了16个用于 IoT 系统开发的平台，显示低代码/MDE 思想已经进入异构设备和物联网开发领域，不过当时仍属于较新、具有研究性质的应用方向。[14] |
| 垂直行业快速应用 | 例如智慧农业、医疗等领域的专业小型应用 | 2021 IEEE AFRICON 已出现利用低代码工具构建智慧农业应用的专门研究；实践者研究中也观察到医疗案例。[15] |

从应用形态看，2021年的低代码其实存在一个明显的“甜蜜点”：最适合的是可以表达成

数据模型 + 表单/UI + 业务规则 + 工作流 + API 集成 + 权限

的系统。[3]

这套结构恰好覆盖了企业信息系统的大量需求，因此低代码首先在内部管理、流程自动化、Web/移动业务应用上成功并不偶然。随后，随着连接器和云服务能力增强，其应用边界向遗留现代化、跨系统集成以及 IoT 等方向扩张。[16]

有趣的发展趋势是从“部门小工具”走向“企业应用平台”。 早期的低代码产品往往来自 RAD、PaaS、模型驱动工具、BPM 或数据管理系统；到了2021年，这些原本不同的产品类别开始在同一个“low-code”市场中汇合。微软当时已经公开把 Power Apps 的应用范围描述为从生产力应用一直延伸到 mission-critical solutions，并用于流程自动化和旧应用现代化；Mendix 同期则将平台定位到从 citizen developer 到专业开发者的多体验应用开发。[17]

不过，这种扩张不能解读为“任何软件都适合低代码”。2021年的实证研究表明，一旦应用大量超出平台预先设计的模式，开发者会遇到定制 UI、动态事件、第三方集成和自动化测试等问题；复杂需求往往又需要回到传统代码。[18]

## 主流平台与工具

“主流平台”需要先区分口径。严格的企业级/专业开发者低代码市场与面向业务用户的 no-code/low-code 工具市场在2021年已经高度重叠，但并不完全相同。Forrester 于2021年5月发布的 Low-Code Development Platforms for Professional Developers, Q2 2021 明确筛选出14家“最重要”的供应商，这可以作为当时专业低代码市场比较可靠的快照。[19]

| 平台/供应商 | 截至2021年底的市场位置或特点 |
| --- | --- |
| Mendix | Forrester 2021专业开发者低代码评估的14家重要厂商之一；2021年9月，Mendix还宣布自己连续第三年进入 Gartner 企业 LCAP Leader 区域。[20] |
| OutSystems | 同属 Forrester 2021 的14家重要专业低代码厂商；2021年9月，其官方公告称其再次进入 Gartner 企业 LCAP Leader 区域。[21] |
| Microsoft Power Apps / Power Platform | Forrester 的14家重要厂商之一。微软在2021年9月宣布 Power Apps 进入当年 Gartner 企业 LCAP Leader 区域；其生态同时覆盖应用、流程/自动化和专业开发扩展。[22] |

| Salesforce | 位列 Forrester 2021 的14家重要供应商，体现了大型 SaaS/CRM 平台把应用扩展、自动化和平台开发逐渐纳入低代码范畴的趋势。[19] |

| GeneXus | 同为 Forrester 2021筛选的重要专业低代码供应商之一。[19] |
| HCL Software | 位于 Forrester 2021低代码专业开发者的14家重要供应商名单。[19] |
| Thinkwise Software | 位于同一 Forrester 2021专业低代码市场名单。[19] |
| Unqork | Forrester 2021列出的重要供应商之一，同时也出现在2021年实践者研究的前端、工作流、集成等多个低代码类别中。[27] |
| WaveMaker | Forrester 14家专业低代码供应商之一；实践者研究也将其观察为能够覆盖前端、后端等应用组成部分的平台。[27] |

在这个较严格的企业级市场之外，截至2021年还存在一个非常活跃的业务开发者/no-code 邻接层。2021年的实践者研究在301个相关讨论帖中识别了137个至少被提及一次的平台；其中出现较频繁的包括 Bubble、Webflow、Adalo、Airtable、AppGyver、Glide、Power Apps、Zapier、AppSheet、OutSystems、Thunkable、Backendless、Softr 等。这个统计反映的是 Stack Overflow/Reddit 等开发者社区的讨论热度，不能解释成市场份额排名。[28]

其中有几个特别值得注意：

- Google AppSheet 到2021年已经明确定位为 no-code 平台。Google 在2020年收购 AppSheet，并在2021年11月宣布 AppSheet 被 Forrester 的 Low-Code Platforms for Business Developers, Q4 2021 评为 Leader，说明“无代码”与“低代码业务开发者平台”在分析机构分类中已经明显交叉。[29]

- Betty Blocks 同样强调面向 citizen developer 的 no-code 环境，同时为专业开发者保留低代码扩展；其官方公告显示，它在 Forrester 2021年第四季度面向业务开发者的低代码评估中被列为 Leader。[30]

- Bubble、Webflow、Airtable、Zapier 等虽然未必符合严格的“企业级 LCAP”定义，却在2021年实践者低代码讨论中具有很高可见度，分别覆盖应用构建、Web 前端、数据协作和自动化/集成等不同需求。[28]

市场结构上的内在联系非常有意思：2021年的“低代码市场”实际上是多个历史产品类别发生汇流，而不是一种统一架构打败了所有其他开发方式。 Bock 与 Frank 对当时产品历史的研究发现，大多数被称作 low-code 的产品早于“low-code”这个标签存在，有些原本叫 RAD，有些是 PaaS、model-driven application platform，还有一些源于 BPM、mobile BPM 或 human-centric BPM；技术和功能范围因此差异极大。[3]

这也解释了为什么2021年的主流厂商看起来如此“不像一类东西”：Mendix/OutSystems 更接近综合应用开发平台，Power Apps 与微软云和办公/业务生态紧密整合，ServiceNow/Pega/Appian 有明显流程与企业工作流属性，Salesforce 依附大型 SaaS 业务平台，Oracle 则具有强数据库背景，而 AppSheet/Betty Blocks/Bubble 更贴近 citizen developer 或 no-code。Forrester 同年甚至分别存在“面向专业开发者”和“面向业务开发者”的低代码评估，本身就反映了这个市场正在按开发者角色与应用复杂度分层。[31]

所以，截至2021年底，评价一个低代码平台时，“它是不是 low-code”其实已经不是最重要的问题；更实用的问题是：它抽象了哪一部分软件开发、目标用户是谁、复杂需求能否退回代码、与现有企业系统怎样集成、以及应用是否能脱离该平台长期生存。 这种高度异质性正是2021年低代码产业最重要的市场特征之一。[3]

## 公认的业务优势

截至2021年底，研究、厂商和实践者之间最稳定的共识，可以概括成一句话：低代码的价值不是“让代码消失”，而是把重复的软件工程劳动平台化，从而让有限的开发资源更快地转化为业务应用。 2021年的实践者实证研究从相关讨论中归纳出16类优势；其中出现次数明显最多的是“开发更快”（65次）和“易学习/易使用”（52次），随后包括降低 IT 成本、现成构件、对新手友好、集成能力、减少开发工作量、易部署以及 IT 治理等。不过这些数字是实践者表达的看法，而不是随机对照实验所测得的生产率提升比例。[32]

| 公认优势 | 背后的技术机制 | 截至2021年的合理解读 |
| --- | --- | --- |
| 缩短开发周期与 Time-to-Market | 可视建模、模板、组件、CRUD 自动生成、预配置运行环境和部署工具取代大量手工实现 | 这是2021年实践者研究中最突出的优势；学术平台分析也认为生产率主要来自减少低到中复杂度项目中的例行工作。[33] |
| 提升开发者生产率 | GUI、ORM/MVC、API 接入、权限和部署等通用架构被平台预先集成 | 开发者不必不断在 IDE、数据库、建模工具、框架和部署工具之间维护大量胶水代码及配置。[3] |
| 降低技术门槛、扩大“开发者”群体 | 拖放、模板、模型、表达式和业务语言替代部分传统编码 | 这为 citizen developer 或技术能力较弱的业务人员参与应用构建创造条件；“对非专业开发者友好”也是2021实践者描述低代码时反复出现的特征。[34] |
| 改善业务与 IT 的协作 | 业务人员可以直接查看和修改更接近业务概念的模型、页面和流程；专业开发者则处理复杂扩展 | 低代码的重要商业诉求之一就是改善 business–IT alignment；2021年微软也积极推广由专业开发者、低代码开发者和 IT 组成的“fusion teams”。[35] |
| 更快迭代和响应需求变化 | 页面、数据字段、规则和工作流可以通过模型修改，而不必全面重写底层实现 | 这使原型、试错和业务规则调整成本下降；Bock 与 Frank认为，在条件合适时 LCP 可以提高软件设计与开发的 agility。[3] |
| 复用成熟构件，减少样板代码 | widgets、模板、API、通用服务和预制应用架构被反复使用 | 实践者把“丰富的开箱即用单元”和“避免 boilerplate”列为明确收益；平台研究则发现真正被大量复用的是 GUI、ORM、MVC、数据接入和部署等通用架构机制。[33] |
| 降低部分项目的开发与运维成本 | 更少的手写开发时间、更短部署周期、更多人员能够承担简单应用开发 | 实践者调查中“Lower IT costs”是较常见的优势，但学术研究特别警告，2021年还缺少充分的跨平台成本效率研究，因此不能简单得出“低代码必然更便宜”。[33] |
| 加速系统集成和旧系统现代化 | API/连接器可以把旧数据库、SaaS、云服务与新界面组合起来 | 低代码能够在不立即重写核心系统的情况下增加现代应用层；微软2021年的官方案例定位直接把“modernize legacy apps”列为 Power Apps 的主要企业用途之一。[36] |
| 简化多端交付和部署 | 同一模型可适配浏览器、平板、手机，并由平台处理部分发布/运行环境 | 典型平台普遍支持部署自动化和不同目标终端；实践者也将 easy deployment 识别为收益。[37] |
| 促进标准化、权限管理与治理 | 应用基于统一平台架构、用户身份、角色权限及部署流程构建 | 相对于大量各自为政的小型手写应用，集中式 LCAP 有机会统一安全和生命周期控制；典型平台普遍内建角色/用户权限，实践者研究中也出现了 improved IT governance。[37] |

这些优势实际上都源于同一个经济机制：

抽象层提高 → 重复工作减少 → 单个开发者产能提高 → 业务人员能够参与 → 从需求到可运行应用的链条缩短。 [38]

因此，“快”“便宜”“容易”“协作更好”并不是四个彼此独立的优势，而是同一套技术选择的不同结果。例如，把数据库和页面关系模型化，会同时减少 CRUD 编码、降低学习门槛、缩短原型时间，并使业务人员更容易理解应用；把 API 做成连接器，则同时提升集成速度和复用性；把发布环境纳入平台，则同时减少 DevOps 配置和部署摩擦。[7]

但2021年已经有足够证据表明，这些优势存在清晰的适用边界。低代码不是无条件的“10倍开发神器”。Bock 与 Frank 的结论是：它最可能在项目需求能够落入平台预先定义框架时产生生产率提升；一旦项目必须不断突破框架，收益就可能快速下降。[3]

这项边界在实践数据中表现得尤其明显。针对约5,000个 Stack Overflow 相关帖子的一项2021年 MSR 研究发现，超过40%的问题涉及定制（customization）；其中动态事件处理是既热门又困难的主题，相关问题中有 75.9% 没有获得被接受的答案，自动化测试也构成明显挑战。[39] 另一项2021年实践者研究则直接记录了高价格、定制受限、复杂问题仍需编码、无法获得源代码、维护和调试困难、集成困难以及 vendor lock-in 等问题。[8]

其中厂商锁定尤其值得注意。典型 LCAP 中的模型和表示方式通常不是跨平台可移植格式；2021年的平台研究明确指出，在一个低代码平台中建立的表示通常不能直接用于另一个平台，因此迁移可能意味着重新开发，这会把前期获得的速度优势转换成长期的切换成本。[3]

所以，以2021年底为截点，对低代码最准确的业务判断并不是：

> “低代码会取代传统软件开发。”

而更接近：

> 低代码把企业应用开发中高度重复、可模型化、可组件化的部分变成平台能力，使专业开发者和业务人员能把精力集中在真正具有业务差异化的部分；传统代码则继续承担复杂算法、深度定制、高性能需求和平台无法抽象的边缘情况。

这一判断与2021年的技术研究相吻合：低代码平台最重要的特点，是在同一个环境里整合原本分散的成熟软件工程构件，以减少例行开发劳动；它更适合作为传统开发的上层抽象与补充，而不是普适性的替代品。[1]

综合四个方面来看，2021年底的低代码已经完成了从“RAD/可视化开发的重新包装”向“企业应用平台类别”的关键转变，但技术核心仍然是模型驱动、可视化、组件复用、API 集成和平台化运行时。 市场竞争的核心也开始从“谁能做到拖拽开发”转向“谁能同时覆盖专业开发者与 citizen developer、谁能连接更多企业系统、谁能处理完整应用生命周期，以及谁能在速度与可扩展性/治理之间取得更好平衡”。Forrester 同年分别评估专业开发者和业务开发者平台，以及大型云/SaaS/BPM厂商同时进入这一市场，正是这种变化最明显的信号。[40]

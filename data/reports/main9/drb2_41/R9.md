# 低代码开发（Low-Code Development）市场与技术调研报告：截至2021年底的行业状况

## 范围、方法与合规说明

本报告聚焦**截至2021年底**低代码开发市场与技术形态。对于题目中明确禁止访问和引用的论文《Modelling in low-code development: a multi-vocal systematic review》及其列出的全部 URL，本报告**不使用、不引用、不纳入分析**。  
需要说明的是，用户提供的材料中有相当一部分为2026年前后的厂商比较、咨询文章或产品导购。本文将其主要作为**后验参照**，用于帮助理解平台能力的延续性与分类逻辑；凡涉及2021年前后市场事实、市场规模、厂商集合和行业判断，优先采用更接近2021年前后的 Gartner、Forrester、Salesforce 2021 公告、Cyclr 对 Gartner 2021 预测的转述等资料。对2026来源中关于平台功能的描述，本文会谨慎标注为“后续资料显示”或“作为能力类型的佐证”，不把它们直接当作2021年前的产品架构证据。

## 一、核心技术基础

### 1.1 视觉化建模与模型驱动开发

低代码开发最核心的技术基础是**视觉化建模**与**模型驱动开发**。平台通常允许开发者通过拖拽组件、配置表单、定义数据模型、设计页面流和业务流程来生成应用，而不是从零编写大量代码。Gartner 对企业低代码应用平台的定义强调，低代码应用平台让专业开发者通过视觉界面、可复用组件和预置逻辑开发应用，其目标是在不完全牺牲控制力和定制性的前提下提升开发速度（[Kissflow, 2026](https://kissflow.com/low-code/gartners-magic-quadrant-about-low-code-vs-no-code-2025/)）。

从技术视角看，这类平台通常内置一种或多种**领域特定语言（DSL）**或元模型：页面、流程、数据实体、权限、集成连接器等都被抽象成平台可解释的模型。平台随后通过运行时解释、代码生成或混合方式将模型转换为可执行应用。Mendix 被后续资料描述为“模型驱动的全栈平台”，其 Studio Pro 建模、Java actions、React widgets、插件、REST/OData/GraphQL 连接器、SSO、审计与治理控制，以及面向 Mendix Cloud、SAP BTP、Kubernetes 和私有云的部署能力，体现了典型企业级低代码平台的技术组合（[WeWeb, 2026](https://www.weweb.io/blog/low-code-development-platforms-buyers-guide)）。

### 1.2 元数据驱动、组件化与模板化

低代码平台通常将应用结构存储为**元数据**：页面布局、字段、业务规则、流程状态、权限关系、API 映射、环境配置等都以结构化方式保存。这样做的好处是，平台可以支持快速复制、版本管理、权限校验、自动部署和环境迁移。组件化则进一步降低开发门槛：按钮、表格、图表、表单、审批节点、连接器、身份认证模块、通知模块等可复用组件成为低代码生产力的基础。

这种组件化并不是孤立存在的。Forrester 早期跟踪的低代码厂商集合非常宽泛，包括 Salesforce、Appian、Bizagi、K2、Kintone、Mendix、Nintex、OutSystems、Quick Base、ServiceNow、Zoho、FileMaker、Magic Software 等，说明低代码在2021年前已经融合了 BPM、工作流、PaaS、SaaS 定制、数据库应用构建器等多种传统根源（[Forrester, n.d.](https://cdn2.hubspot.net/hubfs/2096695/Vendor%20Landscape_A%20Fork%20In%20The%20Road%20For%20Low_Code%20Development%20Platforms.pdf?submissionGuid=83c10178-9f4a-4980-8d27-2f20a0fcdaa1)）。

### 1.3 工作流、BPM、规则引擎与流程编排

截至2021年底，低代码与 BPM、工作流自动化之间的关系非常紧密。许多低代码平台并非从“通用软件工程 IDE”演化而来，而是从流程管理、审批流、表单流转、案例管理和企业自动化工具演化而来。Appian、Pega、Bizagi、K2、Nintex 等平台的市场定位长期围绕流程、案例管理、审批与自动化展开。

这意味着低代码平台的关键技术基础包括：

| 技术基础 | 典型能力 | 与低代码的关系 |
|---|---|---|
| BPMN/流程建模 | 审批、任务分派、状态流转 | 支撑业务流程应用 |
| 规则引擎 | 条件判断、自动路由、合规规则 | 降低业务逻辑编码量 |
| 表单引擎 | 数据采集、校验、动态字段 | 支撑部门级应用 |
| 案例管理 | 长流程、多角色、多状态案件处理 | 适用于金融、政务、保险等复杂流程 |
| RPA 集成 | 跨系统自动操作、重复任务自动化 | 扩展低代码自动化边界 |

低代码/无代码的强适配场景被反复归纳为流程和工作流自动化，例如 RPA、审批路由、业务流程管理、行政自动化、HR 工具、现场服务管理、报价创建、仪表盘和聊天机器人等（[CDP.com, 2026](https://cdp.com/articles/low-code-no-code-development/)）。

### 1.4 API、连接器与企业系统集成

低代码平台若只能生成孤立小应用，其企业价值会非常有限。因此，**连接器、API 集成、数据源适配和身份集成**是企业级低代码的关键基础。2021年前后的企业低代码市场已经把 ERP、CRM、数据库、身份提供商、SaaS 系统和 REST/SOAP API 集成作为重要能力。

企业集成能力通常包括：

- 预置连接器：Salesforce、SAP、Microsoft Dynamics、ServiceNow、Oracle、SQL 数据库等；
- REST/SOAP/OData/GraphQL API 调用；
- 自定义连接器；
- 身份认证集成：SSO、SAML、OAuth、OIDC；
- 数据权限、字段级访问控制和审计日志；
- 与云平台、容器或私有部署环境结合。

后续企业集成研究也指出，现代企业环境往往面对大量数据源和混合云架构，平台需要预置连接器、API-first、事件驱动集成、治理、安全和可扩展性，否则会形成新的数据孤岛（[Informatica, 2026](https://www.informatica.com/resources/articles/enterprise-data-integration-strategy.html)）。

### 1.5 云原生运行时、DevOps、ALM 与治理

截至2021年底，低代码已经不再只是“快速做页面”的工具。企业级低代码平台开始强调**应用生命周期管理（ALM）**、环境分离、版本控制、发布审批、回滚、监控、审计、角色权限、数据防泄露策略和合规控制。Salesforce 在2021年被 Gartner 评为企业低代码应用平台领导者时，其公告提到 Salesforce Platform 的 Dynamic Interactions in App Builder、Einstein Automate、MuleSoft Composer、Salesforce Functions、CLI Unification 和 DevOps Center 等能力，反映出低代码平台正在把声明式开发、自动化、集成、函数扩展和 DevOps 管理结合起来（[Salesforce, 2021](https://www.salesforce.com/news/stories/salesforce-recognized-gartner-magic-quadrant-for-enterprise-low-code-application-platforms/)）。

治理也是核心技术基础之一。低代码如果缺少治理，就容易重现 shadow IT、技术债、碎片化数据模型、安全漏洞和合规风险；如果治理到位，则可以把业务部门创新纳入 IT 可见、可控、可审计的体系内（[Ecosire, 2026](https://ecosire.com/blog/low-code-no-code-enterprise-2026)）。

### 1.6 小结分析：低代码的技术本质是“抽象层 + 集成层 + 治理层”

我的判断是：截至2021年底，低代码的技术本质并不是简单的“拖拽式编程”，而是三层能力的组合：

1. **抽象层**：用模型、元数据、可视化 DSL 和组件替代重复编码；
2. **集成层**：通过连接器、API、身份认证和数据访问把应用嵌入企业系统；
3. **治理层**：通过权限、审计、环境、ALM 和安全策略让快速开发可以进入生产环境。

这三层能力之间存在明显递进关系。只有抽象层的平台适合原型和轻量内部工具；同时具备集成层的平台才能处理 CRM、ERP、客户门户和跨系统流程；进一步具备治理层的平台，才可能承载企业级、受监管或业务关键应用。

## 二、主要应用领域

### 2.1 流程与工作流自动化

截至2021年底，低代码最成熟、最普遍的应用领域是**业务流程和工作流应用**。Forrester 相关研究被后续资料转述为：低代码的主要应用领域包括业务流程/工作流应用、Web 和移动前端、客户面对型应用，并预计会扩展到更广泛的应用和技术栈重构（[CDP.com, 2026](https://cdp.com/articles/low-code-no-code-development/)）。

常见场景包括：

- 审批流：采购审批、费用报销、合同审批；
- 行政自动化：资产申请、会议室预订、员工请求；
- HR 流程：入职、离职、请假、绩效流程；
- 财务流程：发票处理、费用审批、预算申请；
- IT 服务：工单、权限申请、设备申请；
- RPA 自动化：跨系统录入、批量处理、重复事务自动化。

这些场景共同特点是：流程明确、表单驱动、多角色参与、规则较稳定、业务部门最了解细节，因此非常适合低代码和公民开发者参与。

### 2.2 Web、移动前端与多体验应用

低代码平台也常用于快速构建 Web 应用、移动应用和多体验前端。Gartner 在2021年前后已经将低代码应用平台视为快速增长市场，低代码应用平台是低代码技术收入的最大细分市场之一，2021年预计达到约58亿美元（[Cyclr, 2021](https://cyclr.com/blog/low-code-is-revolutionising-the-software-industry)）。

在移动和前端场景中，低代码平台常见用途包括：

- 内部移动审批应用；
- 现场服务应用；
- 销售拜访记录；
- 客户服务门户；
- 数据录入和采集应用；
- 跨设备仪表盘。

这类应用往往不一定要求极复杂算法，但要求快速上线、多端适配、与后台数据连接、权限控制和易维护。

### 2.3 内部工具、仪表盘与数据采集应用

企业内部工具是低代码的重要阵地。业务团队经常需要临时或半正式系统来替代 Excel、邮件、共享文档和手工流程，例如：

- 部门仪表盘；
- 管理后台；
- 数据采集表单；
- 库存或资产跟踪；
- 运营看板；
- 销售漏斗管理；
- 简单 CRM 或项目管理工具。

2026年的公民开发研究虽然不应直接当作2021证据，但其总结与2021前的趋势一致：成熟的企业低代码/公民开发不再相信“任何人可以构建任何东西”，而是把业务用户聚焦在范围清晰的部门工作流、数据收集、仪表盘、管理面板和内部工具上（[Ecosire, 2026](https://ecosire.com/blog/low-code-no-code-enterprise-2026)）。

### 2.4 CRM、ERP 和核心系统周边扩展

低代码平台经常被用于扩展 CRM、ERP、ITSM、HRMS 等核心系统，而不是替换它们。例如 Salesforce Platform 用于 CRM 生态内的对象、流程和页面扩展；Microsoft Power Platform 与 Microsoft 365、Dynamics、Dataverse、Teams、Azure 紧密结合；ServiceNow App Engine 用于 Now Platform 上的服务管理与工作流应用；Oracle APEX 用于 Oracle 数据库环境中的数据密集型应用。

不过，凡是连接 ERP 或 CRM 的低代码应用，都应被视为更高风险或业务关键应用，因为它们与核心系统交换数据，需要更强的数据安全、所有权、QA、ALM 和合规控制（[Columbus Global, 2026](https://www.columbusglobal.com/partners/microsoft-dynamics-365-partner/power-platform-partner/governance-the-missing-but-critical-link-in-no-code-low-code-development/)）。

### 2.5 风险分层下的应用适配

低代码的应用适配不能只看“能不能做”，还要看风险等级。较可靠的治理建议是按风险分层：

| 风险等级 | 典型应用 | 治理要求 |
|---|---|---|
| 低风险 | 团队协作、生日提醒、简单任务跟踪 | 轻量审批、基础权限 |
| 中风险 | 含部分敏感数据的部门应用、内部报表 | 架构审查、数据访问控制 |
| 高风险 | 客户数据、财务数据、CRM/ERP、受监管数据 | 全面安全评估、审计、ALM、合规审查 |

这种分层方法能够在速度和控制之间取得平衡：低风险应用不应被过度审批拖慢，高风险应用则不能因为“低代码”而绕过企业级软件治理（[Kissflow, 2026](https://kissflow.com/no-code/no-code-enterprise-tools-governance-security-scaling/)）。

### 2.6 小结分析：低代码最适合“流程清晰、集成适中、变化频繁”的业务应用

我的结论是：截至2021年底，低代码的最佳应用区域不是操作系统、底层基础设施、高频交易系统或复杂算法平台，而是**流程清晰、数据结构相对稳定、需要快速迭代、业务部门深度参与**的应用。  
低代码最有价值的地方在于“填补企业 IT 长尾需求”：大量部门级、流程型、数据采集型、核心系统周边扩展型应用，传统开发成本过高、排期过长，但完全放任业务部门自行采购 SaaS 又会造成影子 IT。低代码平台正好位于两者之间。

## 三、主流平台与工具

### 3.1 2021年前后的市场规模与分类

低代码市场在2021年前已经进入高速增长期。Forrester 曾预测低代码开发平台市场从2018年的43.5亿美元增长到2019年的65.3亿美元、2020年的101.1亿美元、2021年的151.7亿美元，并在2022年达到212.4亿美元（[Forrester, n.d.](https://cdn2.hubspot.net/hubfs/2096695/Vendor%20Landscape_A%20Fork%20In%20The%20Road%20For%20Low_Code%20Development%20Platforms.pdf?submissionGuid=83c10178-9f4a-4980-8d27-2f20a0fcdaa1)）。Gartner 也预测全球低代码开发技术收入在2021年增长23%，其中低代码应用平台仍是最大细分领域，2021年约达58亿美元（[Cyclr, 2021](https://cyclr.com/blog/low-code-is-revolutionising-the-software-industry)）。

市场并不是单一类别。2019—2021年前后的低代码技术市场包括低代码应用平台、智能 BPM 套件、多体验开发平台、RPA、公民自动化/开发平台以及其他低代码技术（[Cyclr, 2021](https://cyclr.com/blog/low-code-is-revolutionising-the-software-industry)）。

### 3.2 主流平台清单与定位

| 类别 | 代表平台/工具 | 典型定位 | 2021前后意义 |
|---|---|---|---|
| 企业级全栈低代码 | OutSystems、Mendix | 面向专业开发者和 IT 团队，支持复杂应用、移动端、集成和企业治理 | 代表“专业开发者提效”路线 |
| 流程/BPM/案例管理 | Appian、Pega、Bizagi、K2、Nintex | 工作流、BPM、案例管理、审批、RPA/流程自动化 | 代表低代码与流程管理融合 |
| SaaS/生态型平台 | Salesforce Platform、ServiceNow App Engine、Microsoft Power Apps | 在既有企业 SaaS/云生态中扩展应用 | 依托 CRM、ITSM、Microsoft 365/Dynamics 等系统 |
| 数据库/数据应用构建 | Oracle APEX、Quickbase、FileMaker、Zoho Creator、Kintone | 数据密集型内部应用、表单、报表、轻量业务系统 | 继承数据库应用构建器传统 |
| 自动化/RPA 邻近工具 | UiPath、Automation Anywhere、Power Automate | 机器人流程自动化、桌面/系统间自动操作 | 与低代码共同服务业务自动化 |
| 轻量无代码/公民开发 | Airtable、Bubble、Glide、Betty Blocks 等 | 部门级应用、表格型应用、门户、原型 | 更偏业务用户和无代码场景 |

Forrester 在早期低代码供应商研究中已经把 Salesforce、Appian、Bizagi、K2、Kintone、Mendix、Nintex、OutSystems、Quick Base、ServiceNow、Zoho、FileMaker、Magic Software 等纳入观察范围，说明市场边界从一开始就横跨 BPM、工作流、SaaS 定制、数据库应用和 PaaS（[Forrester, n.d.](https://cdn2.hubspot.net/hubfs/2096695/Vendor%20Landscape_A%20Fork%20In%20The%20Road%20For%20Low_Code%20Development%20Platforms.pdf?submissionGuid=83c10178-9f4a-4980-8d27-2f20a0fcdaa1)）。

### 3.3 两条路线：专业开发者低代码与业务开发者低代码

Forrester 曾把市场描述为正在分化为两条路径：一类面向应用开发与交付专业人员，另一类面向业务开发者。这是理解低代码市场的关键分界：前者强调复杂应用、架构、扩展、DevOps、性能和治理；后者强调业务用户可用性、模板、表单、审批、无代码体验和 IT 监督（[Forrester, n.d.](https://cdn2.hubspot.net/hubfs/2096695/Vendor%20Landscape_A%20Fork%20In%20The%20Road%20For%20Low_Code%20Development%20Platforms.pdf?submissionGuid=83c10178-9f4a-4980-8d27-2f20a0fcdaa1)）。

这一区分到2021年底已经非常重要。OutSystems、Mendix 更偏向专业开发者提效；Power Apps、Quickbase、Kintone、Zoho Creator 等更容易进入业务部门和公民开发场景；Appian、Pega 则在流程和案例管理中形成较强专业领域优势。

### 3.4 平台选择与企业技术栈绑定

平台选择往往不是纯功能比较，而是与企业既有技术栈高度相关。较合理的选择逻辑包括：Microsoft-heavy 组织倾向 Power Platform；Oracle 数据库用户可考虑 Oracle APEX；CRM 中心化组织使用 Salesforce Platform；流程自动化可考虑 Appian 或 Pega；服务管理标准化组织适合 ServiceNow；数据密集型 Oracle 场景适合 APEX（[SHIFT ASIA, 2026](https://shiftasia.com/column/top-low-code-no-code-platforms-transforming-enterprise-development/)）。

### 3.5 小结分析：2021年底的低代码市场已是“多源汇流”的复合市场

我的判断是：截至2021年底，低代码不是一个从单一技术路线生长出来的市场，而是至少五条路线汇合：

1. BPM/工作流平台低代码化；
2. PaaS 和云平台声明式开发；
3. SaaS 生态系统扩展；
4. 数据库应用构建器现代化；
5. RPA 和自动化工具与应用构建融合。

这解释了为什么“低代码平台”之间差异巨大：Mendix/OutSystems 与 Quickbase、Salesforce、ServiceNow、Appian、Oracle APEX 解决的问题并不完全相同。真正的选型不应问“哪个低代码最好”，而应问“我的企业栈、风险等级、应用类型、开发者画像和治理要求是什么”。

## 四、公认的业务优势

### 4.1 更快交付与缩短上市时间

低代码最常被认可的优势是**开发速度提升**。通过视觉建模、模板、预置连接器和自动部署，企业可以把许多应用从数月交付缩短为数周甚至数天。低代码/无代码常被用于快速原型、MVP、审批流程、内部工具和部门应用，因为这些场景的需求变化快，传统开发排期往往无法跟上（[SHIFT ASIA, 2026](https://shiftasia.com/column/top-low-code-no-code-platforms-transforming-enterprise-development/)）。

### 4.2 缓解 IT 积压与开发者短缺

2021年前后，企业数字化需求快速增长，而专业开发者资源有限。低代码被认为可以把一部分开发工作转移给业务分析师、流程负责人、运营团队和所谓“公民开发者”，从而让专业开发者集中处理复杂系统、架构、集成和高风险应用。Gartner 在2021年相关材料中被 Salesforce 引述称，到2025年，70%的企业新应用将使用低代码或无代码技术，2020年这一比例低于25%（[Salesforce, 2021](https://www.salesforce.com/news/stories/salesforce-recognized-gartner-magic-quadrant-for-enterprise-low-code-application-platforms/)）。

### 4.3 改善业务与 IT 协作

低代码的另一个优势是改善业务和 IT 之间的沟通。业务人员可以直接参与模型、表单、流程和原型设计，减少“需求文档—开发—返工”的循环。专业开发者则可以在必要时扩展逻辑、编写自定义代码、设计架构和控制发布。这种模式后来常被称为 fusion teams，即业务和 IT 混合团队。

### 4.4 降低部分应用开发成本

对于标准化流程应用、内部工具和中低复杂度应用，低代码可减少重复编码、降低初始开发成本，并通过平台化部署减少基础设施管理负担。不过，这一优势有边界：随着用户数、应用数、连接器、环境、流量和企业功能增加，低代码许可成本可能快速上升。因此，低代码降低的是**特定类型应用的交付摩擦和边际开发成本**，不必然降低所有软件项目总成本。

### 4.5 更强的标准化、治理与安全可见性

如果低代码平台由 IT 正式引入并配置治理规则，企业可以把过去散落在 Excel、Access、宏、个人 SaaS 账号和影子 IT 中的应用纳入统一平台。治理框架应定义谁可以构建、谁可以发布、哪些数据源和 API 可以连接、如何执行合规和审计，以及何时必须升级到 IT 审查（[Caspio, 2026](https://www.caspio.com/blog/citizen-developer-governance-framework/)）。

不过，治理是低代码成败分水岭。无治理的公民开发可能造成 shadow IT、技术债、碎片化数据模型、安全漏洞和合规风险；治理良好的项目则可以显著降低影子 IT，并让业务创新进入受控轨道（[Ecosire, 2026](https://ecosire.com/blog/low-code-no-code-enterprise-2026)）。

### 4.6 更容易实现系统集成与流程自动化

低代码平台通过连接器、API 和流程编排能力，把多个系统中的任务串联起来。它不是简单替代 ERP、CRM 或 HRMS，而是常作为这些系统之上的流程层、体验层或自动化层。后续低代码自动化研究也指出，现代平台常作为系统记录层周围的执行层，通过预置连接器和 API 编排跨 ERP、CRM、HRMS 等系统的流程，而不强迫企业替换底层系统（[Kissflow, 2026](https://kissflow.com/low-code/why-low-code-automation/)）。

### 4.7 关键限制：低代码是补充，不是传统开发替代品

低代码/无代码不适合所有项目。需要深度集成、复杂数据治理、任务关键系统、大规模高并发、复杂算法、底层基础设施控制或特殊运行环境的企业应用，通常仍需要专业开发。低代码更合理的定位是传统开发的补充，而不是替代（[CDP.com, 2026](https://cdp.com/articles/low-code-no-code-development/)）。

### 4.8 小结分析：低代码真正的业务价值来自“受治理的速度”

我的明确观点是：**低代码最有说服力的业务优势不是“任何人都能开发应用”，而是“在治理边界内，让正确的人更快地交付正确复杂度的应用”。**  
如果企业把低代码理解为绕过 IT 的工具，它会放大风险；如果把低代码理解为 IT 提供平台、业务贡献领域知识、双方通过治理模型共同交付应用，它就能显著缓解 IT 积压、提升流程数字化速度，并减少非正式工具造成的数据孤岛。到2021年底，低代码已经从“快速开发工具”演化为“企业应用交付模式”的组成部分。

---

## 结论

截至2021年底，低代码开发已经形成一个高速增长、边界宽泛、技术来源复杂的企业软件市场。它的核心技术基础包括视觉建模、模型驱动、元数据运行时、组件化、流程引擎、连接器、API 集成、云部署、DevOps/ALM、安全与治理。它的主要应用集中在流程自动化、工作流、内部工具、Web/移动前端、客户门户、CRM/ERP 周边扩展和数据采集应用。主流平台则沿着专业开发者提效、业务开发者赋能、流程/BPM、生态扩展、数据库应用构建和 RPA 自动化等路线分化。

从市场与技术趋势看，低代码的演进方向并不是单纯降低代码量，而是把企业软件开发从“代码中心”扩展到“模型、组件、流程、集成和治理中心”。这也是为什么低代码在2021年前后受到企业关注：它解决的不是一个编程语言问题，而是企业数字化需求增长速度超过 IT 交付能力的问题。  
因此，最合理的采用策略是：用低代码处理流程清晰、变化频繁、业务知识密集、风险可分层管理的应用；对连接核心系统、处理敏感数据或承担关键业务的应用，则必须纳入正式架构、安全、质量和生命周期管理。

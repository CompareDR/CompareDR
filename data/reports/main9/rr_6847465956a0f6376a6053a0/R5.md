# Technical Proposal: A Distributed Audio Streaming System with Live Chat

**Document type:** Engineering technical proposal
**Intended audience:** Experienced software developers (streaming, backend, client, and SRE disciplines)
**Status:** For review — v1.0
**Date:** 2026-09-19

---

## Executive Summary

This proposal specifies the architecture, technology stack, and delivery plan for a **distributed live audio streaming platform** — live audio "rooms" or channels with one-to-many broadcast, audience interaction through a **real-time chat subsystem**, and first-class clients for **both browsers and mobile devices**. The system is designed for a growth-stage company: it must run economically at a few thousand concurrent listeners on day one, yet scale along well-understood paths to **100,000+ concurrent listeners per region** without a ground-up rewrite.

The core architectural decision is a **hybrid media plane**: **WebRTC (via an SFU cluster) for speakers and interactive participants**, delivering 0.2–0.5 s glass-to-glass latency among on-stage users, and **Low-Latency HLS (LL-HLS) over CMAF through a commodity CDN for the listening audience**, delivering 2–5 s latency at CDN economics. This hybrid is the default pattern for modern live platforms in 2026 because it reconciles the two things neither protocol does alone: WebRTC is sub-second but caps out around 500–800 viewers per SFU node, while LL-HLS scales to 100K+ viewers on ordinary HTTP/2 CDNs but is one-way ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)). The chat subsystem is an independent real-time plane built on a **stateless WebSocket gateway tier**, a **Valkey (Redis-compatible) pub/sub fast path**, a **Kafka durable log**, and **ScyllaDB for message history** — the same shapes that Slack and Discord validated at far larger scales than we will ever need ([Slack Engineering via systemdesign.academy](https://www.systemdesign.academy/interview/design-slack), [Discord Engineering via handbook.academy](https://hld.handbook.academy/curriculum/case-studies/channel-scale-chat/)).

Everything runs on **Kubernetes** with event-driven autoscaling (KEDA), full OpenTelemetry instrumentation, and GitOps delivery. Audio is extraordinarily cheap to move compared with video — a 96 kbps stereo Opus stream is roughly **0.05 GB per listener-hour**, about 45× less than a 1080p video stream — so the dominant costs at our scale are CDN egress (small in absolute terms), SFU compute, and engineering time, which is why we bias toward managed primitives and open-source building blocks rather than bespoke media infrastructure ([Fora Soft](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)).

## 1. Goals, Scope, and Non-Goals

### 1.1 Product goals

The product delivers **live audio rooms**: a small set of speakers (typically 1–10) broadcast to an audience of listeners who can react, raise a hand, and participate in a **per-room live chat**. Rooms can be recorded and republished as on-demand episodes. Listeners join from a **browser (desktop and mobile web, delivered as a PWA)** and from **native iOS and Android applications**. Chat is first-class, not an afterthought: it carries messages, emoji reactions, hand-raise requests, moderation events, and presence, and it is the primary mechanism by which a 2–5-second-latency broadcast still *feels* live and interactive.

The system boundary covers ingestion of speaker audio, media processing, distribution, the chat real-time plane, persistence, client SDKs/apps, and operational infrastructure. It deliberately excludes payment processing beyond a stub interface, content licensing workflows, and recommendation/feed ranking, which are follow-on initiatives. Where the boundary is fuzzy — for example, recording pipelines that feed a future on-demand catalog — we design the interface now (HLS segment tap + object storage) and defer the product surface.

### 1.2 Scale targets and SLOs

Capacity planning targets three tiers, with the architecture honest about what changes between them. The design point for the initial build is **Tier B**; Tier A must work on day one without Tier B's infrastructure fully provisioned, and Tier C must be reachable by configuration and horizontal scaling, not re-architecture. Latency and cost figures cited throughout come from published production measurements of the same protocols we adopt ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls), [Callaba](https://callaba.io/stream-live)).

These tiers are intentionally asymmetric in what they stress. Listener scale stresses CDN egress and packager throughput — both cheap, linear, and well-understood. Speaker count per room stresses the SFU mesh and the mixer, which is why it is capped conservatively; a 25-speaker stage is already at the edge of what is listenable for humans, independent of what the SFU can forward. Chat message rate stresses the fan-out plane, and it correlates super-linearly with *room heat* rather than raw listener count — 100,000 quiet listeners generate less chat load than 5,000 listeners at a controversial moment — which is why §4.4's degradation ladder is tied to per-room throughput, not global concurrency. Availability targets exclude the CDN itself, which we treat as a dependency with its own SLA and dual-homing strategy (§7.2).

| Dimension | Tier A — Launch | Tier B — Growth (design point) | Tier C — Large events |
|---|---|---|---|
| Concurrent listeners (global) | 1,000–10,000 | 10,000–100,000 | 100,000–1,000,000 |
| Concurrent rooms | 100 | 2,000 | 20,000 |
| Speakers per room | ≤ 10 | ≤ 16 | ≤ 25 (stage) |
| Chat messages/sec (global) | 500 | 10,000 | 100,000+ |
| Audio latency (speaker→listener) | 2–5 s (LL-HLS) | 2–5 s | 2–5 s |
| Speaker↔speaker latency | < 500 ms (WebRTC SFU) | < 300 ms p50 | < 300 ms p50 |
| Chat delivery latency (p99) | < 300 ms | < 500 ms | < 1 s |
| Availability | 99.9% | 99.95% | 99.95% (cellular isolation) |

### 1.3 Non-functional requirements

Beyond raw scale, the system is held to explicit quality bars. **Audio quality** targets "transparent for speech and near-transparent for music" at standard tier — Opus at 64–96 kbps stereo on the WebRTC path and AAC at 96–128 kbps on the LL-HLS path, consistent with published listening-test results showing Opus outperforming AAC below 128 kbps and both reaching near-transparency at 128 kbps stereo ([Ant Media](https://antmedia.io/best-audio-codec/), [LiveAPI](https://liveapi.com/blog/opus-codec/)). **Resilience** requires that no single availability-zone failure degrades more than one region's capacity, that chat reconnects recover missed history via sequence cursors rather than full reloads, and that listener playback degrades gracefully from LL-HLS to classic HLS under client or CDN duress. **Operability** requires every service to emit OpenTelemetry traces and RED/USE metrics, and every user-visible SLO to have a dashboard and an alert. **Cost discipline** requires per-listener-hour cost reporting as a first-class metric, because in streaming the unit economics, not the monthly total, are what the business must manage ([Fora Soft](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)).

Two softer requirements shape the design as much as the numeric ones. **Evolvability**: every external dependency (SFU vendor, CDN, moderation provider) sits behind an internal interface, because the medium-term certainties in this space are protocol churn — Media-over-QUIC and WebTransport are still stabilizing in browsers and CDNs and plausibly matter by 2027–2028 — and pricing renegotiation, not any specific vendor's roadmap ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)). **Operability by a medium-sized team**: the entire system must be runnable on-call by the team that builds it, which is a hard constraint against self-operating exotic stateful systems and a strong argument for managed offerings wherever pricing allows — every "boring" choice below is downstream of this sentence.

## 2. System Architecture Overview

### 2.1 The two-plane design

The fundamental structural choice is to run **two largely independent real-time planes** that share an edge, a control plane, and observability: a **media plane** (audio ingest → processing → distribution) and a **chat plane** (WebSocket gateways → fan-out → persistence). This separation is not merely organizational tidiness. The two planes have different failure modes (media pipelines fail in seconds of silence; chat fails in delayed messages), different scaling axes (media scales with listener egress and speaker count; chat scales with connection count and message rate), and different change cadences (media infra changes slowly and cautiously; chat features change weekly). Decoupling them lets each scale, deploy, and fail independently — the same reason Discord separates its gateway tier from its storage tier and Slack separates Channel Servers from the webapp monolith ([Sujeet Jaiswal](https://sujeet.pro/articles/slack-distributed-architecture)).

The **control plane** is a set of ordinary stateless HTTP/gRPC services — rooms, users, auth, roles, billing hooks — behind an API gateway. It is the only component that touches both planes, issuing SFU join tokens, resolving room membership, and enforcing roles (speaker/listener/moderator). All durable low-write-volume relational data lives in **PostgreSQL**; high-volume append-only data (chat history, analytics events) lives in **ScyllaDB** and **Kafka** respectively; hot ephemeral state (presence, sessions, rate limits) lives in **Valkey**, the Linux Foundation's BSD-licensed Redis fork ([GetStream](https://getstream.io/blog/tools-discord-app/)).

### 2.2 Request/data flow walkthrough

A speaker's audio takes the following path: the client captures microphone audio (Web Audio API in the browser, AVAudioEngine/AudioRecord on mobile), encodes **Opus** (mandatory in WebRTC), and publishes it via WebRTC to the nearest **SFU node**. The SFU forwards speaker streams to the other speakers (sub-second stage mix) and to a **mixer/transcoder service**, which produces a single program feed, transcodes Opus→AAC-LC, and generates an ABR ladder. The **packager/origin** writes **CMAF fMP4** partial segments (~250 ms parts, ~1 s segments) and LL-HLS playlists, which the **CDN** caches and serves to listeners at 2–5 s latency ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls), [Callaba](https://callaba.io/stream-live)). Recordings are tapped at the packager into object storage for post-show VOD republishing.

A chat message takes a shorter path: the client sends it over its persistent **WebSocket** to a gateway node; the gateway validates the session and forwards to the **chat service**, which runs moderation and rate-limit checks, writes the message to **ScyllaDB** (partitioned by `(channel_id, bucket)`, clustered by snowflake ID — Discord's proven schema ([Discord Engineering via handbook.academy](https://hld.handbook.academy/curriculum/case-studies/channel-scale-chat/))), publishes to **Kafka** for durable async processing, and publishes to the room's **Valkey pub/sub channel** for immediate fan-out. Every gateway node subscribed to that room channel pushes the message to its local WebSocket connections. Redis-class pub/sub delivers sub-millisecond fan-out latency, while Kafka absorbs durability, replay, and analytics duties that pub/sub explicitly does not provide ([QueryStack](https://www.querystack.tech/post/designing-a-real-time-chat-system-from-websockets-to-fan-out-at-scale-2a7831)).

## 3. Media Plane: Streaming Protocols and Codecs

### 3.1 Why the hybrid WebRTC + LL-HLS pattern

Protocol selection for live audio is a latency-versus-scale-versus-cost three-way trade, and no single protocol wins all three corners. **WebRTC** is the only widely deployed protocol that achieves true sub-second glass-to-glass latency — production measurements consistently land at **0.2–0.5 s** — because it runs over UDP with DTLS-SRTP, maintains jitter buffers tuned for interactivity, and supports native two-way media ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls), [Ant Media](https://antmedia.io/samples/webrtc-vs-hls/)). Its ceiling is structural: a single SFU node forwards every participant's stream to every other viewer, saturating around **500–800 viewers per node**, and SFU traffic cannot be cached by a CDN, so cost scales with compute and egress on machines we operate ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)). **Classic HLS** inverts the profile: 15–30 s latency but effectively unlimited scale on commodity CDNs. **LL-HLS** closes most of the latency gap — **2–5 s** via partial segments (`EXT-X-PART`) and blocking playlist reloads — while retaining full CDN cacheability, automatic fallback to classic HLS, and universal client reach ([Cloudinary](https://cloudinary.com/guides/live-streaming-video/low-latency-hls-ll-hls-cmaf-and-webrtc-which-is-best)).

Our product needs both corners: speakers must converse naturally (sub-second), and rooms must grow to tens of thousands of listeners (CDN scale). The **hybrid pattern** — WebRTC within the stage, LL-HLS to the audience — is the documented 2026 default for exactly this product shape, and it bounds our SFU fleet to *speakers*, not *listeners*: a room with 10 speakers and 50,000 listeners costs 10 SFU legs plus CDN egress, rather than 50,000 SFU legs ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)). The 2–5 s listener latency is acceptable because interaction flows through the chat plane (sub-second) rather than through the audio path; chat reactions arriving while the listener hears the corresponding moment is a solved synchronization problem (we timestamp chat events against the program clock and let clients align display).

| Protocol | Glass-to-glass latency | Scale ceiling | Two-way | Cost per 1,000 viewer-hours | Fit for us |
|---|---|---|---|---|---|
| WebRTC (SFU) | 0.2–0.5 s | ~500–800 viewers/node, cascade beyond | Native | ~$60 self-hosted ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)) | **Speaker stage only** |
| LL-HLS (CMAF) | 2–5 s | 100K+ via CDN | No (add WS channel) | $6–190 depending on CDN ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)) | **Listener distribution (chosen)** |
| LL-DASH | 1–3 s | 100K+ via CDN | No | CDN egress | Alternative; weaker Safari story |
| Classic HLS | 15–30 s | 1M+ via CDN | No | CDN egress | Fallback tier for weak clients |
| MPEG-DASH | 6–20 s | 100K+ via CDN | No | CDN egress | Not chosen; no advantage over HLS for audio |

### 3.2 SFU selection: LiveKit

For the SFU tier we adopt **LiveKit**: an open-source (Apache 2.0), Go-based SFU built on Pion, shipping as a single binary with built-in room management, Protocol Buffers-over-WebSocket signaling, official client SDKs for web, iOS, Android, Flutter, React Native and Unity, and ingress/egress pipelines for recording and rebroadcast ([Trembit](https://trembit.com/blog/livekit-vs-mediasoup/), [Tumarm](https://tumarm.com/blog/webrtc-media-server-comparison)). LiveKit's clustering model — stateless SFU nodes coordinated through Redis — scales horizontally by adding nodes without configuration changes, and its maintained SDKs eliminate an entire class of client work we would otherwise own ([Tumarm](https://tumarm.com/blog/webrtc-media-server-comparison)). As of January 2026 the project is exceptionally well-funded and widely deployed, including in OpenAI's voice stack, which materially de-risks the dependency ([Vaagmodo](https://vaagmodo.com/insights/kurento-vs-livekit-vs-mediasoup-2026/)).

The serious alternatives were **mediasoup** and **Janus**. mediasoup is a superb low-level SFU library (Node.js control, C++ workers pinned per core) that gives router-level control over codec policy and bandwidth estimation — but it ships no signaling, no room management, and no client SDKs, meaning we would build and operate LiveKit's entire platform layer ourselves; that is a poor trade for a medium-sized team whose differentiation is the product, not media plumbing ([Fora Soft SFU comparison](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion), [Trembit](https://trembit.com/blog/livekit-vs-mediasoup/)). Janus is a C-based general-purpose WebRTC gateway whose strengths are SIP/PBX bridging and plugin-based media handling — irrelevant to our product and heavier to operate ([Tumarm](https://tumarm.com/blog/webrtc-media-server-comparison)). We keep the mediasoup escape hatch open by confining all LiveKit-specific code behind an internal `MediaGateway` interface.

| Candidate | Type | Language | What it ships | Why / why not |
|---|---|---|---|---|
| **LiveKit** ✅ | SFU platform | Go (Pion) | Rooms, auth tokens, SDKs (web/iOS/Android/RN/Flutter), egress/ingress, Redis-coordinated clustering | Fastest path to production; batteries included; strong backing ([Trembit](https://trembit.com/blog/livekit-vs-mediasoup/)) |
| mediasoup | SFU library | Node.js + C++ workers | Transport primitives only (routers/producers/consumers) | Maximum control, but we would own signaling, rooms, SDKs ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)) |
| Janus | WebRTC gateway | C | Plugin architecture (VideoRoom, SIP, AudioBridge) | Best for SIP/PBX bridging — not our product ([Tumarm](https://tumarm.com/blog/webrtc-media-server-comparison)) |
| Managed RTC (Agora/Daily/LiveKit Cloud) | SaaS | — | Everything, usage-billed | ~$0.003–0.004 per participant-minute overtakes CDN/self-host economics well before 10K concurrent; viable fallback if SFU ops burden proves too high ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)) |

### 3.3 Audio codec strategy: Opus inside, AAC outside

We standardize on **Opus** for the interactive/WebRTC path — it is the mandatory-to-implement WebRTC audio codec, royalty-free, and uniquely spans 6–510 kbps with 5–26.5 ms algorithmic delay, built-in packet-loss concealment, and optional in-band FEC for weak networks ([LiveAPI](https://liveapi.com/blog/opus-codec/), [Cloudinary](https://cloudinary.com/guides/video-formats/opus-codec/)). Speaker uplinks run Opus at 32–64 kbps mono/stereo; published listening tests show Opus speech at 32 kbps sounding clearer than AAC at the same rate, and 64 kbps stereo Opus competitive with 96 kbps AAC ([Cloudinary](https://cloudinary.com/guides/video-formats/opus-codec/)). On the distribution path we transcode once to **AAC-LC** for the LL-HLS ladder, because AAC remains the codec with universal hardware decode across iOS, Android, browsers, and smart devices — protocol and device reach, not fidelity, decide the codec above 128 kbps ([LiveAPI](https://liveapi.com/blog/opus-codec/), [Ant Media](https://antmedia.io/best-audio-codec/)).

The ABR ladder for listener distribution is deliberately shallow — audio needs far fewer rungs than video: **HE-AAC v2 at 32 kbps** (congested cellular), **AAC-LC at 64 kbps**, **AAC-LC at 96 kbps (default)**, and **AAC-LC at 128 kbps (high tier)**. HE-AAC v2 earns its place because it is specifically engineered for the low-bitrate range where AAC-LC produces audible artifacts, and it is the standard choice of internet radio for bandwidth-constrained listeners ([Ant Media](https://antmedia.io/best-audio-codec/)). All encoding runs at 48 kHz, the standard sample rate for streaming and the native rate of both Opus and modern production pipelines ([Ant Media](https://antmedia.io/best-audio-codec/)).

### 3.4 Ingest, packaging, and recording

There are three ingest classes. **Speaker ingest** is WebRTC/WHIP into the SFU cluster — WHIP (WebRTC-HTTP Ingestion Protocol) gives us a standard, firewall-friendly way to accept non-client sources such as hardware encoders or studio software ([Callaba](https://callaba.io/stream-live)). **External contribution** (a remote radio studio feeding a show) uses **SRT**, whose ARQ-based loss recovery over UDP is the industry standard for first-mile contribution over imperfect networks ([Callaba](https://callaba.io/stream-live)). RTMP remains supported only as a legacy compatibility input, transmuxed at the edge. Downstream, the packager writes CMAF fMP4 with ~1 s segments and ~250 ms partial segments and a 3–6 s playlist window, which yields 2–6 s end-to-end latency in published reference architectures ([Callaba](https://callaba.io/stream-live)).

**Recording** is a tap, not a pipeline: the packager writes every segment to object storage (S3-compatible) as it serves the live playlist, and a post-show job re-manifests the segment sequence as a VOD HLS asset behind the CDN. This avoids the classic mistake of bolting recording on late — listed among the most common production errors in media-server selection postmortems ([LinkedIn/media-server analysis](https://www.linkedin.com/pulse/janus-vs-mediasoup-livekit-choosing-right-webrtc-media-xhk7c)) — and costs nothing extra in the live path. LL-HLS also gives us recording-compatible, replayable segments for free compared with tapping and re-encoding at the SFU ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)).

## 4. Chat Plane: Real-Time Messaging at Scale

### 4.1 Transport: WebSocket, and why not SSE or MQTT

The client transport is **WebSocket** (WSS). It is bidirectional (messages, reactions, typing, moderation events flow both ways on one connection), persistent (no per-message connection setup), and universally supported in browsers and mobile stacks. Server-Sent Events was evaluated and rejected: SSE is server→client only, forcing a separate HTTP path for sends, and its browser connection-per-domain limits and proxy buffering behaviors are recurring production irritants. MQTT was evaluated for mobile battery efficiency but rejected as the primary transport because browser support requires WebSocket-wrapped MQTT anyway, and its broker semantics (topics, QoS) duplicate what our gateway + pub/sub layer provides; we keep the option of an MQTT edge for future low-power IoT clients. The interview-grade literature is unambiguous that WebSocket is the correct default for chat at any scale from thousands to tens of millions of connections ([QueryStack](https://www.querystack.tech/post/designing-a-real-time-chat-system-from-websockets-to-fan-out-at-scale-2a7831), [Mockingly](https://mockingly.ai/questions/real-time-messaging-system-design-at-microsoft)).

Connection lifecycle engineering matters more than protocol choice. Clients heart-beat every 30–45 s; gateways enforce idle timeouts; reconnects use exponential backoff with jitter to avoid thundering herds after network blips or gateway deploys — a 10 M-connection fleet generates ~220K heartbeats/sec at a 45 s interval, which is precisely why heartbeats must be cheap frames, not application messages ([Algoroq](https://www.algoroq.io/interview-questions/websocket/)). On reconnect, the client presents its last received **sequence ID** and the gateway streams the delta from Valkey Streams rather than forcing a full room-state reload — the difference between a graceful blip and a halftime thundering-herd outage ([Softjourn](https://softjourn.com/insights/real-time-data-synchronization-for-live-sports)).

### 4.2 Gateway tier and fan-out: Valkey fast path, Kafka durable path

The gateway tier is a fleet of **stateless Go services** behind a Layer-4 load balancer (L4, not L7, because L7 adds per-frame overhead that is unacceptable at high connection counts ([Algoroq](https://www.algoroq.io/interview-questions/websocket/))). Each node terminates 50–100K WebSocket connections — a single modern server handles hundreds of thousands of connections, so the real constraint is per-connection message bandwidth, not socket count ([god.ad](https://god.ad/learn/how-websockets-work)). Gateways hold only connection state and per-room subscription sets; all routing intelligence lives behind them. Scaling is event-driven via **KEDA** on Prometheus metrics (connections-per-pod and messages-per-second), because CPU/memory autoscaling badly misreads WebSocket load — a pod can be CPU-idle while holding 80K connections ([OneUptime](https://oneuptime.com/blog/post/2026-02-09-auto-scaling-websocket-keda/view)).

Fan-out uses the two-lane pattern validated across the industry. The **fast lane** is Valkey pub/sub: when a message is accepted, the chat service publishes to `room:{id}`, and only gateway nodes with local subscribers to that room receive it (gateways subscribe/unsubscribe room channels as their local membership changes). Redis-class pub/sub gives sub-millisecond fan-out latency but at-most-once delivery and no persistence ([QueryStack](https://www.querystack.tech/post/designing-a-real-time-chat-system-from-websockets-to-fan-out-at-scale-2a7831)). The **durable lane** is Kafka: every accepted message is appended to a room-partitioned topic, feeding persistence writers, analytics, search indexing, and replay, at a modest latency cost (typically 5–15 ms vs sub-ms for Redis pub/sub ([QueryStack](https://www.querystack.tech/post/designing-a-real-time-chat-system-from-websockets-to-fan-out-at-scale-2a7831))). This dual-write is what lets a gateway crash lose zero acknowledged messages: the client never sees an ACK until the Kafka append succeeds.

| Component | Technology | Role | Why this choice |
|---|---|---|---|
| Gateway | Go (goroutines) WebSocket service | Terminate 50–100K conns/node, validate sessions, local fan-out | Event-driven runtimes (Go/Rust/Elixir) are the standard for 100K-conn nodes ([Algoroq](https://www.algoroq.io/interview-questions/websocket/)); team fluency picks Go |
| Load balancing | L4 (NLB/HAProxy) + consistent hashing on user ID | Even connection distribution; reconnect affinity | L7 per-frame overhead unacceptable at scale ([Algoroq](https://www.algoroq.io/interview-questions/websocket/)) |
| Fast fan-out | Valkey pub/sub + Streams (delta recovery) | Sub-ms room fan-out; reconnect catch-up | Sub-ms latency; Streams fix at-most-once gaps ([Softjourn](https://softjourn.com/insights/real-time-data-synchronization-for-live-sports)) |
| Durable log | Kafka | Persistence feed, replay, analytics, moderation audit | Durable, replayable, millions of msg/s; latency acceptable off the hot path ([QueryStack](https://www.querystack.tech/post/designing-a-real-time-chat-system-from-websockets-to-fan-out-at-scale-2a7831)) |

| Presence | Valkey (TTL keys, scoped subscriptions) | Online state, typing indicators | Heartbeat TTL pattern; UI-scoped subscriptions cut traffic 5× ([handbook.academy](https://hld.handbook.academy/curriculum/case-studies/channel-scale-chat/)) |
| Autoscaling | KEDA on Prometheus connection/message metrics | Right-size gateway fleet | Resource-based autoscaling misreads long-lived connections ([OneUptime](https://oneuptime.com/blog/post/2026-02-09-auto-scaling-websocket-keda/view)) |

### 4.3 Message storage: a deliberately boring start on a proven path

For Tier A/B we persist chat history in **ScyllaDB** rather than growing into it. The reasoning follows Discord's documented evolution: they started on MongoDB, hit a wall at ~100 M messages, moved to Cassandra in 2017 (12 nodes, billions of messages), and by 2022 had 177 nodes with trillions of messages suffering JVM GC pauses, expensive compactions, and p99 read latencies of 40–125 ms; migrating to ScyllaDB (C++ shard-per-core, Cassandra-compatible) cut read p99 to ~15 ms, write p99 to ~5 ms, and node count from 177 to 72 ([ByteByteGo](https://bytebytego.com/guides/how-discord-stores-trillions-of-messages/), [handbook.academy](https://hld.handbook.academy/curriculum/prerequisites/data-structures-for-systems/)). Our message volume will be a rounding error compared to theirs, so the honest question is "why not PostgreSQL?" — and the answer is that PostgreSQL *is* our MVP answer for room chat history (time-partitioned tables handle tens of millions of messages comfortably ([GetStream](https://getstream.io/blog/tools-discord-app/))), with ScyllaDB introduced in Tier B before hot rooms make Postgres write amplification painful. The schema is fixed from day one to be ScyllaDB-compatible — partition key `(channel_id, bucket)` with ~10-day buckets, clustering by snowflake ID descending — so the migration is a data move, not a data-model change.

**Snowflake IDs** (time-ordered, collision-free 64-bit IDs generated at the edge) are adopted for all messages and events. They make pagination a trivial `WHERE message_id < :cursor` range scan, give clients cheap deduplication (`client_msg_id` plus snowflake for at-least-once sends), and keep ordering well-defined across regions without a coordinator ([Mockingly](https://mockingly.ai/questions/real-time-messaging-system-design-at-microsoft)). History retention is 30 days hot (Valkey Streams/ScyllaDB) with archival to S3 in Parquet for compliance and analytics.

### 4.4 Presence, reactions, and hot-room behavior

Presence is the classic N² trap: a naive implementation in a 10K-member room with 1K status changes/sec produces 10M presence events/sec — quadratic in membership ([handbook.academy](https://hld.handbook.academy/curriculum/case-studies/channel-scale-chat/)). We adopt Slack's countermeasures: clients subscribe to presence **only for users visible in the UI** (which cut Slack's delivered presence traffic ~5×), presence deltas are batched and debounced in ~5 s windows, and login storms are absorbed by reconnect jitter and a "eventually correct within 30 s" SLO ([handbook.academy](https://hld.handbook.academy/curriculum/case-studies/channel-scale-chat/)). Emoji reactions are not chat messages — they are aggregated counters with per-user toggles, fanned out as compact deltas (`+37 🎉` over 2 s) rather than 37 individual events, which keeps the biggest rooms' reaction storms off the message path entirely.

Hot rooms get a dedicated degradation ladder, applied automatically by the chat service as room throughput climbs: (1) reactions collapse to counters, (2) typing indicators disabled, (3) presence reduced to moderator/speaker scope, (4) non-speaker messages rate-limited per user and sampled for display, (5) read-only "broadcast chat" mode with moderator-pinned messages. Each rung sheds an order of magnitude of fan-out while preserving the features users actually notice. This ladder is the difference between a 100K-listener event degrading gracefully and a cascading gateway failure.

### 4.5 Moderation pipeline

Moderation is an **inline stage in the chat service's accept path**, not a batch afterthought. Each message passes: deterministic filters (rate limits, link policies, blocklists) → an ML toxicity classifier with per-community thresholds → an AI/context layer for ambiguous cases → human moderator tooling for edge cases. Commercial pipelines in this class automate ~99.9% of decisions and classify inline so toxic content can be blocked before other users see it ([Lasso](https://www.lassomoderation.com/features/text-moderation/toxicity-profanity-detection/)). We will start with a vendor API (this is not a differentiating competency) behind a `ModerationService` interface, with all decisions journaled to Kafka for audit and threshold tuning.

Speaker-side audio moderation (e.g., detecting policy violations in the audio itself) is explicitly out of scope for v1 but anticipated in the architecture: the mixer/transcoder already forks a program feed, so a future ASR + policy service can subscribe to that fork without touching the live path. Moderator actions (mute speaker, eject listener, slow mode) are control-plane commands propagated through the same WebSocket plane, which keeps client handling uniform — one event channel, many event types.

## 5. Client Applications

### 5.1 Web: React PWA with hls.js and the WebRTC SDK

The browser client is a **React + TypeScript PWA**. Listening playback uses **hls.js** on Chromium/Firefox (LL-HLS via MSE) and **native HLS on Safari** (Safari has native LL-HLS support since Safari 14 / iOS 14 ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls))). Speakers use the LiveKit JavaScript SDK over WebRTC; chat uses a single WebSocket with a small protocol of JSON frames (with a protobuf option reserved for hot rooms). The PWA shell gives installability, offline shell caching, and shareable room URLs, which materially reduces friction for casual listeners who will never install an app.

Two web-specific engineering notes deserve emphasis. First, **service workers do not reliably provide background audio on mobile browsers**, so mobile web is a *viewing* experience, not a *pocket listening* experience — that is a platform constraint, and it is the strongest product argument for the native apps ([Quora streaming guide](https://www.quora.com/How-can-I-create-a-simple-app-to-play-a-radio-streaming)). Second, chat/audio clock alignment is implemented client-side: chat events carry program-date-time stamps from the packager, and the web player maps them onto the HLS playback timeline so reactions land on the moment the listener is hearing.

### 5.2 Mobile: React Native shell over native playback and RTC stacks

The mobile apps use **React Native** for UI and product surfaces, over native media stacks where the platform demands it: **AVPlayer/AVFoundation on iOS** (native LL-HLS, low overhead, correct background-audio integration via `AVAudioSession` and `MPRemoteCommandCenter`) and **Media3 ExoPlayer on Android** (the standard library for HLS/DASH with ABR, foreground-service playback, and MediaSession wiring ([Appzoro](https://appzoro.com/blog/live-streaming-app-development-complete-guide))). The pragmatic glue is **react-native-track-player**, which runs playback in a headless service — an Android foreground service backed by ExoPlayer and an iOS background audio session backed by AVPlayer — wires lock-screen/Control Center controls, and streams HLS/DASH out of the box ([Taha Koçal](https://tahakocal.dev/blog/react-native-background-audio/)). Speakers on mobile use the LiveKit iOS/Android SDKs, which handle echo cancellation, audio-route changes, and network handoffs that we never want to own.

React Native over Flutter over fully-native is a judgment call, and we are explicit about it: our product surfaces (room lists, chat, profiles) are standard mobile UI where RN parity is strong, the team already ships React, and one codebase across iOS/Android is worth real velocity for a medium-sized company. The carve-outs are deliberate — playback and RTC run on the platform-native engines under thin bridges — which is exactly where RN apps get into trouble when teams try to do media in JavaScript. If the RN experiment degrades (startup time, scroll perf in 100K-message rooms), the escape hatch is rewriting the shell natively while keeping every media and networking component, because those are already native.

## 6. Data Platform

### 6.1 Polyglot persistence with explicit ownership

Each store has one job and one owning service; nothing is shared across services. **PostgreSQL** owns relational control-plane data — users, rooms, memberships, roles, billing stubs — because it is the boring, correct default for ACID relational data and the team's deepest expertise; Slack's lesson was to add middleware (Vitess) around the database you know rather than chase a rewrite ([Sujeet Jaiswal](https://sujeet.pro/articles/slack-distributed-architecture)). **ScyllaDB** (Tier B onward) owns append-only chat history per §4.3. **Valkey** owns everything ephemeral: sessions, presence, rate-limit counters, pub/sub, and reconnect streams. **S3-compatible object storage** owns recordings and VOD, fronted by the CDN. **Kafka** is the system of record for the event stream (messages, moderation decisions, QoE beacons) feeding analytics and search.

The one deliberate redundancy is message durability (Kafka append + ScyllaDB write), which buys independent recovery: if the history store loses writes, we replay from Kafka; if Kafka retention expires, history is already served from ScyllaDB. Analytics events (join/leave, QoE beacons, chat volume) flow exclusively through Kafka into a columnar store (ClickHouse) — never through the transactional path — so product analytics can never degrade the live planes.

### 6.2 Data-service pattern and hot-key defense

Ahead of the databases we place a thin **data-service layer** (owned per domain) whose job is request coalescing and cache-aside: when 10,000 clients open the same hot room at show start, one database query is issued, not 10,000. Discord introduced exactly this Rust data-services tier in front of ScyllaDB to eliminate hot-partition thundering herds, and it is the single most transferable pattern from their migration for a system like ours where room opens are synchronized events ([penchef](https://www.penchef.com/software-engineering/scaling-mvp-database-0-to-100k-users), [handbook.academy](https://hld.handbook.academy/curriculum/case-studies/chat-system/)). Room metadata, speaker lists, and pinned messages are cached in Valkey with explicit version-keyed invalidation (a `room_version` counter bumped on change, so invalidation is O(1) and lazy ([handbook.academy](https://hld.handbook.academy/curriculum/case-studies/channel-scale-chat/))).

Edge caching extends this idea to the client bootstrap path. Slack's Flannel — an application-level edge cache keyed by consistent hashing per workspace — cut client boot payloads 7–44× and absorbed 4M concurrent connections' worth of startup queries ([systemdesign.academy](https://www.systemdesign.academy/interview/design-slack)). We do not build a Flannel on day one; we design the bootstrap API (room manifest = playback URL + chat resume cursor + role + feature flags) so that one can be inserted transparently when startup load demands it.

## 7. Infrastructure and Operations

### 7.1 Kubernetes, multi-AZ, and progressive cellular isolation

All stateless services (API, gateways, SFU control, chat service, data services) run on **Kubernetes** across three availability zones, with GitOps (Argo CD) for delivery and Terraform for the cloud substrate. Stateful systems (PostgreSQL, ScyllaDB, Kafka, Valkey) run on managed offerings where available or as operators on dedicated node pools where not — we are explicit that self-operating Kafka or ScyllaDB on Kubernetes is a tax a medium-sized company should pay only when managed pricing forces it. Autoscaling is metric-driven via **KEDA** everywhere, since connection-count and message-rate signals, not CPU, express real load for gateways and SFUs alike ([OneUptime](https://oneuptime.com/blog/post/2026-02-09-auto-scaling-websocket-keda/view)).

Blast-radius control is progressive. Tier A/B uses multi-AZ within one primary region plus a warm-standby second region for the control plane and chat history (ScyllaDB's multi-DC replication makes this cheap); the media plane fails over by re-homing rooms (listeners rejoin a fresh SFU + packager path; a few seconds of silence, acceptable at this tier). Tier C adopts **cellular architecture** — full-stack duplication per cell with 1%-granularity traffic draining, the pattern Slack used to reach 5-minute failover at a 99.99% SLA ([Sujeet Jaiswal](https://sujeet.pro/articles/slack-distributed-architecture)). We also institutionalize chaos drills for stateful nodes early — Slack's "Disasterpiece Theater" needed three attempts to correctly partition 25% of their Channel Servers, which is a warning that consistent-hash reassignment under load never works the first time you try it ([Sujeet Jaiswal](https://sujeet.pro/articles/slack-distributed-architecture)).

### 7.2 CDN strategy

LL-HLS distribution runs on a **commercial CDN** — never origin-direct. Provider economics span roughly **$0.085/GB at hyperscaler pay-as-you-go rates down to $0.01–0.02/GB on budget CDNs or negotiated commits** ([Fora Soft](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249), [Fora Soft scale guide](https://forasoft.medium.com/how-to-scale-real-time-video-streaming-to-1-million-viewers-in-2026-webrtc-cdn-and-moq-c9da6ca6b5da)). At Tier B we front one primary CDN and keep a second warm via DNS-based steering, because CDN outages are a when, not an if; the packager writes to both origins. Operational details that matter: pre-warm the CDN ~30 s before scheduled shows (cold edge caches cost 200–500 ms per first request), set short playlist cache TTLs so edges re-fetch at the live edge, and tune the ABR ladder against measured audience bandwidth rather than copying a generic video ladder ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)).

The build-your-own-CDN question deserves an explicit answer even at our scale, because the video-streaming literature makes the 67–300× markup between cloud egress and wholesale IP transit sound tempting ([GetStream](https://getstream.io/blog/live-streaming-infrastructure-costs/)). For audio it is a trap: at Tier B our entire egress bill is a few thousand dollars a month, so a self-built edge would never recover its engineering and peering costs, and Twitch-scale economics (own CDN cutting an estimated $2.4B retail bill to ~$650M ([GetStream](https://getstream.io/blog/live-streaming-infrastructure-costs/))) only become relevant several orders of magnitude beyond our Tier C. We do, however, keep the origin architecture CDN-agnostic — the packager pushes to a generic HTTP origin — so a future multi-CDN or owned-edge strategy is a configuration change, not a rebuild.

### 7.3 Observability and QoE

Every service emits **OpenTelemetry** traces and metrics into Prometheus/Grafana, with logs in Loki. The media plane adds domain-specific telemetry: per-room SFU forwarding latency (target p90 < 200 ms ([Callaba](https://callaba.io/stream-live))), packager playlist staleness, CDN cache-hit ratio and origin offload, and client-side QoE beacons (time-to-first-audio, rebuffer ratio, ABR rung distribution, live-edge drift). The chat plane tracks connect success rate, message accept→delivery p50/p99, fan-out lag, and reconnect storm rate. SLOs from §1.2 are wired to multi-window burn-rate alerts.

Client QoE beacons deserve emphasis because they are the only ground truth for audio quality: server-side health cannot see a listener rebuffering on hotel Wi-Fi. Beacons batch-report every 30 s through the analytics path (Kafka → ClickHouse), and every incident review must include both server and client views — the two routinely disagree, and both are right.

## 8. Security, Privacy, and Compliance

Transport security is table stakes and enumerated for completeness: TLS 1.3 everywhere on HTTP/WS paths; **DTLS-SRTP is native to WebRTC** media ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)); LL-HLS segments served over TLS with **signed URLs/cookies** for paywalled rooms (a standard CDN feature at every provider we evaluated ([Fora Soft](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249))). Authentication is OIDC with short-lived JWTs; SFU join requires a per-room, per-participant token minted by the control plane (LiveKit's native model), so a leaked room link does not grant stage access; chat send requires a session bound to the WS connection with server-side re-checks on role change. Rate limiting is layered: edge (per-IP), gateway (per-connection frame rate), and service (per-user action budgets in Valkey).

Privacy posture: chat history and recordings are stored data and fall under GDPR-style deletion workflows — a user deletion request triggers tombstoning in PostgreSQL, ScyllaDB row deletion, and S3 object expiry, journaled through Kafka so downstream analytics are scrubbed as well. End-to-end encryption of room audio is explicitly **out of scope** (it conflicts with server-side mixing, recording, and moderation, and no comparable live-audio platform offers it), but private-room media is encrypted in transit and at rest, and the access model (token-minted stage access) is documented so a future E2EE stage for small rooms remains possible. DDoS posture: CDN-level absorption for the distribution path, L4 anycast + rate shaping for gateways, and a documented "degraded read-only" mode when chat is under attack but audio must survive.

## 9. Capacity Plan and Cost Model

### 9.1 The math that makes audio cheap

Audio's economics are dominated by one fact: **96 kbps stereo ≈ 0.043 GB per listener-hour** (×1.15 ABR uplift ≈ **0.05 GB**), versus ~2.25 GB/hour for 1080p video ([GetStream](https://getstream.io/blog/live-streaming-infrastructure-costs/)). At the Tier B design point — 10,000 concurrent listeners averaging 3 h/day — that is ~45 TB/month of CDN egress: **~$3.8K/month at hyperscaler PAYG rates, ~$900 at negotiated-commit rates, ~$450 on a budget CDN** (chart below; prices per ([Fora Soft](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249))). SFU compute is modest because only speakers touch SFUs: 2,000 concurrent rooms × ~4 active speakers ≈ 8,000 SFU legs ≈ 15–25 c5-class nodes with headroom at 500–800 legs/node ([Fora Soft](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls)). The gateway fleet at 100K concurrent chat connections is ~4–6 pods at 50–100K connections each ([god.ad](https://god.ad/learn/how-websockets-work), [Algoroq](https://www.algoroq.io/interview-questions/websocket/)). Total infrastructure at Tier B lands in the **$6–12K/month** range depending on CDN commitments — with CDN egress and SFU compute as the only lines that move the needle, exactly as the four-line cost model predicts ([Fora Soft](https://www.forasoft.com/blog/article/how-to-estimate-the-server-cost-for-a-video-platform-249)).

Monthly CDN egress cost versus concurrent listeners at three price tiers

The strategic implication is that **engineering time, not bandwidth, is our scarce resource** — the opposite of a video platform. This justifies every "buy" or "adopt-batteries-included-open-source" decision in this proposal (LiveKit over mediasoup, vendor moderation over in-house ML, managed Kafka/ScyllaDB over self-operated) and it is why the cost model is reported per listener-hour on dashboards rather than as a monthly lump.

### 9.2 Scaling path and known inflection points

The path from Tier A to Tier C is a sequence of named, pre-planned inflections rather than organic growth: (1) **~1K concurrent rooms**: introduce ScyllaDB for chat history and the data-service coalescing layer; (2) **~10K concurrent listeners/room spikes**: enable the hot-room degradation ladder and CDN dual-homing; (3) **~100K concurrent connections**: split Valkey pub/sub into sharded channels per gateway cluster (the "1M channels subscribed on every server" problem has a standard sharding answer ([OneUptime](https://oneuptime.com/blog/post/2026-03-31-redis-how-to-design-a-real-time-chat-system-using/view))); (4) **multi-region audience**: active-active control plane, regional SFU/packager clusters, cellular isolation per §7.1. Each inflection is triggered by a measured SLO threshold, not a calendar date.

Two properties make this sequence cheap to execute when the time comes. First, every inflection is **additive**: nothing in the Tier A architecture is thrown away at Tier B or C — ScyllaDB slides in under a schema that was fixed on day one, the data-service layer inserts in front of stores that already have single owning services, and CDN dual-homing uses the CDN-agnostic origin the packager already writes to. Second, each step has a **rehearsal story**: because triggers are SLO-based, we can force every transition early in staging by injecting synthetic load that trips the threshold, and validate the migration runbook before it is ever load-bearing in production. This is deliberately modeled on the discipline of Slack's chaos program rather than on heroic mid-incident improvisation ([Sujeet Jaiswal](https://sujeet.pro/articles/slack-distributed-architecture)).

## 10. Delivery Plan and Risks

### 10.1 Phased delivery

**Phase 1 (months 1–3) — Walking skeleton.** One region; LiveKit SFU cluster; mixer → packager → CDN for LL-HLS; web listener client (hls.js); WebSocket gateway with Valkey fan-out; chat persisted in PostgreSQL; OIDC auth; Prometheus/Grafana baseline. The goal of this phase is not feature breadth but an end-to-end media and chat path under real network conditions, because every later phase compounds on the correctness of these two planes. Exit criteria: 100-concurrent-listener load test passing, speaker-to-listener latency ≤ 5 s, chat accept→delivery p99 ≤ 500 ms, and a recorded show successfully republished as VOD.

**Phase 2 (months 4–6) — Production launch (Tier A).** iOS and Android apps with native playback engines and background audio; the Kafka durable lane and the moderation pipeline; KEDA-based autoscaling for gateways and SFUs; the hot-room degradation ladder; signed-URL room access; and the full SLO dashboard set from §1.2. This phase is where the system becomes a product rather than a demo, and it is deliberately front-loaded with the features that are expensive to retrofit — recording, moderation, and observability — because media-server postmortems consistently cite "adding recording too late" and "ignoring observability" as top production failures ([LinkedIn/media-server analysis](https://www.linkedin.com/pulse/janus-vs-mediasoup-livekit-choosing-right-webrtc-media-xhk7c)). Exit criteria: load test at 10K concurrent listeners with the degradation ladder verified by forced trip, and a two-week shadow run with real rooms.

**Phase 3 (months 7–10) — Growth hardening (Tier B).** ScyllaDB cutover under the fixed schema; the data-service coalescing layer; dual-CDN steering; warm-standby second region for control plane and chat history; the chaos drill program; and cost-per-listener-hour reporting wired into engineering review. Each phase is independently shippable and leaves the system fully operable if priorities change — there is no phase whose abandonment strands half-built infrastructure.

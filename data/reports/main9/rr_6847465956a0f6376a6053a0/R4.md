# Distributed Audio Streaming Platform: Technical Proposal

This proposal defines a one-to-many live-audio platform with an integrated live-chat room, delivered to browsers and native iOS/Android clients. It is scoped for a medium-sized engineering organization (roughly 20–80 engineers) launching in a single region with conservative concurrency targets. The design makes a small number of explicit, near-irreversible choices, defers features that do not invalidate the core loop, and treats every capacity, latency, and cost figure below as a planning target to validate under load rather than a measured result.

## Stack at a glance

| Layer | Choice | One-line justification |
|---|---|---|
| Ingest | WHIP (RFC 9725) primary; RTMP legacy fallback | Standardized HTTP-based WebRTC ingest; one encoder build targets any WHIP server by changing URL and token |
| Media routing | LiveKit self-hosted (Apache 2.0); mediasoup fallback | Cross-platform SDKs, egress/recording built in, horizontally scalable selective forwarding |
| Delivery | WebRTC primary; LL-HLS/CMAF fallback; classic HLS compatibility floor | Sub-second interactive tier plus CDN-friendly large-audience tier |
| Codec | Opus live; AAC-LC only at HLS/VOD egress | Low delay, built-in resilience, mandatory in WebRTC, royalty-free |
| Chat transport | WSS/WebSocket primary; HTTP for non-realtime; SSE for read-only streams | Full-duplex persistent connection that reuses standard HTTP infrastructure |
| Chat backend | Phoenix Channels + Presence self-hosted | BEAM process per connection, native PubSub and presence |
| Event backbone | NATS JetStream for realtime routing; Kafka for analytics/audit | Subject-routed fanout avoids partition skew; partitioned log provides retention and replay |
| Stores | PostgreSQL, ScyllaDB/Cassandra, Redis, S3/GCS | Polyglot persistence matched to access pattern |
| Identity | OIDC + PKCE; JWT capability tokens; HMAC TURN credentials | Three token classes with different lifetimes and trust boundaries |
| Clients | React/TypeScript browser; native Kotlin/Swift media path; RN/Flutter optional | Background audio and audio-session correctness require platform APIs |
| TURN | coturn with short-lived HMAC credentials | Open source; bounds the blast radius of relay-abuse |
| Observability | Prometheus/Grafana + OpenTelemetry/Tempo + Sentry | Error-budget burn alerting; media/chat correlation by room |

## 1. Scope, Product Model, and Launch Targets

The product is a live room with a media plane and a chat plane sharing one room/session identity. It is explicitly **not** a peer-to-peer mesh and **not** a video product at launch. A Selective Forwarding Unit (SFU) — a media relay that forwards one upstream stream to many downstream subscribers without decoding — inverts the peer-to-peer scaling problem: each publisher uploads exactly once regardless of audience size ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)), whereas a six-participant mesh already manages 30 streams and bandwidth grows with the square of participant count ([Ant Media](https://antmedia.io/webrtc-scalability/)).

### Roles

| Role | Publishes audio | Sends chat | Moderates | Notes |
|---|---|---|---|---|
| Broadcaster/host | Yes | Yes | Yes | Creates/owns the room; invites co-hosts; ends session |
| Co-host/guest | Yes, when on stage | Yes | Optional | Invited speaker; can be promoted from audience |
| Listener | No | If permitted | No | Primary audience; read-only media consumer |
| Chatter | No | Yes | No | Audience member who primarily chats |
| Moderator | Only if also a speaker | Yes | Yes | Mutes/removes speakers, deletes messages, slow mode; produces audit trail |
| Producer | No (off-air) | Internal only | Yes | Manages room flow, queue, metadata; control plane only |
| Admin | No | No | Org-level | Manages tenants, roles, audit; not a per-room participant |

### Comparable products and what they bound

| Product | Verified figure | What it tells us |
|---|---|---|
| Discord Stage Channels | Audio-only audience up to 10,000; video/screen-share 50/150/300 by tier ([FAQ](https://support.discord.com/hc/en-us/articles/1500005513722-Stage-Channels-FAQ); [blog](https://discord.com/blog/introducing-video-screen-share-text-chat-support-for-stage-channels)) | Audio-only rooms support roughly 10–100× larger audiences than video rooms |
| X Spaces | >1 million concurrent listeners on one Space ([Guardian](https://www.theguardian.com/technology/article/2024/aug/12/elon-musk-donald-trump-x-interview)) | Single audio rooms can exceed 1M concurrent at record scale; platform-level, not a product commitment |
| Clubhouse | >10M weekly active a year after launch; declined 21% in three weeks in early 2021 ([Wikipedia](https://en.m.wikipedia.org/wiki/Clubhouse_(app)); [TechCrunch](https://techcrunch.com/2021/02/18/report-social-audio-app-clubhouse-has-topped-8-million-global-downloads/)) | Social audio is hit-driven and retention-challenged |
| Twitch | 2.378M average concurrent viewers platform-wide in 2024 ([TwitchTracker](https://twitchtracker.com/statistics)) | Live platforms operate at millions of concurrent viewers; per-stream concurrency is heavily skewed |
| YouTube Live | 8M peak concurrent for Chandrayaan-3 landing ([Forbes India](https://www.forbesindia.com/article/explainers/top-10-most-viewed-youtube-live-streams-world/87775/1)) | Large one-to-many events reach millions at non-interactive latency |
| Spotify Live | Shut down April 2023 after acquiring Locker Room ([Billboard](https://www.billboard.com/pro/spotify-shuts-down-clubhouse-live-audio-competitor/)) | Standalone social-audio apps struggled; incumbents folded live audio into existing apps |

These are platform-level or record figures, not targets. The launch target is deliberately conservative by comparison: **5,000 listeners/room, 500 chatters/room, 1–3 publishers/room, 50 live rooms, 50k DAU, single-region launch**. The 50k-listener/room and 1M-connection figures are upper-bound stress scenarios used only to test headroom.

### Deferred features and preserved seams

| Feature | Defer to | Why it can wait | Seam preserved |
|---|---|---|---|
| Video rooms | Post-launch | Audio-only supports 10–100× larger audiences | Media pipeline must accept a video track later |
| Multi-region | Phase 3 | Cross-region chat ordering and media affinity are complex | Room/session identity and event schema must be region-routable |
| Recording / VOD | Phase 4 | The live loop is the core | Recording/egress tap on the media pipeline |
| Advanced moderation (ML classifiers, raid defense) | Phase 4 | Block/mute/slow-mode cover launch | Moderation event schema and audit log |
| Reactions | Phase 2+ | Chat works without them; high-frequency ephemeral events | Ephemeral state layer |
| Speaker diarization / transcription | Phase 4+ | Requires server-side audio processing | Side subscriber on the audio track |
| Monetization / marketplace | Out of scope | No launch dependency | Billing/metering service boundary |

No authoritative primary benchmark for the listener-to-chatter ratio was verifiable, so the chat design must serve both **broadcast fan-out** (few chatters, thousands of listeners) and **dense many-to-many** (small rooms) without re-architecting. The switch threshold is a tuning parameter to measure, not a fixed constant.

For a medium-sized company the consequences are direct: launch targets are Phase 0 assumptions, not commitments; the irreversible choices (room data model, media server, chat backend) are captured as architecture decision records (ADRs); reversible choices (web framework, region strategy, UI toolkit) are not over-invested in.

## 2. Non-Functional Requirements and SLOs

The SLO set is tiered, not uniform. Every number below is a target to validate with the measurement method shown.

### Latency tiers

ITU-T G.114 defines one-way transmission limits for echo-controlled connections: 0–150 ms is acceptable for most applications, 150–400 ms is acceptable with awareness of impact, and above 400 ms is unacceptable for general network planning; it also warns that some highly interactive applications degrade even below 150 ms ([ITU-T G.114](https://www.itu.int/rec/T-REC-G.114-200305-I/en)). Glass-to-glass WebRTC is typically 0.2–0.5 s because of capture, encoding, jitter buffering, and decode ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)).

| Tier | Target (validate) | Protocol path | Architecture consequence | Cost consequence |
|---|---|---|---|---|
| Interactive | p95 < 500 ms glass-to-glass; ≤150 ms one-way anchor | WebRTC → SFU → listener | Route-don't-transcode; TURN pools; per-room SFU placement | Egress scales linearly with listeners; TURN relay adds 10–80 ms when 15–20% of sessions fall back ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)) |
| Low-latency | p95 < 3 s | WebRTC or LL-HLS | WebRTC keeps linear egress; LL-HLS moves fanout to CDN | LL-HLS is cheaper at large audiences but adds playlist/segment overhead |
| Near-real-time | p95 < 10 s | LL-HLS (2–8 s) or classic HLS (8–30 s) | CDN cache-friendly; chat runs ahead of audio | Lowest egress cost per listener at very large scale |

LL-HLS is documented at 2–8 s versus 24–30 s for traditional HLS ([Cloudinary](https://cloudinary.com/guides/live-streaming-video/low-latency-hls-ll-hls-cmaf-and-webrtc-which-is-best)); Ant Media reports 3–5 s for LL-HLS and 8–10 s for standard HLS ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)). The tier is chosen per room mode and per client capability, not globally.

### SLO table

| Metric | Target (validate) | Measurement | Notes |
|---|---|---|---|
| Interactive audio latency | p95 < 500 ms glass-to-glass; ≤150 ms one-way | k6/Locust + `RTCPeerConnection.getStats()` | G.114 anchor; multi-speaker rooms |
| Low-latency tier | p95 < 3 s | same | WebRTC or LL-HLS |
| Near-real-time tier | p95 < 10 s | HLS segment/playlist timing | LL-HLS or classic HLS |
| Chat delivery | p50 < 200 ms; p95 < 500 ms; p99 < 1 s | End-to-end trace: send timestamp → receive timestamp | Per-room fanout; p99 binds during bursts |
| Concurrent listeners/room | 5,000 | SFU load test | Launch cap |
| Concurrent chatters/room | 500 | k6/Locust | Launch cap |
| Concurrent publishers | 1–3/room; ≤150 across 50 rooms | SFU load test | Host/co-host/guest |
| Total concurrent listeners | 250k if all rooms at cap; 50k DAU assumption | Capacity model | Stress upper bound, out of launch scope |
| Chat ordering | Per-room monotonic sequence; total order per room | Replay + dedupe test | Sequence assigned at ingestion |
| Chat durability | 90-day retention; persist before fanout ack | Durability test | Hot Redis, warm PostgreSQL, cold object storage |
| Availability | 99.9% monthly (43.8 min error budget) | SLO dashboard + burn-rate alerts | 99.99% optional for paid tiers |
| Audio quality | MOS/POLQA ≥ 4.0; −23 LUFS ±1 LU; true peak ≤ −1 dBTP | POLQA + EBU R128 meter | Opus 48 kHz |
| Startup time | < 2 s to first audio | Client instrumentation | Signaling + ICE + first frame |
| Cellular data | ≤ 28.8 MB/h at 64 kbps; ≤ 14.4 MB/h at 32 kbps | Client telemetry | 64 kbps = 8 kB/s |
| Regional reach | 2-region target validated; single-region MVP | Geo-DNS/anycast test | Multi-region is Phase 3 |

**Chat–audio alignment.** In the interactive tier both planes are sub-second, so a chat message lands near the audio moment it references. In the LL-HLS tier chat is ahead of audio by 2–8 s; the system must either delay chat display by the media offset or accept the skew. The offset calibration is part of the client resilience design.

**Capacity uncertainty.** mediasoup documents that a single C++ worker (one CPU core) handles over ~500 consumers in mixed audio+video rooms, and a single router may be exceeded above roughly 200–300 viewers (400–600 consumers) in broadcast scenarios ([mediasoup scalability](https://mediasoup.org/documentation/v3/scalability/)). That figure is video-conferencing-centric; the audio-only ceiling must be measured. Slack runs millions of simultaneously connected WebSocket users at peak across a fleet of Envoy-terminated services ([Slack Engineering](https://slack.engineering/migrating-millions-of-concurrent-websockets-to-envoy/)), but that is a fleet-level figure, not a per-node guarantee.

**Availability and error budget.** A 99.9% monthly SLO allows 43.8 minutes of downtime; 99.99% allows 4.38 minutes. Google's SRE workbook defines an error budget as 1 minus the SLO and notes that changes are a major source of instability, representing roughly 70% of outages ([Google SRE Workbook](https://sre.google/workbook/error-budget-policy/)). The dominant failure modes to budget against are SFU node failure mid-stream, TURN pool exhaustion, chat gateway overload during a viral room, and regional loss.

**Audio quality baseline.** EBU R128 normalizes programme loudness to −23 LUFS with ±0.5 LU tolerance (±1 LU for live mixed programmes) and caps true peak at −1 dBTP, measured with the ITU-R BS.1770 algorithm ([EBU R128](https://en.wikipedia.org/wiki/EBU_R_128)). Perceptual quality uses POLQA, standardized as ITU-T P.863, which supersedes PESQ for HD-voice and music ([ITU-T P.863](https://www.itu.int/rec/T-REC-P.863)).

## 3. Reference Architecture and Service Boundaries

The platform is organized as three planes that share exactly one identifier — `room_id` (plus `session_id` for multi-episode rooms) — and nothing else:

- **Control plane (stateless services + room registry).** Authenticates participants, enforces entitlement, owns room lifecycle and signaling. No media packets and no chat messages flow through it.
- **Media plane (stateful, per room).** The SFU selectively forwards RTP without opening it; TURN relays when ICE cannot establish a direct path; egress produces recordings and HLS/CMAF output. LiveKit describes the SFU as a specialized router that forwards a copy of each publisher's track to each interested subscriber "without manipulating any underlying packets" ([LiveKit SFU internals](https://docs.livekit.io/reference/internals/livekit-sfu/)).
- **Data plane (durable, replicated).** Chat messages travel client → chat WebSocket tier → message service (assigns ID and per-room sequence) → durable queue → fanout → WebSocket delivery, with read cursors persisted and history in a wide-column store. GetStream's production reference separates exactly these concerns: edge/transport, message path, group/fanout, ephemeral state, media path, and identity ([GetStream](https://getstream.io/blog/chat-application-architecture/)).

```
CONTROL   client -> LB -> API GW -> identity -> room/session -> signaling -> SFU provisioning
MEDIA     publisher --WHIP/JSEP--> SFU --ICE/DTLS/SRTP--> TURN
                  SFU --> egress/transcode --> object storage --> CDN
DATA      client --WSS--> chat WS tier <-- fanout <-- queue <-- message service
                  presence / read state (Redis, TTL)
                  chat history (ScyllaDB/Cassandra)
CROSS     Prometheus/Grafana + OpenTelemetry traces + logs
```

### Component responsibilities

| Component | Plane | Responsibility | Stateful? | Scaling unit |
|---|---|---|---|---|
| Browser / mobile clients | Edge | Capture, encode, decode, render; WebRTC + WSS + optional HLS | Yes (local session) | Per device |
| Edge load balancer | Control/ingress | TLS termination, routing, edge DDoS | Stateless | Per region |
| API gateway | Control | Auth check, rate limit, REST/gRPC routing | Stateless | Per region |
| Identity/auth | Control | OAuth2/OIDC, token issuance and rotation | Stateless (Redis cache) | Per region |
| Room/session service | Control | Room lifecycle, roles, entitlements, region pinning | Yes (PostgreSQL) | Shard by tenant/region |
| Signaling service | Control | SDP offer/answer, WHIP control, SFU provisioning | Yes (in-memory) | Per room/node |
| Media SFU | Media | Selective RTP forwarding; simulcast/SVC; bandwidth estimation | Yes (routing table) | Per-room node pool pinned by `room_id` |
| TURN | Media | Relay for ICE candidates that cannot connect directly | Yes (allocations) | Per-region pool |
| Egress/transcoding | Media | Opus passthrough or Opus→AAC; recording; HLS/CMAF packaging | Yes (sessions) | Per-stream workers |
| Object storage | Data | Recordings, VOD, media assets | Yes (objects) | Per bucket |
| CDN | Data | LL-HLS/VOD distribution, signed URLs | Stateless cache | Per-region edge |
| Chat WebSocket tier | Data | Long-lived WSS connections, room subscription, delivery | Yes (connections) | Shard by `room_id` |
| Message service | Data | Ingest, assign ID + per-room sequence, persist | Yes (write path) | Per-room partition |
| Message queue | Data | Decouple ingestion from fanout; replay; later cross-region replication | Yes (log) | Partition by `room_id` |
| Presence service | Data | Presence, typing, read cursors, TTL; orders of magnitude more write-heavy than messages ([GetStream](https://getstream.io/blog/chat-application-architecture/)) | Yes (Redis) | Per-room key |
| Chat history store | Data | Durable per-room message log | Yes | Partition by `room_id`/time |
| Observability | Cross-cutting | Metrics, traces, logs, SLO dashboards | Yes (TSDB) | Per region + central |

### End-to-end flows

1. **Create room.** Host authenticates; room service creates a `Room` and a chat channel (1:1 default; 1:many for moderator backchannels or language splits) and issues a short-lived publish token plus playback tokens.
2. **Publish.** With WHIP (RFC 9725), the client `POST`s an SDP offer to an HTTP ingest endpoint and receives the answer ([RFC 9725](https://www.rfc-editor.org/info/rfc9725/)). ICE gathers candidates, DTLS runs over ICE, SRTP keys are extracted from DTLS ([WebRTC for the Curious](https://webrtcforthecurious.com/docs/01-what-why-and-how/)). The SFU registers tracks under `room_id`; the room emits `room.live`.
3. **Join and listen.** Listener presents a playback token; signaling returns SFU endpoint and SDP; DTLS-SRTP media flows. A listener better served by LL-HLS receives a signed CDN URL instead and bypasses the SFU; chat still runs over WSS, so the planes remain independent.
4. **Chat.** Client sends over WSS; message service ingests, assigns message ID and per-room monotonic sequence, writes to the durable queue; fanout expands the send and pushes over WebSocket. Login, history pagination, and media uploads stay on HTTP ([GetStream](https://getstream.io/blog/chat-application-architecture/)).
5. **Presence/ephemeral.** Heartbeats with TTL, typing indicators, and reactions are served from the separate in-memory ephemeral layer because their access pattern is very high write frequency and low durability.
6. **Moderation.** Mute, remove speaker, delete message, slow mode go through a privileged API, are authorized by role, recorded in an audit log, and propagated as control events.

### State, ordering, and replication boundaries

- **Control state** — room/session rows and role records live in PostgreSQL, cached in Redis. This plane is the sole source of truth for who may join what.
- **Media state** — the SFU routing table and TURN allocations are in memory; LiveKit uses Redis so clients joining a room all connect to the same node ([LiveKit SFU internals](https://docs.livekit.io/reference/internals/livekit-sfu/)). Live RTP is not replicated; a room is pinned to one region.
- **Data state** — messages are durable in the queue and wide-column store; presence, typing, and read cursors are in Redis with TTLs; recordings live in object storage behind a CDN.
- **Ordering** — chat gets a per-room total order from the sequence assigned at the message service; media has its own RTP sequence/timestamps per track and is not reordered by the SFU. Chat and audio are therefore not synchronized by a shared packet clock; replay alignment uses server timestamps and a client-side offset.

### Room lifecycle

| State | Entered by | Stored in | Next state |
|---|---|---|---|
| `created` | Host `POST /rooms` | PostgreSQL | `ready` / `canceled` |
| `ready` | Publish token issued; SFU provisions room | PostgreSQL + SFU memory | `live` |
| `live` | First subscriber connects; host on air | SFU memory + Redis presence | `ended` |
| `ended` | Host ends, or publisher disconnects (WHIP `DELETE`) | PostgreSQL; chat history finalized | `archived` |
| `archived` | Egress finalized; VOD packaged | Object storage + wide-column store | terminal |

The join key is `room_id` carried inside the capability token. Both planes resolve it independently: the media plane for SFU routing, the chat plane for consistent-hash sharding. Because the token carries role, both enforce the same entitlement policy without sharing a data store. That is the whole point: media and chat scale on different tiers, fail independently, and version independently.

### Service decomposition and gateway

Decompose into six bounded contexts, each owning its own data and exposing only an API ([microservices.io](https://microservices.io/patterns/data/database-per-service.html)):

| Service | Domain data | Store | Scaling unit | Interaction |
|---|---|---|---|---|
| Identity | Users, orgs, profiles, OAuth clients, sessions | PostgreSQL + cache | Read replicas | Sync REST/OIDC |
| Rooms | Rooms, sessions/episodes, roles, membership, region pinning | PostgreSQL | Shard by tenant/region | Sync REST + async events |
| Chat | Messages, reactions, read cursors, presence | ScyllaDB + Redis | `room_id` hash → gateway node | WebSocket + async |
| Media signaling | SDP/ICE relay state, WHIP/WHEP control, room→SFU routing | Redis (ephemeral) | Signaling node | WebSocket / WHIP |
| Recording/egress | Recording jobs, VOD manifests, egress metadata | Object storage + PostgreSQL | Job queue | Async events |
| Billing/metering | Usage events, metering records | PostgreSQL | Append-only | Async events |

Use synchronous request-response when the client needs a response now; use asynchronous events when producer and consumer must be decoupled ([GetStream](https://getstream.io/blog/chat-application-architecture/)). Cross-service invariants use sagas and materialized views rather than distributed transactions.

The gateway terminates TLS, verifies JWT/OIDC tokens, enforces coarse authorization and rate limits, routes, and composes simple reads; domain logic stays in services. Realtime protocol versioning happens at two layers: a versioned WebSocket subprotocol negotiated via `Sec-WebSocket-Protocol` ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)), and an additive, versioned payload schema described with AsyncAPI and registered in a schema registry ([AsyncAPI 3.1.0](https://www.asyncapi.com/docs/reference/specification/latest)). The server supports N and N−1 concurrently so web and mobile release independently.

## 4. Audio Pipeline

### 4.1 Capture and preprocessing

Audio quality is fixed on the producer's device, before the codec. The WebRTC audio pipeline runs a fixed cleanup chain at capture — high-pass filter, AEC3 acoustic echo cancellation, noise suppression, AGC2 — and only then encodes 20 ms Opus frames ([WebRTC Audio Pipeline Cheat Sheet](https://cdn.prod.website-files.com/64e8910adc5a63966a68acea/6a26c7a16209af6a9281fef7_6a26c79fc09b776f66d198bf_webrtc-audio-pipeline-cheatsheet.pdf)). Once audio is compressed, the per-sample information a suppressor or echo canceller needs is gone, so cleanup must run on raw samples. Two rules follow: suppression must run before encoding, never inside a WebRTC Encoded Transform; and exactly one noise suppressor may sit in the path, so the built-in one is switched off when a custom model is added ([Fora Soft](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/real-time-noise-suppression-krisp-rnnoise-deepfilternet-integration)).

| Concern | Placement | Detail |
|---|---|---|
| Echo cancellation | Built into client capture (browser APM; libwebrtc in native SDKs) | AEC3 needs the speaker reference; critical for full duplex ([Cheat Sheet](https://cdn.prod.website-files.com/64e8910adc5a63966a68acea/6a26c7a16209af6a9281fef7_6a26c79fc09b776f66d198bf_webrtc-audio-pipeline-cheatsheet.pdf)) |
| Noise suppression | Built-in default; RNNoise WASM in an `AudioWorklet` optional | Custom model runs on raw samples before Opus; disable built-in NS when used ([Fora Soft](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/real-time-noise-suppression-krisp-rnnoise-deepfilternet-integration)) |
| AGC / high-pass | Built in | Part of the fixed cleanup order |
| Server-side models | SFU, AI agent, or SIP gateway only for endpoints that cannot run their own model | Phone-in callers, central moderation ([Fora Soft](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/real-time-noise-suppression-krisp-rnnoise-deepfilternet-integration)) |

Capture surfaces differ by platform. Browser producers use `getUserMedia()` and constrain tracks with `applyConstraints()` (`echoCancellation`, `noiseSuppression`, `autoGainControl`, `sampleRate`, `channelCount`), rejecting with `OverconstrainedError` when no device can satisfy constraints ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/applyConstraints)). iOS binds to AVFoundation and `AVAudioEngine`; Android to Camera2 and `AudioRecord`. Both mobile platforms require explicit runtime permission and display a persistent indicator while capture is live ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)). Music-mode rooms must disable echo cancellation and noise suppression because they damage music ([LiveKit](https://docs.livekit.io/transport/media/advanced/)).

### 4.2 Codec selection

**Opus** — defined by [RFC 6716](https://www.rfc-editor.org/info/rfc6716) and packetized by [RFC 7587](https://www.rfc-editor.org/rfc/rfc7587) — is the primary codec for the live WebRTC path and for music-mode stereo. Three properties decide this:

- **Delay.** Opus adds as little as 5 ms algorithmic delay and 26.5 ms at the default 20 ms frame size, versus ~20–40 ms for AAC-LC ([Wowza](https://www.wowza.com/blog/opus-codec-the-audio-format-explained); [Forasoft](https://www.forasoft.com/learn/audio-for-video/articles-audio/audio-codec-comparison-table-2026)). Every millisecond counts against the 150 ms one-way anchor.
- **Built-in resilience.** In-band FEC carries a lower-bitrate copy of the previous frame, DTX sends almost nothing during silence, and PLC reconstructs audio when redundancy is absent ([bloggeek.me](https://bloggeek.me/webrtcglossary/opus/)).
- **One codec for speech and music.** SILK handles speech, CELT handles music, and recent versions select the mode automatically ([Wowza](https://www.wowza.com/blog/opus-codec-the-audio-format-explained)).

| Codec | Bitrate range | Latency | FEC/PLC | Support | License | Use |
|---|---|---|---|---|---|---|
| **Opus** | 6–510 kbps | 5 ms algorithmic; 26.5 ms at 20 ms frame | In-band FEC, PLC, DTX; DRED not yet in WebRTC | All major browsers; WebRTC mandatory | Royalty-free | Primary live path; music 96–128 kbps stereo |
| AAC-LC | 128–256 kbps sweet spot | ~20–40 ms | Transport-level only | Universal hardware decode | Via LA patent pool | LL-HLS fallback, VOD |
| HE-AAC | 24–64 kbps | ~40–130 ms | None | Most browsers | Via LA patent pool | Deferred low-bitrate fallback |
| MP3 | 128–192 kbps | ~25 ms | None | All major browsers | Royalty-free since 2017 | Legacy interchange |
| G.711/G.722 | 64 kbps narrowband / wideband | ~0.125 ms / low | None | WebRTC mandatory / limited | ITU royalty-free | Legacy telephony fallback |

Sources: [Forasoft codec comparison](https://www.forasoft.com/learn/audio-for-video/articles-audio/audio-codec-comparison-table-2026), [RFC 7587](https://www.rfc-editor.org/rfc/rfc7587), [RFC 6716](https://www.rfc-editor.org/info/rfc6716), [Wowza](https://www.wowza.com/blog/opus-codec-the-audio-format-explained), [bloggeek.me](https://bloggeek.me/webrtcglossary/opus/).

Opus outperforms AAC at low bitrates in published listening tests; AAC-LC only approaches Opus quality at roughly 1.3–2× the bitrate ([Forasoft](https://www.forasoft.com/learn/audio-for-video/articles-audio/audio-codec-comparison-table-2026); [opus-codec.org](https://opus-codec.org/comparison/)). Its decisive advantage is universal hardware decode and native HLS support — which is why it survives only as the LL-HLS fallback, not as the live codec.

**Bitrates and mobile data.** Speech defaults to mono Opus at 32–64 kbps; music uses stereo at 96–128 kbps. At 64 kbps, cellular consumption is 28.8 MB/hour; at 32 kbps, 14.4 MB/hour; at 128 kbps, 57.6 MB/hour. Enable in-band FEC by default, keep DTX on for speech rooms and off for music rooms, and evaluate application-layer redundancy (RED) only if load tests show burst-loss rates where FEC alone is insufficient. The 20 ms frame is the right default for speech; 60 ms triples framing delay and is unsuitable for interactive audio.

### 4.3 Ingest protocols

**WHIP (WebRTC-HTTP Ingestion Protocol, RFC 9725)** is the primary contribution path. It replaces vendor-specific SDP-over-WebSocket signaling with a four-verb HTTP protocol — `POST`, `DELETE`, `PATCH`, `OPTIONS` — so a single encoder build publishes to any WHIP-speaking server by changing only the URL and bearer token ([RFC 9725](https://www.rfc-editor.org/info/rfc9725/); [Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/whip-webrtc-ingest-rfc-9725)). It does not change the media stack: the offer/answer is still SDP, DTLS-SRTP is still mandatory, and congestion control is still WebRTC's.

| Protocol | Role | Standards status | Browser/mobile ingest | Recommendation |
|---|---|---|---|---|
| **WHIP** ([RFC 9725](https://www.rfc-editor.org/info/rfc9725/)) | Primary contribution | IETF Standards Track, Mar 2025 | Browser via WebRTC; native via WebRTC SDKs; Larix Broadcaster | **Primary ingest** |
| **WHEP** ([draft](https://datatracker.ietf.org/doc/draft-ietf-wish-whep/)) | Egress/playback, not ingest | Active Internet-Draft | Browser playback | Use for WebRTC playback; not yet an RFC |
| **RTMP/RTMPS** ([Trembit](https://trembit.com/blog/webrtc-vs-hls-vs-srt-vs-rtmp/)) | Legacy contribution | Adobe spec; Enhanced RTMP v1 (2025) | Encoder-side only; no browser playback | Legacy fallback |
| **SRT** ([Trembit](https://trembit.com/blog/webrtc-vs-hls-vs-srt-vs-rtmp/)) | Professional contribution | Expired IETF draft; Haivision library | Professional encoders | When a pro uplink justifies the ops cost |
| **RIST** ([VSF TR-06-4](https://static.vsf.tv/download/technical_recommendations/VSF_TR-06-4-Part-6_2024-07-22.pdf)) | Broadcast contribution | VSF TR-06-1/2/3 profiles | Broadcast gear | Defer; evaluate only for broadcast partners |
| **SIP** ([LiveKit SIP](https://github.com/livekit/sip)) | Phone caller bridge | SIP trunk + RTP | Not a browser path | Optional, only if phone-in is in scope |

Build the SDP plan model on **Unified Plan**. Chrome switched the default `sdpSemantics` to unified-plan in M72 and Plan B was removed from Chromium; the current JSEP specification is RFC 9429, which obsoletes RFC 8829 ([webrtc.org](https://webrtc.org/getting-started/unified-plan-transition-guide); [RFC 9429](https://www.rfc-editor.org/info/rfc9429/)). Any design carrying separate tracks — microphone plus music, per-speaker tracks — must assume one `m=` line per track.

NAT traversal uses ICE, STUN, and TURN. Most connections succeed with STUN; TURN relays media only when direct or server-reflexive connectivity fails (symmetric NATs, carrier-grade NAT, restrictive firewalls). Survey data cited by Ant Media puts the relay fraction at roughly 15–20%, adding 20–80 ms versus a direct path depending on relay proximity ([Ant Media](https://antmedia.io/how-to-create-webrtc-peer-to-peer-communication/)); budget relay capacity for the tail, not the mean. Deploy coturn behind the same regional topology as the SFU and secure it with short-lived HMAC REST credentials (see §8.1).

WHIP authentication is a bearer token on the session `POST`; use short-lived, room-scoped capability tokens rotated per session and bound to a publisher identity so a leaked token cannot be replayed against another room. Teardown is explicit (`DELETE`); mid-session network changes use an ICE restart via `PATCH` gated by the session `ETag`; if an ingest server or region fails, the encoder re-`POST`s to a new endpoint with exponential backoff and jitter.

### 4.4 Server-side processing, recording, and egress

On the live path the SFU should **route-and-forward**: it never decodes or re-encodes. It inspects packet headers, decides which subscribers want each packet, and forwards it untouched, keeping server CPU proportional to the number of publishers rather than listeners ([Fora Soft SFU comparison](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion); [mediasoup RTP parameters](https://mediasoup.org/documentation/v3/mediasoup/rtp-parameters-and-capabilities/)).

| Path | Operation | Server CPU | Added latency | When to use |
|---|---|---|---|---|
| Live WebRTC | Route Opus untouched | Low | None (sub-second) | Always; default |
| Live path | Transcode/mix per listener | High | Tens–hundreds of ms | Avoid; only if a live client truly cannot decode Opus |
| Egress LL-HLS | Transcode once → AAC in fMP4/CMAF | Per stream | Segment-level | Legacy/iOS fallback, very large audiences |
| Egress VOD | Transcode once → MP4/HLS | Per stream | Seconds | Archive, replay |
| Archive | Pass-through Opus in MP4/WebM/Ogg | None | None | Preserve source quality |

Transcoding is unavoidable only at the egress boundary: HLS delivery uses AAC in fragmented MP4/CMAF ([Unified Streaming](https://docs.unified-streaming.com/documentation/package/package.html)), VOD players may lack Opus, RTMP/SRT destinations expect AAC, and ABR ladders need multiple renditions. The rule is **transcode once, fan out many**. LiveKit Egress is explicitly optimized to transcode once while sending output to multiple destinations — the same egress can stream to RTMP, record HLS, record MP4, and generate thumbnails simultaneously ([LiveKit Egress outputs](https://docs.livekit.io/transport/media/ingress-egress/egress/outputs/)).

| Egress type | Transcoded? | Outputs | Use |
|---|---|---|---|
| RoomComposite (`audio_only=true`) | Yes (audio mix) | MP4 / HLS / RTMP / SRT | Single mixed audio file |
| Track | No (pass-through) | MP4 / WebM / Ogg; WebSocket audio-only | Per-track archive; captioning/diarization tap |
| Participant / TrackComposite | Yes | MP4 / HLS / RTMP / SRT | Per-participant or multi-track export |
| Auto egress | Configurable | Configurable | Auto-record every room |

Prefer real-time HLS segment write for the live archive — segments are bounded, resumable, and immediately VOD-able — then finalize an MP4 or pass-through Opus track. Package audio-only VOD as AAC-LC in fragmented MP4 using CMAF; CMAF supports a single track per file, with audio as `.cmfa` and Apple recommending 6-second segments ([Unified Streaming](https://docs.unified-streaming.com/documentation/package/package.html); [Wowza](https://www.wowza.com/docs/secure-cmaf-hls-streams-using-common-encryption-cbcs-in-wowza-streaming-engine)). Keep the original Opus track alongside the AAC derivative so repackaging does not require re-transcoding.

Loudness normalization is applied **once at egress**, never per listener and never on the live WebRTC path: target −23 LUFS with ±1 LU for live programmes, true peak ≤ −1 dBTP, measured with an ITU-R BS.1770-compliant meter ([EBU R128](https://tech.ebu.ch/docs/r/r128.pdf)). Treat the target as configurable per destination rather than hard-coded.

Speaker diarization is a deferred seam: tap the audio track with a side subscriber and never touch the live path. LiveKit `TrackEgress` can stream a track to processing services over WebSocket without transcoding ([LiveKit Egress overview](https://docs.livekit.io/egress/)), and LiveKit Agents implements diarization as a streaming-STT option that labels speakers within the current session only — similar voices, overlapping speech, and noise can merge or split speakers ([LiveKit diarization](https://docs.livekit.io/agents/models/stt/diarization/)).

## 5. Media Routing and Delivery

### 5.1 Delivery protocol decision

WebRTC is the only candidate that delivers sub-second glass-to-glass latency at production scale; LL-HLS is the fallback for large passive audiences and iOS-native playback.

| Protocol | Latency (production) | Audience ceiling | Browser / iOS | CDN-friendly | Maturity | Recommendation |
|---|---|---|---|---|---|---|
| **WebRTC** | 0.1–0.5 s ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf); [Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)) | SFU-dependent; thousands/node | Broad; Safari supports WebRTC ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API)) | No — stateful SFU + TURN | Production-proven | **Primary** interactive tier |
| **LL-HLS** | 2–5 s ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf); [LiveKit](https://livekit.com/blog/webrtc-vs-hls-livestreaming)) | Millions via CDN | Safari native; others MSE/hls.js | Yes | Production-proven; Apple authoring spec | **Fallback/scale** tier |
| **CMAF / LL-DASH** | 2–4 s ([Forasoft matrix](https://www.forasoft.com/learn/video-streaming/articles-streaming/protocol-comparison-matrix)) | Millions via CDN | DASH via MSE; Apple cannot play DASH natively | Yes | ISO/IEC 23009-1 | Packaging for LL-HLS; not a separate iOS path |
| **Classic HLS** | 6–30 s ([Wowza](https://www.wowza.com/blog/hls-vs-webrtc)) | Millions via CDN | Native on Apple; MSE elsewhere | Yes | RFC 8216 | Legacy compatibility floor |
| **MoQ** | Target sub-500 ms ([Fora Soft MoQ](https://www.forasoft.com/learn/video-streaming/articles-streaming/media-over-quic-moq)) | Aims CDN-scale via relays | No native browser API; JS over WebTransport | Designed cache-friendly | Active I-D, not RFC ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-moq-transport/)) | Watching brief |
| **WebTransport** | Transport, not a media protocol ([W3C](https://www.w3.org/TR/webtransport/)) | N/A | Limited availability ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API)) | N/A | W3C spec in progress | Substrate for MoQ only |

LL-HLS mechanics depend on partial segments (`EXT-X-PART`), preload hints (`EXT-X-PRELOAD-HINT`), blocking playlist reloads, and playlist delta updates; Apple removed HTTP/2 server push from the 2023 revision, so the CDN requirement is chunked transfer encoding and blocking reloads ([Mux](https://www.mux.com/articles/low-latency-live-streaming-developers-guide-ll-hls-webrtc-cmaf); [pantos HLS](https://datatracker.ietf.org/doc/html/draft-pantos-hls-rfc8216bis-09)).

Select the tier **per client**, not per product: default to WebRTC for interactive rooms up to the low thousands; switch to LL-HLS for large passive audiences, iOS Safari where native playback is preferred, or when the SFU tier is at capacity; fall back to classic HLS for incompatible clients. Keep chat on its independent WebSocket path so the audio tier change does not affect chat ordering.

**Cost crossover.** WebRTC is stateful: every listener is a session on an SFU and the CDN does not help. HLS/LL-HLS is stateless HTTP: the CDN caches segments and fans out at the edge ([fishjam](https://fishjam.swmansion.com/blog/webrtc-vs-hls-which-one-is-better-for-your-streaming-project-0e724ed6fe10); [LiveKit](https://livekit.com/blog/webrtc-vs-hls-livestreaming)). As a transparent illustration, 5,000 listeners at 64 kbps Opus is ≈144 GB/hour of egress; at $0.01–0.05/GB that is ≈$1.4–7.2/hour of CDN egress, while WebRTC adds SFU compute and TURN bandwidth. The exact crossover depends on bitrate, room count, region, and pricing — treat it as a target to validate, with the planning heuristic that cost, not capacity, decides between the two at 5k listeners/room.

**MoQ** is a watching brief: it is an active IETF Internet-Draft with a December 2026 milestone to request publication to the IESG ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-moq-transport/)), its substrate WebTransport is marked limited availability ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API)), and vendor deployments establish feature existence, not performance. Preserve the seam — WHIP/WHEP and the room model should not preclude a future MoQ relay tier.

### 5.2 SFU selection

For an audio-first product at launch scale, the primary SFU should be **LiveKit** (Go/Pion, Apache 2.0), with **mediasoup** (C++/Node/Rust, ISC) as the fallback for teams that need deeper media-plane control.

| SFU | License / language | Control and SDKs | Published capacity | Ops burden | Decision |
|---|---|---|---|---|---|
| LiveKit | Apache 2.0; Go ([GitHub](https://github.com/livekit/livekit)) | Medium; official JS, Swift, Kotlin, Flutter, React Native, Unity, C++, Rust SDKs ([connect docs](https://docs.livekit.io/intro/basics/connect/)) | Horizontally scalable; per-node number not published ([SFU internals](https://docs.livekit.io/reference/internals/livekit-sfu/)) | Low–medium; managed cloud optional | **Primary** |
| mediasoup | ISC; C++ media path + Node/Rust API ([mediasoup.org](https://mediasoup.org/)) | High; mediasoup-client (JS) + libmediasoupclient (C++); no official mobile SDKs | ~500 consumers per worker ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)) | High; owns signaling, TURN, recording, orchestration | **Fallback / control-first** |
| Janus | GPLv3; C ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)) | Medium–high; plugin model; no client SDKs | Not published | Medium; large config surface | Reserve for AudioBridge mixing/SIP |
| SRS | MIT; C++ ([README](https://raw.githubusercontent.com/ossrs/srs/develop/README.md)) | General media server; WebRTC one protocol among many | Not published | Medium | Not audio-first |
| ion-sfu | MIT; Go/Pion ([GitHub](https://github.com/pion/ion)) | Early stage | WIP | Early | Not production-ready |
| Medooze SFU | MIT; Node.js ([README](https://raw.githubusercontent.com/medooze/sfu/master/README.md)) | Experimental; VP9-SVC/Chrome Canary focus | Experimental | Medium | Rejected — video/SVC-first |
| Ant Media Server | Commercial | Platform | Not published | Low–medium | Rejected — video-first |

LiveKit wins on time-to-market and SDK coverage; mediasoup wins on control but forces the team to build signaling, TURN, recording, and orchestration ([trembit](https://trembit.com/blog/livekit-vs-mediasoup/)). Janus AudioBridge decodes and mixes Opus, which gives per-room audio-level events but adds a transcode step and breaks per-listener track selection ([Janus AudioBridge](https://janus.conf.meetecho.com/docs/audiobridge.html)). LiveKit emits `ActiveSpeakersChanged` ordered by audio level, including the local participant ([LiveKit Android reference](https://docs.livekit.io/reference/client-sdk-android/livekit-android-sdk/io.livekit.android.events/-room-event/-active-speakers-changed/index.html)); mediasoup provides an `ActiveSpeakerObserver` ([mediasoup API](https://mediasoup.org/documentation/v3/mediasoup/api/)). Client-side `audioLevel`/`totalAudioEnergy` statistics are a cross-platform fallback ([W3C webrtc-stats](https://www.w3.org/TR/webrtc-stats/)).

**Transferability caveat.** The most cited head-to-head benchmark is the CoSMo study, which used the KITE engine to run identical load scenarios against several open-source SFUs on AWS instances, reporting bitrate, latency, and a video-quality score ([CoSMo study](https://mediasoup.org/resources/CoSMo_ComparativeStudyOfWebrtcOpenSourceSfusForVideoConferencing.pdf); [author summary](https://webrtchacks.com/sfu-load-testing/)). It explicitly focuses on video conferencing, not broadcasting, and its authors caution that load tests do not capture resilience, user behavior, or cost. Treat it as evidence that CPU optimization matters, not as an audio capacity spec.

For the out-of-scope 50k-listener stress scenario, two mechanisms matter: SFU cascading via mediasoup `pipeToRouter()` or LiveKit session splitting ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion); [LiveKit SFU internals](https://docs.livekit.io/reference/internals/livekit-sfu/)), and an RTC-to-CDN bridge such as AnchorNet, which lets a channel publish to a single CDN node and switch modes without a hard cutover, reporting over 60% rebuffering reduction in ByteDance's deployment ([AnchorNet, USENIX ATC '25](https://www.usenix.org/system/files/atc25-meng.pdf)).

### 5.3 SFU scaling, load balancing, and failover

The scaling model is: pin each room to one node, forward one upstream per publisher, and autoscale nodes on media-specific metrics. Audience size does not change the publisher's upload; the SFU performs the fanout. mediasoup runs C++ worker subprocesses pinned to CPU cores, with a router per room holding producers and consumers; cross-worker fanout uses `pipeToRouter`, keeping media in shared memory between workers on the same host. LiveKit is horizontally scalable across nodes with an identical configuration, with Redis required for multi-node routing ([LiveKit SFU internals](https://docs.livekit.io/reference/internals/livekit-sfu/)).

Congestion control decides how many bits to send. Three mechanisms matter:

| Mechanism | Feedback | Estimator | Role |
|---|---|---|---|
| **TwCC** | Receiver → sender (RTCP transport-wide feedback) | Sender-side delay-based estimate from per-packet arrival times | The SFU estimates each subscriber's downlink and selects a forwarding bitrate/layer ([bloggeek.me](https://bloggeek.me/webrtcglossary/transport-cc/)) |
| **GCC** | Receiver → sender | Delay-based + loss-based estimators; final estimate is the minimum | Combined estimator behind WebRTC BWE; drives probing ([IETF GCC](https://datatracker.ietf.org/doc/html/draft-ietf-rmcat-gcc-02)) |
| **REMB** | Receiver → sender | Receiver-estimated maximum bitrate | Older signal, superseded by TwCC but still negotiated in SDP ([IETF GCC](https://datatracker.ietf.org/doc/html/draft-ietf-rmcat-gcc-02)) |

Because TwCC estimation runs on the sender, the SFU retains direct control over adaptation. BWE is an adaptation signal, not an autoscaling signal; scaling uses consumer/track counts, CPU, and loss/jitter.

Room placement uses `room_id` as the pinning key. LiveKit uses Redis-based routing so clients joining a room connect to the same node; an AWS EKS case study adds Route 53 latency DNS plus a geo-sticky JWT that embeds the selected region, so reconnects return to the same cluster instead of drifting to a DNS fallback ([AWS EKS case study](https://hackernoon.com/scaling-real-time-video-on-aws-how-we-keep-webrtc-latency-below-150ms-with-kubernetes-autoscaling)). mediasoup ships no signaling, so the application must implement the same room→node map itself. Media is load-balanced at L4 (UDP/RTP); signaling, chat, and HTTP use L7.

Autoscaling stateful media nodes requires custom metrics, not generic CPU: active consumer/track count per node, rooms per node, CPU, then packet loss/jitter. Use KEDA for bursty live events and HPA on custom metrics as the baseline; VPA is generally inappropriate because a running node cannot be resized. Rolling updates use StatefulSet `RollingUpdate` with `terminationGracePeriodSeconds`, a PodDisruptionBudget, and a preStop hook that stops new joins and drains before termination ([Kubernetes StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)). Mixed-version nodes coexist because WebRTC media and signaling are negotiated per session.

Failure is not masked by the SFU: unanswered STUN binding requests move ICE to `disconnected` (~5 s) then `failed` (~25–30 s) ([Mozilla ICE blog](https://blog.mozilla.org/webrtc/ice-disconnected-not/)). The recommended client behavior is to wait a few seconds, trigger an ICE restart before the state reaches `failed`, and re-join via the room router if the node itself is gone.

### 5.4 CDN, edge, and large-audience delivery

For one-to-many audio, the fanout tier is chosen by audience size. An SFU is right while a room is small and low latency matters; CDN-delivered LL-HLS becomes cheaper and then necessary as the room grows.

| Audience tier | Topology | Rationale |
|---|---|---|
| Up to ~10k | Single LL-HLS origin + CDN, or single SFU mesh | Single origin saturates around 50k req/s without manifest cache ([Fora Soft 1M](https://www.forasoft.com/blog/article/scale-video-streaming-to-1-million-viewers)) |
| 10k–100k | Cascading SFU mesh + LL-HLS hybrid; multi-region CDN | SFU cost outpaces revenue; TURN bills grow |
| 100k–1M | CDN-primary; WebRTC for contribution only | Manifest origin thundering herd; hot-spot saturation |
| 1M+ | Multi-CDN, predictive cache warming, tested failover | Untested failover; segment availability races |

The same source is blunt about the trigger: reach for CDN-primary the moment peak forecast crosses 50k; re-engineering at 200k is expensive. These figures are video-centric; for audio-only the per-node CPU ceiling rises because there is no video encode/decode, but the O(N) egress and per-subscriber state that dominate the crossover do not change. A single well-tuned media-server node forwards roughly 500–800 concurrent subscribers for video before cascading, and modern stacks sit in the 500–2,000 range per node ([Fora Soft WebRTC vs HLS](https://www.forasoft.com/blog/article/webrtc-video-steaming-app-vs-hls); [Fora Soft 1M](https://www.forasoft.com/blog/article/scale-video-streaming-to-1-million-viewers)).

Production default is hybrid: WebRTC for the small interactive speaker group, CDN-delivered LL-HLS for the mass audience. Cloudflare's serverless SFU pushes media to the edge with anycast but does not remove the O(N) fanout limit — every subscriber still consumes SFU egress ([Cloudflare Calls](https://blog.cloudflare.com/cloudflare-calls-anycast-webrtc); [Cloudflare Realtime pricing](https://developers.cloudflare.com/realtime/sfu/platform/pricing/)). P2P offload can reduce egress but trades away moderation, recording, and delivery guarantees; it is a research deployment pattern, not a paid consumer product at 5k/room ([fybrrStream](https://arxiv.org/abs/2105.07558)).

Published egress rates feed the cost model: CloudFront $0.085/GB for the next 9 TB (US) declining to $0.020/GB above 5 PB ([CloudFront pricing](https://aws.amazon.com/cloudfront/pricing/pay-as-you-go/)); Bunny Stream $0.005/GB delivery ([Bunny](https://bunny.net/stream/)); Cloudflare Realtime $0.05/GB SFU/TURN egress ([Cloudflare Realtime pricing](https://developers.cloudflare.com/realtime/sfu/platform/pricing/)); Cloudflare Stream $1 per 1,000 minutes delivered and $5 per 1,000 minutes stored ([Cloudflare Stream pricing](https://developers.cloudflare.com/stream/pricing/)). At 64 kbps, one listener-hour is 28.8 MB of egress.

Live HLS has two object classes with opposite caching needs: the `.m3u8` playlist changes every few seconds and needs a very short TTL, while segments are immutable once written and can carry a long TTL ([OpenResty Edge](https://blog.openresty.com/en/edge-hls-live-streaming/)). The starting point is a playlist TTL of ~1–2 s and a segment TTL of ~60–300 s, validated against origin capacity. Cache-key hygiene is critical: if the player appends per-viewer query parameters, every viewer gets a private cache key and the hit ratio collapses to zero; authentication must be handled by a separate access rule. Audio LL-HLS is unusually CDN-efficient because segments are small and shared — at 64 kbps a 4-second segment is ~32 KB.

Multi-CDN failover uses DNS steering (coarse, resolver-propagation dependent), layer-7 traffic management (per-request control at the cost of an extra controller hop), origin shielding, or client-side steering ([Fastly](https://www.fastly.com/blog/multi-cdn-critical-decision-for-resilient-architecture)). Failover time is set by the routing tier, not the media tier: DNS failover takes 1–5 minutes because resolver caches hold stale answers, while anycast failover takes seconds via BGP withdrawal ([HLD Handbook](https://hld.handbook.academy/curriculum/architecture-patterns/multi-region-architecture/)). For sub-second media failover, use anycast such as AWS Global Accelerator ($0.025/hr fixed plus $0.015–$0.105/GB premium transfer) rather than DNS record swaps ([AWS Global Accelerator pricing](https://aws.amazon.com/global-accelerator/pricing/)).

## 6. Chat Subsystem

### 6.1 Transport and connection lifecycle

WebSocket over WSS is the primary chat transport: it is the only widely deployed, browser-native, full-duplex protocol that holds a persistent connection open at low latency while reusing standard HTTP infrastructure (TLS, load balancers, CDNs).

| Transport | Bidirectional? | Mobile keep-alive | Complexity | Use |
|---|---|---|---|---|
| WebSocket/WSS ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)) | Yes | Poor in background; foreground service + push supplement | Medium | **Primary** |
| SSE / EventSource ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)) | No (server→client) | Poor | Low | Read-only announcements/fallback |
| HTTP long polling ([GetStream](https://getstream.io/blog/chat-application-architecture/)) | Half | Poor | Low–medium | Legacy fallback only |
| MQTT QoS 0/1/2 ([HiveMQ](https://www.hivemq.com/blog/mqtt-essentials-part-6-mqtt-quality-of-service-levels/)) | Yes | Poor; no native browser | Medium–high | Constrained/embedded clients, not primary |
| WebRTC DataChannel ([web.dev](https://web.dev/articles/webrtc-datachannels)) | Yes | Tied to peer-connection lifecycle | High | Small established rooms only |
| XMPP ([RFC 6120](https://www.rfc-editor.org/rfc/rfc6120)) / Matrix ([IETF MIMI](https://www.ietf.org/archive/id/draft-ralston-mimi-matrix-framework-01.html)) | Yes | Poor | High/very high | Rejected — federation overhead unjustified |

WebSocket opens with an HTTP `Upgrade` handshake and uses ping/pong control frames for keepalive ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)). A practical heartbeat cadence is about 30 seconds; Phoenix used a 30-second heartbeat while demonstrating 2M connections on 4-core/15 GB machines after OS-level tuning ([Phoenix](https://www.phoenixframework.org/blog/the-road-to-2-million-websocket-connections)). Combine a server-initiated ping with a missed-pong timeout and a TCP keepalive backstop. Reconnection uses exponential backoff with jitter to avoid a thundering herd.

The edge tier is a pool of stateful WebSocket gateway nodes behind a load balancer, with a service-discovery layer picking the right chat server per user, ideally in their region ([GetStream](https://getstream.io/blog/chat-application-architecture/)). The stable routing key is `room_id`, consistent-hashed to a gateway node, so a room's participants and fanout path stay colocated. Sticky routing must be paired with rebalancing when nodes scale or fail.

Fallbacks are deliberate: HTTP for login, profile, contacts, media upload, and history pagination; SSE for read-only streams; long polling only where WebSocket is blocked. `permessage-deflate` compresses WebSocket payloads per message; a production case reported ~3× transmit bandwidth reduction but ~2× CPU increase ([Centrifugal Labs](https://centrifugal.dev/blog/2024/08/19/optimizing-websocket-compression)), so enable it for text chat but profile device CPU and consider disabling it for very high-frequency small messages.

Reusing `RTCDataChannel` for chat in a large room is not worth it: DataChannel is peer-to-peer with no intermediary server, so a 500-chatter room would require a mesh or server bridge that duplicates the fanout work and couples chat to the media connection lifecycle ([web.dev](https://web.dev/articles/webrtc-datachannels)). Use JSON on the client path with a versioned event schema; consider Protobuf or MessagePack for high-volume internal paths.

### 6.2 Chat server architecture and fanout

The chat tier decomposes into four subsystems with different scaling profiles: a **stateful connection gateway**, a **stateless message service**, a **presence service**, and a **persistence layer**. GetStream's production reference separates exactly these concerns, with a wide-column store for message history and Redis for read state ([GetStream](https://getstream.io/blog/chat-application-architecture/)).

Fanout — turning one sent message into many deliveries — is the dominant cost driver. The three strategies trade write cost against read cost:

| Strategy | Write path | Read path | Best for |
|---|---|---|---|
| Fan-out on read | Store message once | Merge room history per read | Large channels; no live push |
| Fan-out on write | Append to every member's timeline | One timeline lookup | Small groups; fast reads; simple unread tracking |
| Hybrid | Append to active members; store once for the rest | Timeline lookup + merge recent candidates | Large rooms with many passive members |

Sources: [Milan Jovanović](https://milanjovanovic.tech/blog/how-do-you-build-a-social-media-feed-system-design); [GetStream fan-out glossary](https://getstream.io/glossary/fan-out/).

For a live audio room the fanout unit is the room, not the follower graph: a message from one chatter is broadcast to every online member. At launch scale (5,000 listeners + 500 chatters), fan-out-on-write costs ~5,500 deliveries per message — well within a tier of gateway nodes. As a heuristic, rooms up to roughly 10k–20k online members are comfortably served by fan-out-on-write; beyond that, push only to recently active members and serve the rest on read. The strongest lever for large rooms is to **not fan out to passive members**: Discord found around 90% of connections in large servers were passive and stopped updating users not actively viewing a server, reducing fanout work by roughly the same amount ([Level Up Coding](https://blog.levelupcoding.com/p/discord-case-study-one-message-million-users)).

Rooms shard to gateway nodes by consistent hashing on `room_id`. Cross-gateway delivery takes three common forms: distributed broadcast (Phoenix PubSub — one message crosses the network per additional node), message bus (socket.io Redis adapter — every node sees every message), or centralized router (GetStream's group handler — only relevant nodes receive it) ([Phoenix Channels](https://hexdocs.pm/phoenix/channels.html); [Socket.IO Redis adapter](https://socket.io/docs/v4/redis-adapter/); [GetStream](https://getstream.io/blog/chat-application-architecture/)). The first two are simpler but waste bandwidth on irrelevant nodes; the router is more efficient but adds a stateful routing tier.

Presence at 100k+ online users is a separate, ephemeral, in-memory subsystem because its access pattern — very high write frequency, low durability, mostly memory — differs from message delivery ([GetStream](https://getstream.io/blog/chat-application-architecture/)). Two implementations dominate: a Redis sorted set per room with heartbeat timestamps and TTL, or CRDT-based presence such as Phoenix Presence, which replicates transparently across the cluster with no single source of truth and self-heals on node failure ([Phoenix Presence](https://hexdocs.pm/phoenix/presence.html)).

| Option | Concurrency | Cross-node routing | Ops burden | Cost model |
|---|---|---|---|---|
| Phoenix Channels + Presence | Millions of subscribers per box; 2M-connection benchmark on 15 GB/4 cores, 2015 ([Phoenix](https://www.phoenixframework.org/blog/the-road-to-2-million-websocket-connections)) | PubSub broadcast | Low runtime deps; Elixir/BEAM expertise required | Self-hosted CPU/RAM; no per-connection fee |
| socket.io + Redis | No published ceiling; environment-dependent | Redis adapter Pub/Sub; sticky sessions; sharded Pub/Sub (Redis 7.0) | Redis ops; sticky-session LB | Self-hosted CPU/RAM + Redis |
| Managed (PubNub, Sendbird, Ably, Pusher, Stream) | Platform-level; single-chat limits (PubNub 10k, Sendbird 20k supergroups) ([Ably](https://ably.com/compare/pubnub-vs-sendbird)) | Vendor-managed | Minimal; vendor SLAs | MAU / peak connections / connection-minutes / message volume ([GetStream SDK comparison](https://getstream.io/blog/chat-sdk-comparison/)) |

Production references confirm the design space: Discord runs Elixir core services with Rust NIFs for hot data structures and scaled to 11 million concurrent users ([Discord](https://discord.com/blog/using-rust-to-scale-elixir-for-11-million-concurrent-users)); Slack terminates WebSocket connections in a dedicated service behind HAProxy, later migrating to Envoy for dynamic configuration ([Slack Engineering](https://slack.engineering/migrating-millions-of-concurrent-websockets-to-envoy/)); Twitch Chat exposes IRC over WebSocket and explicitly does not guarantee message order or deduplication ([Twitch IRC concepts](https://dev.twitch.tv/docs/chat/irc/)) — which is why clients dedupe by message ID and use per-room sequence numbers.

Delivery semantics are at-least-once with client-side deduplication: a message sent while a recipient is offline must persist durably and replay with no gaps and no duplicates; every device must converge to the same read state ([GetStream](https://getstream.io/blog/chat-application-architecture/)). Managed SDKs implement connection state recovery natively, whereas the socket.io Redis adapter explicitly does not support it ([Ably](https://ably.com/compare/pubnub-vs-sendbird); [Socket.IO Redis adapter](https://socket.io/docs/v4/redis-adapter/)).

### 6.3 Ingestion, ordering, and persistence

The message path is an append-only, per-room log. A message service ingests, assigns a time-sortable ID and a per-room sequence number, and appends to a durable log; a fanout layer expands one append into many deliveries. Ordering is guaranteed **per room, not globally**; delivery is at-least-once with client deduplication.

The ordering problem is a partitioning problem, not a sequencing problem. Route every message for a room to a single partition/stream: Kafka only guarantees ordering within a partition, so key-based partitioning by `room_id` preserves per-room order while keeping rooms independent ([Conduktor](https://www.conduktor.io/glossary/kafka-partitioning-strategies-and-best-practices)). Assign the sequence number **at append time, inside the log**, not in a separate sequencer: Redis Streams assigns a server-side entry ID on `XADD`, and NATS JetStream assigns a sequence number on append ([Redis Streams tutorial](https://redis.io/tutorials/howtos/solutions/microservices/interservice-communication/); [NATS JetStream](https://docs.nats.io/concepts/jetstream)). A centralized sequencer would serialize all rooms and become a bottleneck.

The required guarantee is per-room total order. Within a single conversation, messages must appear in the order sent; duplicates are acceptable if the client can dedupe, but lost messages are never acceptable ([GetStream](https://getstream.io/blog/chat-application-architecture/)). Causal or eventual consistency is acceptable only across rooms and, later, across regions.

| Broker | Ordering unit | Persistence | Replay | Cross-region | Ops | Recommendation |
|---|---|---|---|---|---|---|
| Apache Kafka | Per partition (key-based) | Disk log, retention policy | Offset-based | MirrorMaker 2 / MSK Replicator (Phase 3) | High | Analytics/audit stream |
| Redis Streams | Per stream (server-assigned ID) | In-memory/disk log | `XREADGROUP` from any point | Global Datastore / app mirror (Phase 3) | Low | Fallback if Redis already runs |
| NATS JetStream | Per stream (server-assigned sequence) | Memory or disk | From sequence/time | Leaf node over WebSocket (Phase 3) | Low–medium | **Primary realtime backbone** |
| Apache Pulsar | Per topic/partition | BookKeeper log | Subscription cursors | Native geo-replication | Medium–high | Deferred to multi-region |

Sources: [Redis Streams tutorial](https://redis.io/tutorials/howtos/solutions/microservices/interservice-communication/), [AWS Kafka vs Redis](https://aws.amazon.com/compare/the-difference-between-kafka-and-redis/), [NATS JetStream](https://docs.nats.io/concepts/jetstream), [Pulsar messaging](https://pulsar.apache.org/docs/4.0.x/concepts-messaging/). The main architectural reason to prefer NATS on the realtime path is that room fanout is partition-skew-prone in a fixed-partition system and skew-free in a subject-routed system: subjects are the routing primitive, and a hot room is a hot subject that additional consumers can serve.

Define five message types — `chat`, `reply`, `reaction`, `system/announcement`, `moderator action` — with fields `id`, `room_id`, `sequence`, `sender_id`, `type`, `body`, `reply_to`, `created_at`, and `idempotency_key`. Persistence follows access pattern:

| Tier | Store | Data | Retention | Access pattern |
|---|---|---|---|---|
| Hot | Redis | Recent messages, read cursors, presence | Hours–days | High-frequency reads/writes |
| Warm | PostgreSQL / ScyllaDB | Message history, threads, search index | ~90 days (target) | Paginated history, search |
| Cold | S3/GCS | Archived rooms, compliance export | Per policy | Rare; export/deletion |

Read cursors live in the ephemeral state layer, separate from message delivery. On join, the client fetches history since its last cursor — a keyset pagination query, not an offset scan — and idempotent processing plus durable checkpoints prevent skips and duplicates ([Prismatic](https://prismatic.io/blog/how-do-i-implement-cursor-based-pagination/)).

Message IDs should be unique, coordination-free, and roughly time-ordered. UUIDv7 (RFC 9562) provides a leading Unix timestamp, a counter for same-millisecond monotonicity, and database-index locality; KSUID is compact and lexicographically sortable; Snowflake requires coordination ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.txt); [KSUID](https://github.com/segmentio/ksuid)). Use UUIDv7 or KSUID; a separate search index is populated from the message stream as a derived, rebuildable store.

### 6.4 Ephemeral state: presence, typing, reactions

Presence, typing indicators, reactions, and live read state must be served from a separate in-memory layer, not the durable message store. Their access patterns are fundamentally different: ephemeral state is written very frequently, has low durability requirements, and is safe to lose; messages are written once, read back with pagination, and must survive restarts and partitions ([GetStream](https://getstream.io/blog/chat-application-architecture/)).

| Dimension | Durable message state | Ephemeral state |
|---|---|---|
| Write pattern | Write once; read back with pagination | Very high write frequency; mostly memory |
| Durability | Must survive restart, deploy, partition | Safe to lose; expires on its own |
| Ordering | Per-room total order | Convergence suffices |
| Store | PostgreSQL / ScyllaDB | Redis / in-memory |

**Presence: track connections, not users.** The naive boolean-per-user model breaks as soon as a user opens two tabs or reconnects before the old socket times out ([Syed Wajeeh Haider](https://www.syedwajeehhaider.com/presence-and-typing-indicators)). Track a sorted set per user whose members are socket IDs and whose scores are expiry timestamps; counting live connections is a single `ZCOUNT`. A Lua script makes prune/count/add atomic, and stale entries age out. The reference pattern uses a 60 s key TTL, a 30 s heartbeat, and a 5 s offline grace period, with a sweeper running every 15 s. The grace period prevents flapping on mobile networks; the TTL prevents unbounded growth from crashed nodes.

A CRDT-based alternative (Phoenix Presence) replicates presence across the cluster as a conflict-free replicated data type with no single point of truth, propagating only joins and leaves and tolerating out-of-order or duplicate delivery ([Phoenix Presence](https://tmbb.github.io/phoenix/presence.html); [WorkOS](https://workos.com/blog/in-memory-distributed-state-with-delta-crdts)). It trades operational simplicity for CPU cost on merges and makes presence cost grow with cluster size; at launch scale a sharded Redis model is simpler to bound.

**Typing indicators** should perform zero database writes: client-side debounce emits typing-start on the first keystroke and typing-stop after idle; server-side rate limiting applies a token bucket per connection; a short TTL ensures a missed stop event cannot leave a permanent flag. **Reactions** are modeled as idempotent set operations keyed by `(message_id, emoji, user_id)`; add is a set insert, remove a delete, and a repeated delivery is a no-op. Aggregate counts plus user sets and fan out coalesced deltas, not the full set. Order reaction changes with the same per-room sequence number used for chat; because add/remove are commutative per user, out-of-order delivery still converges ([WorkOS](https://workos.com/blog/in-memory-distributed-state-with-delta-crdts)).

Write amplification is the hidden cost. An illustrative model at launch scale:

| Signal | Trigger | Illustrative rate |
|---|---|---|
| Presence heartbeat | 5,000 listeners × 1 heartbeat / 15 s | ~333 writes/s |
| Chat messages | 500 chatters × 1 message / 5 s | ~100 messages/s |
| Typing | Debounced start/stop | ≤ ~200 events/s |
| Receipts | 1 message × N recipients | Up to thousands per message |

Treat the "orders of magnitude" characterization as a vendor assertion to validate with a load test; the ratio grows with multi-device sessions, mobile handover churn, and receipts. Fanout strategy belongs to §6.2; ordering and persistence belong to §6.3.

### 6.5 Moderation, rate limiting, and abuse prevention

Moderation must not be a synchronous gate on the chat hot path. The design is a five-stage pipeline in which only the rate limiter is synchronous:

| # | Stage | Sync/Async | Added hot-path latency | Failure behavior |
|---|---|---|---|---|
| 1 | Client filter (blocklist, profanity DFA) | Sync, client-side | ~0 ms | Bypassable; UI-level only |
| 2 | Server rate limit (per-user token bucket, per-channel sliding window) | Sync, server-side | <1 ms | Drop excess; emit system notice |
| 3 | Async content moderation (keyword/DFA, ML) | Async | 0 on hot path | Queue; publish unclassified if classifier down |
| 4 | Fanout | Async | — | As §6.2/§6.3 |
| 5 | Tombstone recall | Async | ~100 ms–1 s (target) | Idempotent by message ID |

Rate limiting needs two scopes: a per-user limit stops one chatter flooding, and a per-channel quota bounds total fanout amplification. A token bucket permits short conversational bursts while capping sustained rate; a sliding-window counter is the better per-channel control because it has no window-boundary burst; fixed windows are acceptable only for coarse daily quotas. Distributed enforcement needs atomic counters shared across gateway nodes (Redis with Lua scripting), and history fetched on rejoin must be exempt from send quotas.

Synchronous versus asynchronous moderation trades latency against certainty:

| Approach | Hot-path latency | Catches everything? | Live-room fit |
|---|---|---|---|
| Synchronous block | Adds classifier latency; p99 risk | Yes | Poor for ML; acceptable for deterministic blocklists |
| Async publish-then-recall | 0 | No — brief exposure window | Best default for live rooms |
| Hybrid | Deterministic blocks sync; ML async | Mostly | Recommended |

Tombstone recall makes async moderation viable: when a message is removed, emit a tombstone (message ID + reason) through the same chat event path, so every client removes or collapses it. Recall is idempotent by message ID and ordered by the per-room sequence number; it is not retroactive for push notifications already dispatched.

Layer the content checks by severity:

| Layer | Technique | Strength | Weakness | Role |
|---|---|---|---|---|
| Client filter | Blocklist, profanity DFA | Zero server cost; instant | Bypassable; no recall | First-pass UX |
| Server keyword/DFA | Deterministic finite automaton | High precision; O(n) scan | Low recall; spelling evasion | Pre-publish block of high-confidence content |
| Third-party ML | AWS Comprehend, Perspective API, Hive | Scale; category scoring | Latency; FP/FN; language coverage | Post-publish scoring |
| Human review | Moderator queue, appeals | Judgment; context | Cost; latency | Borderline cases; appeals |

AWS Comprehend Toxicity Detection assigns a 0–1 toxicity score across seven categories, accepts up to 10 segments of ≤1 KB per request, and is English-only and GA in four regions — imposing chunking, batching, and a gap for non-English rooms ([AWS Comprehend](https://aws.amazon.com/blogs/machine-learning/flag-harmful-content-using-amazon-comprehend-toxicity-detection/)). Perspective API thresholds were not verifiable from the documentation page; treat thresholds as targets to validate. Tune precision per category: high-severity categories need high precision to avoid silencing people discussing their own identities.

**End-to-end encryption changes the moderation surface.** The Messaging Layer Security (MLS) protocol, RFC 9420, provides group key agreement with forward secrecy and post-compromise security, but its Delivery Service carries ciphertext and cannot read content ([RFC 9420](https://www.rfc-editor.org/info/rfc9420/)). Consequently, E2EE removes server keyword/ML moderation, server push-preview generation, and searchable history; client-side classifiers, reporting, and metadata/behavioral signals must carry the abuse defense. E2EE is therefore a documented alternative, not the launch default.

Moderator controls must be enforced server-side and propagated as room state events: slow-mode (minimum interval between a user's messages), follow-only (strongest raid control), subscribers-only, emoji-only, and per-channel quotas with drop/sample/batch-merge backpressure. Member actions — block, mute, timeout, kick, ban — must be idempotent and survive reconnection. Raid defense combines per-channel and per-user limits, follow-only/subscribers-only lockdown, new-account gating, device fingerprinting (minimized, disclosed, and purpose-limited under GDPR), anomaly detection on join-and-message rates and duplicate hashes, and rate-limited granular push notifications.

Moderation actions require an append-only, tamper-evident audit log recording actor, action, target, message ID, reason, room ID, timestamp, and source. Retention tension is real: GDPR storage-limitation and erasure obligations require deletion when data is no longer necessary, while audit and legal-hold obligations require retention; a tiered policy with legal-hold flags balances the two, but specific periods and legal bases must be validated with counsel.

The EU Digital Services Act applies to all online services operating in the EU with obligations proportionate to role, size, and impact; micro and small companies have lighter requirements, and only Very Large Online Platforms above 45 million EU monthly users face the additional systemic-risk regime ([EU DSA](https://digital-strategy.ec.europa.eu/en/policies/digital-services-act)). At the launch target of 50k DAU, the baseline regime applies: transparency in content removals, an appeal mechanism, easy flagging of illegal content, response to reports, protection of minors, and priority handling of trusted-flagger notices.

## 7. Client Architecture

### 7.1 Browser client

Use React with TypeScript. Next.js's App Router renders the room shell and initial chat history ahead of time via React Server Components, so server-only libraries stay out of the client bundle and the first paint is visible; Client Components (`"use client"`) own interactivity ([React Server Components](https://react.dev/reference/rsc/server-components)). A Vite-built SPA is simpler for a fully client-rendered embed but loses the server-rendered shell.

Define one `MediaPlayer` interface (`load`, `play`, `pause`, `seek`, `getLatency`, `switchMode`) with two implementations. Latency is a property of the delivery protocol, not the player:

| Path | Latency | Browser support | CPU | Recommendation |
|---|---|---|---|---|
| WebRTC (`RTCPeerConnection`) | 0.2–0.5 s ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)) | All modern browsers ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)) | Moderate | Primary for interactive rooms |
| hls.js LL-HLS | 3–5 s ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)) | MSE-capable browsers; iOS Safari needs ManagedMediaSource (iOS 17.1+) or native HLS ([Shaka Player](https://github.com/shaka-project/shaka-player)) | Low | Primary for broadcast/large rooms |
| Shaka Player | 3–5 s | MSE/EME; DASH/HLS/MSS; iOS native HLS fallback ([Shaka Player](https://github.com/shaka-project/shaka-player)) | Low | Alternative when DASH/MSS or FairPlay is needed |

hls.js exposes `lowLatencyMode`, `liveSyncDurationCount`, `liveMaxLatencyDurationCount`, `maxLiveSyncPlaybackRate`, and `timelineOffset` ([hls.js API](https://raw.githubusercontent.com/video-dev/hls.js/master/docs/API.md); [lowLatencyMode](https://hlsjs.video-dev.org/api-docs/hls.js.hls.lowlatencymode)). Enable `lowLatencyMode`, reduce the live sync target to 1–2 target durations, and cap catch-up playback rate at ~1.2–2; a rate above 1.0 is audible as tempo/pitch increase, so keep it modest for speech.

Chat uses WebSocket; login, profile, contacts, media upload, and history pagination use HTTP ([GetStream](https://getstream.io/blog/chat-application-architecture/)). Use selective subscriptions (Zustand/Jotai or React's `useSyncExternalStore`) and a virtualized list with `requestAnimationFrame` throttling for high-frequency updates. A service worker caches the app shell and static assets and enables push, but live MSE segments are not meaningfully cacheable at the live edge; push subscription endpoints are capability URLs and must be kept secret ([MDN Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API); [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)).

**Autoplay policy.** Every engine blocks audio with sound until a user gesture. Chrome allows muted autoplay and requires interaction or a crossed Media Engagement Index threshold for sound; Safari blocks media with sound by default and restrictions are granted per element; Firefox blocks sound by default with user customization ([Chrome](https://developer.chrome.com/blog/autoplay); [WebKit](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/); [Mozilla](https://support.mozilla.org/en-US/kb/block-autoplay); [MDN](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)). Minimal requirement: a click/tap (for example a "Listen" button) that calls `play()` inside the handler; start muted and unmute on a second gesture if autoplay is uncertain.

**Safari `AudioContext` limitations.** An `AudioContext` must be created or resumed after a user gesture, and iOS Safari's sample rate follows the hardware/`AVAudioSession` and can change dynamically when the audio route changes; do not hard-code the sample rate and test on iOS ([WebKit bug 154538](https://bugs.webkit.org/show_bug.cgi?id=154538)). WebCodecs and AudioWorklet expose codec-level and DSP hooks, but they do not replace `RTCPeerConnection`'s built-in Opus pipeline for live transport ([W3C WebCodecs](https://www.w3.org/TR/webcodecs/); [MDN AudioWorklet](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet)).

When switching tiers, pre-warm the target player before switching and use a short crossfade or a "switching" state to hide the gap; the chat WebSocket stays connected across the switch.

### 7.2 Mobile client

For a live-audio product where background playback, low-latency delivery, and platform audio-session correctness are first-class, native Kotlin/Swift is the default for the media path. React Native and Flutter are acceptable for chat, UI, and non-media logic, but WebRTC/audio still require native modules or official SDKs, and audio-session/background behavior must be implemented per platform regardless of framework.

| Framework | WebRTC/audio path | Background audio | Audio-session control | Recommendation |
|---|---|---|---|---|
| Native Kotlin/Swift | libwebrtc directly; AVAudioEngine / AudioRecord | Direct: `UIBackgroundModes` audio + CallKit (iOS); `mediaPlayback`/`phoneCall` foreground services + `MediaSessionService` (Android) | Full: `AVAudioSession` categories, VPIO, interruptions; Android audio focus | Default for media-critical client |
| React Native | react-native-webrtc (libwebrtc M124) or LiveKit RN SDK; native code required, no Expo Go ([react-native-webrtc](https://github.com/react-native-webrtc/react-native-webrtc)) | Via native modules; New Architecture JSI/TurboModules give synchronous native access ([React Native 0.76](https://reactnative.dev/blog/2024/10/23/the-new-architecture-is-here)) | Indirect; must bridge to platform audio session | Acceptable if the team is JS-heavy; budget for native module work |
| Flutter | flutter_webrtc (based on GoogleWebRTC) or LiveKit Flutter SDK ([flutter_webrtc](https://pub.dev/packages/flutter_webrtc)) | Via plugins; platform-specific background modes | Indirect; `audio_session`/`just_audio` plugins | Acceptable for MVP; validate audio-session behavior on-device |

| Platform | Mechanism | Purpose |
|---|---|---|
| iOS | `UIBackgroundModes` audio | Continue audio while backgrounded ([Apple Audio Session Programming Guide](https://developer.apple.com/library/archive/documentation/Audio/Conceptual/AudioSessionProgrammingGuide/AudioGuidelinesByAppType/AudioGuidelinesByAppType.html)) |
| iOS | CallKit | VoIP-style call UI and audio lifecycle |
| iOS | APNs | Push for go-live alerts/chat |
| Android | Foreground service (`mediaPlayback`) | Continue audio playback via `MediaSessionService`; `FOREGROUND_SERVICE_MEDIA_PLAYBACK` permission ([Android Media3](https://developer.android.com/media/media3/session/background-playback)) |
| Android | Foreground service (`phoneCall`) | Call-style audio via Core-Telecom/`ConnectionService` ([Android Core-Telecom](https://developer.android.com/guide/topics/connectivity/telecom/selfManaged)) |
| Android | WorkManager | Deferrable sync and chat catch-up; Doze-aware ([Android WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent)) |
| Android | FCM | Push for go-live alerts/chat |

FCM is a cross-platform layer whose platform transport routes to the Android transport layer, APNs, or Web Push; use notification messages for user-visible go-live alerts and data messages for silent chat synchronization ([FCM architecture](https://firebase.google.com/docs/cloud-messaging/fcm-architecture)). Push supplements, but does not replace, the live WebSocket chat path while the app is foregrounded.

Prefer hardware-accelerated platform decode (ExoPlayer on Android, AVFoundation on iOS) and keep the live path at a single Opus bitrate rather than transcoding. For background sync, WorkManager constraints prevent chat catch-up from draining the battery. On the creator side, bypass the Voice Processing I/O unit's AEC/noise suppression/AGC for music-mode capture, and remember that Bluetooth HFP routes negotiate at 16 kHz mono regardless of the requested channel count ([LiveSwitch](https://developer.liveswitch.io/liveswitch-server/guides/ios-audio-session-management.html)).

| Player | Transport | Latency tier | Background behavior | Power | Recommendation |
|---|---|---|---|---|---|
| WebRTC SDK player | WebRTC (SFU) | 0.2–0.5 s | Requires active audio session/foreground service; interruption handling is the app's responsibility | Higher CPU/network; adaptive bitrate | Default for interactive/live rooms |
| ExoPlayer/Media3 | LL-HLS/CMAF | 2–8 s | `MediaSessionService` + `mediaPlayback` foreground service; lock-screen metadata | Hardware decode; efficient for long listening | Listener path for large audiences |
| AVPlayer/AVFoundation | HLS/LL-HLS | 2–8 s | `UIBackgroundModes` audio; `MPNowPlayingInfoCenter`/`MPRemoteCommandCenter` | Hardware decode; efficient for long listening | iOS listener path for large audiences |

Both native and cross-platform ecosystems already wrap Google libwebrtc: react-native-webrtc pins M124 and flutter_webrtc is based on GoogleWebRTC ([react-native-webrtc](https://github.com/react-native-webrtc/react-native-webrtc); [flutter_webrtc](https://pub.dev/packages/flutter_webrtc)). Hand-rolling an additional shared C++ core has low marginal benefit unless the team needs custom DSP at the deferred diarization/transcription seam; keep the door open for that seam but do not make it a Phase 1 deliverable.

App-store constraints are real: iOS requires the audio `UIBackgroundModes` flag for background playback/recording, Android 14 requires an explicit foreground-service type and matching permission ([Android 14](https://developer.android.com/about/versions/14/changes/fgs-types-required)), react-native-webrtc is unavailable in Expo Go, and flutter_webrtc requires minSdk 23 and Java 8.

### 7.3 Cross-platform WebRTC and audio integration

Share the SDP offer/answer signaling flow, the chat event schema, room/session state, token/auth flow, reconnection state machine, and time-sync logic. Keep platform-specific: capture, audio session/focus, audio routing, hardware codec configuration, playback, and push/background execution. Managed SDKs are the primary mechanism for this split: they ship one SDK per platform that already implements the platform-specific audio lifecycle ([About LiveKit](https://docs.livekit.io/intro/about/)). Concretely, define the realtime event protocol once (a versioned TypeScript schema with generated Swift/Kotlin models, or Kotlin Multiplatform), implement the signaling/chat state machine once per platform against that protocol, and isolate media behind a thin `MediaTransport` interface.

Pin Opus codec preference through the RTP transceiver's codec-preferences API rather than relying on default ordering, and avoid platform-specific SDP munging. Set the audio session's preferred sample rate once, then let Opus's bandwidth scalability absorb route-driven changes rather than restarting the encoder. Observe route-change notifications and reconfigure on change; Bluetooth HFP headsets negotiate at 16 kHz mono regardless of the app's preferred channel count ([LiveSwitch](https://developer.liveswitch.io/liveswitch-server/guides/ios-audio-session-management.html)).

| Platform / layer | Mechanism | Key behavior | Guidance |
|---|---|---|---|
| iOS `AVAudioSession` | Category `playAndRecord` | Simultaneous record + playback (VoIP); audio continues with Silent switch set and screen locked; background playback requires `audio` in `UIBackgroundModes` ([Apple](https://developer.apple.com/tutorials/data/documentation/avfaudio/avaudiosession/category-swift.struct/playandrecord.json)) | Use for full-duplex host/guest; add background mode for listener playback |
| iOS SDK audio lifecycle | Centralized `AudioSessionManager` | One VPIO AudioUnit per process; eliminates competing echo cancellers, Bluetooth SCO links, and `setCategory`/`setActive` calls | Prefer SDK-managed audio session; manual management only for CallKit ([LiveSwitch](https://developer.liveswitch.io/liveswitch-server/guides/ios-audio-session-management.html)) |
| iOS Bluetooth | HFP headset route | HFP negotiates 16 kHz mono; mic and speaker are tied together | Let the SDK auto-adapt channel count; do not force stereo |
| Android | Audio focus (`requestAudioFocus`) | One app holds focus; request in `onPlay()`, verify `AUDIOFOCUS_REQUEST_GRANTED`; pause or duck on loss; abandon on stop ([Android](https://developer.android.com/media/optimize/audio-focus)) | Duck rather than stop on transient loss; `CONTENT_TYPE_SPEECH` is not auto-ducked by the system |
| Android 12+ (API 31+) | System-managed focus | System forces fade-out when another app gains focus; mutes playback on incoming call ([Android](https://developer.android.com/media/optimize/audio-focus)) | Rely on system enforcement; handle callbacks for older API levels |

For voice, use PlayAndRecord + VideoChat with VoiceProcessingIO enabled; for music, disable voice processing, which is the seam the music-mode path preserves ([LiveSwitch](https://developer.liveswitch.io/liveswitch-server/guides/ios-audio-session-management.html)).

`RTCPeerConnection` configuration knobs and defaults are `iceTransportPolicy` = `"all"`, `bundlePolicy` = `"balanced"`, and `rtcpMuxPolicy` = `"require"` ([W3C WebRTC PC](https://w3c.github.io/webrtc-pc/)). Keep the defaults for audio-only single-track operation; they matter more when video/data tracks are added later.

ICE restart is the application's call — the browser will not trigger it automatically. Triggers include Wi-Fi↔cellular handover, NAT binding timeout, ICE state `failed`/`disconnected`, and TURN allocation expiry. A restart generates a new SDP offer with new `ice-ufrag`/`ice-pwd`, re-gathers candidates, and runs connectivity checks while the old path carries media until a new pair is nominated; it preserves the DTLS handshake and SRTP keys ([bloggeek.me](https://bloggeek.me/webrtcglossary/ice-restart/)). A common heuristic is to restart immediately on `failed` and wait out `disconnected` for about 2 seconds. Critically, confirm with the SFU that it accepts client-initiated restarts; otherwise fall back to building a fresh `PeerConnection`, which costs roughly 1–3 seconds and resets tracks, transceivers, and simulcast layers.

Simulcast has the publisher encode several independent streams at different resolutions/bitrates, and the SFU selects which to forward per subscriber based on receiver bandwidth estimate, requested layer, and streams actually being produced ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/simulcast-svc-sfu)). That evidence is video-conferencing-centric; for audio-only the equivalent adaptation is the congestion controller plus codec DTX/FEC and the bitrate ladder.

The long-term maintenance cost favors managed SDKs: custom media code requires absorbing every WebRTC spec change, OS audio-behavior change, and SFU upgrade, whereas a managed SDK absorbs the platform-specific audio lifecycle and the operational/scaling burden ([LiveSwitch](https://developer.liveswitch.io/liveswitch-server/guides/ios-audio-session-management.html); [About LiveKit](https://docs.livekit.io/intro/about/)).

### 7.4 Resilience, reconnection, and shared infrastructure

Client resilience rests on two independent recovery paths that must not share fate: a stateless, sequence-numbered chat reconnect protocol, and a media-plane recovery ladder. Transport reconnection is the easy half; state synchronization is the hard half. Production analysis notes that mobile reconnection, group fanout, and multi-device sync realistically take years to production-harden, and that duplicates are fine if the client can dedupe them, but lost messages never are ([GetStream](https://getstream.io/blog/chat-application-architecture/)).

**Chat reconnection.** Use exponential backoff with full jitter: start at 500 ms, double each attempt, cap at 30 s, and randomize each delay between 50% and 100% of the computed value. Without jitter, every client that disconnected in the same server restart retries at identical intervals and the retry wave can keep the recovering server down longer than the original failure ([websocket.org](https://websocket.org/guides/reconnection/)). Prefer a stateless recovery protocol over sticky sessions: the server assigns each message a sequence number, the client tracks the last sequence received, and on reconnect sends that sequence so the server replays only what was missed. Compensation runs in both directions — inbound via `since = lastSeq`, outbound via an unacknowledged-message outbox with an idempotency key. Delivery is at-least-once with application-level deduplication. Keep non-realtime operations off the socket, and keep presence off the reconnect path.

**Audio recovery.** Detect the failure via ICE/connection state and network-change events; attempt an ICE restart first; if the restart fails, tear down and rejoin with a new peer connection and, if the SFU node itself failed, a new SFU node. The SFU forwards one upstream per publisher regardless of audience size, so a listener rejoin is cheap and does not multiply publisher bandwidth ([Ant Media](https://antmedia.io/how-to-build-a-webrtc-mobile-app/)). While media is unavailable, the player rebuffers. Player engines differ in failure behavior: AVPlayer freezes on corrupt segments, ExoPlayer needs meticulous buffer tuning, and hls.js carries a high memory footprint on long streams ([Fora Soft](https://www.forasoft.com/blog/article/video-streaming-app-development-challenges-solutions-whm3v)); treat player error callbacks as a first-class signal.

**UX states.** Distinguish reconnecting (socket down, backoff in progress — subtle banner, last messages visible), rejoining (media path reset — spinner on the player, chat usable), and offline (outbox growing — pending-count badge, local queue). The pending count is the honest signal: sends are safe but not yet acknowledged. Multi-device contract — same messages, same read state, same unread counts — is the bar the UX must meet when reconnect completes ([GetStream](https://getstream.io/blog/chat-application-architecture/)).

**High-frequency rendering.** At 500 chatters and viral bursts, message rate can exceed 100 events per second. Render only visible rows plus a small overscan via list virtualization (web; platform equivalents are `VirtualizedList` and `RecyclerView`), coalesce consecutive messages from the same sender into one bubble, and flush at most one render per animation frame ([patterns.dev](https://www.patterns.dev/vanilla/virtual-lists/)). Decouple the socket handler from the render thread: enqueue, then drain.

**Local caching and offline queue.** Cache the last-known room state so the client renders instantly and reconciles on reconnect. On mobile, SQLite holds channels, messages, members, drafts, and reminders; treat it as disposable and rebuild from the server if unreadable, confirming with the user before a destructive rebuild because actions queued while offline are the one real loss ([GetStream](https://getstream.io/chat/docs/sdk/react-native/v8/basics/encrypting-the-offline-database/)). MMKV is a strong key-value choice: `mmap`-based memory/file synchronization, protobuf encoding, multi-process access, and roughly 50 KB per architecture on Android ([MMKV](https://github.com/Tencent/MMKV)). On web, IndexedDB holds structured state and the Cache API holds assets. Encrypt caches at rest where compliance requires it.

**Time-offset calibration.** Stamp every chat message with a server timestamp, calibrate a local clock offset against an NTP source in client/server mode, and render chat against `serverTime + localOffset`. NTP accuracy is environment-dependent: a few milliseconds at 15-minute intervals, about 1 ms at one-minute intervals, on the order of 100 µs on a lightly loaded 100 Mb/s Ethernet, and up to seconds on intercontinental paths ([ntp.org](https://www.ntp.org/reflib/exec/)). A ±100 ms chat-audio alignment target is a reasonable target to validate, not a measured figure; intercontinental paths dominate the error budget.

**Shared client infrastructure.** Version the event envelope, not the transport: each event carries a version, type, and sequence number; new fields are additive; new types are gated by capability negotiation. Gate new features behind feature flags so a bad client release can be rolled back without an app-store release. Instrument with OpenTelemetry plus a crash reporter and a RUM tool, correlating media and chat traces for a single room with a shared trace context ([OpenTelemetry](https://opentelemetry.io/docs/)). Reuse one transport connection across logical channels where the platform allows. Run independent web and mobile release trains with the versioned protocol as the compatibility contract.

## 8. Identity, Events, and Data

### 8.1 Authentication and authorization

Identity splits into three token classes with different lifetimes and trust boundaries. Collapsing these into one type is the most common way live-room auth designs fail at scale.

| Purpose | Model | Lifetime | Revocation | Rationale |
|---|---|---|---|---|
| User login / REST API | OIDC authorization-code + PKCE; short-lived access token, rotated refresh token | Minutes–hours (access), days (refresh) | Server-side session store; RFC 7009 revocation | Instant revocation and multi-device sync |
| Room join / publish / subscribe / chat | Self-contained JWT capability token with explicit grants | Minutes–hours per session | Short TTL + refresh; do not revoke mid-stream | No server round-trip per connection |
| TURN relay access | HMAC-SHA1/SHA-256 ephemeral credential (TURN REST API) or OAuth 2.0 token | Minutes–hours; re-vend on ICE restart | Expiry + re-vend; stateless shared secret | Bounds leak blast radius |

The JWT capability token is the workhorse. LiveKit access tokens are JWTs carrying participant identity, room name, capabilities (`canPublish`, `canSubscribe`, `canPublishData`), and permissions (`roomJoin`, `roomAdmin`, `canUpdateOwnMetadata`, `hidden`), signed with an API secret ([LiveKit tokens](https://docs.livekit.io/frontends/reference/tokens-grants/)). Issue a distinct token per participant per room with only the grants that role needs: host (`roomJoin`, `canPublish`, `canSubscribe`, `canPublishData`, `roomAdmin`), listener (`roomJoin`, `canSubscribe`, `canPublish: false`), moderator (`roomAdmin`). Never put PII in the token identity or room name — those fields appear in logs and traces; use an opaque UUID mapped to user data in the backend. Shorten the TTL to bound the blast radius; expiration affects only the initial connection, not subsequent reconnects, so a short TTL does not force listeners to re-authenticate mid-stream.

Mobile apps are OAuth 2.0 public clients and cannot keep a client secret confidential; PKCE binds the authorization code to a `code_verifier`/`code_challenge` pair generated on the device, mitigating authorization-code interception ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)). The current OAuth 2.0 Security BCP, RFC 9700, makes PKCE a baseline requirement for public clients; the authorization-code flow, not implicit, is correct for both mobile and browser.

**TURN credential security.** The TURN REST API is widely mis-cited as RFC 7353; RFC 7353 is *Security Requirements for BGP Path Validation* and has nothing to do with TURN ([RFC 7353](https://rfcinfo.com/rfc-7353/)). The actual mechanism is specified by the expired draft `draft-uberti-behave-turn-rest-00` and implemented by coturn's `--use-auth-secret` flag ([draft](https://datatracker.ietf.org/doc/html/draft-uberti-behave-turn-rest-00); [coturn wiki](https://github.com/coturn/coturn/wiki/turnserver)); the IETF-standardized OAuth-based alternative is RFC 7635, exposed by coturn under `--oauth`. The mechanism is stateless: the username encodes the expiry timestamp and optional user id, and the password is `base64(HMAC(secret_key, username))`. The draft recommends a one-day TTL and notes that expiry does not tear down existing allocations, so a client needing new candidates during an ICE restart must re-request credentials. Use a shorter TTL (minutes to a few hours), re-vend on ICE restart, ACL the credential endpoint by IP/Origin/User-Agent/cookie/API key, and treat the shared secret as a KMS-managed credential.

Revocation distinguishes the session tier from the media tier. User-session tokens are opaque and server-stored, so they can be revoked immediately via RFC 7009; refresh tokens rotate on use with reuse detection. Media capability tokens are self-contained JWTs, so true revocation requires server-side state or short TTLs; the practical design is short TTLs plus a session-revocation event that disconnects the WebSocket and blocks re-minting — not a mid-stream media cutoff. Enforce bans and moderator removals at the signaling/chat layer and via SFU `roomAdmin` grants; do not try to revoke a live SRTP flow by token alone.

A user signed in on phone, laptop, and tablet must see the same rooms, read state, and unread counts. Keep one session store (PostgreSQL) as the source of truth for sessions and refresh-token state, mirror active sessions into Redis for fast validation, and push a session-revocation event to all of a user's devices when a token is revoked or a password changes. Require MFA for host, moderator, and admin accounts; listener accounts can stay passwordless/email-based.

For LL-HLS listener auth, a CDN signed URL or signed cookie is validated at the edge and scales with the CDN rather than your servers; the origin should be locked down with Origin Access Control or authenticated origin pull ([AWS](https://aws.amazon.com/blogs/networking-and-content-delivery/secure-and-cost-effective-video-streaming-using-cloudfront-signed-urls/)). The cache-efficiency tradeoff decides the form: a unique signature in the query string of every playlist and segment fragments the cache key and raises origin load, whereas a signed cookie or path-prefix policy covers the whole session while keeping the URL cacheable ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/token-authentication-signed-urls)). For audio, where segments are small and highly reused, prefer signed cookies or path-prefix signing; avoid per-segment query-string tokens. The CDN token does not authenticate the WebSocket chat path — chat must present its own token on the handshake.

| Role | Create/delete room | Publish audio | Subscribe/listen | Send chat | Moderate | Record/egress | Org admin |
|---|---|---|---|---|---|---|---|
| Host | Yes | Yes | Yes | Yes | Yes | Yes | No |
| Co-host | No | Yes | Yes | Yes | Yes | Conditional | No |
| Guest speaker | No | Yes (invite-gated) | Yes | Yes | No | No | No |
| Producer | No | No | Yes | Conditional | Conditional | Yes | No |
| Moderator | No | No | Yes | Yes | Yes | No | No |
| Chatter | No | No | Yes | Yes | No | No | No |
| Listener | No | No | Yes | Conditional | No | No | No |
| Admin | Yes | Yes | Yes | Yes | Yes | Yes | Yes |

*Conditional = granted by room-level ABAC policy or explicit invite.*

Encryption layers:

| Layer | Mechanism | Protects | Key management |
|---|---|---|---|
| User login & API | TLS; OAuth2/OIDC authorization-code + PKCE; JWT access token | Credentials, session token | RFC 7636 PKCE; RFC 9700 BCP; refresh rotation |
| Media transport | DTLS-SRTP | Audio RTP/SRTP | Ephemeral SRTP keys from DTLS |
| Signaling & chat | WSS over TLS 1.3 | Room join, publish, chat | Certificates via Let's Encrypt + cert-manager; HSTS |
| Data channels (if reused) | DTLS | Chat over DataChannel | DTLS-derived |
| At rest | AES-256-GCM envelope encryption | Recordings, chat history | KMS; per-environment separation; rotation |
| TURN relay | HMAC-SHA1/SHA-256 ephemeral credential; or OAuth 2.0 token | Relay access | Shared secret server-side; RFC 7635 alternative |
| CDN listener auth | Signed URL / signed cookie | LL-HLS playlist + segments | RSA-SHA256 or HMAC-SHA256; origin lockdown |
| Token signing | JWT HS256/RS256; verification key via JWKS | Token integrity | LiveKit-style API secret; JWKS key-set mechanism |

### 8.2 Event streaming backbone

The backbone carries two structurally different workloads, so broker selection should be per workload. The realtime path — `chat.message`, `room.state_change`, `moderation.action`, and the fanout triggers they produce — is small-message, latency-sensitive, and order-sensitive within a room but not globally. The analytics/audit path is high-throughput, durable, and replay-oriented. Forcing both onto one broker either over-provisions the realtime path or under-serves the audit path.

| Broker | Latency | Throughput | Persistence | WebSocket integration | Ops complexity | Recommendation |
|---|---|---|---|---|---|---|
| **NATS JetStream** | Low | High; streams + replicas scale delivery ([NATS](https://docs.nats.io/nats-concepts/jetstream/streams)) | File/memory streams; acknowledged publish; `Nats-Msg-Id` dedup; retention policies | Native: `nats-server` accepts WebSocket; same JetStream API ([NATS](https://docs.nats.io/learn/websocket/)) | Low: single binary | **Primary realtime backbone** |
| **Kafka** | Low milliseconds ([Redis tutorial](https://redis.io/tutorials/howtos/solutions/microservices/interservice-communication/)) | Highest; millions of events/sec | Partitioned commit log; topic retention; compaction | Not native; gateway required | High: brokers + metadata | Analytics/audit stream |
| **Redis Streams** | Sub-millisecond | Moderate; single-cluster | Stream log; `XACK` at-least-once | Not native; gateway required | Low: built into existing Redis | Fallback if Redis already runs |
| **Pulsar** | Target to validate | High; tiered storage | BookKeeper-replicated; compaction; subscriptions | Not native; gateway required | High | Deferred to multi-region |
| **RabbitMQ** | — | — | — | Not native | — | Rejected: pub/sub fanout, not work-queue routing |

Partition by room. In Kafka, a keyed record is hashed to a partition, so all messages for a room land in one partition and per-room order is preserved — but a single viral room can overload one partition, and adding partitions invalidates the hash mapping and can break ordering ([Conduktor](https://www.conduktor.io/glossary/kafka-partitioning-strategies-and-best-practices)). Mitigations are composite or salted keys, or partitioning by a shard key with order re-established in the consumer. NATS has no partition count to skew: subjects are the routing primitive, and a hot room is a hot subject additional consumers can serve. This is the main architectural reason NATS is preferred for the realtime path.

Consumer groups and replay differ per broker: Kafka consumer groups split partitions among members, track offsets, and support static membership to avoid rebalances on rolling restarts ([Conduktor](https://www.conduktor.io/glossary/kafka-consumer-groups-explained)); Redis Streams uses `XREADGROUP`/`XACK` with at-least-once delivery; NATS JetStream consumers acknowledge delivery and can replay with limits and interest retention; Pulsar subscriptions retain until acknowledged and redeliver on negative acknowledgment. Cross-region replication is a Phase 3 concern: Kafka via MirrorMaker 2 or MSK Replicator, Pulsar with built-in geo-replication (subscriptions remain local to their cluster), NATS via leaf nodes over WebSocket, Redis Streams single-cluster as described.

Schema evolution uses Protobuf or Avro with a schema registry on analytics/audit topics; default `BACKWARD` compatibility with `BACKWARD_TRANSITIVE` the documented best practice for Protobuf ([Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)). For the NATS path, version the event envelope explicitly — `{schema_version, event_type, room_id, message_id, ts, payload}` — because NATS is schema-agnostic.

A moderation action is published as a `moderation.action` event; fanout workers consume it and push a tombstone to room members over the chat WebSocket. Recall latency must stay below the chat delivery p95/p99, otherwise a tombstone can arrive after newer messages and the client must handle out-of-order recall. Target sub-second to a few seconds, validated against the SLOs.

Backpressure policy: when a room's message rate exceeds gateway capacity, drop or sample ephemeral events (typing, reactions), batch-merge rapid reactions, and never drop `chat.message` or `moderation.action`.

### 8.3 Storage and data access

The data layer is polyglot by access pattern. Chat message history is the only dataset that is simultaneously append-only, write-heavy, and unbounded in volume, so it gets a wide-column store; presence and read state are ephemeral and in-memory; media is blob storage; users, rooms, and membership stay relational ([GetStream](https://getstream.io/blog/chat-application-architecture/)).

| Store | Data | Access pattern | Durability | Scaling |
|---|---|---|---|---|
| PostgreSQL | Users, orgs, rooms, sessions, membership/roles | Relational joins, transactional consistency | WAL, backups, Multi-AZ standby ([AWS RDS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html)) | Vertical + async read replicas; time partitioning |
| Cassandra / ScyllaDB | Chat message history | Append-only, high-write, time-range scans per room | Replication across nodes, tunable consistency ([ScyllaDB](https://www.scylladb.com/learn/apache-cassandra/introduction-to-apache-cassandra/)) | Horizontal |
| Redis | Presence, typing, read cursors, ephemeral state | Very high write frequency, in-memory, TTL | Ephemeral: rebuild from durable store | Cluster key sharding |
| S3 / GCS / Azure Blob / MinIO | Media assets, recordings, VOD segments | Write-once/read-many | Default encryption at rest ([AWS S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html)) | Virtually unlimited; CDN front |
| Search index | Full-text search over chat history | Read-only, derived | Rebuildable | Horizontal |

PostgreSQL owns entities with many-to-many relationships and transactional consistency; roles are enforced through membership rows keyed by `(room_id, user_id)`. For large tables that land in PostgreSQL — audit logs, moderation events, billing events — partition by time: a production case stored 500 million chat messages in a single Postgres table and saw queries slow as the btree index grew; daily partitions on `created_at` restored insert and query performance and made old partitions cheap to detach and archive ([Supabase](https://supabase.com/blog/postgres-dynamic-table-partitioning)). Read replicas handle read-heavy traffic and provide DR; a replica can be promoted to standalone on failure ([AWS RDS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html)).

| Store | Model | Ops burden | Control | Fit for chat history |
|---|---|---|---|---|
| Apache Cassandra | Wide-column, CQL, LSM-tree, tunable consistency | High: repairs, compaction, upgrades | High | Excellent write throughput; proven at inbox scale ([ScyllaDB](https://www.scylladb.com/learn/apache-cassandra/introduction-to-apache-cassandra/)) |
| ScyllaDB | Cassandra-compatible, C++ rewrite, shared-nothing | Medium-high: simpler operability, still self-managed | High | Excellent; predictable low latency |
| DynamoDB | Managed key-value/document | Low: fully managed | Low: 400 KB item limit; key-distribution constraints ([dynobase](https://dynobase.dev/dynamodb-vs-cassandra/)) | Good when managed preference dominates |
| MongoDB | Document store, flexible schemas | Medium: replica set or sharded cluster | Medium | Viable for flexible schemas, weaker fit for sustained append-only writes ([benchANT](https://benchant.com/blog/mongodb-vs-scylladb-comparison)) |

Model chat history as one wide-column table partitioned by room and clustered by a time-sortable message ID, so a room's recent messages are a sequential range scan and old rooms can be tiered to cold storage. Read cursors are per-device, per-room pointers to the last acknowledged message; on reconnect the client sends its cursor and the server returns only messages after it, with idempotent processing and durable checkpoints preventing skips and duplicates ([Prismatic](https://prismatic.io/blog/how-do-i-implement-cursor-based-pagination/)).

Media assets and recordings belong in object storage, not the message store. S3 buckets have default encryption at rest with SSE-KMS and client-side options, and objects are private by default, served through time-limited presigned URLs — the console caps a presigned URL at 12 hours and the CLI/SDK at 7 days ([AWS S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html); [AWS S3 presigned URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ShareObjectPreSignedURL.html)). Put a CDN in front so large objects are cached at the edge.

The message path writes to two places: the durable message store and the fanout broker. Writing to both directly is the dual-write problem — the database transaction can commit while the broker publish fails. The transactional outbox pattern solves this: store the message in an outbox table in the same transaction that updates business entities, and a separate relay publishes outbox rows to the broker. Messages are sent if and only if the transaction commits, and consumers must be idempotent ([microservices.io](https://microservices.io/patterns/data/transactional-outbox.html)). On the broker side, Redis Streams provides the same guarantees natively via consumer groups with `XREADGROUP`/`XACK`. Idempotency keys and per-room sequence numbers close the loop.

Retention is enforced by partitioning and tiering rather than deletes: hot messages stay in the wide-column store for the live window (for example 90 days), older partitions detach and archive to object storage. Full-text search is populated from the message stream as a derived, rebuildable store rather than queried directly from the message store.

## 9. Security, Privacy, and Compliance

Security and compliance here are properties of deployment and data governance, not of the SFU itself. The architecture layers three independent protections — DTLS-SRTP on the media plane, WSS/TLS 1.3 on the signaling/chat plane, and AES-256-GCM with KMS-managed keys at rest — and treats end-to-end encryption as a documented alternative rather than the default, because E2EE removes the server's ability to moderate content and generate push previews ([GetStream](https://getstream.io/blog/chat-application-architecture/)).

WebRTC media is protected by **DTLS-SRTP**, which derives SRTP/SRTCP master keys from a DTLS handshake on the media path, independent of the signaling channel; keys are per-session and per-endpoint ([RFC 5764](https://www.rfc-editor.org/info/rfc5764/)). Because SRTP keys never traverse the signaling server, compromising signaling does not expose live media. **SDES is rejected**: the WebRTC security architecture mandates DTLS-SRTP and forbids SDP security descriptions, which would place SRTP keys in SDP where any signaling observer could read them ([RFC 8827](https://www.rfc-editor.org/rfc/rfc8827)).

| Property | AES-CM (AES_CM_128_HMAC_SHA1_80) | AES-GCM (AEAD_AES_128_GCM / AEAD_AES_256_GCM) |
|---|---|---|
| Standard | SRTP default protection profile ([RFC 5764](https://www.rfc-editor.org/info/rfc5764/)) | [RFC 7714](https://www.rfc-editor.org/info/rfc7714/) |
| Confidentiality + authentication | AES-CTR plus separate HMAC-SHA1 tag | Single AEAD |
| Overhead / CPU | Two passes; higher per-packet cost | Lower overhead and CPU |
| IV/nonce constraint | Standard SRTP IV formation | Strict IV uniqueness; nonce reuse is catastrophic; mandates SSRC-collision prevention |
| Interoperability | Universal WebRTC baseline | Supported by modern browsers/SFUs; not universal |
| Recommendation | Fallback for interop | Prefer AEAD_AES_128_GCM where both endpoints support it |

At rest, use envelope encryption with a managed KMS (AWS KMS, GCP KMS, or HashiCorp Vault) and per-environment key separation; the same KMS holds the TURN shared secret. Recordings, chat history, and metadata all use AES-256-GCM; object-storage SSE and encrypted backups are mandatory.

| Threat | Mitigation | Layer |
|---|---|---|
| Connection/request floods on signaling and chat | WAF rate limiting; Shield Advanced automatic L7 mitigation enforces rate limiting on known DDoS sources | [AWS Shield Advanced](https://docs.aws.amazon.com/waf/latest/developerguide/ddos-advanced-summary-capabilities.html) |
| Network/media-plane (L3/L4) floods | Magic Transit for network defense; Spectrum for TCP/UDP apps; provider capacity claims validated by drill | [Cloudflare DDoS](https://www.cloudflare.com/products/ddos/) |
| TURN relay abuse / bandwidth exhaustion | Ephemeral HMAC credentials; per-user/room quotas; relay metering | [TURN REST API scheme](https://datatracker.ietf.org/doc/html/draft-uberti-behave-turn-rest-00) |
| Chat spam floods / coordinated raids | Per-user and per-channel token-bucket limits; moderator actions | §6.5 |
| Credential/token abuse | Short-lived capability tokens; revocation without dropping live sessions | §8.1 |
| Media-plane UDP amplification | Anycast/geo distribution; SFU-level rate limits; autoscaling signals not dependent on a single hotspot | §5.3, §10 |

HTTPS surfaces are well covered by CDN/WAF; the UDP media plane is the harder case, so media nodes need provider/anycast protection, per-room rate limits, and autoscaling signals.

E2EE is a documented alternative, not the default. MLS (RFC 9420) provides asynchronous group key establishment with forward secrecy and post-compromise security; its delivery service carries ciphertext and cannot read content ([RFC 9420](https://www.rfc-editor.org/info/rfc9420/)). Treat MLS as a roadmap seam: preserve a chat event schema and key-management service that can adopt it without reworking the room model. Enabling E2EE would invalidate synchronous server moderation and push previews, so the decision must be explicit and per-room if offered.

| Data class | Recorded? | Store | Retention (target) | Deletion / export path |
|---|---|---|---|---|
| Audio recordings | Optional, per room | Object storage, AES-256-GCM | Configurable; 90 days default | Automated purge jobs; GDPR erasure/portability |
| Chat messages, reactions, system events | Yes | Hot Redis; warm PostgreSQL/ScyllaDB; cold object storage | 90 days default; audit longer | Per-user deletion/export API; retention job |
| Presence / typing / read cursors | Ephemeral only | In-memory with TTL | Not durable | N/A |
| Moderation and audit logs | Yes | Append-only store + SIEM | 1–2 years (verify) | Legal-hold aware; restricted access |
| Identity, membership, room metadata | Yes | Regional PostgreSQL + cache | Account lifetime | GDPR/CCPA deletion/export |
| Metadata: IP, device, precise geolocation | Minimize | Regional stores | Short (e.g., 30 days) unless legally required | Treat precise geolocation as sensitive PI |

Retention numbers are targets to validate against counsel and the DMCA/counter-notice window.

| Obligation | Applies when | Architectural impact |
|---|---|---|
| GDPR | Processing EU residents' personal data | Data residency, retention minimization, deletion/export pipelines, encryption, DPA with subprocessors ([EUR-Lex](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX:32016R0679)) |
| CCPA/CPRA | California consumers, threshold met | Deletion/export; sensitive PI handling ([California AG](https://oag.ca.gov/privacy/ccpa)) |
| COPPA | Directed to children under 13, or actual knowledge of collecting PI from a child | Age-gating account/chat; anonymous listening without account avoids PI collection ([FTC](https://www.ftc.gov/legal-library/browse/rules/childrens-online-privacy-protection-rule-coppa)) |
| DMCA §512 | Hosting user/third-party content | Registered designated agent; notice-and-takedown + counter-notice/put-back; retain notices ([17 U.S.C. §512](https://www.govinfo.gov/content/pkg/USCODE-2023-title17/html/USCODE-2023-title17-chap5-sec512.htm)) |
| EU DSA | Offering the service to the general public in the EU | Notice-and-action, transparency reporting, crisis response, traceability ([EU DSA](https://digital-strategy.ec.europa.eu/en/policies/digital-services-act)) |
| HIPAA | Processing PHI as covered entity or business associate | Generally not applicable to consumer audio+chat; BAA + stricter controls if clinical use is added |

COPPA minimum compliant design: do not collect personal information from users who indicate they are under 13 (treat such indication as actual knowledge); allow anonymous listening without an account so no PI is collected; require an account plus age gate before chat participation. DMCA §512 requires a registered designated agent, a notice-and-takedown process that responds expeditiously, and a repeat-infringer policy; this is why the moderation subsystem must emit durable, queryable events and audit logs must be append-only.

Embed security into the delivery pipeline: threat modeling per feature, dependency and container scanning, SAST/DAST, mandatory code review, least-privilege service accounts, secrets in Vault/KMS rather than environment variables. Route security-relevant events (auth, token issuance, moderation actions, TURN credential issuance, SFU admin operations) to a SIEM with append-only audit logs and alert on anomalous patterns. Incident response and chaos exercises are covered below.

Evidence limits: the EU DSA primary text was not retrievable, so those obligations are directional and must be confirmed with counsel; COPPA mechanics beyond the FTC rule summary are unverified; vendor DDoS capacity claims (for example Cloudflare's 500 Tbps) are not measured guarantees.

## 10. Operations: Observability, Reliability, and Capacity

### 10.1 Media and chat telemetry

Media and chat must be instrumented as two distinct signal families that share a room/session correlation key. Media SLIs come from client-side `RTCPeerConnection.getStats()` and SFU-internal counters; chat SLIs come from ingestion-to-delivery timestamps on the message path.

The W3C WebRTC Statistics API exposes the counters needed to protect audio SLOs: `packetsLost`, `packetsDiscarded`, `jitter`, `jitterBufferDelay`, `concealedSamples`, `nackCount`, `pliCount`, `firCount`, and the audio-specific `audioLevel` and `totalAudioEnergy` ([W3C WebRTC Statistics](https://www.w3.org/TR/webrtc-stats/)). Operationally, `audioLevel` ranges 0.0–1.0, `totalAudioEnergy` is cumulative and suitable for RMS calculation, and `concealedSamples` counts locally generated samples used to hide packet loss ([rtcstats](https://rtcstats.com/kb/webrtc-stats-reference-page)). On the SFU side, replicate the pattern exposed by mediasoup-based `bbb-webrtc-sfu`: per-node connection counts, per-room session counts, and per-worker CPU/memory, all scrapeable by Prometheus ([metrics docs](https://github.com/bigbluebutton/bbb-webrtc-sfu/blob/development/docs/metrics.md)).

Monitor congestion-control signals too: estimated send bitrate, loss rate, RTT, over-use detector state, and TWCC/REMB feedback counts per participant. A rising over-use detector state with falling estimated bitrate is the leading indicator of congestion-induced degradation.

POLQA requires a reference signal and is not suitable for per-packet monitoring of every stream. Use a two-layer approach: continuous proxy metrics (packet loss, jitter, concealment rate, `audioLevel`/`totalAudioEnergy`) on every session, plus periodic POLQA sampling on recorded or looped reference clips to calibrate the proxy-to-MOS mapping. Vendor-published quality numbers from ad-hoc single-machine tests should not be treated as capacity evidence.

Chat SLIs are measured from message ingestion at the chat service to delivery at each recipient's WebSocket, reported as p50/p95/p99 per room and globally. The trace path spans ingestion → queue → fanout → WebSocket delivery. W3C Trace Context defines the `traceparent` and `tracestate` headers that propagate trace identity across service boundaries; the specification is HTTP-header-oriented, so carry the same trace context in WebSocket frames and message-bus envelopes ([W3C Trace Context](https://www.w3.org/TR/trace-context/)). Correlate media and chat traces by a shared `room_id`/`session_id`.

Sample client media stats at a reduced rate (for example one in N sessions, or per-room aggregates) and retain full-fidelity chat traces, which are lower-volume and higher-diagnostic-value; use tail-based sampling to capture error traces that head-based sampling would drop. Standardize on OpenTelemetry for trace export, with Tempo or Jaeger as the backend ([Grafana](https://grafana.com/blog/intro-to-distributed-tracing-with-tempo-opentelemetry-and-grafana-cloud/)).

### 10.2 Alerting, error budgets, and incident response

Alert on error-budget burn rate rather than raw thresholds, so a single viral room is distinguishable from a platform-wide regression. A 99.9% availability SLO yields approximately 43 minutes of allowable downtime per 30-day month; burn rate is the speed at which that budget is consumed ([nobl9](https://www.nobl9.com/service-level-objectives/error-budget)). Design the media plane to 99.95% where feasible (~22 min/month) and the chat plane to 99.9%, reflecting the difference in failover automation and deployment gating.

Organize dashboards by plane (media vs chat) and scope (global → regional → per-node → per-room) so an on-call engineer can drill from a global SLO burn-down to a single hot room. Use Prometheus for metrics, Grafana for dashboards, Loki/ELK/CloudWatch Logs for aggregation, Sentry for client crash reporting, and Alertmanager routing to PagerDuty/Opsgenie.

On-call response flow: alert fires (burn-rate or hard threshold) → triage scope (one room/tenant, one node, one region, global) → classify (single-room failure vs platform-wide) → mitigate (drain/restart the affected SFU node, trigger listener ICE restart or migrate the room; shed chat load, replay from the message log, shed ephemeral presence) → communicate severity → recover and verify against dashboards, then postmortem with error-budget accounting.

Run failover drills at least quarterly for both tiers. For the SFU tier: kill a media node mid-room and verify listener reconnect time and audio gap; verify room pinning and cascading behavior. For the chat tier: terminate a WebSocket gateway node and verify connection migration and message replay from the last cursor; verify fanout completeness after failover. Inject region loss, broker partition, and TURN relay failure in game days to validate graceful degradation. Measure drills against the SLOs, not against "did it survive."

### 10.3 Capacity model and load testing

Two constraints shape every scaling decision. First, an SFU room must fit within a single node: while the SFU scales across nodes, "each room must fit within a single node" ([LiveKit Benchmarking](https://docs.livekit.io/transport/self-hosting/benchmark/)). Second, chat fanout amplification dominates the chat tier: 500 chatters in a 5,000-listener room implies up to 2.5 million deliveries per second if every message is written to every listener.

| Component | Metric | Model / assumption | Verification |
|---|---|---|---|
| SFU media | Listeners per node | Room fits in one node; benchmark config 10 publishers, 1,000 subscribers, 3 kbps avg, 16-core node ([LiveKit Benchmarking](https://docs.livekit.io/transport/self-hosting/benchmark/)) | `lk load-test`; CPU/packet-loss profiling |
| SFU media | Publishers per room | 1–3 speakers at launch; benchmark uses 10 | Same |
| Chat gateway | Connections per node | OS file-descriptor and memory bound; Phoenix reached 2M on 4-core/15 GB in 2015 with `ulimit`/`fs.file-max` tuning ([Phoenix](https://www.phoenixframework.org/blog/the-road-to-2-million-websocket-connections)) | k6 WebSocket load; OS tuning |
| Chat gateway | Fanout amplification | 500 chatters × 5,000 listeners = 2.5M deliveries/s per room at 1 msg/s per chatter | k6 fanout scenario |
| Broker | Message throughput | 500 msg/s/room × 50 rooms = 25k msg/s raw; fanout copies multiply | Consumer lag |
| Storage | Chat history growth | Assumed 200 B/msg; rate × retention | Growth projection |
| TURN/egress | Relay and egress bandwidth | Relay fraction × relay cost; egress $/GB | TURN measurement; rate card |

The 5,000-listener launch target is 5× the benchmark's subscriber count, so a single commodity node is unlikely to suffice; the architecture must support a larger node, SFU cascading, or CDN/LL-HLS offload for listeners beyond the SFU ceiling. mediasoup's standard deployment pattern is one worker per CPU core, so node capacity scales with core count; treat listeners-per-core as a target to validate. Managed plans impose per-room ceilings — LiveKit Cloud's Build plan caps a project at 100 participants — so a 5,000-listener room requires self-hosted or enterprise deployment ([LiveKit quotas](https://docs.livekit.io/deploy/admin/quotas-and-limits/)).

Chat capacity risk is fanout amplification, not connection count. At the launch caps, a single message in a 5,000-listener room generates 5,000 deliveries; at a modest 10 messages/s across the room, that is 50,000 deliveries/s per room. Fan-out-on-write at this scale is impractical; a hybrid strategy is required. The broker sees raw messages, not fanout copies, so partition throughput is 25k msg/s across 50 rooms — well within a modest cluster, but only if fanout is not performed inside the broker.

Chat history grows at (messages/s) × (average message size) × (retention). Assuming 200 B/message and a conservative 0.2 msg/s per chatter across 500 chatters and 50 rooms, raw ingest is ~1 MB/s, or ~86 GB/day; a 90-day retention policy implies ~7.8 TB. Refine with real instrumentation.

| Target | Value | Implied capacity |
|---|---|---|
| Listeners per room | 5,000 | 1 room per SFU node; 5× the benchmark's 1,000-subscriber config |
| Chatters per room | 500 | 500 msg/s peak at 1 msg/s each; 2.5M deliveries/s at 5,000 listeners |
| Live rooms | 50 | 250k concurrent listeners and 25k concurrent chatters if all rooms at cap |
| Regions | 2 | 2× pools; cross-region replication (Phase 3) |
| DAU | 50k | Aggregate concurrency = DAU × concurrency factor (to measure) |

Use k6 for chat and API load — its WebSocket module implements the browser WebSocket API with a global event loop, so one VU can hold multiple concurrent connections ([k6 WebSockets](https://grafana.com/docs/k6/latest/javascript-api/k6-websockets/)) — and LiveKit's `lk load-test` for media, which simulates publishers and subscribers and supports audio-only scenarios ([LiveKit Benchmarking](https://docs.livekit.io/transport/self-hosting/benchmark/)). Three scenarios are required: sustained load at target concurrency for 30+ minutes; a burst of 10k listeners joining in 30 s with 500 simultaneous chatters; and a viral room pushed beyond the provisioned tier to verify hot-room handling and CDN offload or admission control.

### 10.4 Autoscaling, hot rooms, and backpressure

| Tier | Signal | Mechanism | Notes |
|---|---|---|---|
| Stateless API/chat processors | CPU, memory | HPA (VPA for memory-bound) | Fast, reversible |
| Broker consumers | Consumer lag | KEDA `lagThreshold`; replica count capped by partitions ([KEDA](https://keda.sh/docs/2.21/scalers/apache-kafka-go/)) | Lag-driven |
| Stateful SFU pool | Room count, CPU, packet loss | Node pool autoscaler; room pinning | Scale the pool, not the room; single-node room constraint |
| Stateful chat gateway | Connection count, memory | Consistent-hashing rebalance; drain | Graceful drain required |

Because a room fits in one node, you cannot scale a single room horizontally; you scale the node pool and route new rooms to new nodes. LiveKit's self-hosted deployment guidance uses a worker pool with `load_fnc` and `load_threshold` (default CPU utilization 0.7), scaling up at a lower threshold than load shedding, with `stabilizationWindowSeconds` and `terminationGracePeriodSeconds` to drain gracefully ([LiveKit deployments](https://docs.livekit.io/deploy/custom/deployments/)).

Handle a viral room without dropping the stream, in order of preference: (1) offload listeners beyond the SFU ceiling to CDN/LL-HLS — latency increases to 2–8 s, acceptable for listeners but not active speakers; (2) pin the room to a larger node; (3) cascade SFUs; (4) cap the room and queue new listeners via admission control. On the chat side, a viral room concentrates messages in one partition if partitioning by `room_id`; detection and mitigation include partition-level monitoring, leader/replica rebalancing, partition expansion, and key salting — but salting breaks per-key ordering unless a reconciliation layer is added ([AutoMQ](https://www.automq.com/blog/hot-partitions-in-kafka-detection-mitigation-architecture-choices)).

When a room's message rate exceeds gateway capacity, degrade rather than collapse. The Google SRE Book recommends serving degraded responses, enforcing per-customer quotas, and adaptive throttling so clients self-regulate based on rejection rate ([Google SRE Book](https://sre.google/sre-book/handling-overload/)):

| Lever | Behavior | When to use |
|---|---|---|
| Admission control | Reject new connections/jobs at a load threshold | Sustained overload; protects existing sessions |
| Buffering | Durable queue absorbs bursts; lag drives scaling | Transient spikes |
| Degraded delivery | Sample messages, drop reactions/typing, batch-merge | Extreme overload; preserve core chat |
| Client-side throttling | Clients back off based on rejection rate | Prevents retry storms |
| Load shedding | Drop oldest or lowest-priority messages | Queue overflow |

The upper-bound stress scenarios — 50,000 listeners per room and 1M concurrent connections — are explicitly out of launch scope and are used only to test whether the CDN offload path works, whether the chat tier rebalances without message loss, and whether autoscaling signals fire correctly.

## 11. Cost Model and Build-vs-Buy

At launch scale, media delivery — not signaling, compute, or storage — dominates the infrastructure bill, and the unit of account matters more than the protocol. Per-minute managed pricing costs roughly **$59–$240 per 1,000 listener-hours** for audio-only listening, while raw CDN egress for the same 64 kbps audio costs **$1–$25 per 1,000 listener-hours** depending on CDN. That 5–25× gap is the core economic argument for self-hosted media with per-GB CDN delivery; it reverses only when fully-loaded SRE labor is added to the self-hosted side. On infrastructure alone, self-hosting wins above a few hundred thousand listener-hours/month because per-GB egress is so much cheaper than per-minute metering. ### Cost-optimization levers, ranked by impact

1. **CDN selection for per-GB delivery.** At 100 TB/month, published rates range from $415 to $6,965 for transfer alone — a 16.8× spread ([BlazingCDN](https://blazingcdn.com/vs/)). For audio LL-HLS, where segments are small and cache efficiency is high, a cheap CDN is the single largest lever.
2. **Opus passthrough (route-don't-transcode).** Forwarding Opus unchanged avoids transcoding CPU and licensing; transcode once at the protocol boundary only.
3. **LL-HLS for large audiences, WebRTC for interactive.** LL-HLS egress is up to 50× cheaper than managed per-minute delivery at the crossover.
4. **Spot/Preemptible instances for stateless transcoding and egress workers.** SFU nodes are stateful and stay on-demand or reserved; transcoding workers are stateless and can absorb interruption.
5. **CDN cache hit ratio.** Playlists need short TTLs (1–2 s), segments can cache for 60–300 s; a high hit ratio directly reduces origin load and egress.
6. **P2P offload.** Deferred optimization: it trades away moderation, recording, and guaranteed delivery.

Over-provisioning for availability is expensive: a single-region SFU tier at N+1 already costs 33% above minimum; multi-AZ doubles it; burst headroom for a viral room can double it again. Managed services absorb this implicitly — you pay per viewer-hour, not for idle SFU capacity.

TURN relay is the hidden cost. The planning assumption is 15–20% of sessions falling back to TURN (vendor-claimed, to validate). At 14.4 TB/month, that is 2.2–2.9 TB relayed; self-hosted TURN bandwidth at $0.085/GB is $184–$248/month, while managed TURN at published overage rates would be several times that. Measure the relay fraction with a load test rather than assuming it. Cross-region replication in Phase 3 doubles the stateful tier and adds inter-region data transfer; budget this explicitly.

**Recommended hybrid:** self-host the SFU and interactive WebRTC tier (where sub-second latency and Opus passthrough justify the ops burden) and use CDN/LL-HLS for broadcast fanout to large audiences; use a managed service only for the first 6–12 months or for burst absorption if SRE capacity is constrained. This keeps the irreversible media-server decision reversible while capturing the per-GB cost advantage at scale.

Cost tooling should be in place from Phase 1: Kubecost or AWS Cost Explorer for cloud resources, plus per-room cost attribution tags so a viral room's egress and SFU cost is visible before it surprises the monthly bill.

## 12. Technology Decisions, ADRs, and Phased Delivery

### 12.1 Decision matrix

Rejected alternatives and why: video-first SFUs are tuned for conferencing, not audio-only fanout; Janus is a strong C gateway but GPLv3 with a large configuration surface, held as a fallback for telephony/RTSP bridging; MoQ is still a working-group draft with a December 2026 milestone and a preliminary WebTransport substrate ([IETF](https://datatracker.ietf.org/doc/draft-ietf-moq-transport/); [W3C](https://www.w3.org/TR/webtransport/)); XMPP and Matrix add federation overhead a room-scoped chat path does not need; SDES is rejected in favor of DTLS-SRTP.

The SFU choice is the dominant constraint: picking LiveKit commits the client SDKs, the egress/recording path, and the room/track/participant model, whereas mediasoup would commit the team to building signaling, TURN, and orchestration itself. The delivery-protocol choice sets the latency tier and therefore the chat-audio synchronization strategy: WebRTC rooms align tightly, while LL-HLS rooms inherit a 2–8 s offset.

### 12.2 ADR summary

The media server is the most consequential decision because it constrains client SDKs, the recording/egress seam needed for deferred VOD, and the operating model. The exit strategy is to treat LiveKit Cloud as optional and self-host the identical Apache 2.0 server; because ingest is WHIP and delivery is WebRTC, a different SFU can be substituted behind the signaling/room abstraction. Migration cost is nontrivial — re-implementing the room/session layer and exchanging client SDKs — measured in weeks to months, not days.

### 12.3 Phased delivery plan

The smallest shippable end-to-end flow is a single-region WebRTC audio path (WHIP ingest → SFU → listener) plus a WebSocket chat path (send → sequence → fanout → deliver) with presence. The core flow is not the schedule risk; the hardening around it is. Production analysis is blunt: the core message flow takes weeks to build, but mobile reconnection, group fanout, and multi-device sync realistically take years to production-harden ([GetStream](https://getstream.io/blog/chat-application-architecture/)). Front-load spikes on the highest-uncertainty items, ship a deliberately thin MVP, and gate every later phase on measured evidence.

| Phase | Scope | Milestone | Exit criteria |
|---|---|---|---|
| **0 · Discovery and spikes** (2–4 wk target) | De-risk critical path: SFU audio-only throughput per node; TURN fallback rate and cost; iOS Safari audio/autoplay/background; chat fanout and ordering under reconnect; active-speaker detection; WHIP ingest from browser and mobile; sign ADRs | Spike reports + signed ADRs | SFU sustains target listener count at acceptable CPU using add-until-saturation load testing; TURN fallback measured; iOS audio path proven on device; chat fanout spike passes |
| **1 · MVP** (4–6 wk target) | Single region: WebRTC one-to-many audio + WebSocket chat + presence + room create/join; browser client + one mobile platform; WHIP ingest; basic block/mute. No recording, VOD, reactions, ML moderation, multi-region, or video | End-to-end demo → limited beta | 5k listeners/room and 500 chatters sustained under load; chat p95 under target; room lifecycle stable |
| **2 · Scale** (8–12 wk target) | Horizontal scaling of SFU and chat tiers; autoscaling on custom metrics; TURN pool; observability and SLO dashboards; second mobile platform; reactions/threads; rate limiting | Production-ready at launch targets (50 rooms, 50k DAU) | Headroom above targets proven; autoscaling verified; second platform ships |
| **3 · Multi-region** | Geo-DNS/anycast routing; regional SFU pools; cross-region chat replication; per-region TURN; data residency; failover drills | Active-active or primary + failover across 2 regions | Failover time target met; chat ordering preserved; residency satisfied |
| **4 · Recording/VOD + advanced moderation** | Egress to object storage; HLS/CMAF VOD; loudness normalization; transcription/diarization seam; slow-mode/follow-only/subscribers-only; ML moderation | Recording + VOD live; advanced moderation live | Recording integrity verified; VOD latency target met; moderation precision/recall acceptable |
| **5 · Hardening** | Reconnection, multi-device sync, fanout at scale; chaos engineering; failover drills; cost optimization; security/compliance audit | 99.9% availability demonstrated; error-budget policy; runbooks | SLOs met over burn-in; incident response tested |

The "2 regions" launch target is an architecture headroom requirement validated by design review and a failover drill, not a Phase 1 deliverable. Run media and chat as parallel workstreams against a shared room/session identity contract frozen in Phase 0, so the teams move independently.

Each phase's exit criteria are its go/no-go gate, measured by load-test results, chat delivery percentiles, error-budget consumption, and incident frequency. Published SFU benchmarks are a single point in time and do not measure end-to-end experience or ease of development, so go/no-go must rest on your own load tests. Use an add-until-saturation method: add participants until no more can join a room and treat that as the capacity ceiling ([OpenVidu](https://openvidu.io/latest/docs/self-hosting/production-ready/performance/)). Spike on the same media-server edition and configuration you intend to ship, so playback capability, TURN behavior, and autoscaling are proven on the real artifact.

Phase 1 needs roughly 3–4 backend/media engineers, 2 web engineers, 2 mobile engineers (one platform deep, one cross-training), 1 SRE, 1 designer, and 1 QA. The scarcest skill is WebRTC/media expertise; the next gaps are SRE experience with stateful media nodes and mobile audio/background behavior. Treat the Phase 0 SFU spike as a make-or-break hiring signal: if the team cannot staff it, reconsider the self-host-vs-managed decision before Phase 1.

### 13.2 Most consequential risks

Three risks could invalidate the architecture rather than degrade it. First, the SFU capacity ceiling: mediasoup documents roughly 500 consumers per worker, and consumers — not participants — are the right metric ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)). That number sizes the node pool and sets the crossover to LL-HLS. It must be measured, not cited from the CoSMo study, which tests video conferencing with the KITE engine and does not model one-to-many audio forwarding ([CoSMo study](https://mediasoup.org/resources/CoSMo_ComparativeStudyOfWebrtcOpenSourceSfusForVideoConferencing.pdf)). Second, TURN cost: TURN relays all media and is forced by symmetric NAT, carrier-grade NAT on mobile networks, and corporate firewalls that block UDP; the relay fraction, not the session count, is the cost driver and must be measured under load ([bloggeek](https://bloggeek.me/webrtcglossary/turn/)). Third, iOS Safari audio behavior: iOS has required a user gesture for media playback and has historically suspended `AudioContext` when the window is backgrounded, a behavior Chrome and Firefox do not share ([WebKit](https://webkit.org/blog/6784/new-video-policies-for-ios/); [WebKit bug 231105](https://bugs.webkit.org/show_bug.cgi?id=231105)). Current WebRTC-specific behavior across iOS versions remains a validation spike rather than a settled fact.

Chat fanout and moderation are the highest-complexity subsystem risks. Presence alone generates a write on every connect, disconnect, and heartbeat, making it orders of magnitude more write-heavy than messages, and mobile reconnection, group fanout, and multi-device sync realistically take years to production-harden ([GetStream](https://getstream.io/blog/chat-application-architecture/)). E2EE is the documented alternative precisely because it prevents server-side moderation and push previews.

### 13.4 Open questions and exit strategy

Open questions for Phase 0: the actual relay fraction and TURN cost; the real SFU consumer ceiling per worker for audio-only forwarding; iOS Safari WebRTC audio behavior across versions and whether the native app is required for background listening; the chat fanout strategy at launch scale and where the switch threshold to fan-out-on-read lies; the moderation liability model, audit retention, and DMCA §512 process; vendor lock-in exposure and migration cost to self-host; whether MoQ is a roadmap item or a watching brief; and whether music-mode audio justifies its bitrate and data premium.

The exit strategy for open-source components is an adapter boundary, not a rewrite. Signaling and the room/media model are ours, and the SFU is a swappable implementation behind that interface; mediasoup and LiveKit both implement the RFC 7667 SFU topology, so the fallback is to migrate rooms to the other SFU or bridge the affected audience to LL-HLS ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/sfu-comparison-mediasoup-janus-livekit-jitsi-pion)). License terms are a trigger: Janus is GPLv3 and mediasoup is ISC, so a relicensing event is an explicit review trigger. The chat broker sits behind the message service and is interchangeable; the message schema and room identity are the stable seam. For managed services, wrap signaling behind our own interface from day one, because proprietary signaling, token formats, and SDK bindings are what make an exit a real project; if a managed lane is adopted, keep it to one lane and retain a self-host fallback for the rest.

### Consolidated evidence limits

- Every capacity, latency, and cost figure is a planning target to validate under load; no load-test data exists yet.
- The CoSMo SFU comparison is video-conferencing-centric and directional for audio-only forwarding.
- The listener-to-chatter ratio has no authoritative primary benchmark; it is an explicit assumption to measure.
- Vendor-published pricing and capacity numbers (including 100ms, Dolby.io, and some TURN rates) were not fully retrievable and remain directional.
- Several primary documents were inaccessible during research (Apple HLS authoring specification, EU DSA text, full COPPA eCFR text, parts of LiveKit Agents diarization documentation); related claims are supported by adjacent primary sources and should be confirmed before commitment.
- Current iOS Safari WebRTC autoplay and background behavior across versions remains a device-validation spike.

# Distributed Audio Streaming Platform with Live Chat: Technical Proposal

**Status:** Draft for engineering review
**Audience:** Senior/staff software engineers, platform architects, engineering management
**Scope:** End-to-end design for a one-to-many live audio streaming product with a real-time text chat sidecar, targeting web and mobile (iOS, Android), with an optional interactive sub-room tier.

---

## 1. Executive Summary

The system delivers live and on-demand audio to large audiences over commodity HTTP infrastructure, with a real-time text chat plane that operates independently of the audio path. The architecture is built as three independent planes — media, chat, and control/data — each with its own SLA, scaling profile, and failure domain.

The recommended technology stack centers on a small set of mature, well-understood standards:

- **Audio distribution:** Apple Low-Latency HLS (LL-HLS) packaged as CMAF/fMP4 with an AAC-LC bitrate ladder, served through a multi-CDN with HTTP/2.
- **Audio ingest:** SRT for remote contributors (jitter-tolerant, FEC-protected), RTMP/SRT for browser-based broadcaster tooling, and WHIP for WebRTC-based contribution.
- **Optional interactive tier:** LiveKit (Apache 2.0, Go) as the WebRTC SFU, used only for hosts, co-hosts, and small "green room" sub-rooms where sub-second latency is a product requirement, not a marketing claim.
- **Chat transport:** WebSocket (Socket.IO 4.x with the Redis adapter) as the production default, with WebTransport planned as a forward path.
- **Data backbone:** Redis for hot presence and ephemeral chat fan-out, Kafka for durable event sourcing and analytics, Cassandra/ScyllaDB (or partitioned PostgreSQL) for chat history, PostgreSQL for users/billing/rooms, Cloudflare R2 (S3-compatible) for audio VOD storage and chat attachments.
- **Mobile:** React Native (TypeScript) for the shell UI and background services, with native modules (AVPlayer on iOS, Media3/ExoPlayer on Android) for playback. Background playback is a first-class requirement driven by OS policy on iOS 17/18 and Android 14+.
- **Identity, security, access control:** OAuth2/OIDC at the edge, short-lived signed URLs for HLS manifests and segments, AES-128 HLS encryption for free/SaaS tiers, and Multi-DRM (FairPlay/Widevine/PlayReady via CMAF Common Encryption) only where premium entitlements demand it.
- **Observability:** OpenTelemetry for instrumentation, Prometheus + Grafana Mimir for metrics, Loki for logs, Tempo for traces — all behind a single Grafana UI. Day-one investment, not a phase-two project.

The single most consequential decision is to use **LL-HLS over a multi-CDN for the audience plane** and to reserve WebRTC for the narrow interactive tier. This mirrors the architecture choices documented by Stream [1], Mux [2], Twitch-style broadcast systems, and major podcasting platforms. Doing the opposite — running everything over WebRTC, or running everything over plain HLS — leads to either unsustainable CDN cost (WebRTC) or an unacceptable live experience (plain HLS at 10–30s latency).

## 2. Goals, Non-Goals, and Assumptions

### 2.1 Goals

- Deliver live audio to **10,000+ concurrent listeners per broadcast** at < 5 seconds glass-to-glass latency on 4G/LTE, with P95 audio startup time under 2.5s.
- Support an optional **interactive sub-room tier** of up to 200 simultaneous speakers and 5,000 listeners with sub-second latency, leveraging WebRTC only where it pays for itself.
- Carry a real-time **text chat plane** with end-to-end P99 message delivery under 500ms, presence, typing indicators, and read receipts.
- Operate the platform on **browser (Chromium, Firefox, Safari) and mobile (iOS 17/18, Android 14+)** with first-class background audio playback.
- Reach a **99.9% monthly availability** with documented degradation behavior under regional CDN outages.
- Make every plane **independently deployable and scalable** so that a chat incident cannot take the audio plane down, and vice versa.

### 2.2 Non-Goals (this proposal)

- Recommendation, personalization, or content-discovery ML.
- Royalty accounting, payment processing, subscriptions, or tax/VAT handling.
- Carrier-grade PSTN/SIP dial-in for listeners.
- Multi-region active-active database replication. We assume a primary region with edge delivery via CDN; cross-region is a follow-up.
- Full WCAG 2.2 accessibility audit. The chat UI and player must meet the basics, but a comprehensive accessibility pass is its own work item.
- Native smart-TV applications. The web build is the smart-TV target for v1; native TV apps are a follow-up.

### 2.3 Working Assumptions

- The team has Kubernetes experience and a multi-AZ cloud footprint (AWS, GCP, or similar).
- A **multi-CDN relationship** is in place or can be negotiated; we do not assume a single vendor.
- The product surface is **audio first** — there is no synchronous video track for the audience plane in v1. (Video is included only inside the optional interactive sub-room tier, which is a separate scope.)
- Mobile distribution is through the **Apple App Store and Google Play**, so we operate within their background-execution and DRM policies.

## 3. System Overview: Three-Plane Model

The system is modeled as three independent planes. Each plane has its own ingress, runtime, datastore, and SLA. Cross-plane interaction happens only through well-defined, idempotent APIs or asynchronous events.

```
                      ┌────────────────────────────────────────────┐
                      │                Control Plane                │
                      │  Auth (OIDC), config, feature flags,        │
                      │  room/session lifecycle, admin APIs         │
                      └────────┬───────────────────────┬────────────┘
                               │                       │
        ┌──────────────────────┼───────────────────────┼──────────────────────┐
        │                      │                       │                      │
┌───────▼─────────┐    ┌───────▼──────────┐    ┌──────▼───────────┐
│   Media Plane   │    │    Chat Plane     │    │  Data/Event Plane │
│                 │    │                   │    │                   │
│ Ingest (SRT/    │    │ WS gateway        │    │ PostgreSQL        │
│  WHIP/RTMP)     │    │ (Socket.IO)       │    │ (users, rooms)    │
│       │         │    │       │           │    │                   │
│ Transcoder      │    │ Redis pub/sub     │    │ Kafka             │
│ (FFmpeg/        │    │ (cross-node       │    │ (events, audit,   │
│  look-ahead)    │    │  fan-out)         │    │  analytics)       │
│       │         │    │       │           │    │                   │
│ LL-HLS packager │    │ Cassandra/ScyllaDB│    │ R2 / S3           │
│ (CMAF/fMP4)     │    │ (chat history)    │    │ (audio, exports)  │
│       │         │    │                   │    │                   │
│ Multi-CDN edge  │    │ Presence (Redis)  │    │                   │
└─────────────────┘    └───────────────────┘    └───────────────────┘
        ▲                       ▲
        │                       │
        └──────────── clients (web, iOS, Android) ────────────────┘
```

The three planes are not modules in a monolith; they are **separate services with separate deploys, separate datastores, and separate on-call rotations**. A failure in the chat plane must not stall the media plane's CDN, and a transcoder crash must not sever chat WebSocket connections.

## 4. Audio Streaming Pipeline

### 4.1 Ingest

The ingest tier accepts remote audio from two distinct sources, with different reliability profiles.

| Source | Protocol | Why | Trade-off |
|---|---|---|---|
| Remote studio / field contributor | **SRT (Secure Reliable Transport)** | SRT adds ARQ with a fixed-latency jitter window over UDP, with AES-128 encryption. It is the de facto standard for "first-mile" contribution because it survives 20%+ packet loss without dropping frames [3]. | Requires a small SRT listener (e.g., `srt-live-server` or FFmpeg's SRT demuxer) at the origin; not a browser-native protocol. |
| Browser-based broadcaster (Web) | **WHIP (WebRTC-HTTP Ingestion Protocol)** | WHIP is the IETF-draft standard that wraps WebRTC's SDP/ICE exchange in a single HTTP POST. OBS 26+ ships native WHIP support, which means a contributor can broadcast from a browser tab without custom plugins. | Adds a small WebRTC gateway at the origin; this gateway is the same LiveKit or mediasoup process we already run for the interactive tier (see §5.2), so we get the contribution endpoint for free. |
| Legacy encoders (hardware boxes, OBS) | **RTMP** | RTMP remains the lingua franca of broadcast tooling. Most commercial encoders, OBS, and mobile broadcast SDKs default to RTMP. | RTMP over TCP has head-of-line blocking on lossy links; we treat it as a fallback for the contribution edge. |

All three paths terminate at the **packager origin**, which converts the inbound transport into a single internal PCM/AAC representation. This is the only place the pipeline touches the network; everything below this point is internal to the origin VPC.

### 4.2 Transcoding and Packaging

The packager origin runs a per-broadcast transcode cluster. For audio-only, the work is light: a fixed-bitrate AAC-LC ladder is sufficient, and a single 16-core node can fan out 500+ live events concurrently.

**Codec choice for the distribution ladder:** AAC-LC.

Opus is technically the better codec at low bitrates — perceptually transparent at 64 kbps stereo, where AAC-LC needs 96–128 kbps [4]. But Opus's container support in native HLS players is uneven: Apple Podcasts still does not support Opus as of 2024, and some smart-TV and in-vehicle HLS players ship only AAC support [5]. AAC-LC is universally hardware-decoded on iOS (AVPlayer), Android (Media3/ExoPlayer), and all desktop browsers, and is the safe default.

**Audio ABR ladder (recommended starting point):**

| Variant | Bitrate | Sample rate | Channels | Use case |
|---|---|---|---|---|
| Audio-LOW | 32 kbps AAC-LC | 44.1 kHz | mono | 2G/3G fallback, low data-allowance regions |
| Audio-MID | 64 kbps AAC-LC | 44.1 kHz | stereo | Default on cellular |
| Audio-HIGH | 96 kbps AAC-LC | 48 kHz | stereo | Wi-Fi, default on broadband |
| Audio-HD | 128 kbps AAC-LC | 48 kHz | stereo | Premium / studio-quality tier |

The bitrate ladder is encoded once per live event, with a **fixed 1-second segment duration** and a **2-second keyframe interval** (audio-only has no real GOP concept, but the segment boundary serves the same role for LL-HLS partial-segment alignment). The packager emits CMAF/fMP4 with the LL-HLS-required tags: `#EXT-X-PART`, `#EXT-X-PRELOAD-HINT`, and the `_HLS_msn` / `_HLS_part` delivery directives [6].

**Why LL-HLS, not plain HLS:** standard HLS with 6-second segments produces 10–30s glass-to-glass latency, which is unacceptable for live broadcasts where audiences expect feedback loops (chat, polls, call-to-action). LL-HLS uses HTTP/2 chunked transfer of 200ms partial segments to reach 2–5 seconds end-to-end while keeping all the cache-friendliness of HTTP [6]. LL-HLS is also backward-compatible: a non-LL-HLS player simply ignores the partial-segment tags and falls back to standard HLS playback at higher latency.

### 4.3 Distribution: Multi-CDN

The CDN is the dominant cost line and the dominant availability lever. We use a **multi-CDN** from day one.

**Recommended v1 vendor mix:** Cloudflare as primary, plus a second vendor (Fastly or Akamai) for failover and edge-function diversity. The combination is not arbitrary:

- **Cloudflare** operates 330+ data centers across 120+ countries, with 500+ Tbps of provisioned capacity, and serves 81M HTTP requests per second on average [7]. For audio-only segments, this is more than enough headroom; the same edge also gives us bot management, WAF, and the Workers edge compute platform if we need token-validation at the edge.
- **Fastly** is a strong secondary because of its edge-compute model (Compute@Edge) and its Varnish heritage, which gives very fine-grained cache-key control. For LL-HLS this matters: the LL-HLS player sends `_HLS_msn=` and `_HLS_part=` query parameters that must be in the cache key, otherwise partial-segment requests are mis-routed [8].
- **Akamai** is the conventional backup choice for media-heavy customers and offers mature adaptive media delivery features. We keep it in the rotation only if commercial terms are favorable.

**Why multi-CDN from day one, not later:** a single-CDN architecture creates a single point of failure that has, repeatedly, taken large portions of the open web offline. With multi-CDN, the origin uses **DNS-based traffic steering** (e.g., AWS Route 53 with health checks, or NS1) to send each listener to the nearest healthy POP. The cost overhead is ~10–20% versus a single-vendor commit, in exchange for an order-of-magnitude improvement in blast radius.

**CDN cache key design for LL-HLS:** the cache key must include the request path, the `_HLS_msn` and `_HLS_part` query parameters, and (for VOD) the user-agent class to allow differentiated manifests. The cache key must **not** include the signed-URL signature; otherwise the cache hit ratio collapses. Signed URLs are validated at the edge via a Cloudflare Worker or Fastly Compute@Edge hook that strips the signature before the cache lookup, then re-validates the user's entitlement.

### 4.4 Playback Layer

| Client | Player | Why |
|---|---|---|
| **Web (Safari)** | Native `HTMLMediaElement` + HLS | Safari ships native LL-HLS support since iOS 14 / macOS Big Sur [9]. No JS player required. |
| **Web (Chrome, Firefox, Edge)** | `hls.js` 1.4+ with `lowLatencyMode: true` | hls.js has supported LL-HLS since v1.0 (April 2021) and is the de facto player for non-Safari browsers [10]. |
| **iOS / iPadOS** | Native `AVPlayer` with `AVPlayerItem` configured for HLS | Native LL-HLS support since iOS 14; integrates directly with `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter` for lock-screen and Control Center controls. |
| **Android** | `androidx.media3:media3-exoplayer` (Media3, the successor to legacy ExoPlayer) | Media3 ships LL-HLS support natively and is the Google-recommended player for streaming [11]. |
| **React Native (shared shell)** | `react-native-video` 6.x (wraps AVPlayer / Media3) plus `react-native-track-player` for the audio-only background/lock-screen path | `react-native-track-player` exposes the right iOS `MPRemoteCommandCenter` and Android `MediaSession` hooks for background audio. |

**Background playback is a first-class requirement, not an afterthought.** Both iOS and Android have aggressive process-kill policies that terminate media playback unless the app declares the right background capabilities.

- **iOS 17/18** requires the `UIBackgroundModes` capability key with the value `audio`, an active `AVAudioSession` configured with category `.playback`, and the correct `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter` setup for lock-screen and Control Center controls [12]. Apps that declare the audio background mode but cannot demonstrate an audible feature are rejected under App Review guideline 2.5.4 — so the background UI (lock screen, Now Playing, AirPlay routing) must be visible and testable.
- **Android 14+ (API 34+)** requires the foreground service to declare `android:foregroundServiceType="mediaPlayback"` in the manifest, the `FOREGROUND_SERVICE_MEDIA_PLAYBACK` permission, and the matching `FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` flag passed to `startForeground()` [13]. From **Android 15**, the OS additionally refuses to launch a media-playback foreground service from a `BOOT_COMPLETED` broadcast receiver, so any auto-restart logic must be reworked.
- **Audio focus** (Android) and **AVAudioSession interruption** notifications (iOS) must be wired to pause/resume the player; otherwise another app's audio will fight yours and the user experience degrades silently.

## 5. Live Chat Subsystem

The chat subsystem is a real-time message bus with persistence, presence, and push-notification fan-out. It is built as four cooperating services, each of which can fail independently without taking the others down.

### 5.1 WebSocket Gateway

**Default transport: WebSocket via Socket.IO 4.x.** Socket.IO provides automatic reconnection, room/namespace abstractions, and an officially supported Redis adapter for cross-node fan-out. The Redis adapter is the single most important piece: it allows every WebSocket gateway node to publish once and have every other node deliver to its locally connected clients, so we do not need sticky load balancing for correctness (though sticky sessions are still required for the WebSocket upgrade handshake) [14].

A pure Node.js WebSocket server on a 4-vCPU node handles **~50,000 concurrent connections** using `epoll`/`kqueue` [15]. At our 10,000-listener target, we need at least 3–4 gateway nodes behind a single L4 load balancer (NLB or Envoy with WebSocket support), with horizontal scaling to handle chat storms during viral broadcasts.

A production hardening checklist for the gateway:

- **Sticky sessions** at the load balancer for the initial HTTP polling-to-WebSocket upgrade; otherwise the handshake fails [14].
- **Relaxed heartbeats**: `pingInterval: 25s`, `pingTimeout: 20s` to survive transient cellular packet loss without spurious disconnects [14].
- **Binary serialization** (e.g., MessagePack or Protobuf) instead of JSON for in-cluster traffic to halve gateway-to-gateway CPU [14].
- **Kernel tuning**: `net.core.somaxconn = 65535`, `net.ipv4.ip_local_port_range = 1024 65535`, and `ulimit -n 65535` per gateway process.
- **Backpressure**: when a client falls behind, drop them rather than queue forever. Queue depth must be bounded.

**Forward path: WebTransport.** The IETF and W3C are converging on WebTransport as the successor to WebSocket for latency-sensitive applications. WebTransport runs over HTTP/3 + QUIC, providing multiple independent streams, datagrams, and 0-RTT connection migration [16]. Browser support is now viable: Chrome 114+ and Edge 114+ ship full WebTransport, Firefox 114+ supports it (with `network.webtransport.enabled` on by default), and Safari 17+ has experimental support [16]. The W3C WebTransport Working Group is targeting a W3C Recommendation by Q2 2025, and the server ecosystem is catching up — `quic-go/webtransport-go` for Go, `wtransport` for Rust, and `pywebtransport` for Python are production-quality. Socket.IO is adding experimental WebTransport support.

We do not put WebTransport on the critical path for v1 because Safari support is incomplete. We do, however, **abstract the transport behind a single interface** so the v1.5 release can flip the default to WebTransport for Chromium-class browsers and fall back to WebSocket elsewhere. The cost of writing the abstraction now is small; the cost of retrofitting it after launch is large.

### 5.2 Cross-Node Fan-Out: Redis Pub/Sub

The hot path for chat fan-out is **Redis Pub/Sub**. Every gateway node subscribes to a `chat:room:{roomId}` channel; when a node receives a message for a room, it publishes once to Redis and every other node delivers it to locally connected clients. This pattern is identical to what Discord uses for per-guild message distribution [17].

**Redis Pub/Sub is at-most-once by design** — if a subscriber is disconnected, the message is lost. For ephemeral chat this is acceptable; for durable message history we use a separate write-through path to Kafka and Cassandra.

A subtle scaling trap: by default, Socket.IO's Redis adapter publishes the full payload to every node, even nodes with zero subscribers in the room. For a 50-node cluster, this multiplies Redis traffic by 50×. The fix is **sharding the Redis adapter** by hashing the room ID to a small set of dedicated Redis nodes (e.g., 4 shards), so each broadcast only traverses the nodes whose subscribers are present [14].

### 5.3 Persistence and Event Sourcing

Every chat message is written to **two places** in parallel:

1. **Apache Kafka** as a durable, ordered log. Kafka's 24-hour default retention acts as a natural backpressure buffer during traffic spikes, so a slow Cassandra node cannot stall the gateway [18]. The Kafka topic also feeds downstream consumers: search indexing, analytics, abuse detection, and billing.
2. **Cassandra (or ScyllaDB)** for the long-term message store, keyed by `(conversation_id, message_id)` where `message_id` is a Snowflake-style timestamp-ordered ID. The partition key aligns reads within a conversation, so the common "give me the last N messages in this room" query is a single-partition sequential read [19]. PostgreSQL with declarative partitioning is a viable alternative up to ~100M total messages, after which the operational cost of moving partitions outweighs the simplicity.

**Delivery semantics:** at-least-once at the gateway, with **idempotency keys** (client-generated UUIDs) attached to every message. Clients deduplicate on receive. Exactly-once is unachievable across a distributed chat system; at-least-once + idempotency is the pragmatic baseline used by Slack, WhatsApp, and Discord.

### 5.4 Presence and Typing

Presence and typing indicators are **ephemeral** and must not touch Cassandra. They live entirely in Redis with a key like `presence:{userId}` (TTL 60s) refreshed by a 30s client heartbeat. Typing events are published to a per-room Redis channel and have a 5-second client-side timeout; the server never persists them.

### 5.5 Push Notifications

When a user is offline or the app is backgrounded, new chat messages are delivered via **Firebase Cloud Messaging (FCM)** on Android and **Apple Push Notification service (APNs)** on iOS. The notification service is a small stateless worker that consumes from a dedicated Kafka topic (`chat.notifications.outbound`) and dispatches to FCM/APNs. We do **not** open a WebSocket from the OS notification service; the chat gateway's job ends at "is this user online right now? if not, enqueue a push."

### 5.6 The Fan-Out Cliff

The hardest chat problem at scale is the **fan-out cliff**: a single message in a 100,000-member room requires 100,000 individual deliveries. Discord solved this for the MidJourney community (1M+ online users in a single guild) by introducing a "passive session" concept — clients not actively viewing the guild do not receive per-message notifications — which cut fan-out cost by 90% [17]. The lesson: the architecture must treat a 1M-member broadcast room differently from a 50-member group chat. The 1M room uses **fan-out-on-read** with a single Kafka topic and per-user offsets; the 50-member group uses **fan-out-on-write** via Redis Pub/Sub. The product decides which mode each room uses at creation time, and the gateway enforces the mode at the protocol level.

## 6. Optional Interactive Sub-Room Tier

The audience plane is one-to-many over LL-HLS. Some product surfaces (e.g., listener call-ins, host green rooms, podcast recording with remote co-hosts) need sub-second latency and bidirectional audio. That is a different system: a **WebRTC SFU**.

**Recommended SFU: LiveKit (Apache 2.0, Go).** LiveKit is the most production-credible open-source SFU today: OpenAI's ChatGPT Advanced Voice Mode runs on it, as do deployments at Snap, Reddit, Spotify, and Asana [20]. Its data plane is a single Go binary that scales horizontally on Kubernetes, it ships first-class SDKs for web, iOS, Android, React Native, and Flutter, and it supports WHIP/WHEP for ingest and egress, simulcast, and server-side recording out of the box.

A single LiveKit node handles **500–800 concurrent audio-only subscribers** comfortably; for a 5,000-listener interactive event we cascade 7–10 nodes [21]. The cost is per-minute of connection and per-GB of downstream bandwidth, which is **4× or more** than the LL-HLS distribution path for the same audience size [2]. This is exactly why the interactive tier is a separate product surface, gated by a feature flag, and not the default distribution path.

**When the interactive tier is the right call:** listener call-ins that need to feel conversational, multi-host green rooms, audience Q&A where the host responds to specific questions in real time. **When it is the wrong call:** a one-to-many broadcast where the audience only listens. The trap is to assume that "ultra-low latency" is always better; for a 50,000-listener concert broadcast, the SFU economics break, and the audience does not benefit from sub-second latency when there is no one to talk to.

## 7. Data Model and Storage

| Store | What it holds | Access pattern | Why this store |
|---|---|---|---|
| **PostgreSQL** (primary, multi-AZ) | Users, OAuth identities, subscriptions, rooms metadata, room membership, host permissions, billing | OLTP, transactional, indexed lookups by ID | PostgreSQL is the boring, correct choice for the system of record. Use a single primary with read replicas. |
| **Redis** (cluster) | Hot presence (`presence:{userId}`, TTL), ephemeral chat rooms, rate-limit counters, session cache, JWT denylist | Sub-millisecond reads, pub/sub fan-out | Redis is the only store that gives both in-memory speed and pub/sub. Treat it as ephemeral; never as the only copy of state. |
| **Cassandra / ScyllaDB** | Chat message history, audit log of moderation actions | Sequential reads within a `(conversation_id, message_id)` partition | The "give me the last N messages" access pattern is sequential within a partition. Cassandra's write path is also robust under multi-DC replication if we ever go multi-region. |
| **Apache Kafka** (3+ brokers, ISR=3) | Chat events, room lifecycle events, abuse signals, analytics, billing metered usage | Append-only, ordered, replayable | Kafka is the durable spine that lets every downstream consumer (analytics, search, billing) catch up at its own pace. 24h retention is the default; long-term topics get a longer retention policy. |
| **Cloudflare R2** (S3-compatible) | VOD audio recordings, chat attachments, exported chat transcripts, transcoded ABR ladders for catch-up playback | Range requests, multipart uploads, presigned URLs | R2's zero-egress pricing makes it the cheapest durable storage for the audio bytes that the CDN will then re-deliver [22]. $0.015/GB-month storage, $0 egress. |
| **OpenSearch** (optional, for v1.5) | Full-text search across chat history and episode metadata | Inverted index, faceted search | Postgres `tsvector` is fine up to a few million messages; beyond that, dedicated search is operationally simpler. |

Message IDs are **Snowflake-style 64-bit integers** (timestamp + machine ID + sequence), so they are globally unique, roughly time-ordered, and indexable. This eliminates the UUID-v4 ordering problem where a chat history query returns messages out of order.

## 8. Identity, Security, and Content Protection

### 8.1 Authentication

OAuth2 / OIDC at the edge. The mobile and web clients obtain a short-lived access token (15 minutes) and a long-lived refresh token (30 days, stored in the platform-secure keychain on iOS and the EncryptedSharedPreferences on Android). The WebSocket gateway validates the access token on connection and on every reconnect.

The API gateway issues a **per-session media token** (separate from the OIDC token) that the audio client exchanges at the edge for a signed HLS URL. This indirection lets us rotate media-token signing keys without forcing a user re-login.

### 8.2 Signed URLs for HLS

Every HLS request — playlist and segment — carries a short-lived signed URL (e.g., 5 minutes for live edge, 1 hour for VOD). The signature is validated at the CDN edge (Cloudflare Worker / Fastly Compute@Edge) **before** the request enters the cache, then stripped so the cache key is signature-free. This is the only way to keep the CDN cache hit ratio high while still gating access.

### 8.3 Encryption and DRM

Three tiers of content protection, escalating with the value of the content:

| Tier | Mechanism | Use case | Cost |
|---|---|---|---|
| **Free / SaaS** | AES-128 HLS segment encryption, key delivered over HTTPS to authenticated clients only | Free podcasts, public live events, ad-supported content | Low. ~28ms added latency per stream init [23]. |
| **Premium** | CENC (Common Encryption) with **FairPlay on iOS, Widevine on Android/Chrome, PlayReady on Windows/Edge** | Paid subscriptions, premium live events | Higher. License-server ops, per-platform QA. FairPlay SDK last updated June 2021; Widevine and PlayReady are more actively maintained [23]. |
| **Enterprise / regulated** | End-to-end SFrame (IETF draft) on top of WebRTC for the interactive tier | Compliance-sensitive industries, internal corporate broadcasts | Highest. Custom key management, key rotation, MLS-style group key agreement. |

For v1, the recommendation is **AES-128 HLS for everything**. Apple Music itself uses HLS with AES-128 encryption for the majority of its 87% of streams (as of 2024), having retired FairPlay for newly purchased music in 2019 [23]. The DRM systems pay for themselves only when there is a meaningful piracy incentive, which a podcast or live-audio product typically does not have until the catalog becomes high-value.

## 9. Observability and SLOs

Observability is a **day-one** investment, not a phase-two task. The Grafana 2024 Observability Survey found that 98% of responding organizations use open-source observability tools, with Grafana, Prometheus, Loki, and OpenTelemetry being the most common stack [24]. The pattern is well-trodden; we adopt it as the default.

**Stack:** OpenTelemetry SDKs in every service (auto-instrumentation where possible), Prometheus for metrics, Grafana Mimir for long-term metrics storage, Grafana Loki for logs, Grafana Tempo for traces, all behind a unified Grafana UI.

**Key SLOs and their measurement:**

| SLO | Target | Measurement |
|---|---|---|
| Audio startup time (click → first audio) | P95 < 2.5s on LTE | Player-side telemetry via OpenTelemetry; `timeToFirstAudio` event |
| End-to-end audio latency (live edge) | P95 < 5s | Difference between ingest timestamp and play timestamp, sampled |
| Audio rebuffer ratio | < 0.5% of session time | Player telemetry; aggregated per session and per region |
| Chat end-to-end delivery | P99 < 500ms | WebSocket client `sentAt` to `receivedAt`; sampled |
| Chat delivery success rate | > 99.95% | Gateway ACK + client confirmation |
| WebRTC sub-room audio latency (interactive tier) | P95 < 400ms | LiveKit stats + client `getStats()` aggregation |
| Availability (each plane independently) | 99.9% per month | Synthetic probes + per-region health checks |

**Three signals that pay for themselves in week one:** (1) **WebRTC `getStats()` from LiveKit** — bitrate, jitter, packet loss, RTT per subscriber — surfaced on the same dashboard as the LL-HLS segment-delivery latency. (2) **CDN cache hit ratio per region per bitrate** — a sudden drop in cache hit ratio on the audio segments is the earliest signal of a misconfiguration or an attack. (3) **WebSocket connection count per gateway node** — a node drifting from the median is either a noisy neighbor or a partial network partition.

## 10. Deployment and Scaling

### 10.1 Topology

- **One primary region** for stateful services (control plane, packager origin, gateways, Cassandra, Postgres primary, Kafka). Multi-region is a follow-up.
- **Multi-AZ within the primary region** for every service. Stateless services (gateways, packager workers, push-notification workers) are deployed across all three AZs with at least N+2 redundancy.
- **Multi-CDN** at the edge, with DNS-based traffic steering. Origin shield is enabled at both CDN vendors to reduce origin egress.
- **Kubernetes** as the orchestration layer for all services except the LL-HLS packager, which is a stateful, high-I/O workload better run on dedicated nodes (EC2 i4i or equivalent with local NVMe for the segment cache).
- **Terraform / Pulumi** for all infrastructure, with environments for `dev`, `staging`, and `prod` provisioned from the same modules.

### 10.2 Capacity Targets (v1 Launch)

- 10,000 concurrent listeners per broadcast, 50 concurrent broadcasts at peak.
- 100,000 concurrent chat users across all rooms.
- 1 billion chat messages per day at peak (~12,000 msg/sec sustained, 60,000 msg/sec peak).
- Audio egress: 10,000 listeners × 96 kbps average × 50 broadcasts = ~48 Gbps aggregate. Multi-CDN pricing is roughly $0.005–$0.02/GB depending on commit; assume $1,000–$4,000/hour at peak load.
- Chat WebSocket gateway: 100,000 connections ÷ 50,000 per node = 2–3 nodes (with 3× redundancy, 6–9 nodes).

### 10.3 Cost Envelope (Rough Order of Magnitude)

A 10,000-listener × 50-broadcast peak with a 100K-user chat day and full observability stack lands in the **$15,000–$30,000/month range** for cloud spend, dominated by CDN egress and Kafka brokers. Cloudflare R2 at zero egress for VOD and chat attachments makes the storage line essentially free. LiveKit Cloud for the optional interactive tier, if used, adds variable cost per connection-minute.

## 11. Risks, Open Questions, and Future Work

### 11.1 Top Risks

1. **LL-HLS CDN misconfiguration** is the single most likely production failure. A CDN that serves each partial segment as a separate cache entry will turn a 2–5s stream into a 30s+ stream. Mitigation: have a synthetic monitoring stream in every region that continuously measures partial-segment fetch time and alerts on regression.
2. **WebRTC SFU cost at scale.** If the interactive tier is over-used, the per-minute cost will outrun the audience plane. Mitigation: gate the interactive tier behind a feature flag and meter it from day one.
3. **Chat fan-out cliff in viral broadcasts.** A single 100K-member room can saturate Redis. Mitigation: ship the fan-out-on-read path before the first big launch, not after.
4. **iOS background-audio App Review rejection.** Apps that declare `UIBackgroundModes: audio` without a visible feature get rejected under guideline 2.5.4. Mitigation: ensure the lock-screen Now Playing UI is testable and demoable before each submission.
5. **Android 15 background-service restrictions.** The OS refuses to launch media-playback foreground services from `BOOT_COMPLETED` broadcasts; auto-restart logic must be reworked. Mitigation: track this in the platform team's quarterly OS-update review.

### 11.2 Open Questions for the Review

- **Live or near-live VOD transition.** When a live broadcast ends, do we keep the segment files for instant catch-up, or repackage as a VOD asset on a longer ladder? The simplest answer is "keep them," but the storage cost should be modeled.
- **Multi-region strategy.** A primary-region design works until the first cross-region latency complaint. We should plan a follow-up that puts the read-only chat history and audio cache in two regions.
- **DRM escalation trigger.** At what subscriber-revenue threshold do we move from AES-128 to Multi-DRM? This should be a finance-and-product decision, not a security decision.
- **WebTransport v1.5 adoption.** If Safari ships general WebTransport support in 2025, we should plan the v1.5 rollout of the WebTransport chat transport behind a feature flag.

### 11.3 Future Work

- **Media over QUIC (MoQ).** MoQ is the IETF draft that aims to be both real-time and CDN-friendly in a single transport. It is not yet production-ready, but if it ships, the WebRTC-vs-LL-HLS dichotomy collapses. We monitor the IETF MoQ Working Group and plan an evaluation in 2026.
- **Speech-to-text for chat-search and live captioning.** A natural follow-up once the chat store and audio pipeline are stable.
- **Recommendation system for "what to listen to next."** This requires a separate ML platform; it is out of scope here.
- **Native smart-TV apps.** The web build is the v1 target. Roku, Fire TV, and Apple TV are follow-ups.

## 12. Reference Architecture Trade-Offs (Summary)

| Decision | Chosen | Alternative | Reason |
|---|---|---|---|
| Audience distribution protocol | LL-HLS via CMAF | Plain HLS, WebRTC | LL-HLS gives 2–5s latency at CDN economics; plain HLS is too slow; WebRTC is too expensive at scale [1][2]. |
| Audio distribution codec | AAC-LC | Opus, xHE-AAC | Universal hardware decode on iOS, Android, all browsers. Opus has better low-bitrate quality but uneven HLS container support [5]. |
| Ingest from remote contributors | SRT | RTMP, WebRTC WHIP | SRT is the modern standard for contribution; ARQ with fixed jitter window survives 20%+ loss [3]. |
| Chat transport | WebSocket (Socket.IO) | WebTransport, MQTT, gRPC | Universal browser support, well-understood ops, mature Redis adapter [14]. WebTransport planned for v1.5. |
| Chat cross-node fan-out | Redis Pub/Sub | Kafka for hot path, NATS | Pub/Sub is microsecond-latency and sharded cheaply; Kafka is for durable events, not hot fan-out [15]. |
| Chat history store | Cassandra / ScyllaDB | PostgreSQL (partitioned) | Sequential-read access pattern within a partition; horizontal scaling is built in [19]. |
| Object storage | Cloudflare R2 | Amazon S3 | R2 has zero egress, which is the dominant cost for audio catch-up and chat attachments [22]. |
| Interactive sub-room SFU | LiveKit (Apache 2.0, Go) | mediasoup, Janus, Jitsi | Most production-credible open-source SFU; runs ChatGPT Voice; single-binary Kubernetes deploy [20]. |
| Audio ABR ladder | 32/64/96/128 kbps AAC-LC stereo | 5-rung ladder up to 320 kbps | Audio-only does not benefit from very high bitrates; the cost saving on CDN egress from capping at 128 kbps is significant. |
| Background audio on iOS | `UIBackgroundModes: audio` + AVAudioSession `.playback` | Push-driven audio | Apple does not allow arbitrary background audio; we must use the documented capability [12]. |
| Background audio on Android 14+ | `FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` | WorkManager / JobScheduler | Android requires a foreground service for sustained audio; WorkManager alone will be killed [13]. |
| Observability | OTel + Prometheus + Grafana + Loki + Tempo | Datadog, New Relic | Open-source stack adopted by 98% of organizations per Grafana's 2024 survey; no per-host or per-GB vendor lock-in [24]. |
| Content protection (v1) | AES-128 HLS | FairPlay, Widevine, PlayReady | 87% of Apple Music streams use AES-128 HLS; DRM is unnecessary until the catalog becomes high-value [23]. |

# Technical Proposal: Distributed Audio Streaming with Integrated Live Chat

## Executive summary

This proposal recommends a **hybrid media architecture** rather than forcing every participant through a single transport. Hosts, speakers, moderators, and listeners who genuinely need sub-second interaction should use **WebRTC with Opus through regional SFUs**. The much larger passive audience should consume **AAC-LC packaged as low-latency HLS over CMAF and distributed through a CDN**. Live chat should run on an independent **secure WebSocket data plane backed by NATS JetStream**, with Redis for ephemeral state and PostgreSQL for durable application data. This separation is the key architectural decision: WebRTC supplies interactivity, HTTP streaming supplies economical one-to-many distribution, and the chat plane can scale and fail independently. WebRTC's standardized stack includes RTP media, ICE-based connectivity, and secure transports; Apple's LL-HLS extensions add partial segments and blocking reloads, while Apple states that delays of two seconds or less are achievable when the complete pipeline is tuned correctly. [[1]](https://www.rfc-editor.org/info/rfc8825/)

The principal architectural insight is that **“low-latency CMAF” is not itself a client protocol**. CMAF/fMP4 is a media fragmentation/container approach; low-latency delivery still needs a protocol such as LL-HLS or low-latency DASH. Apple's low-latency HLS uses partial CMAF delivery techniques, while Android Media3 also supports low-latency HLS and ultra-low-latency CMAF playback through DASH. [[15]](https://developer.apple.com/videos/play/wwdc2020/10229/?time=161)

This proposal assumes **no specific constraint** on budget, absolute peak user count, cloud provider, or regulatory jurisdiction. Consequently, all SLOs and sizing numbers below are engineering targets to validate, not requirements already supplied by the business. Cloud-provider choice, whether LiveKit is managed or self-hosted, whether multi-CDN is justified, data-residency topology, E2EE, and the number of regions should be revisited once actual peak concurrency, geographic distribution, content sensitivity, and negotiated bandwidth prices are known.

A realistic production program for a medium-sized engineering organization is approximately **22–28 calendar weeks**, roughly **120–160 engineer-weeks**, with six to eight core engineers plus shared SRE, QA/SDET and security capacity. A single-region MVP can be delivered substantially earlier; global active/active behavior, polished mobile background audio, disaster recovery and large-event hardening account for much of the later effort.

## Requirements and engineering targets

The system should explicitly distinguish three workloads because they have fundamentally different scaling properties.

**Interactive stage traffic** consists of the host, speakers, invited participants and possibly a relatively small set of “ultra-low-latency” listeners. These clients need conversational latency, rapid mute/unmute and speaker-role changes, and therefore belong on WebRTC. WebRTC was designed for real-time browser communication and uses RTP for media with standardized secure transport and connectivity procedures. [[16]](https://www.w3.org/TR/webrtc/)

**Broadcast audience traffic** is overwhelmingly one-way. Replicating one RTP stream independently from an SFU to every passive listener wastes the most important advantage of HTTP streaming: edge caching and CDN fan-out. LL-HLS keeps HTTP/CDN operational characteristics while reducing latency through partial segments, preload hints and blocking playlist reload. Apple's implementation guidance describes these mechanisms and positions delays around two seconds as achievable under favorable conditions. [[17]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls)

**Chat traffic** has different semantics again. Chat requires low fan-out latency, moderation, replay/history, user identity, rate limits and sometimes ordering, but it does not require media-grade jitter handling. Keeping it on WebSocket rather than WebRTC data channels allows LL-HLS-only listeners to participate, preserves chat while clients switch media transports, and supports durable server-side history independently of an RTC room.

The following should be treated as the initial engineering SLO envelope:

| Metric | Proposed production target | Design consequence |
| --- | --- | --- |
| Host/speaker WebRTC glass-to-ear latency | p50 150–250 ms; p95 ≤500 ms for reasonably near regions | Regional SFU placement; Opus; UDP preferred; TURN fallback |
| WebRTC join time | p95 ≤2 s | Trickle ICE, pre-issued short-lived credentials and regional endpoint selection |
| LL-HLS glass-to-ear latency | p95 2–4 s | Partial CMAF segments, tuned player live offset, CDN configured specifically for LL-HLS |
| Standard HLS fallback latency | approximately 8–20 s operational target | Used when compatibility/reliability matters more than chat synchronization |
| Chat gateway-to-connected-client latency | p95 ≤150 ms within region; ≤300 ms across regions | Regional WSS gateways and home-region stream routing |
| Chat-to-audio synchronization error in aligned mode | ≤500 ms p95 | Every chat event carries media-time metadata; rendering follows player position |
| Control/chat availability | ≥99.95% monthly | Multi-AZ services, replicated NATS, managed HA data stores |
| HTTP playback availability | ≥99.99% target | CDN plus protected/redundant origin |
| SFU node-failure recovery | p95 reconnect ≤3 s target | Automatic reconnect rather than pretending RTC state can migrate seamlessly |
| Full-region disaster recovery | RTO ≤2 min initially; RPO ≤5 s for non-media state | Paired-region failover and replicated durable data |
| Chat event durability after accepted ACK | No acknowledged event intentionally lost | JetStream acceptance before application ACK; idempotent persistence |

WebRTC setup should use **Trickle ICE** so candidates can be supplied incrementally instead of waiting for full candidate gathering; this exists specifically to improve session establishment behavior. [[18]](https://www.rfc-editor.org/search/?page=6&q=WebRTC)

The media quality profile should differ for speech and music rather than assuming one bitrate fits everything. For WebRTC, the default should be **Opus**, typically mono around 32–48 kbit/s for speech-oriented rooms and roughly 64–96 kbit/s for music or stereo program audio, followed by empirical listening tests. Those are proposed product profiles rather than codec limits: Opus itself supports a far wider 6–510 kbit/s operating range and is designed to adapt between speech and music modes. [[19]](https://www.rfc-editor.org/rfc/rfc6716.html)

For HTTP broadcast output, start with **AAC-LC at 64 kbit/s for speech** and **96–128 kbit/s for music-oriented streams**, with a second rendition only where measurement demonstrates value. Apple explicitly includes AAC-LC and HE-AAC in its HLS authoring requirements and recommends against HE-AAC when the bitrate exceeds 64 kbit/s. [[20]](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html)

Avoid creating five or six audio renditions merely because video ABR systems often have many ladders. Audio bitrates are small, and every rendition adds packaging, storage, cache-key and testing complexity. For most audio-only applications, one high-quality AAC-LC stream plus an optional lower-bandwidth rendition is a better starting point.

A critical product requirement should be **explicit chat synchronization policy**. LL-HLS listeners are several seconds behind a WebRTC host. If host chat is rendered immediately, passive listeners may see reactions or spoilers before hearing the corresponding audio. Each stream therefore exposes one of two modes:

social_realtime displays chat immediately using wall-clock delivery time.

playout_aligned anchors messages to program media time and displays them when the client's current playhead reaches that media position.

The second mode is the recommended default for broadcasts, sports commentary, town halls and synchronized listening events.

## Reference architecture and data flows

The architecture separates **control**, **interactive media**, **broadcast media**, and **chat** planes. LiveKit's distributed mode uses Redis for room data and cluster coordination; its self-hosting documentation supports Kubernetes deployments and separate ingress/egress services. Its Egress service can emit HLS segments and external live-stream outputs, but because the official Egress documentation describes HLS rather than guaranteeing Apple's complete LL-HLS semantics, the design should not assume that plain LiveKit HLS egress automatically provides the desired LL-HLS behavior. A dedicated LL-HLS packaging path is therefore explicit. [[21]](https://docs.livekit.io/transport/self-hosting/distributed/)

The concrete AWS reference path uses a compatible encoder/bridge feeding **MediaPackage v2** through an appropriate managed or self-hosted encoding stage. AWS currently documents MediaPackage support for both HLS and LL-HLS and describes CMAF ingest into MediaPackage v2 as the recommended path for new glass-to-glass low-latency workflows. CDN configuration must specifically account for LL-HLS rather than applying ordinary static-file caching defaults. [[22]](https://docs.aws.amazon.com/mediapackage/latest/userguide/hls-overview.html)

For a medium-sized organization, a managed encoder/packager is preferable initially because implementing a correct LL-HLS origin—including blocking reload semantics, partial availability, discontinuities, clock/timeline correctness and failover—is disproportionately risky. At very large sustained audio volumes, a specialized self-hosted packager may become financially attractive; that decision should be driven by measured stream-hours and managed-service costs, not by architectural purity.

WebRTC signaling itself is intentionally application-specific—the WebRTC protocol suite does not dictate the application's signaling protocol. LiveKit uses its own WebSocket-based signaling APIs, allowing clients to stay on standard SDKs instead of implementing SDP signaling manually. [[23]](https://www.rfc-editor.org/info/rfc8825/)

For professional or hardware contribution feeds, expose **WHIP** in addition to normal LiveKit client publishing. WHIP is now an IETF-standard HTTP-based WebRTC ingestion protocol, and LiveKit's ingress layer supports WHIP as well as RTMP, SRT and file/HTTP inputs. [[24]](https://www.rfc-editor.org/info/rfc9725/)

The timeline synchronization model should be first-class rather than inferred from receipt time:

```text
stream epoch T0
        │
        ├──────── program media time ──────────────────────────────►
        │
host    │ spoken phrase
        │       │
WebRTC  │       └─ heard ~hundreds of ms later
        │
LL-HLS  │                 └─ heard ~2–4 s later
        │
chat    │       message media_time_ms = position in program timeline
        │
        └─ each listener renders message when local playhead reaches that position
```

Every live session has a stable stream_epoch. Every client tracks current media_time_ms. A WebRTC sender's program time can normally be estimated from the synchronized session timeline. A delayed HLS listener sends its **actual player position**, not merely the current server time, when reacting to content. The server validates that supplied time against a plausible window and stamps a trusted server timestamp as well. LL-HLS's structured timeline and HLS program-time facilities make this mapping practical; partial segments and blocking reloads reduce but do not eliminate the need for explicit synchronization logic. [[25]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls)

A useful ordering contract is **monotonic within a stream's chat-ordering epoch, but not globally gapless**. Requiring a strict, globally synchronous total order across continents would add latency and availability coupling for little user-visible benefit. A stream has one authoritative chat home region; after a regional sequencer failover, the epoch increments. Clients order by (epoch, seq) and deduplicate by message_id.

JetStream is appropriate because an accepted event can survive consumer outages and be replayed; its standard semantics are at-least-once, so database consumers must be idempotent rather than assuming exactly-once execution. NATS documentation explicitly distinguishes persistent JetStream delivery from non-replayable Core NATS messaging. [[26]](https://docs.nats.io/concepts/jetstream)

## Technology choices and trade-offs

The central transport decision is deliberately **WebRTC plus HTTP streaming**, not WebRTC *versus* HTTP streaming.

| Technology | Proposed operational latency | Main advantages | Main disadvantages | Recommended use |
| --- | --- | --- | --- | --- |
| WebRTC | 150–500 ms target | Interactive, bidirectional; RTP media; congestion/jitter handling; ICE/STUN/TURN connectivity; secure media transport. [[27]](https://www.rfc-editor.org/info/rfc8835/) | More networking complexity; SFU egress grows with listeners; TURN can be expensive | Hosts, speakers, moderators, small interactive audience |
| LL-HLS + CMAF | 2–4 s target | HTTP/CDN scaling; partial segments, preload hints and blocking reload; Apple documents ≤2 s as achievable in tuned systems. [[28]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls) | Not conversational; more HTTP requests; cache/origin configuration is subtle | Default mass audience |
| Standard HLS | 8–20 s target | Extremely operationally mature; simple caching; robust fallback | Chat/media desynchronization becomes large; poor for interactive experiences | Compatibility/failure fallback, non-interactive streams |
| Low-latency DASH + CMAF | 2–4 s target | Standards-based low-latency HTTP option; Android Media3 supports ultra-low-latency CMAF DASH. [[29]](https://developer.android.com/media/media3/exoplayer/dash) | Additional manifest/player/test matrix, particularly where Apple clients are already HLS-centric | Add only for ecosystem or business requirements |
| WHIP contribution | Sub-second ingest target | Standard HTTP/WebRTC ingestion; good for external production encoders. [[30]](https://www.rfc-editor.org/info/rfc9725/) | Ingestion protocol, not a mass-playback solution | Professional publisher ingest |
| SRT/RTMP contribution | Ingest-dependent | Strong compatibility with existing broadcasting tools; LiveKit ingress accepts these sources. [[31]](https://docs.livekit.io/transport/media/ingress-egress/ingress/) | Not browser-native playback; introduces gateway/transcode stage | Legacy/professional ingest |

WebRTC traffic should attempt direct UDP media connectivity first, with ICE selecting viable paths and TURN as a relay fallback. TURN/TLS on port 443 is valuable for networks that block UDP, but it should be monitored as a cost and quality signal rather than treated as the normal path. LiveKit's deployment guidance explicitly calls out public-IP, UDP and TURN/TLS considerations. [[32]](https://docs.livekit.io/transport/self-hosting/deployment/)

**Codec selection** should similarly be asymmetric:

| Codec | Strengths | Weaknesses | Recommendation |
| --- | --- | --- | --- |
| Opus | Interactive speech and music; 6–510 kbit/s defined range; WebRTC interoperability requirement. [[33]](https://www.rfc-editor.org/rfc/rfc6716.html) | HLS/Apple broadcast interoperability is less universally straightforward than AAC | Default RTC codec |
| AAC-LC | Excellent HLS/device compatibility; explicitly in Apple's HLS audio requirements. [[20]](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html) | Less attractive than Opus for highly interactive packet-loss-sensitive RTC | Default LL-HLS/HLS output |
| HE-AAC | Useful at low audio bitrates; Apple includes it in HLS compatibility guidance. [[20]](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html) | Apple advises against HE-AAC above 64 kbit/s | Optional low-bandwidth broadcast rendition |
| xHE-AAC | Modern low-bitrate capabilities and supported in Apple's HLS ecosystem. [[34]](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html) | More device/encoder validation and operational complexity | Later optimization, not launch baseline |

Do not transcode Opus independently for every listener. One program feed should be decoded/transcoded into each required HTTP rendition **once per live stream**, after which the CDN performs audience fan-out. This is one of the biggest structural cost advantages of the hybrid architecture.

**SFU/server choice** is a build-versus-framework decision rather than a codec decision:

| Media server | Architectural character | Advantages for this project | Trade-offs | Verdict |
| --- | --- | --- | --- | --- |
| LiveKit | Opinionated distributed WebRTC platform/SFU | Redis-based distributed mode; Kubernetes support; ingress/egress; browser/mobile SDKs; fastest path to a complete product. [[35]](https://docs.livekit.io/transport/self-hosting/distributed/) | More opinionated; application becomes coupled to LiveKit room/token abstractions | **Recommended default** |
| mediasoup | Low-level programmable SFU/library | High control over signaling and application semantics; suited to teams wanting to build their own RTC orchestration. [[36]](https://mediasoup.org/documentation/v3/scalability/) | Significantly more engineering for signaling, room orchestration, scaling and operational tooling | Choose when RTC itself is strategic IP |
| Janus | C WebRTC server with plugin model | Mature gateway model; VideoRoom provides SFU-style conferencing; flexible protocol interop. [[37]](https://janus.conf.meetecho.com/docs/videoroom) | More application/session plumbing; plugin architecture is less turnkey for this product | Strong specialized gateway alternative |
| Jitsi | Complete conferencing architecture centered on Jitsi Videobridge and signaling components | Battle-tested meeting stack and strong conferencing semantics. [[38]](https://jitsi.github.io/handbook/docs/devops-guide/devops-guide-docker/) | More meeting-oriented infrastructure than needed for an audio broadcast product | Prefer for meeting products, not this default |

LiveKit's most important architectural limitation should be accepted rather than hidden: a real-time room is stateful at the SFU layer. Distributed routing can place rooms on healthy nodes, but a failed SFU should be treated as an event that causes participant reconnection; do not architect an SLO around magical live migration of every RTP state machine. LiveKit's distributed mode uses Redis and node-reported statistics for routing and placement, which is useful for redundancy but does not eliminate the inherent statefulness of an active media session. [[39]](https://docs.livekit.io/transport/self-hosting/distributed/)

The **browser implementation** should use React with TypeScript, a thin state-management layer, the LiveKit JavaScript client for RTC, and a separate playback abstraction for HTTP streaming. Use native HLS in browsers where the platform supplies it and an MSE-based HLS implementation such as hls.js where required. React's current official documentation supports TypeScript directly, and Apple continues to maintain HLS as its native HTTP streaming stack. [[40]](https://react.dev/learn/typescript)

The playback component must expose a transport-neutral interface such as:

```ts
interface LiveAudioPlayer {
  connect(source: MediaSourceDescriptor): Promise<void>;
  play(): Promise<void>;
  pause(): void;
  getMediaTimeMs(): number;
  getLiveEdgeDistanceMs(): number | null;
  getStats(): PlaybackStats;
  on(event: "state" | "stats" | "fatalError", handler: (value: unknown) => void): void;
}
```

That prevents chat synchronization, UI and analytics from depending on whether the current transport is WebRTC or LL-HLS.

For **mobile**, React Native is a good default for a medium-sized company because screen/UI/business logic can be shared while the media paths remain native. React Native's current architecture explicitly provides typed native-module interfaces through Codegen, so AVPlayer, Android Media3, audio-session controls and platform background-playback behavior can remain in Swift/Kotlin modules instead of being forced through a generic JavaScript-only player. [[41]](https://reactnative.dev/docs/turbo-native-modules-introduction)

On Android, Media3/ExoPlayer currently supports fMP4/CMAF HLS, Apple's LL-HLS features including blocking playlist reload and preload hints, and low-latency DASH/CMAF playback. [[42]](https://developer.android.com/media/media3/exoplayer/hls)

For applications where premium audio behavior, Bluetooth routing, automotive integration, lock-screen controls or background execution are a primary competitive feature, the alternative is **fully native Swift and Kotlin clients**. That costs approximately twice the UI implementation surface but reduces cross-platform abstraction risk. Flutter is also viable because the media layer can be native, but choosing it merely substitutes Dart for TypeScript and does not remove the underlying native audio requirements. With no team-language constraint specified, React Native gives the stronger organizational reuse with the proposed React web stack.

**Chat should not use the SFU's WebRTC data channel as its primary transport.** Such a design would exclude HTTP-stream-only clients unless a second chat implementation existed, couple chat failure to RTC connection state and complicate durable history. Secure WebSockets terminate on stateless chat gateway pods; gateway instances authorize the connection, rate-limit writes and subscribe only to streams with local users.

NATS JetStream is the default inter-service chat bus because it supplies persistence, replay and at-least-once delivery. Redis Pub/Sub should remain confined to deliberately ephemeral events because Redis documents its Pub/Sub semantics as at-most-once. [[43]](https://docs.nats.io/concepts/jetstream)

A recommended event topology is:

```text
chat.command.<stream-id>          user-originated messages
chat.message.<stream-id>          accepted visible messages
chat.moderation.<stream-id>       hide / restore / mute / ban actions
chat.presence.<stream-id>         ephemeral presence summaries
chat.system.<stream-id>           stream lifecycle announcements
```

JetStream should retain accepted chat and moderation events long enough to replay recent outages. PostgreSQL remains the durable user-facing history and audit store. Because JetStream can redeliver an event after an unacknowledged consumer failure, the history writer uses message_id as an idempotency key. [[44]](https://docs.nats.io/learn/jetstream/delivery-and-acknowledgment)

For the first production deployment, use one **NATS R3 cluster per primary chat region**, with replicas in independent availability zones. NATS explicitly notes that an R3 stream can survive one server loss only when replicas are placed across independent failure domains; merely running three copies in one zone does not provide that property. [[45]](https://docs.nats.io/learn/topologies/jetstream-in-a-cluster)

**CDN selection** should be driven primarily by the company's cloud contracts, audience geography, LL-HLS behavior under load, support quality and negotiated egress pricing rather than feature checklists alone.

| CDN | Useful capabilities | Best fit | Trade-off |
| --- | --- | --- | --- |
| AWS CloudFront | Origin Shield and origin failover are directly integrated with AWS origins. [[46]](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html) | Default for AWS + MediaPackage deployment | Strongest operational coupling to AWS |
| Cloudflare | Tiered Cache and Cache Reserve provide layered origin protection/caching. [[47]](https://developers.cloudflare.com/cache/how-to/tiered-cache/) | Multi-cloud edge strategy, especially if Cloudflare is already the security edge | Validate LL-HLS blocking-request behavior and contracts with realistic load |
| Fastly | Origin shielding and highly programmable delivery controls. [[48]](https://www.fastly.com/documentation/guides/concepts/shielding/) | Teams needing sophisticated cache/edge configuration | Higher specialist operational skill requirement |
| Akamai | Mature distributed caching and tiered-delivery facilities. [[49]](https://techdocs.akamai.com/property-mgr/docs/know-caching) | Very large global media workloads with enterprise support requirements | Contract and operational complexity can exceed an early-stage need |

Use **one CDN initially**, but keep manifests, segment naming, authentication and origin APIs portable. Once traffic is large enough that a CDN outage has material business impact, introduce dual-CDN steering. A dual-CDN architecture before the team has realistic production telemetry doubles cache debugging, analytics reconciliation and incident paths without automatically doubling reliability.

AWS's own LL-HLS documentation has special CDN recommendations, underscoring that ordinary HLS cache behavior should not simply be copied to a low-latency endpoint. [[50]](https://docs.aws.amazon.com/mediapackage/latest/userguide/cdn-recommendations.html)

## Reliability, security, and observability

Fault tolerance should be designed around the fact that different planes have different recoverability.

| Failure | Expected behavior | Recovery design |
| --- | --- | --- |
| API/chat pod | No user-visible interruption beyond retried request | ≥3 replicas, topology spread, HPA, PDB |
| One availability zone | Control/chat remain online | Replicas across ≥3 AZs; managed DB/cache HA; JetStream R3 |
| One SFU pod/node | Participants in affected rooms reconnect | Client auto-reconnect, capacity headroom, failed node removed from placement |
| TURN node | New ICE session selects another relay; affected relayed sessions reconnect if necessary | Multiple TURN instances and health-based routing |
| Broadcast bridge/encoder | LL-HLS may stall briefly | Warm standby for important events; health-driven restart/failover |
| LL-HLS origin | CDN serves cacheable media; live edge eventually needs alternate origin | Redundant origin/package path for high-value streams |
| Chat persistence worker | Live chat continues; durable DB history lags | JetStream backlog/replay |
| PostgreSQL transient outage | Existing media/chat continue as much as possible | Avoid synchronous DB dependency on every media packet/chat fan-out |
| Redis outage | RTC room placement/cache/presence affected | Managed HA Redis; isolate chat durability from Redis |
| Entire region | Streams reconnect/restart in paired region; existing HTTP delivery may have a short discontinuity | DNS/traffic failover, secondary compute and replicated control data |

Kubernetes should use **topology spread constraints** across zones and nodes, and PDBs should limit voluntary simultaneous disruptions. HPA is appropriate for stateless APIs and chat gateways, but media workloads require more than CPU scaling. Kubernetes documents all three primitives; topology spreading explicitly targets failure-domain diversity. [[13]](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/)

SFU placement should use metrics such as outgoing bitrate, active tracks, room count, packet-processing load, memory, network-interface headroom and TURN proportion. Scale-out should start early enough that a new node is available before existing network interfaces are saturated. Scale-in must be conservative: mark an SFU as draining, stop assigning new rooms, and let active rooms end or move through controlled reconnect rather than terminating a node merely because a CPU HPA threshold fell.

For mass-audience availability, the CDN is the primary fan-out boundary. Protect the origin through shielding/tiered caches, use immutable content keys for finalized media objects, short-lived live playlists, and correct cache-key handling for LL-HLS delivery directives. Apple explains that blocking playlist reload was specifically designed to reduce segment-discovery latency and interact correctly with HTTP caching behavior. [[51]](https://developer.apple.com/videos/play/wwdc2020/10231/)

**Authentication** should use an external or existing enterprise **OpenID Connect provider over OAuth 2.0**. OIDC defines an interoperable identity layer over OAuth, while current OAuth security BCPs address modern browser threat models and recommended security practice. [[52]](https://www.rfc-editor.org/info/rfc9700/)

Browser and mobile sign-in should use authorization-code flows with PKCE and the platform browser rather than embedding user credentials inside the application. Access grants should be short-lived and narrowly scoped. A useful authorization model is:

```text
stream:view
stream:publish
stream:moderate
stream:produce
stream:record
stream:admin
chat:read
chat:write
chat:moderate
```

Each RTC token must additionally name the exact room and permissions—for example, a viewer token cannot publish audio. CDN playback authorization should similarly be stream-specific and short-lived.

WebSocket connections should not rely on a long-lived bearer token embedded permanently in a URL. A safer application design is:

```text
authenticated HTTPS request
        ↓
POST /v1/chat-tickets
        ↓
single-use, stream-scoped, ~30–60 s ticket
        ↓
WSS upgrade
        ↓
ticket consumed; connection becomes server-side authenticated session
```

At transport level, APIs, WSS, signaling and HTTP media use modern TLS, with TLS 1.3 as the preferred protocol. TLS 1.3 is designed to protect client/server communications against eavesdropping, tampering and message forgery. [[53]](https://www.rfc-editor.org/info/rfc8446/)

WebRTC media additionally follows its secure media architecture rather than transmitting plain RTP over the Internet. The IETF WebRTC transport and security specifications define the secure transport framework used by conforming implementations. [[54]](https://www.rfc-editor.org/info/rfc8835/)

**TURN credentials must be short-lived**, issued to an authenticated session rather than distributing permanent relay passwords inside applications. TURN capacity should be rate-limited and separately monitored because a leaked relay credential can become a bandwidth-abuse vector.

For particularly confidential interactive rooms, **SFrame** is the right standards-based technology to evaluate for media E2EE. SFrame was specifically designed so a central SFU can make forwarding decisions without reading encrypted media content. [[55]](https://www.rfc-editor.org/rfc/rfc9605)

That has an important architectural consequence: because an LL-HLS transcoder must decode the program audio before creating AAC renditions, genuine endpoint-to-endpoint encryption is incompatible with ordinary server-side broadcast transcoding or server-side recording unless a trusted endpoint/decryptor terminates that protection. This is an inference directly from SFrame's property that the SFU cannot read protected media. [[56]](https://www.rfc-editor.org/subjects/sframe/) Therefore:

**Public/hybrid broadcast mode:** DTLS-SRTP transport security, server transcoding/recording allowed.

**Confidential RTC mode:** optional SFrame E2EE, but no transparent server-side AAC/HLS conversion or content moderation of the media payload.

The product must represent those as distinct security modes rather than marketing one mode as simultaneously fully E2EE and server-transcodable.

Chat should normally be TLS-encrypted in transit and storage-encrypted at rest but **not application-level E2EE** if server-side moderation, abuse investigation, search or history are required. If private E2EE chat later becomes a requirement, make it a separate feature with consciously reduced moderation capability.

Additional security controls should include a CDN/WAF at the HTTP edge, per-user/per-IP/per-stream rate limits, maximum message and frame sizes, WebSocket Origin validation, CORS/CSRF controls for browser endpoints, signed media authorization, secrets from a cloud KMS or Vault-like system, audit records for moderation and role changes, container/image scanning, dependency scanning, SBOM generation and explicit retention policies.

No regulatory region was specified. Therefore the design should support configurable storage retention and region pinning, but it should **not claim GDPR, HIPAA, financial or other regulatory compliance by architecture alone**. Data residency, deletion semantics, moderation retention and audit requirements require jurisdiction-specific review.

Observability needs three layers.

**Application observability** should use OpenTelemetry for traces, metrics and logs. OpenTelemetry defines these as first-class signals, while its Collector provides a vendor-neutral receiving, processing and export layer. [[14]](https://opentelemetry.io/docs/concepts/signals/)

**Media telemetry** needs domain-specific statistics beyond generic HTTP latency. The W3C WebRTC Stats API exposes standardized RTC statistics and network characteristics, making it suitable for client QoE telemetry. [[57]](https://www.w3.org/TR/webrtc-stats/) Collect, with sampling:

| Plane | Core measurements |
| --- | --- |
| WebRTC client | RTT, jitter, packet loss, packets received/sent, jitter-buffer delay, concealment, ICE candidate pair/type, reconnect count, audio level |
| SFU | active rooms/participants/tracks, ingress and egress bps, packets/s, loss/NACKs, reconnects, node network utilization, room placement rejection |
| TURN | allocations, bandwidth, allocation failures, UDP/TLS ratio, relay percentage by ASN/network |
| LL-HLS client | first-audio time, live-edge distance, stalls, rebuffer duration, rendition, playlist latency, partial-segment request failures |
| CDN/origin | cache-hit ratio, origin request rate, 4xx/5xx, part/segment latency, playlist age, shield hit rate |
| Chat | connected sockets, connection churn, publish ACK latency, fan-out latency, message rate, rate-limit rejects, moderation latency |
| JetStream | stream size, replication health, redeliveries and consumer lag |
| PostgreSQL | write/read p95, pool saturation, replication lag, deadlocks, table/index growth |

NATS specifically identifies **consumer lag** as a primary health signal, so expose it directly in alerting rather than relying on generic CPU utilization. [[58]](https://docs.nats.io/learn/monitoring/jetstream-health)

Do not emit a trace span per RTP packet or HLS partial fragment: cardinality and telemetry cost would be enormous. Trace lifecycle operations—stream creation, join, credential issue, chat publish, moderation, egress start/failure—and correlate them by stream_id, participant_id, playback_session_id, region and deployment version.

Recommended alert conditions include: WebRTC p95 join time above target; relay/TURN ratio suddenly increasing; per-ASN connection failure spikes; SFU NIC headroom below threshold; LL-HLS live-edge distance exceeding target; origin 5xx; CDN cache-hit collapse; NATS consumer lag rising continuously; chat fan-out p95 breach; PostgreSQL replication lag; or a statistically significant increase in player rebuffering after a deployment.

│   ├── CDN + WAF
│   ├── container registry
│   ├── CI identity / signing keys
│   └── central telemetry backend
│
├── Region A
│   ├── Kubernetes control/chat node pools
│   │   ├── API
│   │   ├── chat gateways
│   │   ├── moderation
│   │   ├── history workers
│   │   └── OpenTelemetry collectors
│   │
│   ├── Kubernetes media node pools
│   │   ├── LiveKit SFUs
│   │   ├── TURN
│   │   ├── ingress

LiveKit explicitly documents Kubernetes deployment and warns that WebRTC deployments require correct UDP/public-IP and load-balancer behavior; its Helm deployment supports distributed configurations. [[59]](https://docs.livekit.io/transport/self-hosting/kubernetes/)

A concrete AWS implementation would use:

| Function | Concrete implementation |
| --- | --- |
| Kubernetes | EKS |
| API/WSS HTTP load balancing | ALB or Envoy-backed ingress |
| RTC/UDP entry | NLB/direct UDP-capable networking |

| LL-HLS packager | MediaPackage v2, with a compatible encoder/bridge stage |

| IaC | Terraform |

| GitOps | Argo CD |
| Telemetry | OpenTelemetry Collector plus Prometheus/Grafana-compatible stack |

The core design remains portable because LiveKit, PostgreSQL, Redis, NATS, Kubernetes, Terraform and OpenTelemetry are not tied to AWS. The intentionally cloud-specific part is LL-HLS packaging/CDN integration. If the company already has a large GCP, Cloudflare, Fastly or Akamai commitment, preserve the media contracts and substitute that delivery layer rather than migrating clouds merely to follow this reference topology.

**Kubernetes scheduling.** Use separate media and application node groups. Media nodes should have high network throughput and predictable CPU performance; do not colocate arbitrary batch jobs with SFUs. Apply zone topology spreading and anti-affinity. Critical control/chat services get PDBs. Kubernetes formally supports both topology spread constraints and disruption budgets for these purposes. [[60]](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/)

For stateless application pods, HPA can scale from CPU plus custom Prometheus metrics such as sockets or request concurrency. Kubernetes HPA is explicitly designed to change replica counts to match demand. [[61]](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) For SFUs, use a custom controller or external autoscaling metric based on placement capacity, bitrate and network headroom; CPU alone is not a safe proxy.

A conceptual production deployment policy:

```yaml
controlPlane:
  minReplicasPerService: 3
  topology: 3-availability-zones
  autoscaling:
    api: cpu_and_request_rate
    chatGateway: websocket_connections_and_messages_per_second

mediaPlane:
  sfus:
    scaleMetric: available_network_and_room_capacity
    scaleDownPolicy: drain_only
  turn:
    minInstancesPerRegion: 2
    scaleMetric: allocations_and_bandwidth

jetstream:
  replicas: 3
  placement: cross_zone

postgres:
  managedHA: true
  backups: point_in_time

redis:
  managedHA: true
```

Application manifests belong in Helm charts and a Git repository reconciled by Argo CD. Argo CD's GitOps model makes Git the deployment source of truth and supports automated synchronization; Terraform provides the infrastructure-as-code layer beneath it. [[62]](https://developer.hashicorp.com/terraform/intro)

**CI** can use GitHub Actions if the company has no existing preference, but the design is CI-provider-neutral. Every change should pass:

```text
format / lint
    ↓
unit + property tests
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

```

Control-plane services can use a conventional percentage-based canary. SFU upgrades require a different deployment primitive: **drain old nodes, stop scheduling new rooms to them, wait for sessions or deliberately reconnect them, then remove the nodes**. Treating an SFU like a stateless HTTP pod and terminating 25% of replicas at random during a rolling update will create avoidable live-audio outages.

Database migrations should use an expand-and-contract strategy: deploy additive schema first, deploy code that understands both schemas, backfill, switch reads/writes, and only later remove obsolete columns. Never couple rollback safety to an irreversible migration.

Mobile releases require a server compatibility window because app-store deployment is not instantaneous. API and WebSocket schemas therefore carry explicit versions, and the server should support at least the previous mobile protocol generation during normal rollout.

Testing should be organized around failure modes, not just functions.

**Unit and contract testing** covers authorization decisions, stream state machines, media-mode selection, chat ordering, idempotency, JSON schema compatibility and moderation rules.

**Browser end-to-end tests** should run Chrome/Chromium, Firefox and WebKit-family tests through Playwright. Playwright provides a cross-browser automation platform suited to this matrix. [[63]](https://playwright.dev/)

**Mobile tests** need native iOS and Android instrumentation in addition to JavaScript tests. Explicitly test audio interruption/resumption, Bluetooth device changes, wired/unwired headphones, backgrounding, lock screen, calls/alarms, network transition between Wi-Fi and cellular, and process suspension.

**Media interoperability tests** should include:

```text
UDP available
UDP blocked → TURN/TLS
IPv4-only
IPv6 / dual stack
corporate proxy/VPN
high RTT
1–5% random packet loss
burst loss
bandwidth collapse/recovery
network handover
host reconnect
SFU restart
TURN restart
packager restart
CDN cold cache
```

The W3C WebRTC statistics interface makes packet loss, RTT and related quality indicators observable during these experiments. [[57]](https://www.w3.org/TR/webrtc-stats/)

**LL-HLS validation** should use Apple's HLS tools as part of media-pipeline CI and pre-production validation. Apple maintains dedicated tooling for segmenting and validating HLS authoring workflows. [[64]](https://developer.apple.com/documentation/http-live-streaming/using-apple-s-http-live-streaming-hls-tools)

**Load testing** should separately test RTC and chat because a workload that stresses one may barely affect the other. LiveKit supplies load-testing capabilities for its deployments, while k6 supports WebSocket load testing and associated metrics. [[65]](https://github.com/livekit/livekit-cli)

Representative gates should be:

| Test | Pass criterion before production |
| --- | --- |
| Normal peak | 1.25× forecast traffic for ≥60 min, all SLOs met |
| Spike | 0→2× forecast within 2 min without cascading failure |
| Soak | 8–12 h, no unbounded memory/socket/consumer-lag growth |
| Hot chat room | Maximum projected single-room message rate plus safety margin |
| RTC degradation | Acceptable audio under target loss/RTT envelope |
| SFU kill | Affected clients reconnect within recovery SLO |
| NATS node kill | No acknowledged chat loss |
| DB outage | Media and live chat fan-out remain operational; persistence catches up |
| Cache miss storm | Origin protected and remains below safe request ceiling |
| Regional simulation | DNS/routing and control-plane DR procedure works from clean runbook |

The staging environment must exercise the same transport topology as production. A “staging” system that has no real UDP, TURN, CDN, TLS termination or LL-HLS origin does not validate the highest-risk parts of this architecture.

## Cost model, roadmap, and risk register

For audio streaming, **network egress is likely to become the dominant variable cost before storage does**. Because exact audience scale, cloud discounts and CDN contract are unspecified, the proposal should use a transparent formula rather than invented dollar figures.

At bitrate $B$ kbit/s and $L$ listener-hours:

$$
\text{GB delivered} \approx 0.00045 \times B \times L
$$

before container/protocol overhead.

Thus:

| Encoded bitrate | Data per listener-hour | Data per one million listener-hours |
| --- | --- | --- |
| 48 kbit/s | 21.6 MB | 21.6 TB |
| 64 kbit/s | 28.8 MB | 28.8 TB |
| 96 kbit/s | 43.2 MB | 43.2 TB |
| 128 kbit/s | 57.6 MB | 57.6 TB |

For a CDN rate of P dollars/GB, the first-order delivery cost is therefore:

```text
media_egress_cost
    ≈ 0.00045 × bitrate_kbps × listener_hours × P
      + HTTP request cost
      + origin/packaging cost
```

LL-HLS raises HTTP transaction volume relative to long-segment HLS because partial segments, playlist reload behavior and preload mechanisms deliberately expose media in smaller increments; Apple's LL-HLS documentation describes these partial-segment and blocking-request mechanisms. [[25]](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls) This means CDN evaluation must benchmark **request pricing as well as $/GB**, particularly for very low-bitrate audio where bytes are cheap but requests are numerous.

WebRTC bandwidth has the same fundamental listener-byte multiplication but lacks normal CDN cache fan-out. If 100,000 passive listeners receive a 64-kbit/s stream directly from an SFU tier, the SFU/media network must originate that audience traffic; with LL-HLS, the origin primarily supplies cache fills and the CDN handles the audience edge. That difference—not codec bitrate alone—is the main reason to avoid “WebRTC for everybody.”

TURN adds another cost variable:

```text
turn_cost
    ∝ WebRTC traffic
      × percentage of sessions requiring relay
      × relay provider's bandwidth/compute pricing
```

Monitor the **TURN ratio by geography, ASN, application version and network type**. A sudden increase can indicate a firewall/connectivity regression as well as higher cost.

Transcoding/packaging costs scale primarily with **active stream-hours and number of renditions**, not audience size. That favors one or two AAC renditions rather than an unnecessarily large audio ladder.

Other meaningful cost categories are:

| Driver | Scaling dimension | Control |
| --- | --- | --- |
| CDN egress | Listener-hours × bitrate | Codec/rendition selection, contracted CDN rates |
| LL-HLS requests | Listener-hours × parts/playlist frequency | Tune segment/part strategy; validate CDN pricing |
| SFU networking | RTC participant-hours | Keep passive audience on HTTP |
| TURN | Relayed RTC participant-hours | Connectivity optimization and regional relays |
| Encoder/packager | Active stream-hours × rendition count | Avoid unnecessary renditions; benchmark managed vs self-hosted |
| Kubernetes compute | SFU capacity + chat/control baseline | Separate pools, right-size, autoscale conservatively |
| NATS/Redis/PostgreSQL | Chat volume, connections, retention | Retention, partitioning, managed-service sizing |
| Recordings | Recorded stream-hours × bitrate × retention | Lifecycle policies/object-storage archive tiers |
| Observability | Telemetry events/cardinality | Sampling, aggregation and disciplined labels |

Do **not** optimize away the managed LL-HLS packager during the MVP merely because self-hosting looks cheaper per CPU-hour. The operational risk of faulty live manifests, discontinuity handling, clock errors and origin overload can dominate the nominal savings. Revisit custom packaging only after real production listener-hours make the managed packaging bill material.

The recommended implementation program is:

| Phase | Calendar estimate | Approx. effort | Main outcome |
| --- | --- | --- | --- |
| Architecture and media spikes | 3 weeks | 8–12 engineer-weeks | Prove WebRTC→broadcast bridge, LL-HLS latency, chat/media synchronization and mobile background playback |
| Single-region MVP | 6–7 weeks | 30–40 engineer-weeks | Web + mobile listening, host publishing, LiveKit, LL-HLS, chat, stream APIs, basic moderation |
| Production hardening | 5–6 weeks | 28–36 engineer-weeks | Kubernetes production topology, security, durable chat, observability, CI/CD, load and failure tests |
| Multi-region and mobile hardening | 5–6 weeks | 28–36 engineer-weeks | Regional media, robust reconnect, native background controls, DR and traffic steering |
| Scale and resilience | 3–6 weeks | 20–35 engineer-weeks | Large-event tuning, origin protection, regional failure drills, optional second CDN |
| Optional advanced security/features | Separate track | Requirement-dependent | SFrame E2EE, professional WHIP ingest, recording, advanced moderation |

A suitable core team is roughly two media/backend engineers, two application/backend engineers, one web engineer, one or two mobile engineers, plus shared SRE/platform, QA/SDET and security support. A team already experienced with LiveKit/WebRTC and native audio will be at the low end of the schedule; a team learning RTC, HLS packaging and iOS/Android background-media behavior simultaneously should plan around the high end.

The highest-value architecture spike is **not** “can we make WebRTC play audio?” That is well-established technology. The spike should prove the difficult boundary: one live Opus program enters the SFU, the broadcast pipeline generates standards-compliant low-latency AAC/CMAF output, a realistic CDN preserves the intended latency, and a WebRTC listener and an LL-HLS listener see chat aligned to the same program event despite their different playout delays.

The final risk register should remain visible throughout implementation:

| Risk | Probability | Impact | Mitigation |
| --- | --- | --- | --- |
| LL-HLS/chat synchronization feels wrong | High | High | Make media_time_ms a protocol primitive; build automated cross-client sync tests in the first spike |
| SFU node failure causes disruptive reconnects | Medium | High | Explicit reconnect SLO; spare capacity; node draining; bounded interactive cohort |
| High TURN percentage drives cost/quality problems | Medium | Medium–High | UDP-friendly deployment, TURN/UDP + TLS fallback, monitor relay ratio by network |
| CDN configuration breaks blocking LL-HLS behavior | Medium | High | Vendor-specific preproduction load tests, correct cache keys, origin shielding |
| Large stream creates a “hot room” chat bottleneck | Medium | High | Stream home region, horizontal gateways, NATS, hot-room load test, moderation/rate limits |
| NATS at-least-once delivery creates duplicate DB records | Expected behavior | Medium | Stable message_id, idempotent history consumer, unique constraints |
| Mobile background audio is less reliable than desktop testing suggests | High | High | Native player/session modules; test interruptions, Bluetooth, backgrounding and network handoff early |
| SFU autoscaling based only on CPU misses NIC exhaustion | Medium | High | Placement capacity and network-bitrate metrics; drain-based scale-in |
| Managed encoding/packaging becomes expensive at scale | Medium | Medium–High | Measure stream-hour cost; optimize only after traffic justifies custom pipeline |
| Dual-CDN architecture introduces more complexity than reliability initially | Medium | Medium | Launch single-CDN; add second provider only at proven business scale |
| E2EE requirement conflicts with HLS transcoding/recording | Medium | High | Separate confidential RTC and broadcast security modes; decide product policy explicitly |
| Abuse/spam/DDoS overwhelms chat or TURN | High for public systems | High | WAF, authentication, per-principal limits, ephemeral TURN credentials, moderation and anomaly alerts |
| Cross-region strict chat ordering becomes a hidden latency requirement | Medium | Medium | Define epoch-local ordering rather than global serializability |
| Cloud/vendor lock-in accumulates | Medium | Medium | Keep control/chat APIs, media contracts and client abstraction portable; confine cloud-specific logic to packaging/CDN adapters |

The recommended production endpoint is therefore **not a single monolithic streaming service**. It is a deliberately separated system:

```text
Interactive path:
Client → WebRTC / Opus → regional LiveKit SFU → interactive clients

Broadcast path:
SFU program audio
    → one-time AAC transcode
    → CMAF / LL-HLS package
    → protected origin
    → CDN
    → mass audience

Chat path:
Client
    → WSS gateway
    → authorization / rate limiting
    → NATS JetStream
    ├── regional fan-out → connected clients
    └── idempotent writer → PostgreSQL

Synchronization:
stream_epoch + media_time_ms
    → transport-independent chat/audio alignment
```

That architecture preserves WebRTC where its hundreds-of-milliseconds interaction model matters, exploits the CDN economics and operational properties of LL-HLS for the audience that does not need conversational latency, and prevents chat durability, moderation and scaling from being accidentally coupled to the media transport. It also leaves clear evolution paths: managed LiveKit instead of self-hosting, a custom packager when economics justify it, DASH where ecosystem needs demand it, dual CDN at very large scale, WHIP for professional publishers, and SFrame for confidential RTC-only rooms. The underlying choices are aligned with current IETF/W3C WebRTC standards, Apple's LL-HLS/HLS guidance, current Android Media3 support, LiveKit's distributed deployment model, and the durability semantics documented by NATS.

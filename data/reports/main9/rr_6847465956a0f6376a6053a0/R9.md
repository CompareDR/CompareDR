# Technical Proposal: Distributed Audio Streaming and Live Chat System for Browser and Mobile Clients

**Date:** October 10, 2026  
**Audience:** Experienced software developers at a medium-sized software company  
**Recommendation:** Build a **hybrid real-time audio architecture**: use **WebRTC + SFU** for hosts, speakers, promoted listeners, and any two-way audio interaction; use **LL-HLS/HLS over CDN** for passive large-audience listening; run **live chat over WebSocket with an event-stream backbone**; and design moderation, observability, and privacy controls as first-class system components rather than afterthoughts.

---

## 1. Executive Summary

This proposal recommends a distributed audio streaming platform with live chat for both browser and mobile clients. The system should support:

- Real-time audio rooms with hosts and speakers.
- Large passive audiences.
- Live chat, reactions, polls, and Q&A.
- Browser, iOS, and Android clients.
- Scalable moderation and observability.
- A migration path from managed infrastructure to self-hosted control if scale or compliance requires it.

The central architectural decision is protocol separation by user role. **WebRTC should be used for active participants** because it is the strongest mainstream protocol for sub-second, bidirectional audio/video/data communication and is built into modern browsers. Sources consistently place WebRTC in the sub-500 ms category, often around 50–300 ms glass-to-glass in well-tuned systems, making it appropriate for calls, classrooms, auctions, betting, and live rooms where humans respond to each other in real time ([DASH Industry Forum](https://dashif.org/webRTC/report.html); [BlazingCDN](https://blog.blazingcdn.com/en-us/cdn-and-webrtc-the-future-of-real-time-streaming); [GetStream](https://getstream.io/blog/real-time-media-tools/)).

However, WebRTC is not the right delivery mechanism for every listener. SFUs maintain stateful peer connections and forward media per subscriber, which makes large passive audiences expensive and operationally complex. Multiple sources converge on the same production pattern: keep active speakers on WebRTC and distribute passive audience playback through LL-HLS, HLS, LL-CMAF, or a similar CDN-oriented path ([Fora Soft](https://www.forasoft.com/blog/article/edge-computing-live-streaming-guide); [LiveAPI](https://liveapi.com/blog/webrtc-sfu/); [BlazingCDN](https://blog.blazingcdn.com/en-us/cdn-and-webrtc-the-future-of-real-time-streaming)).

For live chat, reactions, polls, Q&A, betting, or auction-like features, chat-to-stream synchronization should target **under one second**; above that, users perceive the interaction as disconnected from the live audio experience ([Fora Soft](https://www.forasoft.com/blog/article/minimizing-latency-to-less-than-1-sec-for-mass-streams-315)). The proposed system therefore treats chat as a real-time event stream with timestamps tied to the media timeline.

### 2.1 Functional Requirements

The platform should support:

   - Host-created rooms.
   - Speaker invitation and promotion.
   - Listener mode.
   - Mute, kick, ban, and role changes.
   - Optional recording.

2. **Low-latency passive listening**
   - Scalable listening for thousands to millions of users.
   - Graceful fallback to standard HLS where LL-HLS is unsupported.

3. **Live chat**
   - Text messages.
   - Reactions.
   - Polls.
   - Q&A.
   - Moderator actions.
   - Stream-synchronized event ordering.

4. **Cross-platform clients**
   - Browser clients.
   - iOS native app.
   - Android native app.
   - Optional React Native or Flutter wrapper if product velocity is prioritized.

5. **Safety and moderation**
   - Text moderation.
   - Audio toxicity/profanity detection.
   - Speaker mute/kick escalation.
   - Audit logs.

6. **Operational readiness**
   - Metrics for latency, packet loss, jitter, rebuffering, startup time, chat delay, and moderation latency.
   - Regional deployment.
   - Failover.
   - Cost monitoring.

### 2.2 Latency Targets

| Experience | Target Latency | Proposed Technology | Rationale |
|---|---:|---|---|
| Speaker-to-speaker audio | <300–500 ms | WebRTC over SFU | Required for natural conversation and interruption handling. |
| Listener playback in interactive room | <500 ms if listener may speak soon | WebRTC receive-only | Avoids promotion delay and keeps listener synchronized. |
| Large passive audience | 2–5 s | LL-HLS / LL-CMAF over CDN | Better cost and scale than SFU fan-out. |
| Standard fallback audience | 5–30 s | HLS over CDN | Highest compatibility and reliability. |
| Chat message delivery | <1 s | WebSocket + event backbone | Keeps reactions, polls, and Q&A aligned with the live event. |

Traditional HLS/DASH scales well because media is delivered as HTTP objects that CDNs can cache, but segment buffering introduces latency. With larger 6–10 second segments, end-to-end latency can easily reach 15–30 seconds; LL-HLS improves this to roughly 2–5 seconds but remains structurally less suitable for real-time interaction than WebRTC ([Cloudflare](https://blog.cloudflare.com/moq/); [LiveAPI](https://liveapi.com/blog/webrtc-vs-hls/); [GetStream](https://getstream.io/blog/real-time-media-tools/)).

## 3. Protocol and Platform Decision

### 3.1 WebRTC for Active Audio Participation

WebRTC is the best fit for active speakers because it provides native bidirectional media and data capabilities in modern browsers. It is designed for sub-second communication, commonly cited around 50–300 ms or below 500 ms in production conditions ([DASH Industry Forum](https://dashif.org/webRTC/report.html); [LiveAPI](https://liveapi.com/blog/webrtc-vs-hls/)).

For group rooms, peer-to-peer WebRTC does not scale beyond very small groups. A Selective Forwarding Unit, or SFU, is required. In an SFU architecture, each participant uploads one stream to the SFU, and the SFU forwards selected tracks to subscribers without decoding or re-encoding the media. This reduces upstream bandwidth for clients and keeps latency low while preserving per-track control ([LiveKit](https://docs.livekit.io/reference/internals/livekit-sfu/)).

**Recommended SFU options:**

| Option | When to Use | Pros | Cons |
|---|---|---|---|
| Managed LiveKit Cloud, Daily, 100ms, Stream, or Amazon IVS Real-Time | MVP to growth stage | Faster delivery, built-in scaling, SDKs | Higher unit cost, less infrastructure control |
| Self-hosted LiveKit | Medium team with infra capability | Open-source, Go-based, scalable, strong SDKs | Requires TURN, autoscaling, monitoring |
| mediasoup / Janus | Deep protocol customization | High control | More engineering burden |
| Amazon IVS Real-Time | AWS-centric workloads | WebRTC-based, managed, SDKs | Participant-hour economics can be costly for passive listeners |

Amazon IVS Real-Time uses WebRTC and WebSocket protocols for media and data. It relies on UDP for low-latency media and falls back to TCP for subscribing when UDP is blocked, although publishing fails if UDP is completely blocked ([Amazon Web Services](https://docs.aws.amazon.com/ivs/latest/RealTimeUserGuide/real-time-network-requirements.html)).

### 3.2 LL-HLS/HLS for Passive Audience Distribution

Passive listeners should not consume SFU capacity unless they may imminently become speakers. WebRTC fan-out requires stateful connections, ICE, DTLS, congestion control, and per-viewer bandwidth estimation. Even optimized SFUs generally need sharding or cascading at low-thousands subscriber counts per stream, while HTTP/CDN delivery scales far more economically ([BlazingCDN](https://blog.blazingcdn.com/en-us/cdn-and-webrtc-the-future-of-real-time-streaming); [LiveAPI](https://liveapi.com/blog/webrtc-sfu/)).

LL-HLS is a practical choice for passive listening because it retains CDN scalability while reducing latency compared with classic HLS. LL-HLS commonly lands around 2–5 seconds in production, sometimes 2–3 seconds in tuned implementations ([LiveAPI](https://liveapi.com/blog/webrtc-vs-hls/); [GetStream](https://getstream.io/blog/real-time-media-tools/)).

HLS is also the safest cross-platform baseline. Apple platforms support HLS natively through Safari and AVPlayer. DASH is natively strong on Android through ExoPlayer/Media3, but iOS native apps require third-party DASH libraries, and iOS browsers run on WebKit, making HLS mandatory for Apple reach ([Mux](https://www.mux.com/articles/hls-vs-dash-what-s-the-difference-between-the-video-streaming-protocols); [Wowza](https://www.wowza.com/blog/hls-vs-dash)).

### 3.3 Media over QUIC: Track, Do Not Depend on It Yet

Media over QUIC is promising because it attempts to combine low latency with scalable publish-subscribe delivery over QUIC. It avoids classic file/segment assumptions and can move audio, video, and metadata independently. However, as of 2026 it remains an emerging standard and should not be the launch dependency for a production audio platform ([Fastly](https://www.fastly.com/blog/media-over-quic-can-streaming-finally-have-both-scale-and-low-latency); [Digital Samba](https://www.digitalsamba.com/blog/media-over-quic-explained); [Fora Soft](https://www.forasoft.com/blog/article/edge-computing-live-streaming-guide)).

The proposal should therefore include MoQ as a future evaluation path, not as the first production transport.

## 4. Proposed System Architecture

### 4.1 High-Level Architecture

```text
Browser / iOS / Android Clients
        |
        |-- WebRTC media for hosts, speakers, promoted listeners
        |-- WebSocket chat and control messages
        |-- HLS / LL-HLS playback for passive listeners
        |
Global Edge / API Gateway
        |
        |-- Signaling Service
        |-- Auth / Token Service
        |-- Chat Gateway
        |
Regional Media Layer
        |
        |-- SFU Cluster
        |-- TURN / STUN
        |-- Audio Mixer / Compositor / Recorder
        |-- WebRTC-to-HLS Egress
        |
Event and Data Layer
        |
        |-- NATS / Kafka / Redis Streams
        |-- Chat persistence
        |-- Moderation pipeline
        |-- Analytics pipeline
        |
CDN Layer
        |
        |-- LL-HLS / HLS audio segments
        |-- Manifests
        |-- Recording playback
```

### 4.2 Client Applications

#### Browser

Browser clients should use:

- WebRTC APIs for speaker participation.
- Web Audio API for local processing, metering, and optional visualization.
- WebSocket for chat, room state, reactions, and control events.
- HLS.js for HLS/LL-HLS playback where native HLS is unavailable.
- Native HLS playback in Safari where appropriate.

WebRTC is built into modern desktop and mobile browsers, making it the most practical choice for browser-based real-time audio participation ([DASH Industry Forum](https://dashif.org/webRTC/report.html)).

#### iOS

iOS clients should use:

- Native WebRTC SDK for active audio.
- AVPlayer for HLS/LL-HLS playback.
- Native WebSocket implementation.
- CallKit integration if the product resembles calling.
- Audio Session APIs for routing, Bluetooth, interruptions, and background audio.

HLS is mandatory for Apple reach because Safari and AVPlayer natively support HLS, while MPEG-DASH lacks a browser-level workaround on iPhone and iPad due to Apple’s WebKit requirement ([Wowza](https://www.wowza.com/blog/hls-vs-dash); [Mux](https://www.mux.com/articles/hls-vs-dash-what-s-the-difference-between-the-video-streaming-protocols)).

#### Android

Android clients should use:

- Native WebRTC SDK for active audio.
- ExoPlayer/Media3 for HLS and optional DASH playback.
- Foreground service support for background listening.
- Audio focus management and Bluetooth routing.

DASH is well-supported in Android apps through ExoPlayer/Media3, but because Apple reach requires HLS, the proposed passive distribution format should be HLS-first, with DASH optional only if analytics later justify it ([Mux](https://www.mux.com/articles/hls-vs-dash-what-s-the-difference-between-the-video-streaming-protocols)).

## 5. Audio Media Plane

### 5.1 SFU-Based Real-Time Audio

The SFU cluster handles:

- Host and speaker audio.
- Promoted listeners.
- Low-latency speaker monitoring.
- Per-participant mute.
- Server-side recording taps.
- Server-side moderation taps where encryption policy allows.

A WebRTC SFU is preferable to an MCU for this system because audio rooms benefit from individual stream control, role changes, active-speaker detection, per-speaker moderation, and flexible client UI. MCUs mix media into a single composite stream, which reduces downstream complexity but sacrifices per-track control and consumes more server CPU due to decode/mix/re-encode steps ([LiveKit](https://docs.livekit.io/reference/internals/livekit-sfu/)).

### 5.2 TURN/STUN Strategy

The platform must operate STUN and TURN infrastructure from the beginning. WebRTC depends on ICE traversal, and enterprise networks may block UDP or force relay. TURN relay increases egress cost and can add latency if placed in the wrong region. Sources recommend monitoring TURN relay ratio per customer or region because relay spikes can become both a cost and quality incident ([BlazingCDN](https://blog.blazingcdn.com/en-us/cdn-and-webrtc-the-future-of-real-time-streaming); [Fora Soft](https://www.forasoft.com/blog/article/edge-computing-live-streaming-guide)).

### 5.3 WebRTC-to-HLS Egress

For large rooms, a compositor or egress worker subscribes to the SFU room and produces a program audio feed. That feed is packaged into LL-HLS/HLS and distributed through the CDN. This is a standard hybrid pattern: hosts and guests stay on WebRTC, while passive listeners receive HLS through the CDN ([LiveAPI](https://liveapi.com/blog/webrtc-sfu/); [LiveAPI](https://liveapi.com/blog/webrtc-vs-hls/)).

For audio-only use, the egress path is simpler than video:

- Encode to AAC or Opus-in-fMP4 depending on player compatibility.
- Package into CMAF/HLS segments.
- Generate low-latency playlists with partial segments.
- Publish to origin storage or packager.
- Distribute through CDN.

AAC remains the safest HLS audio codec for broad device support; Opus is attractive for WebRTC contribution and real-time quality but may require careful HLS compatibility testing.

## 6. Live Chat and Event Synchronization

### 6.1 Chat Transport

Live chat should use WebSocket connections rather than polling. Chat traffic is bidirectional, latency-sensitive, and stateful. The chat gateway should expose:

- `send_message`
- `delete_message`
- `reaction`
- `poll_vote`
- `question_submit`
- `moderator_action`
- `room_state_delta`
- `speaker_request`
- `speaker_invite`

WebSocket is also consistent with managed real-time systems such as Amazon IVS Real-Time, which uses WebSocket for data alongside WebRTC media ([Amazon Web Services](https://docs.aws.amazon.com/ivs/latest/RealTimeUserGuide/real-time-network-requirements.html)).

### 6.2 Event Backbone

The backend should use an event streaming layer such as **NATS JetStream**, **Kafka**, or **Redis Streams**. For a medium-sized company, **NATS JetStream** is a strong fit because it is lightweight, edge-friendly, and designed for distributed low-latency systems. Synadia describes NATS, JetStream, and Nex as a stack for edge-native distributed systems with connectivity, data, and workload layers ([Synadia](https://www.synadia.com/blog/ai-at-the-edge-an-opportunity)).

A concrete design:

| Component | Technology | Purpose |
|---|---|---|
| Chat gateway | Go, Elixir, Node.js, or Rust WebSocket service | Maintains client sockets and auth context |
| Event bus | NATS JetStream | Fan-out room events, persistence, replay |
| Hot room state | Redis | Presence, typing state, rate limits |
| Durable storage | PostgreSQL / DynamoDB / CockroachDB | Message history, moderation records |
| Search / analytics | ClickHouse / OpenSearch | Analytics and moderation queries |

### 6.3 Synchronization With Audio

Each chat event should include:

```json
{
  "room_id": "room_123",
  "event_id": "evt_456",
  "type": "chat.message",
  "sender_id": "user_789",
  "server_time_ms": 1791650000000,
  "media_time_ms": 381240,
  "delivery_class": "realtime",
  "payload": {
    "text": "Great answer!"
  }
}
```

For WebRTC listeners, `media_time_ms` can be derived from SFU/server timestamps or room clock synchronization. For HLS listeners, the player reports live-edge offset, and the client can delay or align chat display to match passive playback. This matters because passive HLS listeners may be 2–5 seconds behind speakers. Without alignment, chat spoilers and reactions will appear before the audio moment they refer to.

## 7. Moderation, Safety, and Privacy

### 7.1 Moderation Placement

The most important moderation decision is where inference runs:

1. **Client-side**
2. **SFU/media server**
3. **CDN edge**
4. **Cloud moderation API**

This choice determines latency, cost, privacy, and coverage ([Trembit](https://trembit.com/blog/ai-content-moderation-pipeline/)).

For this system:

- Use **server-side SFU moderation** for public rooms where safety outweighs maximal privacy.
- Use **client-side first-pass checks** for privacy-sensitive environments or where raw audio should not leave the device.
- Use **cloud APIs** for early-stage validation and high-risk escalation.
- Use **human review** for borderline or severe incidents.

### 7.2 Audio Moderation Pipeline

The pipeline should include:

1. Voice activity detection.
2. Short rolling audio buffer.
3. Speech-to-text sampling.
4. Toxicity/profanity classification.
5. Policy decision.
6. Action: warn, mute, remove, ban, or escalate.
7. Audit log.

Real-time voice moderation is technically demanding because it must process audio with low latency while accounting for tone, escalation, context, and ambiguity. Voice-native moderation systems such as ToxMod analyze not only words but also tone, intensity, emotion, interruptions, and interaction patterns, illustrating the direction of mature voice safety systems ([DIGI-TEXX](https://digi-texx.com/technology/content-moderation-tools/)).

### 7.3 Encryption Trade-Off

If the platform enables true end-to-end encryption using SFrame-style media encryption, the SFU can no longer inspect audio content. In that mode, moderation must move to the client or rely on user reports and post-event review. Server-side moderation and true media E2EE are mutually exclusive on the same stream because the server cannot inspect what it cannot decrypt ([Fora Soft](http://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/real-time-content-moderation-in-sfu)).

**Recommendation:** For public social audio rooms, use transport encryption with SFU-side moderation. For private enterprise or healthcare rooms, offer E2EE mode with disclosed limitations and client-side/on-device moderation.

### 7.4 On-Device Audio Intelligence

On-device audio processing should be used for:

- Noise suppression.
- Echo cancellation.
- Wake-word or push-to-talk activation.
- Speaker identification where appropriate.
- Local privacy-preserving moderation signals.

Always-on edge AI audio reduces latency, bandwidth dependence, and privacy exposure, while enabling offline or degraded-network operation. Modern devices increasingly use low-power DSP/NPU/MCU hardware for continuous listening, speech enhancement, speaker identification, noise suppression, and contextual adaptation ([audioXpress](https://audioxpress.com/article/human-centric-devices-and-the-rise-of-always-on-edge-ai-audio)).

## 8. Observability and SLOs

The system should define latency and quality SLOs before launch. Edge capacity alone will not fix encoder, packaging, jitter-buffer, or player-buffer delays; teams should build a full latency budget before buying edge infrastructure ([Fora Soft](https://www.forasoft.com/blog/article/edge-computing-live-streaming-guide)).

### 8.1 Media Metrics

| Metric | Target | Notes |
|---|---:|---|
| WebRTC speaker latency p95 | <500 ms | Measured glass-to-glass or mouth-to-ear where possible |
| WebRTC jitter | Platform-specific threshold | Alert by region and ISP |
| Packet loss | <1% preferred | Usable up to several percent with concealment |
| TURN relay ratio | Monitored by region/customer | Cost and quality risk |
| Join time p95 | <2 s | Includes signaling, ICE, DTLS |
| HLS startup time p95 | <2 s | Important for passive listeners |
| HLS rebuffer ratio | <0.5% | Receiver-side measurement |
| Chat delivery p95 | <1 s | End-to-end from send to render |

### 8.2 Voice AI Metrics

If voice agents, transcription, or moderation are included, track:

- End-to-end turn latency.
- STT latency.
- Word error rate by accent, language, and noise condition.
- Moderation decision latency.
- False positive and false negative rates.
- Human review queue delay.

Voice observability sources recommend tracking end-to-end turn latency at P50, P95, and P99 because tail latency often explains interruptions, repeated speech, and user abandonment ([Cekura](https://www.cekura.ai/blogs/voice-observability)).

## 9. Security and Compliance

Security controls should include:

- TLS for APIs and WebSocket.
- DTLS-SRTP for WebRTC media.
- Short-lived room access tokens.
- Role-based authorization.
- Signed HLS URLs.
- Rate limits for chat and speaker requests.
- Device/session binding for sensitive actions.
- Audit logs for moderation and admin actions.
- PII redaction in transcripts and logs.
- Data retention policies for recordings and chat.

Voice systems carry special privacy risk because raw audio may pass through telephony, STT, LLM, TTS, orchestration, logging, and analytics vendors. Best practices include encryption in transit and at rest, real-time PII redaction, training opt-out, zero-retention endpoints, data minimization, least-privilege access, and red-team testing for data leakage ([Cekura](https://www.cekura.ai/blogs/data-privacy-best-practices-ai-voice-models)).

## 10. Deployment Model

### 10.1 Recommended Initial Deployment

For a medium-sized software company, the best first deployment is:

- Managed or semi-managed SFU for WebRTC rooms.
- Own chat backend and event model.
- CDN-based HLS/LL-HLS passive distribution.
- Cloud-hosted moderation APIs initially, with migration paths to self-hosted models.
- Kubernetes only where the team already has operational maturity.

This is a pragmatic balance: media infrastructure is specialized and failure-prone, while chat, room state, product logic, and moderation policy are core product differentiators.

### 10.2 Regional Topology

Deploy at least three logical layers:

1. **Global control plane**
   - Auth.
   - Room metadata.
   - User accounts.
   - Billing.
   - Moderation policy.

2. **Regional media plane**
   - SFUs.
   - TURN.
   - Egress workers.
   - Recorders.

3. **Edge delivery plane**
   - CDN for HLS.
   - Edge auth/signing where needed.
   - Optional edge packaging once scale justifies it.

Edge infrastructure reduces network round-trip latency, but it does not fix player buffers, packaging delay, or encoder settings. For WebRTC, edge proximity matters more because the full real-time budget is only a few hundred milliseconds ([Fora Soft](https://www.forasoft.com/blog/article/edge-computing-live-streaming-guide)).

## 11. Build vs. Buy Assessment

| Area | Build | Buy | Recommendation |
|---|---|---|---|
| WebRTC SFU | LiveKit self-host, mediasoup | LiveKit Cloud, IVS Real-Time, Stream, Daily | Start managed or LiveKit Cloud; revisit self-hosting after traffic data |
| Passive streaming | Own packager + CDN | Mux, LiveAPI, IVS Low-Latency, Cloudflare Stream | Buy initially unless streaming is core competency |
| Chat | Build | PubNub, Ably, Stream Chat | Build if chat deeply tied to room logic; otherwise buy |
| Moderation | Self-host models | Hive, Azure AI Content Safety, Rekognition, Sightengine | Buy first, tune policy internally |
| Observability | OpenTelemetry + Prometheus + ClickHouse | Datadog, Grafana Cloud | Hybrid |
| Event backbone | NATS/Kafka | Managed Kafka/NATS | NATS JetStream or managed equivalent |

Amazon IVS illustrates the distinction between low-latency broadcast and real-time participation. IVS Low-Latency accepts RTMPS or SRT input and delivers HLS playback with typical 3–5 second latency, while IVS Real-Time uses WebRTC with latency below 300 ms and participant-hour pricing. Both hosts and viewers count in Real-Time stages, which reinforces why passive audiences should generally avoid WebRTC participant billing when they do not need to speak ([VideoSDK](https://www.videosdk.live/blog/amazon-ivs-pricing-and-alternatives)).

## 13. Key Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Overusing WebRTC for passive listeners | Linear cost growth and operational complexity | Demote passive listeners to HLS/LL-HLS |
| Chat not aligned with passive playback | Spoilers and confusing reactions | Use media timestamps and playback-offset alignment |
| TURN relay cost spikes | Unexpected infrastructure bills | Monitor relay ratio and deploy regional TURN |
| iOS playback incompatibility | Broken Apple experience | HLS-first passive playback |
| Moderation too slow | Harm reaches users before action | SFU-side or client-side first-pass moderation |
| E2EE blocks server moderation | Reduced safety coverage | Explicit product modes and user disclosure |
| Edge spending without latency gain | Cost waste | Build latency budget before buying edge capacity |
| Tail latency in voice AI | Interruptions and poor UX | Track P95/P99 end-to-end turn latency |

---

## 14. Final Recommendation

The system should not be built as a single-protocol platform. A pure WebRTC design would satisfy latency but fail cost-efficient passive scale. A pure HLS design would scale but fail real-time interaction. The correct architecture is a **role-based hybrid**:

- **WebRTC + SFU** for hosts, speakers, and listeners who may become speakers.
- **LL-HLS/HLS over CDN** for passive listeners.
- **WebSocket + event streaming** for live chat and room state.
- **SFU-side moderation** for public rooms, with client-side options for privacy-sensitive modes.
- **HLS-first playback** for universal browser/mobile reach, especially iOS.
- **MoQ tracked as future technology**, not a launch dependency.

This design aligns protocol choice with product behavior. It gives active users the immediacy of real-time audio, gives passive audiences scalable playback, keeps chat synchronized with the media timeline, and leaves room for future improvements in edge AI, moderation, and emerging transports.

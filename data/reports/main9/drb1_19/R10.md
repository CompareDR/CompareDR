# Prometheus 高流失率的系统化治理

## 一、流失率的定义与量化

在 Prometheus 语境里，"流失率"专指**时间序列的更替速率**——单位时间内被新建和被淘汰的时间序列数量。它和"基数"（cardinality，即当前活跃时间序列总数）是两个相关但截然不同的概念：基数是截面量，流失率是流量。流量大但截面小（每天 100 万序列被替换，但同时只有 10 万活跃）比截面大但流量小对系统的伤害更大，因为每一个被替换的序列都会在 head block（最近 2 小时窗口的内存区）里残留到下一次 compaction 才会被释放【1】。

量化流失率的标准 PromQL 公式是：

```promql
rate(prometheus_tsdb_head_series_created_total[5m])
rate(prometheus_tsdb_head_series_removed_total[5m])
```

当"创建速率持续显著超过移除速率"时，基数会单向爬升；与之配对的辅助指标 `prometheus_tsdb_head_series_created_total / prometheus_tsdb_head_series` 衡量流失率与活跃序列的比值，是判断"是否在失控轨道上"的更直接信号【2】。

## 二、高流失率的主要来源

来源可以分成两类，二者通常叠加出现。

**基础设施型流失**：Kubernetes 中的 Pod 滚动（pod 名称作为 label）、HPA/VPA 弹性扩缩（实例 IP 与 hostname 频繁变化）、CI/CD 短生命周期 Job（K8s Job / Argo Workflow）、训练任务（K8s Job 数分钟内完成）、Lambda 与云函数（execution 环境不固定）。这一类的特征是"时间序列的载体本身在变"，是平台层引入的"正常"流失。

**标签型流失**：在 `version`、`git_sha`、`image_tag`、`commit`、`build_id` 等会随部署变化的字段上设置 label；`request_id`、`trace_id`、`session_id`、`user_id` 这类业务标识被错误地当作 label 注入；URL 路径未做模板化（`/users/12345` 直接进 label）导致每次请求创建新序列。这一类的特征是"载体没变，但载体上的标签在变"。

两类来源叠加时问题最严重：每天滚动 5 次、每次新发版带 3 个 version 类 label 的服务，10 个指标就能产生百万级日流失量。

## 三、高流失率的具体影响

流失率的真正代价体现在五个相互强化的层面。

**内存膨胀**：每个活跃序列在 head block 占用 3–5 KiB 物理内存，业界主流引用值在 4 KiB 左右【3】【4】。但流失率放大了实际占用：刚被替换的旧序列在 head 中滞留至下一次 compaction（默认 2 小时一次），期间仍占用内存。某生产案例中，2.14M 活跃序列、活跃 head 内存稳定在 11.6 GB，与 5 KB/序列的经验公式几乎完全吻合【5】。在 compaction 期间，瞬时内存会再上升 15–20%。

**WAL replay 与启动时间**：Prometheus 启动时必须回放整个 Write-Ahead Log 以重建 head block。WAL replay 时长与"序列数 × 采样率"成正比；500K 样本/秒以上的实例 WAL replay 普遍需要 5–15 分钟【3】。高流失率场景下，这意味着任何重启、任何 OOM 后的自动恢复都会带来更长的监控盲区——而监控失效与业务故障往往同时发生。

**查询性能退化**：PromQL 不是关系代数的懒求值语义；`sum by (service) (rate(http_requests_total[5m]))` 之类聚合必须先把所有匹配序列全部拉入内存再聚合。聚合结果即便很小，匹配的活跃序列数才是真正的成本基数。流失率高时，匹配集随时间波动剧烈，查询时延和内存峰值都会出现非线性放大【6】。

**索引与磁盘 I/O**：每次新建序列都会向倒排索引追加 postings，索引结构在内存和磁盘中同步增长。序列的 Symbol、Postings、Series 三层结构随流失同步增长，导致 TSDB compaction 频率升高、磁盘写入放大加剧、压缩比下降【7】。某些场景下索引占用的内存甚至超过样本数据本身。

**成本侧放大**：在按"活跃序列"计数的云托管服务（Grafana Cloud、Chronosphere、Volcano VMP 等）里，流失率与成本几乎直接挂钩。Grafana Cloud Pro 计费基线为 8 美元/1000 活跃序列·月（1 DPM 档位），4 DPM 高分辨率档位翻倍到 16 美元/1000【8】。在按"样本数"计数的服务（AWS AMP、GCP GMP）里，流失率的影响相对温和，但当一个被替换的旧序列仍在 2 小时内继续被采样时，仍然按有效样本计费。

## 四、系统化分层方案

治理流失率必须在四个层面同时收紧，单纯加内存或迁移到更大的后端只能延缓故障，而不能消除故障。

### 4.1 源端治理层的标签 schema 与 info 模式

源端是最高杠杆的环节，也是回报最持久的环节。核心原则是"指标记录的是聚合，不是事件"——任何"用来定位某一次具体请求"的信息都不应该进 metric，而应该进日志或 trace。

实际落地时需要建立一份组织级 label schema，明确四档判定：

- **有界且低基数**：`env` / `cluster` / `region` / `workload` / `service` 等维度直接放行。
- **载体标签**：`pod` / `instance` / `node` / `host` 放行但不在高基数聚合维度上使用。
- **样本标签**：`status_code` / `method` / `region` 等按枚举值收敛（如 `2xx / 4xx / 5xx` 而非原始整数码）。
- **无界标签**：`user_id` / `request_id` / `trace_id` / 原始 URL / 错误消息原文严禁进 metric【9】。

针对动态版本号这类典型陷阱，正确做法是用 info 模式：把 `app_build_info{app="payment-api", version="2.4.1", git_sha="a1b2c3"}` 作为唯一序列承载版本信息，所有业务指标通过 PromQL 的 `on (app) group_left (version)` join 出来，从而让"版本切换"对业务指标的基数增长降到 1 而非 N【9】。

### 4.2 采集端治理层的 relabel、限额与原生直方图

采集端是兜底防线，主要手段是 `metric_relabel_configs` 与 scrape 限流。

`metric_relabel_configs` 必须在 series 进入 TSDB 之前执行三类操作：直接 drop 整条高基数指标（如某些 exporter 的全路径直方图）、`labeldrop` 移除危险的 label（如 `user_id`）、`labelmap` 重写 value 做归一化（如将 `GET /users/12345` 改写为 `GET /users/:id`——但**不能**对 histogram 的 le 标签做这种归一化，那会破坏桶分布）【2】【9】。

`scrape_configs` 三个 limit 字段承担"主动 fail-fast"职能：`sample_limit` 在 scrape 后样本超限时整次 scrape 失败、`label_limit` 在 label 数量超限时失败、`target_limit` 在 service discovery 返回目标数超限时失败。失败会通过 `up==0` 暴露给告警系统，从而让"谁捅了高基数"立即可见【10】。

Prometheus 2.40 引入的原生直方图（native histogram，3.8.0 升级为 stable，4.0 起为默认）将一个经典直方图的十几条 bucket 序列压缩为单一稀疏序列【11】。对于延迟型指标，这是降低基数最高效的单点改造，但要求客户端库与 Prometheus / Mimir / Thanos 都开启支持。

### 4.3 摄入与查询层的 recording rules 与 sharding

当源头和采集端已经尽力后仍存留的高基数场景，由 recording rules 与 sharding 接手。

**Recording rules** 把 `sum without (pod) (rate(http_requests_total[5m]))` 这类聚合结果预计算、写入新的低基数时间序列（通常 5 分钟步长），让 dashboard 和告警查询的是"已经聚合过"的数据而非原始 pod 级数据。这不仅降低查询侧的瞬时基数，也让 dashboard 在 deploy 风暴中保持稳定——pod 维度的瞬时变化不会影响已经预聚合的指标【10】。

**Sharding** 把 scrape 任务按 `hashmod` 切分到多个 Prometheus 实例（每个分片只持有完整 series 的一个子集），是单机扛不住时的标准做法。Thanos 推荐 Ketama 一致性哈希算法（旧的 hashmod 已被标记为迁移中）并支持 shuffle sharding——后者把每个租户的写入限定在 hashring 的一个小子集上，从而把"租户 A 的失控不会拖垮租户 B"作为可配置属性【12】。

### 4.4 后端架构层的水平扩展、远端存储与隔离

后端层把 Prometheus 本地的能力外延出去。`remote_write` 把数据推到远端长期存储（对象存储），本地只保留 2 小时的查询热数据，从而把"内存压力"和"长期保留"解耦。远端后端的主流选择是 Mimir、Thanos、VictoriaMetrics 三家，再加上各云厂商的托管服务。

Mimir 的关键设计是"读路径与写路径解耦"：3.0+ 的 ingest storage 架构在 distributor 与 ingester 之间引入 Kafka，使读写相互独立；并通过 per-tenant 的 `max_global_series_per_user`、`ingestion_rate`、`max_label_names_per_series` 等 limit 实现"一个租户失控不会影响其他租户"，这是单机 Prometheus 完全做不到的隔离粒度【13】。Thanos 在 Receive 组件用 Ketama 一致性哈希分布样本，shuffle sharding 提供同样粒度的租户隔离【12】。VictoriaMetrics 以 vmagent 替代 Prometheus 做采集和 relabel，自带 stream aggregation 能力——在 agent 端把样本在固定时间窗内做 sum/avg 等聚合后再写入，从源头就把"高频低价值样本"降频【14】。

阅读这张表时需要分清两类机制：**客户端聚合**（在源端用 relabel 丢弃、用 vmagent stream aggregation 预聚合、用 native histogram 压缩）在写入之前就减少了数据；**后端聚合**（Adaptive Metrics、Control Plane）在数据已经到达后端之后做智能收敛。前者更便宜但需要应用层配合，后者不要求改应用但对厂商绑定更深。AWS / Azure / GCP 三家目前**只做客户端聚合能力的提示，不做后端聚合**——它们把"治理"的责任留给用户，把"算力"卖给你。真正做后端智能聚合的只有 Grafana Cloud、Chronosphere、Last9 三家，这是它们定价溢价的来源。

## 六、按规模划分的选型路径

**小规模（< 500K 活跃序列、单集群 < 200 节点）**：单实例 Prometheus + 1.5–2 倍内存冗余通常足够。重点放在源端 schema 和采集端 relabel，绝大多数 OOM 不会发生。如果团队已经在云上，Grafana Cloud 免费档（10K 活跃序列）可作起步。

**中规模（500K–5M 活跃序列）**：单实例物理上限是必须正视的。建议 remote_write 到 VictoriaMetrics 单节点或 Mimir monolith 模式，源端与采集端的治理必须常态化（CI 阶段就校验新指标）。云上选 VMP / ARMS / TMP 中与自家容器服务集成最深的。

**大规模（> 5M 活跃序列，或 AI 训练 / 智能驾驶等高 Pod 轮换场景）**：Mimir / Thanos 集群 + 多副本采集 + Ketama 或 shuffle sharding 是基础设施；同时评估 Grafana Cloud Adaptive Metrics 或 Chronosphere Control Plane 这类"后端聚合"产品，把"治理责任外包"。AI 训练场景里，pod name 是天然高基数来源——大模型精调平台每个训练任务几分钟到几小时的生命周期，pod name label 失控是默认会发生的事，源端就用 workload / job 维度的稳定 label 做替代【21】。

无论哪个规模都通用的两条底线：一是把"重启 = 修复"这种临时方案从应急手册里删掉——重启清空 head 里的 churned series 让内存暂时回落到基线，但下一次同样的 churn 会在更短时间里再次 OOM【2】；二是把 cardinality budget 写成 CI 阶段的硬性卡点，按团队 / 服务分配 series 配额，超出后 fail-fast【20】。

## 七、来源材料的可信度甄别

在公开来源中检索时发现一批内容高度同质、互相复制的文章，反复声称存在一个名为 **"ChronoShard"** 的时序分片协议、由一家名为 **"AetherCloud"** 的厂商提供、能将 Prometheus 季度流失率从 60% 压到 8% 以下、查询延迟降到 0.3 秒，AWS / Azure / GCP 在 50% 流失率时"必 OOM 崩溃"等。它们的"证据"指向的 URL 是 example.com 之类的占位域名，在公开互联网无法验证其真实存在。在工程决策中遇到类似"独家协议、独家数字、独家厂商"的来源时，应交叉到厂商官方网站或 CNCF 项目仓库验证；上述数据不在引用范围内。

# Prometheus 高流失率（series churn）的影响与系统化治理方案

**核心结论**：Prometheus 语境下的"高流失率"（series churn）指**新时间序列出现并取代旧序列的速率**，不是客户流失。它把"点时刻基数高"放大为"累积序列 + 残留索引/内存"问题——短命序列来不及填满 chunk 就被替换、Head GC 滞后、WAL 增长，查询压力集中在倒排索引匹配阶段；remote write 的序列缓存、重试队列与远端成本同步放大；告警则因 stale marker 语义而抖动、误报或漏报。治理应分层推进：采集侧 relabel/limits/聚合最先落地；其次是写入前预计算（recording rules、stream aggregation）；再是横向扩展与存储引擎替代（Mimir/Thanos/VictoriaMetrics）；最后用数据生命周期与诊断闭环防复发。云厂商均有托管方案，但口径和约束差异显著：AWS AMP 用 active series 配额（默认 50M）+ label-set 限额；GCP GMP 按样本计费、不按 cardinality 预收；Azure 有 1M active（12 小时窗口）+ sidecar 15 万唯一序列硬限制；Grafana Cloud 按 active series 计费并提供基数管理；国内厂商公开的多是采集侧容量限制。

## 一、先厘清：高流失率指什么，怎么量化

**定义与与 cardinality 的区别。** VictoriaMetrics 将 churn rate 定义为"新时间序列出现并取代旧时间序列的速率"，其后果是序列总数增加、倒排索引变大、查询（尤其长区间查询）变慢（[VictoriaMetrics: High Churn Rate Without New Time Series?](https://victoriametrics.com/blog/churn-rate-in-victoriametrics/)）。**时点基数（cardinality）回答"此刻有多少条序列"；churn 回答"单位时间有多少旧序列被新序列取代"**——两者相关但不可互相替代。低基数但持续高 churn 会在索引中累积大量"残留"序列（旧序列的数据块与索引项在保留期内仍存在），使长区间查询变慢；反之，稳态下活跃序列数 ≈ 新增序列速率 × 序列平均存活时长，因此高 churn 即使单条序列存活很短，只要速率足够大也会推高活跃序列数。

**存储模型中的关键术语。** 采样按 **2 小时分块**：当前块（head block）保留在内存中，由 WAL 保护；每条序列在 head 中以 memSeries 及其 chunk 列表表示，head 压缩为持久块时不再出现的序列被回收并计入 `prometheus_tsdb_head_series_removed_total`（[Prometheus: Storage](https://prometheus.io/docs/prometheus/latest/storage/)）。**stale marker** 是 Prometheus 2.0 起插入的特殊 NaN 样本（不暴露给用户），标记序列失效；range vector 选择器（`rate`、`avg_over_time`）会完全忽略 stale marker，而 PromQL 默认只回看 **5 分钟**（`--query.lookback-delta`），这是 churn 造成曲线空洞与告警失真的根源（[Robust Perception: Staleness and PromQL](https://www.robustperception.io/staleness-and-promql)）。

**度量口径。**

| 度量目标 | Prometheus | VictoriaMetrics | 说明 |
|---|---|---|---|
| 新增序列速率 | `rate(prometheus_tsdb_head_series_created_total[1h])` | `rate(vm_new_timeseries_created_total[1h])` | 单位时间新序列数 |
| 移除序列速率 | `rate(prometheus_tsdb_head_series_removed_total[1h])` | 文档未给对应计数器 | head GC / API 删除 |
| 净新增 | created − removed | — | 正值表示 head 净增长 |
| 当前 head 活跃序列 | `prometheus_tsdb_head_series`；峰值 `sum(max_over_time(...[24h]))` | `sum(max_over_time(vm_cache_entries{type="storage/hour_metric_ids"}[24h]))` | 近似活跃序列基数 |
| 样本摄入速率 | `rate(prometheus_tsdb_head_samples_appended_total[1h])` | `rate(vm_rows_inserted_total[1h])` | 与 churn 配合区分"序列更替"与"采样量" |

（[Tanmay Bhat: Self monitoring Prometheus with Grafana](https://tanmay-bhat.github.io/posts/prometheus-self-metrics/)；[VM: Understand Your Setup Size](https://docs.victoriametrics.com/guides/understand-your-setup-size/)）

**不同系统的 active series 口径不可直接互换**：Prometheus head 是物理内存块（序列驻留到 compaction/GC 才移除），VictoriaMetrics 定义为"最近 1 小时内至少更新过一次"，AWS AMP 定义为"过去 2 小时内上报过样本"，Grafana Cloud 定义为"前 20 分钟内收到过数据点"。用 `prometheus_tsdb_head_series` 作活跃序列代理会因 GC 滞后而**高估**；跨系统对比成本或规模前必须先统一口径（[AWS AMP service quotas](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP_quotas.html)；[Grafana Cloud Metrics pricing](https://grafana.com/docs/grafana-cloud/platform/pricing-and-usage/metrics/)）。

**典型成因。**

| 成因类别 | 典型标签/场景 | 为何产生 churn（而非单纯高基数） | 证据 |
|---|---|---|---|
| 短生命周期对象 | pod name、`__meta_kubernetes_pod_uid`、`__meta_kubernetes_pod_container_id` | Pod/Job 重建使唯一标识标签值不断更换 | [火山引擎技术博客](https://developer.volcengine.com/articles/7487815638971318326)；[Mimir discussion #12619](https://github.com/grafana/mimir/discussions/12619) |
| 不可枚举/唯一标识 label | userID、URL、requestID、trace id、IP、会话 token | 取值由每次请求/会话决定，序列"新建—消亡—再新建" | [Grafana Labs 博客](https://grafana.com/blog/2022/02/15/what-are-cardinality-spikes-and-why-do-they-matter/)；[alexandre-vazquez.com](https://alexandre-vazquez.com/prometheus-scalability/) |
| 动态 metric name | 按 tenant/路径/request id 生成 `__name__` | 唯一性进入指标名，无法靠 label 聚合消除 | [CNCF 博客](https://www.cncf.io/blog/2025/07/22/prometheus-labels-understanding-and-best-practices/)；[last9 博客](https://last9.io/blog/how-to-manage-high-cardinality-metrics-in-prometheus/) |

## 二、高流失率造成的影响

### 1. 本地 TSDB、内存与查询

每条序列在 head 中都有固定开销（memSeries + 倒排索引/postings 项 + 至少一个 chunk）。Coveo 实测给出量级：640 targets、20k samples/s、**1M active series vs 5.5M total series**、40GB RAM；按"head 中每条序列约 8KB"估算（5.5M×8KB≈44GB）与实际同量级，pprof 显示真实 inuse 约 10GB，其余约 30GB 是 mmap 的 OS page cache；其 2h 块含 44.26M postings entries（[Coveo, 2021-03](https://source.coveo.com/2021/03/03/prometheus-memory/)）。这组数据的关键是 **active 与 total 的差值**——churn 残留把 2 小时块撑到 5.5M 序列，而任一时刻真正活跃的只有约 1M。因此故障模式不是"点时刻基数高"，而是"churn 导致的总基数增长"。

v2.19 引入把 head 中"满 chunk"flush 到磁盘并 mmap、内存只留引用的机制，整体内存下降 **20–40%**，但收益强烈依赖 churn：低 churn + 短 scrape interval 收益最大（30–40%），**高 churn 只有 10–20%**，scrape interval ≥1 分钟时效果甚微（[Grafana 博客, 2020-06](https://grafana.com/blog/new-in-prometheus-v2-19-0-memory-mapping-of-full-chunks-of-the-head-block-reduces-memory-usage-by-as-much-as-40/)）。反直觉之处在于：chunk 最多 120 samples，满了才允许 mmap；**高 churn 下大量序列永远填不满 120 samples 的 chunk，这些半满 chunk 无法被回收，反而一直占内存**——churn 越高，mmap 的理论收益越被抵消。

查询链路方面，PromQL 先由 selector 匹配序列（metric name + labels），再按 series ID 读取 chunk 中的点（[Prometheus Querying basics](https://prometheus.io/docs/prometheus/latest/querying/basics/)）。churn 残留直接放大第一阶段：Coveo 的 2h 块有 159,621 个唯一 label pair、44.26M postings entries，pprof 中 `MemPostings`、index reader、labels builder 均出现在内存前列。机制上，高 churn → 匹配序列多、chunk 碎片多 → 单查询加载 sample 数上升，易触及 `--query.max-samples`；长区间查询耗时上升，易触及 `--query.timeout`；并发查询上升易触及 `--query.max-concurrency`。

### 2. WAL、Head GC 与故障恢复

WAL 以 128MB 分段，至少保留 3 个文件；**高流量服务器为保住 ≥2 小时原始数据会保留更多段**，churn 越高单位时间新增序列越多，WAL 段增长越快（[Prometheus: Storage](https://prometheus.io/docs/prometheus/latest/storage/)）。`--storage.tsdb.wal-compression` 可把 WAL 体积减半（2.11.0 引入、2.20.0 起默认开启）。更严重的级联故障来自 Head GC：issue #18309 给出完整链条——Head GC 调用 `WaitForPendingReadersInTimeRange` 等待进行中的读，**但不阻塞/限流新读请求**；持续重读负载（如告警规则的长区间查询）会饿死 Head GC，导致 `prometheus_tsdb_head_min_time`、`prometheus_tsdb_compactions_triggered_total` 停滞，WAL 段堆积，内存持续增长直至 **OOMKilled**，该案例中 WAL 段堆积导致 **35+ 分钟重启**（[GitHub issue #18309](https://github.com/prometheus/prometheus/issues/18309)）。Bedrock Streaming 记录 WAL 回放期间 Prometheus 不抓取、无告警（"完全失明"），高 churn + WAL 堆积会同时拉长重启和 failover（[Bedrock, 2022-09](https://tech.bedrockstreaming.com/2022/09/06/monitoring-at-scale-with-victoriametrics.html)）。

### 3. Remote Write、长期存储与成本放大

高 churn 在 remote write 路径上同时放大发送端内存、重试队列与远端成本。对 WAL 中每条序列，remote write 代码缓存 series ID→label values 映射——**即使 head 中当前序列数不高，只要创建/消亡速率高，缓存仍会持续膨胀**；官方给出的整体量级是"多数用户报告约 25% 的内存增长"（取决于数据形态）（[Prometheus Remote write tuning](https://prometheus.io/docs/practices/remote_write)）。shard 内存近似正比于 `number of shards × (capacity + max_samples_per_send)`，默认 `capacity: 10000`、`max_samples_per_send: 2000` 会把每个 shard 内存限制在 2 MB 以内；官方建议提高 capacity/max_samples_per_send 时应同时降低 `max_shards`，以免耗尽内存。

可靠性上有一个硬约束：当某个 shard 积压填满队列时，Prometheus 会阻塞从 WAL 向任何 shard 的读取；失败会无丢失地重试，**除非远端持续不可用超过 2 小时——2 小时后 WAL 会被压缩，未发送数据将丢失**（[Prometheus Remote write tuning](https://prometheus.io/docs/practices/remote_write)；[GitHub discussion #16943](https://github.com/prometheus/prometheus/discussions/16943)）。高 churn 场景下短生命周期序列的样本更容易在窗口内堆压，被丢弃后远端可能再无补采机会，形成"远端空洞"。

计费侧，churn 通过两条路径推高成本：① 每条新序列在存活期内持续产生样本，churn 越高单位时间写入的样本数越多；② 序列元数据（label values）推高存储与活跃序列计数。AWS AMP 按摄入样本（$0.90/10M，前 20 亿样本）、存储（$0.03/GB）、查询（$0.10/十亿样本处理）计费，官方算例显示 10 节点 × 1000 指标 / 30 秒采集的月成本约 $81.75（[AWS AMP pricing](https://aws.amazon.com/prometheus/pricing/)）；GCP GMP 按样本计费且明确"不按 cardinality 预收费，只在容器存活期间付费"，对 HPA 场景相对宽容（[Google Cloud Managed Service for Prometheus](https://cloud.google.com/managed-prometheus)）。

### 4. 告警、仪表盘与 SLO 的隐性失真

核心机制是 Prometheus 的 staleness 语义：instant vector 只返回最近样本落在 lookback 窗口（默认 5 分钟）内的序列，序列一旦 stale 就被从查询结果中摘除；range vector 又完全忽略 stale 样本。于是 churn 造成的高频"旧序列 stale、新序列创建"会转化为三类告警失真：**告警抖动与恢复误报**（旧序列 stale 时表达式返回空、告警实例被 resolve，新 pod 序列出现后新实例 firing）；**`for` 窗口失效**（条件中断导致漏报或延迟触发）；**聚合型告警速率偏差**（`rate()`/`avg_over_time()` 输入出现缺口并触发外推，导致 SLO burn rate 瞬时跳变）（[Robust Perception, 2019-04-01](https://www.robustperception.io/staleness-and-promql)）。Robust Perception 据此建议 scrape/evaluation 间隔不要超过约 2 分钟，否则一次失败抓取就会撞上 5 分钟 lookback 边界。

仪表盘按 `instance`/`pod` 等易变标签画图时，旧序列 stale 会让曲线断开、图例跳变，表现为空洞与长期趋势"断裂"。更根本的是 churn 对时间窗口的影响：**窗口内唯一序列数只会随时间增加**——序列在窗口内停止上报并不会降低该窗口的基数；低 point-in-time 基数、高 churn 的工作负载在长区间查询上的性能恶化甚至比高基数低 churn 更严重（[Chronosphere 技术文章](https://chronosphere.io/learn/how-cloud-native-workloads-affect-cardinality-over-time/)）。SLO 方面，错误预算 = 1 − SLO 目标，分子分母通常都是对 `rate()` 的聚合；churn 通过两条路径让分母漂移：序列 stale 使 range 函数在缺口处只统计部分序列贡献，以及若分母是 `count(count by (pod)(...))` 这类"序列计数"而非请求计数，churn 会直接改变分母数值。量化上目前没有公开通用公式，需按具体 SLI 定义实测。

**区分"churn 消失"与"抓取失败消失"**是诊断根基：抓取失败时该 target 上一批所有序列立即 stale（避免新旧 target 双计），而 target 从服务发现中消失时 Prometheus 会等待约 2 个 scrape interval 再写 stale marker，若 target 在此期间重建则 stale marker 被拒绝；Prometheus 自身重启时延迟的 stale marker 缺失，回退到"5 分钟无样本即视为陈旧"的旧逻辑（[Robust Perception](https://www.robustperception.io/staleness-and-promql)）。可操作的检测思路：先用 `up` 排除抓取失败，再用 `prometheus_tsdb_head_series_created_total` 与 `_removed_total` 的差值/比值量化 churn 速率，用 `scrape_series_added` 看单次抓取的新增序列。

## 三、系统化的解决方案

治理应按介入深度递进：**采集侧（写入前减少新序列）→ 写入前聚合预计算 → 横向扩展/查询下推 → 存储引擎替代 → 数据生命周期 → 诊断闭环**。采集侧是成本最低、应最先落地的一层。

### 1. 采集侧治理

**relabel 两段式**：`relabel_configs` 在服务发现之后、抓取之前生效，作用于 target 标签集；`metric_relabel_configs` 在抓取之后、写入存储之前生效，作用于样本标签（[Robust Perception](https://www.robustperception.io/relabel_configs-vs-metric_relabel_configs)）。对 churn 治理主战场是 `metric_relabel_configs`：用 `labeldrop`/`labelkeep` 按标签名批量裁剪，或用 `drop` action 按 `__name__` 或 label 组合丢弃整个指标。安全边界有两条：① Alloy 文档明确"如果 relabel 规则应用后没有标签剩下，该 metric 会被丢弃"——`labelkeep` 写得过窄会连带丢掉指标本体，应只丢弃确认无用的易变标签（如 pod uid、request id），保留 `job`/`instance`；② `honor_labels=true` 时 target 暴露的 `job`/`instance` 会覆盖 Prometheus 的命名，应保持默认 `false`（[Alloy prometheus.relabel](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.relabel/)；[Alloy prometheus.scrape](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.scrape/)）。

**scrape limits 给单 target 封顶**：`sample_limit`（单次抓取 metric relabel 后的样本数）、`label_limit`（单样本标签数）、`label_name_length_limit`/`label_value_length_limit`（标签名/值长度）、`target_limit`（单 scrape config 中唯一 target 数）、`body_size_limit`（响应体大小），默认均为 `0`（不限），超限行为是"整次抓取失败"或"target 被标记失败"。这些限额是防止单 target 打爆 head 的硬闸门，但不区分是否为高 churn 序列，更适合作兜底而非精准 churn 治理（[Prometheus 配置文档](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)）。

**OTel Collector 管线**提供 filter（OTTL 条件过滤）、attributes/resource（属性删改）、metricstransform（指标重命名/合并）、k8sattributes（K8s 元数据富化）、groupbyattrs（把指定属性从 datapoint 移到 Resource 并合并同 Resource 记录）。优势是能表达复杂条件并对 OTLP 原生；劣势是引入独立组件且聚合后丢失可下钻维度（[OpenTelemetry Transforming telemetry](https://opentelemetry.io/docs/collector/transforming-telemetry/)；[groupbyattrs README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/groupbyattrsprocessor/README.md)）。**Grafana Alloy** 与 **vmagent** 都提供采集/relabel/remote-write 代理能力；vmagent 额外内置 stream aggregation 与 cardinality limiter，可在抓取时和发送前限制唯一序列数（[Alloy 文档总览](https://grafana.com/docs/alloy/latest/)；[vmagent 文档](https://docs.victoriametrics.com/vmagent/)）。

**native histograms** 是数据模型层面的降 churn 手段：经典直方图会被拆成 `_bucket`/`_sum`/`_count` 多个 float 序列，native histogram 把整个分布合并为一条序列，直接减少序列数与 churn。版本门槛：v2.40.0 起实验性支持（需 `--enable-feature=native-histograms`），v3.8.0 起稳定，自 v4 起抓取与 remote write 默认开启（[Prometheus Native Histograms 规范](https://prometheus.io/docs/specs/native_histograms/)）。Prometheus 3.x 还原生支持 OTLP 接收（`--web.enable-otlp-receiver`，端点 `/api/v1/otlp/v1/metrics`），但官方明确建议同时启用 out-of-order 接收（`storage.tsdb.out_of_order_time_window: 30m`），因为 OTel Collector 鼓励批处理且多副本互不协调，天然产生乱序样本（[Prometheus OTel 指南](https://prometheus.io/docs/guides/opentelemetry/)）。OTel 资源属性方面，Prometheus 默认不提升任何资源属性为标签，官方给出推荐清单（`service.instance.id`、`service.name`、`k8s.pod.name` 等），其余附加到 `target_info`；把 `service.instance.id` 提升为标签会让每次实例重启都产生新序列，对 churn 敏感的工作负载应只提升稳定属性（同上）。

> 注意：增大 `scrape_interval` 主要降低单位时间样本数，并不改变 target 暴露的 label 组合集合，因此不直接减少 churn；间隔越长反而越容易触发 stale 标记造成查询空洞。要降 churn 应依靠 relabel/聚合/降基数。

### 2. 写入前聚合与预计算

三条路线代价不同：**Prometheus recording rules** 在数据已写入 TSDB 后预计算并写回，能加速查询，却增加存储与评估负载；**VictoriaMetrics `stream_aggregation`** 在写入远端存储前完成聚合，只落盘聚合结果，从源头减少序列数；**Prometheus agent 模式 / vmagent** 是"只采集、只转发"的轻量 agent，资源低、易水平扩展，但牺牲本地查询与 recording rules 能力（[VictoriaMetrics 官方博客](https://victoriametrics.com/blog/reducing-costs-p2/)；[Prometheus Agent Mode 官方文档](https://prometheus.io/docs/prometheus/latest/prometheus_agent/)）。

VictoriaMetrics 配置示例：

```yaml
match: "grpc_server_handled_total"
interval: "2m"
outputs: ["total"]
without: ["grpc_method"]
# 结果：grpc_server_handled_total:2m_without_grpc_method_total
```

该博客案例中，查询原始指标 30 天需约 4 秒，改查聚合结果降到"几分之一秒"，同时减少存储样本数与序列数（[官方博客](https://victoriametrics.com/blog/reducing-costs-p2/)）。

recording rules 的关键约束：组内规则顺序执行、共享同一评估时间；官方提供 `query_offset` 来"确保底层指标已被接收并存储"，明确针对短评估间隔场景；`limit` 限制规则产出的序列数，超限后该规则产生的**所有序列被丢弃**且不写 stale marker，是防止聚合规则爆炸的内置护栏；若上一轮评估未结束下一轮会被跳过，`rule_group_iterations_missed_total` 会计数每次错过（[Prometheus 官方 recording rules 文档](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/)）。**分层聚合**可设计为：高频层（15s–30s）用 `sum/avg without (高基数标签)` 输出 instance/path 级；中频层（1m）只消费高频层输出，聚合到 service/job 级；低频层（5m–1h）生成全局趋势序列。关键原则是每层只消费下一层的聚合结果，避免重复扫描原始高基数数据；官方命名规范 `level:metric:operations` 可让聚合层级显式化（[Prometheus 官方 rules 最佳实践](https://prometheus.io/docs/practices/rules/)）。聚合必然丢失被 `without`/`by` 掉的维度，排障时无法再下钻；统计原则是不要对 ratio 或 average 再取平均，比率应分别聚合分子分母再相除（同上）。

| 维度 | Prometheus recording rules | VM stream_aggregation | Prometheus agent 模式 | vmagent |
|---|---|---|---|---|
| 聚合时机 | 写入 TSDB 后 | 写入远端存储前 | 不聚合 | 发送前聚合 |
| 是否新增序列 | 是，写回数据库 | 否，只存聚合结果 | 原样转发 | 只发聚合结果 |
| 本地查询 | 保留 | 保留 | 禁用 | 无本地存储 |
| 断连缓冲 | 2h WAL | per-URL 磁盘缓冲 | 2h 缓冲 | per-URL 磁盘缓冲 |

### 3. 横向扩展与多租户

单实例无法承载高 churn 时，横向扩展收敛为两条主路线：**(A) 分片抓取 + 中心化查询**——用 `hashmod` 把 target 分散到多个 Prometheus 副本，再用 `/federate` 或 Thanos/Mimir/VictoriaMetrics 查询层聚合；**(B) 完全托管多租户后端**——Mimir/Cortex 用 query-frontend + shuffle sharding 把租户隔离在共享集群的实例子集上。关键分歧在**查询路径**：原生 Remote Read 会把跨实例的原始序列全部拉进单个 querier，因此现代系统普遍改为把聚合算子拆成部分子查询（query sharding / distributed execution），只回传聚合结果。

`hashmod` 标准写法是先用 `hashmod` 动作计算分片号，再用 `keep`/`drop` 按模值筛选（[PromLabs](https://training.promlabs.com/training/relabeling/writing-relabeling-rules/hashing-and-sharding-on-label-values/)）。副作用与边界：分片不均（哈希基于标签值）、标签跳转（分片键变化导致目标在不同副本间跳变，应选稳定标签如 `job`）、查询歧义（需 `external_labels`/`replica_label` 去重）、**只分散抓取负载而不减少序列总数**。Thanos 提案明确指出 Querier 需先把 Store 数据全部拉进内存才能求值，Cortex/Mimir 提案指出 querier 常把全部数据拉到单节点形成瓶颈（[Thanos 分布式执行提案](https://web.archive.org/web/2024/https://thanos.io/tip/proposals-done/202301-distributed-query-execution.md/)；[Cortex/Mimir 提案](https://cortexmetrics.io/docs/proposals/distributed-query-execution/)）。Mimir 明确 `sum`/`min`/`max`/`count`/`avg` 等结合律聚合可分片，而 `absent`、`absent_over_time`、`histogram_quantile`、`sort_desc`、`sort` 不可（[Grafana Mimir query sharding](https://grafana.com/docs/mimir/latest/references/architecture/query-sharding/)）。

| 维度 | Thanos Query | Mimir query-frontend | VictoriaMetrics vmselect |
|---|---|---|---|
| 执行模型 | 从 StoreAPI 拉数据、中心求值；可选分布式执行 | query-scheduler 分配 fragment，querier 执行，frontend 聚合 | 向所有 `vmstorage` 发检索请求，中心合并/去重/聚合 |
| 聚合下推 | distributed optimizer 把 `sum`/`rate` 拆成子查询 | query sharding（可分片算子有限） | 聚合仍在 vmselect 中心完成；下推的是序列检索 |
| 去重 | `--query.replica-label` | shuffle sharding + per-tenant limits | `vminsert`/`vmselect` 复制数据合并去重 |
| 多租户 | external labels/StoreAPI 组合 | accountID/租户 + shuffle sharding | `accountID`/`projectID` |

（[Thanos Query v0.36](https://thanos.io/v0.36/components/query.md/)；[Mimir query sharding](https://grafana.com/docs/mimir/latest/references/architecture/query-sharding/)；[VM Cluster 文档](https://docs.victoriametrics.com/victoriametrics/cluster-victoriametrics/)）

分片架构下，聚合类 recording rule 若放在单个分片会产出部分或重复结果，应放在全局查询层（Thanos Ruler / Mimir Ruler）。shuffle sharding 默认 shard size=0 时一个租户用全部实例，故障/OOM 租户会影响所有租户，调大后才能收敛爆炸半径（[Grafana Mimir shuffle sharding](https://grafana.com/docs/mimir/latest/configure/configure-shuffle-sharding/)）。

### 4. 存储引擎替代

面向高 churn 的存储替代并非"一种引擎通吃"，而是三种设计哲学的取舍（细节归各引擎）：

| 引擎 | 存储/索引设计 | 高 churn 下的关键机制 | 限额与多租户 | 兼容性 |
|---|---|---|---|---|
| Grafana Mimir | 多租户块存储；compactor split-and-merge | per-tenant 限额 + distributor 限流；in-memory series 限额；query sharding；compactor 分片 | per-tenant（`max_global_series_per_user`、`ingestion_rate`、`ingester_limits.max_series`） | remote write v1/v2、OTLP、Influx；PromQL |
| Thanos | 对象存储 + Prometheus TSDB 块 | Receive 接收 remote write；compactor 长期存储 | 多租户依赖外部，无 Mimir 式 per-tenant 限额 | remote write；PromQL |
| VictoriaMetrics | 磁盘驻 IndexDB + 有界 TSID 缓存（默认约 37% TSID 内存预算） | 高压缩、低内存；按分区 IndexDB；官方建议降 churn | 本轮未验证其多租户限额能力 | Prometheus querying API、MetricsQL；remote write |
| Promscale/TimescaleDB、InfluxDB IOx、ClickHouse | 列存 | — | — | remote write（证据不足/弃用线索） |

Mimir 的关键机制：distributor 设请求速率与摄入速率限流（超限 429 丢弃），per-ingester `max_series` 超限属服务端错误（新序列写入失败、已有序列继续追加），每租户全局序列数超限属客户端错误（多余数据丢弃）（[Mimir distributor 文档](https://grafana.com/docs/mimir/latest/references/architecture/components/distributor/)；[Mimir runbooks](https://grafana.com/docs/mimir/latest/manage/mimir-runbooks/)）。**active series ≠ in-memory series** 是理解 Mimir 限额的关键：社区案例中 `cortex_ingester_active_series` 仅约 5 万却被 `"per-user series limit of 150000 exceeded"` 拒绝，因为限额作用于 in-memory series 而非 active series，两者在 Pod 频繁重启换新 hostname 时会分叉（[GitHub discussion #12619](https://github.com/grafana/mimir/discussions/12619)）。compactor 用 split-and-merge 把源块分成 N 组、输出 M 个 split block，官方建议**每约 800 万 active series 用 1 个 shard**（1 亿序列约 16 个 shard）；当单租户接近 10 亿 active series 时 shard 数超过约 96 后收益递减（[Mimir compactor 文档](https://grafana.com/docs/mimir/latest/references/architecture/components/compactor/)）。

VictoriaMetrics 官方对 high churn rate 的容量规划指引：active time series = 过去 1 小时内至少更新过一次，churn rate = 新序列创建的频率；高 churn 常由高易变标签引起（如 `client_id`、`url`、`checksum`，K8s 中 pod 名也是易变标签）；一个服务暴露 1000 序列、部署 100 副本即 10 万 active，**每次重新部署会新建 10 万序列**；官方明确"尽可能降低 churn rate"；磁盘空间公式含 1.2 倍 merge 空闲余量（[VM: Understand Your Setup Size](https://docs.victoriametrics.com/guides/understand-your-setup-size/)）。其内存效率声明（最多省 7 倍内存、少 7 倍存储）是**厂商自报数字**、非独立验证，实测条件是 node-exporter 指标与数百万唯一序列，规划时应以自身负载测试外推（[VM 单节点文档](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/)）。

外部列存（Promscale/TimescaleDB、InfluxDB IOx、ClickHouse）理论上可接收 remote write，但本轮未获得足够一手证据证明其在高 churn 下的适配，且 Promscale 已出现弃用线索（仓库标注 DEPRECATED），不宜作为首选（[Promscale 仓库](https://github.com/timescale/promscale)）。

### 5. 数据生命周期：retention、downsampling 与分级存储

**Prometheus 原生保留是实例级的，不能按标签/序列分级**：`--storage.tsdb.retention.time`（默认 15d）与 `--storage.tsdb.retention.size` 是 immutable system parameters，无法按序列设置不同保留期（[Prometheus 命令行文档](https://prometheus.io/docs/prometheus/latest/command-line/prometheus/)；[配置文档](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#storage)）。要把"高价值低基数长保留、低价值高基数短保留或降采样"落地，必须借助下游存储或托管服务的按标签限制。

**降采样能显著降低长期存储与查询成本，但会不可逆地丢失原始样本与高 churn 细节**，应在降采样前用 recording rules / 流式聚合固化需要保留的维度。

| 引擎 | 降采样组件 | 分辨率/粒度 | 精度影响 |
|---|---|---|---|
| Prometheus | 无原生降采样 | — | 保留原始样本，长期成本高 |
| Thanos | compactor | raw / 5m / 1h，各分辨率保留期独立可配（默认永久） | `AggrChunk` 保留 sum/count/min/max/counter/raw，原始单点丢失 |
| Mimir | compactor（负责保留与压缩） | 具体分辨率未能核实 | 未能核实 |
| VictoriaMetrics | 企业版 Downsampling / Multiple retentions | 未能核实 | 官方称降低历史查询成本 |

（[Thanos compactor 文档](https://thanos.io/tip/components/compact.md/)；[Mimir compactor 文档](https://grafana.com/docs/mimir/latest/references/architecture/components/compactor/)；[VM Enterprise 文档](https://docs.victoriametrics.com/victoriametrics/enterprise/)）

AWS AMP 的 workspace 配置支持"label sets + active time series limits"：为某个标签集（如 `team=A env=prod`）设置 active series 上限，超限只对匹配该标签集的序列节流；但保留期仍是工作区级（最大 1095 天），**按标签能力本质是摄入侧限制而非保留侧分级**（[AWS AMP workspace configuration](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP-workspace-configuration.html)）。

### 6. 诊断与治理闭环

可复制的诊断路径是三层：① 用 Prometheus 自身指标判断 churn 是否异常（`prometheus_tsdb_head_series`、`_created_total`/`_removed_total`、`prometheus_tsdb_head_samples_appended_total`）；② 用 `/api/v1/series`、`/api/v1/label/__name__/values` 与 `promtool tsdb analyze` 把异常定位到具体指标名与标签；③ 回到 relabel/服务发现配置修复。`promtool tsdb analyze` 对单个 TSDB block 输出"Label pairs most involved in churning""Highest cardinality labels/metric names"等排行，只读 block 索引、不读样本、不检查 staleness，可在运行中的 Prometheus block 上运行，耗时约 1 分钟（[Robust Perception, 2019](https://www.robustperception.io/using-tsdb-analyze-to-investigate-churn-and-cardinality)）。

治理闭环按"发现→归因→修复→验证→防复发"运营：发现阶段监控 churn/活跃序列/摄入速率；归因阶段输出具体 metric/label 清单；修复阶段用 relabel/limits/聚合；验证阶段双写/灰度比对 created/removed、active series、查询延迟；防复发阶段靠标签契约、上线前基数评估与 quota 监控。标签契约的核心检查项：明确每个指标允许的标签集合；禁止把唯一标识（userID、requestID、trace id、pod uid/container id）放进标签；统一 `instance`/`job`/`external_labels` 命名；避免 `honor_labels` 让外部标签覆盖内部标签。Azure 官方也建议用 `metric_relabel_configs` 丢弃不必要标签来压掉高基数指标；Prometheus 官方 storage 文档指出"减少序列数比增大抓取间隔更有效，因为序列内样本会被压缩"（[Azure 最佳实践](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)；[Prometheus Storage](https://prometheus.io/docs/prometheus/latest/storage/)）。

## 四、各家云厂商的现有方案

### AWS AMP：入口限额 + 标签集隔离 + 可观测性

AMP 对 churn 的治理是"入口限额 + 标签集隔离 + 可观测性"的托管式方案，而不是存储引擎级优化。官方把 active series 定义为"过去 2 小时内上报过样本的序列"——短生命周期序列在消亡后最长 2 小时仍占用 active 配额，churn 因此会被"延迟"计入成本（[AMP service quotas](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP_quotas.html)）。默认 active series 上限为 **50M/workspace**（2025-07 由 10M 提升，已自动应用到既有 workspace），可申请上限 1B；容量在 2M–50M 之间按最近 30 分钟用量自动调整（[2025-07 公告](https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-managed-service-prometheus-50M-default-activeserieslimit/)）。

**label-based active series limits**（2025-04-18 推出）按 label set 设定 active series 限额，某 label set 超限只节流匹配该集合的序列，其他租户/来源不受影响；workspace 配置页还提供 "Default bucket limit" 约束不匹配任何 label set 的序列，label set 数量上限 100/workspace（[2025-04 公告](https://aws.amazon.com/about-aws/whats-new/2025/04/amazon-managed-service-prometheus-label-based-series-limits/)；[Configure your workspace](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP-workspace-configuration.html)）。这与全局上限的区别在于：全局上限约束整个 workspace，label-based 限额是子集配额，用于多租户/多应用隔离，防止 noisy neighbor 打爆整个 workspace。

观测侧，CloudWatch 的 `AWS/Prometheus` 命名空间提供 per-label-set 指标（`ActiveSeriesPerLabelSet`、`IngestionRatePerLabelSet`、`DiscardedSamplesPerLabelSet` 等），`AWS/Usage` 提供 workspace 级 `ActiveSeries`、`IngestionRate`、`DiscardedSamples`；丢弃原因包括超出 active series 限额、触及摄入速率限额、乱序样本或时间戳超出接受窗口（[Use CloudWatch metrics to monitor AMP resources](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP-CW-usage-metrics.html)；[Optimizing metrics ingestion with AMP, 2025-09](https://aws.amazon.com/blogs/mt/optimizing-metrics-ingestion-with-amazon-managed-service-for-prometheus/)）。乱序窗口默认 60 秒（0–600 秒，更高需申请），规则查询偏移新工作区默认 60 秒（范围 0–86,400 秒），用于补偿摄入延迟/乱序；查询跨度自 2025-05 起由 32 天扩至 95 天；保留期默认 150 天、最长 1095 天，均工作区级（同上）。

**能力边界**：AMP 不暴露 TSDB/head/WAL/compaction 参数，不提供按序列或标签的保留与降采样；churn 控制集中在入口限额、采集侧治理（由自管 collector 或 ADOT 承担）与丢弃/利用率可观测性。计费按样本摄入（$0.90/10M，前 20 亿）、存储 GB（$0.03）、查询样本处理（$0.10/十亿）与 collector 时长计费，**不直接按 active series 收费**（[AMP pricing](https://aws.amazon.com/prometheus/pricing/)）。

### GCP GMP：按样本计费，不按 cardinality 预收

GMP 是 fully managed Prometheus 兼容服务，查询与存储底座是 Google 自用的 Monarch，默认 24 个月保留、跨所有 Google Cloud 区域最多 3,500 个项目做全球联合查询（[GMP 文档总览](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus)）。官方文档页被索引的表述称对活跃与总时间序列"无上限"，但页面正文未能逐字复核，按"官方文档表述（待逐字复核）"处理；**可逐字验证的硬性限制在 Cloud Monitoring 配额页**：每个被监控资源的 Prometheus 活跃时间序列上限为 **1,000,000**，注明为 system-wide safety limit、不可定制；另有每项目 25,000 个指标描述符、每个 Prometheus 指标描述符 200 个 label、单写请求 200 条序列、单序列每 5 秒一个点、查询响应 200 MB 等限制（[Cloud Monitoring 配额与限制](https://docs.cloud.google.com/monitoring/quotas)）。

计费按摄入样本数，账单 SKU 为 "Prometheus Samples Ingested"，官方明确 "the number of samples ingested is the primary contributor to your cost"；产品页说明 per-sample 定价 **"does not charge for cardinality up front when a new container is spun up… only pay while the container is alive, so you are not penalized for using Horizontal Pod Autoscaling"**（[GMP cost controls](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/cost-controls)；[GMP 产品页](https://cloud.google.com/managed-prometheus)）。对 churn 的含义是：GMP 不按活跃序列预收费，但每条短生命周期序列在存活期间仍持续产生样本，churn 越高、总样本量与 24 个月保留的存储越大，账单越高。官方给出的降 churn 手段是采集侧过滤（PodMonitoring/ClusterPodMonitoring 的 `metricRelabeling` keep/drop）、降低采样频率（10s→30s 减少约 66%、10s→60s 减少约 83%）、本地 recording rules 聚合、`--export.match` 只发送聚合结果（[GMP cost controls](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/cost-controls)）。

### Azure Monitor managed Prometheus：双硬限制下的节流

Azure 托管 Prometheus 的规模天花板由两类硬限制共同决定——Azure Monitor workspace（AMW）的"活跃时间序列数"（默认 **100 万**，过去约 12 小时内有样本上报，可申请提升）与 remote-write sidecar 容器能处理的"唯一时间序列数"（**150,000**，不可提升）。高 churn 负载会同时推高这两个指标，直接后果是**节流与 sidecar 报错**，而不是线性费用增长（[Azure Monitor service limits](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/service-limits)；[Scaling best practices](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)）。官方给出的 sidecar 缓解手段是把 remote batch size 从默认 500 提高到 1,000，以减少并发连接数。

其他关键限制：DCR/DCE 摄入请求 15,000/分钟、数据摄入 50 GB/分钟（均不可提升）；数据保留 **18 个月**且不可提升；查询时间跨度 **32 天**且不可提升；单 metric 查询 500,000 序列、单查询返回 50,000,000 样本；≥48 小时查询最小 step 60 秒；label name/value 长度 511/1023、每序列 63 个 label（超限导致整个 scrape job 失败并丢弃指标）（[Azure Monitor service limits](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/service-limits)；[Technical details](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-metrics-details)）。**两个与高 churn 相关的行为差异**：Azure 托管 Prometheus 是**大小写不敏感**系统（与开源 Prometheus 不同），仅大小写不同的序列会被视为同一条；重复序列会以 422 错误显式抛出而非静默丢弃。官方建议用 `Active Time Series % Utilization` 与 `Events Per Minute Ingested % Utilization` 两个指标做监控，>80% 时告警；当单 workspace 接近摄入限制时按主权云/合规区域/部署环境等拆分多个 workspace，**跨租户查询不受支持**（[Troubleshoot](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/prometheus-metrics-troubleshoot)；[Scaling best practices](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/azure-monitor-workspace-scaling-best-practice)）。

计费维度是**摄入数据样本数与查询处理样本数**，18 个月保留不额外收费；因此 churn 直接放大 ingestion 费用与查询费用，而 active series 上限是"硬节流"而非计费维度——高 churn 下更常见的问题是"数据进不来"而非"账单爆炸"（[Azure Monitor cost and usage](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/cost-usage)）。本次未找到 Azure Data Explorer 作为 managed Prometheus 长期存储路径的官方文档证据，官方对长期保留的表述是 AMW 提供 18 个月保留、不可提升，不将 ADX 列为长期层。

### Grafana Cloud：active series 计费 + 基数管理 + Adaptive Metrics

Grafana Cloud Metrics 底层是 Mimir，是本次覆盖中唯一在官方文档中给出"每用户 active series 硬限额 + 基数管理工具 + 写入前聚合建议"完整链条的托管服务。计费口径：**active series 定义为"前 20 分钟内收到过新数据点"的序列**，账单按 active series 与 DPM 两者取大、并以 **95 百分位**计量，从而豁免每月约 36 小时的突发尖峰；公式为 `usage = max(active_series, total_dpm/included_dpm)`，native histogram 活动桶按 0.25 比例折算（[Grafana Cloud Metrics pricing](https://grafana.com/docs/grafana-cloud/platform/pricing-and-usage/metrics/)）。默认限额：`max_global_series_per_user` 默认 **150,000**、`ingestion_rate` 默认 10,000 samples/s、`out_of_order_time_window` 2 小时、`max_partial_query_length` 32 天，部分限额按消费自动伸缩（[Grafana Cloud usage limits](https://grafana.com/docs/grafana-cloud/platform/pricing-and-usage/usage-limits/)）。

治理工具两套互补：**Cardinality management 面板**聚焦"最近 2 小时内的 active time series"，展示最高基数指标/标签、标签值分布，并标注某指标是否 *unused*（过去 30 天未被查询、也未用于仪表盘/recording rule/告警规则，每 24 小时重算）；**Adaptive Metrics** 通过分析指标实际使用自动给出"把低利用指标聚合为低基数版本"的建议，并支持 UI/API/Terraform 应用规则、豁免与审计日志，官方称既有仪表盘、告警与查询可无缝继续使用聚合后的指标（[Grafana Cloud cardinality management](https://grafana.com/docs/grafana-cloud/platform/cost-management-and-billing/analyze-costs/metrics-costs/prometheus-metrics-costs/cardinality-management/)；[Adaptive Metrics](https://grafana.com/docs/grafana-cloud/cost-management-and-billing/reduce-costs/metrics-costs/control-metrics-usage-via-adaptive-metrics/)）。

### 火山引擎 VMP：预聚合、查询下推、查询熔断

火山引擎 VMP 与火山方舟、智能驾驶数据服务合作的实践，针对"pod name 高频变化 + 大模型接入点数量极高"两类高 churn 场景。四层能力分别解决不同环节：**写入侧预聚合**——在 VKE 采集组件中对 `container_cpu_usage_seconds_total` 之类指标，按业务真实关注粒度（节点池/训练任务组）在写入前聚合掉 `pod` 等高频标签；**查询下推**——将 PromQL 解析为 AST 后，把 `sum/count/avg` 等可下推算子替换为多个 Workspace 的查询请求并合并结果，只传聚合结果而非原始时序，不含可下推算子时退化为 RemoteRead，官方明确这与 Thanos 社区的 distributed query execution 提案思路一致；**查询熔断**——命中时序基数超阈值时触发熔断，防止"类 MySQL 全表扫描"式大查询冲击稳定性；**专家分析服务**——面向已产生高基数的指标做归因分析（目前为邀测功能）（[火山引擎可观测团队](https://developer.volcengine.com/articles/7487815638971318326)）。此外 VKE 采集组件提供可视化指标丢弃（等价于 relabel 丢弃），支持把数据分片写入多个 Prometheus 实例，查询侧通过路由信息跳过特定 Workspace 以提升跨云/跨 Region 查询效率。

## 五、决策框架与落地路线

### 1. 规模边界

| 规模/现象 | 观察 | 来源 |
|---|---|---|
| 100–200 万活跃序列 | 单实例"舒适区"上限，超过后内存成为顾虑 | [Exoscale](https://www.exoscale.com/blog/prometheus-limits-at-scale/) |
| ~800 万活跃序列 | Pipedrive 32 vCPU/256GB 达失败阈值，继续加资源无效；重启 WAL replay 长达 15 分钟 | [Groundcover](https://www.groundcover.com/guides/reduce-prometheus-metric-cardinality) |
| 查询延迟 | PromCon 2019：`count(metric_a)` 10 万序列≈1.5s、20 万≈5s | [Groundcover](https://www.groundcover.com/guides/reduce-prometheus-metric-cardinality) |
| 托管上限 | AMP 默认 5000 万/workspace（最大 10 亿）；active=过去 2h 有样本 | [AMP quotas](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP_quotas.html) |

高 churn 会额外压低有效边界：部分填满的 head chunk、WAL 增长与 head GC 滞后使有效承载能力低于"点时刻基数相同但低 churn"的场景。

### 2. 自托管 vs 云托管

TCO 通常分为基础设施、人力、商业服务三维。第三方咨询口径估算：基础设施按每活跃序列约 8 KB RAM 预留（优化环境 3–4 KB），1000 万序列≈80 GB RAM，HA 需两份副本加 Alertmanager，基础设施成本约三倍；人力约消耗 0.5–1.5 FTE SRE，单 FTE 年成本约 25–30 万美元；云托管若每年 6 万美元但节省 25% SRE 时间，ROI 即为正（[Siriusopensource《The True Cost of Prometheus》](https://www.siriusopensource.com/en-us/blog/true-cost-prometheus)）。

**关键洞察**：云托管按样本计费，惩罚高频抓取与高 churn；自托管按 RAM/HA/人力计费，惩罚高基数。两者对 churn 的敏感度不同，选型时需先明确抓取间隔与留存需求。算例（基于 AMP 公布费率与假设）：1000 万活跃序列、15s 抓取间隔 → 约 66.7 万样本/秒 → 每月约 1728 亿样本；若按最高档 $0.90/1000 万估算，仅摄入费上限约 $155k/月（未计存储与查询；AMP 采用阶梯计价，实际会低于此值）。已有 AWS/Azure/GCP 绑定时，原生托管服务在 IAM、账单与生态集成上更顺畅，代价是厂商锁定。

### 3. "先降基数、再扩展"是默认值而非定律

社区常见顺序（relabel/limits/recording rules → 查询优化 → 横向扩展 → 换引擎/上托管）应视为待验证假设。支持证据：Groundcover 把"诊断 → `metric_relabel_configs` → 丢弃整族指标 → recording rules"作为有序工作流，称 relabel 是"第一补救"（[Groundcover](https://www.groundcover.com/guides/reduce-prometheus-metric-cardinality)）。反例与边界：① 降基数可能破坏信号——若丢掉的标签是区分两条序列的唯一标签，序列会坍缩，而 Prometheus 只保留每个时间戳的第一个样本，2.52.0 起才有 `prometheus_target_scrapes_sample_duplicate_timestamp_total` 计数器暴露这一问题（同上）；② 换引擎可以不降基数——VictoriaMetrics 官方基准（1000 个 Node Exporter、每个约 1200 序列、15s 抓取、每 10 分钟 5% churn≈6 万新序列、3 vCPU/12GiB）显示中位读延迟快 16 倍、P99 快 1.9 倍、内存少 1.7 倍、磁盘少 2.5 倍，且定位为 drop-in replacement（[VictoriaMetrics《How to reduce expenses on monitoring》](https://victoriametrics.com/blog/reducing-costs-p1/)，厂商基准）；③ 垂直扩容在约 800 万序列失效，强制在"降基数"与"改架构"之间做选择；④ metric-name churn（动态 `__name__`）无法靠 relabel 解决，需要改埋点。

### 4. 分阶段落地与迁移风险

按"带验收门"的阶段推进：**阶段 0 诊断与基线**（建立 churn/活跃序列/摄入基线，记录查询 P95、OOM、compaction 时长与当前成本）→ **阶段 1 采集侧治理**（relabel/limits，预期 churn 与活跃序列较基线下降，无新增 scrape 失败）→ **阶段 2 计算/存储侧优化**（remote write queue_config 调优、retention、downsampling；注意远端不可用超过 2 小时会触发 WAL 压缩、未发送数据丢失）→ **阶段 3 架构升级**（分片/Thanos/Mimir/VictoriaMetrics；验收查询 P95 在 SLO 内）→ **阶段 4 托管迁移评估**（双写到托管服务，按 namespace/cluster 灰度）→ **阶段 5 持续治理**（churn SLO/告警、标签契约、quota 监控）。

**双写验证**是阶段 4 的核心安全网。时长没有官方硬性规定，但可从机制推导下限：remote write 把样本先写入 WAL 再由各 shard 队列发送，若远端持续不可用超过 2 小时 WAL 会被压缩、未发送数据永久丢失，因此双写窗口至少要覆盖"最长可接受中断窗口 + 一个完整 WAL/compaction 周期"，工程上通常需要数天到数周才能对序列级一致性有统计信心（[Prometheus Remote write tuning](https://prometheus.io/docs/practices/remote_write/)；[Remote-Write 1.0 规范](https://prometheus.io/docs/specs/prw/remote_write_spec/)）。**切换前必须建立成本回归基线**（每百万序列成本、每百万样本成本、存储 GB/天），否则无法判断托管迁移是否真的更便宜。回滚预案需保留：自管 Prometheus 实例及其本地 TSDB/WAL 至少保留到一个完整保留窗结束；recording rules/告警规则源文件保持可移植；双写链路保持可回切。

**迁移兼容性要点**：Remote Write 2.0 为实验性规范（2026-10 rc.6），引入 `io.prometheus.write.v2.Request` 与强制响应头，需确认收发双方版本协商一致（[Prometheus Remote-Write 2.0 specification](https://prometheus.io/docs/specs/remote_write_spec_2_0/)）；native histograms（NHCB）把经典直方图桶/计数/求和合并为单条序列，但发送需设 `send_native_histograms: true` 且 `protobuf_message: io.prometheus.write.v2.Request`，查询/可视化需适配（[Grafana Mimir native histograms](https://grafana.com/docs/mimir/latest/send/native-histograms/_custom_buckets/)）；Azure 明确不支持 `PrometheusRule` CRD、大小写不敏感、最小抓取频率 1s（[Azure 迁移指南](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-migrate)）；AWS 迁移中 Grafana Agent 移除 recording/alerting rules 支持（换来约 40% 内存下降），不能依赖它承载规则（[AWS 迁移博客](https://aws.amazon.com/blogs/opensource/best-practices-for-migrating-self-hosted-prometheus-on-amazon-eks-to-amazon-managed-service-for-prometheus/)）。

---

**总结**：高流失率的影响不止于"查不到数据"，而是同时作用于内存/索引（churn 残留撑大 head）、故障恢复（Head GC 饿死 → OOM/WAL 堆积/重启延长）、remote write（序列缓存膨胀、2 小时截断丢失、成本放大）与告警语义（stale marker 导致抖动与 SLO 分母漂移）。系统方案的核心是"在写入前减少新序列、在写入前完成聚合、在查询时只回传聚合结果、在存储层用限额与分片抑制残留"，并通过诊断闭环把 churn 归因到可修改的配置。云厂商均已提供托管方案，但治理强度与口径差异显著：AMP 有最完整的 active series 配额 + label-set 隔离 + per-label-set 可观测性；GMP 用按样本计费规避 cardinality 预收费；Azure 受 sidecar 15 万唯一序列硬约束；Grafana Cloud 有基数管理与 Adaptive Metrics；VMP 把预聚合/查询下推/熔断打包为托管能力。选型时应先统一 active series 口径、量化 churn 类型，再按规模边界在自托管与托管之间做成本/运维/合规的权衡。

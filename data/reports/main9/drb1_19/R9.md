# Prometheus 高流失率（Cardinality Churn）的影响与系统性治理方案研究报告

## 摘要

Prometheus 的“高流失率”通常指 **时间序列 churn**：系统不断创建新的 metric+label 组合，而旧序列虽然不再写入，但仍在保留期内占用索引、存储和查询空间。它和“高基数”高度相关，但并不完全相同：高基数强调某一时刻活跃序列数量多，高流失率强调序列集合变化快。Kubernetes、云原生自动扩缩容、临时 Pod、Pod UID、容器 ID、IP、请求 ID、用户 ID、原始 URL 等动态标签，是 Prometheus churn 的主要来源。研究结论是：**高流失率首先应通过指标设计、采集治理、relabel、聚合与预算机制解决，而不是直接通过扩容或更换后端解决**。云厂商和托管 Prometheus 可以降低运维复杂度、提供更长保留期和全局查询能力，但无法从根本上替代对标签、采集和使用价值的治理。

---

## 1. 问题定义：Prometheus 的“高流失率”到底是什么？

在 Prometheus 中，每一个唯一的 **metric name + 完整 label set** 都是一条独立时间序列。只要任意一个标签值发生变化，就会产生新序列；旧序列即使不再写入，也会在保留期内继续存在于历史数据中。因此，`pod="api-7c9f..."`、`container_id="..."`、`request_id="..."`、`user_id="..."`、`raw_url="/users/123/orders/456"` 等动态值，会持续制造新时间序列。Prometheus 风格系统的成本主要由唯一时间序列数量、样本数、WAL 写入、索引、查询扇出和远端写入带宽共同驱动，而不是仅由 metric 数量决定（[OneUptime, 2026](https://oneuptime.com/blog/post/2026-07-31-high-cardinality-host-labels/view)）。

“高基数”是某个字段或标签拥有大量不同值；“高流失率”则是这些值不断变化，导致时间序列集合持续替换。Parseable 将这种现象称为 **cardinality churn**：Pod 名称、容器 ID、构建 ID、重新创建的主机 ID 等会不断产生新历史序列，即使当前活跃工作负载规模没有明显变化，历史唯一序列仍会快速膨胀（[Parseable, 2026](https://www.parseable.com/blog/what-is-high-cardinality)）。

Kubernetes 环境尤其容易出现该问题，因为 Pod 创建和销毁频繁、IP 会变化、服务会自动扩缩容、发现标签和应用标签会快速组合放大（[Palo Alto Networks, n.d.](https://www.paloaltonetworks.com/cyberpedia/what-is-high-cardinality)）。这意味着 Prometheus churn 不是单一组件问题，而是指标建模、服务发现、采集策略、远端存储和组织治理共同作用的结果。

## 2. 高流失率会造成什么影响？

### 2.1 内存压力与 OOM 风险

Prometheus 的 TSDB head 会把活跃时间序列保存在内存中，每个活跃 series 都必须装入 RAM，并不存在自动 spill-to-disk 机制。因此，当 churn 推动活跃序列数和短期新增序列数快速上升时，Prometheus 内存压力会近似随活跃序列数量线性增长，极端情况下会导致 OOM crash（[OpenObserve, n.d.](https://openobserve.ai/blog/prometheus-data-cardinality/)）。

`prometheus_tsdb_head_series` 是观察当前 head block 中活跃序列数量的核心指标。Grafana 文档指出，该指标可能包含最多约一小时内已经停止接收样本的序列，因此在频繁创建和销毁 Pod 的环境中，它既反映当前活跃序列，也会体现短期 churn 的残留影响（[Grafana Labs, n.d.](https://grafana.com/docs/grafana/latest/alerting/examples/high-cardinality-alerts/)）。

### 2.2 WAL、磁盘和保留期压力

Prometheus 写入新样本时会先写入内存和 WAL，再压缩成时间块；保留清理以 block 为单位删除，而不是逐样本删除。因此，高 churn 会造成更多 series metadata、更多 WAL 流量和更多 block/index 压力，实际磁盘使用也可能超过名义保留窗口的直觉估计（[Last9, n.d.](https://last9.io/blog/prometheus-data-retention/)）。

这类压力有两个特点：

1. **短期冲击**：新增 series 会增加 head、WAL、symbol table、index 负担。  
2. **长期残留**：旧 series 在 retention 到期前仍可查询，导致历史查询和存储持续受影响。

### 2.3 查询、仪表盘和告警性能下降

Prometheus 查询通常先在索引中定位匹配 series，再读取样本。高 churn 会扩大索引和历史序列集合，使 dashboard 长时间范围查询、`group by`、`count by`、`label_values`、全局 regex 查询更慢，甚至超时。Parseable 总结的典型症状包括：dashboard latency 上升、长时间范围查询超时、告警评估延迟、存储成本增长快于业务流量、active series 在业务流量平稳时仍上升（[Parseable, 2026](https://www.parseable.com/blog/what-is-high-cardinality)）。

### 2.4 远端写入、云账单和多租户平台成本上升

如果使用 remote_write 到 Grafana Cloud、Mimir、Cortex、VictoriaMetrics、Azure Managed Prometheus 或其他后端，高 churn 不仅影响本地 Prometheus，还会增加远端写入带宽、远端存储、压缩和查询成本。Azure Monitor workspace 对 Managed Prometheus 和 OpenTelemetry metrics 按 ingest samples、query samples processed 等维度计费，并且 Prometheus 数据保留 18 个月；高 churn 会显著提高样本摄取和查询处理规模（[Microsoft Azure, n.d.](https://azure.microsoft.com/en-us/pricing/details/monitor/)）。

### 2.5 数据质量和语义风险

盲目删除标签可能导致多条原本不同的序列合并成相同 label set。Prometheus 不支持同一时间戳下重复时间序列；如果删除了唯一标识标签，而没有先聚合，可能造成冲突、丢样或错误语义。例如两个进程指标：

```text
host_process_cpu_seconds_total{pid="101",name="worker"}
host_process_cpu_seconds_total{pid="102",name="worker"}
```

如果直接删除 `pid`，二者会变成同一序列，Prometheus 无法安全表达“两个 worker 进程各自 CPU 使用量”。因此治理 churn 不能简单等同于“删除所有高基数标签”，而应区分可安全聚合、可丢弃和必须保留的标签（[OneUptime, 2026](https://oneuptime.com/blog/post/2026-07-31-high-cardinality-host-labels/view)）。

## 3. 常见根因：从指标设计到服务发现

| 根因类别 | 典型示例 | 影响机制 | 治理优先级 |
|---|---|---|---|
| 无界业务标签 | `user_id`、`session_id`、`request_id`、`device_id` | 每个新值生成新 series | 最高 |
| 原始路径和 URL | `/users/123/orders/456`、带 query string URL | 动态 path segment 放大路由维度 | 最高 |
| Kubernetes 临时身份 | `pod`、`pod_uid`、`container_id`、Pod IP | Pod 重建导致历史 series 不断累积 | 高 |
| 服务发现标签误提升 | `__meta_kubernetes_pod_uid`、所有 cloud tags | target label 附加到所有样本，放大全量指标 | 高 |
| Exporter 过度暴露 | Node exporter、MySQL exporter、大量设备/挂载/进程指标 | 默认指标量大且含设备、进程、mount 维度 | 中高 |
| 指标名嵌入值 | `http_200_count`、`user_123_latency` | metric name 数量异常膨胀 | 中高 |

Grafana 的 Kubernetes cardinality 研究指出，`session_id`、`user_id`、`device_id` 等随机或无上限标签，会在流量上升时导致时间序列爆炸；同时，很多 exporter 默认输出大量指标，Node exporter 默认约 500 条时间序列，MySQL exporter 约 1,000 条时间序列，并非全部都有业务价值（[Grafana Labs, 2022](https://grafana.com/blog/how-to-manage-high-cardinality-metrics-in-prometheus-and-kubernetes/)）。

New Relic 也强调，Kubernetes service discovery 如果配置不当，可能把 host IP、Pod UUID、Pod name 等高变化标签暴露为持久标签，这些标签日常监控价值有限，却会显著增加成本（[New Relic, 2024](https://newrelic.com/blog/observability/manage-prometheus-cardinality)）。

## 4. 诊断体系：先量化，再治理

### 4.1 使用 Prometheus 内置 TSDB API

Prometheus 提供 `/api/v1/status/tsdb`，可查看当前 head series 数、按 metric name 的 series 数、label value 数、昂贵 label-value pair、按 label name 估算的内存等。该 API 应优先用于 cardinality 探查，避免一开始就在大型 Prometheus 上执行宽范围 PromQL 扫描导致额外压力（[Parseable, n.d.](https://www.parseable.com/blog/prometheus-cardinality)）。

常用 PromQL 示例：

```promql
# 找出 series 数最多的 metric
topk(20, count by (__name__) ({__name__=~".+"}))

# 按 job 查看 cardinality
topk(20, count by (job) ({__name__=~".+"}))

# Prometheus head 活跃序列数
prometheus_tsdb_head_series
```

在大规模实例上，应按 `job`、`namespace`、metric prefix 缩小查询范围，避免对全索引造成压力（[Parseable, n.d.](https://www.parseable.com/blog/prometheus-cardinality)）。

### 4.2 使用 promtool tsdb analyze 离线分析

`tsdb analyze`，后续并入 `promtool tsdb analyze`，可以直接读取 TSDB block 索引，分析 churn 和 cardinality，而不通过 PromQL 扫描 live samples。输出会指出 churn 最多的 label pair、label name、最常见 label pair、高基数 label、高基数 metric name 等，适合定位具体 job、instance、metric 或 label（[Brazil, 2019](https://www.robustperception.io/using-tsdb-analyze-to-investigate-churn-and-cardinality)）。

该工具尤其适合回答两个问题：

- 是哪一批 label pair 在 churn？
- 是哪个 metric name 的 series 数异常高？

如果 `__name__` 数量达到数万甚至更多，往往意味着本应作为 label 的值被嵌入了 metric name（[Brazil, 2019](https://www.robustperception.io/using-tsdb-analyze-to-investigate-churn-and-cardinality)）。

### 4.3 持续监控关键指标

容量规划应持续跟踪：

| 指标 | 含义 | 用途 |
|---|---|---|
| `prometheus_tsdb_head_series` | head 中活跃 series | 内存压力核心指标 |
| `prometheus_tsdb_head_series_created_total` | 创建过的 series 数 | churn 速度 |
| `scrape_samples_scraped` | 每次 scrape 样本数 | exporter 或采集爆炸 |
| `prometheus_tsdb_symbol_table_size_bytes` | symbol table 内存 | label/name 字符串压力 |
| `prometheus_tsdb_blocks_loaded` | 加载 block 数 | 查询和 compaction 压力 |
| `prometheus_target_scrapes_exceeded_sample_limit_total` | 超过 sample limit 次数 | 防护阈值触发 |

Last9 建议将 head series、symbol table、blocks loaded、compactions 等作为容量规划指标，因为 series 数、block 数和 compaction 行为共同决定内存、磁盘和查询性能（[Last9, n.d.](https://last9.io/blog/prometheus-data-retention/)）。

## 5. 系统性解决方案：从源头到架构

### 5.1 第一原则：先降基数和 churn，再扩展架构

Prometheus 官方定位是可靠的单节点监控系统：每个 server 本地 scrape 和存储数据，默认不依赖分布式存储，适合运维监控，但不适合要求 100% 精确的逐请求计费等场景（[Prometheus Authors, n.d.](https://prometheus.io/docs/introduction/overview/)）。因此，当 churn 过高时，直接“加机器”或“上分布式后端”只是推迟问题，不能修正坏标签设计。

我的判断是：**治理顺序必须是：指标建模治理 → scrape/ingestion 过滤 → 聚合降维 → 预算和告警 → 分片/远端存储。** 如果跳过前四步直接上 Thanos、Mimir 或 VictoriaMetrics，很可能只是把本地 OOM 问题转化为更高的云账单和更复杂的查询性能问题。

### 5.2 指标设计：限制无界标签

应禁止或严格审查以下标签进入 metrics：

- `user_id`
- `request_id`
- `session_id`
- `trace_id`
- `container_id`
- `pod_uid`
- `filename`
- `timestamp`
- 原始 URL path
- 邮箱、手机号、信用卡号等 PII

这些信息若有诊断价值，应进入 logs 或 traces；metrics 只保留稳定、可聚合、低基数维度，如 `service`、`namespace`、`deployment`、`region`、`env`、`status_class`、标准化 route 等（[Middleware, n.d.](https://middleware.io/blog/prometheus-data-cardinality/)）。

对 HTTP 指标，应把 `/users/123/orders/456` 规范化为 `/users/:id/orders/:id`，并去掉 query string。Parseable 明确建议在 instrumentation 阶段完成路由标准化，而不是等数据进入 TSDB 后再查询过滤（[Parseable, 2026](https://www.parseable.com/blog/what-is-high-cardinality)）。

### 5.3 Scrape 与 relabel：在进入 TSDB 前过滤

Prometheus 有三个常见 relabel 阶段：

| 阶段 | 配置 | 作用 | 能节省本地 TSDB 成本吗 |
|---|---|---|---|
| target relabel | `relabel_configs` | scrape 前选择 target、提升或删除 discovery label | 是 |
| metric relabel | `metric_relabel_configs` | scrape 后、本地 ingest 前过滤样本或标签 | 是 |
| write relabel | `write_relabel_configs` | 本地写入后，remote_write 前过滤 | 否，仅节省远端成本 |

如果只在 `write_relabel_configs` 过滤，仍会消耗本地 scrape parsing、head memory、WAL 和本地 TSDB 存储。因此，想降低 Prometheus 本地压力，应优先使用 exporter 配置、`relabel_configs` 和 `metric_relabel_configs`（[OneUptime, 2026](https://oneuptime.com/blog/post/2026-07-31-high-cardinality-host-labels/view)）。

示例：远端写入时丢弃某个 metric family：

```yaml
remote_write:
  - url: https://example/api/prom/push
    write_relabel_configs:
      - source_labels: [__name__]
        regex: "thanos_objstore_bucket_operation_duration_seconds_bucket"
        action: drop
```

Grafana Cloud 文档提供了类似示例，用于停止向 Grafana Cloud remote_write 某个高成本 metric，但该方式不会降低本地 Prometheus 成本（[Grafana Labs, 2023](https://grafana.com/blog/identify-unused-costly-metrics-with-cardinality-management-dashboards-in-grafana-cloud/)）。

### 5.4 聚合、Recording Rules 与 Streaming Aggregation

Recording rules 可以生成预聚合指标，提高查询速度，但它们是在原始数据已经写入数据库之后再计算，并会把聚合结果写回数据库，所以不减少原始数据的存储成本。VictoriaMetrics 的 stream aggregation 则在数据进入远端存储前完成聚合，只保存后续真正查询的低基数数据，因此可同时减少样本数和 series 数（[VictoriaMetrics, n.d.](https://victoriametrics.com/blog/reducing-costs-p2/)）。

例如，对 `grpc_server_handled_total` 按 2 分钟窗口聚合，并去掉 `grpc_method`：

```yaml
- match: "grpc_server_handled_total"
  interval: "2m"
  outputs: ["total"]
  without: ["grpc_method"]
```

这类方案适合已经确认不需要原始高维度明细、只需要趋势和 SLO 的指标。

### 5.5 使用 Mimirtool 和使用率分析删除无用指标

仅看高基数还不够，还要看“是否被使用”。Mimirtool 可以分析 Grafana dashboards、Prometheus rule files，并与 Prometheus、Mimir 或 Grafana Cloud 中实际存在的 metrics 对比，输出 used 与 unused metrics。示例研究中，一个默认 Kubernetes 环境只有 270/1377 个 metric 被使用，约 80% 被抓取指标从未用于 dashboard 或 rules（[Calvert, 2023](https://0xdc.me/blog/how-to-find-unused-prometheus-metrics-using-mimirtool/)）。

这说明治理应优先处理“两高一低”指标：**高基数、高成本、低使用价值**。Grafana Cloud 的 Cardinality Management dashboards 将 metric 标记为 used/unused，并结合 dashboard、alert、recording rule 和最近 30 天查询日志判断是否使用，适合托管环境成本治理（[Grafana Labs, 2023](https://grafana.com/blog/identify-unused-costly-metrics-with-cardinality-management-dashboards-in-grafana-cloud/)）。

### 5.6 设立 Cardinality Budget 与准入治理

建议为每个 scrape job 或团队设定：

- 每 target 期望 series 数；
- 每 target 最大 series 数；
- 新 series 速率上限；
- 允许提升的 target labels；
- exporter collector allowlist；
- 设备、mount、process 标签规则；
- 例外审批和 owner。

Prometheus 的 `sample_limit`、`label_limit`、`label_name_length_limit`、`label_value_length_limit` 可以作为 guardrail，但它们不是截断机制；超过限制时整个 scrape 会失败。因此应结合 `up == 0`、scrape duration、sample count、head series 和 rule failures 告警使用，而不是作为主要治理手段（[OneUptime, 2026](https://oneuptime.com/blog/post/2026-07-31-high-cardinality-host-labels/view)）。

### 5.7 架构扩展：分片、联邦与远端存储

Prometheus 默认不是水平扩展系统。推荐路径是：先减少 cardinality，再按 cluster/team/service 做功能分片；需要全局聚合视图时使用 federation；需要长期存储和全局原始查询时使用 Thanos、Mimir/Cortex 或 VictoriaMetrics（[Oodle, 2026](https://blog.oodle.ai/scaling-prometheus-from-single-node-to-enterprise-grade-observability/)）。

| 方案 | 适用场景 | 优点 | 局限 |
|---|---|---|---|
| 功能分片 | 单 Prometheus 超载 | 简单、保持 Prometheus 模型 | 跨分片查询不方便 |
| Federation | 汇总核心指标 | 适合聚合视图 | 不适合全量原始数据查询 |
| Thanos | 已有多 Prometheus，需要统一查询和对象存储 | 改造相对小，长期存储强 | 组件多，长范围查询仍可能慢 |
| Mimir/Cortex | 多团队、多租户、集中平台 | 水平扩展、多租户、限额 | 运维复杂 |
| VictoriaMetrics | 想要更简单高性能远端存储 | 部署相对简单、资源效率好 | 多租户能力取决于版本和架构 |

Federation 适合抓取精选或预聚合 series 到上层 Prometheus，但不是集中式原始数据查询或长期存储的替代品；随着 federated series 增加，它也会带来 scrape delay 和额外运维负担（[Oodle, 2026](https://blog.oodle.ai/scaling-prometheus-from-single-node-to-enterprise-grade-observability/)）。

## 6. 各家云厂商和平台是否有现有方案？

### 6.1 Azure Monitor Managed Service for Prometheus

Azure 提供 Azure Monitor managed service for Prometheus，支持 Prometheus 数据进入 Azure Monitor workspace，并可用于 AKS、Arc-enabled Kubernetes、AWS EKS、GCP GKE 等多云集群，非 Azure 集群可以通过 Prometheus remote write 发送数据（[Microsoft, n.d.](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/best-practices-multicloud)）。

Azure 的重要特点：

- Prometheus 数据保留 18 个月；
- 有 ingestion limits 和 quotas，触达限制可能 throttling；
- metric name、label name、label value 和每条 series label 数都有约束；
- 与开源 Prometheus 不同，Azure Managed Prometheus 对 metric names、label names、label values **大小写不敏感**；
- label name 最长 511 字符，label value 最长 1023 字符，每条 series 最多 63 个 label，metric name 最长 511 字符；某些违规会导致整个 scrape job 失败，metric name 过长则只丢弃该 series（[Microsoft, 2025](https://learn.microsoft.com/en-us/azure/azure-monitor/metrics/prometheus-metrics-details)）。

这意味着 Azure 有明确平台防护，但治理高 churn 仍需用户控制标签和采集策略。Azure 更适合已经使用 AKS、Azure Monitor、Azure Arc 和 Managed Grafana 的组织。

### 6.2 Grafana Cloud / Grafana Mimir

Grafana Cloud 底层使用 Mimir 架构，提供 Cardinality Management dashboards、Usage column、Adaptive Metrics 等成本治理能力。它不仅能展示高 cardinality metrics 和 labels，还能判断 metrics 是否用于 dashboards、alerts、recording rules 和最近 30 天查询，从而识别高成本但未使用指标（[Grafana Labs, 2023](https://grafana.com/blog/identify-unused-costly-metrics-with-cardinality-management-dashboards-in-grafana-cloud/)）。

Mimir OSS/GEM 还可启用 cardinality analysis API，通过 `/prometheus/api/v1/cardinality/label_names` 和 `/prometheus/api/v1/cardinality/label_values` 支撑 Grafana dashboard 展示；社区实践使用 JSON API datasource 访问这些接口重建 cardinality dashboard（[Grafana Mimir Community, 2023](https://github.com/grafana/mimir/discussions/4590)）。

Grafana 生态的优势在于“发现高成本 + 判断使用价值 + 自动聚合建议”相对完整，适合多团队平台和成本治理成熟的企业。

### 6.3 AWS Managed Service for Prometheus

AWS AMP 是 serverless 托管 Prometheus 兼容服务，底层基于 Cortex，提供水平扩展存储和 PromQL 查询能力，常与 Amazon Managed Grafana 配合使用（[Logz.io, n.d.](https://logz.io/blog/comparing-prometheus-managed-services/)）。它适合 AWS 原生环境和需要托管 Prometheus 后端的团队。

但 AMP 更多解决运行和扩展问题，并不天然解决 bad labels。若 remote_write 前不做 relabel、过滤或聚合，高 churn 仍会进入托管后端并体现在成本和查询压力上。

### 6.4 Google Cloud Managed Service for Prometheus

Google Cloud Managed Service for Prometheus 使用 Prometheus 兼容接口和 PromQL Query API，并把数据存储在 Google Monarch 中，支持混合云和多云 workload，文献提到可保留 24 个月（[Logz.io, n.d.](https://logz.io/blog/comparing-prometheus-managed-services/)）。GMP 适合 GKE 和 Google Cloud 体系。

与 Azure、AWS 类似，GMP 降低了后端运维复杂度，但用户仍需在采集侧控制动态标签和高 churn。

### 6.5 Alibaba Cloud Managed Service for Prometheus

阿里云 Managed Service for Prometheus 是全托管、Prometheus 兼容服务，支持 PromQL、exporters、dashboards、alerts、ServiceMonitor/PodMonitor，并可通过 remote write 集中自建 Prometheus 数据。其产品能力包括 metric management 工具识别高基数 series、Recording Rules 做降采样和降维、全局视图跨实例和跨账号查询、标准存储和归档存储分层（[Alibaba Cloud, n.d.](https://www.alibabacloud.com/help/en/arms/prometheus-monitoring/product-overview/what-is-prometheus)）。

阿里云还支持云服务指标接入，并会将实例 ID、实例名、resource group、region、zone、namespace、product 等元数据作为 labels 添加到指标中；自定义 tag 前缀 `o11y.aliyun.dev/` 也会转为 label（[Alibaba Cloud, n.d.](https://www.alibabacloud.com/help/en/prometheus/cloud-service-observable)）。这一能力便于云资源定位，但也意味着 tag 治理非常重要：如果把高度动态或无边界 tag 转为 label，同样会导致 cardinality 增长。

### 6.6 New Relic、VictoriaMetrics 与其他方案

New Relic 提供 cardinality 管理思路，包括通过 scrape job 评估、labeldrop、drop datapoints、长短期聚合策略减少成本，并指出 Kubernetes service discovery 要避免暴露 pod UUID、host IP 等无用高变化标签（[New Relic, 2024](https://newrelic.com/blog/observability/manage-prometheus-cardinality)）。

VictoriaMetrics 提供 Cardinality Explorer、vmagent stream aggregation、vmestimator 等能力。vmestimator 可在采集点从 incoming stream 估算全局 cardinality、按 metric/job/tenant cardinality、churn rate 和长期趋势，用于容量规划和告警（[VictoriaMetrics, n.d.](https://victoriametrics.com/blog/vmestimator-announcement/)）。这类工具的价值在于把 cardinality 观测前移到 ingestion pipeline，而不是等 Prometheus 已经 OOM 后再分析。

## 7. 推荐落地路线图

### 阶段一：建立现状基线

1. 拉取 `/api/v1/status/tsdb`；
2. 记录 `prometheus_tsdb_head_series`、`head_series_created_total`、`scrape_samples_scraped`；
3. 用 `promtool tsdb analyze` 分析最新 blocks；
4. 用 `topk(count by (__name__))` 找最贵 metric；
5. 按 `job`、`namespace`、`team` 做成本归属。

### 阶段二：分类治理

将 metric 分为四类：

| 类型 | 处理策略 |
|---|---|
| 高基数且未使用 | 优先 drop 或禁用 exporter collector |
| 高基数但重要 | 聚合、标准化 label、缩短保留或迁移至 traces/logs |
| 低基数且重要 | 保留 |
| 低基数但未使用 | 延后处理，避免过度优化 |

### 阶段三：从采集侧修复

- 禁止 `request_id`、`user_id`、`session_id` 进入 metrics；
- route 规范化；
- 不提升 Pod UID、container ID、全量 cloud tags；
- `metric_relabel_configs` 在本地 ingestion 前 drop 无用 metric；
- `write_relabel_configs` 控制远端成本；
- 对 exporter 使用 collector allowlist；
- 对 Kubernetes ServiceMonitor/PodMonitor 做模板化审查。

### 阶段四：组织治理

- PR 模板加入 metrics label review；
- 每个团队有 series budget；
- 每周输出 high-cardinality 和 unused metrics 报告；
- 对超过预算的 job 告警；
- 将高基数上下文转移到 logs/traces，并使用 exemplars 关联 traces。

### 阶段五：架构扩展

只有在完成前述治理后，才考虑：

- 按团队/集群分片 Prometheus；
- 用 federation 汇聚少量聚合指标；
- 用 Thanos 做长期存储和统一查询；
- 用 Mimir/Grafana Cloud 做多租户平台；
- 用 VictoriaMetrics 简化远端存储与聚合。

## 8. 结论

Prometheus 高流失率的核心影响不是“指标多一点”这么简单，而是会同时推高 **内存、WAL、磁盘、索引、compaction、remote_write、查询扇出、dashboard latency、告警延迟和云账单**。在 Kubernetes 和多云环境中，churn 往往来自动态标签和服务发现标签误提升，而不是业务规模本身。

本报告的明确判断是：**系统性解决方案必须以“减少进入 TSDB 的无价值新序列”为中心，而不是以“更大后端”作为第一反应。** 托管 Prometheus、Mimir、Thanos、VictoriaMetrics、Azure、AWS、GCP、阿里云、Grafana Cloud 都提供了不同程度的扩展、保留、查询和分析能力，但没有任何厂商能自动理解哪些标签对你的业务有价值。云平台可以承接规模，不能替代指标治理。

对于已经遇到 Prometheus churn 的组织，最有效路径是：先用 TSDB API、promtool、Mimirtool 或云厂商 cardinality dashboard 找到“高成本、低价值”指标；再在 instrumentation、scrape、metric relabel、remote_write 和聚合层逐步治理；最后再根据组织规模选择托管或分布式后端。

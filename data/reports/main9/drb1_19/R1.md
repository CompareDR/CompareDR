# Prometheus 高时间序列流失率（High Series Churn）影响、诊断与系统治理研究报告

## 执行摘要

Prometheus 中的 **high series ****churn（高时间序列流失率）**，指持续、大量地创建新的 label-set 时间序列，并在较短时间内停止更新或被移出 Head 的现象。它与 high cardinality（高基数）相关，但不是同一问题：**cardinality ****描述“同时存在多少条序列”，churn** **描述“序列集合变化得有多快”**。因此，一个系统可能只有几十万 active series，却因为 Pod、UUID、request ID、动态 URL、任务 ID 等标签每几分钟整体换一批，产生极高 churn；反过来，一个存在几百万条稳定、长期存活序列的环境可以具有高 cardinality 但相对较低 churn。Prometheus 官方没有给出统一的 “high churn” 数值阈值，因此本文建议将 churn 归一化为“单位时间新建 series 数 / active series 数”，并结合自身历史基线判断。Prometheus 当前直接暴露 prometheus_tsdb_head_series_created_total、prometheus_tsdb_head_series_removed_total、prometheus_tsdb_head_series 等指标，可直接用于这一衡量。[[1]](https://github.com/prometheus/prometheus/blob/main/tsdb/head.go)

高 churn 的问题不只是“磁盘多写一点”。它会持续创建 Head 中的 series metadata、symbol/postings/index 状态及 WAL series records，同时增加 Head GC、WAL checkpoint/truncation、block index 与 compaction 的工作；如果使用 remote_write，Prometheus 还要维护 WAL series ID 到 labels 的缓存，官方文档明确指出 **大量**** series churn ****会显著增加**** remote_write ****内存使用**。Remote write 本身通常就会使 Prometheus 内存增加约 25%，具体幅度取决于数据形状。[[2]](https://prometheus.io/docs/practices/remote_write/)

最重要的结论是：**迁移到托管**** Prometheus ****并不会自动消除**** churn。** AWS AMP、Google Managed Service for Prometheus、Azure Managed Prometheus、阿里云、腾讯云、华为云等可以把存储、扩容、HA 和长期保留的运维责任转移给云厂商，但输入端的 label 设计、短生命周期 workload、采集频率以及“哪些指标应该进入系统”的治理责任仍主要属于用户。AWS AMP 会自动扩展 workspace 的 active-series capacity 并提供限流；Azure 有 active-series 与 ingestion quota；Google 按 sample ingestion 计费并提供 metric relabeling；阿里云支持 Agent HPA；腾讯云有 Series、单指标维度组合与查询限制。这些能力主要是**吸收或限制**** churn ****的后果，而不是修复**** churn ****的根因**。[[3]](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP_quotas.html)

建议的优先级是：

- **先治理**** source cardinality ****与**** churn ****标签**：禁止 request_id、UUID、timestamp、完整 URL、Pod UID、容器 ID、query ID 等无界或快速变化维度进入常规 metrics label。

- **再治理**** ingestion**：通过 metric_relabel_configs、指标 allowlist、sample_limit、label_limit、scrape interval 和 remote-write filter 限制输入。

- **建立**** churn SLO**：持续观测 created/removed series rate、normalized churn、Head series、WAL 增长、remote-write backlog、compaction 与查询 latency。

- **大规模环境使用隔离与**** admission control**：按 cluster/team/tenant 分片，实施 series budget、samples/s budget、每目标 series budget。

- **长期存储或托管平台只解决** **scalability，不替代治理**；若需要后端原生的 cardinality/churn guardrail，VictoriaMetrics 与 Grafana Mimir 在这方面提供了比单体 Prometheus 更直接的限制机制。VictoriaMetrics 原生支持 hourly/daily unique-series limiter，其中 daily limiter 明确面向 daily churn；Mimir 支持 per-tenant ingestion 和 active-series limits。[[4]](https://docs.victoriametrics.com/victoriametrics/)

## 定义、区别与常见根因

Prometheus 的一条 time series 由 metric name 和完整 label set 唯一确定；任何 label value 变化都会形成一条新的 series。Prometheus 官方 instrumentation best practices 明确指出每一个 label set 都带来 RAM、CPU、磁盘和网络成本，并建议绝大多数 metric 不使用 label；对于单个 metric，如果 cardinality 已经可能达到 100 以上，应该认真评估是否应减少维度或把该分析转移到更适合的系统。这个“100”是针对单 metric 标签维度的经验建议，不是 whole-Prometheus 的 series 上限。[[5]](https://prometheus.io/docs/practices/instrumentation/)

**High cardinality** 可以定义为当前或给定活跃窗口中的 distinct label-set 数量过大，例如 prometheus_tsdb_head_series 很高。**High churn** 更适合定义成一个“速率”：

$$
{C}_{new}(T)=\frac{ \Delta SeriesCreated(T)}{T}
$$

$$
{C}_{removed}(T)=\frac{ \Delta SeriesRemoved(T)}{T}
$$

以及归一化 churn：

$$
{R}_{churn}(T)=\frac{ \Delta SeriesCreated(T)}{\overline{ActiveSeries}(T)}
$$

例如当前稳定 active series 约 2,000,000 条，但每 5 分钟新增 200,000 条新的 label-set，则 R_churn(5m)=10%。即使 active-series 总量长期维持在 200 万，这种持续替换仍然意味着 Head/WAL/index/remote-write cache 不断处理新 series。Prometheus 官方并未定义 1%、5% 或 20% 为标准阈值，因此这些阈值必须视为**治理启始值，而不是产品规格**。建议初始采用：5 分钟 churn <1% 通常正常；1–5% 观察；持续 >5% 告警；持续 >20% 视为严重；同时要求至少超过过去 7 天同期 P95 的 2–3 倍，避免自然扩缩容被误报。上述区间属于本文工程建议，官方阈值目前**未定**。Prometheus 提供 created/removed/head-series 指标，因此这一归一化方式可以直接实施。[[6]](https://github.com/prometheus/prometheus/blob/main/tsdb/head.go)

最常见根因可以归为六类。第一类是**无界**** label**，例如 user_id、request_id、trace ID、订单号、session ID、完整 URL path、SQL query ID、UUID、时间戳等。VictoriaMetrics 官方 FAQ 将 queryid、Pod 名、timestamp、hash、UUID 明确列为高 churn 常见来源；Prometheus 官方也明确警告不要使用高基数 label。[[7]](https://docs.victoriametrics.com/victoriametrics/faq/)

第二类是 **Kubernetes ****短生命周期对象**。Kubernetes/kube-state-metrics 的 Pod 指标大量包含 pod 与 uid，例如 kube_pod_info、kube_pod_status_phase、kube_pod_container_info 等。Deployment rollout、Job/CronJob、HPA、Cluster Autoscaler、spot/preemptible node、CI runner 等都持续产生新的 Pod/UID，因此即使工作负载规模不增长，也可能持续产生新 series。[[8]](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/workload/pod-metrics.md)

第三类是 **Kubernetes label/annotation ****无限制映射**。kube-state-metrics 默认提供 allowlist 机制，并明确警告对 pods=[*] 等 wildcard label/annotation 暴露存在严重性能影响，因此应采用显式 allowlist，而不是把所有业务 label 复制成 Prometheus labels。[[9]](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/developer/cli-arguments.md)

第四类是 **采集和**** relabel ****配置错误**。例如通过 labelmap 将所有 service discovery metadata 复制成指标 label，保留 pod_uid、container hash、image digest、动态 IP 等，或者错误地给每次 scrape 添加变化值。Prometheus 支持 labeldrop、labelkeep、drop、keep、hashmod 等 relabel action，同时特别提醒 labeldrop/labelkeep 后仍须保证 series 唯一性。[[10]](https://prometheus.io/docs/prometheus/3.10/configuration/configuration/)

第五类是 **应用端指标暴增**。常见模式包括 histogram bucket 数量过多、动态业务维度、每个 SQL/endpoint/entity 生成独立 metric、自动注册大量 metric name，以及错误地把日志分析问题塞进 metrics。Prometheus 的数据模型会把不同 label-set 分别作为独立 series，因此多个高基数 label 的组合是乘法关系。[[11]](https://prometheus.io/docs/practices/the_zen/)

第六类是 **Pushgateway ****生命周期管理错误**。Pushgateway 不会因为源 job 消失就自动删除其 series；Prometheus 官方明确警告 Pushgateway 会永久暴露已 push 的 series，除非显式调用删除 API。因此把 short-lived instance ID、Pod ID 或任务实例 ID 作为 grouping label 推入 Pushgateway，往往把原本“短暂 churn”变成“长期 cardinality 泄漏”。官方建议 Pushgateway 主要用于 service-level batch job，而不是常规实例监控。[[12]](https://prometheus.io/docs/practices/pushing/?from=20423&from_column=20423)

## 诊断方法、指标体系与告警

最直接的方法是监控 Prometheus 自身 TSDB 指标。当前 Prometheus Head 暴露 prometheus_tsdb_head_series、prometheus_tsdb_head_series_created_total、prometheus_tsdb_head_series_removed_total、prometheus_tsdb_head_chunks、GC 与 WAL truncation 等指标；Compactor 暴露 prometheus_tsdb_compactions_total、prometheus_tsdb_compaction_duration_seconds 等。[[13]](https://github.com/prometheus/prometheus/blob/main/tsdb/head.go)

可直接创建以下 recording rules：

```yaml
groups:
- name: prometheus-churn
  interval: 30s
  rules:
  - record: prometheus:series_created:rate5m
    expr: rate(prometheus_tsdb_head_series_created_total[5m])

  - record: prometheus:series_removed:rate5m
    expr: rate(prometheus_tsdb_head_series_removed_total[5m])

  - record: prometheus:series_churn_ratio:5m
    expr: |
      increase(prometheus_tsdb_head_series_created_total[5m])
      /
      clamp_min(avg_over_time(prometheus_tsdb_head_series[5m]), 1)

  - record: prometheus:samples_ingested:rate5m
    expr: sum(rate(prometheus_tsdb_head_samples_appended_total[5m]))

  - record: prometheus:compactions:rate1h
    expr: rate(prometheus_tsdb_compactions_total[1h])
```

基于上述 recording rule，推荐使用下列**初始告警值**；这些值是工程起点而非 Prometheus 官方阈值：

```yaml
groups:
- name: prometheus-churn-alerts
  rules:
  - alert: PrometheusHighSeriesChurn
    expr: prometheus:series_churn_ratio:5m > 0.05
    for: 15m
    labels:
      severity: warning
    annotations:
      summary: "Prometheus series churn > 5% / 5m"
      description: "过去 5 分钟新增 series 超过平均 active series 的 5%"

  - alert: PrometheusCriticalSeriesChurn
    expr: prometheus:series_churn_ratio:5m > 0.20
    for: 10m
    labels:
      severity: critical

  - alert: PrometheusRemoteWriteBacklog
    expr: prometheus_remote_storage_samples_pending > 100000
    for: 10m
    labels:
      severity: warning

  - alert: PrometheusCompactionFailures
    expr: increase(prometheus_tsdb_compactions_failed_total[15m]) > 0
    labels:
      severity: critical
```

如果 Prometheus 是自身监控 target，可以直接利用 /api/v1/status/tsdb。该接口返回 numSeries、chunk count、每 metric series count、每 label 的 distinct value count，以及 label value memory 统计；对于寻找“哪个 metric/label 在爆炸”，它通常比直接在数百万 series 上执行全局 PromQL 更安全。官方 promtool tsdb analyze 也专门支持分析 churn、label-pair cardinality 与 compaction efficiency。[[14]](https://prometheus.io/docs/prometheus/latest/querying/api/)

用于临时分析的 PromQL 可以包括：

```promql
# 当前 Head series
prometheus_tsdb_head_series

# 每秒新增 / 删除 series
rate(prometheus_tsdb_head_series_created_total[5m])
rate(prometheus_tsdb_head_series_removed_total[5m])

# 5 分钟归一化 churn
increase(prometheus_tsdb_head_series_created_total[5m])
/
avg_over_time(prometheus_tsdb_head_series[5m])

# Top metric by series count
topk(20, count by (__name__) ({__name__=~".+"}))

# namespace / job 等维度的 series 数
topk(20, count by (namespace) ({namespace!=""}))
topk(20, count by (job) ({job!=""}))

# remote write backlog
prometheus_remote_storage_samples_pending

# remote write failure / retry
rate(prometheus_remote_storage_samples_failed_total[5m])
rate(prometheus_remote_storage_samples_retried_total[5m])

# WAL truncation latency
rate(prometheus_tsdb_wal_truncate_duration_seconds_sum[15m])
/
rate(prometheus_tsdb_wal_truncate_duration_seconds_count[15m])

# compaction 频率
increase(prometheus_tsdb_compactions_total[1h])

# compaction P99
histogram_quantile(
  0.99,
  sum by (le) (rate(prometheus_tsdb_compaction_duration_seconds_bucket[15m]))
)
```

全局 count by (__name__) 在极高 cardinality 环境中本身可能成为昂贵查询，因此生产环境建议优先使用 /api/v1/status/tsdb、离线 promtool tsdb analyze，或者先限定 job/namespace。Prometheus API 官方明确提供 TSDB cardinality statistics，正是为了诊断这一类问题。[[15]](https://prometheus.io/docs/prometheus/latest/querying/api/)

建议 dashboard 至少包含以下视图：

| 面板 | 指标/计算 | 初始阈值建议 | 诊断目的 |
| --- | --- | --- | --- |
| Active Head Series | prometheus_tsdb_head_series | 对容量预算 70/85/95% | 判断 cardinality |
| New Series Rate | rate(...series_created_total[5m]) | 相对历史 P95 | 判断 churn |
| Removed Series Rate | rate(...series_removed_total[5m]) | 与 created 对比 | 判断生命周期 |
| Normalized Churn | increase(created[5m])/avg(head[5m]) | 5% warn / 20% critical* | 跨实例比较 |
| Samples/s | rate(head_samples_appended_total[5m]) | 容量预算 | 采集吞吐 |
| Chunks | prometheus_tsdb_head_chunks | 关注突变 | Head 压力 |
| WAL truncation | prometheus_tsdb_wal_truncate_duration_seconds | 基线×2–3 | WAL 压力 |
| Compaction | compactions_total, duration | 失败必须告警 | TSDB 后台压力 |
| Remote backlog | samples_pending | 持续增长告警 | remote-write 落后 |
| Process RSS | process_resident_memory_bytes | Pod limit 70/85% | OOM 风险 |
| Query latency | HTTP/query metrics | P95/P99 基线 | 用户体验 |
| Top metrics/labels | TSDB API | 周期审计 | 找 churn 源 |

* 为本文建议，不是官方硬阈值。

为了做持续治理，还应每天生成一份 series inventory，建议字段至少包括：

timestamp, cluster, tenant, namespace, job, metric_name, active_series, new_series_1h, removed_series_1h, churn_ratio, samples_per_second, distinct_pod, distinct_uid, distinct_instance, distinct_path, estimated_cost, owner_team。

这种表的核心价值不是精确计费，而是把“哪个团队新增了多少 series、哪些 label 在增长”纳入可追责的容量治理。

## Prometheus 内部机制与资源影响

Prometheus 当前数据先进入可变的 Head block，再由 WAL 提供崩溃恢复；持久化数据通常形成约 2 小时 block，随后后台 compaction 合并为更大的 immutable blocks。WAL segment 默认为 128 MB。官方文档给出的持久化样本粗略存储量约为 **1–2 bytes/sample**，并建议以 retention_seconds × samples_per_second × bytes_per_sample 估算 block sample 存储；该估算不包含 churn 所增加的 label/index/WAL 等额外开销。[[16]](https://prometheus.io/docs/prometheus/latest/storage/)

因此，churn 对各内部组件的影响不同：

| 层 | High churn 的主要影响 | 可量化方法 |
| --- | --- | --- |
| Head 内存 | 不断创建新的 series metadata、labels、postings/index entry；旧 series 在 GC 前仍产生生命周期成本 | RSS / head_series 只能作趋势；更可靠的是做 controlled Δseries 实验 |
| CPU | hashing、label intern、series insert/delete、Head GC、index/postings 更新增加 | 比较 created series/s 与 process CPU |
| WAL | 新 series 需要写 series records，短命 series 使 metadata/sample 比率变差 | WAL bytes/s、segment 增长、truncation latency |
| Head chunks | 短命 series 经常只产生很少 samples/chunk，降低 chunk 利用率 | head_chunks / head_series、chunk creation rate |
| Index | 同一时间窗产生更多 distinct label sets 与 symbols/postings | TSDB status label cardinality |
| Compaction | 更多短 series 进入 block index，需要读取、重写和合并更多 index metadata | compaction CPU/duration、block size |
| Remote write | series-ID→labels cache 增长，queue 内存与网络开销上升 | pending samples、shards、RSS |
| Query | selector 命中更多 series/postings；聚合需要处理更多 label sets | query P95/P99、samples touched |
| 成本 | sample-based 平台主要由 sample 数决定；active-series 计费平台则同时受 active series/DPM 影响 | samples/s、active series、DPM |

Remote write 是 churn 尤其敏感的地方。Prometheus 官方说明 remote write 从 WAL 读取并进入 sharded queue；每个 WAL series 需要在 remote-write 层缓存 series ID 到 label set 的映射，因此 series churn 会显著扩大内存。官方还指出 remote write 常见内存增幅大约 25%，但高度依赖数据形状；每 shard 内存近似与 shards × (capacity + max_samples_per_send) 成正比。[[17]](https://prometheus.io/docs/practices/remote_write/)

可以用以下方法做容量估算。假设：

- active series = 2,000,000

- scrape interval = 15s

- 普通 sample 采样速率约 = 2,000,000 / 15 ≈ 133,333 samples/s

- 采用 1.5 bytes/sample 作为 block payload 中间估算值

则纯样本压缩体积约：

$$
133333 \times 86400 \times 1.5 \approx 17.3 GB/day
$$

这只是 Prometheus 官方 1–2 bytes/sample 公式的 sample payload 估算，不包含 WAL、index、symbols、filesystem overhead、临时 compaction 双份空间和 remote-write 开销。[[16]](https://prometheus.io/docs/prometheus/latest/storage/)

如果这 200 万 active series 每 5 分钟有 10% 被新 series 替换，则每 5 分钟产生约 20 万新的 label-set，即约 667 new series/s；两小时内理论累计创建约 480 万新 series identity。即使 active-series gauge 仍稳定在约 200 万，系统实际处理过的 distinct series 数已经远大于 static-cardinality 环境。这就是为什么**只看** **prometheus_tsdb_head_series** **会漏掉**** churn ****问题**。

内存不能用一个固定“每 series X KB”公式可靠预测，因为 label 数量/长度、chunk 数、histogram 类型、版本、remote-write、Go allocator 和 query workload 都会改变真实占用。更安全的做法是 staging 上做阶梯压测，记录：

$$
MemoryPerIncrementalSeries=\frac{RS{S}_{2} - RS{S}_{1}}{ActiveSerie{s}_{2} - ActiveSerie{s}_{1}}
$$

然后再乘以 1.5–2.0 的安全系数用于生产规划。官方 TSDB status 还提供 label-value memory 字节统计，可用于找超长 label。[[15]](https://prometheus.io/docs/prometheus/latest/querying/api/)

## 系统性治理、配置与落地路线

治理必须从**指标语义**开始，而不是先调大 Prometheus 内存。指标 label 应当是数量可控、长期稳定且能够用于聚合的维度；实体 ID、请求 ID、trace ID、完整 URI、时间戳、随机 hash 等应该进入日志或 trace，而不是常规 metric label。对 Kubernetes，可保留 cluster/namespace/workload/service 等稳定维度，而将 pod_uid/container_id/image_id 仅保留到确实需要的少数指标。Prometheus 与 kube-state-metrics 官方都建议限制 label cardinality/allowlist。[[18]](https://prometheus.io/docs/practices/instrumentation/)

采集端首先使用 metric_relabel_configs：

```yaml
scrape_configs:
- job_name: kubernetes-pods
  scrape_interval: 30s

  sample_limit: 50000
  label_limit: 30

  metric_relabel_configs:

  # 删除明确无价值的高 churn label
  - action: labeldrop
    regex: 'pod_uid|container_id|request_id|trace_id|session_id'

  # 丢弃调试/实验指标
  - source_labels: [__name__]
    regex: 'debug_.*|experimental_.*'
    action: drop

  # 对含动态数字 ID 的 URL 进行规范化
  - source_labels: [path]
    regex: '/api/users/[0-9]+/orders/[0-9]+'
    target_label: path
    replacement: '/api/users/:id/orders/:id'
    action: replace
```

Prometheus 官方支持 sample_limit 和 label_limit；其中 sample_limit 是 **单次**** scrape ****在**** metric relabel ****后允许接收的样本数**，超过后整次 scrape 会视为失败，因此不能把它当成“悄悄截断前 N 条”的 limiter。Metric relabel 在 ingestion 之前执行，可以直接删除昂贵 series。[[19]](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)

对 remote write，再做第二层出口过滤：

```yaml
remote_write:
- url: https://metrics.example.com/api/v1/write
  name: central-metrics

  write_relabel_configs:
  - source_labels: [__name__]
    regex: 'go_.*|process_.*'
    action: drop

  queue_config:
    capacity: 20000
    max_samples_per_send: 5000
    max_shards: 20
```

Prometheus 官方明确支持 write_relabel_configs 在 remote-write 之前过滤样本，并建议 capacity 通常保持为 max_samples_per_send 的约 3–10 倍；max_shards 不宜为了追赶 backlog 无限制调高，因为会同时扩大远端压力与本地内存。[[20]](https://prometheus.io/docs/prometheus/3.12/configuration/configuration/)

对于必须保留高基数 raw metrics、但大多数查询只需要业务聚合值的场景，可以在本地先用 recording rules 聚合：

```yaml
groups:
- name: http-preaggregate
  interval: 30s
  rules:
  - record: service:http_requests:rate5m
    expr: |
      sum by (cluster, namespace, service, method, status_class) (
        rate(http_requests_total[5m])
      )

  - record: service:http_request_duration:p95_5m
    expr: |
      histogram_quantile(
        0.95,
        sum by (cluster, namespace, service, le) (
          rate(http_request_duration_seconds_bucket[5m])
        )
      )
```

随后 remote write 只发送 recording-rule 输出，而 raw high-cardinality 数据在本地仅保留数小时用于故障定位。这比把所有 raw series 长期写入中心系统通常更经济。

Pushgateway 不应用来“解决” Kubernetes churn。对于机器/实例级 batch job，Prometheus 官方更建议 Node Exporter textfile collector；Pushgateway 只适合生命周期与具体实例解耦的 service-level batch job，并应建立 delete 生命周期。[[21]](https://prometheus.io/docs/practices/pushing/?from=20423&from_column=20423)

Mimir 支持 per-tenant sample ingestion rate、burst 与 active-series/global-series limits，因此更适合做真正的 multi-tenant admission control。VictoriaMetrics 则提供 -storage.maxHourlySeries 和 -storage.maxDailySeries，官方明确指出 daily unique-series limit 可用于限制 daily churn；超过后新的 series samples 会被丢弃，并有专门 metrics 可监控。[[4]](https://docs.victoriametrics.com/victoriametrics/)

> 0.9

落地建议分三阶段：

| 阶段 | 任务 | 验收指标 | 回滚条件 |
| --- | --- | --- | --- |
| 小规模验证 | 选一个高 churn namespace；建立 churn dashboard；只做 labeldrop/metric drop shadow analysis | new series rate ↓30%+；关键 dashboard/alerts 无缺失 | 任一 SLO/告警关键指标缺失 |
| 试点 | 10–20% cluster；启用 metric allowlist、scrape interval 分级、recording rules、remote-write filter | churn ↓50%；Head RSS ↓20%+；remote backlog 不增长；费用下降 | 数据缺失 >1%；告警漏报；P99 query 退化 |
| 全量推广 | GitOps 化治理、team budget、CI lint、tenant isolation、周期审计 | churn 与 cost 均进入预算；异常 15 分钟内发现；owner 可定位 | 大规模 false-positive 或 SLO 监控完整性下降 |

这里的百分比属于实施目标建议，而不是 Prometheus 官方保证。为了降低发布风险，应优先 **drop ****标签而不是**** drop metric**，并用 7–14 天 shadow dashboard 比较治理前后查询结果，再逐步扩大覆盖面。

持续治理责任应明确：应用团队负责 metric semantic 与 label bound；平台团队负责 scrape/relabel/budget；SRE 负责 TSDB SLO 与容量；FinOps 负责 samples/active-series 成本；安全/架构委员会负责高基数标签准入规范。Prometheus 配置应纳入 CI，可自动检查禁止 label 名、histogram bucket 数量、metric allowlist 和 ServiceMonitor/PodMonitor 是否带 wildcard。

AWS 的一个关键特点是 active-series quota 会根据最近使用量自动扩容：低于 5M 时 capacity 可约按实际使用的两倍调整，高于 5M 时增加约 10M buffer，默认最多 50M active series；突发超越历史 baseline 仍可能被 throttle。也就是说 AWS 能较好吸收“缓慢增长”，但极端 churn/突发 series explosion 仍可能触发限流和 DiscardedSamples。[[23]](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP_quotas.html)

Google GMP 对成本治理较透明：官方明确建议通过 fewer targets 和 metric relabeling 降低采集量，并给出 kube-state-metrics allowlist 的例子；公开示例显示在一个新的三节点集群中，一个精简过滤规则可减少约 125 samples/s。[[40]](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/cost-controls)

Azure 的差异化能力是 **minimal ingestion profile**：默认 target 可以只收集默认 dashboards、recording rules 和 alerts 所需指标，再通过 keep-list 逐步增加，因此它从“默认值”层面比完全采集所有 exporter metric 更偏向 cost/cardinality control。[[41]](https://learn.microsoft.com/azure/azure-monitor/containers/prometheus-metrics-scrape-configuration)

阿里云的 Agent HPA 会根据采集规模和 worker 内存扩容，文档说明 worker 内存超过约 60% 时进行抓取任务重分配与副本扩容；但这是 collector scalability 机制，不会让动态 label 的 churn 消失。[[42]](https://help.aliyun.com/zh/prometheus/developer-reference/hpa-for-prometheus-agents)

腾讯云已经提供较明确的存储侧 guardrail，例如 Series 上限、单 metric 维度组合 10 万以及单查询 series/data 上限，同时支持 metric_relabel_configs。这有助于阻断 cardinality explosion，但如果触发限制，结果可能是数据被拒绝或查询受限，因此治理仍应在采集前完成。[[43]](https://cloud.tencent.com/document/product/1416/113553)

Thanos 更适合“已有大量 Prometheus、希望长期存储和统一查询”的组织。其 Compactor 会对 object storage 中的 block 做合并和 downsampling，当前文档说明超过约 40 小时的数据可生成 5m resolution，超过约 10 天可生成 1h resolution；但 downsampling 优化的是长期查询成本，不会降低初始 ingestion churn。[[44]](https://thanos.io/tip/components/compact.md/)

| 约束 | 首选方向 | 原因 |

| 500k–数百万，Kubernetes 为主 | 云厂商 Managed Prometheus | 减少 TSDB/HA 运维 |
| 多云、统一 PromQL | Grafana Cloud / GMP / Mimir | 跨集群与多租户更成熟 |
| SaaS、多 tenant、有 noisy-neighbor 风险 | Mimir / VictoriaMetrics / Managed backend + tenant quota | 可实施 tenant limit |
| 极高 ingestion、churn 明显 | VictoriaMetrics 或 Mimir + edge aggregation | 强 limiter / 聚合机制 |
| 已有大量 Prometheus，希望长期历史 | Thanos | 复用 Prometheus，object storage |
| AWS-only | AMP | 自动扩 active-series capacity、EKS 集成 |
| Azure/AKS-only | Azure Managed Prometheus | minimal ingestion + Managed Grafana |
| 国内公有云生态 | 对应云厂商托管 Prometheus | 网络、支持、生态与计费更直接 |

## 结论、实施优先级与来源

对于**小团队**，不建议因为出现 churn 就立即部署 Mimir/Thanos。优先完成 label contract、drop 动态标签、限制 scrape metrics，并建立 series_created_rate + normalized_churn + head_series + RSS 四个核心指标。只有当单体 Prometheus 的容量和 HA 运维成为主要问题时，再迁移托管服务。

对于**企业级平台团队**，推荐把 series budget 纳入平台规范：每个 namespace/team 明确 active-series budget、new-series/hour budget 和 samples/s budget；ServiceMonitor/PodMonitor 进入 CI lint；metric-relabel policy 由 GitOps 管理；每周自动生成 top cardinality/top churn 报告。这比单纯扩大 Prometheus Pod memory 更能从根本上控制成本。

对于 **SaaS/多租户**，重点不是“Prometheus 可以存多少 series”，而是 noisy-neighbor isolation。应采用 Mimir、VictoriaMetrics Cluster、Grafana Cloud 或支持 workspace/tenant quota 的托管系统，并对 tenant 设置 ingestion、series 和 query budgets。Mimir 的 per-tenant active-series 和 ingestion-rate limit、VictoriaMetrics 的 hourly/daily series limiter 都是可直接落地的 guardrail。[[45]](https://docs.victoriametrics.com/victoriametrics/)

对于**高吞吐**** Kubernetes ****环境**，建议采用“边缘过滤/预聚合 + 中央长期存储”：cluster 内 agent 先 drop 动态 label 与无用 metrics，必要时做 stream/recording aggregation，再 remote write 到 central backend。不要把 Kubernetes 的所有 label/annotation、Pod UID 和 container ID 无条件写入长期 TSDB；kube-state-metrics 自身也建议使用 allowlist，而不是 wildcard。[[46]](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/developer/cli-arguments.md)

最终应把 churn 视作一个独立容量维度：

$$
Metrics Capacity \neq ActiveSeries
$$

而更接近：

$$
Capacity=f(ActiveSeries, NewSeriesRate, SamplesRate, LabelSize, QueryLoad, RemoteWriteLoad)
$$

**最值得优先实施的三个动作**是：建立 normalized churn dashboard 与告警；在采集端删除无界/短生命周期 label；按团队建立 series/samples budget。托管服务应作为扩大可靠性和降低运维成本的手段，而不是 high churn 的治理替代品。
